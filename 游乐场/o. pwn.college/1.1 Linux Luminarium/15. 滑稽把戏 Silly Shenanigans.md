#### Bashrc 后门

当你的 shell 启动时，它会在你的主目录中查找 `.bashrc` 文件，并将其作为*启动脚本*执行。你可以用有用的内容自定义 `/home/hacker/.bashrc`，例如设置环境变量、调整 shell 配置等。

你也可以用它来作恶！毫无戒心的受害者的 `.bashrc` 是恶作剧的常见目标。想象一下偷偷溜进朋友的电脑，在他们的 `.bashrc` 末尾添加 `echo "Hackers were here!"`。这很有趣，但同样的能力也可用于更邪恶的目的。例如，恶意软件经常针对 `.bashrc` 等启动脚本，以在未来保持持久化！

在本挑战中，我们假设你已经闯入了受害者用户的机器！该用户名为 `zardus`，主目录为 `/home/zardus`。你作为 `hacker` 用户，对他的 `.bashrc` 具有写权限，而 `zardus` 对 `/flag` 具有读权限。受害者由脚本 `/challenge/victim` 模拟，你可以随时启动该脚本以观察受害者登录计算机。你能拿到 flag 吗？

**提示：**  
就像你在 [Chaining Commands] 中探索过的脚本一样，`.bashrc` 脚本只是一个 shell 脚本。添加一行命令（例如 `echo Hello Hackers`）就会执行该命令，所以你真正需要思考的是，什么命令能让你拿到 flag！

**注意：**  
受害者的 `/home/zardus/.bashrc` 中已经有很多内容：shell 启动是一个复杂的过程。不要慌张——只需将你的载荷添加到末尾，并期待最好的结果！

#### 过度共享的目录

好吧，Zardus 已经学聪明了——他为什么要有一个可写的 `.bashrc` 呢？但更常见的情况是，同一系统上的用户为了方便协作，会将他们的主目录设为*全局可写*。这里有什么问题？

问题在于 Linux 文件/目录权限的一个微妙之处：任何对目录具有写权限的人都可以*移动*和*删除*其中的文件。例如，假设 Zardus 有一个用于协作的全局可写目录：

```console
zardus@dojo:~$ mkdir /tmp/collab
zardus@dojo:~$ chmod a+w /tmp/collab
zardus@dojo:~$ echo "do pwn.college" > /tmp/collab/todo-list
```

然后一个黑客来了，*尽管并不拥有 todo-list 文件*，却做了以下事情！

```console
hacker@dojo:~$ ls -l /tmp/collab/todo-list
-rw-r--r-- 1 zardus zardus 15 Jun  6 13:12 /tmp/collab/todo-list
hacker@dojo:~$ rm /tmp/collab/todo-list
rm: remove write-protected regular file '/tmp/collab/todo-list'? y
hacker@dojo:~$ echo "send hacker money" > /tmp/collab/todo-list
hacker@dojo:~$ ls -l /tmp/collab/todo-list
-rw-r--r-- 1 hacker hacker 18 Jun  6 13:12 /tmp/collab/todo-list
hacker@dojo:~$
```

这可能看起来违反直觉：`hacker` 对 `todo-list` 没有写权限，但最终结果是他们可以更改内容。但这样想：文件与目录的关联最终存在于目录中，而对该目录具有写权限的用户可以干扰它。当然，当重要目录全局可写时，这会有安全影响。

在本挑战中，为了方便，Zardus 开放了他的主目录：

```console
zardus@dojo:~$ chmod a+w /home/zardus
```

如你所知，该目录中有许多敏感文件，*例如 `.bashrc`*！你能利用对 `/home/zardus` 的写权限而不是 `/home/zardus/.bashrc` 来复现之前的攻击吗？

#### 棘手的链接

好吧，Zardus 已经学聪明了！不再共享主目录：尽管便利性降低，Zardus 已改为共享 `/tmp/collab`。他已将该目录设为全局可写，并开始记录一份邪恶命令清单！

```console
zardus@dojo:~$ mkdir /tmp/collab
zardus@dojo:~$ chmod a+w /tmp/collab
zardus@dojo:~$ echo "rm -rf /" > /tmp/collab/evil-commands.txt
```

在本挑战中，当你运行 `/challenge/victim` 时，Zardus 会将 `cat /flag` 添加到该命令清单中：

```console
hacker@dojo:~$ /challenge/victim

Username: zardus
Password: **********
zardus@dojo:~$ echo "cat /flag" >> /tmp/collab/evil-commands.txt
zardus@dojo:~$ exit
logout

hacker@dojo:~$
```

回想上一关，由于对 `/tmp/collab` 具有写权限，`hacker` 用户可以替换该 `evil-commands.txt` 文件。还要记得在 [Comprehending Commands] 中，文件可以*链接*到其他文件。如果 `hacker` 将 `evil-commands.txt` 替换为指向某个 `zardus` 可写的敏感文件的符号链接，会发生什么？混乱和恶作剧！

你知道要链接到哪个文件。实施攻击，并获取 `/flag`（在本关中，Zardus 又可以读取它了！）。

**使用 `/tmp` 危险吗？？？**  
尽管这里展示了攻击，`/tmp` 仍可安全使用。该目录*是全局可写的*，但设置了一个特殊权限位：

```console
hacker@dojo:~$ ls -ld /tmp
drwxrwxrwt 29 root root 1056768 Jun  6 14:06 /tmp
hacker@dojo:~$
```

末尾的 `t` 位是 *sticky* 位。sticky 位意味着该目录只允许文件所有者重命名或删除目录中的文件。它正是为了防止这种攻击而设计的！当然，本挑战中的问题在于 Zardus 没有在 `/tmp/collab` 上启用 sticky 位。启用它将堵住这个特定情况下的漏洞：

```console
zardus@dojo:~$ chmod +t /tmp/collab
```

当然，像全局可写目录这样的共享资源仍然很危险。很久以后，在 Green Belt 材料的 [Race Conditions] 中，你将看到此类资源可能导致安全问题的许多方式！

这就是本挑战要探索的内容。Zardus 正在使用一个自动化脚本，并将他的账户密码作为参数传递给它。Zardus 还被允许使用 `sudo`（因此可以使用 `sudo cat /flag`！）。窃取密码，登录 Zardus 的账户（回忆 [Untangling Users] 模块中的 `su` 命令），并拿到 flag！

#### 窥探配置

即使没有犯错，用户也可能无意中让自己处于风险之中。例如，典型用户主目录中的许多文件*默认是全局可读的*，尽管它们经常被用来存储敏感信息。信不信由你，除非你显式更改，否则你的 `.bashrc` 是全局可读的！

```console
hacker@dojo:~$ ls -l ~/.bashrc
```

```log
-rw-r--r-- 1 hacker hacker 148 Jun  7 05:56 /home/hacker/.bashrc
```

```console
hacker@dojo:~$
```

你可能会想，“嘿，至少它默认不是全局可写的”！但即使全局可读，也可能造成损害。由于 `.bashrc` 在启动时由 shell 处理，人们通常在那里初始化他们想要自定义的任何环境变量。大多数时候，这是像 `PATH` 这样的无害内容，但有时人们会把 API 密钥存储在那里以便访问。例如，在本挑战中：

```console
zardus@dojo:~$ echo "FLAG_GETTER_API_KEY=sk-XXXYYYZZZ" > ~/.bashrc
```

之后，Zardus 可以轻松引用该 API 密钥。在本关中，用户可以使用有效的 API 密钥获取 flag：

```console
zardus@dojo:~$ flag_getter --key $FLAG_GETTER_API_KEY
Correct API key! Do you want me to print the key (y/n)? y
pwn.college{HACKED}
zardus@dojo:~$
```

自然地，Zardus 将他的密钥存储在 `.bashrc` 中。你能窃取密钥并获取 flag 吗？

**注意：**  
当你获得 API 密钥后，只需以 `hacker` 用户身份执行 `flag_getter`。本挑战的 `/challenge/victim` 只是为了主题效果：你不需要使用它。
