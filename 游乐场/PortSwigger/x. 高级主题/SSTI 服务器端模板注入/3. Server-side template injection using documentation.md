- 查看安全内容 `23.  Can I allow users to upload templates and what are the security implications? `

    ```md
    一般来说，你不应该允许这样做，除非这些用户是应用程序开发人员、系统管理员或其他高度受信任的人员。将模板视为源代码的一部分，就像 `*.java` 文件一样。如果你仍然想允许不受信任的用户上传模板，以下是你需要考虑的事项：

    - **数据模型与包装（`Configuration.setObjectWrapper`）**：数据模型可能会暴露你放入其中的某些对象的公共 Java API。默认情况下，对于不属于特殊处理类型（`String`、`Number`、`Boolean`、`Date`、`Map`、`List`、数组及其他少数类型）的对象，它们的公共 Java API 将被暴露，包括从标准 Java 类继承的大多数方法（`getClass()` 等）。为了避免这种情况，你必须构造数据模型，使其仅暴露模板真正必要的成员。一种可能性是使用 `SimpleObjectWrapper`（通过 `Configuration.setObjectWrapper` 或 `object_wrapper` 设置），然后纯粹从 `Map`、`List`、`Array`、`String`、`Number`、`Boolean` 和 `Date` 构建数据模型。但对许多应用程序来说这过于严格，此时你必须创建一个 `WhitelistMemberAccessPolicy`，并创建一个使用该策略的 `DefaultObjectWrapper`（或你将要使用的其他 `BeansWrapper` 子类）。更多信息请参见 `WhitelistMemberAccessPolicy` 的 Java API 文档。（或者，你也可以自己实现 `MemberAccessPolicy`，甚至自己实现限制性的 `ObjectWrapper`。）

    始终要预期模板可能获取一些你并未亲自放入数据模型的对象。特别地，模板总是可以通过 `.locale_object` 表达式获取 `Locale` 对象。或者，你正在使用的 Web 应用程序框架可能暴露一些对象，例如 Servlet 作用域中的属性。这些对象仍然会使用你在 `Configuration` 中设置的 `ObjectWrapper` 进行包装，这就是为什么确保该层级的安全性很重要。控制模板将能访问哪些对象是很困难的，但你可以集中控制它们能访问任何对象的哪些成员。

    如果你在自定义代码中创建 `TemplateModel`（而不是由 `ObjectWrapper` 创建），请确保避免使用已弃用的容器构造器，如 `new SimpleSequence()`，因为那些会使用同样已弃用的默认对象包装器实例，该实例不具有你在 `Configuration` 上设置的 `ObjectWrapper` 相同的限制。

    另外，不要忘记 [`?api` 内置指令](ref_builtins_expert.html#ref_buitin_api_and_has_api)（如果你已启用它，默认是禁用的）。虽然大多数 `ObjectWrapper` 不会直接暴露 `Map`、`List` 及类似容器对象的 Java API，因此 `someMap.someJavaMethod()` 不会生效，但使用 `?api`，模板作者仍然可以访问这些对象的 Java API，例如 `someMap?api.someJavaMethod()`。但请注意，`ObjectWrapper` 仍然处于控制地位，因为它决定哪些对象支持 `?api`，以及 `?api` 为它们暴露什么（它通常暴露与普通 POJO 相同的内容）。`MemberAccessPolicy` 不允许的成员在 `?api` 下也不可见（假设你使用的是行为良好的 `ObjectWrapper`，如 `DefaultObjectWrapper`）。

    如果你使用的是默认对象包装器类（`freemarker.template.DefaultObjectWrapper`）或其子类，你应该通过将其 `DOMNodeSupport` 属性设置为 `false` 来禁用其 XML（DOM）包装功能。XML 包装功能会以特殊方式包装 `org.w3c.dom.Node` 对象，以便在模板中更方便地使用，但该功能的设计允许模板作者评估任意的 XPath 表达式，而 XPath 在某些设置中可能做太多事情。如果你确实需要 XML 包装功能，请仔细审查在你的设置中哪些 XPath 表达式是可能的。同时，请确保你不使用早已弃用且更危险的 `freemarker.ext.xml` 包，而应使用 `freemarker.ext.dom`。另外，请注意，当使用 XML 包装功能时，在 `MemberAccessPolicy` 中不允许 `org.w3c.dom.Node` 方法是无效的，因为它不会直接向模板暴露 Java `Node` 成员。

    最后但同样重要的是，一些人可能知道历史遗留问题：标准对象包装器会过滤掉一些众所周知的“不安全”方法，如 `System.exit`。永远不要依赖于此，因为它只阻止了一个小型预定义列表中的方法。标准 Java API 庞大且不断增长，此外还有第三方库和你自己的应用程序的 API。显然，不可能将这些中所有有问题的成员都列入黑名单。

    - **模板加载器（`Configuration.setTemplateLoader`）**：模板可以通过名称（路径）加载其他模板，例如 `<#include "../secret.txt">`。为避免加载敏感数据，你必须使用一个 `TemplateLoader` 来双重检查要加载的文件是否应被暴露。FreeMarker 会尝试阻止加载模板根目录之外的文件（无论模板加载器如何），但根据底层存储机制，可能存在 FreeMarker 无法考虑的利用方式（例如，`~` 跳转到当前用户的主目录）。注意，`freemarker.cache.FileTemplateLoader` 会检查规范路径，因此它可能是一个很好的候选，但添加文件扩展名检查（文件必须是 `*.ftl`）也许是个好主意。

    - **`new` 内置指令（`Configuration.setNewBuiltinClassResolver`、`Environment.setNewBuiltinClassResolver`）**：它在模板中像 `"com.example.SomeClass"?new()` 这样使用，对于部分用 Java 实现的 FTL 库很重要，但在普通模板中不应该需要。虽然 `new` 不会实例化不是 `TemplateModel` 的类，但 FreeMarker 包含一个可用于创建任意 Java 对象的 `TemplateModel` 类。其他“危险的” `TemplateModel` 可能存在于你的类路径中。此外，即使一个类没有实现 `TemplateModel`，它的静态初始化也将被执行。为了避免这些，你应该使用一个 `TemplateClassResolver`，将可访问的类限制到绝对最小值（可能基于哪个模板请求它们），例如 `TemplateClassResolver.ALLOWS_NOTHING_RESOLVER`。**不要**使用 `TemplateClassResolver.SAFER_RESOLVER`，它对此目的来说不够严格！注意，当且仅当你的 `ObjectWrapper` 是 `BeansWrapper` 或其子类（通常为 `DefaultObjectWrapper`）时，`MemberAccessPolicy` 不允许的构造器对于 `?new` 也不可访问。

    - **拒绝服务（DoS）攻击**：创建几乎永远运行的模板（通过循环）或耗尽内存（通过在循环中拼接字符串）是微不足道的。FreeMarker 无法强制 CPU 或内存使用限制，这是 FreeMarker 层面无法解决的问题。
    ```
