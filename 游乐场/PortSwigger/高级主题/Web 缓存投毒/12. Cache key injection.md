# 实验室：缓存键注入

本实验室包含多个独立漏洞，包括缓存键注入。一名用户定期使用 Chrome 访问该网站首页。

要解决本实验室，请组合这些漏洞以在受害者浏览器中执行 `alert(1)`。注意，你需要使用 `Pragma: x-get-cache-key` 头来解决此实验室。

> **提示**
> 解决本实验室需要理解其他几个 Web 漏洞。如果几个小时后仍然无法解决，建议先完成 [Web Security Academy](https://portswigger.net/web-security) 上的所有其他主题。

> **提示**
> 请记住，注入的 origin 头必须是小写，以符合 HTTP/2 规范。有关 Burp Suite 如何支持基于 HTTP/2 的测试的更多信息，请参阅 [在 Burp Suite 中使用 HTTP/2](https://portswigger.net/burp/documentation/desktop/http2)。

回顾
- 线路1，参数反射：请求参数 `lang` 的值被反射到 HTML 的 JS URL 中
    `src='/js/localize.js?lang=en&cors=0'`
    - 若可控制 `lang` 的值，即可在 JS URL 注入载荷

- 线路2，JS 投毒：修改 JS URL 请求参数 `cors=1` 将使得后端解析并最终反射请求头部 `origin`
    - 反射 `origin` 头部的响应存在 HTTP 请求拆分漏洞，从而注入响应头/体，最终完全控制 JS 内容
        `Origin: *%0d%0aContent-Length:%208%0d%0a%0d%0aalert(1)$$$$`

- 线路2.1：请求参数中作为缓存分隔符的元字符 `$$`
    - 缓存将无头请求与缓存键头部请求视为相同缓存字符串
    - 缓存键头部投毒载荷从此可被普通 GET 访问
        `cors=1$$origin=*%0d%0aContent-Length:%208%0d%0a%0d%0aalert(1)$$`

- 线路1.1：重定向链中存在不被视为缓存键的参数 `utm_content`
    - 投毒普通参数的同时携带载荷 `utm_content=载荷`
    - 隐含与之前 JS 投毒的关联，若可控制 JS URL，即同时控制投毒的 JS 缓存响应

- 线路1到2：前后端对字符 `?` 的解释不同
    - 前端缓存视为参数分隔符，后端视为普通字符
    - 对普通参数端点进行缓存投毒，同时发送载荷到后端 `lang=en?utm_content=任意内容&实际载荷`。
        - 此时，主要载荷为 `utm_content` 之后的参数载荷，`utm_content` 的参数值本身将被无视
    - 投毒重定向链中的普通参数端点，携带载荷到最终页面，设置载荷到 JS URL

- 此处省略说明：根据服务器重定向与浏览器解析的 URL 解码，对载荷进行 URL 编码
