## 引言

规定电子邮件地址格式的一些 RFC 已经存在了 50 多年，它们被拼凑在一起形成了一个过于宽松的电子邮件地址标准。电子邮件可以包含带引号的值、注释、转义字符和各种编码。如果你面临编写电子邮件解析器的任务，从技术上讲你应该遵循规范，但由于所有这些复杂性，这是一项艰巨的工作。Web 应用程序将这些复杂性外包给电子邮件解析库，因此它们实际上并不知道电子邮件是如何被解析的。当它们决定基于电子邮件域做出安全决策时，这就会导致问题。

如果你查看 RFC2822 的 [3.2.5](https://datatracker.ietf.org/doc/html/rfc2822#section-3.2.5) 和 [3.2.2](https://datatracker.ietf.org/doc/html/rfc2822#section-3.2.2) 节，它允许你使用带引号的值和转义字符。它们使你能够在电子邮件地址的 local-part 中使用通常不允许的字符。以下是一些示例：

```
"@"@example.com
"\""@example.com
```

在第一个示例中，由于 local-part 被引号括起来，at 符号将被用作目标邮箱，引号会被移除。在第二个示例中，它展示了如何在带引号的 local-part 中使用转义字符，从而将双引号本身作为目标邮箱。如果我们深入研究同一 RFC 的 [3.2.3](https://datatracker.ietf.org/doc/html/rfc2822#section-3.2.3) 节，可以看到它支持注释。注释使用括号构造，可以包含空格甚至嵌套。以下是一些使用注释的“有效”电子邮件示例：

```
(foo)user@(bar)example.com
```

你不仅限于字母数字值；你可以在注释中放置大量字符。通过制造解析器、应用程序和邮件程序之间的混淆，这一切似乎都容易被滥用。我的研究之旅就是从尝试利用转义和注释来制造这种混淆开始的。

## 制造电子邮件域名混淆

关于我是如何发现这一点的故事我并不引以为傲，但这是事实。我没有花数小时用调试器查看 Postfix 和 Sendmail 的源代码，这当中确实有一定的随机性和运气成分。

事情始于我登录一个用于测试的机器时，我安装了一个未命名的应用程序并开始测试其电子邮件解析差异。我毫无进展。我尝试的一切都失败了，我甚至想过完全放弃这项研究。然后出于绝望，我拿起了应用程序正在使用的特殊字符并将其粘贴到我的电子邮件地址中。我知道这应该是有效的，因为这些字符都是他们允许的，但我只是想看看邮件程序会发生什么。

我检查了机器的 syslog，注意到我收到了一条 DSN（投递状态通知），其中包含一个无效主机。对此感到惊讶，我开始深入挖掘。我开始从电子邮件地址中移除字符，以缩小为什么 Sendmail 认为它是一个无效主机的范围。最终，我将范围缩小到了感叹号，并想起了在研究过程中读到的 [UUCP 协议](https://www.jochentopf.com/email/address.html#uucp)。

UUCP 是一种古老协议，存在于互联网和电子邮件之前。它允许你在 Unix 系统之间发送消息，代表 Unix to Unix Copy（Unix 到 Unix 复制）。它的工作原理是使用感叹号作为域和用户部分之间的分隔符，但顺序与传统电子邮件地址相反。

这太疯狂了，纯粹靠运气，我粘贴的字符以反斜杠结尾，反斜杠转义了 at 符号，然后感叹号将该地址视为 UUCP 地址！以下是我发现的完整过程：

**原始发现：**

```
 !#$%&'*+\/=?^_`{|}~-collab\@psres.net
```

自然，我必须用一个不同的 Collaborator 域跟进以确定它是否真的去往不同的服务器：

```
 oastify.com!collab\@example.com
```

前面的示例在使用 Sendmail 8.15.2 时，实际去往的是 Collaborator 域 "oastify.com" 而不是 example.com。这真的让我很兴奋，因为我证明了这项研究确实有进展。下一步是找到其他导致此行为的字符，所以我很快编写了一个 SMTP 模糊测试器。我发现 Postfix 没有这种行为，因为它更安全，对吧？嗯，我原本也是这么想的，直到我通过模糊测试器在 Postfix 3.6.4 中发现了一个变种：

```
 collab%psres.net(@example.com
```

这实际上去往的是 psres.net 而不是 example.com，它使用了另一种名为 [源路由（source routes）](https://www.jochentopf.com/email/address.html#sourcerouting) 的古老协议。源路由允许你使用一系列服务器来发送邮件。其思路是用逗号分隔每个主机，然后在末尾包含最终目的地。还有一种所谓的“百分号技巧”（percent hack），即邮件程序将 % 或不同的选定字符转换为 at 符号，然后将电子邮件转发到该服务器。以下示例说明了这一点：

```
foo%psres.net@example.com
foo@psres.net
```

在此过程中，电子邮件最初被发送到 example.com，之后百分号被转换为 at 符号，并向 foo@psres.net 发送了一封电子邮件。这正是该向量所发生的情况——括号将电子邮件地址的域部分注释掉，然后 Postfix 将 local-part 用作源路由，将电子邮件发送到非预期的目的地。Postfix 实际上也支持 UUCP。我后来发现了使用单括号的技巧。

这些发现给了我信心，让我相信那里有大量的漏洞，于是我开始寻找更多。

## 解析器差异

### Unicode 溢出

这项研究中我必须要解决的主要问题之一是生成被阻止的字符。因为许多 Web 应用程序会阻止多个 at 符号。这就是我开始研究 unicode 溢出的原因。

我在测试一个未命名的目标时注意到，当使用较高的 unicode 字符时，它们会生成其他 ASCII 字符。起初这种模式看起来很随机，但后来我明白了发生了什么。用 PHP 中 chr() 算法的工作原理来图解最好。chr() 函数返回由整数码点指定的字符：

![PHP chr() 函数](https://portswigger.net/cms/images/ce/93/0cef-article-php-chr-function.png)

在该示例中，PHP 循环遍历字节并检查它是否小于零，如果是，则加 256 直到为正。然后它执行取模运算以将值适配到 0-255 范围内。这意味着如果你传入一个大于 255 的字节值，它将因为取模运算而溢出并被强制到 0-255 范围内。这正是 unicode 溢出的工作原理；我们只需要提供一个码点大于 255 的字符来生成其他字符。一个简单的例子最能说明这一点：

```php
String.fromCodePoint(0x100 + 0x40)
```

在前面的示例中，我使用 fromCodePoint 函数生成一个字符，我传入的十六进制值 0x100 对应十进制的 256，然后我加上 0x40，即 at 符号的十六进制数。然后当系统执行像 PHP 中的 chr() 函数这样的操作时，unicode 码点将溢出并适配到 0-255 范围内，从而生成 at 符号。

在我发现这一点后，我开始用 Turbo Intruder 对未命名的目标进行模糊测试，并注意到其他字符也表现出这种行为。起初看起来是随机的，但后来我意识到发生了什么——0x100 只是你可以用来执行溢出的数字之一。如果你使用更高的字符，你可以使用介于两者之间的任何字符。

```php
String.fromCodePoint(0x100 + 0x40) // ŀ → @
String.fromCodePoint(0x1000 + 0x40) // ၀ → @
String.fromCodePoint(0x10000 + 0x40) // 𐁀 → @
...
0x10ffff
```

上面的每个十六进制值都会产生溢出，因为取模运算的结果为零，而且这种情况可以一直持续到当前最大的 unicode 码点 0x10ffff。这个目标允许各种 unicode 字符来生成其他字符：

```php
'✨' === '('
'✩' === ')'
'✻' === ';'
'✼' === '<'
'✽' === '='
'✾' === '>'
'❀' === '@'
```

如果你对每个字符执行 256 取模运算，它将产生生成的字符：

```
//Mod each code point by 256
'❀'.codePointAt(0) % 256 === 0x40
String.fromCodePoint(0x40)
// @
```

虽然我能够伪造各种各样的字符，但我无法用这种技术在这个未命名的目标上拆分电子邮件。但这仅仅是个开始，我证明了生成被阻止字符是可能的。这给了我继续寻找更多东西的信心。

### Encoded-word

我越深入研究，电子邮件 RFC 给我的就越多。在这项研究之前，我曾假设电子邮件通常是字母数字的，local-part 中带点。我从没想过存在一个完整的复杂编码系统允许你执行多层编码。然而这正是我发现的。仔细查阅 RFC，我注意到了 rfc2047 和 [encoded-word](https://datatracker.ietf.org/doc/html/rfc2047#section-2)，这种编码系统允许你使用 hex 和 base64 来表示字符。

如果我们用一个编码的电子邮件作为示例说明：

![encoded-word 工作原理](https://portswigger.net/cms/images/6e/a0/3665-article-how-encoded-word-works.png)

"=?" 表示 encoded-word 的开始，然后你指定字符集，这里是 UTF-8。然后问号分隔下一个命令 "q"，表示 "Q-Encoding"，之后又一个问号表示编码格式的结束和编码数据的开始。Q-Encoding 就是带有等号前缀的 hex。在这个示例中我使用 =41=42=43，即大写的 "ABC"。最后，?= 表示编码的结束。当被电子邮件库解析时，电子邮件目的地将是 ABCUSER@psres.net！

有了这些信息，我开始寻找使用这种编码解析电子邮件的真实系统。为了帮助实现这一点，我提出了两个在大多数具有此行为的站点上都能起作用的探测：

![探测 encoded-word](https://portswigger.net/cms/images/2b/1b/de46-article-probing-encoding-word-corrected.png)

最初我使用字符集 "x" 来减小探测的大小，然而一些系统会拒绝未知的字符集并失败。最好使用这两个探测，因为经过大量站点测试后我发现它们是最常被允许的字符集。使用 Collaborator 生成一个载荷，并将上图中的 "collab" 替换为生成的载荷。然后如果你在 SMTP 会话的 RCPT TO 命令中收到了带有该电子邮件的 SMTP 交互：

```
abccollab@psres.net
```

这证明了电子邮件解析器正在使用 "encoded word" 解码电子邮件。

我发现了许多具有此行为的网站，它们都有一个共同点：Ruby。它们似乎都使用了名为 "Mail" 的同一个 Ruby Gem，该 Gem 的下载量超过 5.08 亿次。我开始查看源代码，发现该库正在[解码 UTF-7](https://github.com/mikel/mail/blob/10a4443b9d4ffa71b9ad643ad86cc23ccc99f0f3/lib/mail/utilities.rb#L399)！在我的测试环境中，我尝试重现这一点：

![更改字符集](https://portswigger.net/cms/images/66/41/d073-article-changing-the-charset.png)

这太疯狂了！电子邮件现在可以使用 UTF-7 了！然后一个想法出现在我的脑海中：如果有 Q-Encoding 和字符集，你能同时拥有两者吗？对这个问题的令人惊讶的答案是肯定的。你可以将 UTF-7 与 Q-Encoding 混合使用！

![混合 Q-Encoding 和 UTF-7](https://portswigger.net/cms/images/89/59/a4d9-article-blending-q-encoding-utf7.png)

在那之后，我开始尝试 base64 编码，因为 "encoded-word" 在电子邮件中当然也支持这种编码！你只需在编码类型中使用 "b" 而不是 "q" 即可。

![Base64 encoded-word](https://portswigger.net/cms/images/93/e1/cf1e-article-base64-encoded-word.png)

前面的示例使用了 base64 编码的字符串 "foobar"，它被解析器解码。我知道你在想什么（或者也许只有我这么想），是的，你可以使用 UTF-7 和 base64 编码的数据：

![组合 base64 和 UTF-7](https://portswigger.net/cms/images/15/96/06e0-article-combining-utf-7-base64.png)

在这个示例中，有一个 base64 编码的地址和 UTF-7 字符集。首先电子邮件解析器将解码 base64。然后电子邮件解析器将解码 UTF-7 字符集。最后电子邮件被解码为 foobar@psres.net。此时你可能对严格遵守 RFC 有些怀疑。尤其是我告诉你当我在测试 Mail 库时，这在域部分也同样有效。请注意我在这里使用的是字母数字值，但你当然也可以编码任何特殊字符。

### Encoded-word 案例研究

### Github：访问受 Cloudflare "Zero Trust" 保护的内部网络

到目前为止，我们已经看到了如何制造电子邮件域名混淆和令人惊讶的编码，但现在是时候利用这些知识来攻击真实系统了。我测试的首批目标之一是 Github。我特意选择 Github 是因为我知道它是用 Ruby 编写的。

我使用了之前提到的两个探测来确认 Github 支持 "encoded-word"。在 Collaborator SMTP 会话中，电子邮件被解码了！于是我开始进一步测试。我需要做的是使用 "encoded-word" 来产生另一个 at 符号。起初我尝试使用带引号的 local-part 值，并成功地在带引号的值中嵌入了原始的 at 符号。也许我可以在带引号的 local-part 中使用 "encoded-word" 来突破引号值并产生两个不同的地址？我尝试了 =22（双引号）和 =40（at 符号）但没有成功。

这项研究的困难之处在于，有时你得不到任何反馈，因为它通过了电子邮件验证，但在到达邮件程序之前就失败了。你可以使用 DNS 交互作为线索，但它们通常几乎没用，因为你无法确定是失败的原因导致无法到达邮件程序。

经过多次尝试后，我开始思考 SMTP 会话，并尝试放置大于号。这里的想法是，我可以使用它来结束 SMTP 会话中的 RCPT TO 命令：

```
RCPT TO:<"collab@psres.net>collab"@psres.net>
```

前面的示例显示了一个带引号的 local-part，其中包含原始 at 符号和大于号。你可以开始看到攻击是如何形成的。你有两个地址，使用大于号的想法将使你能够在 SMTP 会话中忽略第二个地址。带着这个想法，我开始使用编码向量来构建攻击。

我很快发现双引号对 Github 没什么用，原因在于它总是留下一个开放的双引号，导致验证失败。我当然尝试了编码和转义，但都没有成功。我移除了引号，并使用 "encoded-word" 来生成 at 符号和大于号，它通过了验证，但我没有收到电子邮件。没有 SMTP 会话。什么都没有。考虑到这一点，我想也许电子邮件末尾的尾部垃圾导致邮件程序失败，要么是异常要么是验证失败。如果我能引入一些避免异常或验证的字符呢？我尝试了编码的空格，但失败了，然后我尝试了编码的空字节，成功了！我收到了以下电子邮件的交互：

![利用 Github 电子邮件验证](https://portswigger.net/cms/images/ff/1b/5723-article-exploiting-github-email-verification.png)

对于 Github，字符集无关紧要，所以我用了 "x"，编码的 at 符号（=40）被转换为 at，大于号（=3e）完成了 RCPT TO 命令，最后空字节（=00）使邮件程序忽略之后的所有内容，你需要在编码后放置一个有效的 local-part，所以我用了 "foo"，这成功通过了验证并拆分了电子邮件。然后我可以验证任何我喜欢的电子邮件域。我在我的测试账户上验证了 microsoft.com、mozilla.com 和 github.com 的地址：

![Github 已验证的电子邮件](https://portswigger.net/cms/images/b5/1b/fb1b-article-github-verified-emails.png)

这本身已经是一个漏洞，因为你本不应该能够验证你不拥有的地址。然后我的同事 [James Kettle](https://x.com/albinowax) 建议我看看 Cloudflare "Zero Trust"，看看它是否可以配置为信任某些电子邮件域。我创建了一个测试账户并深入研究了配置，发现你可以使用 Github 作为 IdP，并使用电子邮件域来确定你是否可以访问某个站点。这可以是内部网络或任何其他受 Zero Trust 保护的域，前提是它们使用 Github 作为 IdP。

![Cloudflare Zero Trust 配置界面](https://portswigger.net/cms/images/e7/5b/0f66-article-cloudflare-zero-trust.png)

### Zendesk：访问受电子邮件域保护的客服中心

在 Github 成功之后，我开始寻找使用 Ruby 并具有某种形式的电子邮件域验证的应用程序。其中一个引起我注意的是 Zendesk，因为也许你可以获得对受保护的客服台的访问权限？在尝试拆分电子邮件地址之前，我搜索了他们的文档，发现你需要打开客服中心，允许注册，然后选择允许注册的域。

客服中心配置好后，我开始测试。我尝试了所有在 Github 上使用的攻击，但没有成功。也许他们使用了不同的邮件程序或验证方式？我尝试了一些新想法，使用带引号的 local-part，并且在 Collaborator 中收到的交互看起来比测试 Github 时更有希望。

我发现有用的一点是使用两个重复的 Collaborator 域，这样我总是能收到交互，通过检查 SMTP 会话你可以看到什么被转换了。我发送了以下内容：

```
Input:
=?x?q?=41=42=43collab=40psres.net=3e=20?=@psres.net
```

并收到了以下返回：

```
Output:
RCPT TO:<"ABCcollab@psres.net> "@psres.net>
```

这个交互告诉了我很多事情：首先，他们允许大写。其次，他们允许转换空格，第三，当解码时，他们似乎会引用在 local-part 中通常不允许的值。也许我可以滥用这种行为？

经过更多次尝试，我终于取得了一些进展。我欺骗了解析/验证来转换被阻止的字符，双重编码引号并生成会被其代码移除的字符，直到最终我构建了一个有效的电子邮件拆分攻击：

![利用 Zendesk 电子邮件验证](https://portswigger.net/cms/images/50/32/943f-article-zendesk-email-verification.png)

使用这个 "电子邮件"，我能够绕过对客服中心设置的限制。这个攻击的关键是嵌入的编码引号被解析器解码。然后 =3c22 生成了一个小于号，该字符被移除，从而完成了引号，使其通过了他们的验证/异常处理。你会注意到 "=3e=00" 与我在 Github 上使用的序列相同，所以它们显然共享一些相同的代码，但它们响应的方式有很大不同，因此形成了更完整的攻击。

### Gitlab：获得对 Gitlab Enterprise 服务器的未授权访问

寻找更多 Ruby 目标时，我转向了 Gitlab。它们是一个 IdP 并提供企业产品，所以看起来是一个很好的测试目标。James 有一个他之前测试过的 Gitlab 服务器，所以我首先开始查看那个服务器。你可以配置它允许使用特定域进行注册。这立刻引起了我的注意。我尝试了在 Github 和 Zendesk 上使用的向量，但它们不起作用。然后我记起 "encoded-word" 允许你使用下划线作为空格，这个向量是我目前演示过的最优雅的：

![利用 Gitlab Enterprise 服务器](https://portswigger.net/cms/images/be/6b/47dc-article-exploiting-gitlab-enterprise-servers.png)

我使用 Postfix 作为配置的企业实例的邮件程序。你可以使用 =20 来做同样的事情，但下划线只有一个字符，我喜欢优雅的向量！

这意味着我可以访问那些使用基于域的注册限制的 Gitlab Enterprise 服务器。正如我提到的，Gitlab 也是一个 IdP，所以我也开始测试 Web 应用程序。企业版的方法在这里不起作用。我想这是因为它们使用了不同的邮件程序。然而，没过多久我就找到了另一个向量。此时我已经收集了一堆向量，所以我有一个 Turbo Intruder 脚本，可以遍历所有已知向量并尝试其他向量。它发现了一个使用编码空格的新向量，这很合理，因为它在企业产品上有效，只是需要不同的利用方法：

![利用 Gitlab 电子邮件验证](https://portswigger.net/cms/images/70/fb/1fbe-article-gitlab-email-verification.png)

这与 Github 的攻击非常相似，但它需要一个有效的字符集并且需要空格而不是空字节。在图中我使用了 "x"，但在实际攻击中你会使用 "iso-8859-1"。

### PHPMailer

不幸的是，我并没有利用所有测试过的目标，也有很多失败。每一次都是一个学习过程，但这个案例研究的有趣之处在于 "encoded-word" 在一个非 Ruby 系统上被解析和解码了。

在 James 的建议下，我已经构建了一个测试环境，于是我开始测试 PHPMailer 如何解析电子邮件。我进行了黑盒和白盒混合测试，发现它不会在电子邮件地址的 local-part 或域部分内解析 "encoded-word"。然而，它确实会在电子邮件地址之外的名字部分解析和解码它！

```
=?utf8?q?=61=62=63?=<collab@psres.net>
```

分析代码发现，尖括号是必需的，这意味着它在像 Wordpress 这样的应用程序中经常会验证失败。我尝试在各种应用程序的 name 参数中嵌入载荷，但无法利用这个特定的库。不过我打赌你可以用 "encoded-word" 嵌入 XSS 载荷，并且这在某个地方会起作用。如果你成功做到了，请联系我，我很想听听。

## Punycode

我们已经探讨了如何操纵电子邮件解析来绕过[访问控制](/web-security/access-control)。但让我们更进一步。如果一个电子邮件地址可以被武器化以获得远程代码执行（RCE）呢？在本节中，我们将介绍 Punycode 攻击以及我如何利用 Joomla。

### 什么是 Punycode？

Punycode 是一种在当前 DNS 系统中表示 unicode 字符的方式。Punycode 总是以 xn-- 开头，后面跟着连字符和字母数字字符。非 ASCII 字符使用一种特殊算法编码，该算法表示这些字符。该算法将 unicode 字符序列转换为仅使用 ASCII 字符的表示形式。该算法规定，通常输入中不构成 unicode 字符的任何 ASCII 字符都要原样添加到输出中。例如，域名 münchen.com 用以下 Punycode 序列编码：

```
xn--mnchen-3ya.com
```

Punycode 的工作方式本身就使得测试变得困难，因为由于算法的工作方式，更改一个字符会影响整个输出和字符位置。我们想要做的是在解码编码值时生成恶意字符，而要做到这一点是一个巨大的挑战。在以下示例中，你可以看到当修改一个字节时，unicode 字符的位置会发生变化：

```
foo@xn--mnchen-2ya.com → foo@ümnchen.com
foo@xn--mnchen-3ya.com → foo@münchen.com
foo@xn--mnchen-4ya.com → foo@mnüchen.com
foo@xn--mnchen-5ya.com → foo@mncühen.com
```

### 畸形的 Punycode

在维基百科上阅读了所有相关内容后，我跟随一个链接进入了一个在线的 Punycode 转换器。该转换器使用了 IDN PHP 库。我开始尝试各种 Punycode 地址。我发现如果你在开头使用两个零，可以生成非预期的字符：

```
Input:
psres.net.com.xn--0049.com.psres.net

Output:
psres.net.com.,.com.psres.net
```

这是我第一次成功尝试创建畸形的 Punycode。输入包含 Punycode "xn--0049"，由于一个有缺陷的库，它解码为一个逗号。我能够使用这种技术生成更多的字符：

```
Input:
foo@xn--0117.example.com 

Output:
foo@@.example.com
```

有许多方法可以生成相同的字符。我考虑了电子邮件拆分攻击，但我得出结论，Punycode 地址在发送电子邮件时不会被解码，因为它会是无效的。更有可能的是，它会在显示电子邮件时被解码。自然，我问自己的问题是：你能创建一个 [XSS](/web-security/cross-site-scripting) 向量吗？

这是一项适合模糊测试器的工作。我开始构建一个，它立即开始产生有趣的结果：

```
x@xn--42 → x@,
x@xn--024 → x@@
x@xn--694 → x@;

x@xn--svg/-9x6 → x@<svg/
x@xn--svg/-f18 → x@<svg/
x@xn--svg/-fq1 → x@<svg/
```

我认为这是寻找使用 IDN PHP 库的应用程序的好时机。在搜索 Github 后，我发现了一个使用该库的有趣目标：Joomla！这很棒，因为如果我获得 XSS，那么我就获得了 RCE。通过源代码分析，我注意到他们在对用户的电子邮件进行 Punycode 解码之前对其进行了转义。这意味着如果我能产生一些畸形的 Punycode，在解码时产生 HTML，我就可以获得 XSS，但这不会那么容易。

![Joomla 不正确的转义](https://portswigger.net/cms/images/ef/86/6932-article-joomla.png)

### 尝试利用 Joomla

我满怀兴奋地回到我的模糊测试器，开始生成数百万个字符组合。我设法构建了部分 XSS 向量，但遇到了几个问题。通过使用多个 Punycode 子域，我只能生成两个 ASCII 字符。这个限制源于 Punycode 算法、PHP 以及有缺陷的 PHP IDN 库的特殊工作方式。正如你在示例中看到的，我很接近了，但这些问题使得利用 Joomla 变得非常困难。

```
xn--x-0314.xn--0026.xn--0193.xn--0218 → <x.. .=
xn--x-0314.xn--0026.xn--0193.xn--54_52932 → <x.. .='
```

我得出结论，XSS 不可行，因为虽然我能够生成单引号 HTML 属性，但它需要一个下划线字符。然而，Joomla 不允许在电子邮件地址的域部分使用下划线。

### 利用 Joomla 实现 RCE

简述：
- 载荷1：在 email 字段导入开 HTML 标签 `<style`
- 载荷2：在 name 字段
  - 使用 `{}` 将载荷1到载荷2开头的所有内容构造为无效 css 选择器，以便之后设置代码
  - 使用 `@import` 导入恶意 style

那么这就是故事的结局了吗？不完全是。我想了一段时间，并得出结论，如果你使用单个 Punycode 子域，你可以生成任何开标签！经过大量测试后，我得出结论，唯一可利用的向量是开头的 style 标签：

![畸形的 Punycode 产生 style 标签](https://portswigger.net/cms/images/15/e5/dfca-article-punycode-style.png)

Joomla 现有 HTML 代码的其余部分会添加一个空格和闭合的尖括号。该电子邮件在用户列表页面上输出。这意味着它是持久性的，并且甚至不需要激活账户。你可以简单地注册一个用户，它就会是持久性的 style 注入！但我们如何把恶意的 CSS 放进去呢？要做到这一点，你需要一个地方来放置 CSS 而不被阻止。用户的 name 字段是一个很好的选择，你可以使用 @import 来导入恶意的 style。

我遇到的问题是在 style 注入之后出现的所有 HTML 代码都将被视为 CSS！为了解决这个问题，你只需欺骗 CSS 解析器，让它认为这全是一个无效的 CSS 选择器，这意味着只需使用 {}。所以如果你在 name 字段的开头放置它，你就可以在之后导入一个 style。攻击方式如下：

![利用 Joomla 两个不同的账户](https://portswigger.net/cms/images/95/b2/f311-article-joomla-account-registration.png)

注意第一个账户名有一个 "a"，第二个账户名有一个 "x"，这是为了确保 style 注入先发生，第二个账户使用 @import。花括号用于将导入之前的所有 HTML 视为无效的 CSS 选择器。Chrome 严格的 CSS MIME 类型检查在这里也不适用，因为使用的是内联 style。

我们现在需要做的是通过 CSS 泄露 CSRF 令牌，幸运的是已经有很多好的文章介绍了这一点。最好的方法是使用导入链，并使用由 [d0nut](https://d0nut.medium.com/better-exfiltration-via-html-injection-31c72a2dae8b) 和 [Pepe Vila](https://vwzq.net/slides/2019-s3_css_injection_attacks.pdf) 开发的工具之一。我决定定制我已经用我的[盲 CSS 泄露研究](https://portswigger.net/research/blind-css-exfiltration)开发的工具，这涉及到使其提取特定的 Joomla 令牌。我将在本文后面的 Github 仓库中分享定制的代码。

在我运行 CSS 泄露器时，我注册了两个账户，并用超级管理员账户访问了用户页面。泄露器显示了管理员的 CSRF 令牌，所以下一步是向管理员提供使用泄露令牌的 CSRF 漏洞。我的泄露器还会构建 [CSRF](/web-security/csrf) 漏洞。然后该漏洞修改一个管理员模板以获得 RCE！

以下是攻击的演示视频：

<iframe src="https://www.youtube.com/embed/VjnBsA_oen4?origin=https://portswigger.net&rel=0"></iframe>

在视频中，颜色较亮的左侧是管理员浏览器，颜色较深的右侧是攻击者浏览器。攻击者注册两个账户，第一个注入来自畸形 Punycode 地址的 style 标签，第二个注入 CSS 泄露样式表。然后管理员访问后台和用户列表页面，恶意 CSS 立即被加载并在几秒钟内泄露令牌。

一旦发生这种情况，攻击者会收到管理员 CSRF 令牌的通知，然后开始与管理员进行即时消息对话。管理员点击攻击者的链接，遭受 CSRF 攻击，编辑后端模板，注入一些 PHP 代码来执行系统命令以 cat /etc/passwd。


## 方法论与工具

![电子邮件拆分方法论](https://portswigger.net/cms/images/8e/95/25ea-article-methodology.png)

在进行这项研究时，我开发了一种方法论，我发现它在测试时很有用。探测、观察、编码和利用。首先使用本文中提到的探测，然后在 Collaborator 等工具中观察结果。重复该过程，直到你拥有攻击所需的字符。当这个过程完成时，进行利用。你可以将这种方法论应用于 encoded-word 和 Punycode 攻击。

首先探测 "encoded-word"，观察解码后的电子邮件以确认它是否被支持。然后编码各种字符并观察它们如何被解码。然后跟进利用这些字符的攻击。

为了观察结果，我使用了 [Burp Collaborator](https://portswigger.net/burp/documentation/collaborator)，它允许我查看 SMTP 交互。

### 使用 Hackvertor 标签生成电子邮件拆分攻击

为了帮助找到电子邮件拆分攻击，我创建了几个 Hackvertor 标签。[Hackvertor](https://portswigger.net/bappstore/65033cbd2c344fbabe57ac060b5dd100) 是我编写的一个免费 Burp Suite 扩展，它允许你在请求中使用标签并对数据执行嵌套转换。你只需将标签放在你想要发生 unicode 溢出的位置，然后将你想要转换的字符放在标签内：

```
<@_unicode_overflow(0x100,'...')>@</@_unicode_overflow>
<@_unicode_overflow_variations(0xfff,'...')>@</@_unicode_overflow_variations>
foo<@_encoded_word_encode('...')>@</@_encoded_word_encode>example.com
<@_encoded_word_decode('...')>=41=42=43</@_encoded_word_decode>
<@_email_utf7('...')></@_email_utf7>
<@_email_utf7_decode('...')></@_email_utf7_decode>
<@_encode_word_meta('iso-8859-1','...')></@_encode_word_meta>
```

第一个标签创建单个 unicode 溢出，并使用标签参数 0x100（十进制 256）来创建溢出。第二个使用标签参数作为最大 unicode 码点，并生成尽可能多的溢出到标签内指定字符的字符。第三个标签允许你执行 encoded-word 转换，在示例中我编码了 @ 符号。第四个标签将解码 encoded-word 序列。还有更多标签可以帮助创建和解码 UTF-7 电子邮件以及 encoded-word 元字符。

要使用这些标签，你需要在 Hackvertor 菜单中启用 "Allow code execution tags"。然后点击同一菜单中的 "View Tag Store"。你可以通过点击标签名称然后使用安装按钮来安装这两个标签。

### 使用 Turbo Intruder 自动化利用 Encoded-word

当我发现最初几个漏洞时，我发现自动化对于寻找其他漏洞非常有用，而 [Turbo Intruder](https://portswigger.net/bappstore/9abaa233088242e8be252cd4ff534988) 经常在自动化这个过程中非常有用。Turbo Intruder 是 [James Kettle](https://x.com/albinowax) 编写的另一个免费 Burp 扩展。我创建了一个 Turbo Intruder 脚本来帮助利用邮件程序。当你已经确定服务器支持 encoded-word，但你想知道邮件程序是否允许你使用空字节或其他字符拆分电子邮件时，使用此脚本。

它使用了我测试 Github、Zendesk、Gitlab、Bugcrowd 和许多其他系统时发现的一系列已知的电子邮件拆分技术。你可以轻松地自定义脚本来执行本演示中提到的其他攻击。要使用它，你只需要将 validServer 变量更改为你要伪造的目标域。然后在你希望添加电子邮件的位置放置 %s，右键点击请求并发送到 Turbo Intruder，使用修改后的脚本。然后运行攻击。如果攻击成功，你应该会在 Turbo Intruder 中收到一个 collaborator 交互。这意味着该电子邮件域是可伪造的。如果你遇到有速率限制的应用程序（就像我遇到的那样），你可以更改 REQUEST_SLEEP 变量以更好地与这些服务器配合。

![Turbo Intruder encoded-word 截图](https://portswigger.net/cms/images/8d/6d/9c4d-article-turbo-intruder-screenshot.png)

### 模糊测试畸形 Punycode

![Punycode 模糊测试器](https://portswigger.net/cms/images/60/aa/55e4-article-punycode-fuzzer.png)

我创建了一个 Punycode 模糊测试器来帮助发现畸形的 Punycode。我与 PortSwigger 的同事分享了它，并创建了一个挑战，看看是否有人在限制条件下生成 XSS 向量。没有人做到，但我还是通过 CSS 泄露获得了 RCE。该模糊测试器的工作原理是给它一些带有 Punycode 地址的输入，然后用随机数字、字符或空格替换占位符。Matches 和 contains 只是用来匹配模糊测试输出的正则表达式。它在发现可以生成哪些字符方面非常有效。

## 额外内容

在 DEF CON 上，因为我多出了 5 分钟的时间，我展示了一些额外的向量。

RFC 允许所谓的 SMTP 可选参数。其中一个参数 "[ORCPT](https://www.rfc-editor.org/rfc/rfc3461#section-4.2)" 可用于走私电子邮件地址的域部分并更改其目的地。由于许多应用程序经常接受带引号的 local-part 但错误地处理转义字符，你可以滥用这一点来更改电子邮件目的地：

```
"foo\\"@psres.net> ORCPT=test;admin"@example.com
```

这种技术在 Postfix 中有效，可能也适用于其他邮件程序。

作为额外内容，这里还有一些我发现的在 Postfix 中有效的令人惊讶的电子邮件解析行为。我无法将它们用于访问控制绕过，但它们仍然很有趣，并且挑战了你对电子邮件地址如何被解析的假设。第一个使用 UUCP，并且无论引号如何都会被发送。

```
Input: "psres.net!collab"(\"@example.com
Results in email to: collab@psres.net  
```

第二个即使使用方括号语法也使用源路由。

```
Input: collab%psres.net@[127.0.0.1]
Results in email to: collab@psres.net  
```

## 防御措施

我建议在使用电子邮件解析库时禁用 "encoded-word"。作为最后的手段，你可以通过在电子邮件地址中查找 "encoded-word" 的开头和结尾字符来阻止它被使用，使用以下正则表达式：

```
=[?].+[?]=
```

你应该始终验证电子邮件地址，即使它来自像 Github 这样的 SSO 提供商。永远不要使用电子邮件域作为唯一的授权手段，因为正如我们所见，它可以很容易地被伪造。

## 要点总结

- 有效的电子邮件地址可以触发重大的解析器差异。
- 即使以 "@example.com" 结尾的地址也可能被路由到其他地方。
- 因此，使用电子邮件域来强制执行访问控制从来都不安全。
