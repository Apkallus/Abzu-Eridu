# 逻辑漏洞

> 此处不尝试拆分为应用逻辑、业务逻辑。而综合所有逻辑漏洞

## 引言

所有 Web 应用程序都通过逻辑实现各种功能。从根本上讲，用编程语言编写代码就是把一个复杂的进程分解成一些非常简单而又相互独立的逻辑步骤。将一项对人类有用的功能转换成一系列计算机能够执行的细微操作，需要掌握大量的技巧并进行周密的安排。顺利、安全地完成以上任务就更显困难。如果由背景各不相同的开发者与程序员并行开发同一个应用程序，那么在这个过程中可能会发生很多错误。

在所有即使是非常简单的 Web 应用程序中，每个阶段都会执行数目庞大的逻辑操作。这些逻辑代表着一个复杂的受攻击面，它虽然从未消失，但往往被人们忽略。许多代码审查与渗透测试主要针对典型漏洞，如 SQL 注入和跨站点脚本，因为它们几乎总是呈现出一种一致的形态，从而具有容易辨别的签名。这使得它们很容易用诸如注入或拒绝服务等术语进行分类。这也意味着，针对常见漏洞的攻击或缓解策略在所有受影响的应用中相对一致。

虽然应用程序之间可能存在通用功能，如登录页面、忘记密码和搜索栏，但应用程序的性质各不相同，每个应用程序都以独特的方式实现其业务逻辑。这意味着业务逻辑缺陷的性质可能差异很大。独特的漏洞最常出现的原因是应用实现了特定的业务逻辑规则。然后黑客找到利用这些编程规则并获得非预期结果的方法。

## 什么是业务逻辑漏洞？

业务逻辑漏洞是应用程序设计和实现中的缺陷，允许攻击者引发非预期的行为。这可能使攻击者能够操纵合法功能以达到恶意目的。这些缺陷通常是由于未能预见可能发生的异常应用程序状态，从而未能安全地处理它们所致。

> **注意：** 在此上下文中，“业务逻辑”一词仅指定义应用程序如何运行的一组规则。由于这些规则并不总是与业务直接相关，相关的漏洞也被称为“应用程序逻辑漏洞”或简称为“逻辑缺陷”。

逻辑缺陷对于不特意寻找它们的人来说通常是不可见的，因为它们通常不会通过应用程序的正常使用而暴露。然而，攻击者可能能够通过以开发人员从未预期的方式与应用程序交互来利用行为异常。

业务逻辑的主要目的之一是强制执行在设计应用程序或功能时定义的规则和约束。广义上讲，业务规则规定了应用程序在给定场景发生时应如何反应。这包括防止用户做出对业务产生负面影响或根本没有意义的事情。

逻辑中的缺陷可能允许攻击者绕过这些规则。例如，他们可能能够在未经过预期购买工作流程的情况下完成交易。在其他情况下，对用户提供的数据的验证不完善或缺失可能允许用户对交易关键值进行任意更改或提交无意义的输入。通过向服务器端逻辑传递非预期值，攻击者可以诱使应用程序执行它本不该执行的操作。

## 业务逻辑漏洞是如何产生的？

业务逻辑漏洞通常是由于设计和开发团队对用户如何与应用程序交互做出了错误的假设。这些错误的假设可能导致对用户输入的验证不足。例如，如果开发人员假设用户将仅通过 Web 浏览器传递数据，则应用程序可能完全依赖薄弱的客户端控制来验证输入。攻击者使用拦截代理可以轻松绕过这些控制。

最终，这意味着当攻击者偏离预期的用户行为时，应用程序未能采取适当措施来阻止这种情况，并随后未能安全地处理这种情况。

逻辑缺陷在过于复杂的系统中尤其常见，甚至连开发团队自己都无法完全理解。为了避免逻辑缺陷，开发人员需要整体理解应用程序。这包括了解不同功能如何以意外方式组合。在大型代码库上工作的开发人员可能无法深入了解应用程序所有区域的工作方式。负责一个组件的人可能对另一个组件的工作方式做出错误的假设，从而无意中引入严重的逻辑缺陷。如果开发人员没有明确记录所做的任何假设，这些类型的漏洞很容易潜入应用程序。

## 业务逻辑漏洞会造成什么影响？

业务逻辑漏洞的影响有时可能相当微不足道。这是一个广泛的类别，影响程度差异很大。然而，如果攻击者能够以正确的方式操纵应用程序，任何非预期的行为都可能潜在地导致严重攻击。因此，即使您自己无法弄清楚如何利用，也最好修复异常的逻辑。总是存在其他人能够利用的风险。

从根本上说，任何逻辑缺陷的影响取决于它与什么功能相关。例如，如果缺陷在身份验证机制中，这可能对您的整体安全性产生严重影响。攻击者可能利用它进行权限提升，或完全绕过身份验证，从而访问敏感数据和功能。这也为其他攻击暴露了更大的攻击面。

金融交易中的逻辑缺陷显然可能通过资金被盗、欺诈等给企业造成巨大损失。

您还应注意，即使逻辑缺陷可能不允许攻击者直接获益，它们仍然可能允许恶意方以某种方式损害企业。

## 逻辑测试的挑战

当攻击应用程序的逻辑缺陷时，渗透测试员既要进行系统性地探查，也要从不同的角度思考问题。如前所述，渗透测试员应该始终执行各种关键检查以确定应用程序在收到反常输入后的行为。这类反常输入包括从请求中删除参数、使用强制浏览不按预定顺序访问功能，以及向应用程序的不同位置提交参数。通常，应用程序响应这些操作的方式会反应出一些存在缺陷的假设。

除了这些基本的测试外，在探查逻辑缺陷时面临的最大挑战，是如何深入了解开发者的思维方式。需要了解他们想要达到什么目的、可能会做出什么假设、可能采用哪些捷径、将会犯下什么错误。如何利用这些错误？

大多数业务逻辑问题围绕着参数篡改、缺乏验证、工作流验证不足和竞争条件。这些都是攻击者可以利用来操纵应用程序预期流程或访问未授权信息的常见向量。

以下示例将说明理解应用程序功能、开发人员意图以及一些创造性的“跳出框框”思维如何能够破坏应用程序的逻辑。

**示例 1**：

假设一个电子商务网站允许用户选择要购买的商品、查看汇总页面，然后进行销售结算。如果攻击者能够返回到汇总页面，保持相同的有效会话，并注入较低的商品价格以完成交易，然后结账，会怎样？

**示例 2**：

持有/锁定资源并阻止其他人在线购买这些商品，此时相关商品的业务几乎被冻结。解决此问题的对策是实施超时和机制

**示例 3**：

如果用户能够启动其账户关联的交易，然后在积分已添加到其账户后取消交易，会怎样？积分/信用额是否仍会应用到其账户？

## 常见的业务逻辑漏洞

业务逻辑漏洞相对特定于它们发生的上下文。然而，尽管逻辑缺陷的个别实例差异很大，但它们可以共享许多共同主题（如 Web 参数篡改、竞争条件和 IDOR）。特别是，它们可以根据最初引入漏洞的错误类型进行粗略分组。

让我们评估一些常见的业务逻辑漏洞——并讨论利用它们的方法。

### 自定义数学漏洞

与数学相关的漏洞是最常见的业务逻辑漏洞形式之一。几乎所有应用都代表用户使用数学进行计算，但数学运算背后的逻辑往往不同。

考虑示例应用 MegaBank。在前面的章节中，我们注意到 MegaBank 为其客户托管的 Web 应用允许已认证用户通过向另一用户发送货币来完成交易。

让我们考虑在像 MegaBank 这样的应用中转账是什么样的：

1. 当前已认证用户（用户 A）在用户界面中指定他们希望向用户 B 发送 500 美元。
2. 服务器验证用户 B 存在。
3. 服务器向用户 A 发送确认请求。
4. 用户 A 向服务器发送确认“接受”请求。
5. 服务器通过将数据库中与用户 A 关联的余额字段减少 500 来从用户 A 中扣除。
6. 服务器将 500 添加到数据库中与用户 B 关联的余额字段。
7. 服务器向用户 A 发送交易完成的确认。

现在，这种转账方法在冗余性、故障安全和并发性方面存在许多问题。出于本章的目的，让我们仅评估服务器上为完成此交易而执行的数学运算可能出现什么问题。

首先，虽然服务器检查以确保用户 B 存在，但并未检查用户 A 是否实际拥有转账给用户 B 所需的资金。一个简单的对用户 A 余额的缺失验证（检查是否有足够的金额进行转账）可能会带来多种后果。

在最好的情况下，数据库模式中的验证会取消交易并报错——尽管应用在其代码中缺少适当的业务逻辑检查。在最坏的情况下，用户 A 的资金在 $0 处停止，而用户 B 的资金继续每笔交易增加 $500。这允许用户 B 和用户 A 合作，在银行注意到之前提取数千美元。

上述示例实际上是一个非常简单的业务逻辑漏洞。

如果一个应用未能实现以下两个要求，它将成为黑客利用的绝佳目标：

- 满足其业务逻辑期望的适当数学运算
- 对数学函数输入进行适当的验证

由于这些漏洞依赖于银行关于转账的特定业务模型，因此不太可能被任何静态分析工具发现。

你可以将针对此漏洞的攻击描述为黑客找到一种方法，在遵守编程规则的同时绕过预期功能。

### 编程副作用

大多数应用在编程时都考虑到了主要用例，该用例用于开发应用将运行的业务规则。通常，随着 Web 应用复杂性的增加，应用将开始产生副作用，即由于以开发者未预见的方式使用编程功能而发生的非预期变化。

考虑另一个 Web 应用：MegaCrypto。在这个假设的 Web 应用中，MegaBank 用户能够使用新的 MegaCrypto 门户网站相互购买、出售和转换加密货币。MegaBank 预测这将提高其在更年轻、更懂技术的客户中的受欢迎程度。

与其他交易所一样，MegaBank 知道它需要流动性来支持用户的购买、出售和加密货币转换。它决定最初提供五种主要的加密货币币种。MegaCrypto 出售这些货币的价格将由市场需求决定。当 MegaCrypto 推出时，MegaBank 假设本地市场汇率将反映 MegaCrypto 决定在其平台上提供的加密货币币种的全球市场汇率。在 MegaCrypto 上出售和交换的币种如下：

- MegaCoin
- ByteCoin
- DoggoCoin
- GhostCoin
- HardDriveCoin

因为此应用的预期功能是市场需求决定加密货币的购买或交换汇率，当前汇率如下：

- MegaCoin——$1
- GhostCoin——$2,000
- HardDriveCoin——$10
- ByteCoin——$50,000
- DoggoCoin——$5

每晚午夜，MegaCrypto 通过首先从其用户处购买（如果已提交卖出订单），然后从另一家交易所购买来补充其流动性池。MegaCrypto 的业务逻辑以这种方式运作，首先从其出售的用户处回购加密货币，因为这减少了 MegaCrypto 原本需要支付给另一家交易所的流动性购买费用。

MegaCrypto 的客户 Henry Hacker 能够查看公共记录，并注意到 MegaCrypto 在流动性低时首先从其用户处回购币种。换句话说，他已经逆向工程了 MegaCrypto 用于维护流动性池的业务逻辑。他在侦察日志中记录了这一情况。

Henry Hacker 观察到，新交易所在任何给定时间持有的总币量相当低。换句话说，在满负荷情况下，该交易所的流动性仅占全球加密货币市场的一小部分——实际上，它仅占一组投资者能够汇集资金的一小部分。在任何给定时间，流动性储备中持有的总币量约为 100 万美元。

在执行了几次交易并观察新交易所按市场汇率从现有用户处购买以补充其流动性池后，Henry Hacker 决定请他的富豪朋友筹集一些资金供他投资。他获得了 100 万美元的初始资本。

Henry 看到，随着时间的推移，MegaCrypto 交易所对 ByteCoin 的需求平均为每天 20 笔购买（按每枚 $50,000 的价格计算，总额为 100 万美元）。他注意到每年平均有 20 枚 ByteCoin 从 MegaCrypto 的流动性池流出到其用户的 MegaCrypto 钱包。

同样，每天下午 MegaCrypto 以当地市场汇率在其本地用户池中创建 20 枚 ByteCoin 的买单。通过在夜间以当地汇率从本地用户回购币种，MegaCrypto 最终从交易费中获得可观收益，其用户也很满意。

Henry 决定编写一个算法，每晚自动以 $50,000 的汇率购买 20 枚 ByteCoin，这与全球市场汇率相匹配。之后，他的脚本将立即以每枚 $100,000 的价格将这些 ByteCoin 挂单出售。在将此算法部署到生产环境后，他在前一天仅投资 100 万美元的情况下，醒来时账户中有 200 万美元。

Henry 所做的实际上可能并不违法，但根据 MegaCrypto 的标准，这绝对会被视为一个漏洞。如果不迅速修复，可能每天给 MegaCrypto 造成数百万美元的损失。

这里的问题是 MegaCrypto 的应用逻辑没有考虑到有限的本地流动性池可能不够大，无法模拟全球市场价格。此外，如此小的总流动性池允许非常富有的个人（或在本例中是一个团体）操纵市场上下波动。

MegaCrypto 是一个数字货币交易所，这意味着它所要做的就是在应用中包含逻辑，以防止在没有本地币种以全球市场汇率提供时购买本地币种（并转向其他地方）。

表面上看是经济问题，实际上也是一个业务逻辑漏洞。MegaCrypto 的这些重大损失本可以通过适当的边缘情况检测来避免，该检测允许 MegaCrypto 仅在价格在平均全球市场价格的一定百分比阈值内时才回购本地币种。

这类漏洞需要深入理解复杂系统，但一旦获得这些知识，就可能以高利润且难以检测的方式攻击 Web 应用或一组数字系统。

### 准现金攻击

到目前为止，我们看了因数学运算不当而产生的业务逻辑漏洞，以及因预期功能的副作用未被适当纳入初始应用架构而产生的业务逻辑漏洞。

然而，有时主要功能本身也可能容易受到业务逻辑漏洞的影响，尤其是当主要功能涉及多个协同工作的系统时。在信用卡行业，最常见（且代价高昂）的业务逻辑漏洞形式之一是准现金交易漏洞。

考虑我们示例公司 MegaBank 提供的以下信用卡。这张卡称为 MegaCard，具有以下属性：

- 25% 年利率
- $0 年费
- 所有购买 5% 现金返还（前三年）

这是 MegaBank 向其客户提供的第一张卡。它是内部开发的，而不是 MegaBank 销售由 Visa 或 Mastercard 等主要成熟卡供应商生产的产品。

假设是 MegaBank 从其其他业务部门赚取大量资金，因此在这张卡推出后的前三年内，5% 的**立即现金返还**将得到适当资金支持，以吸引新客户。假设所有竞争对手都提供较低的现金返还率，因此该利率将推动 MegaCard 的大规模市场普及。

Henry Hacker 看到高现金返还率，决定申请一张 MegaCard。起初他对非常高的现金返还率感到满意，但在被 EvilCorp 解雇后，他急需现金。

在 EvilCorp 工作时，他花了很多时间处理 API，用于将替代数字支付方法集成到 EvilCorp 的业务部门中。其中一个工具称为 PayBuddy。它提供一个在线门户，供应商可以注册、创建发票、接收付款，并将收入直接存入企业银行账户。

PayBuddy 每笔交易仅收取 1% 的费用，这对 Henry 的前雇主 EvilCorp 很有吸引力。在学习如何使用 PayBuddy 的 API 时，Henry Hacker 设置了自己的商家账户，将其连接到他的银行账户，并在下班后用于测试。

在被 EvilCorp 解雇后不久，Henry 想出了一个主意：

1. Henry 使用他在 PayBuddy 上的商家账户，创建一张 $1,000 的发票，用于一分钟的咨询。
2. 然后他会用他的 MegaCard  向 Henry 自己的**商家账户**支付 $1,000 的发票。
3. 现在他的 MegaCard 上会有 $1,000 的信用额度，但他的商家账户中会有 $990 的借方（$1,000，扣除 1% 的费用）。
4. 接下来，他将获得 5%（信用卡奖励率）的 $1,000 购买金额的返现，即 $50，存入他的**个人银行账户**。
5. 在第 4 步之后，Henry 会将 $990 从 PayBuddy 商家账户转入他的个人银行账户。
6. 最终，Henry 的个人银行账户将包含 $1,040（来自 PayBuddy 的 $990 和来自 MegaCard 的 $50 奖励），比他开始时的 $1,000 多 $40。

通过反复重复这一系列交易，Henry 每个周期将不断为他的个人银行账户增加 $40 的净资产。手动操作这将是一个缓慢而乏味的过程。然而，Henry Hacker 创建了一个脚本，能够每分钟重复上述所有步骤一次。有了这种自动化，他现在每小时赚取 $2,400 的 MegaCard 奖励。在短短 24 小时内，Henry 可以通过此漏洞赚取 $57,600 的奖励——足以支付他一整年的租金。

最后一步，Henry 在 MegaBank 注意到之前兑现了他的余额。MegaBank 只能承担账单，因为从技术上讲，Henry 没有违反服务协议中的任何规则。

在这种情况下，MegaCard 按设计工作。该卡是“安全的”，对购买提供 5% 的现金返还，并且易于使用。MegaCard 的设计没有考虑到的是，MegaCard 客户同时也可以是供应商，从而能够对自己进行快速自动化的购买。

这被称为准现金交易漏洞，因为 PayBuddy 实际上并不是银行账户。相反，它是一个金融中介，允许程序化的商业交易，这些交易最终将以真实货币结算，但在此之前，它们实际上只是数据库中的字段。

如果 MegaCard 独立存在于更传统（非数字）的经济中，Henry Hacker 可能以易于预测的方式进行交易。购买杂货、看电影或在餐厅用餐是 MegaBank 假设 Henry Hacker 会为了使用这张新信用卡而进行的活动。

不幸的是，由于 MegaBank 未在运行 MegaCard 的服务器上的应用逻辑中包含制衡机制，Henry 能够利用此业务逻辑漏洞赚取数万美元。



### 同账户的自我转账漏洞，导致资金翻倍

在一次渗透测试中，发现了一个银行应用程序的漏洞，该漏洞允许用户作为受益人向自己的账户转账，导致相应账户金额翻倍。漏洞的根本原因是未能执行验证检查，以防止账户所有者将自己添加为受益人并向自己的账户汇款，这可能导致未授权交易。此漏洞可能导致用户账户中的财务资源膨胀，或可能耗尽另一个账户的资源。

以下是渗透测试期间发送的一个伪匿名化和哈希化请求的示例：

**请求**
```http
POST /api/transfer HTTP/1.1
Host: vulnerablebank.com
Content-Type: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9

{
    "beneficiary_account": "46452132",
    "sender_account": "46452132",
    "amount": "1000",
    "currency": "USD",
    "transaction_id": "xyz3523"
}
```

在此示例中，用户发送请求，从其账户（987654321）向其自己的受益人账户（123456789）转账 1,000 美元。由于缺乏验证，转账金额将在受益人账户中翻倍，造成财务差异和未授权交易。


### 同账户的自我活动奖励，导致无限制钱包余额

某网约车应用程序实现了一项名为“为朋友预订”的功能，旨在鼓励用户为朋友和家人预订车辆。预订者会获得 5 美元的钱包充值作为奖励。然而，应用程序未能正确验证 `friend_number` 参数中提供的手机号是否与预订者（`user_number`）的手机号不同。这种缺乏验证的情况允许恶意用户通过“为朋友预订”功能反复为自己预订车辆，从而多次获得 5 美元奖励，无限增加其钱包余额。

应用程序未执行服务器端逻辑验证，以确保 `friend_number` 参数中提供的手机号与预订者（`user_number`）的手机号不同。此外，API 端点缺乏速率限制，允许用户在短时间内发出无限数量的请求。

这种疏忽允许用户通过反复为自己预订车辆来利用该功能，从而多次获得推荐奖励。以下 HTTP 请求演示了该漏洞：

**请求**
```
POST /api/v1/users/friend_referral_reward/ HTTP/1.1
Host: secure.example.com
Content-Type: application/json; charset=UTF-8
Content-Length: 204
Connection: close
Accept-Encoding: gzip, deflate
User-Agent: okhttp/3.12.1

{
    "user_number": "123456789012",
    "friend_number": "123456789012",
    "user_id": "abc123def456ghi789",
    "token_id": "zyx987wvu654tsr321"
}
```

在此示例中，`user_number` 和 `friend_number` 参数都包含相同的手机号，允许用户为自己预订车辆并获得奖励。应用程序未执行足够的服务器端逻辑检查以防止此情况。

### 身份验证漏洞/会话固定 -> 业务逻辑缺陷，购物车合并

一家在线零售商店实现了一项功能，使用 `cart_session` Cookie 在浏览器会话期间跟踪购物车项目。然而，该 Cookie 具有较长的过期时间，并且缺少 `HTTPOnly` 标志，使其可被客户端脚本访问。

此外，当用户登录其账户时，身份验证前购物车中的项目会与已认证购物车中的任何项目合并。然而，`cart_session` Cookie 在交易完成之前保持不变。在线零售商店允许购买数字礼品卡，并直接发送到购买时设置的用户电子邮件。

如果攻击者通过 XSS 或在共享计算机上的信息泄露获得 `cart_session`，他们可以添加任何他们选择的项目，包括发送到攻击者电子邮件的数字礼品卡，一旦受害者完成支付。让我们逐步了解攻击者为重现此漏洞所采取的步骤：

1. 攻击者使用前面讨论的任何攻击方法获取受害者的 `cart_session` ID。

2. 攻击者将会话 ID 注入浏览器，并向受害者的购物车添加设置了攻击者电子邮件的礼品卡。

3. 受害者登录零售商店网站后，应用程序合并受害者和攻击者的项目，因为 `cart_session` Cookie 保持不变。

## 易受攻击的标准与约定

根据您所针对的应用，业务逻辑漏洞可能从容易发现到需要大量领域特定知识才能识别不等。然而，您可以应用一些技巧来使发现这些漏洞更容易一些。这些技巧通常表现为由常见反模式产生的边缘情况，而程序员在不理解其影响的情况下使用了这些反模式。让我们讨论数字精度损失，这是其中一个技巧。

如前所述，业务逻辑漏洞通常涉及某种形式的数学运算，要么输入处理不当，要么结构不正确导致非预期输出。如果代码在您无法访问的服务器上执行，可能难以正确猜测数学函数的结构以及哪些边缘情况已被考虑在内。

幸运的是，由于数学是一个标准化的系统，一些常见错误可能会引导您找到逻辑漏洞。其中一个例子源于理解大多数编程语言如何处理数字。

几乎每种主要编程语言都使用 IEEE754 浮点数格式（JavaScript、Java、Ruby、Python 等）。使用这种数字格式是因为计算机中的内存是（或至少曾经是）稀缺的，导致人们希望使用更有效的方法来存储极长的数字，而不是简单地将每个位存储在内存中。

与其他格式相比，IEEE754 通过使用浮点（可变位置小数与固定位置小数）并依赖科学计数法来表示数字，提供了一种高效的数字存储机制。

使用 IEEE754 的缺点是，为了实现更节省内存的数字存储，IEEE754 有一个权衡，即牺牲精度以换取空间。这意味着，在任何涉及小数点的计算中，结果值可能被近似，但与真实数学结果不完全相同。

尝试以下步骤：

1. 打开 Chrome Web 浏览器。
2. 导航到开发者工具（通常是 F12 快捷键）。
3. 点击 Console 标签。
4. 对 Chrome 的 v8 JavaScript 解释器执行 JavaScript 代码。
5. 输入以下代码：`0.1 + 0.2`。
6. 点击 Enter。

您会期望在这种情况下 JavaScript 解释器返回正确的数学结果 0.3，但实际返回的是 `0.30000000000000004`。发生这种情况是因为 IEEE754 数字格式无法表示 0.1 + 0.2 的和，因此它以精度损失来近似结果。

在本例中，精度损失为 0.0000000000000004，这是一个极小的数字，在大多数情况下不会导致任何不正确的计算。然而，在处理金融计算时——尤其是快速自动化的计算——这种计算误差可能在短时间内累积成一笔可观的金额。

想象一个金融应用在重新加载时重新计算用户账户余额。如果 0.0000000000000004 的误差直接加到余额上，需要数百万次重新计算才能使真实余额与记录余额显著不同。

另一方面，如果涉及更复杂的计算，其中和相乘或更糟的是求幂，这可能很快失控，导致记录余额与实际余额出现巨大差异。因此，许多业务逻辑漏洞源于不当的数学计算。理解数学运算的常见实现方式将使您在 Web 应用中寻找这些漏洞时具有优势。

总之，虽然业务逻辑漏洞特定于应用的业务逻辑，但大多数应用在实现上有相似之处，可以用于洞察业务逻辑漏洞可能存在于何处。

在本例中，通过了解编程语言默认如何处理浮点数，您获得了一些可以开始手动测试的表面区域。

## 利用业务逻辑漏洞

现在我们已经看到了许多业务逻辑漏洞，显然逻辑漏洞很难具体分类，因为它们与特定应用的特定预期用例紧密相关。

当尝试使用业务逻辑漏洞攻击 Web 应用时，您需要做的第一件事是深入了解该应用的预期用例。使用 MegaCard 示例——将您的思维框架设定为 MegaBank 的典型 MegaCard 客户。您想使用该卡购买杂货、看电影和外出就餐。

写下您能想到的该应用或技术的每一个预期用例。然后，对于每个预期用例，确保详细说明您想象它在后端（应用逻辑中）是如何工作的。

例如，MegaCard 的笔记可能如下所示：

1. 我使用 MegaCard 在 FoodCo 购买杂货。
2. 一旦我刷卡，MegaBank 和 FoodCo 之间会执行某种类型的网络握手。
3. MegaBank 的数据库将相当于我购买的食品价值的信用添加到我的卡上，这将在我还清余额时从我的银行账户中结算。
4. MegaBank 的服务器计算相当于食品购买金额 5% 的金额，并在单独的交易中，将其从我的个人银行账户中扣除。

更复杂的应用功能（如市场操纵示例）将需要更多时间和精力来理解和绘制地图。一旦您绘制了所有预期功能以及您对应用在服务器内部工作原理的最佳猜测，现在您就准备好开始计划攻击了。

对于您记录的每个功能，考虑可能未得到适当处理的边缘情况。这些可能如下所示：

- 如果我以加元购买 $1,000 的杂货，我会获得 5%（$50）的美元返现，还是会进行货币转换？
- 如果我在 PayBuddy 上设置一个在线商家商店，考虑到费用与奖励的差异（1% 对 5%），我能否在零成本交易上净赚 4%？
- 如果我设置一个在线商家账户，我能否执行一张 -$1,000 的负发票，将资金加到我的信用卡余额中而不是减去？
- 如果我购买然后立即退款，我是否仍保留 5% 的奖励？

这些边缘情况是您在考虑通过业务逻辑漏洞利用 MegaCard 时的初始攻击向量。

如先前示例所示，利用业务逻辑漏洞的最常见方法是找到应用代码中未适当处理的业务逻辑边缘情况。

注意：在此过程中也应当关注操作对应的参数，推测其作用

## 小结

业务逻辑漏洞是 Web 应用中最难发现的高级漏洞形式。这些漏洞通常具有重大影响，并且很难或不可能以自动化方式检测。

发现业务逻辑漏洞通常需要真正的独创性、创造力和跳出框架思考的能力。

## 如何防止业务逻辑漏洞？

简而言之，防止业务逻辑漏洞的关键是：

- 确保开发人员和测试人员了解应用程序所服务的领域
- 避免对用户行为或应用程序其他部分的行为做出隐含的假设

您应该识别您对服务器端状态所做的假设，并实现必要的逻辑来验证这些假设是否得到满足。这包括在继续之前确保任何输入的值都是合理的。

确保开发人员和测试人员都能充分理解这些假设以及应用程序在不同场景下应如何反应也很重要。这有助于团队尽早发现逻辑缺陷。为促进这一点，开发团队应尽可能遵循以下最佳实践：

- 为所有交易和工作流维护清晰的设计文档和数据流，注明在每个阶段所做的任何假设。
- 尽可能清晰地编写代码。如果难以理解应该发生什么，就很难发现任何逻辑缺陷。理想情况下，编写良好的代码应该不需要文档就能理解。在不可避免的复杂情况下，生成清晰的文档对于确保其他开发人员和测试人员了解所做的假设以及确切的预期行为至关重要。
- 注明使用每个组件的其他代码的所有引用。如果有恶意方以异常方式操纵这些依赖项，请考虑它们的任何副作用。

由于许多逻辑缺陷具有相对独特的性质，很容易将它们视为一次性的人为错误而忽略并继续前进。然而，正如我们所展示的，这些缺陷通常是应用程序构建初期阶段不良实践的结果。分析逻辑缺陷最初存在的原因，以及团队是如何遗漏它的，可以帮助您发现流程中的弱点。通过进行细微调整，您可以增加类似缺陷在源头被切断或在开发过程中更早被发现的可能性。
