# WebSocket 安全漏洞测试

在本节中，我们将解释如何操纵 WebSocket 消息和连接，描述 WebSocket 可能引发的各种安全漏洞，并给出一些利用 WebSocket 漏洞的示例。

## WebSocket

WebSocket 在现代 Web 应用程序中被广泛使用。它们通过 HTTP 发起，并提供双向异步通信的持久连接。

WebSocket 可用于各种目的，包括执行用户操作和传输敏感信息。实际上，常规 HTTP 中出现的任何 Web 安全漏洞，都可能在与 WebSocket 通信相关的情境中出现。

> **延伸阅读**
> [什么是 WebSocket？](https://portswigger.net/web-security/websockets/what-are-websockets)

## 操纵 WebSocket 流量

发现 WebSocket 安全漏洞通常涉及以应用程序预期之外的方式操纵它们。你可以使用 Burp Suite 来完成此操作。

你可以使用 Burp Suite 进行以下操作：

- [拦截和修改 WebSocket 消息](#intercepting-and-modifying-websocket-messages)
- [重放和生成新的 WebSocket 消息](#replaying-and-generating-new-websocket-messages)
- [操纵 WebSocket 连接](#manipulating-websocket-connections)

### 拦截和修改 WebSocket 消息

你可以使用 Burp Proxy 按如下方式拦截和修改 WebSocket 消息：

1. 打开 Burp 的浏览器。
2. 浏览使用 WebSocket 的应用程序功能。你可以通过使用该应用程序并查看 Burp Proxy 的 WebSockets 历史选项卡中出现的条目来确定是否正在使用 WebSocket。
3. 在 Burp Proxy 的 Intercept 选项卡中，确保拦截已开启。
4. 当浏览器或服务器发送 WebSocket 消息时，它会显示在 Intercept 选项卡中，供你查看或修改。点击 Forward 按钮转发该消息。

> **注意**
> 你可以在 Burp Proxy 中配置是拦截客户端到服务器还是服务器到客户端的消息。请在设置对话框的 [WebSocket 拦截规则](https://portswigger.net/burp/documentation/desktop/settings/tools/proxy#websocket-interception-rules) 设置中进行配置。

### 重放和生成新的 WebSocket 消息

除了即时拦截和修改 WebSocket 消息外，你还可以重放单个消息并生成新消息。你可以使用 Burp Repeater 执行此操作：

- 在 Burp Proxy 中，在 WebSockets 历史记录或 Intercept 选项卡中选择一条消息，然后从上下文菜单中选择 "Send to Repeater"。
- 在 Burp Repeater 中，你现在可以编辑所选消息，并反复发送。
- 你可以输入新消息，并在任意方向（向客户端或服务器）发送。
- 在 Burp Repeater 的 "History" 面板中，你可以查看通过该 WebSocket 连接传输的消息历史记录。这包括你在 Burp Repeater 中生成的消息，以及由浏览器或服务器通过同一连接生成的任何消息。
- 如果你想编辑并重新发送历史面板中的任何消息，可以通过选择该消息并从上下文菜单中选择 "Edit and resend" 来完成。

### 操纵 WebSocket 连接

除了操纵 WebSocket 消息之外，有时还需要操纵建立连接的 [WebSocket 握手](https://portswigger.net/web-security/websockets/what-are-websockets#how-are-websocket-connections-established)。

操纵 WebSocket 握手可能必要的场景有多种：

- 它可以让你接触更多的攻击面。
- 某些攻击可能导致你的连接断开，因此你需要建立新连接。
- 原始握手请求中的令牌或其他数据可能已失效，需要更新。

你可以使用 Burp Repeater 操纵 WebSocket 握手：

- 按[前述方法](https://portswigger.net/web-security/websockets#replaying-and-generating-new-websocket-messages)将 WebSocket 消息发送到 Burp Repeater。
- 在 Burp Repeater 中，点击 WebSocket URL 旁边的铅笔图标。这将打开一个向导，允许你附加到现有的已连接 WebSocket、克隆已连接的 WebSocket，或重新连接到已断开连接的 WebSocket。
- 如果你选择克隆已连接的 WebSocket 或重新连接到已断开连接的 WebSocket，则向导将显示 WebSocket 握手请求的完整详细信息，在执行握手之前，你可以根据需要对其进行编辑。
- 当你点击 "Connect" 时，Burp 将尝试执行配置的握手并显示结果。如果成功建立了新的 WebSocket 连接，则你可以使用它在 Burp Repeater 中发送新消息。

## WebSocket 安全漏洞

原则上，几乎任何 Web 安全漏洞都可能与 WebSocket 相关：

- 用户提供的输入传输到服务器时可能以不安全的方式处理，导致 SQL 注入或 XML 外部实体注入等漏洞。
- 某些通过 WebSocket 可达的盲注漏洞可能只能使用[带外（OAST）技术](https://portswigger.net/blog/oast-out-of-band-application-security-testing)才能检测到。
- 如果攻击者控制的数据通过 WebSocket 传输给其他应用程序用户，则可能导致 XSS 或其他客户端漏洞。

### 操纵 WebSocket 消息以利用漏洞

影响 WebSocket 的大多数基于输入的漏洞都可以通过[篡改 WebSocket 消息的内容](https://portswigger.net/web-security/websockets#intercepting-and-modifying-websocket-messages)来发现和利用。

例如，假设一个聊天应用程序使用 WebSocket 在浏览器和服务器之间发送聊天消息。当用户A输入聊天消息时，会向服务器发送如下 WebSocket 消息：

```json
{"message":"Hello Carlos"}
```

该消息的内容（再次通过 WebSocket）传输给另一个聊天用户B

```json
{"user":"User_A","content":"Hello Carlos"}
```

并在用户的浏览器中呈现如下：

```html
<td>Hello Carlos</td>
```

在这种情况下，如果没有其他输入处理或防御措施，攻击者可以通过提交以下 WebSocket 消息来执行概念验证 XSS 攻击：

```json
{"message":"<img src=1 onerror='alert(1)'>"}
```

> 注意区分发送到服务器与发送到客户端这两类信息，使用的字段或不同

### 操纵 WebSocket 握手以利用漏洞

某些 WebSocket 漏洞只能通过[操纵 WebSocket 握手](https://portswigger.net/web-security/websockets#manipulating-websocket-connections)来发现和利用。这些漏洞往往涉及设计缺陷，例如：

- 错误地信任 HTTP 头来执行安全决策，例如 `X-Forwarded-For` 头。
- 会话处理机制中的缺陷，因为处理 WebSocket 消息的会话上下文通常由握手消息的会话上下文决定。
- 应用程序使用的自定义 HTTP 头引入的攻击面。

### 使用跨站点 WebSocket 利用漏洞

当攻击者从攻击者控制的网站发起跨域 WebSocket 连接时，就会产生某些 WebSocket 安全漏洞。这称为跨站点 WebSocket 劫持攻击，它涉及利用 WebSocket 握手上的跨站请求伪造（CSRF）漏洞。该攻击通常具有严重影响，允许攻击者代表受害用户执行特权操作，或捕获受害用户有权访问的敏感数据。

> **延伸阅读**
> [跨站点 WebSocket 劫持](https://portswigger.net/web-security/websockets/cross-site-websocket-hijacking)

## 如何保护 WebSocket 连接

为了最大程度降低 WebSocket 带来的安全漏洞风险，请遵循以下指南：

- 使用 `wss://` 协议（基于 TLS 的 WebSocket）。
- 硬编码 WebSocket 端点的 URL，并且绝对不要将用户可控的数据并入此 URL。
- 保护 WebSocket 握手消息免受 CSRF 攻击，以避免跨站点 WebSocket 劫持漏洞。
- 将经由 WebSocket 接收的数据视为双向不可信的数据。在服务器端和客户端都安全地处理数据，以防止基于输入的漏洞，例如 SQL 注入和跨站脚本攻击。
