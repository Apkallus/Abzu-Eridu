# 控制 Web 消息源

在本节中，我们将探讨如何利用 Web 消息作为源，在接收页面上利用基于 DOM 的漏洞。我们还将描述此类攻击的构造方式，包括常见的来源验证技术通常如何被绕过。

如果页面以不安全的方式处理传入的 Web 消息，例如在事件监听器中未正确验证传入消息的来源，则事件监听器调用的属性和函数可能成为“汇”。例如，攻击者可以托管一个恶意 `iframe`，并使用 `postMessage()` 方法将 Web 消息数据传递给存在漏洞的事件监听器，然后该监听器将负载发送到父页面上的汇。这种行为意味着你可以使用 Web 消息作为源，将恶意数据传播到任何这些汇中。

## 基于 DOM 的 Web 消息漏洞有何影响？

漏洞的潜在影响取决于目标文档对传入消息的处理方式。如果目标文档信任发送者不会在消息中传输恶意数据，并以不安全的方式将数据传递到汇中，则两个文档的联合行为可能允许攻击者危害用户。

## 如何利用 Web 消息作为源构造攻击

考虑以下代码：

```html
<script>
    window.addEventListener('message', function(e) {
        eval(e.data);
    });
</script>
```

此代码存在漏洞，因为攻击者可以通过构造以下 `iframe` 来注入 JavaScript 负载：

```html
<iframe src="//vulnerable-website" onload="this.contentWindow.postMessage('print()','*')"></iframe>
```

由于事件监听器未验证消息的来源，且 `postMessage()` 方法指定了 `targetOrigin` 为 `"*"`，事件监听器接受该负载并将其传递到汇中（此处为 `eval()` 函数）。

当汇点为动态 HTML 插入（如，`innerHTML`）时：

```html
<iframe src="//vulnerable-website" onload="this.contentWindow.postMessage('<img src onerror=print()>','*')"></iframe>
```

## 来源验证

即使事件监听器确实包含某种形式的来源验证，该验证步骤有时也可能存在根本性缺陷。例如，考虑以下代码：

```javascript
window.addEventListener('message', function(e) {
    if (e.origin.indexOf('normal-website.com') > -1) {
        eval(e.data);
    }
});
```

此处使用 `indexOf` 方法来尝试验证传入消息的来源是否为 `normal-website.com` 域。然而，实际上它仅检查字符串 `"normal-website.com"` 是否出现在来源 URL 的任何位置。因此，如果攻击者恶意消息的来源是 `http://www.normal-website.com.evil.net`，他们可以轻松绕过此验证步骤。

同样的缺陷也适用于依赖 `startsWith()` 或 `endsWith()` 方法的验证检查。例如，以下事件监听器会将来源 `http://www.malicious-websitenormal-website.com` 视为安全的：

```javascript
window.addEventListener('message', function(e) {
    if (e.origin.endsWith('normal-website.com')) {
        eval(e.data);
    }
});
```

## 哪些汇可能导致基于 DOM 的 Web 消息漏洞？

只要网站因缺乏充分的来源验证而接受来自不受信任来源的 Web 消息数据，传入消息事件监听器所使用的任何汇都可能潜在地导致漏洞。
