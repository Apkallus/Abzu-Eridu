# CORS 与 Access-Control-Allow-Origin 响应头

在本节中，我们将解释 `Access-Control-Allow-Origin` 头与 CORS 的关系，以及它如何构成 CORS 实现的一部分。

[跨域资源共享](https://portswigger.net/web-security/cors) 规范通过使用一组 HTTP 头，为从一个网站域到另一个网站域的 HTTP 请求提供了同源策略的受控放宽。浏览器根据这些头指令，允许访问跨域请求的响应。

## 概述

按照最初的设计，XMLHttpRequest 仅允许向与调用页面的来源相同的来源提出请求。随着 HTML5 的出现，这一技术已得以修改，从而可以与其他域进行双向交互，前提是被访问的域为交互提供权限(设置HTTP消息头部)。

如果某个脚本尝试使用 XMLHttpRequest 提出跨域请求，处理该请求的方式将因请求的具体内容而异。

- 对于“常规”请求，即可以使用现有的 HTML 结构跨域生成的请求，浏览器将提出请求，并检查生成的响应消息头，以确定是否应允许调用脚本访问该请求的响应。

- 其他无法使用现有的HTML生成的请求，如那些使用非标准 HTTP 方法或 Content-Type、或添加了定制 HTTP 消息头的请求，将进行不同处理。浏览器会首先向目标URL提出一个 OPTIONS 预检请求，然后检查响应消息头，以确定是否应允许那些请求。

在上述两种情况下，浏览器都会添加一个`Origin`消息头，用于指示尝试提出跨域请求的域。

要确定可能执行双向交互的域，服务器的响应中应包含`Access-Control-Allow-Origin`消息头，其中包括以逗号分隔的允许的域列表和通配符

在第二种情况下，如果已使用OPTIONS请求预先验证了跨域请求，则使用以下消息头来指示尝试提出的请求的具体内容

- `Access-Control-Request-Method` 
- `Access-Control-Request-Haders`

为响应OPTIONS请求，服务器使用以下消息头来指定允许提出的跨域请求的类型

- `Access-Control-Allow-Origin`
- `Access-Control-Allow-Methods`
- `Access-Control-Allow-Headers`
- `Access-Control-Max-Age`

### 渗透测试步骤

1. 要测试应用程序如何使用 XMLHttpRequest 处理跨域请求，测试员应尝试添加一个用于指定其他域的 Origin 消息头，并检查返回的任何 Access-Control 消息头。

2. 如果有任何跨域访问受到支持，则测试员还应使用 OPTIONS 请求来了解到底允许哪些消息头和其他请求。

攻击者在载荷端点页面设置对目标脆弱敏感端点的访问，获取数据后发送到攻击者数据接收端点以窃取数据。

更常见的是攻击者可以借助 XMLHttpRequest 的特性，利用恶意或被攻破的网站，通过访问网站用户的浏览器来实施攻击，即使这时跨域访问已遭到禁止。跨域端口扫描表明，使用 XMLHttpRequest 尝试向任意主机和端口提出请求，并观察响应的时间差异，可以推断所请求的端口是否已打开、关闭或被过滤。此外，与传统的生成跨域请求的方法相比，使用 XMLHttpRequest 可以更快速地实施分布式拒绝服务攻击。如果目标应用程序禁止跨域访问，则需要在 URL 参数中增加一个值，以确保每个请求针对不同的 URL，因此实际上由浏览器提出。

## 什么是 Access-Control-Allow-Origin 响应头？

`Access-Control-Allow-Origin` 头包含在一个网站对来自另一个网站的请求的**响应**中，用于标识允许的请求来源。Web 浏览器会将 `Access-Control-Allow-Origin` 与请求网站的来源进行比较，如果匹配则允许访问响应。

## 实现简单的跨域资源共享

跨域资源共享（CORS）规范规定了 Web 服务器和浏览器之间交换的头内容，这些头限制了源域之外的 Web 资源请求的来源。CORS 规范定义了一组协议头，其中 `Access-Control-Allow-Origin` 是最重要的。当网站请求跨域资源时，浏览器会添加 `Origin` 头，服务器会返回此头。`Origin` 头不能通过 JavaScript 更改，[浏览器（用户代理）将阻止其修改](https://developer.mozilla.org/en-US/docs/Glossary/Forbidden_header_name)

例如，假设一个源为 `normal-website.com` 的网站发起以下跨域请求：

```http
GET /data HTTP/1.1
Host: robust-website.com
Origin : https://normal-website.com
```

`robust-website.com` 上的服务器返回以下响应：

```http
HTTP/1.1 200 OK
...
Access-Control-Allow-Origin: https://normal-website.com
```

由于来源匹配，浏览器将允许在 `normal-website.com` 上运行的代码访问该响应。

`Access-Control-Allow-Origin` 的规范允许多个来源、值 `null` 或通配符 `*`。但是，没有浏览器支持多个来源，并且对通配符 `*` 的使用有限制。

## 处理带有凭据的跨域资源请求

跨域资源请求的默认行为是不传递 Cookie 和 Authorization 头等凭据。但是，跨域服务器可以通过将 CORS 头 `Access-Control-Allow-Credentials` 设置为 `true`，来允许**在传递凭据时读取响应**。此时，如果请求网站使用 JavaScript 声明它将在请求中发送 Cookie：

```http
GET /data HTTP/1.1
Host: robust-website.com
...
Origin: https://normal-website.com
Cookie: JSESSIONID=<value>
```

并且对请求的响应为：

```http
HTTP/1.1 200 OK
...
Access-Control-Allow-Origin: https://normal-website.com
Access-Control-Allow-Credentials: true
```

那么，由于 `Access-Control-Allow-Credentials` 响应头设置为 `true`，浏览器将允许请求网站读取响应。否则，浏览器将不允许访问响应。

## 使用通配符放宽 CORS 规范

`Access-Control-Allow-Origin` 头支持通配符。例如：

```http
Access-Control-Allow-Origin: *
```

> **注意**
> 通配符不能用于任何其他值中。例如，以下头是**无效**的：
> `Access-Control-Allow-Origin: https://*.normal-website.com`

幸运的是，从安全角度来看，规范中对通配符的使用进行了限制，因为你不能将通配符与跨域传输凭据（身份验证、Cookie 或客户端证书）结合使用。因此，跨域服务器响应如下形式：

```http
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true
```

是不被允许的，因为这将是危险的不安全的，会将目标站点上的任何经过身份验证的内容暴露给所有人。

鉴于这些限制，一些 Web 服务器会根据客户端指定的来源动态创建 `Access-Control-Allow-Origin` 头。这是对 CORS 限制的一种变通方法，但并不安全。我们将在后面向你展示[如何利用这一点](https://portswigger.net/web-security/cors#server-generated-acao-header-from-client-specified-origin-header)。

## 预检请求

预检检查被添加到[W3C CORS 规范](https://www.w3.org/TR/cors/)中，以保护传统资源免受 CORS 允许的扩展请求选项的影响。在某些情况下，当跨域请求包含非标准的 HTTP 方法或头时，跨域请求之前会有一个使用 `OPTIONS` 方法的请求，并且 CORS 协议要求在允许跨域请求之前，先对允许的方法和头进行初始检查。这称为预检请求。服务器除了返回受信任的来源外，还返回允许的方法列表，浏览器会检查请求网站的方法是否被允许。

例如，这是一个试图使用 `PUT` 方法以及名为 `Special-Request-Header` 的自定义请求头的预检请求：

```http
OPTIONS /data HTTP/1.1
Host: <some website>
...
Origin: https://normal-website.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Special-Request-Header
```

服务器可能会返回如下响应：

```http
HTTP/1.1 204 No Content
...
Access-Control-Allow-Origin: https://normal-website.com
Access-Control-Allow-Methods: PUT, POST, OPTIONS
Access-Control-Allow-Headers: Special-Request-Header
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 240
```

此响应列出了允许的方法（`PUT`、`POST` 和 `OPTIONS`）和允许的请求头（`Special-Request-Header`）。在这种特定情况下，跨域服务器还允许发送凭据，并且 `Access-Control-Max-Age` 头定义了缓存预检响应以供重用的最大时间范围。如果请求方法和头被允许（如此示例中所示），则浏览器将照常处理跨域请求。预检检查为跨域请求增加了一次额外的 HTTP 请求往返，因此增加了浏览开销。

额外头部：
- `Access-Control-Expose-Headers`，它指示哪些头部可以安全地暴露给 CORS API 规范的 API。

## CORS 能防范 CSRF 吗？

CORS 不能防范跨站请求伪造（CSRF）攻击，这是一个常见的误解。

CORS 是对同源策略的受控放宽，因此配置不当的 CORS 实际上可能会增加 CSRF 攻击的可能性或加剧其影响。

有多种方法可以在不使用 CORS 的情况下执行 CSRF 攻击，包括简单的 HTML 表单和跨域资源包含。

## 通过代理服务应用程序跨域 - 历史

一些公开发布的Web应用程序提供高效的代理服务功能，允许从不同域检索内容，但服务于代理Web应用程序中的用户。Google翻译（GT）就是一个典型的例子，它可以请求指定的外部URL并返回其内容（虽然翻译引擎可能会修改检索到的响应中的文本，但基本的HTML标记和任何脚本代码仍保持不变。

如果两个不同的外部域均通过GT应用程序访问，这时可能会一个有趣的问题。这种情况下，在浏览器看来，来自每个外部域的内容将驻留在GT域中，因为这是浏览器从中检索内容的域。虽然两组内容均驻留在同一个域中，它们之间可以进行双向交互（如果这种交互也通过GT域实施的话）。
