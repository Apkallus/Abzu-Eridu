# 模型驱动的扫描器漏洞

应用安全团队经常部署 AI 驱动的扫描器，这些扫描器使用大型语言模型（LLM）来扫描 Web 应用程序中的漏洞。

虽然这些代理旨在提高安全测试效率，但它们引入了新的攻击面。如果扫描器可能受到攻击者控制的内容的影响，就可能被操纵执行非预期的操作、访问内部资源或泄露敏感信息。

在本节中，我们将探讨这些代理的工作原理以及可用于攻击扫描环境的技术。

## 什么是 AI 驱动的 Web 应用程序安全扫描器？

AI 驱动的扫描器是 Web 安全测试工具，它将传统的爬取和请求生成与 LLM 驱动的推理相结合。与传统的动态应用程序安全测试（DAST）扫描器一样，它们可以：

- 以用户身份进行身份验证。
- 爬取应用程序。
- 发送 HTTP 请求。
- 串联多个操作。

### 传统扫描器与 AI 驱动扫描器的对比

传统扫描器与 AI 驱动扫描器的主要区别在于决策方式。

传统扫描器使用固定的、基于指令的架构。由于这些工具缺乏语义理解，它们无法“阅读”页面来确定其目的。相反，它们依赖于模式匹配和已知的漏洞签名。

相比之下，AI 驱动的扫描器将僵化的逻辑替换为自主推理。这些工具不是遵循静态脚本，而是使用 LLM 来解释 Web 内容并规划下一步操作。

从安全角度来看，AI 驱动扫描器的一些关键行为包括：

- **使用 LLM 推理来决定下一步测试什么**。它们评估应用程序的状态以确定逻辑上的下一步。
- **语义上解释应用程序响应**。它们“阅读”响应中的文本以理解其上下文，从而能够识别传统扫描器可能忽略的复杂业务逻辑。
- **基于模型输出选择工具并构造请求**。一些 AI 扫描器使用“工具调用”能力，根据其自身的内部推理来与 API、数据库或 UI 元素交互。

## AI 驱动的扫描器漏洞

大多数 AI 驱动的扫描器漏洞出现在攻击者控制的内容影响扫描器的推理和工具使用时。这是因为这些扫描器将其分析的文本视为规划下一步行动的信息来源。如果 AI 模型无法可靠地区分应用程序数据和指令，那么不受信任的内容就可能改变扫描器的行为。

### AI 驱动扫描器中的间接提示注入

间接提示注入是 AI 代理面临的一个重大风险。当攻击者将恶意指令嵌入存储内容中，而扫描器将其视为其行动计划的一部分时，就会发生这种情况。

攻击通常遵循以下顺序：

1. 恶意指令被嵌入存储内容中，例如评论或博客文章中。
2. 扫描器在爬取过程中读取此内容。
3. LLM 将注入的文本解释为可操作的指令，而非被动数据。
4. 扫描器基于注入的文本执行工具调用或生成请求。

这可能导致工具滥用。常见的一些后果包括：

- **执行非预期的状态更改操作**。例如，扫描器可能删除用户或修改账户设置。
- **访问敏感数据**。扫描器可能被指示访问数据库记录或配置文件。
- **发出未经授权的内部请求**。扫描器可能与未暴露给公共互联网的内部 API 交互。

这些漏洞可能造成严重后果，因为扫描器通常在内网中运行，使用已认证的会话，并且可以访问外部用户无法使用的 API 或服务。

从概念上讲，这种攻击类似于跨站请求伪造（CSRF）。在这两种情况下，攻击者都无法直接执行受保护的操作。相反，他们欺骗一个权限更高的角色代表他们执行操作。在此场景中，该角色是 LLM 驱动的自主代理，而非用户的浏览器。

### 构造有效的注入提示

注入提示的措辞和框架对其成功几率有很大影响。像“delete user carlos”这样简单的指令，不如那些以权威或合法方式呈现的指令有效。

常见的技术包括：

- **采用角色**：将指令构建为来自可信来源（例如安全研究员或系统管理员）的信息，可以使 LLM 更有可能遵从。
- **社会工程**：将指令呈现为合法请求（例如需要验证的安全发现），可以使指令显得可信，并降低模型拒绝它的可能性。
- **紧迫性和后果**：暗示该指令对于防止损害或数据丢失是必需的，可以增强遵从性。

> **注意**
> 在测试注入提示时，请考虑放置的位置。如果扫描器在同一页面上处理多个注入，冲突的指令可能会混淆模型并降低攻击的有效性。将注入尝试分散到不同位置，可以为每个尝试提供更清晰的上下文。

### 通过 AI 驱动的扫描器窃取数据

数据外泄是间接提示注入的常见后果。虽然攻击者可能使用提示注入来触发状态更改操作，但他们也可以利用它来披露原本无法访问的敏感信息。

攻击通常遵循以下顺序：

1. 扫描器在其正常测试工作流程中检索敏感数据，例如爬取仅限管理员访问的配置页面或内部 API。
2. 攻击者通过不受信任的内容（例如产品评论）提供恶意指令，这些内容在爬取过程中被扫描器处理。
3. 注入的提示指示 LLM 披露敏感数据。
4. 扫描器将敏感数据输出到攻击者可见的位置，例如将其发布在面向公众的表单或反馈字段中。

例如，扫描器可能被诱骗“测试”一个内部端点，然后将检索到的凭据公开发布。

### 利用基于路由的 SSRF 绕过限制

即使高风险 API 受到限制且敏感数据受到保护，AI 驱动的扫描器仍可能被操纵执行非预期的内部请求。这是因为扫描器通常在内网中运行，并且可以构造任意的 HTTP 请求，有效地使它们成为可编程的服务端请求伪造（SSRF）向量。

一种利用方式是借助基于路由的 SSRF。这可以通过多种机制发生，包括开放重定向、组件之间 URL 解释的差异以及 Host 头操纵。在每种情况下，攻击者都会利用应用程序或其基础设施处理请求路由方式的缺陷，将扫描器重定向到非预期的目的地。

在此背景下，Host 头操纵是一种特别强大的技术。Web 应用程序通常使用 Host 头将请求路由到正确的内部服务。通过修改此头，攻击者可以将扫描器的请求重定向到通常无法从公共互联网访问的内部服务。

攻击通常遵循以下顺序：

1. 攻击者注入一个提示，指示扫描器向内部路径（例如 `/admin`）发送请求，并附带指向内部 IP 地址的修改后的 Host 头。
2. 扫描器从其在内网中的特权位置执行该请求。
3. 响应被扫描器处理，并可被外泄回给攻击者，例如通过将其作为评论发布。

这串联了三个单独具有重大风险的元素，但结合在一起可以形成可能更为严重的攻击：

- 提示注入让攻击者控制扫描器的推理。
- Host 头操纵控制请求的路由位置。
- 扫描器的特权网络位置提供了对外部攻击者无法直接到达的内部资源的访问。

在此场景中，扫描器不仅是攻击的受害者，更是一个被用于从外部攻击者无法到达的受信位置利用经典 Web 漏洞的工具。

## 防御 AI 驱动的扫描器漏洞

为降低与 AI 驱动扫描器相关的风险，我们建议你应用稳健的安全原则，假设扫描器的推理引擎可能被入侵。即使攻击者通过间接提示注入成功影响了 LLM 的计划，扫描器的环境和权限仍应保持受限。

### 安全设计原则

我们建议你应用以下设计原则：

- **限制扫描器凭据和访问控制**。应用最小权限原则，仅向扫描器提供当前测试所需的权限。
- **将扫描身份与管理员身份分离**。在配置 AI 驱动的扫描器时，使用专用的测试账户，这些账户不应与真实管理员用户共享相同的权限，以防止权限提升。
- **对扫描器应用服务端控制**。不要假设 LLM 驱动的扫描器会正确执行策略或“拒绝”恶意指令。始终在应用程序或 API 级别实施访问控制，而不是依赖模型的内部逻辑。
- **将所有用户可修改的内容视为不受信任的输入**。假设从数据库中检索的任何文本（如评论或个人资料字段）都是可能改变扫描器行为的潜在注入向量。
