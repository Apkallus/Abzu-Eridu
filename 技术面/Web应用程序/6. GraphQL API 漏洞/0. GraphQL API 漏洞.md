# GraphQL API 漏洞

GraphQL 漏洞通常源于实现和设计缺陷。例如，自省（introspection）功能可能被保留为开启状态，使攻击者能够查询 API 以获取其架构信息。

GraphQL 攻击通常以恶意请求的形式发起，这些请求可使攻击者获取数据或执行未经授权的操作。此类攻击可能造成严重影响，特别是当用户能够通过操纵查询或执行 CSRF 漏洞利用来获得管理员权限时。易受攻击的 GraphQL API 还可能导致信息泄露问题。

在本节中，我们将探讨如何测试 GraphQL API。即使你不熟悉 GraphQL 也不必担心——我们会在过程中介绍相关细节。我们还提供了一些实验室，供你练习所学内容。

![GraphQL 示例](https://portswigger.net/web-security/graphql/images/graphql-graphic.png)

> **更多信息**
> - 要了解 GraphQL 是什么及其工作原理，请参阅我们的 Web Security Academy 页面：[什么是 GraphQL](https://portswigger.net/web-security/graphql/what-is-graphql)。
> - 要学习如何在 Burp Suite 中使用 GraphQL，请参阅[使用 GraphQL](https://portswigger.net/burp/documentation/desktop/testing-workflow/working-with-graphql)。

## 查找 GraphQL 端点

在测试 GraphQL API 之前，首先需要找到其端点。由于 GraphQL API 对所有请求使用相同的端点，因此这是一条有价值的信息。

> **注意**
> 本节介绍如何手动探测 GraphQL 端点。不过，Burp Scanner 可以在扫描过程中自动测试 GraphQL 端点。如果发现任何此类端点，它会发出“发现 GraphQL 端点”问题。

### 通用查询

如果你向任何 GraphQL 端点发送 
- `query{__typename}`
```json
{
    "query": "query{__typename}"
}
```

它会在响应中包含字符串 
- `{"data": {"__typename": "query"}}`

这被称为通用查询，是探查 URL 是否对应 GraphQL 服务的有用工具。

该查询有效的原因是每个 GraphQL 端点都有一个名为 `__typename` 的保留字段，它以字符串形式返回所查询对象的类型。

### 常见端点名称

GraphQL 服务通常使用类似的端点后缀。在测试 GraphQL 端点时，你应尝试向以下位置发送通用查询：

```
/graphql
/api
/api/graphql
/graphql/api
/graphql/graphql
```

如果这些常见端点未返回 GraphQL 响应，你也可以尝试在路径前后附加 `/v1`。

> **注意**
> GraphQL 服务通常会对任何非 GraphQL 请求返回 "query not present" “查询不存在”或类似错误。在测试 GraphQL 端点时应记住这一点。

更全面的列表，见 [SecLists 的 discovery/graphql.txt](https://github.com/danielmiessler/SecLists/blob/master/Discovery/Web-Content/graphql.txt)

### 请求方法

寻找 GraphQL 端点的下一步是尝试使用不同的请求方法。

生产环境 GraphQL 端点的最佳实践是仅接受内容类型为 `application/json` 的 POST 请求，因为这有助于防止 CSRF 漏洞。然而，某些端点可能接受替代方法，例如 GET 请求或使用 `x-www-form-urlencoded` 内容类型的 POST 请求。

如果无法通过向常见端点发送 POST 请求找到 GraphQL 端点，请尝试使用其他 HTTP 方法重新发送通用查询。

### 初始测试

一旦发现端点，你可以发送一些测试请求以进一步了解其工作方式。如果该端点为网站提供支持，请尝试在 Burp 的浏览器中浏览 Web 界面，并使用 HTTP 历史记录检查发送的查询。

## 利用未清理的参数

此时，你可以开始寻找漏洞。测试查询参数是一个不错的起点。

如果 API 使用参数直接访问对象，则可能存在访问控制漏洞。用户只需提供与相应信息对应的参数，就可能获取本不该访问的信息。这有时被称为不安全的直接对象引用（IDOR）。

> **更多信息**
> - 有关 GraphQL 参数的一般说明，请参阅[参数](https://portswigger.net/web-security/graphql/what-is-graphql#arguments)。
> - 有关 IDOR 的更多信息，请参阅[不安全的直接对象引用（IDOR）](https://portswigger.net/web-security/access-control/idor)。

例如，以下查询请求了在线商店的产品列表：

```graphql
# 示例产品查询

query {
    products {
        id
        name
        listed
    }
}
```

返回的产品列表仅包含上架产品。

```json
# 示例产品响应

{
    "data": {
        "products": [
            {
                "id": 1,
                "name": "Product 1",
                "listed": true
            },
            {
                "id": 2,
                "name": "Product 2",
                "listed": true
            },
            {
                "id": 4,
                "name": "Product 4",
                "listed": true
            }
        ]
    }
}
```

根据这些信息，我们可以推断出：

- 产品按顺序分配 ID。
- 产品 ID 3 从列表中缺失，可能是因已下架。

通过查询缺失产品的 ID，我们可以获取其详细信息，即使它未在商店中列出，也未在原始产品查询中返回。

```graphql
# 获取缺失产品的查询

query {
    product(id: 3) {
        id
        name
        listed
    }
}
```

```json
# 缺失产品的响应

{
    "data": {
        "product": {
        "id": 3,
        "name": "Product 3",
        "listed": no
        }
    }
}
```

## 发现架构信息

测试 API 的下一步是拼凑有关底层架构的信息。

最好的方法是使用自省查询。自省是 GraphQL 的一项内置功能，使你能够向服务器查询有关架构的信息。

自省有助于你了解如何与 GraphQL API 交互，也可能披露敏感数据，如描述字段。

### 使用自省

要使用自省发现架构信息，请查询 `__schema` 字段。该字段在所有查询的根类型上可用。

与常规查询一样，你可以在运行自省查询时指定要返回的响应字段和结构。例如，你可能希望响应仅包含可用变异的名称。

> **注意**
> Burp 可以为你生成自省查询。更多信息，请参阅[使用自省访问 GraphQL API 架构](https://portswigger.net/burp/documentation/desktop/testing-workflow/working-with-graphql#accessing-graphql-api-schemas-using-introspection)。

### 探测自省

最佳实践是在生产环境中禁用自省，但这一建议并不总是被遵循。

你可以使用以下简单查询来探测自省是否启用。如果自省已启用，响应将返回所有可用查询的名称。

```json
# 自省探测请求

{
    "query": "{__schema{queryType{name}}}"
}
```

> **注意**
> Burp Scanner 可以在扫描过程中自动测试自省功能。如果发现自省已启用，它会报告“GraphQL 自省已启用”问题。

### 运行完整自省查询

下一步是向端点运行完整自省查询，以尽可能多地获取底层架构信息。

以下示例查询返回所有查询、变异、订阅、类型和片段的信息。

```graphql
# 完整自省查询

query IntrospectionQuery {
    __schema {
        queryType {
            name
        }
        mutationType {
            name
        }
        subscriptionType {
            name
        }
        types {
             ...FullType
        }
        directives {
            name
            description
            args {
                ...InputValue
            }
            onOperation  # 运行查询时通常需要删除
            onFragment   # 运行查询时通常需要删除
            onField      # 运行查询时通常需要删除
        }
    }
}

fragment FullType on __Type {
    kind
    name
    description
    fields(includeDeprecated: true) {
        name
        description
        args {
            ...InputValue
        }
        type {
            ...TypeRef
        }
        isDeprecated
        deprecationReason
    }
    inputFields {
        ...InputValue
    }
    interfaces {
        ...TypeRef
    }
    enumValues(includeDeprecated: true) {
        name
        description
        isDeprecated
        deprecationReason
    }
    possibleTypes {
        ...TypeRef
    }
}

fragment InputValue on __InputValue {
    name
    description
    type {
        ...TypeRef
    }
    defaultValue
}

fragment TypeRef on __Type {
    kind
    name
    ofType {
        kind
        name
        ofType {
            kind
            name
            ofType {
                kind
                name
            }
        }
    }
}
```

> **注意**
> 如果自省已启用但上述查询无法运行，请尝试从查询结构中删除 `onOperation`、`onFragment` 和 `onField` 指令。许多端点不接受这些指令作为自省查询的一部分，删除它们通常能提高成功率。

字段：
- `kind` 类型
- `name` 对象/字段名
- `args` 方法的参数
- `type` 字段、函数返回值类型

### 可视化自省结果

自省查询的响应可能包含大量信息，但通常非常冗长且难以处理。

使用 [GraphQL 可视化工具](http://nathanrandal.com/graphql-visualizer/) 更轻松地查看架构实体之间的关系。这是一个在线工具，它接收自省查询的结果，并生成返回数据的可视化表示，包括操作和类型之间的关系。

- nathanrandal 的可视化工具丢失部分数据，或需寻找类似工具

其他工具：
- https://apis.guru/graphql-voyager/

### 建议（Suggestions）

即使自省被完全禁用，有时你也可以利用“建议”功能来获取 API 结构的信息。

建议是 Apollo GraphQL 平台的一项功能，服务器可以在错误消息中建议查询的修正。这些通常用于查询略有错误但仍可识别的情况（例如，`There is no entry for 'productInfo'. Did you mean 'productInformation' instead?`）。

你可以从中获取有用的信息，因为响应实际上泄露了架构的有效部分。

[Clairvoyance](https://github.com/nikitastupin/clairvoyance) 是一个工具，即使自省被禁用，它也能利用建议自动恢复全部或部分 GraphQL 架构。这大大节省了从建议响应中拼凑信息的时间。

在 Apollo Server v4 及以上版本中，你可以使用 `hideSchemaDetailsFromClientErrors` 选项禁用建议。对于更早版本，请参阅[此 GitHub 讨论线程](https://github.com/apollographql/apollo-server/issues/3919#issuecomment-836503305)以获取变通方法。

> **注意**
> Burp Scanner 可以在扫描过程中自动测试建议功能。如果发现建议功能处于启用状态，它会报告“GraphQL 建议已启用”问题。

## 绕过 GraphQL 自省防御

如果无法为你正在测试的 API 运行自省查询，请尝试在 `__schema` 关键字后插入特殊字符。

当开发人员禁用自省时，他们可能会使用正则表达式来排除查询中的 `__schema` 关键字。你应尝试使用空格、换行和逗号等字符，因为 GraphQL 会忽略它们，但有缺陷的正则表达式不会。

因此，如果开发人员仅排除了 `__schema{`，则以下自省查询不会被排除。

```json
# 包含换行的自省查询

{
    "query": "query{__schema
    {queryType{name}}}"
}
```

如果这不起作用，请尝试通过替代请求方法运行探测，因为自省可能仅在 POST 请求上被禁用。尝试 GET 请求，或使用 `x-www-form-urlencoded` 内容类型的 POST 请求。

以下示例展示了通过 GET 发送的自省探测，带有 URL 编码参数。

```http
# 作为 GET 请求的自省探测

GET /graphql?query=query%7B__schema%0A%7BqueryType%7Bname%7D%7D%7D
```

> **注意**
> 你可以将 GraphQL 查询保存到站点地图。更多信息，请参阅[使用 GraphQL](https://portswigger.net/burp/documentation/desktop/testing-workflow/working-with-graphql)。

## 使用别名绕过速率限制

通常情况下，GraphQL 对象不能包含多个同名的属性。别名通过显式命名你希望 API 返回的属性，使你可以绕过此限制。你可以使用别名在一次请求中返回同一类型对象的多个实例。

> **更多信息**
> 有关 GraphQL 别名的更多信息，请参阅[别名](https://portswigger.net/web-security/graphql/what-is-graphql#aliases)。

虽然别名旨在减少你需要发出的 API 调用次数，但它们也可用于暴力破解 GraphQL 端点。

许多端点会实施某种速率限制器来防止暴力破解攻击。某些速率限制器基于收到的 HTTP 请求数量而非端点上执行的操作数量。由于别名实际上使你可以通过单个 HTTP 消息发送多个查询，因此可以绕过此限制。

以下简化示例展示了一系列别名的查询，用于检查商店折扣码是否有效。此操作可能绕过速率限制，因为即使它可以用来同时检查大量折扣码，它也只是单个 HTTP 请求。

```graphql
# 包含别名查询的请求

query isValidDiscount($code: Int) {
    isValidDiscount(code:$code){
        valid
    }
    isValidDiscount2:isValidDiscount(code:$code){
        valid
    }
    isValidDiscount3:isValidDiscount(code:$code){
        valid
    }
}
```

## GraphQL CSRF

跨站请求伪造（CSRF）漏洞使攻击者能够诱导用户执行非本意的操作。这是通过创建一个恶意网站来实现的，该网站向易受攻击的应用程序伪造跨域请求。

> **更多信息**
> 有关 CSRF 漏洞的更多信息，请参阅 [CSRF Academy 主题](https://portswigger.net/web-security/csrf)。

GraphQL 可用作 CSRF 攻击的向量，攻击者创建漏洞利用程序，诱使受害者的浏览器以受害用户的身份发送恶意查询。

### GraphQL CSRF 漏洞如何产生？

当 GraphQL 端点未验证发送给它的请求的内容类型，且未实施 CSRF 令牌时，就可能产生 CSRF 漏洞。

只要内容类型经过验证，使用 `application/json` 内容类型的 POST 请求是安全的，不易被伪造。在这种情况下，即使受害者访问恶意站点，攻击者也无法使受害者的浏览器发送此请求。（由于非常规 POST 类型将触发跨域的预检）

然而，替代方法如 GET，或任何内容类型为 `x-www-form-urlencoded` 的请求，可由浏览器发送，因此如果端点接受这些请求，用户可能面临攻击风险。在这种情况下，攻击者或许能够构造漏洞利用程序，向 API 发送恶意请求。

> 构造 CSRF 攻击和交付漏洞利用的步骤，对于基于 GraphQL 的 CSRF 漏洞与“常规”CSRF 漏洞相同。有关此过程的更多信息，请参阅[如何构造 CSRF 攻击](https://portswigger.net/web-security/csrf#how-to-construct-a-csrf-attack)。

- 将原 JSON 的名值对最外层双引号去除后，URL 编码作为表单参数

## 预防 GraphQL 攻击

为预防许多常见的 GraphQL 攻击，请在将 API 部署到生产环境时采取以下步骤：

- **如果 API 不面向公众使用，请禁用自省功能。** 这将使攻击者更难获取 API 工作方式的信息，并降低意外信息泄露的风险。有关如何在 Apollo GraphQL 平台中禁用自省的信息，请参阅[此博文](https://www.apollographql.com/blog/graphql/security/why-you-should-disable-graphql-introspection-in-production/#turning-off-introspection-in-production)。

- **如果 API 面向公众使用，则可能需要保留自省功能。** 但是，你应审查 API 的架构，确保其不会向公众暴露非预期的字段。

- **确保建议功能已禁用。** 这将防止攻击者使用 Clairvoyance 或类似工具获取底层架构的信息。在 Apollo Server v4 及以上版本中，你可以使用 `hideSchemaDetailsFromClientErrors` 选项禁用建议。对于更早版本，请参阅[此 GitHub 讨论线程](https://github.com/apollographql/apollo-server/issues/3919#issuecomment-836503305)以获取变通方法。

- **确保 API 的架构不暴露任何私有用户字段，例如电子邮件地址或用户 ID。**

### 预防 GraphQL 暴力破解攻击

在使用 GraphQL API 时，有时可以绕过标准速率限制。有关示例，请参阅[使用别名绕过速率限制](#bypassing-rate-limiting-using-aliases)部分。

考虑到这一点，你可以采取一些设计步骤来保护 API 免受暴力破解攻击。这通常涉及限制 API 接受的查询复杂度，并减少攻击者执行拒绝服务（DoS）攻击的机会。

为防御暴力破解攻击：

- **限制 API 查询的深度。** “查询深度”指查询中的嵌套层级数。深度嵌套的查询可能对性能产生重大影响，如果被接受，可能为 DoS 攻击提供机会。通过限制 API 接受的查询深度，你可以降低此风险。

- **配置操作限制。** 操作限制允许你配置 API 可以接受的最大唯一字段数、别名数和根字段数。

- **配置查询可包含的最大字节数。**

- **考虑对 API 实施成本分析。** 成本分析是一种过程，库应用程序通过该过程在收到查询时识别运行这些查询的资源成本。如果查询的计算复杂度过高，API 将丢弃它。

> **更多信息**
> 有关如何在 Apollo 中实现这些功能的信息，请参阅[此博文](https://www.apollographql.com/blog/graphql/security/securing-your-graphql-api-from-malicious-queries/)。

### 预防 GraphQL CSRF

为专门防御 GraphQL CSRF 漏洞，在设计 API 时请确保以下事项：

- API 仅接受基于 JSON 编码的 POST 查询。
- API 验证提供的内容与所声明的内容类型匹配。
- API 具有安全的 CSRF 令牌机制。
