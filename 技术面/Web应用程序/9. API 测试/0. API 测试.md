# API 测试

API（应用程序编程接口）使软件系统和应用程序能够相互通信和共享数据。API 测试非常重要，因为 API 中的漏洞可能会破坏网站机密性、完整性和可用性的核心方面。

所有动态网站都由 API 组成，因此 SQL 注入等经典 Web 漏洞也可归类为 API 测试。在本主题中，我们将教你如何测试网站前端未完全使用的 API，重点放在 RESTful 和 JSON API 上。我们还将教你如何测试可能影响内部 API 的服务端参数污染漏洞。

为了说明 API 测试与常规 Web 测试之间的重叠，我们在现有主题与 [OWASP API Security Top 10 2023](https://portswigger.net/web-security/api-testing/top-10-api-vulnerabilities) 之间建立了映射。

## API 侦查

要开始 API 测试，你首先需要尽可能多地收集有关 API 的信息，以发现其攻击面。

首先，你应该识别 API 端点。这些是 API 接收关于其服务器上特定资源请求的位置。例如，考虑以下 `GET` 请求：

```http
GET /api/books HTTP/1.1
Host: example.com
```

此请求的 API 端点是 `/api/books`，它会与 API 交互以从图书馆检索书籍列表。另一个 API 端点可能是 `/api/books/mystery`，它将检索悬疑类书籍列表。

识别端点后，你需要确定如何与它们交互。这使你能够构造有效的 HTTP 请求来测试 API。例如，你应该了解以下信息：

- API 处理的输入数据，包括必填和可选参数。
- API 接受的请求类型，包括支持的 HTTP 方法和媒体格式。
- 速率限制和身份验证机制。

## API 文档

API 通常都有文档，以便开发者了解如何使用和集成它们。

文档可以是人类可读和机器可读两种形式。人类可读的文档旨在帮助开发者理解如何使用 API，可能包含详细说明、示例和使用场景。机器可读的文档旨在供软件处理，用于自动化 API 集成和验证等任务，以 JSON 或 XML 等结构化格式编写。

API 文档通常是公开可用的，尤其是在 API 供外部开发者使用的情况下。如果是这样，务必从查阅文档开始你的侦查工作。

### 发现 API 文档

即使 API 文档未公开开放，你仍然可以通过浏览使用该 API 的应用程序来访问它。

为此，你可以使用 Burp Scanner 爬取 API。你也可以使用 Burp 的浏览器手动浏览应用程序。寻找可能引用 API 文档的端点，例如：

- `/api`
- `/swagger/index.html`
- `/openapi.json`

如果你识别了某个资源的端点，请务必调查其基础路径。例如，如果你识别了资源端点 `/api/swagger/v1/users/123`，则应调查以下路径：

- `/api/swagger/v1`
- `/api/swagger`
- `/api`

你也可以使用常见路径列表通过 Intruder 查找文档。

### 使用机器可读文档

你可以使用一系列自动化工具来分析你找到的任何机器可读 API 文档。

你可以使用 Burp Scanner 爬取和审计 OpenAPI 文档，或任何 JSON 或 YAML 格式的文档。你也可以使用 [OpenAPI Parser](https://portswigger.net/bappstore/6bf7574b632847faaaa4eb5e42f1757c) BApp 解析 OpenAPI 文档。

你也可以使用专用工具来测试文档中记录的端点，例如 [Postman](https://www.postman.com/) 或 [SoapUI](https://www.soapui.org/)。

## 识别 API 端点

你也可以通过浏览使用 API 的应用程序来收集大量信息。即使你可以访问 API 文档，这通常也值得做，因为有时文档可能不准确或已过时。

你可以使用 Burp Scanner 爬取应用程序，然后使用 Burp 的浏览器手动调查有趣的攻击面。

在浏览应用程序时，寻找 URL 结构中暗示 API 端点的模式，例如 `/api/`。同时留意 JavaScript 文件，它们可能包含你未通过 Web 浏览器直接触发的 API 端点引用。Burp Scanner 会在爬取期间自动提取部分端点，但如需更彻底的提取，可使用 [JS Link Finder](https://portswigger.net/bappstore/0e61c786db0c4ac787a08c4516d52ccf) BApp。你也可以在 Burp 中手动审查 JavaScript 文件。

### 与 API 端点交互

识别 API 端点后，使用 Burp Repeater 和 Burp Intruder 与之交互。这使你能够观察 API 的行为并发现额外的攻击面。例如，你可以调查 API 如何响应更改 HTTP 方法和媒体类型。

在与 API 端点交互时，仔细查看错误消息和其他响应。有时它们包含可用于构造有效 HTTP 请求的信息。

#### 识别支持的 HTTP 方法

HTTP 方法指定要对资源执行的操作。例如：

- `GET` - 从资源检索数据。
- `PATCH` - 对资源应用部分更改。
- `OPTIONS` - 检索关于资源上可用的请求方法类型的信息。

一个 API 端点可能支持不同的 HTTP 方法。因此，在调查 API 端点时，务必测试所有可能的方法。这可以让你识别额外的端点功能，从而打开更多攻击面。

例如，端点 `/api/tasks` 可能支持以下方法：

- `GET /api/tasks` - 检索任务列表。
- `POST /api/tasks` - 创建新任务。
- `DELETE /api/tasks/1` - 删除任务。

你可以使用 Burp Intruder 中的内置 **HTTP verbs** 列表来自动循环测试一系列方法。

> **注意**
> 在测试不同 HTTP 方法时，请以低优先级对象为目标。这有助于确保你避免意外后果，例如更改关键项目或创建过多记录。

#### 识别支持的内容类型

API 端点通常期望特定格式的数据。因此，它们的行为可能因请求中提供的数据内容类型而异。更改内容类型可以让你：

- 触发泄露有用信息的错误。
- 绕过有缺陷的防御措施。
- 利用处理逻辑的差异。例如，API 在处理 JSON 数据时可能是安全的，但在处理 XML 时可能容易受到注入攻击。

要更改内容类型，请修改 `Content-Type` 头，然后相应地重新格式化请求体。你可以使用 [Content type converter](https://portswigger.net/bappstore/db57ecbe2cb7446292a94aa6181c9278) BApp 自动将请求中提交的数据在 XML 和 JSON 之间转换。

#### 使用 Intruder 查找隐藏端点

识别一些初始 API 端点后，你可以使用 Intruder 发现隐藏端点。例如，考虑一个场景，你已识别了以下用于更新用户信息的 API 端点：

`PUT /api/user/update`

要识别隐藏端点，你可以使用 Burp Intruder 查找具有相同结构的其他资源。例如，你可以向路径的 `/update` 位置添加一个包含其他常见函数（如 `delete` 和 `add`）的负载。

在查找隐藏端点时，使用基于常见 API 命名约定和行业术语的单词列表。确保还包含基于你初始侦查的与应用程序相关的术语。

## 查找隐藏参数

在进行 API 侦查时，你可能会发现 API 支持未记录的参数。你可以尝试使用它们来改变应用程序的行为。Burp 包含多种工具，可帮助你识别隐藏参数：

- Burp Intruder 使你能够使用常见参数名称的单词列表自动发现隐藏参数，以替换现有参数或添加新参数。确保还包含基于你初始侦查的与应用程序相关的名称。
- [Param miner](https://portswigger.net/bappstore/17d2949a985c4b7ca092728dba871943) BApp 使你能够自动猜测每个请求多达 65,536 个参数名称。Param miner 会根据从范围中获取的信息自动猜测与应用程序相关的名称。
- [内容发现](https://portswigger.net/burp/documentation/desktop/tools/engagement-tools/content-discovery)工具使你能够发现未从可见内容链接的内容，包括参数。

### 批量赋值漏洞

批量赋值（也称为自动绑定）可能会无意中创建隐藏参数。当软件框架自动将请求参数绑定到内部对象的字段时，就会发生这种情况。因此，批量赋值可能导致应用程序支持开发者从未打算处理的参数。

#### 识别隐藏参数

由于批量赋值从对象字段创建参数，你通常可以通过手动检查 API 返回的对象来识别这些隐藏参数。

例如，考虑一个 `PATCH /api/users/` 请求，它允许用户更新其用户名和电子邮件，并包含以下 JSON：

```json
{
    "username": "wiener",
    "email": "wiener@example.com",
}
```

并发的 `GET /api/users/123` 请求返回以下 JSON：

```json
{
    "id": 123,
    "name": "John Doe",
    "email": "john@example.com",
    "isAdmin": "false"
}
```

这可能表明隐藏的 `id` 和 `isAdmin` 参数与更新的用户名和电子邮件参数一起被绑定到内部用户对象。

#### 测试批量赋值漏洞

要测试你是否可以修改枚举出的 `isAdmin` 参数值，请将其添加到 `PATCH` 请求中：

```json
{
    "username": "wiener",
    "email": "wiener@example.com",
    "isAdmin": false,
}
```

此外，发送一个带有无效 `isAdmin` 参数值的 `PATCH` 请求：

```json
{
    "username": "wiener",
    "email": "wiener@example.com",
    "isAdmin": "foo",
}
```

如果应用程序行为不同，这可能表明无效值影响了查询逻辑，而有效值没有。这可能表明用户能够成功更新该参数。

然后，你可以发送一个将 `isAdmin` 参数值设置为 `true` 的 `PATCH` 请求，以尝试利用该漏洞：

```json
{
    "username": "wiener",
    "email": "wiener@example.com",
    "isAdmin": true,
}
```

如果请求中的 `isAdmin` 值在未经充分验证和清理的情况下被绑定到用户对象，用户 `wiener` 可能被错误地授予管理员权限。要确定是否如此，请以 `wiener` 身份浏览应用程序，查看你是否可以访问管理功能。

## 预防 API 中的漏洞

在设计 API 时，确保从一开始就将安全性纳入考虑。具体来说，请确保：

- 如果你不打算让 API 公开访问，请保护你的文档。
- 确保你的文档保持最新，以便合法测试人员能够全面了解 API 的攻击面。
- 应用允许的 HTTP 方法白名单。
- 验证每个请求或响应的内容类型是否符合预期。
- 使用通用错误消息，避免泄露对攻击者有用的信息。
- 对你的 API 的所有版本都使用保护措施，而不仅仅是当前的生产版本。

为防止批量赋值漏洞，请允许用户可更新的属性白名单，并阻止不应由用户更新的敏感属性。
