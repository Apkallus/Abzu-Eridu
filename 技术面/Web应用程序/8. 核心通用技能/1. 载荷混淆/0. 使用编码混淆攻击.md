# 使用编码混淆攻击

在本节中，我们将展示如何利用网站执行的标准解码过程来绕过输入过滤器，从而注入有害负载，用于 XSS、SQL 注入等多种攻击。

## 上下文相关的解码

客户端和服务器都使用多种不同的编码方式在系统间传递数据。当它们需要使用数据时，通常必须先进行解码。解码步骤的确切顺序取决于数据出现的上下文。例如，查询参数通常在服务器端进行 URL 解码，而 HTML 元素的文本内容可能会在客户端进行 HTML 解码。

在构造攻击时，你应该考虑负载的确切注入位置。如果能够根据上下文推断输入是如何被解码的，那么你就有可能找到表示同一负载的替代方式。

## 解码差异

注入攻击通常涉及注入使用可识别模式的负载，例如 HTML 标签、JavaScript 函数或 SQL 语句。由于这些负载的输入几乎不会预期包含用户提供的代码或标记，网站通常会实施防御措施，阻止包含这些可疑模式的请求。

然而，这类输入过滤器也需要对输入进行解码，以检查其是否安全。从安全角度来看，检查输入时执行的解码必须与后端服务器或浏览器最终使用数据时执行的解码相同。任何差异都可能使攻击者通过应用不同的编码，在过滤器之后自动被移除，从而将有害负载偷偷带过过滤器。

## 通过 URL 编码进行混淆

在 URL 中，一系列保留字符具有特殊含义。例如，与号（`&`）用作查询字符串中分隔参数的定界符。问题是，基于 URL 的输入可能出于其他原因包含这些字符。考虑一个包含用户搜索查询的参数。如果用户搜索类似于“Fish & Chips”的内容，会发生什么？

浏览器会自动对任何可能对解析器造成歧义的字符进行 URL 编码。这通常意味着将它们替换为 `%` 字符及其两位十六进制代码，如下所示：

```text
[...]/?search=Fish+%26+Chips
```

这确保了与号不会被误认为是定界符。

> **注意**
> 虽然空格字符可以编码为 `%20`，但通常用加号（`+`）表示，如上例所示。

任何基于 URL 的输入都会在服务器端分配给相关变量之前自动进行 URL 解码。这意味着，对于大多数服务器而言，查询参数中的序列如 `%22`、`%3C` 和 `%3E` 分别等同于 `"`、`<` 和 `>` 字符。换句话说，你可以通过 URL 注入 URL 编码的数据，后端应用程序通常仍会正确解释。

偶尔，你可能会发现 WAF 等在检查输入时未能正确进行 URL 解码。在这种情况下，你可以简单地编码被列入黑名单的任何字符或单词，从而将负载走私到后端应用程序。例如，在 SQL 注入攻击中，你可以对关键字进行编码，使 `SELECT` 变成 `%53%45%4C%45%43%54` 等。

## 通过双重 URL 编码进行混淆

出于某种原因，某些服务器会对收到的任何 URL 执行两轮 URL 解码。只要安全机制在检查输入时也进行双重解码，这本身不一定是问题。否则，这种差异使攻击者只需对输入进行两次编码，即可将恶意输入走私到后端。

假设你试图通过查询参数注入标准的 XSS 概念验证负载，如 `<img src=x onerror=alert(1)>`。此时，URL 可能如下所示：

```text
[...]/?search=%3Cimg%20src%3Dx%20onerror%3Dalert(1)%3E
```

当检查请求时，如果 WAF 执行标准 URL 解码，它会轻松识别这个众所周知的负载。请求被阻止，无法到达后端。但如果你对注入进行双重编码呢？实际上，这意味着 `%` 字符本身被替换为 `%25`：

```text
[...]/?search=%253Cimg%2520src%253Dx%2520onerror%253Dalert(1)%253E
```

由于 WAF 只对其进行一次解码，它可能无法识别请求的危险性。如果后端服务器随后对输入进行双重解码，负载将被成功注入。

## 通过 HTML 编码进行混淆

在 HTML 文档中，某些字符需要转义或编码，以防止浏览器将其错误地解释为标记的一部分。这是通过将违规字符替换为引用来实现的，引用以与号开头，以分号结尾。在许多情况下，可以使用名称作为引用。例如，序列 `&colon;` 表示冒号字符。

或者，可以使用字符的十进制或十六进制代码点来提供引用，分别对应 `&#58;` 和 `&#x3a;`。

在 HTML 内的特定位置，例如元素文本内容或属性值，浏览器在解析文档时会自动解码这些引用。当在此类位置注入时，你可以偶尔利用这一点来混淆客户端攻击的负载，使其躲避任何已部署的服务器端防御。

如果你仔细观察前面示例中的 XSS 负载，会注意到负载是在 HTML 属性（即 `onerror` 事件处理器）内注入的。如果服务器端检查明确寻找 `alert()` 负载，那么你对其中一个或多个字符进行 HTML 编码后，它们可能无法发现：

```html
<img src=x onerror="&#x61;lert(1)">
```

当浏览器渲染页面时，它会解码并执行注入的负载。

### 前导零

有趣的是，在使用十进制或十六进制样式的 HTML 编码时，你可以选择性地在代码点中包含任意数量的前导零。一些 WAF 和其他输入过滤器未能充分考虑到这一点。

如果负载在 HTML 编码后仍被阻止，你可能会发现只需在代码点前添加几个零即可绕过过滤器：

```html
<a href="javascript&#00000000000058;alert(1)">Click me</a>
```

## 通过 XML 编码进行混淆

XML 与 HTML 密切相关，也支持使用相同的数字转义序列进行字符编码。这使你可以安全地在元素文本内容中包含特殊字符而不会破坏语法，例如在测试基于 XML 输入的 XSS 时会很有用。

即使不需要编码特殊字符来避免语法错误，你也可以利用此行为，以与 HTML 编码相同的方式混淆负载。不同之处在于，负载是由服务器自身解码的，而不是由浏览器在客户端解码。这对于绕过 WAF 和其他过滤器很有用，因为它们如果检测到与 SQL 注入攻击相关的某些关键字，可能会阻止请求。

```xml
<stockCheck>
    <productId>
        123
    </productId>
    <storeId>
        999 &#x53;ELECT * FROM information_schema.tables
    </storeId>
</stockCheck>
```

## 通过 Unicode 转义进行混淆

Unicode 转义序列由前缀 `\u` 后跟字符的四位十六进制代码组成。例如，`\u003a` 表示冒号。ES6 还支持一种使用花括号的新形式：`\u{3a}`。

在解析字符串时，大多数编程语言都会解码这些 Unicode 转义。这包括浏览器使用的 JavaScript 引擎。当在字符串上下文中注入时，你可以像上例中使用 HTML 转义一样，使用 Unicode 来混淆客户端负载。

例如，假设你试图利用 DOM XSS，而你的输入作为字符串传递给 `eval()` 汇点。如果初始尝试被阻止，请尝试按如下方式转义其中一个字符：

```javascript
eval("\u0061lert(1)")
```

由于这在服务器端将保持编码状态，因此可能不会被检测到，直到浏览器再次解码它。

> **注意**
> 在字符串内部，你可以像这样转义任何字符。但在字符串外部，转义某些字符会导致语法错误。例如，这包括左右括号。

另外值得注意的是，ES6 样式的 Unicode 转义也允许可选的前导零，因此一些 WAF 可能很容易像我们对 HTML 编码那样被欺骗。例如：

```html
<a href="javascript:\u{00000000061}alert(1)">Click me</a>
```

## 通过十六进制转义进行混淆

在字符串上下文中注入时的另一种选择是使用十六进制转义，它使用字符的十六进制代码点，前缀为 `\x`。例如，小写字母 `a` 表示为 `\x61`。

与 Unicode 转义一样，只要输入被评估为字符串，这些转义将在客户端被解码：

```javascript
eval("\x61lert")
```

请注意，有时你也可以使用前缀 `0x` 以类似方式混淆 SQL 语句。例如，`0x53454c454354` 可以被解码为 `SELECT` 关键字。

## 通过八进制转义进行混淆

八进制转义的工作方式与十六进制转义大致相同，不同之处在于字符引用使用八进制编号系统而非十六进制。它们以前缀为独立反斜杠，因此小写字母 `a` 表示为 `\141`。

```javascript
eval("\141lert(1)")
```

## 通过多重编码进行混淆

值得注意的是，你可以组合编码，将负载隐藏在多层混淆之后。看以下示例中的 `javascript:` URL：

```html
<a href="javascript:&bsol;u0061lert(1)">Click me</a>
```

浏览器首先会对 `&bsol;` 进行 HTML 解码，得到一个反斜杠。这样会将原本任意的 `u0061` 字符转换为 Unicode 转义 `\u0061`：

```html
<a href="javascript:\u0061lert(1)">Click me</a>
```

然后进一步解码，形成可执行的 XSS 负载：

```html
<a href="javascript:alert(1)">Click me</a>
```

显然，要成功以这种方式注入负载，你需要扎实理解对输入执行了哪些解码及其顺序。

## 通过 SQL CHAR() 函数进行混淆

尽管严格来说并非编码形式，但在某些情况下，你可以使用 `CHAR()` 函数来混淆 SQL 注入攻击。该函数接受一个十进制或十六进制代码点，并返回匹配的字符。十六进制代码必须以 `0x` 为前缀。例如，`CHAR(83)` 和 `CHAR(0x53)` 均返回大写字母 `S`。

通过连接返回的值，你可以使用此方法来混淆被阻止的关键字。例如，即使 `SELECT` 被列入黑名单，以下注入最初看起来是无害的：

```sql
CHAR(83)+CHAR(69)+CHAR(76)+CHAR(69)+CHAR(67)+CHAR(84)
```

但是，当应用程序将其作为 SQL 处理时，它将动态构造 `SELECT` 关键字并执行注入的查询。
