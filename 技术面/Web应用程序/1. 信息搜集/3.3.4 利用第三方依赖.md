# 利用第三方依赖

众所周知，当今的软件是构建在开源软件（OSS）之上的。即使在商业领域，许多最大、最赚钱的产品也是建立在全球大量开发者的开源贡献之上的。

一些构建在 OSS 之上的产品包括：

- Reddit（BackBoneJS、Bootstrap）
- Twitch（Webpack、nginx）
- YouTube（Polymer）
- LinkedIn（EmberJS）
- Microsoft Office Web（Angular）
- Amazon DocumentDB（MongoDB）

除了仅仅依赖 OSS 之外，许多公司现在将其核心产品作为开源软件提供，并通过支持或持续服务而非直接销售产品来获得收入。例如：

- Automattic Inc.（WordPress）
- Canonical（Ubuntu）
- Chef（Chef）
- Elastic（Elasticsearch）
- Mongo（MongoDB）
- GitLab（GitLab）
- Docker（Docker）

工具
- [BuiltWith](https://builtwith.com/zh/) 指纹识别其他 Web 应用构建技术。

依赖 OSS 虽然方便，但往往带来显著的安全风险。这种风险可以被机智和具有战略眼光的黑客所利用。OSS 可能对应用安全构成风险的原因有很多，所有原因都值得关注。

首先，依赖 OSS 意味着
- 不可控的初始审计
- 后续更新的审计：因为 OSS 代码库不断更新。理想情况下，应对每个传入的拉取请求进行安全评估。但这通常不会发生

因此，OSS 集成和依赖是想要入侵他人软件的黑客的绝佳起点。请记住，链条的强度取决于其最薄弱的环节，而最薄弱的环节往往是质量保证最不严格的环节。

作为黑客，发现要利用的 OSS 集成或依赖的第一步是侦察。侦察之后，对这些集成的可利用性可以从许多不同角度入手。

让我们进一步研究 OSS 集成。首先，我们希望了解 Web 应用如何与 OSS 集成的一些基础知识。

一旦我们理解了这些集成发生的基本原理，我们就可以进一步研究 OSS 集成的风险。然后我们可以学习如何利用 Web 应用中的 OSS 集成。

## 集成方法

当 Web 应用开发者希望与 OSS 应用集成时，从架构角度来看通常有几种方式。了解 Web 应用与 OSS 包之间的集成结构很重要，因为这通常决定了两者之间移动的数据类型、数据移动的方式，以及主应用赋予 OSS 代码的权限级别。

OSS 集成可以通过多种不同方式设置。
- 集中：直接集成到核心应用代码中。
- 分散：在自己的服务器上运行 OSS 代码，并设置一个 API，用于从主应用到 OSS 集成的单向通信。

### 分支与复刻（Fork）

如今的大多数 OSS 都托管在基于 Git 的版本控制系统（VCS）上。这是现代 Web 应用与传统 Web 应用之间的一个主要区别，因为 10 年前 OSS 可能托管在 Perforce、Subversion 甚至 Microsoft 的 Team Foundation Server 上。

与许多传统 VCS 不同，Git 是分布式的。这意味着，每个开发者下载自己的软件副本并在本地进行更改，而不是在中央服务器上进行更改。一旦在主构建的“分支”上进行了适当的修改，开发者就可以将其更改合并到主分支（唯一事实来源）中。

当开发者将 OSS 用于自己的目的时，有时他们会针对该软件创建一个分支，并运行他们创建的分支而不是主分支。这种工作流程允许他们进行自己的修改，同时轻松地从主分支中拉取其他开发者推送的更改。

分支模型带来风险。开发者更容易意外地将未审查的代码从主分支拉入其生产分支。而复刻则提供了更高程度的隔离，因为复刻是新的仓库，从复刻创建之前推送到主分支的最后一次提交开始。作为一个新仓库，复刻可以有自己的权限系统、自己的所有者，并实现自己的 Git 钩子，以确保不会合并意外的不安全更改。

使用复刻模型部署 OSS 的一个缺点是，随着时间的推移，从原始仓库合并代码可能变得相当复杂，需要仔细挑选提交。有时，如果在复刻创建后进行了重大重构，主仓库的提交将不再与复刻兼容。

### 自托管应用集成

一些 OSS 应用是预先打包的，通常带有简单的安装程序。WordPress 就是一个典型例子。它最初是一个高度可配置的基于 PHP 的博客平台，现在在大多数基于 Linux 的服务器上提供简单的一键安装。

WordPress 开发者不通过源代码分发 WordPress，而是建议下载一个脚本，该脚本将在您的服务器上自动设置 WordPress 安装。运行此脚本，将设置正确的数据库配置，并根据安装 UI 中呈现给您的配置专门生成文件。

这类应用集成到您的 Web 应用中的风险最高。听起来一键安装的博客软件不会造成很多麻烦，但通常情况下，这种系统使得以后发现和解决漏洞变得更加困难（您需要花费大量精力逆向工程安装脚本才能知道所有文件的位置）。一般来说，您应该远离这种部署方法，但当您必须走这条路时，您还应该找到 OSS 仓库，并仔细分析该仓库中的安装脚本和对您系统运行的任何代码。

这类包需要提升权限，并且很容易导致后门 RCE。这可能对您的组织造成损害，因为脚本本身可能以管理员或提升用户身份在您的 Web 服务器上运行。

### 源代码集成

OSS 与专有 Web 应用集成的另一种方法是通过直接的源代码级集成。这是一种花哨的说法，实际上就是复制/粘贴，但通常更复杂；大型库可能还需要其自己的依赖和资产一起集成。

这种方法在处理大型 OSS 库时前期需要相当多的工作，但对于较小的 OSS 库则非常简单。对于 50–100 行的短脚本，这可能是理想的集成方法。直接源代码集成通常是小型实用程序或辅助函数的最佳选择。

较大的包不仅更难集成，而且带来更多风险。复刻和分支模型带来风险；不安全的上游更改可能意外地被集成到与您的 Web 应用集成的 OSS 代码中。直接集成方法也有其自身的风险；没有简单的方式可以获知上游修复的通知，并将该补丁引入您的软件可能困难且耗时。

每种方法都有优缺点，没有一种方法适用于所有应用。请确保根据多种指标（包括大小、依赖链和主分支的上游活动）仔细评估您希望引入和集成的代码。

## 包管理器

如今，专有 Web 应用与 OSS 之间的许多集成都是通过一个称为包管理器的中介应用实现的。包管理器是确保您的软件始终从网络上可靠的来源下载正确依赖项，并正确设置它们以便无论您的应用在何种设备上运行都可以使用的应用。

包管理器之所以有用，原因众多。它们抽象了复杂的集成细节，缩小了仓库的初始大小，并且如果配置正确，可以只拉取当前开发工作所需的依赖项，而不是为大型应用拉取每个依赖项。在小型应用中这可能没有用，但对于拥有上百个依赖项的大型企业软件包，这可以为您节省数 GB 的带宽和数小时的构建时间。

每种主流编程语言都至少有一个包管理器，其中许多遵循与其他语言类似的架构模式。每个主要包管理器都有自己的特点、安全防护措施和安全风险。

### JavaScript

直到最近，JavaScript（和 Node.js）开发生态系统几乎完全构建在一个名为 npm 的包管理器之上。

尽管市场上出现了替代品，npm 仍然为全球绝大多数基于 JavaScript 的 Web 应用提供支持。[npm](https://www.npmjs.com) 在大多数应用中作为 CLI 存在，用于访问由 npm, Inc. 免费托管的大型开源库数据库。

您可能有意或无意地遇到过基于 npm 的应用。应用通过 npm 引入依赖项的关键标志是应用根目录中的 `package.json` 和 `package-lock.json` 文件，它们向 CLI 指示在构建时引入哪些依赖项和版本。

与大多数现代包管理器一样，npm 不仅解析顶级依赖项，还解析递归的子依赖项。这意味着，如果您的依赖项在 npm 上也有依赖项，npm 也会在构建时引入这些依赖项。

npm 松散的安全机制使其在过去成为恶意用户的目标。由于其广泛使用，其中一些事件影响了数百万应用的正常运行。

一个例子是 `left-pad`，一个简单工具库。2016 年，`left-pad` 从 npm 被移除，破坏了依赖这个单页工具的数百万应用的构建管道。作为回应，npm 不再允许包在发布后经过一定时间后被移除。

2018 年，`eslint-scope` 所有者的凭据被黑客入侵，黑客发布了一个新版本的 `eslint-scope`，它会窃取安装它的任何机器上的本地凭据。这证明 npm 库可以作为黑客的攻击向量。自该事件以来，npm 增加了安全文档，但被入侵的包维护者凭据仍然是一个风险，如果被利用，可能因恶意脚本下载而导致公司源代码、IP 丢失或一般性恶意破坏。

2018 年晚些时候，`event-stream` 发生了类似攻击，它添加了一个依赖 `flatmap-stream`。`flatmap-stream` 包含一些恶意代码，用于窃取安装它的计算机上的比特币钱包，从而从许多不知不觉依赖 `flatmap-stream` 的用户那里窃取钱包。

如您所见，npm 在许多方面都容易被利用，并带来显著的安全风险，因为几乎不可能在源代码级别评估大型应用的每个依赖项和子依赖项。仅仅将您的 OSS npm 包集成到商业应用中，就可能成为导致公司 IP 完全受损或更糟的攻击向量。

### Java

Java 使用多种包管理器，如 Ant 和 Gradle，其中最流行的是由 Apache 软件基金会支持的 Maven。Maven 的操作方式类似于 JavaScript 的 npm——它是一个包管理器，通常集成在构建管道中。

由于 Maven 早于 Git 版本控制，其依赖管理代码的更多部分是从头编写的，而不是依赖 Git 提供的内容。因此，npm 和 Maven 之间的底层实现不同，尽管两者的功能相当相似。

Maven 过去也曾是攻击目标，尽管通常这些攻击获得媒体关注较少。与 npm 一样，Maven 项目和插件可能被入侵并导入到合法应用中。此类风险并非任何单一包管理软件所独有。

### 其他语言

C#、C、C++ 和大多数其他主流编程语言都有类似于 JavaScript 或 Java 的包管理器（NuGet、Conan、Spack 等）。每一种都可以通过类似方法受到攻击，要么通过添加一个恶意包然后将其纳入合法应用的代码库，要么通过添加一个恶意依赖项，然后将其纳入合法包，再纳入合法应用的代码库。

通过包管理器进行攻击可能需要结合社会工程学和代码混淆技术。恶意代码必须隐藏，以便不易被识别，但仍能执行。

最终，包管理器带来的风险与任何 OSS 集成方法类似。全面审查大型 OSS 包中的代码是困难的，尤其是考虑到其依赖项时。

## 通用漏洞披露（CVE）数据库

一般来说，将包部署到包管理器并使其集成到应用中可能是一种攻击向量，但这需要大量的长期努力和规划。快速利用第三方依赖的最流行方式是确定应用依赖中已知但尚未修补的漏洞，并攻击这些依赖。

幸运的是，许多包中的漏洞在被发现时会被公开披露。这些漏洞通常会出现在如美国商务部国家漏洞数据库（NVD）或 Mitre 的[通用漏洞披露（CVE）数据库](https://cve.mitre.org)（由美国国土安全部赞助）等在线数据库中。

这意味着，由于许多公司合作并贡献他们自己的安全分析研究供他人阅读，流行的第三方应用很可能有已知且有记录的漏洞。

在尝试查找较小包中的已知漏洞时，CVE 数据库并不特别有用，例如一个只有两个贡献者、被下载三百次的 GitHub 仓库。另一方面，像 WordPress、Bootstrap 或 JQuery 这样拥有数百万用户的主要依赖项，在被引入生产环境之前往往已经受到许多审查。因此，大多数严重漏洞很可能已经被发现、记录并发布在网上。

JQuery 就是一个很好的例子。作为 JavaScript 中最常用的十大库之一，JQuery 被超过 1000 万个网站使用，在 GitHub 上有超过 18,000 个复刻和超过 250 个贡献者，并有约 7,000 次提交，构成 150 个版本。

由于其广泛使用和可见性，JQuery 在安全编码和架构方面不断受到高度关注。JQuery 中的严重漏洞可能对世界上一些最大的公司造成严重破坏——损害将非常广泛。

快速扫描 NVD 的 CVE 数据库可以发现多年来 JQuery 中报告的数十个漏洞。这些漏洞包括复现步骤和威胁评级，以确定漏洞的易利用性以及该漏洞会给组织带来何种风险。

作为攻击者，这些 CVE 数据库可以为您提供详细的利用方法，针对包含先前披露漏洞的应用。CVE 数据库使发现和利用漏洞变得非常容易，但您仍然必须使用侦察技术来正确识别依赖项、它们与主应用的集成方式，以及这些依赖项所使用的版本和配置。

## 小结

第三方依赖的泛滥使用，尤其是来自开源领域的依赖，已经在许多 Web 应用的安全中造成了一个容易被忽视的缺口。黑客、漏洞赏金猎人或渗透测试员可以利用这些集成，快速启动他们寻找活漏洞的工作。第三方依赖可以通过多种方式被攻击，从粗糙的集成到第四方代码，或者仅仅通过发现其他研究人员或公司发现的已知利用。

虽然第三方依赖作为进攻性攻击向量的主题很广泛且难以精确定位，但在任何类型的进攻性测试环境中，这些依赖项都应始终被考虑。第三方依赖需要一些侦察工作来完全理解它们在复杂 Web 应用中的作用，但一旦侦察工作完成，依赖项中的漏洞通常会比第一方代码中的漏洞更快显现。这是因为这些依赖项缺乏与第一方代码相同的严格审查和保证流程，使它们成为任何类型 Web 应用利用的绝佳起点。
