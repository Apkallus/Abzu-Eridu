# 服务器端模板注入（SSTI）

> 此技术由 PortSwigger Research 在会议演讲 [Server-Side Template Injection: RCE for the Modern Web App](https://portswigger.net/research/server-side-template-injection) 中首次记录。

## 什么是服务器端模板注入？

服务器端模板注入是指攻击者能够使用原生模板语法将恶意载荷注入到模板中，然后在服务器端执行。

模板引擎旨在通过将固定模板与动态数据相结合来生成网页。当用户输入被直接拼接到模板中，而不是作为数据传入时，就会发生服务器端模板注入攻击。这允许攻击者注入任意模板指令以操纵模板引擎，通常使他们能够完全控制服务器。顾名思义，服务器端模板注入载荷是在服务器端交付和评估的，这可能使它们比典型的客户端模板注入危险得多。

## 模板引擎简介

模板引擎在现代 Web 开发中已变得非常流行，因为它们允许开发人员用更少的代码生成更动态的内容。在模板引擎出现之前，开发人员必须直接将 HTML 与服务器端编程语言（如 PHP、ASP 等）混合，这使得代码难以维护。模板引擎将业务逻辑与表示层分离，意味着 HTML/CSS 与服务器端编程代码分开。这种分离使代码更具可读性，增强了可维护性，并提高了代码重用性。

让我们看一下Jinja，这是一种Python的模板语言。以下是一个用Jinja编写的模板文件，我们将其保存为`example.jinja`：

```py
<html>
<body>
① <h1>{{ list_title }}</h1>
<h2>{{ list_description }}</h2>
② {% for item in item_list %}
  {{ item }}
  {% if not loop.last %},{% endif %}
{% endfor %}
</body>
</html>
```

如你所见，此模板文件看起来像普通的HTML。然而，它包含特殊语法来指示模板引擎应解释为模板代码的内容。在Jinja中，双花括号`{{ }}`内的任何代码将被解释为Python表达式，而括号和百分号配对`{% %}`内的代码应被解释为Python语句。

在编程语言中，**表达式**是变量或返回值的函数，而**语句**是不返回任何内容的代码。在这里，你可以看到模板首先在HTML标题标签中嵌入表达式`list_title`和`list_description`①。然后它创建一个循环，在HTML正文中渲染`item_list`变量中的所有项目②。

现在开发人员可以将模板与Python代码结合以创建完整的HTML页面。以下Python代码从`example.jinja`读取模板文件，并通过向模板引擎提供要插入模板的值来动态生成HTML页面：

```python
from jinja2 import Template

with open('example.jinja') as f: ①
    tmpl = Template(f.read())

print(tmpl.render( ②
    list_title = ③ "Chapter Contents",
    list_description = ④ "Here are the contents of chapter 16.",
    item_list = ⑤ ["Mechanisms Of Template Injection", "Preventing Template Injection",
                  "Hunting For Template Injection", 
                  "Escalating Template Injection", "Automating Template Injection", "Find Your First Template Injection!"]
))
```

1. 首先，Python代码读取名为`example.jinja`的模板文件①。
2. 然后它通过向模板提供所需值来动态生成HTML页面②。
3. 使用字符串对象与列表③④⑤来渲染模板。

模板引擎将结合Python脚本中提供的数据和模板文件`example.jinja`来创建此HTML页面：

```html
<html>
<body>
    <h1>Chapter Contents</h1>
    <h2>Here are the contents of chapter 16.</h2>
    Mechanisms Of Template Injection,
    Preventing Template Injection,
    Hunting For Template Injection,
    Escalating Template Injection,
    Automating Template Injection,
    Find Your First Template Injection!
</body>
</html>
```

模板引擎使渲染网页更加高效，因为开发人员可以通过重用模板以标准化方式呈现不同数据集。当开发人员需要生成具有自定义内容的相同格式页面时，此功能尤其有用，例如批量电子邮件、在线市场上的单个商品页面以及不同用户的个人资料页面。

## 服务器端模板注入的影响是什么？

服务器端模板注入漏洞可能使网站面临各种攻击，具体取决于所使用的模板引擎以及应用程序如何使用它。在某些罕见情况下，这些漏洞不会构成真正的安全风险。然而，大多数情况下，服务器端模板注入的影响可能是灾难性的。

在最严重的情况下，攻击者可能实现远程代码执行，完全控制后端服务器，并利用它对内部基础设施执行其他攻击。

即使在无法实现完全远程代码执行的情况下，攻击者通常仍然可以将服务器端模板注入作为众多其他攻击的基础，可能获得对服务器上敏感数据和任意文件的读取访问权限。

## 服务器端模板注入漏洞是如何产生的？

当用户输入被拼接到模板中而不是作为数据传入时，就会产生服务器端模板注入漏洞。

仅提供占位符以渲染动态内容的静态模板通常不容易受到服务器端模板注入的攻击。典型的例子是一封按用户名问候每位用户的电子邮件，例如来自 Twig 模板的以下片段：

```php
$output = $twig->render("Dear {first_name},", array("first_name" => $user.first_name) );
```

这不容易受到服务器端模板注入的攻击，因为用户的名字仅仅是作为数据传入模板。

然而，由于模板只是字符串，Web 开发人员有时会在渲染之前直接将用户输入拼接到模板中。让我们看一个与上面类似的例子，但这次用户在发送电子邮件之前可以自定义电子邮件的部分内容。例如，他们可能能够选择使用的名称：

```php
$output = $twig->render("Dear " . $_GET['name']);
```

在此示例中，不是将静态值传入模板，而是使用 `GET` 参数 `name` 动态生成部分模板本身。由于模板语法在服务器端进行评估，这潜在允许攻击者将服务器端模板注入载荷放入 `name` 参数中，如下所示：

`http://vulnerable-website.com/?name={{bad-stuff-here}}`

此处提交了一个对模板引擎具有特殊含义的表达式 `{{bad-stuff-here}}`，模板渲染引擎将双花括号`{{ }}`内的任何内容解释为代码。

此类漏洞有时是由于不熟悉安全影响的开发人员设计不当而偶然引起的。如上面的示例所示，您可能会看到不同的组件（其中一些包含用户输入）被拼接并嵌入到模板中。在某些方面，这类似于在编写不当的预编译语句中出现的 SQL 注入漏洞。

虽然有许多模板引擎，但你在野外可能经常遇到的一些著名的模板注入如下：

- Smarty（PHP）
- Blade（PHP，与 Laravel 一起使用）
- Pug（原 Jade，JavaScript）
- Liquid（Ruby，由 Shopify 使用）
- Freemarker（Java）
- Twig（PHP，与 Symfony 一起使用）
- Mustache（跨平台）
- Jinja2（Python）
- Mako（Python）

然而，有时这种行为实际上是有意实现的。例如，某些网站故意允许特定特权用户（如内容编辑者）编辑或提交自定义模板。任何支持高级用户提供标记的功能都可能容易受到 SSTI 攻击，包括 Wiki 页面、评论、营销应用程序、CMS 系统等。某些模板引擎采用各种机制（例如沙盒、白名单等）来防范 SSTI。

## 构造服务器端模板注入攻击

识别服务器端模板注入漏洞并成功实施攻击通常涉及以下流程

1. 检测
2. 识别
3. 利用
    1. 阅读
    2. 探索
    3. 攻击

### 检测

服务器端模板注入漏洞经常被忽视，不是因为它们很复杂，而是因为它们仅对明确寻找它们的审计人员真正可见。如果您能够检测到存在漏洞，利用它可能出奇地容易。在无沙箱环境中尤其如此。

与任何漏洞一样，利用的第一步是能够找到它。也许最简单的初始方法是尝试通过注入模板表达式中常用的特殊字符序列来模糊测试模板，例如 

- `${{<%[%'"}}%\`
- `{var} ${var} {{var}} <%var%> [% var %]`

如果引发异常，这表明注入的模板语法可能在某种程度上被服务器解释。这是可能存在服务器端模板注入漏洞的一个迹象。

服务器端模板注入漏洞发生在文本上下文或代码上下文中，每种上下文都需要自己的检测方法。无论您的模糊测试结果如何，尝试以下特定于上下文的方法也很重要。如果模糊测试不确定，使用其中一种方法仍可能揭示漏洞。即使模糊测试确实表明存在模板注入漏洞，您仍然需要识别其上下文才能利用它。

模板通常用于根据存储的数据或用户输入动态生成网页。例如，应用程序经常使用模板引擎根据用户信息生成自定义电子邮件或首页。因此，要寻找模板注入，寻找接受最终将显示回给用户的用户输入的端点。这些端点通常与可能的XXS攻击端点重合。记录这些输入位置以供进一步测试。

[PayloadsAllTheThings 模板表达式测试载荷列表](https://github.com/swisskyrepo/PayloadsAllTheThings/tree/master/Server%20Side%20Template%20Injection)。

#### 纯文本上下文

大多数模板语言允许您通过直接使用 HTML 标签或使用模板的原生语法自由输入内容，这些内容将在 HTTP 响应发送之前在后端渲染为 HTML。例如，在 Freemarker 中，行 `render('Hello ' + username)` 将渲染为类似于 `Hello Carlos` 的内容。

这有时可以被利用进行 XSS，并且实际上经常被误认为是一个简单的 XSS 漏洞。然而，通过将数学运算设置为参数的值，我们可以测试这是否也是服务器端模板注入攻击的潜在入口点。

例如，考虑一个包含以下易受攻击代码的模板：

```php
render('Hello ' + username)
```

这通常会导致 XSS，因此 XSS 的存在可以作为更全面的模板注入探测的线索。模板语言使用的语法显式选择不与普通 HTML 中使用的字符冲突，因此手动的黑盒安全评估很容易完全忽略模板注入。为了检测它，我们需要通过嵌入语句来调用模板引擎。模板语言数量庞大，但其中许多共享基本的语法特征。我们可以利用这一点，通过发送通用的、与模板无关的载荷，使用基本操作来通过单个 HTTP 请求检测多个模板引擎：

```log
smarty=Hello ${7*7}
Hello 49

freemarker=Hello ${7*7}
Hello 49
```

如果结果输出包含 `Hello 49`，这表明数学运算正在服务器端被评估。这是服务器端模板注入漏洞的一个很好的概念证明。

常见的模板表达式示例：

```
a{{bar}}b
a{{7*7}}
{var} ${var} {{var}} <%var%> [% var %]
```

请注意，成功评估数学运算所需的特定语法将根据所使用的模板引擎而有所不同。我们将在[识别](#识别)步骤中更详细地讨论这一点。

#### 代码上下文

在其他情况下，漏洞通过用户输入被放置在模板表达式内部而暴露，正如我们在前面的电子邮件示例中看到的。这可能采取用户可控的变量名被放置在参数中的形式，例如：

```php
greeting = getQueryParameter('greeting')
engine.render("Hello {{"+greeting+"}}", data)
```

在网站上，生成的 URL 将类似于：

`http://vulnerable-website.com/?greeting=data.username`

例如，这将在输出中渲染为 `Hello Carlos`。

这种上下文在评估期间很容易被忽略，因为它不会导致明显的 XSS，并且几乎与简单的哈希映射查找无法区分。在此上下文中测试服务器端模板注入的一种方法是，首先通过向值中注入任意 HTML 来确定参数不包含直接的 XSS 漏洞：

`http://vulnerable-website.com/?greeting=data.username<tag>`

在没有 XSS 的情况下，这通常会导致输出中的空白条目（只是 `Hello` 而没有用户名）、编码的标签或错误消息。下一步是尝试使用常见的模板语法跳出语句，并尝试在其后注入任意 HTML：

`http://vulnerable-website.com/?greeting=data.username}}<tag>`

如果这再次导致错误或空白输出，则您要么使用了错误模板语言的语法，要么如果没有模板样式语法看起来有效，则服务器端模板注入不可能。或者，如果输出与任意 HTML 一起正确渲染，这是存在服务器端模板注入漏洞的关键指示：

`Hello Carlos<tag>`

### 识别

一旦检测到潜在的模板注入，下一步就是识别模板引擎。

尽管有大量的模板语言，但其中许多使用非常相似的语法，这些语法专门选择不与 HTML 字符冲突。因此，构建探测载荷以测试正在使用哪个模板引擎可能相对简单。

仅仅提交无效语法通常就足够了，因为由此产生的错误消息将准确地告诉您模板引擎是什么，有时甚至告诉您版本。例如，无效表达式 `<%=foobar%>` 会触发基于 Ruby 的 ERB 引擎的以下响应：

```log
(erb):1:in `<main>': undefined local variable or method `foobar' for main:Object (NameError)
from /usr/lib/ruby/2.5.0/erb.rb:876:in `eval'
from /usr/lib/ruby/2.5.0/erb.rb:876:in `result'
from -e:4:in `<main>'
```

否则，您需要手动测试不同的语言特定载荷，并研究模板引擎如何解释它们。通过基于哪些语法看起来有效或无效的排除过程，您可以比想象中更快地缩小选项范围。一种常见的方法是使用来自不同模板引擎的语法注入任意数学运算。然后您可以观察它们是否被成功评估。为了帮助这个过程，您可以使用类似于以下的决策树：

![portswigger 模板决策树](https://portswigger.net/web-security/images/template-decision-tree.png)

您应该注意，相同的载荷有时可以在多个模板语言中返回成功响应。例如，载荷 `{{7*'7'}}` 在 Twig 中返回 `49`，在 Jinja2 中返回 `7777777`。因此，不要仅凭一次成功响应就匆忙下结论。

## 如何防止服务器端模板注入漏洞

防止服务器端模板注入的最佳方法是禁止任何用户修改或提交新模板。然而，由于业务需求，这有时是不可避免的。

避免引入服务器端模板注入漏洞的最简单方法之一是，除非绝对必要，始终使用“无逻辑”模板引擎，如 Mustache。尽可能将逻辑与表示分离可以大大减少您暴露于最危险的基于模板的攻击。

另一种措施是仅在沙箱环境中执行用户代码，其中潜在危险的模块和函数已被完全移除。不幸的是，对不可信代码进行沙箱隔离本质上是困难的，并且容易被绕过。

最后，另一种补充方法是接受任意代码执行几乎是不可避免的，并通过在锁定好的 Docker 容器中部署您的模板环境来应用您自己的沙箱。
