# CRLF 注入 —— curl

## 概述

当输入上下文位于请求头部字段，且回车换行被解释为元数据字符而非普通文本时存在换行注入。预期情景：服务器解析输入后构建请求

普通请求：

```http
GET / HTTP/1.1
Host: example.com
```

HTTP 动词、URI、Host 头为 CTF 常见注入点

### curl 换行注入缺陷

[Tornado 换行注入缺陷](https://osv.dev/vulnerability/GHSA-w235-7p84-xx57)
- 指出缺陷似乎源于 libcurl (pycurl) 缺乏头部验证 

[curl - libcurl](https://curl.se/libcurl/c/CURLOPT_HTTPHEADER.html) 
> 链表中包含的头**绝不能**以 CRLF 结尾，因为 libcurl 会在每个头项之后自行添加 CRLF。不遵守这一点可能会导致奇怪的行为。libcurl 会原样传递你给它的逐字字符串，不进行任何过滤或其他安全防护。这包括空白字符和控制字符。
- 在 2011 年即存在[回车注入邮件通信](https://curl.se/mail/lib-2011-03/0061.html)。开发者在[回应中](https://curl.se/mail/lib-2011-03/0067.html)，表示 libcurl 不应当对回车换行进行转换。
- libcurl 的回车换行注入将延续之前的风格而持续存在，已经并将继续成为 CTF 挑战中的常客
