## 二阶 SQL 注入

**一阶 SQL 注入**发生在应用程序直接在 SQL 查询中使用用户提交的输入时。而**二阶 SQL 注入**发生在用户输入被存储到数据库中，然后被检索出来并在 SQL 查询中被不安全地使用时。

即使应用程序在用户提交输入时能够安全处理这些数据，若随后应用程序本身或其他后端进程从数据库检索数据时以危险的方式处理这些数据，这些漏洞也可能发生。许多这类组件并不像面向因特网的主要应用程序一样安全，但却拥有较高权限的数据库账户。

在一些应用程序中，用户输入在到达时通过转义单引号来进行确认: 用户提交的单引号被转换为两个单引号，因而传送给数据库的搜索项与用户最初输入的表达式具有相同的字符含义。

与单引号配对方法有关的问题出现在更复杂的情形中，此时同一个数据项被提交给几个SQL查询，然后写入数据库被几次读取（不同组件，不同位置）。这是证明简单输入确认相对于边界确认存在不足的一个示例。

假设开发者将使用双重单引号以转义单个单引号，它不会在数据库中造成问题。然而，假设应用程序的其他功能从数据库中使用此数据，此时单引号在未被转义的语句中实现注入（数据存入时转义，取出作为另一个SQL查询时未转义。即，功能a传递载荷，功能b触发载荷）

### 简略示例


例如，考虑一个允许用户通过指定用户名和密码创建账户的 Web 应用程序。假设恶意用户提交以下请求：

```
POST /signup
Host: example.com
(POST request body)
username="vickie' UNION SELECT Username, Password FROM Users;--
"&password=password123
```

此请求向 `/signup` 端点提交了用户名 `vickie' UNION SELECT Username, Password FROM Users;--` 和密码 `password123`。用户名 POST 请求参数包含一个 SQL 注入载荷，该载荷将 `SELECT` 所有用户名和密码并将它们与数据库查询结果拼接。

应用程序在提交时正确处理了用户输入，使用了下一节将要讨论的保护技术。字符串 `vickie' UNION SELECT Username, Password FROM Users;--` 作为攻击者的用户名存储到应用程序的数据库中。

之后，恶意用户通过以下 GET 请求访问其电子邮件：

```
GET /emails
Host: example.com
```

在这种情况下，假设如果用户未提供用户名和访问密钥，应用程序将从数据库中检索当前登录用户的用户名，并使用它填充 SQL 查询：

```sql
SELECT Title, Body FROM Emails
WHERE Username='USERNAME'
```

但攻击者的用户名包含 SQL 代码，将 SQL 查询变成：

```sql
SELECT Title, Body FROM Emails
WHERE Username='vickie'
UNION SELECT Username, Password FROM Users;--
```

这将以电子邮件标题和正文的形式在 HTTP 响应中返回所有用户名和密码！

### 真实场景

让我们考虑一个涉及 Joomla 版本（CVE-2018-6376）的真实场景，该版本易受二阶 SQL 注入影响，导致权限提升。其中，
- 保存主题的功能将用户输入存入数据库
- 展示主题时从数据库读取保存的主题
    - 将数据字符串直接拼接到 where 字句中

**易受攻击的代码**

让我们检查位于 `administrator/templates/hathor/postinstall/hathormessage.php` 的易受攻击代码。

```php
1    function hathormessage_postinstall_condition()
2    {
3        ⋮
4        $adminstyle = $user->getParam('admin_style', '');
5	 if ($adminstyle != '')
6	 {
7            $query = $db->getQuery(true)
8                ->select('template')
9                ->from($db->quoteName('#__template_styles'))
10               ->where($db->quoteName('id') . ' = ' . $adminstyle[0])
11               ->where($db->quoteName('client_id') . ' = 1');
12
13            // Get the template name associated to the admin style
14            $template = $db->setquery($query)->loadResult();
15            ⋮
16        }
17        ⋮
18    }
```

Joomla 中的 `hathormessage_postinstall_condition()` 函数是处理安装后消息的代码的一部分。每次加载管理员仪表板时都会调用它。

以下代码中的 `$adminstyle` 变量通过用户可控的 `admin_style` 参数获得。

**代码**
```php
$adminstyle = $user->getParam('admin_style', '');
```

用户提供的输入直接插入到 `where` 子句中，未经清理或过滤。

**代码**
```php
->where($db->quoteName('id'). ' = '. $adminstyle[0])
```

这里的 `$adminstyle[0]` 元素表示字符串的第一个字符。由于代码缺少类型强制转换检查，意味着输入数据类型未明确定义，因此可以提供数组而不是字符串，第一个索引指向我们的 payload。一旦插入此 payload，下次加载仪表板时将调用该函数，从而触发我们的漏洞。这种延迟执行将其特征化为二阶 SQL 注入。

让我们检查 Joomla 开发者应用的修复，以更好地理解此漏洞：

**补丁分析**
```php
$query = $db->getQuery(true)
    ->select('template')
    ->from($db->quoteName('#__template_styles'))
    ->where($db->quoteName('id'). ' = '. (int) $adminstyle)
    ->where($db->quoteName('client_id'). ' = 1');
$template = $db->setQuery($query)->loadResult();
```

修复涉及将 `$adminstyle` 类型强制转换为整数（`(int)`）；它确保在 SQL 查询上下文中，`$adminstyle` 持有的任何值都被视为整数。原始代码使用 `$adminstyle[0]`，它访问字符串的第一个字符。在修复后的代码中，删除了此特定数组访问，并将整个 `$adminstyle` 变量类型强制转换为整数。

#### 重现漏洞

要重现漏洞，我们需要确定接受 `adminstyle` 变量输入的位置。变量 `adminstyle` 用于在用户个人资料更新期间修改仪表板的外观。当用户在 Joomla 管理面板中编辑其个人资料时，会显示一个下拉菜单以选择他们首选的模板样式。这就是 `adminstyle` 参数发挥作用的地方。

拦截请求后，我们可以看到存在 `admin_style` 参数

现在，让我们尝试通过将 `jform[params][admin_style]` 参数修改为 `jform[params][admin_style][0]` 并传递单引号（`'`）来重现漏洞。

更新详细信息后，返回消息指示“项目已保存”。

当用户浏览主页时，会调用 `hathormessage_postinstall_condition()` 函数，从而导致插入我们的 payload。

**示例**
```
http://localhost:8080/administrator/index.php
```

将出现 MySQL 语法错误

