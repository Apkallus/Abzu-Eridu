# 如何保护您的身份验证机制

在本节中，我们将讨论如何防止我们之前讨论过的一些漏洞出现在您的身份验证机制中。

身份验证是一个复杂的话题，正如我们所展示的，不幸的是，弱点与缺陷太容易渗透进来。显然，不可能列出您可以采取的保护自己网站的所有措施。然而，有几个通用原则您应始终遵循。

## 谨慎处理用户凭据 —— 避免使用未加密的 HTTP 协议

如果您无意中向攻击者泄露了一组有效的登录凭据，即使是最健壮的身份验证机制也是无效的。不言而喻，您绝不应通过未加密的连接发送任何登录数据。尽管您可能已经为登录请求实施了 HTTPS，请确保您同时通过将任何尝试的 HTTP 请求重定向到 HTTPS 来强制执行这一点。

您还应该审计您的网站，以确保没有用户名或电子邮件地址通过公开可访问的个人资料或在 HTTP 响应中被泄露。

### 非加密证书传输

如果应用程序使用非加密的HTTP连接传输登录证书，处于网络适当位置的窃听者当然就能够拦截这些证书。根据用户的位置，窃听者可能位于：

- 用户的本地网络中；
- 用户的IT部门内；
- 用户的ISP内；
- 因特网骨干网上；
- 托管应用程序的ISP内；
- 管理应用程序的IT部门内。

即使是通过HTTPS登录，如果应用程序处理证书的方式并不安全，证书仍有可能被泄露给未授权方：

- 如果以查询字符串参数、而不是在POST请求主体中传送证书，许多地方都可能记录这些证书，例如用户的浏览器历史记录中、Web服务器日志内以及主机基础架构采用的任何反向代理中。如果攻击者成功攻破这些资源，就能够获取保存在这些地方的用户证书，从而提升其访问权限。

- Web应用程序有时将用户证书保存在cookie中，通常是为了执行设计不佳的登录、密码修改、“记住我”等机制。攻击者通过攻击用户cookie即可获取这些证书。如果cookie相对安全可靠，可通过访问客户端的本地文件系统获得它们。即使证书被加密，攻击者仍然不需要用户证书就可以通过重新传送cookie实施登录。

许多应用程序对应用程序中未经验证的区域使用HTTP，而在登录时转而使用HTTPS。如果是这样，应在向浏览器加载登录页面时转换到HTTPS，使得用户能够在输入证书前核实页面是否真实可信。但是，一些应用程序通常使用HTTP加载登录页面，而在提交证书时才转换到HTTPS。这样做是不安全的，因为用户不能核实登录页面的真实性，因此无法保证安全提交证书。那么，处在适当位置的攻击者就可以拦截并修改登录页面，更改登录表单的目标URL以使用HTTP。等到精明的用户意识到证书已使用HTTP提交时，攻击者已成功获取这些证书。

## 不要依赖用户来保证安全

严格的身份验证措施通常需要您的用户付出一些额外努力。人性几乎不可避免会导致一些用户找到省去这些努力的方法。因此，您需要尽可能强制执行安全行为。

最明显的例子是实施有效的密码策略。一些较传统的策略失败是因为人们将自己可预测的密码硬塞进策略中。相反，实施某种简单的密码检查器可能更有效，它允许用户尝试密码并实时提供关于其强度的反馈。一个流行的例子是 Dropbox 开发的 JavaScript 库 `zxcvbn`。通过只允许密码检查器评级较高的密码，您可以比传统策略更有效地强制使用安全密码。

## 防止用户名枚举 —— 返回通用响应与错误信息

如果您揭示系统上存在某个用户，攻击者破解您的身份验证机制会容易得多。甚至在有些情况下，由于网站的性质，知道某个特定人拥有账户本身就是敏感信息。

无论尝试的用户名是否有效，使用相同的通用错误消息并确保它们确实相同是很重要的。您应该始终对每个登录请求返回相同的 HTTP 状态码，最后，使不同场景下的响应时间尽可能难以区分。

## 实施健壮的暴力破解保护

考虑到构建暴力破解攻击是多么简单，确保您采取措施防止或至少干扰任何暴力破解登录的尝试至关重要。

一种更有效的方法是实施严格的、基于 IP 的用户速率限制。这应包括防止攻击者操纵其显示 IP 地址的措施。理想情况下，您应在达到一定限制后要求用户在每次登录尝试时完成 CAPTCHA 测试。

请记住，这并不能保证完全消除暴力破解的威胁。然而，使过程尽可能繁琐和手动化，会增加任何潜在攻击者放弃并转而寻找更软目标的可能性。

## 再三检查您的验证逻辑

简单的逻辑缺陷很容易渗透到代码中，而在身份验证的情况下，这些缺陷有可能完全破坏您的网站和用户。彻底审计任何验证或确认逻辑以消除缺陷，是健壮身份验证的关键。一个可以被绕过的检查，最终并不比没有检查好多少。

## 不要忘记辅助功能

请务必不要只关注中央登录页面而忽视与身份验证相关的附加功能。这在攻击者可以自由注册自己的账户并探索此功能的情况下尤其重要。请记住，密码重置或更改与主要登录机制一样是有效的攻击面，因此必须同样健壮。

## 实施正确的多因素身份验证

虽然多因素身份验证可能不适用于每个网站，但当正确实施时，它比仅基于密码的登录要安全得多。请记住，验证同一因素的多个实例并不是真正的多因素身份验证。通过电子邮件发送验证码本质上只是一种更冗长的单因素身份验证形式。

基于短信的 2FA 在技术上是验证了两个因素（你知道的东西和你拥有的东西）。然而，通过 SIM 卡交换等方式滥用的可能性意味着该系统可能不可靠。

理想情况下，2FA 应使用直接生成验证码的专用设备或应用程序来实现。由于它们是专门为提供安全性而构建的，因此通常更安全。

最后，与主要身份验证逻辑一样，请确保您的 2FA 检查中的逻辑是健全的，以便它不会被轻易绕过。
