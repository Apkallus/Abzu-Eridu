# OAuth 授权类型

在本节中，我们将介绍两种最常见的 OAuth 授权类型的基础知识。如果您完全是 OAuth 新手，我们建议您在尝试完成我们的 [OAuth 身份验证](/web-security/oauth) 实验之前先阅读本节。

## 什么是 OAuth 授权类型？

OAuth 授权类型决定了 OAuth 过程中涉及的具体步骤序列。授权类型还影响客户端应用程序在每个阶段如何与 OAuth 服务通信，包括访问令牌本身的发送方式。因此，授权类型通常被称为“OAuth 流程”。

OAuth 服务必须配置为支持特定的授权类型，然后客户端应用程序才能发起相应的流程。客户端应用程序在发送给 OAuth 服务的初始授权请求中指定它想要使用的授权类型。

为了向客户端应用程序提供访问权限，OAuth 依赖于几种[授权类型](https://oauth.net/2/grant-types/)来生成访问令牌：

- [授权码](https://oauth.net/2/grant-types/authorization-code/)：由公共客户端和机密客户端共同使用，用于将授权码交换为访问令牌，但建议仅用于机密客户端。
- [用于代码交换的证明密钥（PKCE）](https://oauth.net/2/pkce/)：PKCE 建立在授权码授权之上，为其提供更强的安全性，使其可用于公共客户端，并改善机密客户端的安全态势。
- [客户端凭据](https://oauth.net/2/grant-types/client-credentials/)：用于机器对机器通信，其中“用户”是请求访问资源服务器上自身资源的机器。
- [设备码](https://oauth.net/2/grant-types/device-code/)：用于输入能力受限的设备。
- [刷新令牌](https://oauth.net/2/grant-types/refresh-token/)：由授权服务器提供的令牌，允许客户端在访问令牌失效或过期时刷新用户访问令牌。此授权类型与其他授权类型结合使用。

在 [OAuth2.1](https://oauth.net/2.1/) 发布时，以下两种流程将被弃用，不建议使用：

- [隐式流*](https://oauth.net/2/grant-types/implicit/)：PKCE 的安全实现使此流程过时。在 PKCE 出现之前，隐式流被客户端应用程序（如[单页应用程序](https://en.wikipedia.org/wiki/Single-page_application)）使用，因为 [CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/CORS) 放宽了站点间通信的[同源策略](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy)。有关不推荐隐式授权的更多信息，请参阅此[部分](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-security-topics#section-2.1.2)。
- [资源所有者密码凭据](https://oauth.net/2/grant-types/password/)：用于将用户的凭据直接交换给客户端，然后客户端将其发送给授权服务器以换取访问令牌。有关不推荐此流程的原因，请参阅此[部分](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-security-topics#section-2.4)。

*：隐式流在 OAuth 中已被弃用，但在 Open ID Connect（OIDC）中仍然是获取 `id_tokens` 的可行解决方案。请注意理解隐式流的使用方式，如果仅使用 `/authorization` 端点获取访问令牌，而不以任何方式依赖 `/token` 端点，则可识别为隐式流。相关示例可参考[此处](https://auth0.com/docs/get-started/authentication-and-authorization-flow/implicit-flow-with-form-post)。

## OAuth 作用域

对于任何 OAuth 授权类型，客户端应用程序都必须指定它想要访问哪些数据以及想要执行哪种操作。它通过在发送给 OAuth 服务的授权请求中使用 `scope` 参数来实现这一点。

对于基本的 OAuth，客户端应用程序可以请求访问的作用域是每个 OAuth 服务独有的。由于作用域名称只是一个任意文本字符串，其格式在不同提供商之间可能有很大差异。有些甚至使用完整的 URI 作为作用域名称，类似于 REST API 端点。例如，当请求读取用户的联系人列表时，作用域名称可能采用以下任意形式，具体取决于所使用的 OAuth 服务：

```
scope=contacts
scope=contacts.read
scope=contact-list-r
scope=https://oauth-authorization-server.com/auth/scopes/user/contacts.readonly
```

然而，当 OAuth 用于身份验证时，通常会使用标准化的 OpenID Connect 作用域。例如，作用域 `openid profile` 将授予客户端应用程序对一组预定义的用户基本信息的读取访问权限，例如他们的电子邮件地址、用户名等。我们将在后面详细讨论 OpenID Connect。

## 授权码授权类型

授权码授权类型一开始看起来相当复杂，但一旦您熟悉了一些基本知识，它实际上比您想象的要简单。

简而言之，客户端应用程序和 OAuth 服务首先使用重定向来交换一系列基于浏览器的 HTTP 请求，从而启动流程。用户被询问是否同意所请求的访问权限。如果他们接受，客户端应用程序将获得一个“授权码”。然后，客户端应用程序将此代码与 OAuth 服务交换以接收一个“访问令牌”，他们可以使用该令牌进行 API 调用来获取相关的用户数据。

从代码/令牌交换开始的所有通信都是通过安全的、预先配置的后端通道在服务器之间发送的，因此对最终用户是不可见的。这个安全通道是在客户端应用程序首次向 OAuth 服务注册时建立的。此时，还会生成一个 `client_secret`，客户端应用程序在发送这些服务器到服务器请求时必须使用它来进行身份验证。

由于最敏感的数据（访问令牌和用户数据）不通过浏览器发送，这种授权类型可以说是最安全的。如果可能，服务器端应用程序理想情况下应始终使用此授权类型。

![OAuth 授权码授权类型流程](https://portswigger.net/web-security/images/oauth-authorization-code-flow.jpg)

### 1. 授权请求

客户端应用程序向 OAuth 服务的 `/authorization` 端点发送请求，请求访问特定用户数据的权限。请注意，端点映射可能因提供商而异——我们的实验使用端点 `/auth` 来实现此目的。但是，您应该始终能够根据请求中使用的参数来识别端点。

```http
GET /authorization?client_id=12345&redirect_uri=https://client-app.com/callback&response_type=code&scope=openid%20profile&state=ae13d489bd00e3c24 HTTP/1.1
Host: oauth-authorization-server.com
```

此请求包含以下值得注意的参数，通常在查询字符串中提供：

- `client_id`
  客户端应用程序的唯一标识符，必需参数。此值在客户端应用程序向 OAuth 服务注册时生成。

- `redirect_uri`
  “回调 URI”或“回调端点”：将授权码发送给客户端应用程序时，用户浏览器应重定向到的 URI。许多 OAuth 攻击都是基于利用此参数验证中的缺陷。

- `response_type`
  决定客户端应用程序期望哪种响应，从而决定它想要启动哪个流程。对于授权码授权类型，该值应为 `code`。

- `scope`
  用于指定客户端应用程序想要访问用户数据的哪个子集。请注意，这些可能是 OAuth 提供商设置的自定义作用域，也可能是 OpenID Connect 规范定义的标准作用域。我们将在后面更详细地介绍 OpenID Connect。

- `state`
  存储一个唯一的、不可猜测的值，该值绑定到客户端应用程序上的当前会话。OAuth 服务应在响应中返回此确切值以及授权码。此参数通过确保对其 `/callback` 端点的请求来自发起 OAuth 流程的同一人，充当客户端应用程序的一种 CSRF 令牌。

### 2. 用户登录和同意

当授权服务器收到初始请求时，它会将用户重定向到登录页面，在那里他们将被提示登录到他们在 OAuth 提供商处的账户。例如，这通常是他们的社交媒体账户。

然后，他们将看到客户端应用程序想要访问的数据列表。这是基于授权请求中定义的作用域。用户可以选择是否同意此访问。

> 需要注意的是，一旦用户为某个客户端应用程序批准了给定作用域，只要用户与 OAuth 服务仍有有效会话，此步骤将自动完成。换句话说，用户第一次选择“使用社交媒体账户登录”时，他们需要手动登录并给予同意，但如果他们稍后重新访问客户端应用程序，他们通常可以通过一次点击重新登录。

### 3. 授权码授予

如果用户同意所请求的访问权限，他们的浏览器将被重定向到授权请求的 `redirect_uri` 参数中指定的 `/callback` 端点。生成的 `GET` 请求将包含授权码作为查询参数。根据配置，它还可能发送与授权请求中相同值的 `state` 参数。

```http
GET /callback?code=a1b2c3d4e5f6g7h8&state=ae13d489bd00e3c24 HTTP/1.1
Host: client-app.com
```

### 4. 访问令牌请求

一旦客户端应用程序收到授权码，它需要将其交换为访问令牌。为此，它向 OAuth 服务的 `/token` 端点发送一个服务器到服务器的 `POST` 请求。从此时开始的所有通信都在安全的后端通道中进行，因此通常无法被攻击者观察或控制。

```http
POST /token HTTP/1.1
Host: oauth-authorization-server.com

client_id=12345&client_secret=SECRET&redirect_uri=https://client-app.com/callback&grant_type=authorization_code&code=a1b2c3d4e5f6g7h8
```

除了 `client_id` 和授权码 `code` 之外，您还会注意到以下新参数：

- `client_secret`
  客户端应用程序必须通过包含其在向 OAuth 服务注册时分配的秘密密钥来进行身份验证。

- `grant_type`
  用于确保新端点知道客户端应用程序想要使用哪种授权类型。在这种情况下，应将其设置为 `authorization_code`。

### 5. 访问令牌授予

OAuth 服务将验证访问令牌请求。如果一切符合预期，服务器将响应授予客户端应用程序具有所请求作用域的访问令牌。

```json
{
    "access_token": "z0y9x8w7v6u5",
    "token_type": "Bearer",
    "expires_in": 3600,
    "scope": "openid profile",
    …
}
```

### 6. API 调用

现在客户端应用程序有了访问令牌，它终于可以从资源服务器获取用户数据了。为此，它向 OAuth 服务的 `/userinfo` 端点发出 API 调用。访问令牌在 `Authorization: Bearer` 头中提交，以证明客户端应用程序有权访问此数据。

```http
GET /userinfo HTTP/1.1
Host: oauth-resource-server.com
Authorization: Bearer z0y9x8w7v6u5
```

### 7. 资源授予

资源服务器应验证令牌是否有效以及是否属于当前客户端应用程序。如果是，它将响应发送所请求的资源，即基于访问令牌作用域的用户数据。

```json
{
    "username":"carlos",
    "email":"carlos@carlos-montoya.net",
    …
}
```

客户端应用程序最终可以将此数据用于其预期目的。在 OAuth 身份验证的情况下，它通常被用作一个 ID 来授予用户一个已认证的会话，从而有效地将他们登录。

## 隐式授权类型

隐式授权类型要简单得多。客户端应用程序不是首先获取授权码然后将其交换为访问令牌，而是在用户给予同意后立即接收访问令牌。

您可能想知道为什么客户端应用程序不总是使用隐式授权类型。答案相对简单——它远不够安全。当使用隐式授权类型时，所有通信都通过浏览器重定向进行——没有像授权码流程那样的安全后端通道。这意味着敏感的访问令牌和用户数据更容易受到潜在攻击。

隐式授权类型更适合单页应用程序和原生桌面应用程序，这些应用程序无法轻松地在后端存储 `client_secret`，因此从使用授权码授权类型中获益较少。

![OAuth 隐式授权类型流程](https://portswigger.net/web-security/images/oauth-implicit-flow.jpg)

### 1. 授权请求

隐式流程的开始方式与授权码流程大致相同。唯一的主要区别是 `response_type` 参数必须设置为 `token`。

```http
GET /authorization?client_id=12345&redirect_uri=https://client-app.com/callback&response_type=token&scope=openid%20profile&state=ae13d489bd00e3c24 HTTP/1.1
Host: oauth-authorization-server.com
```

### 2. 用户登录和同意

用户登录并决定是否同意所请求的权限。此过程与授权码流程完全相同。

### 3. 访问令牌授予

如果用户同意所请求的访问权限，这就是开始有所不同之处。OAuth 服务将用户的浏览器重定向到授权请求中指定的 `redirect_uri`。但是，它不是发送包含授权码的查询参数，而是将访问令牌和其他令牌特定数据作为 **URL 片段**发送。

```http
GET /callback#access_token=z0y9x8w7v6u5&token_type=Bearer&expires_in=5000&scope=openid%20profile&state=ae13d489bd00e3c24 HTTP/1.1
Host: client-app.com
```

由于访问令牌在 URL 片段中发送，它永远不会直接发送到客户端应用程序。相反，客户端应用程序必须使用适当的脚本来提取片段并存储它。

### 4. API 调用

一旦客户端应用程序成功从 URL 片段中提取了访问令牌，它就可以使用它向 OAuth 服务的 `/userinfo` 端点发出 API 调用。与授权码流程不同，这也通过浏览器进行。

```http
GET /userinfo HTTP/1.1
Host: oauth-resource-server.com
Authorization: Bearer z0y9x8w7v6u5
```

### 5. 资源授予

资源服务器应验证令牌是否有效以及是否属于当前客户端应用程序。如果是，它将响应发送所请求的资源，即基于与访问令牌关联的作用域的用户数据。

```json
{
    "username":"carlos",
    "email":"carlos@carlos-montoya.net"
}
```

客户端应用程序最终可以将此数据用于其预期目的。在 OAuth 身份验证的情况下，它通常被用作一个 ID 来授予用户一个已认证的会话，从而有效地将他们登录。
