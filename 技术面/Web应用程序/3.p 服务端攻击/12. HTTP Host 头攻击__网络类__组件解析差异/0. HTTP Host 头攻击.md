## 什么是 HTTP Host 头？

HTTP Host 头是 HTTP/1.1 起强制要求的请求头。它指定了客户端想要访问的域名。例如，当用户访问 `https://portswigger.net/web-security` 时，他们的浏览器会构造一个包含如下 Host 头的请求：

```http
GET /web-security HTTP/1.1
Host: portswigger.net
```

在某些情况下，例如请求被中间系统转发时，Host 值在到达预期的后端组件之前可能会被修改。我们将在下文更详细地讨论这种情况。

## HTTP Host 头的用途是什么？

HTTP Host 头的目的是帮助识别客户端想要与哪个后端组件通信。如果请求不包含 Host 头，或者 Host 头以某种方式格式错误，这可能在将传入请求路由到预期应用程序时导致问题。

从历史上看，这种模糊性并不存在，因为每个 IP 地址只会为一个域托管内容。如今，很大程度上由于基于云的解决方案和外包相关架构的日益增长的趋势，多个网站和应用程序通过同一个 IP 地址访问是很常见的。这种方法也因 IPv4 地址耗尽而日益普及。

当多个应用程序可通过同一 IP 地址访问时，这通常是以下场景之一的结果。

### 虚拟主机

一种可能的情况是单个 Web 服务器托管多个网站或应用程序。这可能是同一个所有者的多个网站，但不同所有者的网站托管在单个共享平台上也是可能的。这不像过去那么常见，但仍然发生在某些基于云的 SaaS 解决方案中。

无论哪种情况，尽管每个不同的网站都有不同的域名，但它们都与服务器共享一个共同的 IP 地址。以这种方式在单台服务器上托管的网站被称为“虚拟主机”。

对于访问网站的正常用户来说，虚拟主机通常与托管在专用服务器上的网站无法区分。

### 通过中间系统路由流量

另一种常见情况是网站托管在不同的后端服务器上，但客户端和服务器之间的所有流量都通过中间系统路由。这可能是一个简单的负载均衡器或某种反向代理服务器。当客户端通过内容分发网络（CDN）访问网站时，这种设置尤其普遍。

在这种情况下，即使网站托管在不同的后端服务器上，它们的所有域名都解析到中间组件的单一 IP 地址。这带来了一些与虚拟主机相同的挑战，因为反向代理或负载均衡器需要知道应将每个请求路由到哪个适当的后端。

### HTTP Host 头如何解决这个问题？

在这两种场景中，都依赖 Host 头来指定预期的接收者。一个常见的类比是向住在公寓楼里的人寄信的过程。整栋楼有相同的街道地址，但在这个街道地址背后有许多不同的公寓，每个公寓都需要以某种方式收到正确的邮件。解决这个问题的一个方法就是在地址中包含公寓号码或收件人姓名。在 HTTP 消息的情况下，Host 头起到了类似的作用。

当浏览器发送请求时，目标 URL 将解析到特定服务器的 IP 地址。当该服务器收到请求时，它会参考 Host 头来确定预期的后端，并相应地转发请求。

## 什么是 HTTP Host 头攻击？

HTTP Host 头攻击利用的是以不安全方式处理 Host 头值的易受攻击网站。如果服务器隐式信任 Host 头，并且未能正确验证或转义它，攻击者可能能够使用此输入注入有害载荷来操纵服务器端行为。直接将载荷注入 Host 头的攻击通常被称为“Host 头注入”攻击。

现成的 Web 应用程序通常不知道它们被部署在哪个域上，除非在设置期间手动在配置文件中指定。当它们需要知道当前域时（例如，生成包含在电子邮件中的绝对 URL），它们可能会从 Host 头中检索域：

```php
<a href="https://_SERVER['HOST']/support">Contact support</a>
```

该头值也可能用于网站基础设施不同系统之间的各种交互中。

由于 Host 头实际上是用户可控的，这种做法可能导致许多问题。如果输入没有被正确转义或验证，Host 头就是利用一系列其他漏洞的潜在向量，最显著的是：

- Web 缓存投毒
- 特定功能中的业务逻辑缺陷
- 基于路由的 SSRF
- 经典服务端漏洞，如 SQL 注入

## HTTP Host 头漏洞是如何产生的？

HTTP Host 头漏洞通常源于错误地认为该头不是用户可控的。这导致对 Host 头产生隐式信任，并导致对其值的验证或转义不足，尽管攻击者可以使用 Burp Proxy 等工具轻松修改它。

即使 Host 头本身被更安全地处理，根据处理传入请求的服务器的配置，Host 也可能通过注入其他头而被覆盖。有时网站所有者不知道这些头默认被支持，因此它们可能不会受到同等程度的审查。

事实上，许多这些漏洞的产生不是因为不安全的编码，而是因为相关基础设施中一个或多个组件的不安全配置。这些配置问题之所以发生，是因为网站将第三方技术集成到其架构中，但不一定了解配置选项及其安全影响。

## 如何防止 HTTP Host 头攻击

要防止 HTTP Host 头攻击，最简单的方法是完全避免在服务端代码中使用 Host 头。仔细检查每个 URL 是否真的需要是绝对路径。您通常会发现自己可以使用相对 URL 代替。这个简单的更改可以帮助您特别防止 Web 缓存投毒漏洞。

防止 HTTP Host 头攻击的其他方法包括：

### 保护绝对 URL

当必须使用绝对 URL 时，您应该要求在配置文件中手动指定当前域，并引用该值而不是 Host 头。例如，这种方法将消除密码重置投毒的威胁。

### 验证 Host 头

如果必须使用 Host 头，请确保正确验证它。这应涉及根据允许域的白名单进行检查，并拒绝或重定向任何未识别主机的请求。您应查阅框架的文档以获取如何操作的指导。例如，Django 框架在设置文件中提供了 `ALLOWED_HOSTS` 选项。这种方法将减少您对 Host 头注入攻击的暴露。

### 不支持 Host 覆盖头

同样重要的是，检查您不支持可用于构造这些攻击的额外头，特别是 `X-Forwarded-Host`。请记住，这些可能默认被支持。

### 白名单允许的域

为了防止对内部基础设施的基于路由的攻击，您应将负载均衡器或任何反向代理配置为仅将请求转发到允许域的白名单。

### 小心内部专用虚拟主机

使用虚拟主机时，您应避免将内部专用网站和应用程序与面向公众的内容托管在同一台服务器上。否则，攻击者可能通过 Host 头操纵访问内部域。
