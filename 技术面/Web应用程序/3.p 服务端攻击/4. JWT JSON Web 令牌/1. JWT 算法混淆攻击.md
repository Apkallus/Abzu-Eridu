# 算法混淆攻击

算法混淆攻击（也称为密钥混淆攻击）发生在攻击者能够强制服务器使用与网站开发者预期不同的算法来验证 JSON Web 令牌（JWT）签名时。如果这种情况没有得到妥善处理，攻击者可能能够在不需要知道服务器秘密签名密钥的情况下，伪造包含任意值的有效 JWT。

## 对称与非对称算法

JWT 可以使用一系列不同的算法进行签名。其中一些算法，如 HS256（HMAC + SHA-256），使用“对称”密钥。这意味着服务器使用单个密钥来签署和验证令牌。显然，这需要像密码一样保密。

其他算法，如 RS256（RSA + SHA-256），使用“非对称”密钥对。这包括一个私钥（服务器用它来签署令牌）和一个数学上相关的公钥（可用于验证签名）。

顾名思义，私钥必须保密，但公钥通常被共享，以便任何人都可以验证服务器颁发的令牌的签名。

## 算法混淆漏洞是如何产生的？

算法混淆漏洞通常源于 JWT 库的实现缺陷。尽管实际的验证过程因使用的算法而异，但许多库提供了一种通用的、与算法无关的验证签名方法。这些方法依赖于令牌头中的 `alg` 参数来确定它们应执行的验证类型。

以下伪代码展示了一个简化的示例，说明了 JWT 库中这个通用 `verify()` 方法的声明可能的样子：

```java
function verify(token, secretOrPublicKey){
    algorithm = token.getAlgHeader();
    if(algorithm == "RS256"){
        // Use the provided key as an RSA public key
    } else if (algorithm == "HS256"){
        // Use the provided key as an HMAC secret key
    }
}
```
- 此处正确的按照算法进入不同分支

当随后使用此方法的网站开发者假设它将专门处理使用非对称算法（如 RS256）签名的 JWT 时，问题就出现了（即，开发者假设库方法将自动区分算法）。由于这种有缺陷的假设，他们可能总是向该方法传递一个固定的公钥（也向对称算法传递服务器公钥），如下所示：

```java
publicKey = <public-key-of-server>;
token = request.getCookie("session");
verify(token, publicKey);
```

在这种情况下，如果服务器收到使用对称算法（如 HS256）签名的令牌，库的通用 `verify()` 方法将把公钥视为 HMAC 密钥。这意味着攻击者可以使用 HS256 和公钥签署令牌，而服务器将使用相同的公钥来验证签名。
- 服务器使用服务器的公开公钥进行对称算法验证（公钥作为对称算法的秘密），攻击者在对称算法中使用服务器公钥对 JWT 签名

> **注意：** 您用来签署令牌的公钥必须与服务器上存储的公钥完全一致。这包括使用相同的格式（如 X.509 PEM）并保留任何不可打印字符（如换行符）。在实践中，您可能需要尝试不同的格式才能使此攻击生效。

## 执行算法混淆攻击

算法混淆攻击通常涉及以下高级步骤：

1. [获取服务器的公钥](#步骤-1---获取服务器的公钥)
2. [将公钥转换为合适的格式](#步骤-2---将公钥转换为合适的格式)
3. [创建一个恶意的 JWT](#步骤-3---修改您的-jwt)，其中包含修改后的载荷，并将 `alg` 头设置为 `HS256`。
4. [使用 HS256 签署令牌](#步骤-4---使用公钥签署-jwt)，使用公钥作为密钥。

在本节中，我们将更详细地介绍此过程，演示如何使用 Burp Suite 执行此类攻击。

### 步骤 1 - 获取服务器的公钥

服务器有时会通过映射到 `/jwks.json` 或 `/.well-known/jwks.json` 等标准端点，以 JSON Web Key（JWK）对象的形式暴露其公钥。这些可能存储在一个名为 `keys` 的 JWK 数组中，这被称为 JWK Set。

```json
{
    "keys": [
        {
            "kty": "RSA",
            "e": "AQAB",
            "kid": "75d0ef47-af89-47a9-9061-7c02a610d5ab",
            "n": "o-yy1wpYmffgXBxhAUJzHHocCuJolwDqql75ZWuCQ_cb33K2vh9mk6GPM9gNN4Y_qTVX67WhsN3JvaFYw-fhvsWQ"
        },
        {
            "kty": "RSA",
            "e": "AQAB",
            "kid": "d8fDFo-fS9-faS14a9-ASf99sa-7c1Ad5abA",
            "n": "fc3f-yy1wpYmffgXBxhAUJzHql79gNNQ_cb33HocCuJolwDqmk6GPM4Y_qTVX67WhsN3JvaFYw-dfg6DH-asAScw"
        }
    ]
}
```

即使密钥没有被公开暴露，您也可能能够从一对现有的 JWT 中[提取它](#从现有令牌中推导公钥)。


或者，应用程序可能将同一密钥复用于 TLS 证书和签名 JWT 。在这种情况下，使用以下命令从服务器下载密钥：

```sh
openssl s_client -connect example.org:443 | openssl x509 -pubkey -noout
```

### 步骤 2 - 将公钥转换为合适的格式

尽管服务器可能以 JWK 格式暴露其公钥，但在验证令牌签名时，它将使用来自其本地文件系统或数据库的自己的密钥副本。这可能以不同的格式存储。

为了使攻击生效，您用来签署 JWT 的密钥版本必须与服务器的本地副本完全一致。除了格式相同外，每个字节都必须匹配，包括任何不可打印字符。

出于本示例的目的，假设我们需要 X.509 PEM 格式的密钥。您可以使用 Burp 中的 [JWT Editor](https://portswigger.net/bappstore/26aaa5ded2f74beea19e2ed8345a93dd) 扩展将 JWK 转换为 PEM，如下所示：

1. 加载扩展后，在 Burp 的主标签栏中，转到 **JWT Editor Keys** 选项卡。
2. 点击 **New RSA Key**。在对话框中，粘贴您之前获取的 JWK 格式公钥。
3. 选择 **PEM** 单选按钮，并复制转换生成的 PEM 格式公钥。
4. 转到 **Decoder** 选项卡，对 PEM 格式公钥进行 Base64 编码。
5. 回到 **JWT Editor Keys** 选项卡，点击 **New Symmetric Key**。
6. 在对话框中，点击 **Generate** 以 JWK 格式生成一个随机新密钥。
7. 将生成的 `k` 参数值（对称算法秘密）替换为您刚刚复制的 Base64 编码的 PEM 密钥。
8. 保存密钥。

### 步骤 3 - 修改您的 JWT

一旦您获得了合适格式的公钥，随意修改 JWT。只需确保 `alg` 头设置为 `HS256`。

### 步骤 4 - 使用公钥签署 JWT

使用 HS256 算法，以 RSA 公钥作为密钥，签署令牌。

## 从现有令牌中推导公钥

在公钥不易获得的情况下，您仍然可以通过从一对现有的 JWT 中推导密钥来测试算法混淆。使用诸如 `jwt_forgery.py` 之类的工具，此过程相对简单。您可以在 [`rsa_sign2n` GitHub 仓库](https://github.com/silentsignal/rsa_sign2n) 中找到此工具以及其他几个有用的脚本。

portswigger 创建了一个简化版本的工具，可将其作为单个命令运行（silentsignal 原始仓库提供本地构建的 docker 容器）：

```sh
docker run --rm -it portswigger/sig2n <token1> <token2>
```

> **注意：** 您需要 Docker CLI 来运行任一版本的工具。首次运行此命令时，它将自动从 Docker Hub 拉取镜像，这可能需要几分钟时间。

这将使用您提供的 JWT 来计算一个或多个 `n` 的潜在值。这些值中只有一个与服务器密钥使用的 `n` 值匹配。对于每个潜在值，我们的脚本都会输出：

- X.509 和 PKCS1 格式的 Base64 编码 PEM 格式公钥。
- 使用每个此类公钥签名的伪造 JWT（用来立即测试）。

要识别正确的密钥，请使用 Burp Repeater 发送包含每个伪造 JWT 的请求。其中只有一个是服务器能接受的。然后，您可以使用匹配的密钥来构造算法混淆攻击。

有关此过程如何工作的更多信息，以及如何使用标准 `jwt_forgery.py` 工具的详细信息，请参阅[仓库](https://github.com/silentsignal/rsa_sign2n)中提供的文档。
