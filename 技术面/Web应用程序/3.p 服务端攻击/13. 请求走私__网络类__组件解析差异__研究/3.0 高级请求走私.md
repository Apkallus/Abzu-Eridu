## HTTP/2 请求走私

在本节中，我们将向您展示，与普遍看法相反，实现 HTTP/2 实际上使许多网站更容易受到请求走私的攻击，即使它们以前对此类攻击是安全的。

### HTTP/2 消息长度

请求走私的根本在于利用不同服务器解释请求长度方式之间的差异。HTTP/2 引入了一种单一、健壮的机制来解决这个问题，长期以来被认为使其天生免疫请求走私。

虽然您在 Burp 中看不到这一点，但 HTTP/2 消息是通过网络以一系列独立的“帧”发送的。每个帧前面都有一个明确的长度字段，告诉服务器要读取多少字节。因此，请求的长度是其帧长度之和。

理论上，只要网站端到端使用 HTTP/2，这种机制意味着攻击者无法引入请求走私所需的歧义。然而，在实际中，由于 HTTP/2 降级这一普遍但危险的做法，情况往往并非如此。

### HTTP/2 降级

HTTP/2 降级是使用 HTTP/1 语法重写 HTTP/2 请求以生成等效 HTTP/1 请求的过程。Web 服务器和反向代理经常这样做，以便在与仅支持 HTTP/1 的后端服务器通信时为客户提供 HTTP/2 支持。这种做法是本节涵盖的许多攻击的先决条件。

#### 什么是 HTTP/2 降级？

由于 HTTP/2 仍然相对较新，支持它的 Web 服务器通常仍然需要与仅支持 HTTP/1 的遗留后端基础设施通信。因此，前端服务器将每个传入的 HTTP/2 请求使用 HTTP/1 语法重写，有效地生成其 HTTP/1 等效请求，这已成为一种常见做法。然后，这个“降级”后的请求被转发到相关的后端服务器。

当支持 HTTP/1 的后端发出响应时，前端服务器会逆转此过程，生成返回给客户端的 HTTP/2 响应。

这之所以有效，是因为每个版本的协议本质上都只是表示相同信息的不同方式。HTTP/1 消息中的每个项在 HTTP/2 中都有大致对应的项。

![将 HTTP/2 请求映射到 HTTP/1 请求](https://portswigger.net/web-security/request-smuggling/advanced/http2-downgrading)

因此，服务器在两种协议之间转换这些请求和响应相对简单。实际上，这正是 Burp 能够在消息编辑器中使用 HTTP/1 语法显示 HTTP/2 消息的方式。

HTTP/2 降级非常普遍，甚至是一些流行反向代理服务的默认行为。在某些情况下，甚至没有禁用它的选项。

#### HTTP/2 降级存在哪些风险？

HTTP/2 降级可能使网站暴露于请求走私攻击，尽管 HTTP/2 本身在端到端使用时通常被认为具有免疫力。

HTTP/2 的内置长度机制意味着，当使用 HTTP 降级时，可能存在三种不同的方式来指定同一请求的长度，这正是所有请求走私攻击的基础。

>
> - 我们将每条消息显示为单个实体，而不是单独的“帧”。
> - 我们使用纯文本名称和值字段显示头。

### H2.CL 漏洞

HTTP/2 请求不需要在头中明确指定其长度。在降级期间，这意味着前端服务器通常会添加一个 HTTP/1 `Content-Length` 头，其值使用 HTTP/2 的内置长度机制派生。有趣的是，HTTP/2 请求也可以包含自己的 `content-length` 头。在这种情况下，一些前端服务器会直接在生成的 HTTP/1 请求中重用此值。

规范规定 HTTP/2 请求中的任何 `content-length` 头必须与使用内置机制计算的长度匹配，但在降级之前并不总是被正确验证。因此，可能通过注入误导性的 `content-length` 头来走私请求。虽然前端将使用隐式的 HTTP/2 长度来确定请求的结束位置，但 HTTP/1 后端必须参考从您注入的头派生的 `Content-Length` 头，从而导致不同步。

**前端（HTTP/2）请求头：**

- `:method`: `POST`
- `:path`: `/example`
- `:authority`: `vulnerable-website.com`
- `content-type`: `application/x-www-form-urlencoded`
- `content-length`: `0`

**消息体：**

```http
GET /admin HTTP/1.1
Host: vulnerable-website.com
Content-Length: 10

x=1
```

**后端（HTTP/1）接收到的内容：**

```http
POST /example HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 0

GET /admin HTTP/1.1
Host: vulnerable-website.com
Content-Length: 10

x=1GET / H
```

> **提示：** 在执行某些请求走私攻击时，您希望受害者的请求头被附加到您的走私前缀中。然而，在某些情况下，这些可能会干扰您的攻击，导致重复头错误等。在上面的示例中，我们通过在走私前缀中包含一个尾随参数和一个 `Content-Length` 头来缓解此问题。通过使用比消息体稍长的 `Content-Length` 头，受害者的请求仍将附加到您的走私前缀，但会在头之前被截断（与之前小节的技术相同）。

### H2.TE 漏洞

分块传输编码与 HTTP/2 不兼容，规范建议任何您尝试注入的 `transfer-encoding: chunked` 头都应被剥离或请求被完全阻止。如果前端服务器未能做到这一点，并随后将请求降级给确实支持分块编码的 HTTP/1 后端，这也可能导致请求走私攻击。

**前端（HTTP/2）请求头：**

- `:method`: `POST`
- `:path`: `/example`
- `:authority`: `vulnerable-website.com`
- `content-type`: `application/x-www-form-urlencoded`
- `transfer-encoding`: `chunked`

**消息体：**

```
0

GET /admin HTTP/1.1
Host: vulnerable-website.com
Foo: bar
```

**后端（HTTP/1）接收到的内容：**

```http
POST /example HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Transfer-Encoding: chunked

0

GET /admin HTTP/1.1
Host: vulnerable-website.com
Foo: bar
```

如果网站容易受到 H2.CL 或 H2.TE 请求走私的攻击，您可以利用此行为执行我们在之前的请求走私实验中涵盖的相同攻击。

### 隐藏的 HTTP/2 支持

浏览器和其他客户端（包括 Burp）通常仅使用 HTTP/2 与通过 ALPN 作为 TLS 握手的一部分明确通告支持 HTTP/2 的服务器通信。

某些服务器支持 HTTP/2，但由于配置错误未能正确声明这一点。在这种情况下，由于客户端默认将其作为后备选项，服务器可能看起来仅支持 HTTP/1.1。因此，测试人员可能会忽略可行的 HTTP/2 攻击面，并错过协议级别的问题，例如我们上面介绍的基于 HTTP/2 降级的请求走私示例。

要强制 Burp Repeater 使用 HTTP/2，以便您可以手动测试此配置错误：

1. 从 **Settings** 对话框中，转到 **Tools > Repeater**。
2. 在 **Connections** 下，启用 **Allow HTTP/2 ALPN override** 选项。
3. 在 Repeater 中，转到 **Inspector** 面板并展开 **Request attributes** 部分。
4. 使用开关将 **Protocol** 设置为 **HTTP/2**。Burp 现在将在此选项卡上使用 HTTP/2 发送所有请求，无论服务器是否通告支持此协议。

> **注意：** 如果您使用 Burp Suite Professional，Burp Scanner 会自动检测隐藏的 HTTP/2 支持实例。

## 通过 CRLF 注入进行请求走私

即使网站采取措施防止基本的 H2.CL 或 H2.TE 攻击，例如验证 `content-length` 或剥离任何 `transfer-encoding` 头，HTTP/2 的二进制格式也启用了一些新的方式来绕过这些前端措施。

在 HTTP/1 中，有时您可以利用服务器处理独立换行符（`\n`）字符方式的差异来走私被禁止的头。如果后端将其视为分隔符，而前端服务器不这样做，则某些前端服务器将完全无法检测到第二个头。

```http
Foo: bar\nTransfer-Encoding: chunked
```

这种差异在完整 CRLF（`\r\n`）序列的处理中不存在，因为所有 HTTP/1 服务器都认为这会终止头。

另一方面，由于 HTTP/2 消息是二进制的而不是基于文本的，每个头的边界基于明确的预定偏移量，而不是分隔符字符。这意味着 `\r\n` 在头值内不再具有特殊意义，因此可以包含在值**内部**而不会导致头被拆分：

- `foo`: `bar\r\nTransfer-Encoding: chunked`

这本身可能看起来相对无害，但当它被重写为 HTTP/1 请求时，`\r\n` 将再次被解释为头分隔符。因此，HTTP/1 后端服务器将看到两个不同的头：

```http
Foo: bar
Transfer-Encoding: chunked
```

## HTTP/2 请求拆分

当我们研究[响应队列投毒]时，您学习了如何将单个 HTTP 请求在后端拆分为恰好两个完整的请求。在我们看的示例中，拆分发生在消息体内部，但当涉及 HTTP/2 降级时，您也可以改为在头中引起此拆分。

这种方法更加通用，因为您不依赖于使用允许包含消息体的请求方法。例如，您甚至可以使用 `GET` 请求：

**前端（HTTP/2）请求头：**

- `:method`: `GET`
- `:path`: `/`
- `:authority`: `vulnerable-website.com`
- `foo`: 
  ```
  bar\r\n
  \r\n
  GET /admin HTTP/1.1\r\n
  Host: vulnerable-website.com
  ```

这在 `content-length` 被验证且后端不支持分块编码的情况下也很有用。

### 考虑前端重写

要在头中拆分请求，您需要了解前端服务器如何重写请求，并在手动添加任何 HTTP/1 头时考虑这一点。否则，其中一个请求可能缺少强制性头。

例如，您需要确保后端接收的两个请求都包含 `Host` 头。前端服务器通常在降级期间剥离 `:authority` 伪头，并将其替换为新的 HTTP/1 `Host` 头。有不同的方法来实现这一点，这会影响您需要将注入的 `Host` 头放置在哪里。

考虑以下请求（注意 `foo` 头中的内容）：

**前端（HTTP/2）请求头：**

- `:method`: `GET`
- `:path`: `/`
- `:authority`: `vulnerable-website.com`
- `foo`:
  ```
  bar\r\n
  \r\n
  GET /admin HTTP/1.1\r\n
  Host: vulnerable-website.com
  ```

在重写期间，一些前端服务器会将新的 `Host` 头附加到当前头列表的末尾。就 HTTP/2 前端而言，这在 `foo` 头之后。请注意，这也在请求在后端被拆分的位置之后。这意味着第一个请求将根本没有 `Host` 头，而走私的请求将有两个。在这种情况下，您需要定位您注入的 `Host` 头，以便它在拆分发生后最终出现在第一个请求中：

**调整后的请求头：**

- `:method`: `GET`
- `:path`: `/`
- `:authority`: `vulnerable-website.com`
- `foo`:
  ```
  bar\r\n
  Host: vulnerable-website.com\r\n
  \r\n
  GET /admin HTTP/1.1
  ```

您还需要以类似方式调整您想要注入的任何内部头的位置。

> **提示：** 在上面的示例中，我们以触发[响应队列投毒]的方式拆分请求，但您也可以以这种方式走私用于经典请求走私攻击的前缀。在这种情况下，您注入的头可能与后端附加到您前缀的请求中的头冲突，导致重复头错误或导致请求在错误位置终止。为了缓解此问题，您可以在走私前缀中包含一个尾随消息体参数以及一个比消息体稍长的 `Content-Length` 头。受害者的请求仍将附加到您的走私前缀，但会在头之前被截断。

## HTTP 请求隧道

我们到目前为止涵盖的许多请求走私攻击之所以可能，是因为前端和后端服务器之间的同一连接用于处理多个请求。HTTP 请求隧道提供了一种即使在完全不复用连接的情况下也能构造高严重性漏洞利用的方法。

## 0.CL 请求走私

当前端服务器忽略后端服务器处理的 `Content-Length` 头时，就会发生 0.CL 反同步攻击。由于服务器之间的连接死锁，这种情况长期以来被认为无法利用。

然而，通过将 0.CL 攻击与早期响应小工具（一种使后端在收到完整请求体之前响应的技术）相结合，攻击者可以打破死锁，然后使用双重反同步构建完整的漏洞利用。这一突破使得利用 0.CL 场景成为可能。

有关更多技术细节，请参见随附的白皮书：[HTTP/1.1 Must Die](https://portswigger.net/research/http1-must-die)。

0.CL 死锁：
- 前后端对 CL 头部的解析存在差异
- 前端无视请求1的 CL 发送到后端并等待响应1
- 后端等待前端发送请求1的 CL 数量字符

0.CL 死锁打破：
- 发送后端的特异路径为请求1
  - 静态资源立即返回资源
  - `con`、`nul` 等文件名立即返回异常响应，但不关闭连接
- 后端访问请求1的特异路径，并立即返回响应1
- 此时前端收到响应1，发送请求2
- 后端收到请求2，提取其中被视为之前请求1残余的 CL 数量字符并丢弃。解析剩余内容作为后端视角的请求2，并返回响应2
  - 注，与研究的理想示例不同（前端不重写、排序请求头，后端精准切割），由于前端的重写、排序行为，导致载荷请求2无法被后端精确分隔，几乎必然导致载荷请求2的响应为异常响应。响应2无法用来判断走私是否成功。
  - 注，应当实际查看载荷请求2中的最终走私请求是否成功被附加到后续普通请求。但仍不稳定，几乎未在响应3出现，而是不定的出现在后续的十几个请求其中之一。需在走私后发送大量普通请求，并多次尝试。
