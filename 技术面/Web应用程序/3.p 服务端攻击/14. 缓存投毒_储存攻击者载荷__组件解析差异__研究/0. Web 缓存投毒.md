# Web 缓存投毒

在本节中，我们将讨论什么是 Web 缓存投毒，以及哪些行为可能导致 Web 缓存投毒漏洞。我们还将介绍一些利用这些漏洞的方法，并提出一些可以减少风险的建议。

## 什么是 Web 缓存投毒？

Web 缓存投毒是一种高级技术，攻击者利用 Web 服务器和缓存的行为，将有害的 HTTP 响应提供给其他用户。

从根本上说，Web 缓存投毒涉及两个阶段。
1. 首先，攻击者必须弄清楚如何从后端服务器获取一个无意中包含某种危险载荷的响应。
2. 一旦成功，他们需要确保其响应被缓存，然后提供给预期的受害者。

被投毒的 Web 缓存可能成为分发各种不同攻击的毁灭性手段，利用 XSS、JavaScript 注入、开放重定向等漏洞。

### Web 缓存投毒研究

此技术最早由我们 2018 年的研究论文《Practical Web Cache Poisoning》推广，并在 2020 年通过第二篇研究论文《Web Cache Entanglement: Novel Pathways to Poisoning》进一步发展。如果您有兴趣详细了解我们如何在实际中发现并利用这些漏洞，完整文章可在我们的研究页面上找到。

### Web 缓存如何工作？

要理解 Web 缓存投毒漏洞是如何产生的，对 Web 缓存的工作原理有一个基本了解是很重要的。

如果服务器必须为每个 HTTP 请求单独发送新的响应，这可能会使服务器过载，导致延迟问题和糟糕的用户体验，尤其是在繁忙时期。缓存主要是减少此类问题的一种手段。

缓存位于服务器和用户之间，它保存（缓存）对特定请求的响应，通常持续一段固定的时间。如果另一个用户随后发送一个等效的请求，缓存只需直接将缓存响应的副本提供给用户，而无需后端参与。这通过减少服务器必须处理的重复请求数量，大大减轻了服务器的负载。

#### 缓存键

当缓存收到 HTTP 请求时，它首先必须确定是否有可以直接提供的缓存响应，还是必须将请求转发给后端服务器处理。缓存通过比较请求的预定义子集（统称为“缓存键”）来识别等效请求。通常，这包括请求行和 `Host` 头。不包含在缓存键中的请求组件被称为“未键化”（unkeyed）。

如果传入请求的缓存键与先前请求的键匹配，则缓存认为它们是等效的。因此，它将为原始请求生成的缓存响应的副本提供给当前请求。这适用于所有后续具有匹配缓存键的请求，直到缓存响应过期。

关键在于，请求的其他组件完全被缓存忽略。我们将在后面更详细地探讨这种行为的影响。

#### 缓存条件

后端服务器或使用特定状态决定当前请求的响应是否被缓存。例如，根据是否携带有效 Cookie

- 设置有效 cookie
    - 请求
        ```http
        GET / HTTP/2
        Host: id.web-security-academy.net
        Cookie: session=ZZgCsogG2X3s9kUPC3g4e9MT5XWJ39bl
        ```

    - 响应
        ```http
        HTTP/2 200 OK
        Content-Type: text/html; charset=utf-8
        X-Frame-Options: SAMEORIGIN
        Cache-Control: max-age=30
        Age: 0
        X-Cache: miss
        Content-Length: 11581
        ```
        - `Cache-Control: max-age=30` 包含缓存头部

- 设置无效 cookie
    - 请求
        ```http
        GET / HTTP/2
        Host: id.web-security-academy.net
        Cookie: session=x
        ```

    - 响应
        ```http
        HTTP/2 200 OK
        Content-Type: text/html; charset=utf-8
        Set-Cookie: session=sosuDmb81wn9WywJ18aOnh9IcONR5uib; Secure; HttpOnly; SameSite=None
        Cache-Control: no-cache
        X-Frame-Options: SAMEORIGIN
        Content-Length: 11531
        ```
        - `Cache-Control: no-cache` 且无缓存头部

## Web 缓存投毒攻击的影响是什么？

Web 缓存投毒的影响在很大程度上取决于两个关键因素：

- **攻击者能够成功缓存的内容**：由于投毒的缓存更多是一种分发手段而非独立攻击，Web 缓存投毒的影响与注入载荷的有害程度密不可分。与大多数攻击类型一样，Web 缓存投毒也可以与其他攻击结合使用，以进一步升级潜在影响。
- **受影响页面的流量大小**：投毒的响应只会提供给在缓存被投毒期间访问受影响页面的用户。因此，影响范围可能从不存在到巨大，具体取决于该页面是否受欢迎。例如，如果攻击者成功投毒了某个主要网站首页的缓存响应，攻击可能会影响成千上万的用户，而无需攻击者的任何后续交互。

请注意，缓存条目的持续时间不一定影响 Web 缓存投毒的影响。攻击通常可以被编写为无限期地重新投毒缓存。

## 构造 Web 缓存投毒攻击

一般来说，构造基本的 Web 缓存投毒攻击涉及以下步骤：

1. [识别和评估未键化输入](#识别和评估未键化输入)
2. [从后端服务器获取有害响应](#从后端服务器获取有害响应)
3. [使响应被缓存](#使响应被缓存)

### 识别和评估未键化输入

任何 Web 缓存投毒攻击都依赖于操纵未键化输入（如头）。Web 缓存在决定是否向用户提供缓存响应时会忽略未键化输入。这种行为意味着您可以使用它们注入载荷并获取一个“投毒的”响应，如果被缓存，该响应将提供给所有具有匹配缓存键的请求用户。因此，构造 Web 缓存投毒攻击的第一步是识别服务器支持的未键化输入。

您可以通过手动向请求添加随机输入并观察它们是否对响应产生影响来识别未键化输入。这可能是明显的，例如直接在响应中反射输入，或触发完全不同的响应。然而，有时影响更为微妙，需要一些侦探工作来弄清楚。您可以使用 Burp Comparer 等工具来比较有和没有注入输入的响应，但这仍然涉及大量手动工作。

#### Param Miner

幸运的是，您可以通过从 BApp 商店向 Burp 添加 [Param Miner](https://portswigger.net/bappstore/17d2949a985c4b7ca092728dba871943) 扩展来自动化识别未键化输入的过程。要使用 Param Miner，您只需右键单击要调查的请求，然后点击 “Guess headers”。Param Miner 随后在后台运行，从其内置的广泛头列表发送包含不同输入的请求。如果包含其注入输入的请求对响应产生影响，Param Miner 会在 Burp 中记录这一点——如果您使用 Burp Suite Professional，则在 “Issues” 窗格中；如果您使用 Burp Suite Community Edition，则在扩展的 “Output” 选项卡中（“Extensions” > “Installed” > “Param Miner” > “Output”）。

**注意：** 在实时网站上测试未键化输入时，存在无意中导致缓存将您生成的响应提供给真实用户的风险。因此，重要的是确保您的请求都具有唯一的缓存键，以便它们只为您自己服务。为此，您可以在每次发出请求时手动向请求行添加缓存破坏器（如唯一参数）。或者，如果您使用 Param Miner，它有选项可以自动为每个请求添加缓存破坏器。

除此之外，添加缓存破坏参数后的缓存键不同，导致每次的测试请求均得到即时响应（未命中），而不是之前测试的缓存命中。

> issues 显示的请求响应内容可能不匹配。需在 issues 或扩展的输出界面报告简略探测结果时，于 logger 中搜索对应项目以查看实际请求响应，或手动测试

### 从后端服务器获取有害响应

一旦您识别了一个未键化输入，下一步是评估网站究竟如何处理它。理解这一点对于成功获取有害响应至关重要。如果输入在服务器响应中被反射而未经适当清理，或被用于动态生成其他数据，那么这就是 Web 缓存投毒的潜在入口点。

### 使响应被缓存

操纵输入以获取有害响应只是成功的一半，但除非您能导致响应被缓存，否则不会有多大作用，而这有时可能很棘手。

响应是否被缓存可能取决于各种因素，例如文件扩展名、内容类型、路由、状态码和响应头。您可能需要花一些时间在不同页面上尝试请求并研究缓存的行为。一旦您弄清楚了如何缓存包含恶意输入的响应，您就可以准备将漏洞利用传递给潜在受害者。

## 如何防止 Web 缓存投毒漏洞

防止 Web 缓存投毒的最终方法显然是完全禁用缓存。虽然对于许多网站来说这可能不是一个现实的选择，但在其他情况下，可能是可行的。例如，如果您仅因为采用 CDN 时默认开启了缓存而使用缓存，那么评估默认缓存选项是否真的反映了您的需求可能是值得的。

即使您确实需要使用缓存，将其限制为纯静态响应也是有效的，前提是您对什么算作“静态”保持足够的警惕。例如，确保攻击者无法诱骗后端服务器获取他们制作的恶意版本的静态资源而不是真实版本。

这也与更广泛的 Web 安全观点有关。如今大多数网站都将各种第三方技术融入其开发流程和日常运营中。无论您自己的内部安全态势多么健壮，一旦您将第三方技术融入您的环境，您就依赖其开发者同样具有安全意识。基于“您的安全性取决于您最薄弱的环节”这一原则，务必确保在集成任何第三方技术之前完全了解其安全影响。

具体到 Web 缓存投毒的上下文中，这不仅意味着决定是否保持默认开启缓存，还意味着查看您的 CDN 支持哪些头。上面讨论的几个 Web 缓存投毒漏洞之所以暴露，是因为攻击者能够操纵一系列晦涩的请求头，其中许多对网站功能完全是不必要的。同样，您可能纯粹因为实现了一些默认支持这些未键化输入的技术，而在不知不觉中暴露于此类攻击。如果某个头对于网站运行不是必需的，则应禁用它。

在实现缓存时，您还应采取以下预防措施：

- 如果出于性能考虑考虑将某些内容从缓存键中排除，请改为重写请求。
- 不接受胖 `GET` 请求。请注意，某些第三方技术可能默认允许此行为。
- 修补客户端漏洞，即使它们看起来不可利用。其中一些漏洞可能由于缓存行为的不可预测特性而实际上可以被利用。迟早会有人发现一个特性（无论是基于缓存的还是其他），使该漏洞变得可利用。
