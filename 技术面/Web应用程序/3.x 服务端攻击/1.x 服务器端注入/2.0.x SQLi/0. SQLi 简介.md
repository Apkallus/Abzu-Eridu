## SQL 注入

几乎每一个Web应用程序都使用数据库来保存操作所需的各种信息。例如，网上零售商所用的Web应用程序使用数据库保存以下信息：

- 用户账户、证书和个人信息；
- 所销售商品的介绍与价格；
- 订单、账单和支付细节；
- 每名应用程序用户的权限。

应用程序与后端数据库交互以执行各种操作，例如访问、检索和删除记录。而 SQL（结构化查询语言）是应用程序管理和与数据库通信的语言。SQL是一种解释型语言，Web应用程序经常建立合并用户提交的数据的 SQL 语句。因此，如果建立语句的方法不安全，那么应用程序可能易于受到 SQL 注入攻击。

许多主流应用程序采用 API 来避免 SQL 注入，如果使用得当，这些 API 能够有效阻止 SQL 注入攻击。在这些情况下，通常只有在无法应用这些防御机制时，SQL 注入才会发生。有时，查找 SQL 注入漏洞是一项艰难的任务，需要测试员坚持不懈地在应用程序中探查一两个无法应用常规控制的实例。

成功的 SQL 注入攻击可以从数据库读取敏感数据、修改数据库数据（插入/更新/删除）、对数据库执行管理操作（例如关闭 DBMS）、恢复 DBMS 文件系统上给定文件的内容或将文件写入文件系统，并在某些情况下向操作系统发出命令。SQL 注入攻击是注入攻击的一种，其中 SQL 命令被注入数据平面输入，以影响预定义 SQL 命令的执行。

通常，Web 应用程序构造 SQL 语句的方式涉及程序员编写的 SQL 语法与用户提供的数据混合。例如：

`select title, text from news where id=$id`

在上面的示例中，变量 `$id` 包含用户提供的数据，其余部分是程序员提供的 SQL 静态部分；使 SQL 语句动态化。

由于其构造方式，用户可以提供精心设计的输入，试图使原始 SQL 语句执行用户选择的进一步操作。下面的示例说明了用户提供的数据 "10 or 1=1"，改变了 SQL 语句的逻辑，修改了 WHERE 子句，添加了条件 "or 1=1"。

`select title, text from news where id=10 or 1=1`

对于各种数据库的特性，访问与目标数据库相同的、在本地安装的数据库会有极大帮助。通常，只需修改一个语法或者参考一个内置表或功能就可实现自己的目的。从目标应用程序收到的响应一般并不完整或者含义模糊，需要猜测才能理解。如果能交叉参考相同数据库的一个完全“透明”运行的版本，理解起来就容易得多。

如果这种方法不可行，最好找一个可以进行测试的适当交互式在线环境，如 [SQLzoo.net 中的交互式在线教程](https://sqlzoo.net/wiki/SQL_Tutorial)。

### SQL 注入的分类

SQL 注入涉及检索数据库内容，这取决于所使用的 SQL 注入方法和用于提取数据库的通道。尽管此分类中有多种选择，但它们通常取决于所实现的后端技术。

- **In-band（带内注入）**：
    使用与注入 SQL 代码相同的通道提取数据，检索到的数据直接呈现在应用程序网页中。基于错误和基于 UNION 的提取方法属于此类别。

- **Out-of-band（带外注入）**：
    使用不同的通道检索数据。例如，HTTP 请求、DNS 查找甚至电子邮件等替代方式

- **Inferential（推断注入）/ Blind（盲注）**：
    攻击者不直接检索数据，而是向数据库发送一系列真/假条件问题，并根据数据库的响应推断数据。响应可能是网站内容的变化、错误消息或响应所花费的时间。基于布尔和基于时间的 SQL 注入技术属于此类别。

### SQL 注入的技术

关于利用 SQL 注入漏洞的技术，有五种常见技术。此外，这些技术有时可以组合使用（例如联合运算符和带外）：

- 联合运算符：当 SQL 注入漏洞发生在 SELECT 语句中时可以使用，使得将两个查询合并为单个结果或结果集成为可能。
- 布尔型：使用布尔条件来验证某些条件是真还是假。
- 基于错误：此技术强制数据库生成错误，为攻击者或测试人员提供信息，以便优化其注入。
- 带外：使用不同通道检索数据的技术（例如，建立 HTTP 连接将结果发送到 Web 服务器）。
- 时间延迟：使用数据库命令（例如 sleep）在条件查询中延迟响应。当攻击者无法从应用程序获得任何答案（结果、输出或错误）时，此技术非常有用。

### 额外：情景示例代码

SQL 注入漏洞自 20 世纪 90 年代末就已为人所知。尽管开发了旨在防止原始 SQL 查询未经检查即执行的强大框架，但 SQL 注入在许多应用程序中仍然是一个常见问题。这种持续性可归因于多种原因。开发人员可能误用或绕过框架的保护功能，或者漏洞可能源于未充分更新或加固的遗留代码。

传统上，许多开源软件包是使用 PHP 和 SQL（通常是 MySQL）的组合构建的。历史上许多最常被引用的 SQL 注入漏洞都是由于 PHP 对视图、逻辑和数据代码之间的插值持宽松态度而发生的。老派的 PHP 开发人员会将 SQL、HTML 和 PHP 交织到他们的 PHP 文件中——这种组织模式虽然受 PHP 支持，但被滥用，导致了大量易受攻击的 PHP 代码。

让我们看一个老派论坛软件的 PHP 代码块示例，它允许用户登录：

```php
<?php if ($_SERVER['REQUEST_METHOD'] != 'POST') {
  echo'
  <div class="row">
    <div class="small-12 columns">
      <form method="post" action="">
        <fieldset class="panel">
          <center>
            <h1>Sign In</h1><br>
          </center>
          <label>
            <input type="text" id="username" name="username"
                   placeholder="Username">
          </label>
          <label>
            <input type="password" id="password" name="password"
                   placeholder="Password">
          </label>
          <center>
            <input type="submit" class="button" value="Sign In">
          </center>
        </fieldset>
      </form>
    </div>
  </div>';
} else {
  // 用户已填写登录表单。
  // 从 config.php 拉取数据库信息
  $servername = getenv('IP');
  $username   = $mysqlUsername;
  $password   = $mysqlPassword;
  $database   = $mysqlDB;
  $dbport     = $mysqlPort;

  $database = new mysqli($servername, $username, $password, $database, $dbport);

  if ($database->connect_error) {
    echo "ERROR: Failed to connect to MySQL";
    die;
  }

  $sql = "SELECT userId, username, admin, moderator FROM users WHERE username = '"
         .$_POST['username']."' AND password = '".sha1($_POST['password'])."';";
  $result = mysqli_query($database, $sql);
}
```

如您在此登录代码中所见，PHP、SQL 和 HTML 全部混杂在一起。此外，SQL 查询是通过连接查询参数生成的，在生成查询字符串之前没有进行任何清理。

HTML、PHP 和 SQL 代码的交织确实使基于 PHP 的 Web 应用更容易受到 SQL 注入攻击。甚至一些最大的开源 PHP 应用，如 WordPress，过去也曾因此受害。

近年来，PHP 编码标准变得更加严格，该语言也实现了降低 SQL 注入发生几率的工具。
事实上，根据国家漏洞数据库的数据，注入漏洞已从 2010 年占所有漏洞的近 5% 下降到当今发现的所有漏洞的不到 1%。

从 PHP 中学到的安全教训在其他语言中得以延续，在当今的 Web 应用中更难找到 SQL 注入漏洞。然而，这仍然是可能的，并且在不使用安全编码最佳实践的应用中仍然很常见。

让我们考虑另一个简单的 Node.js/Express.js 服务器——这次是与 SQL 数据库通信的：

```javascript
const sql = require('mssql');

/*
 * 接收对 /users 的 POST 请求，请求体中带有 user_id 参数。
 *
 * 将执行 SQL 查找，尝试在数据库中找到与 `user_id` 参数中提供的 `id` 匹配的用户。
 *
 * 数据库查询的结果将在响应中返回。
 */
app.post('/users', function(req, res) {
  const user_id = req.body.user_id;

  /*
   * 连接到 SQL 数据库（服务端）。
   */
  await sql.connect('mssql://username:password@localhost/database');

  /*
   * 查询数据库，提供 HTTP 请求体中的 `user_id` 参数。
   */
  const result = await sql.query('SELECT * FROM users WHERE USER = ' + user_id);

  /*
   * 在 HTTP 响应中将 SQL 查询结果返回给请求者。
   */
  return res.json(result);
});
```

在此示例中，开发者使用直接字符串拼接将查询参数附加到 SQL 查询。这假设通过网络发送的查询参数未被篡改，但我们知道这不能作为合法性的可靠指标。

在合法的 `user_id` 情况下，此查询将向请求者返回一个用户对象。在更恶意的 `user_id` 字符串情况下，可能从数据库返回更多对象。让我们看一个例子：

```javascript
const user_id = '1=1'
```

啊，老式的真值判断。现在查询变成 `SELECT * FROM users WHERE USER = true`，这相当于“将所有用户对象返回给请求者”。

如果我们直接在 `user_id` 对象中开始一个新语句呢？我们将在以下代码中这样做：

```javascript
user_id = '123abc; DROP TABLE users;';
```

现在我们的查询如下：`SELECT * FROM users WHERE USER = 123abd; DROP TABLE users;`。换句话说，我们在原始查询之上附加了另一个查询。糟糕，现在我们需要重建用户表了。

一个更隐蔽的例子可能是这样的：

```javascript
const user_id = '123abc; UPDATE users SET credits = 10000 WHERE user = 123abd;'
```

现在，我们不是请求所有用户列表，也不是删除用户表，而是使用第二个查询来更新数据库中我们自己的用户账户——在这种情况下，给自己比应得的更多的应用内积分。
