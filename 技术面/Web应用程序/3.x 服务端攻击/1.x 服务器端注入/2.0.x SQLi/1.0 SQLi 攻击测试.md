## 测试目标

- 识别 SQL 注入点。
- 评估注入的严重性以及通过注入可达到的访问级别。

## 如何测试

**测试方法**
通过针对应用程序中的每个入口点进行系统化的测试来手动检测 SQL 注入。为此，你通常会提交：

- 单引号字符 `'`，并观察错误或其他异常。
- 一些 SQL 特定的语法，它们分别计算为入口点的原始值和不同的值，并观察应用程序响应中的系统差异。
- 布尔条件，如 `OR 1=1` 和 `OR 1=2`，并观察应用程序响应的差异。
- 旨在在 SQL 查询中执行时触发时间延迟的载荷，并观察响应时间的差异。
- 旨在在 SQL 查询中执行时触发带外网络交互的 OAST 载荷，并监控任何由此产生的交互。

**注入位置**
大多数 SQL 注入漏洞发生在 `SELECT` 查询的 `WHERE` 子句中。大多数有经验的测试人员都熟悉这种 SQL 注入。

然而，SQL 注入漏洞可能出现在查询中的任何位置，以及不同的查询类型中。SQL 注入出现的其他一些常见位置是：

- 在 `UPDATE` 语句中，位于更新的值或 `WHERE` 子句中。
- 在 `INSERT` 语句中，位于插入的值中。
- 在 `SELECT` 语句中，位于表名或列名中。
- 在 `SELECT` 语句中，位于 `ORDER BY` 子句中。

**注入示例**

在不同情况下存在许多 SQL 注入漏洞、攻击和技术。一些常见的 SQL 注入示例包括：

- [检索隐藏数据]，修改 SQL 查询以返回额外结果。
- [颠覆应用逻辑]，更改查询以干扰应用程序的逻辑。
- [UNION 攻击]，从不同的数据库表中检索数据。
- [盲 SQL 注入]，其中你控制的查询结果不会在应用程序的响应中返回。

**盲 SQL 注入利用方式**

- 更改查询的逻辑，以根据单个条件的真假在应用程序的响应中触发可检测的差异。这可能涉及向某些布尔逻辑中注入新条件，或有条件地触发错误（如除以零）。
- 有条件地在查询处理中触发时间延迟。这使你能够根据应用程序响应所需的时间来推断条件的真假。
- 使用 OAST 技术触发带外网络交互。这种技术非常强大，在其他技术无效的情况下也能起作用。通常，通过带外通道直接泄露数据。例如，将数据放入你控制的域的 DNS 查找中。

### 查明 SQL 注入漏洞

对于在应用程序解析过程中，确定的应用程序访问后端数据库的各种情形。应当在所有这些情形中探查SQL注入漏洞。

探测时了解应用程序何时与数据库服务器交互以访问某些数据。应用程序需要与数据库通信的典型示例包括：

- 认证表单：当使用 Web 表单进行认证时，用户凭据很可能与包含所有用户名和密码（或更准确地说，密码哈希）的数据库进行核对。
- 搜索引擎：用户提交的字符串可用于 SQL 查询，从数据库中提取所有相关记录。
- 电子商务网站：产品及其特性（价格、描述、可用性等）很可能存储在数据库中。

现在，测试人员列出所有其值可用于构造 SQL 查询的输入字段。实际上，提交给服务器的任何数据都能够以用户无法察觉的方式传送给数据库函数，并且可能得到不安全的处理。因此，需要检查所有这些数据，以查找SQL注入漏洞。这包括所有URL参数、cookie、POST数据项以及HTTP消息头。

在探查SQL注入漏洞时，一定要确保完全遍历任何可以提交专门设计的输入的多阶段过程。应用程序通常会从几个请求中收集一组数据，一旦收集到全部的数据，就将其保存在数据库中。这时，如果仅在每个请求中提交专门设计的数据并监控应用程序对那个请求的响应，就会遗漏许多SQL注入漏洞。

#### 注入字符串数据

如果SQL查询合并用户提交的数据，它会将这些数据包含在单引号中。为利用任何SQL注入漏洞，攻击者需要摆脱这些引号的束缚。

单引号 `'` 在 SQL 中用作字符串终止符，如果未被应用程序过滤，将导致不正确的查询。

渗透测试步骤:

1. 提交一个单引号作为目标查询的数据。观察是否会造成错误，或结果是否与原始结果不同。如果收到详细的错误消息，查询以了解此消息的含义。

2. 如果发现错误或其他异常行为，同时提交两个单引号 `''`，看会出现什么情况。数据库使用两个单引号作为转义序列，表示一个原义单引号（literal single quote），因此这个序列被解释成引用字符串中的数据，而不是结束字符串的终止符。如果这个输入导致错误或异常行为消失，则应用程序可能易于受SQL注入攻击。

3. 为进一步核实漏洞是否存在，可以使用SQL连接符建立一个等同于“良性”输入的字符串。如果应用程序以与处理对应“良性”输入相同的方式处理专门设计的输入，那么它很可能易于受到攻击。每种数据库使用的字符连接方法各不相同。

可以通过在特定的参数中提交SQL通配符 `%` 来确定应用程序是否正与后端数据库交互。例如，在搜索字段中提交这个通配符通常会返回大量结果，表明输入正被传送到SQL查询中。当然，这不一定表示应用程序易受攻击——只是应该深入探查以确定是否存在任何具体的漏洞。

使用单引号查找SQL注入漏洞时，应特别注意浏览器处理返回的页面时发生的任何JavaScript错误。应用程序经常在JavaScript中返回用户提交的输入，原义单引号将导致JavaScript解释器中出现错误。在响应中注入任意JavaScript将导致跨站点脚本攻击。


#### 注入数字数据

如果 SQL 查询合并用户提交的数字数据，应用程序仍然可能将它包含在单引号之中，作为字符串数据进行处理。因此，一定要执行前面描述的针对字符串数据的渗透测试步骤。

但是，许多时候，应用程序会将数字数据以数字格式直接传送到数据库中，并不把它放入单引号中。如果前面描述的测试方法无法检测到漏洞，还可以采取以下针对数字数据的特殊测试步骤。

渗透测试步骤:
1. 尝试输入一个结果等于原始数字值的简单数学表达式。例如，如果原始值为`2`，尝试提交`1+1`或`3–1`。如果应用程序做出相同的响应，则表示它易于受到攻击。

2. 如果证实被修改的数据会对应用程序的行为造成明显影响，则前面描述的测试方法最为可靠。例如，如果应用程序使用数字化 PageID 参数指定应返回什么内容，则用`1+1`代替`2`得到相同的结果明显表示存在 SQL 注入。但是，如果能够在数字化参数中插入任意输入，但应用程序的行为却没有发生改变，那么前面的检测方法就无法发现漏洞。

3. 如果第一个测试方法取得成功，利用更加复杂的、使用特殊 SQL 关键字和语法的表达式进一步获得与漏洞有关的证据。`ASCII()` 命令就是一个典型的示例，它返回被提交字符的数字化 ASCII 代码。例如，因为 A 的ASCII 值为65，在 SQL 中，`67-ASCII('A')` 等于2。

4. 如果单引号被过滤掉，那么前面的测试方法就没有作用。但是，这时可以利用这样一个事实：即在必要时，数据库会隐含地将数字数据转化为字符串数据。例如，因为字符1的 ASCII 值为49，在 SQL 中，`51-ASCII(1)` 等于2。
    - SQL 中，各种数字隐式转为字符串的功能或已失效（在线 SQL 环境中）

在探查应用程序是否存在SQL注入之类的缺陷时，常常会犯一个错误，即忘记某些字符在HTTP请求中具有特殊含义。如果你希望在攻击有效载荷中插入这些字符，必须谨慎地对它们进行URL编码，确保应用程序按预料的方式解释它们

一般来说，前面描述的步骤足以确定绝大多数的SQL注入漏洞，包括许多向浏览器返回无用结果或错误信息的漏洞。但是，在某些情况下，可能有必要使用更加高级的技巧，如时间延迟，来确定漏洞是否存在。

#### 注入查询结构

如果用户提交的数据被插入 SQL 查询结构，而不是查询中的数据项中，这时实施 SQL 注入攻击只需要直接应用有效的 SQL 语法，而不需要进行任何“转义”。

SQL 查询结构中最常见的注入点是 `ORDER BY` 子句。`ORDER BY` 关键字接受某个列名称或编号，并根据该列中的值对结果集进行排序。用户经常使用这种功能对浏览器中的表进行排序。

如果 `ORDER BY` 中的列名称由用户指定，就没有必要使用单引号，因为用户提交的数据已经直接修改了SQL查询的结构。

在极少数情况下，用户提交的输入可能会指定 `WHERE` 子句中的列名称。由于这些输入也没有包含在单引号中，因此会导致与前面介绍的漏洞类似的问题。最终，有大量应用程序允许用户指定排序关键字（ASC 或 DESC），可能认为这并不会导致 SQL 注入攻击。

在列名称中查找 SQL 注入漏洞可能会相当困难。如果提交一个并非有效列名称的值，查询将导致错误。这意味着，无论攻击者提交路径遍历字符串、单引号、双引号或任何其他任意字符串，应用程序都会返回相同的响应。因此，采用常用的自动模糊测试和手动测试技巧往往会遗漏某些漏洞。如果提交用于探查各种漏洞的标准测试字符串全部导致相同的响应，这本身并不表示出现任何错误。

传统的SQL注入防御措施并不能防范用户提交的列名称。使用预处理的语句或转义单引号也不能阻止这类 SQL 注入。

渗透测试步骤:
1. 记下任何可能控制应用程序返回的结果的顺序或其中的字段类型的参数。

2. 提供一系列在参数值中提交数字值的请求，从数字1开始，然后逐个请求递增。

- 如果更改输入中的数字会影响结果的顺序，则说明输入可能被插入到`ORDER BY` 子句中。在 SQL 中，`ORDER BY 1` 将依据第一个列进行排序。然后，将这个数字增加到2将更改数据的显示顺序，以依据第二个列进行排序。如果提交的数字大于结果集中的列数，查询将会失败。在这种情况下，通过使用以下字符串，检查是否可以颠倒结果的顺序，从而确认是否可以注入其他 SQL：

    - `1 ASC -- `
    - `1 DESC -- `

- 如果提交数字1生成一组结果，其中一个列的每一行都包含一个1，则说明输入可能被插入到查询返回的列的名称中。

在 `ORDER BY` 子句中实施SQL注入与其他注入情形有很大区别。此时，数据库不会接受查询中的 `UNION`、`WHERE`、`OR`或`AND`关键字。通常，实施注入攻击需要攻击者指定一个嵌套查询来替代参数，如用条件异常语句 `select 1 where <<condition>> or 1/0=0` 替代列名称进行推断。对于支持批量查询的数据库（如MS-SQL），这可能是最有效的注入攻击方法。

#### 其他尝试

分号 `;` 用于结束 SQL 语句，如果未被过滤，也可能生成错误。易受攻击字段的输出可能类似于以下（在此示例中为 Microsoft SQL Server）：

```log
Microsoft OLE DB Provider for ODBC Drivers error '80040e14'
[Microsoft][ODBC SQL Server Driver][SQL Server]Unclosed quotation mark before the
character string ''.
/target/target.asp, line 113
```

注释分隔符（`--` 或 `/* */` 等）以及其他 SQL 关键字（如 `AND` 和 `OR`）也可用于尝试修改查询。一种非常简单但有时仍然有效的技术是在期望数字的地方插入字符串，因为可能会生成如下错误：

```log
Microsoft OLE DB Provider for ODBC Drivers error '80040e07'
[Microsoft][ODBC SQL Server Driver][SQL Server]Syntax error converting the
varchar value 'test' to a column of data type int.
/target/target.asp, line 113
```

监视 Web 服务器的所有响应，并查看 HTML/JavaScript 源代码。有时错误存在于其中，但由于某种原因（例如 JavaScript 错误、HTML 注释等）未呈现给用户。

在任何情况下，逐一测试每个字段非常重要：只有一个变量变化，而所有其他变量保持不变，以便精确了解哪些参数易受攻击，哪些不易受攻击。

### 标准 SQL 注入示例

通过 SQL 注入可以实现的影响取决于用户输入在 SQL 查询中的位置以及权限，基于此，你可能能够改变逻辑，例如绕过身份验证、检索记录等。

**注意**：虽然 SQL 注入可能发生在 SQL 查询的不同部分，但通常出现在 WHERE 子句中，这是操纵查询逻辑和影响数据检索或修改的关键区域。

#### 检索隐藏内容，返回所有记录

假设一个购物应用程序按不同类别显示产品。当用户点击 **Gifts** 类别时，他们的浏览器请求 URL：

```
https://insecure-website.com/products?category=Gifts
```

这导致应用程序执行 SQL 查询以从数据库中检索相关产品的详细信息：

```sql
SELECT * FROM products WHERE category = 'Gifts' AND released = 1
```

此 SQL 查询要求数据库返回：

- 所有详细信息（`*`）
- 来自 `products` 表
- 其中 `category` 是 `Gifts`
- 且 `released` 是 `1`。

限制条件 `released = 1` 用于隐藏未发布的产品。我们可以假设对于未发布的产品，`released = 0`。

应用程序没有实现任何针对 SQL 注入攻击的防御措施。这意味着攻击者可以构造如下攻击，例如：

```
https://insecure-website.com/products?category=Gifts'--
```

这导致 SQL 查询：

```sql
SELECT * FROM products WHERE category = 'Gifts'--' AND released = 1
```

关键要注意，`--` 是 SQL 中的注释指示符。这意味着查询的其余部分被解释为注释，从而有效地将其移除。在此示例中，这意味着查询不再包含 `AND released = 1`。因此，所有产品都被显示，包括尚未发布的产品。

使用类似的攻击使应用程序显示任何类别中的所有产品，包括他们不知道的类别：

```
https://insecure-website.com/products?category=Gifts'+OR+1=1--
```

这导致 SQL 查询：

```sql
SELECT * FROM products WHERE category = 'Gifts' OR 1=1--' AND released = 1
```

修改后的查询返回所有 `category` 为 `Gifts` 或 `1` 等于 `1` 的项目。由于 `1=1` 始终为真，查询返回所有项目。

> **警告**：在向 SQL 查询注入条件 `OR 1=1` 时要小心。即使在你注入的上下文中看似无害，但应用程序通常会在多个不同的查询中使用来自单个请求的数据。例如，如果你的条件到达了 `UPDATE` 或 `DELETE` 语句，可能导致意外的数据丢失。

在MySQL中，需在双连字符后加入一个空格，或者使用 `#` 符号指定注释。

#### 颠覆应用逻辑，绕过身份验证

让我们探讨如何使用 SQL 注入绕过身份验证，假设一个应用程序允许用户使用用户名和密码登录：

```sql
SELECT * FROM users WHERE username = '$username' AND password = '$password'
```

如果查询返回一个值，则表示数据库中存在具有该组凭据的用户，然后允许用户登录系统，否则访问被拒绝。输入字段的值通常通过 Web 表单从用户获取。

在这种情况下，攻击者可以在不需要密码的情况下以任何用户身份登录。他们可以使用 SQL 注释序列 `--` 来从查询的 `WHERE` 子句中移除密码检查。例如，提交用户名 `administrator'--` 和空密码会导致以下查询：

```sql
SELECT * FROM users WHERE username = 'administrator'--' AND password = ''
```

此查询返回 `username` 为 `administrator` 的用户，并使攻击者成功以该用户身份登录。

再考虑提供 payload 设置 `$username` 参数为 `' OR 1 = 1 --`，输入将查询转换为：

```sql
SELECT * FROM users WHERE username = '' OR 1 = 1 -- ' AND password = 'pass';
```

由于 `OR 1 = 1` 部分始终为真，实际上将 WHERE 子句转换为真语句，从而匹配 users 表中的所有行。这样，系统在不知道用户名和密码的情况下验证了用户身份。

> 在某些系统中，用户表的第一行可能是管理员用户。在某些情况下，这可能就是返回的个人资料。

#### 前缀/后缀

在某些情况下，查询的构造方式要求在注入我们自己的命令之前添加额外的字符来关闭现有的输入参数。这称为前缀。类似地，后缀可用于确保 SQL 查询正确关闭且不会导致错误。为了解释此概念，让我们看一下易受攻击的代码：

```sql
SELECT * FROM Users WHERE ((Username='$username') AND (Password=MD5('$password')))
```

在这种情况下，存在两个问题:
1. 一个由于括号的使用
2. 另一个由于 MD5 哈希函数的使用。

首先，我们解决括号的问题。这只需添加一些右括号，直到获得正确的查询。为了解决第二个问题，我们尝试规避第二个条件。我们向查询添加一个最终符号 `--`，表示注释开始。这样，该符号之后的所有内容都被视为注释。因此，我们将用作用户名和密码的值为：

`$username = ' OR 1 = 1))--`

`$password = foo`

这样，我们将得到以下查询：

```sql
SELECT * FROM Users WHERE ((Username='' OR 1 = 1))--') AND (Password=MD5('$password')))
```

这可能会返回一些值。有时，认证代码会验证返回的记录/结果数量是否恰好等于 1。在前面的示例中，这种情况可能难以实现（在数据库中每个用户只有一个值）。为了解决这个问题，只需插入一个 SQL 命令，强制返回结果的数量为一个（返回一条记录）。为达到此目的，我们使用运算符 `LIMIT <num>`，其中 `<num>` 是我们希望返回的结果/记录数量。关于前面的示例，用户名和密码字段的值将修改如下：

`$username = ' or 1 = 1)) LIMIT 1--`

`$password = foo`


#### 通配符注入

大多数 SQL 方言支持单字符通配符（通常是 "`?`" 或 "`_`"）和多字符通配符（通常是 "`%`" 或 "`*`"），可以在使用 `LIKE` 运算符的查询中使用。即使使用了适当的控制措施（如参数或预处理语句）来防止 SQL 注入攻击，也可能将通配符注入查询中。

例如，如果 Web 应用程序允许用户在结账过程中输入折扣代码，并使用如下查询检查数据库中是否存在该代码

```sql
SELECT * FROM discount_codes WHERE code LIKE ':code'
``` 

则输入 `%`（将插入到 `:code` 参数的位置）将匹配所有折扣代码。

此技术也可用于通过越来越具体的查询（如 `a%`、`b%`、`ba%` 等）确定确切的折扣代码。

### 注入不同的语句类型

SQL语言中包含许多可能出现在语句开头的动词。由于SELECT是最常用的动词，因此绝大多数的SQL注入漏洞出现在这种语句中。任何类型的语句都可能存在SQL缺陷

根据使用的应用程序功能对后端 SQL 语句进行猜测

#### SELECT 语句

SELECT语句被用于从数据库中获取信息。它们常用于应用程序响应用户操作而返回信息的功能中，如浏览一个产品目录、查看一名用户的资料或者进行一项搜索。根据数据库中的数据核对用户提交的信息的登录功能也经常使用这种语句。

SQL注入攻击的进入点（entry point）通常是查询中的WHERE子句，它将用户提交的数据传送给数据库，以控制查询结果的范围。因为WHERE子句一般在SELECT语句的最后，攻击者就可以使用注释符号将查询截短到其输入的结束位置，而不会使整个查询的语法失效。

SQL注入漏洞偶尔也会影响SELECT查询的其他部分，如ORDER BY子句或表和列名称。

考虑以下 SQL 查询：

```sql
SELECT * FROM products WHERE id_product=$id_product
```

同时考虑执行上述查询的脚本请求：

`https://www.example.com/product.php?id=10`

当测试人员尝试一个有效值（例如本例中的 10）时，应用程序将返回产品的描述。在此场景中测试应用程序是否存在漏洞的好方法是使用逻辑运算，使用 AND 和 OR 运算符。

考虑请求：

`https://www.example.com/product.php?id=10 AND 1=2`

```sql
SELECT * FROM products WHERE id_product=10 AND 1=2
```

在这种情况下，应用程序可能会返回一些消息，告诉我们没有可用内容或返回空白页面。然后测试人员可以发送一个真语句，并检查是否有有效结果：

`https://www.example.com/product.php?id=10 AND 1=1`

#### 各种语句中

SQL 注入不仅限于 `SELECT` 语句。攻击者还可以将代码注入 `UPDATE`（用于更新记录）、`DELETE`（用于删除现有记录）和 `INSERT`（用于在表中创建新条目）等语句中。例如，假设这是目标网站上用于更新用户密码的 HTTP POST 请求：

```http
POST /change_password
Host: example.com

new_password=password12345
```

网站会使用你的新密码和当前登录用户的 ID 形成一条 `UPDATE` 查询。此查询将更新 `Users` 表中 `Id` 字段等于 2 的行，并将其密码设置为 `password12345`：

```sql
UPDATE Users
SET Password='password12345'
WHERE Id = 2;
```

在这种情况下，攻击者可以控制语句的 `SET` 子句，该子句用于指定表中哪些行应被更新。攻击者可以构造如下 POST 请求：

```http
POST /change_password
Host: example.com

new_password="password12345';--"
```

此请求生成以下 SQL 查询：

```sql
UPDATE Users
SET Password='password12345';-- WHERE Id = 2;
```

指定更新条件的 `WHERE` 子句在此查询中被注释掉了。数据库将更新表中的所有行，将 `Users` 表中的所有密码都改为 `password12345`。攻击者现在可以使用该密码以任何人的身份登录。

##### INSERT语句

INSERT语句用于在表中建立一个新的数据行。应用程序通常使用这种语句添加一条新的审计日志、创建一个新用户账户或生成一个新订单。

例如，如果一个应用程序允许用户自我注册，指定他们自己的用户名和密码，就可以使用语句将用户资料插入表中。

如果 username 或 password 字段存在 SQL 注入漏洞，那么攻击者就可以在表中插入任何数据。然而，要想这样做，攻击者就必须确保 VALUES 子句的其他部分正常运行。特别是其中数据项的个数与类型必须正确。

假如某字段用来决定账户权限，那么攻击者就可以利用它创建一个管理用户。

有时，攻击者完全盲目地注入一个INSERT语句也能够从应用程序中提取出字符串数据。例如，攻击者可以拦截数据库的版本字符串，并把它插入自己用户资料的一个字段中；正常情况下，浏览器将显示数据库的版本信息。

当设法注入一个INSERT语句时，可能无法提前知道需要提交多少个参数或参数的类型。可以通过在子句中持续增加一个新的字段，直到应用程序创建了确实想要的用户账户，从而解决上述问题。

由于大多数数据库都会隐式地将一个整数转换为一个字符串，可以在每个位置都使用一个整数。

确定注入点之后的正确字段数后，在MS-SQL中，测试员可以任意添加另外一个查询。

在Oracle中，则可以在insert查询内发布subselect查询。该subselect查询可能导致主查询成功或失败。

##### UPDATE语句

UPDATE语句用于修改表中的一行或几行数据。它们经常用在用户修改已有数据值的功能中，例如，更新联系信息、修改密码或更改订单数量。

典型UPDATE语句的运行机制与INSERT语句类似，只是UPDATE语句中通常包含一个WHERE子句，告诉数据库更新表中哪些行的数据。例如，当用户修改密码时，查询首先核实用户的现有密码是否正确，如果密码无误，就用新的值更新它。如果这项功能存在SQL注入漏洞，那么攻击者就能避开现有密码检查，更新管理员的密码

##### DELETE语句

DELETE语句用于删除表中的一行或几行数据，例如用户从他们的购物篮中删除一件商品或从个人资料中删除一个交货地址。

与UPDATE语句一样，DELETE语句通常使用WHERE子句告诉数据库更新表中哪些行的数据，并很可能在这个子句中并入用户提交的数据。

#### 堆叠查询

根据 Web 应用程序使用的 API 和 DBMS（例如 PHP + PostgreSQL、ASP + SQL SERVER），可能可以在一次调用中执行多个查询。

考虑以下 SQL 查询：

```sql
SELECT * FROM products WHERE id_product=$id_product
```

利用上述场景的一种方式是：

`https://www.example.com/product.php?id=10; INSERT INTO users (…)`

这样，可以连续执行多个查询，且独立于第一个查询。

### 不同注入点的 SQL 注入

在之前的示例中，使用查询字符串来注入恶意的 SQL 载荷。然而，任何被应用程序处理为 SQL 查询的可控输入均可执行 SQL 注入攻击。例如，某些网站以 JSON 或 XML 格式接收输入，并使用它来查询数据库。

这些不同的格式可能提供不同的方式来[混淆攻击]否则这些攻击可能被 WAF 和其他防御机制阻止。弱实现通常会在请求中查找常见的 SQL 注入关键字，因此通过编码或转义被禁止关键字中的字符来绕过这些过滤器。例如，以下基于 XML 的 SQL 注入使用 XML 转义序列对 `SELECT` 中的 `S` 字符进行编码：

```xml
<stockCheck>
    <productId>123</productId>
    <storeId>999 &#x53;ELECT * FROM information_schema.tables</storeId>
</stockCheck>
```

这在传递给 SQL 解释器之前会在服务端被解码。
