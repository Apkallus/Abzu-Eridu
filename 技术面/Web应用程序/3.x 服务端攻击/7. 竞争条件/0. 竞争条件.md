# 竞争条件

竞争条件是一种常见漏洞，与业务逻辑缺陷密切相关。当网站并发处理请求但缺乏充分防护时，就可能出现竞争条件。这会导致多个不同线程同时与同一数据交互，产生“冲突”，从而引发应用程序的非预期行为。竞争条件攻击利用精心计时的请求，故意制造冲突，并以此恶意利用这些非预期行为。

![竞争条件——重复兑换单次使用礼品卡](https://portswigger.net/web-security/race-conditions/images/race-conditions-main-graphic.png)

冲突可能发生的时间段称为“竞争窗口”。例如，这可能是在两次与数据库交互之间的几分之一秒内。

与其他逻辑缺陷一样，竞争条件的影响在很大程度上取决于应用程序及其发生的具体功能。

在本节中，你将学习如何识别和利用不同类型的竞争条件。我们将教你如何利用 Burp Suite 的内置工具来克服传统攻击的挑战，并提供一套经过实践检验的方法论，帮助你检测隐藏在多步流程中的新型竞争条件。这些内容远超你可能已熟悉的限额超限攻击。

## 限额超限竞争条件

最广为人知的竞争条件类型允许你突破应用程序业务逻辑施加的某种限制。

例如，考虑一个在线商店，它允许你在结账时输入促销码以获得一次性折扣。为了应用此折扣，应用程序可能执行以下高级步骤：

1. 检查你是否尚未使用过此代码。
2. 将折扣应用于订单总额。
3. 更新数据库记录，反映你已使用此代码。

如果你稍后尝试重复使用此代码，流程开始时执行的初始检查应阻止你这样做：

![折扣码验证流程](https://portswigger.net/web-security/race-conditions/images/race-conditions-discount-code-normal.png)

现在考虑一下，如果从未使用过此折扣码的用户几乎同时尝试应用两次，会发生什么：

![折扣码验证中的竞争条件](https://portswigger.net/web-security/race-conditions/images/race-conditions-discount-code-race.png)

如你所见，应用程序会经过一个临时子状态；也就是说，它在请求处理完成之前会进入并再次退出的状态。在这种情况下，子状态从服务器开始处理第一个请求时开始，到更新数据库以表明你已使用此代码时结束。这引入了一个小的竞争窗口，在此期间根据需要多次重复领取折扣。

此类攻击有许多变体，包括：

- 多次兑换礼品卡
- 多次评价产品
- 超出账户余额提取或转账现金
- 重复使用单个 CAPTCHA 解决方案
- 绕过防暴力破解速率限制

限额超限是所谓的“检查时间与使用时间”（TOCTOU）缺陷的一种子类型。在本主题的后续部分，我们将介绍一些不属于这两类别的竞争条件漏洞示例。

高级步骤
- 测试次数限制（优惠券应用次数、账户登录次数）
    - 记录普通与超限的响应状态作为触点（成功、失败消息）
- 测试限制类型（账户、会话、IP）
- 测试竞争超限请求
    - 若存在超过限制数量的 hit，则可能存在竞争条件攻击（如，应用程序限制3次登录尝试，预期收到3次登录失败消息，其余为锁定信息。但最终收到多于3次登录失败消息）

### 使用 Burp Repeater 检测和利用限额超限竞争条件

检测和利用限额超限竞争条件的过程相对简单。从高层次上讲，你只需：

1. 识别一个具有某种安全影响或其他有用目的的单次使用或速率受限端点。
2. 快速连续向该端点发出多个请求，看看是否能超限该限制。

主要挑战在于对请求进行计时，使至少两个竞争窗口对齐，从而产生冲突。这个窗口通常只有几毫秒，甚至可能更短。

即使你同时发送所有请求，实际上也存在各种不可控且不可预测的外部因素，影响服务器处理每个请求的时间和顺序。

![对齐竞争窗口](https://portswigger.net/web-security/race-conditions/images/race-conditions-basic.png)

[Burp Suite 2023.9](https://portswigger.net/burp/releases#professional) 为 Burp Repeater 增加了强大的新功能，使你能够轻松地并行发送一组请求，从而大大减少其中一个因素（即网络抖动）的影响。Burp 会根据服务器支持的 HTTP 版本自动调整所使用的技术：

- 对于 HTTP/1，使用经典的**最后字节同步**技术。
- 对于 HTTP/2，使用**单数据包攻击**技术，该技术由 PortSwigger Research 在 Black Hat USA 2023 上首次演示。

单数据包攻击通过使用单个 TCP 数据包同时完成 20-30 个请求，从而完全消除网络抖动带来的干扰。

![单数据包攻击](https://portswigger.net/web-security/race-conditions/images/race-conditions-single-packet-attack.png)

尽管通常只需两个请求即可触发漏洞利用，但像这样发送大量请求有助于减轻内部延迟（也称服务端抖动）。这在初始发现阶段尤其有用。我们将在后面更详细地介绍这种方法论。

### 使用 Turbo Intruder 检测和利用限额超限竞争条件

除了在 Burp Repeater 中提供对单数据包攻击的原生支持外，我们还增强了 Turbo Intruder 扩展以支持该技术。从 [BApp Store](https://portswigger.net/bappstore/9abaa233088242e8be252cd4ff534988) 下载最新版本。

Turbo Intruder 需要一定的 Python 熟练度，但适用于更复杂的攻击，例如需要多次重试、错开请求时间或极大量请求的攻击。

要在 Turbo Intruder 中使用单数据包攻击：

1. 确保目标支持 HTTP/2。单数据包攻击与 HTTP/1 不兼容。
2. 为请求引擎设置 `engine=Engine.BURP2` 和 `concurrentConnections=1` 配置选项。
3. 在排队请求时，通过为 `engine.queue()` 方法的 `gate` 参数指定名称，将它们分配到指定的门（gate）中分组。
4. 要发送给定组中的所有请求，使用 `engine.openGate()` 方法打开相应的门。

```python
def queueRequests(target, wordlists):
    engine = RequestEngine(endpoint=target.endpoint,
                            concurrentConnections=1,
                            engine=Engine.BURP2
                            )
    
    # 在门 '1' 中排队 20 个请求
    for i in range(20):
        engine.queue(target.req, gate='1')
    
    # 并行发送门 '1' 中的所有请求
    engine.openGate('1')
```

更多详情，请参阅 Turbo Intruder 默认示例目录中提供的 `race-single-packet-attack.py` 模板。

## 隐藏的多步序列

在实践中，单个请求可能在幕后启动整个多步序列，使应用程序经过多个隐藏状态，并在请求处理完成前进入并再次退出。我们将这些称为“子状态”。

如果你能识别出一个或多个与同一数据交互的 HTTP 请求，你就可以利用这些子状态，暴露出多步工作流中常见的逻辑缺陷的时间敏感性变体。这使得竞争条件漏洞利用远远超出了限额超限的范围。

例如，你可能熟悉有缺陷的多因素身份验证（MFA）工作流，它允许你使用已知凭据执行登录的第一部分，然后通过强制浏览直接进入应用程序，从而完全绕过 MFA。

以下伪代码演示了网站如何容易受到这种攻击的竞争变体影响：

```python
session['userid'] = user.userid
if user.mfa_enabled:
    session['enforce_mfa'] = True
    # 生成并发送 MFA 代码给用户
    # 将浏览器重定向到 MFA 代码输入表单
```

如你所见，这实际上是在单个请求范围内的多步序列。最重要的是，它会经过一个子状态，在该子状态下，用户暂时拥有有效的登录会话，但 MFA 尚未强制执行。攻击者可以通过同时发送登录请求和对敏感、已认证端点的请求来利用这一点。

稍后我们将看一些隐藏多步序列的更多示例，在我们的交互式实验室中练习利用它们。然而，由于这些漏洞与特定应用程序紧密相关，首先了解更广泛的方法论至关重要，这样你才能有效地在实验室和实际环境中识别它们。

## 方法论

为了检测和利用隐藏的多步序列，我们推荐以下方法论，该方法论摘自 PortSwigger Research 的白皮书 [《粉碎状态机：Web 竞争条件的真正潜力》](https://portswigger.net/research/smashing-the-state-machine)。

![预测、探测、证明](https://portswigger.net/web-security/race-conditions/images/race-conditions-methodology.png)

### 1 - 预测潜在冲突

测试每个端点是不切实际的。在正常映射目标站点后，通过问自己以下问题来减少需要测试的端点数量：

- **该端点是否涉及安全关键功能？** 许多端点不涉及关键功能，因此不值得测试。
- **是否存在冲突可能性？** 要成功发生冲突，通常需要两个或更多在同一记录上触发操作的请求。例如，考虑以下密码重置实现的变体：

![冲突可能性](https://portswigger.net/web-security/race-conditions/images/race-conditions-collision-potential.png)

在第一个示例中，为两个不同用户请求并行密码重置不太可能导致冲突，因为它会导致更改两个不同的记录。然而，第二种实现允许你通过为两个不同用户的请求来编辑同一记录。

### 2 - 探测线索

要识别线索，首先需要基准测试端点在正常条件下的行为。在 Burp Repeater 中通过将所有请求分组并使用 **按顺序发送组（单独连接）** 选项来完成此操作。更多信息，请参阅[按顺序发送请求](https://portswigger.net/burp/documentation/desktop/tools/repeater/send-group#sending-requests-in-sequence)。

接下来，使用单数据包攻击（或不支持 HTTP/2 时使用最后字节同步）一次性发送同一组请求，以最小化网络抖动。在 Burp Repeater 中通过选择 **并行发送组** 选项来完成此操作。更多信息，请参阅[并行发送请求](https://portswigger.net/burp/documentation/desktop/tools/repeater/send-group#sending-requests-in-parallel)。或者，使用 Turbo Intruder 扩展，该扩展可从 [BApp Store](https://portswigger.net/bappstore/9abaa233088242e8be252cd4ff534988) 获取。

任何微小的差异都可能是线索。只需寻找与基准测试中观察到的任何偏差。这包括一个或多个响应的变化，但不要忘记二阶效应，例如不同的电子邮件内容或之后应用程序行为的可见变化。

> **注意**
> **专业版** 要快速轻松地测试竞争条件漏洞，使用 [触发竞争条件](https://github.com/PortSwigger/bambdas/blob/main/CustomAction/ProbeForRaceCondition.bambda) 自定义操作。此操作只需单击即可发送并行请求，无需在 Repeater 中手动创建和分组选项卡。
>
> 有关如何使用自定义操作的更多信息，请参阅[自定义操作](https://portswigger.net/burp/documentation/desktop/tools/repeater/http-messages/custom-actions)。

### 3 - 证明概念

尝试理解发生了什么，移除多余的请求，并确保你仍然可以复现效果。

高级竞争条件可能导致异常且独特的原语，因此通往最大影响路径并不总是显而易见的。将每个竞争条件视为结构性弱点而非孤立漏洞可能更有帮助。

## 多端点竞争条件

这类竞争条件中最直观的形式可能是涉及同时向多个端点发送请求的情况。

想想在线商店中经典的逻辑缺陷：你将商品添加到购物车，付款，然后再添加更多商品，然后强制浏览到订单确认页面。

> **注意**
> 如果你不熟悉这种利用方式，请查看我们业务逻辑漏洞主题中的工作流验证不足实验室。

当支付验证和订单确认在单个请求处理期间执行时，就会出现此漏洞的变体。订单状态的状态机可能如下所示：

![购物车调整逻辑缺陷的竞争变体](https://portswigger.net/web-security/race-conditions/images/race-conditions-basket-adjustment-race.png)

在这种情况下，在支付验证和订单最终确认之间的竞争窗口内，向购物车中添加更多商品。

### 对齐多端点竞争窗口

在测试多端点竞争条件时，即使使用单数据包技术同时发送所有请求，也可能遇到对齐每个请求竞争窗口的问题。

![对齐多端点竞争窗口](https://portswigger.net/web-security/race-conditions/images/race-conditions-multi-endpoint.png)

这个常见问题主要由以下两个因素引起：

- **网络架构引入的延迟** - 例如，当前端服务器与后端建立新连接时可能存在延迟。所使用的协议也会产生重大影响。
- **端点特定处理引入的延迟** - 不同端点的处理时间固有差异，有时差异很大，具体取决于它们触发的操作。

幸运的是，这两个问题都有潜在的变通方法。

#### 连接预热 —— 测试延迟来源是否为网络延迟

后端网络连接延迟通常不会干扰竞争条件攻击，因为它们通常会同等延迟并行请求，因此请求仍保持同步。

必须能够将这些延迟与端点特定因素造成的延迟区分开来。一种方法是通过一个或多个无关紧要的请求来“预热”连接，看看这是否能平滑剩余的处理时间。在 Burp Repeater 中，尝试在选项卡组开头添加一个对首页的 `GET` 请求，然后使用 **按顺序发送组（单连接）** 选项。

如果第一个请求仍有较长的处理时间，但其余请求现在在较短的窗口内处理，则可以忽略明显的延迟并继续并行测试。

网络延迟测试
- 确认并行单包延迟
    - 发送多端点请求到重复器，设置为并行单包组，测试几次延迟
- 确认顺序单连接延迟
    - 添加无关请求到并行单包组的第一项，修改设置为顺序单连接，测试几次延迟
- 观察：若顺序单连接的后续请求延迟降低，且时间接近
- 分析：则此处的延迟为网络延迟，可继续进行并行单包攻击

如果即使在单数据包技术下，某个端点的响应时间仍然不一致，则表明后端延迟正在干扰你的攻击。尝试使用 Turbo Intruder 先发送一些连接预热请求，然后发送主要攻击请求来解决这个问题。

#### 滥用速率或资源限制

如果连接预热没有效果，则存在多种解决方案。

使用 Turbo Intruder，引入一个较短的客户端延迟。但是，由于这会将你的实际攻击请求分散到多个 TCP 数据包中，你将无法使用单数据包攻击技术。因此，在高抖动目标上，无论你设置什么延迟，攻击都不太可能可靠工作。

![在请求之间引入客户端延迟](https://portswigger.net/web-security/race-conditions/images/race-conditions-client-side-delay.png)

相反，通过滥用常见安全功能来解决此问题。

Web 服务器通常在发送过多过快请求时会延迟处理请求。通过发送大量虚拟请求以故意触发速率或资源限制，你或许能够引起适当的服务端延迟。这使得单数据包攻击即使在需要延迟执行时也能有效。

![滥用速率或资源限制以引入服务端延迟](https://portswigger.net/web-security/race-conditions/images/race-conditions-abusing-rate-or-resource-limits.png)

## 单端点竞争条件

向单个端点并行发送具有不同值的请求有时会触发强大的竞争条件。

考虑一个密码重置机制，它将用户 ID 和重置令牌存储在用户会话中。

在这种情况下，从同一会话但使用两个不同用户名同时发送两个密码重置请求，可能会导致以下冲突：

![密码重置机制中的冲突](https://portswigger.net/web-security/race-conditions/images/race-conditions-password-reset-collision.png)

注意所有操作完成时的最终状态：

- `session['reset-user'] = victim`
- `session['reset-token'] = 1234`

会话现在包含受害者的用户 ID，但有效的重置令牌却发送给了攻击者。

> **注意**
> 要使此攻击成功，每个进程执行的不同操作必须以恰到好处的顺序发生。要达到预期结果，可能需要多次尝试或一点运气。

电子邮件地址确认或任何基于电子邮件的操作通常是单端点竞争条件的好目标。电子邮件通常在服务器向客户端发出 HTTP 响应后在后台线程中发送，这使得竞争条件更可能发生。

分析竞争条件
- 任何时刻仅保持1个有效邮件修改令牌（潜在线程不安全容器），而不是每个请求设置独立令牌（独立容器）
- 提交修改请求 x 发送邮件，尝试插入其他邮件的修改请求：
    1. 邮件组件创建与目标邮件地址关联的修改密码令牌
    2. 邮件组件发送令牌到目标邮件地址
        - 若组件读取线程不安全容器，则可能发送步骤1的邮件地址令牌到步骤2被修改后的邮件地址。

## 基于会话的锁定机制

某些框架尝试通过使用某种形式的请求锁定来防止意外数据损坏。例如，PHP 的原生会话处理模块每次仅处理每个会话的一个请求。

识别这种行为至关重要，否则它可能会掩盖本可轻易利用的漏洞。如果你注意到所有请求都是按顺序处理的，请尝试使用不同的会话令牌发送每个请求。即，锁定基于会话，不同会话无锁定

## 部分构建竞争条件 —— 未完全创建或关联对象时的初始状态

许多应用程序分多步创建对象，这可能会引入一个临时的中间状态，在该状态下该对象是可被利用的。

例如，在注册新用户时，应用程序可能会使用两个独立的 SQL 语句在数据库中创建用户并设置其 API 密钥。这会留下一个短暂的窗口，此时用户已存在但 API 密钥未初始化。

这种行为为漏洞利用铺平了道路，注入一个输入值，使其返回与未初始化的数据库值（如空字符串或 JSON 中的 `null`）匹配的内容，并在安全控制中进行比较。

框架通常允许你使用非标准语法传入数组和其他非字符串数据结构。例如，在 PHP 中：

- `param[]=foo` 等价于 `param = ['foo']`
- `param[]=foo&param[]=bar` 等价于 `param = ['foo', 'bar']`
- `param[]` 等价于 `param = []`

Ruby on Rails 允许你通过提供一个有键但无值的查询或 `POST` 参数来实现类似功能。换句话说，`param[key]` 会产生以下服务端对象：

```ruby
params = {"param"=>{"key"=>nil}}
```

在上面的示例中，这意味着在竞争窗口期间，像这样发出已认证的 API 请求：

```http
GET /api/user/info?user=victim&api-key[]= HTTP/2
Host: vulnerable-website.com
```

> **注意**
> 也可能使用密码而非 API 密钥导致类似的部分构建冲突。但是，由于密码是哈希存储的，这意味着你需要注入一个值，使哈希摘要与未初始化值匹配。

## 时间敏感型攻击

有时你可能找不到竞争条件，但精确计时请求的技术仍然可以揭示其他漏洞的存在。

一个例子是使用高分辨率时间戳代替加密安全随机字符串来生成安全令牌。

考虑一个仅使用时间戳随机化的密码重置令牌。在这种情况下，可能为两个不同用户触发两次密码重置，并且两者使用相同的令牌。你只需对请求进行计时，使它们生成相同的时间戳即可。

步骤
- 使用两组会话令牌/csrf令牌/邮箱地址，并发发送重置请求
- 检查是否存在相同的重置邮箱令牌值

## 如何防范竞争条件漏洞

当单个请求可以使应用程序经历不可见的子状态时，理解和预测其行为极其困难，这使得防御变得不切实际。为了正确保护应用程序，我们建议通过应用以下策略来消除所有敏感端点中的子状态：

- 避免混合来自不同存储位置的数据。
- 通过使用数据存储的并发功能，确保敏感端点以原子方式进行状态更改。例如，使用单个数据库事务检查支付是否与购物车价值匹配，并确认订单。
- 作为纵深防御措施，利用数据存储的完整性和一致性功能，如列唯一性约束。
- 不要试图使用一个数据存储层来保护另一个。例如，会话不适合防止对数据库的限额超限攻击。
- 确保你的会话处理框架保持会话内部一致性。逐个更新会话变量而不是批量更新可能是一个诱人的优化，但这极其危险。ORM 也是如此；通过隐藏事务等概念，它们完全承担了相应责任。
- 在某些架构中，完全避免服务端状态可能是合适的。相反，使用加密将状态推送到客户端，例如使用 JWT。请注意，这有其自身风险，正如我们在 [JWT 攻击](https://portswigger.net/web-security/jwt) 主题中广泛讨论的那样。
