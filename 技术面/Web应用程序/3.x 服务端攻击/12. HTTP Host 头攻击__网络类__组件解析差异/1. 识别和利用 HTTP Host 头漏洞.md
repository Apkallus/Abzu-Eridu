# 如何识别和利用 HTTP Host 头漏洞

在本节中，我们将更详细地介绍如何识别网站是否容易受到 HTTP Host 头攻击。然后，我们将提供如何利用这些漏洞的示例，以及几个交互式实验，供您在故意易受攻击的网站上练习这些利用技术。

## 如何使用 HTTP Host 头测试漏洞

要测试网站是否容易受到 HTTP Host 头攻击，您需要一个拦截代理（如 Burp Proxy）和手动测试工具（如 Burp Repeater 和 Burp Intruder）。

简而言之，您需要确定是否能够修改 Host 头，同时仍然能够让请求到达目标应用程序。如果可以，您就可以使用此头来探测应用程序，并观察这对响应产生的影响。

### 提供任意 Host 头

在探测 Host 头注入漏洞时，第一步是测试当您通过 Host 头提供任意、未识别的域名时会发生什么。

某些拦截代理直接从 Host 头派生出目标 IP 地址，这使得此类测试几乎不可能进行；您对头所做的任何更改都只会导致请求被发送到完全不同的 IP 地址。然而，Burp Suite 能够准确保持 Host 头与目标 IP 地址之间的分离。这种分离使您能够提供任意或格式错误的 Host 头，同时仍然确保请求被发送到预期的目标（保持 IP 数据包不变的同时，修改应用层 HTTP 协议数据包的花哨描述）。

> **提示：** 目标 URL 显示在面板顶部（对于 Burp Repeater 和 Proxy 拦截）或 Burp Intruder 的 “Target” 选项卡上。您可以通过单击铅笔图标手动编辑目标。

有时，即使您提供了意外的 Host 头，仍然能够访问目标网站。这可能出于多种原因。例如，服务器有时会配置默认或备用选项，以应对它们收到不认识的域名请求。如果您的目标网站恰好是默认的，那您就幸运了。在这种情况下，您可以开始研究应用程序如何处理 Host 头，以及这种行为是否可利用。

另一方面，由于 Host 头是网站工作方式的基本组成部分，篡改它通常意味着您根本无法到达目标应用程序。接收您请求的前端服务器或负载均衡器可能只是不知道将其转发到哪里，从而导致某种“`Invalid Host header`”错误。如果您的目标是通过 CDN 访问的，这种情况尤其可能发生。在这种情况下，您应该继续尝试下面概述的一些技术。

### 检查验证缺陷

您可能会发现，您的请求由于某种安全措施而被阻止，而不是收到“`Invalid Host header`”响应。例如，某些网站会验证 Host 头是否与 TLS 握手中的 SNI 匹配。但这并不一定意味着它们对 Host 头攻击免疫。

您应该尝试了解网站如何解析 Host 头。这有时会揭示可用于绕过验证的漏洞。例如，某些解析算法会从 Host 头中省略端口，这意味着只验证域名。如果您也能提供一个非数字端口，则可以保持域名不变以确保到达目标应用程序，同时可能通过端口注入载荷。

```http
GET /example HTTP/1.1
Host: vulnerable-website.com:bad-stuff-here
```

其他网站会尝试应用匹配逻辑来允许任意子域。在这种情况下，您可以通过注册一个以与白名单域相同字符序列结尾的任意域名来完全绕过验证：

```http
GET /example HTTP/1.1
Host: notvulnerable-website.com
```

或者，您也可以利用您已经入侵的安全性较弱的子域：

```http
GET /example HTTP/1.1
Host: hacked-subdomain.vulnerable-website.com
```

有关常见域验证缺陷的更多示例，查看 [绕过常见 SSRF 防御] 和 [Origin 头解析错误] 的内容。

### 发送歧义请求

验证 Host 的代码和对其进行危险操作的代码通常位于不同的应用程序组件中，甚至位于不同的服务器上。通过识别和利用它们检索 Host 头的方式上的差异，您可以发出一个歧义请求，根据查看它的系统不同，该请求看起来具有不同的主机。

以下只是您如何创建歧义请求的几个示例。

#### 注入重复的 Host 头

一种可能的方法是尝试添加重复的 Host 头。诚然，这通常只会导致您的请求被阻止。然而，由于浏览器不太可能发送这样的请求，您偶尔可能会发现开发人员没有预料到这种情况。在这种情况下，您可能会暴露一些有趣的行为特性。

不同的系统和技术将不同地处理这种情况，但常见的情况是两个头中的一个被赋予优先权，从而有效地覆盖其值。当系统在哪个头是正确的上存在分歧时，这可能导致您可能能够利用的差异。考虑以下请求：

```http
GET /example HTTP/1.1
Host: vulnerable-website.com
Host: bad-stuff-here
```

假设前端优先考虑第一个头实例，但后端更喜欢最后一个实例。在这种情况下，您可以使用第一个头确保您的请求被路由到预期的目标，并使用第二个头将您的载荷传递到服务器端代码。

#### 提供绝对 URL

尽管请求行通常指定所请求域上的相对路径，但许多服务器也被配置为理解对绝对 URL 的请求。

同时提供绝对 URL 和 Host 头所造成的歧义也可能导致不同系统之间的差异。正式地，在路由请求时应优先考虑请求行，但在实践中，情况并非总是如此。您可以像使用重复的 Host 头一样利用这些差异。

```http
GET https://vulnerable-website.com/ HTTP/1.1
Host: bad-stuff-here
```

请注意，您可能还需要尝试不同的协议。根据请求行包含的是 HTTP URL 还是 HTTPS URL，服务器的行为有时会有所不同。

#### 添加缩进

您还可以通过使用空格字符缩进 HTTP 头来发现奇特的行为。某些服务器会将缩进的头解释为换行，因此将其视为前一个头值的一部分。其他服务器则会完全忽略缩进的头。

由于对此情况的高度不一致处理，处理您请求的不同系统之间通常会出现差异。例如，考虑以下请求：

```http
GET /example HTTP/1.1
    Host: bad-stuff-here
Host: vulnerable-website.com
```

网站可能会阻止带有多个 Host 头的请求，但您可以通过像这样缩进其中一个来绕过此验证。如果前端忽略缩进的头，该请求将被处理为对 `vulnerable-website.com` 的普通请求。现在假设后端忽略前导空格，并在重复情况下优先考虑第一个头。这种差异可能允许您通过“换行”的 Host 头传递任意值。

#### 请求走私

这只是发出有害的、歧义请求的众多可能方式中的一小部分。例如，您还可以调整许多 HTTP 请求走私技术来构造 Host 头攻击。我们将在专门的请求走私主题中更详细地介绍这一点。

见 [HTTP 请求走私] 小节

### 注入 Host 覆盖头

即使您无法使用歧义请求覆盖 Host 头，仍然有其他可能性可以在保持其完整的同时覆盖其值。这包括通过其他几个 HTTP 头注入您的载荷，这些头正是为此目的而设计的，尽管用于更无害的用例。

正如我们已经讨论过的，网站通常通过某种中间系统（如负载均衡器或反向代理）访问。在这种架构中，后端服务器接收到的 Host 头可能包含其中一个中间系统的域名。这通常与所请求的功能无关。

为了解决这个问题，前端可能会注入 `X-Forwarded-Host` 头，其中包含客户端初始请求中 Host 头的原始值。因此，当存在 `X-Forwarded-Host` 头时，许多框架会引用它而不是 Host 头。即使没有使用此头的前端，您也可能观察到这种行为。

您有时可以使用 `X-Forwarded-Host` 注入您的恶意输入，同时绕过对 Host 头本身的任何验证。

```http
GET /example HTTP/1.1
Host: vulnerable-website.com
X-Forwarded-Host: bad-stuff-here
```

虽然 `X-Forwarded-Host` 是此行为的事实标准，但您可能会遇到其他用于类似目的的头，包括：

- `X-Host`
- `X-Forwarded-Server`
- `X-HTTP-Host-Override`
- `Forwarded`

> **提示：** 在 Burp Suite 中，您可以使用 [Param Miner](https://portswigger.net/bappstore/17d2949a985c4b7ca092728dba871943) 扩展的 “Guess headers” 功能，利用其广泛的内置字典自动探测受支持的头。

从安全角度来看，重要的是要注意，某些网站（甚至可能是您自己的网站）无意中支持这种行为。这通常是因为它们使用的某些第三方技术中默认启用了一个或多个此类头。

### 通过 Host 头进行 Web 缓存投毒

在探测潜在的 Host 头攻击时，您经常会遇到看似易受攻击但无法直接利用的行为。例如，您可能会发现 Host 头在响应标记中被反射而没有进行 HTML 编码，甚至直接在脚本导入中使用。反射型的客户端漏洞（如 XSS）在由 Host 头引起时通常无法利用。攻击者无法强制受害者的浏览器以有用的方式发出不正确的主机。

然而，如果目标使用 Web 缓存，则可能通过说服缓存向其他用户提供投毒的响应，将这种无用的反射型漏洞转变为危险的存储型漏洞。

要构造 Web 缓存投毒攻击，您需要从服务器获取一个反射了注入载荷的响应。挑战在于在保持缓存键的同时做到这一点，该缓存键仍然可以映射到其他用户的请求。如果成功，下一步是让此恶意响应被缓存。然后，它将提供给任何试图访问受影响页面的用户。

独立缓存通常将 Host 头包含在缓存键中，因此这种方法通常最适合集成的应用程序级缓存。尽管如此，前面讨论的技术有时也可以让您投毒独立的 Web 缓存。

> 见 [Web 缓存投毒] 主题

### 利用经典服务端漏洞

每个 HTTP 头都是利用经典服务端漏洞的潜在向量，Host 头也不例外。例如，您应该通过 Host 头尝试通常的 SQL 注入探测技术。如果头的值被传递到 SQL 语句中，这可能是可利用的。

### 绕过身份验证

出于相当明显的原因，网站通常会将某些功能的访问权限限制为仅限内部用户。然而，某些网站的访问控制功能做出了有缺陷的假设，允许您通过对 Host 头进行简单修改来绕过这些限制。这可以为其他攻击暴露更大的攻击面。
- 修改为本机 `localhost` 

### 通过虚拟主机暴力破解访问内部网站

公司有时会犯错误，将可公开访问的网站和私有的内部网站托管在同一台服务器上。服务器通常同时具有公共和私有 IP 地址。由于内部主机名可能解析为私有 IP 地址，因此仅通过查看 DNS 记录并不总能检测到这种情况：

```
www.example.com: 12.34.56.78
intranet.example.com: 10.0.0.132
```

在某些情况下，内部站点甚至可能没有与之关联的公共 DNS 记录。尽管如此，只要攻击者能够猜到主机名，他们通常可以访问他们有权访问的任何服务器上的任何虚拟主机。如果他们通过其他方式（如信息泄露）发现了隐藏的域名，他们可以直接请求该域名。否则，他们可以使用 Burp Intruder 等工具，使用候选子域的简单字典来暴力破解虚拟主机。

#### 虚拟主机配置缺陷

在Apache中，虚拟主机通过以下方式配置：

```config
<VirtualHost *>
    ServerName eis
    DocumentRoot /var/www2
</VirtualHost>
```

除DocumentRoot指令外，还可以使用虚拟主机容器为Web站点指定其他配置选项。这时，我们常犯的一个错误是忽略默认主机，导致任何安全配置仅适用于一台虚拟主机，而在访问默认主机时却可轻易避开。

渗透测试步骤
1. 使用以下方式向根目录提交GET请求：

    - 正确的Host消息头；
    - 随意Host消息头；
    - Host消息头中的服务器IP地址；
    - 无Host消息头。

2. 对这些请求的响应进行比较。常见的结果是，在Host消息头中使用一个IP地址可获得目录列表。还可以获得各种默认内容。

3. 如果观察到不同的行为，使用生成不同结果的Host消息头重复应用程序解析过程。一定要使用`-vhost`选项进行一次Nikto扫描，确定在最初的应用程序解析过程中忽略的任何默认内容。

### 基于路由的 SSRF

有时也可以使用 Host 头发起高影响的、基于路由的 SSRF 攻击。这些有时被称为“Host 头 SSRF 攻击”，PortSwigger Research 在 [Cracking the lens: targeting HTTP's hidden attack-surface](https://portswigger.net/research/cracking-the-lens-targeting-https-hidden-attack-surface) 中对此进行了深入探讨。

经典的 SSRF 漏洞通常基于 XXE 或可利用的业务逻辑，这些逻辑将 HTTP 请求发送到源自用户可控输入的 URL。另一方面，基于路由的 SSRF 依赖于利用许多云架构中普遍存在的中间组件。这包括内部负载均衡器和反向代理。

尽管这些组件出于不同目的而部署，但从根本上说，它们接收请求并将其转发到适当的后端。如果它们被不安全地配置为基于未经验证的 Host 头转发请求，则可能被操纵将请求错误路由到攻击者选择的任意系统。

这些系统是极好的目标。它们位于特权网络位置，允许它们直接接收来自公共网络的请求，同时也可以访问大部分（如果不是全部）内部网络。这使得 Host 头成为 SSRF 攻击的强大向量，可能将简单的负载均衡器转变为通往整个内部网络的门户。

您可以使用 Burp Collaborator 来帮助识别这些漏洞。如果您在 Host 头中提供 Collaborator 服务器的域，随后从目标服务器或路径中的其他系统收到 DNS 查找，这表明您可能能够将请求路由到任意域。

确认您可以成功操纵中间系统将请求路由到任意公共服务器后，下一步是看看您是否可以利用此行为访问仅限内部的系统。为此，您需要识别目标内部网络上正在使用的私有 IP 地址。除了应用程序泄露的任何 IP 地址之外，您还可以扫描属于该公司的任何主机名，看看它们是否解析为私有 IP 地址。如果所有其他方法都失败，您仍然可以通过暴力破解标准私有 IP 范围（如 `192.168.0.0/16`）来识别有效的 IP 地址。

> **CIDR 表示法：** IP 地址范围通常使用 CIDR 表示法表示，例如 `192.168.0.0/16`。
>
> IPv4 地址由四个 8 位十进制值（称为“八位组”）组成，每个值用点分隔。每个八位组的值范围可以从 0 到 255，这意味着最低可能的 IPv4 地址是 `0.0.0.0`，最高是 `255.255.255.255`。
>
> 在 CIDR 表示法中，范围中的最低 IP 地址被明确写出，后跟另一个数字，表示给定地址从开头起有多少位对于整个范围是固定的。例如，`10.0.0.0/8` 表示前 8 位是固定的（第一个八位组）。换句话说，此范围包括从 `10.0.0.0` 到 `10.255.255.255` 的所有 IP 地址。

### 连接状态攻击

出于性能原因，许多网站会为与同一客户端的多个请求/响应周期重用连接。实现不佳的 HTTP 服务器有时会基于危险的假设，即某些属性（如 Host 头）对于通过同一连接发送的所有 HTTP/1.1 请求都是相同的。这对于浏览器发送的请求可能成立，但对于从 Burp Repeater 发送的一系列请求则不一定成立。这可能导致许多潜在问题。

例如，您偶尔会遇到只在新建连接上收到的第一个请求执行彻底验证的服务器。在这种情况下，您可以通过先发送一个看似无害的初始请求，然后通过同一连接发送恶意请求来绕过此验证。

> 使用 burp 的“单连接”组，或使用脚本中保存连接状态的会话
> 
> 见“请求走私”主题

许多反向代理使用 Host 头将请求路由到正确的后端。如果它们假设连接上的所有请求都与初始请求指向同一主机，这可能为许多 Host 头攻击提供有用的向量，包括基于路由的 SSRF、密码重置投毒和缓存投毒。

### 通过格式错误的请求行进行 SSRF

自定义代理有时无法正确验证请求行，这可能允许您提供异常的、格式错误的输入，并导致不良后果。

例如，反向代理可能会从请求行中获取路径，在其前面加上 `http://backend-server`，并将请求路由到该上游 URL。如果路径以 `/` 字符开头，这可以正常工作，但如果它以 `@` 字符开头呢？

```http
GET @private-intranet/example HTTP/1.1
```

生成的上游 URL 将是 `http://backend-server@private-intranet/example`，大多数 HTTP 库将其解释为以用户名 `backend-server` 访问 `private-intranet` 的请求。
