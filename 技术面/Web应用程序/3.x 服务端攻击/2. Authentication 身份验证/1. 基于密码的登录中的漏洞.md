# 基于密码的登录中的漏洞

对于采用基于密码的登录流程的网站，用户要么自行注册账户，要么由管理员分配账户。该账户与唯一的用户名和秘密密码相关联，用户在登录表单中输入这些信息与数据库中存储的内容匹配以进行身份验证。

在这种情况下，他们知道秘密密码这一事实被视为用户身份的充分证明。这意味着，如果攻击者能够获取或猜测其他用户的登录凭据，网站的安全性就会受到损害。

这可以通过多种方式实现。以下各节将展示攻击者如何使用暴力破解攻击，以及暴力破解保护中的一些缺陷。您还将了解 HTTP 基本身份验证中的漏洞。

## 暴力破解攻击

暴力破解攻击是指攻击者使用试错系统来猜测有效的用户凭据。这些攻击通常使用用户名和密码的字典列表进行自动化。自动化此过程，尤其是使用专用工具，可能使攻击者能够高速进行大量登录尝试。

暴力破解并不总是仅仅对用户名和密码进行完全随机的猜测。通过同时使用基本逻辑或公开可用的知识，攻击者可以微调暴力破解攻击以进行更有依据的猜测。这大大提高了此类攻击的效率。如果网站没有实施足够的暴力破解保护，那么依赖基于密码的登录作为其唯一用户身份验证方法的网站可能非常容易受到攻击。

### 暴力破解用户名

如果用户名符合可识别的模式（例如电子邮件地址），则尤其容易猜测。例如，以 `firstname.lastname@somecompany.com` 格式看到企业登录名是非常常见的。然而，即使没有明显的模式，有时甚至高权限账户也是使用可预测的用户名创建的，例如 `admin` 或 `administrator`。

在审计期间，检查网站是否公开披露了潜在的用户名。例如，您是否可以在不登录的情况下访问用户个人资料？即使个人资料的实际内容被隐藏，个人资料中使用的名称有时也与登录用户名相同。您还应该检查 HTTP 响应以查看是否有任何电子邮件地址被披露。有时，响应中包含高权限用户的电子邮件地址，例如管理员或 IT 支持人员。

### 暴力破解密码

密码同样可以被暴力破解，其难度因密码的强度而异。许多网站采用某种形式的密码策略，强制用户创建高熵密码，至少从理论上讲，这使得单独使用暴力破解更难破解。这通常涉及强制执行包含以下内容的密码：

- 最小字符数
- 大小写字母混合
- 至少一个特殊字符

然而，虽然高熵密码很难单独由计算机破解，但我们可以利用对人类行为的基本了解来利用用户无意中引入此系统的漏洞。用户通常不会创建一个由随机字符组合而成的强密码，而是会选择一个他们能记住的密码，并试图将其硬塞进密码策略中。例如，如果不允许使用 `mypassword`，用户可能会尝试类似 `Mypassword1!` 或 `Myp4$$w0rd` 的密码。

在策略要求用户定期更改密码的情况下，用户通常也会对他们偏好的密码进行微小的、可预测的更改。例如，`Mypassword1!` 变为 `Mypassword1?` 或 `Mypassword2!`。

这种对可能凭据和可预测模式的了解意味着暴力破解攻击通常可以更加复杂，因此更有效，而不仅仅是遍历所有可能的字符组合。

字典攻击正是针对此类弱点：使用常用密码列表，许多此类列表由研究人员分析数百次数据库泄露事件后编制而成。

其中一种资源是 SecLists 的“Common-Credentials”[https://github.com/danielmiessler/SecLists/tree/master/Passwords/Common-Credentials]，它提供了最常用的密码列表，还涵盖了广泛的内容管理系统（CMS）和软件包的默认凭据列表。

#### 凭据填充（Credential Stuffing）

一旦攻击者获得用户名或电子邮件地址，他们通常会转向暗网和泄露数据库，搜索相关联的泄露密码。这种利用是由用户在不同网站重复使用相同密码的常见倾向推动的。因此，在一次泄露中泄露的密码可能在别处同样脆弱。

Haveibeenpwned.com 等工具允许用户检查其账户详细信息是否在过去的泄露事件中遭到入侵，还可以识别泄露来源。值得注意的是，即使密码以加密或哈希形式存储，攻击者也具备字典攻击、暴力破解和预计算表（通常称为“彩虹表”）等方法来破解它们。

### 用户名枚举

用户名枚举是指攻击者能够观察网站行为的变化，以识别给定的用户名是否有效。

用户名枚举通常发生在登录页面上（例如，当您输入有效的用户名但密码错误时），或者在注册表单上（当您输入已被占用的用户名时）。这大大减少了暴力破解登录所需的时间和精力，因为攻击者能够快速生成有效用户名的候选列表。

在尝试暴力破解登录页面时，您应特别注意以下方面的任何差异：

- **状态码**：在暴力破解攻击期间，由于绝大多数猜测都是错误的，返回的 HTTP 状态码可能相同。如果某个猜测返回不同的状态码，这是用户名正确的一个强烈迹象。最佳实践是网站无论结果如何都返回相同的状态码，但这种做法并不总是被遵循。
- **错误消息**：有时，返回的错误消息会因用户名和密码都不正确还是只有密码不正确而有所不同。最佳实践是网站在两种情况下都使用相同的通用消息，但有时会出现小的拼写错误。即使只是一个字符的位置不对，也会使两条消息变得不同，即使在渲染的页面上该字符不可见。
    - 字符差异可能出现在各种位置，尝试不同位置的正则提取高亮对比
- **响应时间**：如果大多数请求的处理时间相似，任何偏离此时间的请求都表明幕后发生了不同的事情。这是猜测的用户名可能正确的另一个迹象。例如，网站可能仅在用户名有效时才检查密码是否正确。这额外的一步可能会导致响应时间略微增加。
    - 这可能很微妙，攻击者尝试输入过长的密码使网站处理时间明显延长，从而使这种延迟更加明显。

## 有缺陷的暴力破解保护

暴力破解攻击在攻击者成功入侵账户之前，很可能会涉及大量失败的猜测。从逻辑上讲，暴力破解保护的核心是尽可能使自动化过程变得棘手，并减慢攻击者尝试登录的速度。防止暴力破解攻击的两种最常见的方式是：

- 如果远程用户尝试访问的账户登录失败次数过多，则锁定该账户
- 如果远程用户的 IP 地址在短时间内进行过多登录尝试，则阻止该 IP 地址

这两种方法都提供了不同程度的保护，但都不是无懈可击的，尤其是在使用有缺陷的逻辑实现时。

例如，您有时可能会发现，如果您登录失败的次数过多，您的 IP 会被阻止。
- 在某些实现中，如果 IP 所有者成功登录，失败尝试次数的计数器会重置。这意味着攻击者只需每隔几次尝试就登录他们自己的账户，就可以防止达到此限制。
- 有时，服务器解析请求的 IP 覆盖头部，例如 `X-Forwarded-For`。此时设置 IP 覆盖头部即可绕过此限制。见 `授权与访问控制 - 基于位置的访问控制` 小节中的 IP 地址混淆 ⚠ 或者，之后需设置一个单独的通用小节 ⚠

在这种情况下，只需在字典列表中每隔一段时间包含您自己的登录凭据，就足以使这种防御几乎毫无用处。

### 账户锁定

网站试图防止暴力破解的一种方法是在满足某些标准时锁定账户，通常是达到一定次数的失败登录尝试。锁定持续时间因组织而异：有些组织可能选择每 30 分钟解锁一次，而另一些（如银行应用程序）则要求用户联系支持热线并验证凭据后才能解锁。更糟的是，用户可能因支持人员不在岗而排队等待，尤其是在周末。

账户锁定策略存在安全困境。如果过于宽松，可能在用户被阻止前允许过多尝试；如果过于严格，则可能导致拒绝服务（DoS）。

与正常的登录错误一样，来自服务器的指示账户已被锁定的响应也可以帮助攻击者枚举用户名。
- 不存在的用户通常不会触发账户锁定保护。账户锁定状态通常可用来作为账户名是否存在的触点
- 当账户被锁定时，对有效/无效密码的响应也可能不同。导致攻击者在账户锁定状态下可无限制继续暴破

锁定账户针对特定账户的目标性暴力破解提供了一定的保护。然而，这种方法无法充分防止攻击者只是试图访问他们能够获取的任何随机账户的暴力破解攻击。

例如，可以使用以下方法来绕过这种保护：

1. 建立一个可能是有效的候选用户名列表。这可以通过用户名枚举或简单地基于常用用户名列表来完成。
2. 确定一个非常小的密码候选列表，你认为至少有一个用户可能使用。关键的是，你选择的密码数量不得超过允许的登录尝试次数。例如，如果你已经确定限制是 3 次尝试，你最多需要选择 3 个密码猜测。
3. 使用 Burp Intruder 等工具，用每个候选用户名尝试每个选定的密码。这样，你就可以在不触发账户锁定的情况下尝试暴力破解每个账户。你只需要一个用户使用了这三个密码中的一个，就可以入侵一个账户。

账户锁定也无法防御撞库攻击。这涉及使用一个庞大的 `用户名:密码` 对字典，该字典由数据泄露中窃取的真实登录凭据组成。撞库依赖于这样一个事实：许多人在多个网站上重复使用相同的用户名和密码，因此字典中的一些被泄露的凭据也可能在目标网站上有效。账户锁定无法防御撞库，因为每个用户名只被尝试一次。撞库尤其危险，因为它有时会导致攻击者通过一次自动化攻击入侵许多不同的账户。

#### 特殊的锁定机制

还有一些更特殊的锁定机制实现，其中之一是 AWS 的 [Cognito](https://docs.aws.amazon.com/cognito/latest/developerguide/authentication.html#authentication-flow-lockout-behavior)。它使用一种简单的缩放算法，既能缓解暴力破解攻击，又不会对受影响用户造成长期的拒绝服务攻击。在 5 次密码登录失败后，用户被锁定 1 秒。锁定持续时间随每次失败尝试翻倍，最大为 15 分钟。在锁定期间进行的登录尝试会抛出异常，称为 `Password attempts exceeded`，在大多数实现中，这些异常不会返回给发起登录的用户。如果不向用户显示这些异常，测试人员可能会认为没有使用任何锁定机制，因为 200 次快速登录尝试会产生大量异常，而合法的失败登录尝试却很少。

该机制的数学原理是：`2^(n-5)`，其中 `n` 是失败登录尝试的次数。计算结果为锁定用户的秒数。要重置锁定计数，用户必须成功登录或等待 15 分钟。

要使用模糊测试工具（如 Burp Suite 的 Intruder）进行测试，请进入“资源池”，然后将最大并发请求数设置为 1，请求间延迟设置为 2 秒。尝试 200 次无效认证，然后在模糊测试工具完成后立即使用有效凭据尝试 3 次。等待 2 分钟再尝试登录。如果此时登录成功，则可能正在使用 Cognito。然后可以进一步测试以验证 Cognito 的使用，尝试将锁定时间推高，但向客户验证此信息可能更容易。

#### 解锁机制

为了评估解锁机制对未授权账户解锁的抵抗能力，请启动解锁机制并寻找弱点。典型的解锁机制可能涉及安全问题或通过电子邮件发送的解锁链接。分析解锁链接是否为唯一的一次性链接，以防止攻击者猜测或重放链接并批量进行暴力破解。

### 用户速率限制

网站试图防止暴力破解攻击的另一种方式是通过用户速率限制。在这种情况下，在短时间内发出过多登录请求会导致您的 IP 地址被阻止。通常，IP 只能通过以下方式之一解除阻止：

- 经过一定时间后自动解除
- 由管理员手动解除
- 用户成功完成 CAPTCHA 后手动解除

用户速率限制有时比账户锁定更受青睐，因为它不太容易导致用户名枚举和拒绝服务攻击。然而，它仍然不是完全安全的。正如我们在之前的实验中看到的示例，攻击者可以通过多种方式操纵其显示的 IP 以绕过阻止。

由于限制基于从用户 IP 地址发送的 HTTP 请求速率，如果您能找出如何通过单个请求猜测多个密码，有时也可以绕过此防御。
- 例如，以 JSON 格式提交凭证。然而可设置 JSON 属性值为列表，从而一次进行大量尝试

在一次安全测试中遇到了类似场景，IP 地址在 10 次不成功尝试后被封锁。

然而，通过将 `X-Forwarded-For` 头设置为 `127.0.0.1`，我们发现应用程序被误导，认为请求来自其本地网络，从而允许其通过。

根据应用程序的功能，其他几个头也可用于达到类似效果。

**示例**
```http
X-Originating-IP: 127.0.0.1
X-Remote-IP: 127.0.0.1
X-Remote-Addr: 127.0.0.1
X-Client-IP: 127.0.0.1
X-Host: 127.0.0.1
X-Forwarded-Host: 127.0.0.1
```

同样，你也可以尝试使用双重 `X-Forwarded-For` 头或类似头。服务器或 WAF 可能因存在两个此类头而混淆，导致处理不当。建议将 IP 地址替换为私有 IP 子网，甚至是应用程序枚举期间可能无意中暴露的合法内部路径。

#### 绕过速率限制的其他方法

- **使用多个 IP 地址**：达到阈值后轮换 IP 地址。虽然某些 WAF 使用 IP 信誉系统识别和阻止可疑尝试，但这可以通过使用私有代理绕过。类似地，AWS Lambda 和 Azure Functions 等云函数也可用于轮换 IP 地址。
- **更改路径**：某些配置欠佳的 Web 应用程序可能无法有效处理端点路径变化。这种疏忽有时可被利用来绕过速率限制。改变字符大小写或使用某些编码也可能规避此类速率限制机制。例如，对于标准端点 `/api/v4/endpoint`，可测试的变体包括：

**示例**
```
/api/v4/Endpoint
/api/v4/endpoint%00
/api/v4/endpoint%01
/api/v4/endpoint%0A
```

- **使用不同端点**：某些应用程序的速率限制可能在不同平台或端点之间应用不一致。例如，Web 版本可能有速率限制，但其移动对应版本可能没有。
- **账户轮换**：面对速率限制时，可考虑登录有效账户，然后尝试无效账户，并在两者之间轮换。这种方法有助于混淆系统并绕过 IP 限制。

## HTTP 基本身份验证

虽然相当古老，但 HTTP 基本身份验证相对简单且易于实现，这意味着您有时可能会看到它被使用。在 HTTP 基本身份验证中，客户端从服务器接收一个身份验证令牌，该令牌通过连接用户名和密码并进行 Base64 编码来构造。此令牌由浏览器存储和管理，浏览器会自动将其添加到每个后续请求的 `Authorization` 头中，如下所示：

```http
Authorization: Basic base64(username:password)
```

由于多种原因，这通常不被认为是一种安全的身份验证方法。首先，它涉及在每次请求中重复发送用户的登录凭据。除非网站也实施了 HSTS，否则用户凭据容易在中间人攻击中被捕获。

此外，HTTP 基本身份验证的实现通常不支持暴力破解保护。由于令牌仅由静态值组成，这可能使其容易受到暴力破解的攻击。

HTTP 基本身份验证也特别容易受到与会话相关的攻击（尤其是 CSRF）的影响，它本身对此不提供任何保护。

在某些情况下，利用易受攻击的 HTTP 基本身份验证可能只会让攻击者访问一个看似无趣的页面。然而，除了提供进一步的攻击面之外，以这种方式暴露的凭据可能会在其他更机密的环境中被重复使用。

## 故障开放登录机制

故障开放逻辑是一种逻辑缺陷，触发异常后代码走异常处理分支，以绕过登录确认

### 渗透测试步骤：故障开放登录机制

1. 使用控制的一个账户执行一次完整、有效的登录。使用拦截代理服务器记录提交的每一份数据、收到的每一个响应。

2. 多次重复登录过程，以非常规方式修改提交的数据。例如，对于客户端传送的每个请求参数或cookie：

    - 提交一个空字符串值；
    - 完全删除名/值对；
    - 提交非常长和非常短的值；
    - 提交字符串代替数字或相反；
    - 以相同和不同的值，多次提交同一个数据项。

3. 仔细检查应用程序对提交的每个畸形请求的响应，确定任何不同于基本情况的差异。

4. 根据这些观察结果调整测试过程。如果某个修改造成行为改变，设法将这个修改与其他更改组合在一起，使应用程序的逻辑达到最大限度。

## 方法论

### 渗透测试步骤：暴破

1. 用控制的某个账户手动提交几个错误的登录尝试，监控接收到的错误消息。

2. 如果应用程序在大约10次登录失败后还没有返回任何有关账户锁定（account lockout）的消息，再尝试正确登录。如果登录成功，应用程序可能并未采用任何账户锁定策略。

3. 如果账户被锁定，可以尝试重复使用不同的账户。如果应用程序发布任何cookie，这次可以将每个cookie仅用于一次登录尝试，并为随后的每次登录尝试获取新cookie。

4. 此外，如果账户被锁定，应查看与提交无效密码相比，提交有效密码是否会导致应用程序的行为出现任何差异。如果确实如此，则可以继续实施密码猜测攻击，即使账户被锁定。

5. 如果没有控制任何账户，尝试枚举一个有效的用户名并使用它提交几次错误登录，监控有关账户锁定的错误消息。

6. 发动蛮力攻击前，首先确定应用程序响应成功与失败登录之间的行为差异，以此分清它们在自动攻击过程中表现出的区别。

7. 列出已枚举出的或常见的用户名列表和常用密码列表。根据所获得的任何有关密码强度规则的信息对上述列表加以修改，以避免进行多余测试。

8. 使用这些用户名和密码的各种排列组合，通过适当的工具或定制脚本迅速生成登录请求。监控服务器响应以确定成功的登录尝试。

9. 如果一次针对几个用户名，通常最好以广度优先（breadth-first）而非深度优先（depth-first）的方式实施这种蛮力攻击。这包括循环使用一组密码（从最常用的密码开始）并轮流对每个用户名使用每一个密码。这种方法有两方面的好处：首先，可以更加迅速地确定使用常用密码的账户；其次，这样做可以降低触发任何账户锁定防御的可能性，因为在使用同一个账户进行连续登录之间存在时间延迟。


### 评估密码强度

评估密码的长度、复杂性、重用和老化要求，确定应用程序抵抗使用可用密码字典进行暴力破解密码猜测的能力。

1. 密码中允许和禁止使用哪些字符？是否要求用户使用来自不同字符集的字符，例如大小写字母、数字和特殊符号？
2. 用户多久可以更改一次密码？用户在先前更改后多久可以再次更改密码？用户可能通过连续更改密码 5 次来绕过密码历史要求，以便在最后一次密码更改后重新设置其初始密码。
3. 用户必须在何时更改密码？
    - [NIST](https://pages.nist.gov/800-63-3/sp800-63b.html#memsecretver) 和 [NCSC](https://www.ncsc.gov.uk/collection/passwords/updating-your-approach#PasswordGuidance:UpdatingYourApproach-Don'tenforceregularpasswordexpiry) 均建议 **不要** 强制定期密码过期，尽管 PCI DSS 等标准可能要求这样做。
4. 用户多久可以重用一次密码？应用程序是否维护用户先前使用过的 8 个密码的历史记录？
5. 下一个密码必须与上一个密码有多大差异？
6. 是否防止用户在密码中使用其用户名或其他账户信息（例如名字或姓氏）？
7. 可以设置的最小和最大密码长度是多少？它们对于账户和应用程序的敏感性是否适当？
8. 是否可以设置常见密码，例如 `Password1` 或 `123456`？
9. 凭据是由应用程序为用户选择的，例如社会安全号码或出生日期？用于替代标准密码的凭据是否易于获取、可预测或容易受到暴力破解攻击？

### 获取触点

一个典型的登录表单要求用户输入两组信息（用户名和密码）

如果登录尝试失败，当然可以得出结论：至少有一组信息出错。但是，如果应用程序通知是哪一组信息无效，就可以利用它显著降低登录机制的防御效能。

在最简单的情况下，如果只需要用户名和密码登录，应用程序可能会通过指出失败的原因（用户名无效或密码错误）来响应失败的登录尝试

在这种情况下，攻击者可以发动一次自动化攻击，遍历大量常见的用户名，确定哪些有效。并将枚举出的用户名列表作为随后各种攻击的基础，包括密码猜测、攻击用户数据或会话，或者社会工程

除主要的登录功能外，还可以对验证机制的其他组件进行用户名枚举。理论上，需要提交真实或潜在用户名的任何功能都可用于这一目的。例如，通常都可以对用户注册功能进行用户名枚举。如果应用程序允许新用户注册并指定他们自己的用户名，由于应用程序需要防止注册重复用户名，在这种情况下，几乎不可能阻止用户名枚举攻击。有时也可以对密码修改或忘记密码功能进行用户名枚举。

在更复杂的登录机制中，应用程序要求用户提交几组信息，或者完成几个步骤。这时，详细的失败消息或差异点可帮助攻击者轮流针对登录过程的每个阶段发动攻击，提高其获得未授权访问的可能性。

即使响应有效和无效用户名的错误消息表面看来完全相同，它们之间仍然存在细微的差别，可用于枚举有效的用户名。例如，如果应用程序中的多条代码路径返回“相同的”失败消息，这些消息之间仍然可能存在细小的排版差异。有些时候，应用程序响应在屏幕上显示的内容完全相同，但其HTML源代码可能隐藏着细微的区别，如注释或布局方面的不同。如果无法轻易枚举出有效的用户名，应当仔细比较应用程序对有效和无效用户名作出的响应。

#### 测试步骤：获取触点渗透

1. 如果已经知道一个有效的用户名（例如一个受控制的账户），使用这个用户名和一个错误的密码进行一次登录，然后使用一个完全随机的用户名进行另一次登录。

2. 记录服务器响应两次登录尝试的每一个细节，包括状态码、任何重定向、屏幕上显示的信息以及任何隐藏在HTML页面中的差异。使用拦截代理服务器保存服务器上来回流量的完整历史记录。

3. 努力找出服务器响应两次登录尝试的任何明显或细微的差异。

4. 如果无法发现任何差异，在应用程序中任何提交用户名的地方（例如自我注册、密码修改与忘记密码功能）重复上述操作。

5. 如果发现服务器响应有效和无效用户名之间的差异，收集一个常见用户名列表并使用一个定制脚本或自动工具迅速提交每个用户名，过滤出说明用户名有效的响应

6. 开始枚举操作之前，请确定应用程序是否在登录尝试失败次数达到一定数目后执行账户锁定。如果应用程序执行账户锁定，最好在设计枚举攻击时记住这一点。例如，如果应用程序只允许登录某个账户时失败3次，可能就会在使用通过自动枚举发现的每个用户名登录时“浪费” 一次登录机会。因此，当进行枚举攻击时，不要在每次登录时提交完全不合理的密码，而是提交常见的密码，如`password1`或以用户名为密码。如果应用程序执行脆弱的密码强度规则，在枚举操作过程中执行的一些登录尝试就很可能会取得成功，有些情况下还可能同时查明用户名和密码。

即使应用程序对包含有效与无效用户名登录尝试的响应完全相同，我们仍然可以根据应用程序响应登录请求的时间枚举出用户名。应用程序通常依据登录请求是否包含有效用户名，对其进行截然不同的后端处理。例如，如果登录请求中包含一个有效的用户名，应用程序可能会从后端数据库中获取用户资料，对这些资料进行各种处理（如检查账户是否到期），然后确认密码（可能使用一个资源密集型散列算法），如果密码错误返回一条常规消息。仅仅使用浏览器可能无法检测出应用程序处理两个请求之间的时间差异，但自动工具能够区分这种差异。即使这种操作会产生大量错误警报

### 证书确认不完善

设计不佳的验证机制：
- 截短密码，只确认前n个字符；
- 并不对密码进行大小写检查；
- 在检查密码之前删除不常用的字符

以上这些密码确认限制可显著减少可能的密码数量。通过实验，渗透测试员可以判定一个密码是否得到完全确认，或者某个限制是否生效。然后就可以针对登录机制的自动攻击方法进行调整，删除不必要的测试，大量减少攻破用户账户所需提交的请求的数量。

#### 渗透测试步骤：证书确认不完善

1. 使用一个现有的账户，尝试用密码的各种变化形式进行登录：删除最后一个字符、改变字符大小写、删除任何特殊排版的字符。如果其中一些尝试取得成功，继续实验过程，尝试了解完整的证书确认过程。

2. 利用得到的所有结果调整自动密码猜测攻击，删除多余的测试，提高成功的几率。

### 非唯一性用户名

设计存在缺陷的自我注册功能可能造成用户枚举漏洞。如果应用程序禁止使用相同的用户名，那么攻击者可以注册大量常见的用户名，从而确定遭到拒绝的现有用户名。

#### 渗透测试步骤：非唯一性用户名

1. 如果应用程序允许自我注册，尝试用不同的密码两次注册同一个用户名。

2. 如果应用程序阻止第二次注册企图，尝试枚举现有的用户名。用一组常见的用户名进行多次注册尝试，设法确定被应用程序阻止的已注册用户名。

### 证书分配不安全

许多应用程序并不在用户与应用程序正常交互的过程中分配新建账户的证书，而是通过邮寄或电子邮件等方式。

这种分配方式有时会带来安全风险。例如，如果分配证书的邮件中同时包含用户名和密码，没有给邮件设置使用时间限制，没有要求用户在第一次登录时修改密码，那么，大多数甚至是绝大部分应用程序用户都不会修改初始证书，并且将收到的邮件保存很长一段时间，而未授权方有可能在此期间访问这些分配证书的邮件。

有时应用程序并不分配证书，而是传送一个“账户激活”URL，用户通过它设置自己的初始密码。如果发送给连续用户的URL表现出某种顺序，攻击者就可以通过注册几个紧密相连的用户确定这种顺序，以此推断出发送给最近与后续用户的激活URL。

某些Web应用程序表现的一种相关行为是，允许新用户以看似安全的方式注册账户，然后向每个新用户发送一封包含其完整的登录证书的欢迎电子邮件。

#### 渗透测试步骤：证书分配不安全

1. 获得一个新账户。如果应用程序并不要求在注册阶段设置所有证书，弄清应用程序如何向新用户分配证书。

2. 如果应用程序使用账户激活URL，设法注册几个紧密相连的新账户，确定收到的URL中的任何顺序。如果确定某种模式，尝试预测应用程序发送给最近与后续用户的激活URL，尝试使用这些URL占有他们的账户。

3. 尝试多次重复使用同一个激活URL，看看应用程序是否允许这样做。如果遭到拒绝，尝试在重复使用URL之前锁定目标账户，看看现在这种方法是否可行。
