# 多因素身份验证中的漏洞

许多网站完全依赖基于密码的单因素身份验证来认证用户。然而，有些网站要求用户使用多种身份验证因素来证明其身份。

MFA 意味着认证需要*至少*以下因素中的两种：

| 因素 | 示例 |
|--------|----------|
| 你知道的内容 | 密码、PIN 码和安全问题。 |
| 你拥有的内容 | 硬件或软件令牌、证书、电子邮件*、短信和电话呼叫。 |
| 你的特征 | 指纹、面部识别、虹膜扫描、掌纹扫描和行为因素。 |
| 位置 | 源 IP 范围、地理位置。 |

\* 电子邮件只有在电子邮件账户本身受到 MFA 保护时，才真正构成“你拥有的内容”。因此，它应被视为比证书或 TOTP 等其他替代方案更弱，在某些定义下可能不被接受为 MFA。

注意，只有验证多个**不同的因素**，才能充分实现多因素身份验证的好处。以两种不同方式验证**同一因素**并不是真正的双因素身份验证。基于电子邮件的 2FA 就是这样一个例子。虽然用户必须提供密码和验证码，但获取验证码只依赖于他们知道其电子邮件账户的登录凭据。因此，知识认证因素只是被验证了两次，尽管它可能比单纯密码提供一些安全优势，并可能被视为两步验证（2SV）。

由于在基于浏览器的环境中实施生物识别的复杂性，“你的特征”很少用于 Web 应用程序，尽管它正开始通过 WebAuthn 等标准被采用。然而，基于**你知道的东西**和**你拥有的东西**的双因素身份验证（2FA），无论是强制的还是可选的，都越来越普遍。这通常要求用户同时输入传统密码和来自其拥有的带外物理设备的临时验证码。

Google 与纽约大学和圣地亚哥大学等知名机构合作进行的一项长达一年的综合研究揭示了一些惊人的发现。具体来说，基于 SMS 的双因素认证（2FA）有效阻止了 100% 的自动化机器人攻击、96% 的网络钓鱼尝试和 76% 的定向威胁。相比之下，基于设备的 2FA 表现更出色，阻止了 100% 的机器人攻击、99% 的大规模钓鱼事件和 90% 的定向攻击 [https://security.googleblog.com/2019/05/new-research-how-effective-is-basic.html]。

虽然攻击者有时可以获取一个基于知识的因素（例如密码），但同时从带外来源获取另一个因素的可能性要小得多。因此，双因素身份验证显然比单因素身份验证更安全。然而，与任何安全措施一样，它的安全性取决于其实现方式。实现不当的双因素身份验证可能被攻破，甚至被完全绕过，就像单因素身份验证一样。

当前小节聚焦与逻辑缺陷绕过与暴破验证码，各种 MFA 形式描述见“多因素身份验证功能与形式”小节

## 多因素认证绕过

- 暴力破解：
    如果 OTP（一次性密码）长度短且无过期时间，攻击者可以尝试所有可能组合直至找到正确的一个。

- 较少使用的接口：
    某些接口（如移动应用或 API）可能不具备与主应用程序相同的严格 2FA 保护，特别是当安全措施在不同平台上的实现不一致时。

- 强制浏览：
    某些页面可能在无需 MFA 甚至无需身份验证的情况下即可访问。“授权与访问控制”部分

- 可预测/可重用的令牌：
    如果令牌可预测或可重用，攻击者可能猜测或重用以绕过 MFA。

- 参数篡改：
    攻击者可能操纵应用程序参数以绕过 2FA。“授权与访问控制 - Web 参数篡改”部分

- 应用程序使用自定义认证流程：
    如果认证使用的是允许自定义认证流程（或策略）的 OpenID Connect（OIDC）提供商（如 Azure B2C），则可能定义了多个流程，其中一些可能不需要 MFA。例如，如果应用程序使用名为 `B2C_1_SignInWithMFA` 的流程进行认证，则尝试将其篡改为 `B2C_1_SignIn`、`B2C_1_SignInWithoutMFA` 或其他类似值。

- 应用程序在特定条件下不要求 MFA：
    - 来自特定 IP 地址（可能使用 `X-Forwarded-For` HTTP 头进行欺骗）。
    - 设置了特定的 HTTP 头（如非标准头 `X-Debug`）。
    - 针对特定硬编码账户（如“root”或“breakglass”账户）。

- 应用程序同时支持本地登录和联合登录，且这两种账户类型之间没有强隔离：
    例如，如果用户注册了本地账户并为其配置了 MFA，但未在联合登录提供商上的账户配置 MFA，则攻击者可能通过破坏用户在联合登录提供商上的账户，使用相同的电子邮件地址在目标应用程序上重新注册（或关联）一个联合账户。

- MFA 组件并未完全集成到主应用程序：
    如果 MFA 在不同于主应用程序的系统上实现（例如在反向代理上，以保护原本不支持 MFA 的旧应用程序），则可能通过直接连接到后端应用服务器来绕过它

## 双因素身份验证令牌

验证码通常由用户从某种物理设备上读取。现在许多高安全性网站为此目的向用户提供专用设备，例如 RSA 令牌或键盘设备，您可能使用它们来访问网上银行或工作笔记本电脑。这些专用设备除了专为安全性而设计外，还具有直接生成验证码的优势。同样，网站也常使用专用的移动应用程序（如 Google Authenticator）来生成验证码。

另一方面，一些网站通过短信将验证码发送到用户的手机上。虽然这在技术上仍然验证了“你拥有的东西”这一因素，但它容易被滥用。首先，验证码是通过 SMS 传输的，而不是由设备本身生成的。这造成了验证码被拦截的可能性。还存在 SIM 卡交换的风险，即攻击者通过欺诈手段获取带有受害者电话号码的 SIM 卡。然后攻击者将收到发送给受害者的所有 SMS 消息，包括包含验证码的那条。


## 多阶段登录机制中的逻辑缺陷

一些应用程序使用精心设计的多阶段登录机制，例如：

- 输入用户名和密码；
- 响应一个质询，答案是PIN中的特殊数字；
- 提交在不断变化的物理令牌上显示的某个值。

多阶段登录机制旨在提高基于用户名和密码的简单登录模型的安全性。通常，多阶段登录机制首先要求用户通过用户名或类似数据项确认自己的身份；随后，登录阶段再执行各种验证检查。这种机制常常存在安全漏洞，特别是各种逻辑缺陷。

在执行过程中，一些多阶段登录机制对用户与早先阶段的交互做出潜在不安全的假设，如下所示。

- 应用程序可能认为访问第三阶段的用户已经完成第一、二阶段的验证。因此，它可能允许直接由第一阶段进入第三阶段并且提供正确证书的攻击者通过验证，使仅拥有部分正常登录所需的各种证书的攻击者能够成功登录。

- 应用程序可能会信任由第二阶段处理的一些数据，因为这些数据已经在第一阶段得到确认。但是，攻击者能够在第二阶段操控这些数据，提供一个不同于第一阶段的值。例如，在第一阶段，应用程序会判定用户的账户是否已经过期、被锁定或者属于管理用户，或者是否需要完成第二阶段以外的其他登录阶段。如果攻击者能在不同登录阶段的转换过程中干扰这些标记，他们就可以更改应用程序的行为，让他们只需部分证书即可通过验证，或者提升其权限。

- 应用程序可能认为每个阶段的用户身份不会发生变化，因此，它并不在每个阶段明确确认用户身份。例如，第一阶段可能需要提交一个有效的用户名和密码，第二阶段需要重新提交用户名（此时保存在隐藏表单字段中）和不断变化的物理令牌上的一个值。如果攻击者在每个阶段提交有效的数据对，但这些数据属于两个不同的用户，那么应用程序可能会允许该用户通过验证，认为他是两名用户中的任意一名用户。这就允许拥有自己物理令牌并发现其他用户密码的攻击者能够以该用户的身份登录（反之亦然）。虽然不对其他信息加以利用，攻击者无法完全攻破登录机制，但它的总体安全状态已严重削弱，应用程序为执行二元机制所投入的大量开支和努力并未取得预期的效果。

### 完全绕过双因素身份验证

如果首先提示用户输入密码，然后在单独的页面上提示输入验证码，则用户实际上在输入验证码之前就已经处于“已登录”状态。在这种情况下，值得测试在完成第一个身份验证步骤后，您是否可以直接跳过进入“仅限登录后”的页面。有时您会发现，网站在加载页面之前实际上并不检查您是否完成了第二步。

#### 示例：使用强制导航绕过多因素身份验证

假设一个应用程序实现了三步登录流程。首先，应用程序检查用户的密码。然后，它向用户发送MFA码并验证。最后，应用程序在登录用户之前询问安全问题：

```
步骤1（密码检查）→ 步骤2（MFA）→ 步骤3（安全问题）
```

正常的认证流程如下：

1. 用户访问 `https://example.com/login/`。应用程序提示用户输入密码，用户输入。
2. 如果密码输入正确，应用程序向用户的邮箱发送MFA码，并将用户重定向到 `https://example.com/mfa/`。在这里，用户输入MFA码。
3. 应用程序检查MFA码，如果正确，将用户重定向到 `https://example.com/security_questions/`。在那里，应用程序询问用户几个安全问题，如果提供的答案正确则登录用户。

但有时，用户可以在未完成步骤1或2的情况下到达认证流程的步骤3。虽然易受攻击的应用程序在步骤2完成后将用户重定向到步骤3，但它没有验证用户在允许进入步骤3之前是否已完成步骤2。在这种情况下，攻击者所要做的就是操纵站点的URL并直接请求后续阶段的页面。

如果攻击者可以直接访问 `https://example.com/security_questions/`，他们就可以完全绕过多因素认证。他们可能只需凭某人的密码和安全问题答案就能登录，而无需其MFA设备。

### 有缺陷的双因素验证逻辑：服务器端缺乏上下文，过程中切换用户

有时，双因素身份验证中的逻辑缺陷意味着，在用户完成初始登录步骤后，网站没有充分验证同一用户是否在执行第二步。

例如：

1. 用户在第一步中使用其正常凭据登录

    ```http
    POST /login-steps/first HTTP/1.1
    Host: vulnerable-website.com
    ...
    username=carlos&password=qwerty
    ```

2. 然后他们被分配一个与其账户关联的 Cookie

    ```http
    HTTP/1.1 200 OK
    Set-Cookie: account=carlos
    ```

3. 然后浏览器携带 account cookie 访问第二步验证端点，此时服务器发送验证码
    ```http
    GET /login-steps/second HTTP/1.1
    Cookie: account=carlos
    ```

4. 最后提交验证码时，服务器使用请求中的 Cookie 来确定当前账户：

    ```http
    POST /login-steps/second HTTP/1.1
    Host: vulnerable-website.com
    Cookie: account=carlos
    ...
    verification-code=123456
    ```

在这种情况下，攻击者可以使用自己的凭据登录，但在触发/提交验证码时将 `account` Cookie 的值更改为任意用户名。或者，当服务器缺乏会话 cookie 验证时，甚至可直接访问步骤2的端点触发验证码发送

```http
POST /login-steps/second HTTP/1.1
Host: vulnerable-website.com
Cookie: account=victim-user
...
verification-code=123456
```

如果攻击者随后能够暴力破解验证码，这将允许他们完全基于用户名登录任意用户的账户。

### 渗透测试步骤：多阶段登录机制中的缺陷

1. 使用控制的一个账户执行一次完整、有效的登录。使用拦截代理服务器记录向应用程序提交的每一份数据。

2. 确定各个不同登录阶段以及在每个阶段收集到的数据。确定是否不止一次收到某条信息，或者是否有信息被返回给客户端，并通过隐藏表单字段、cookie或者预先设置的URL参数重新提交。

3. 使用各种畸形请求多次重复登录过程：

    - 尝试按不同的顺序完成登录步骤；

    - 尝试直接进入任何特定的阶段，从那里继续登录；

    - 尝试省略每个阶段并从下一阶段继续登录；

    - 运用想象力，想出其他开发者无法预料的方式访问不同的登录阶段。

4. 如果有数据不止提交一次，尝试在另一个阶段提交一个不同的值，看看是否仍然能够成功登录。有些提交数据可能是多余的，实际上并不由应用程序处理。有些数据在某个阶段得到确认，随后就被应用程序所信任。在这种情况下，尝试在一个阶段提供一名用户的证书，然后在下一阶段转换成由另一名用户进行验证。应用程序可能在几个阶段都对同一个数据进行确认，但执行不同的检查。在这种情况下，尝试在第一个阶段提供（例如）一名用户的用户名和密码，然后在第二个阶段提供另一名用户的用户名和PIN号码。

5. 特别注意任何通过客户端传送、并不由用户直接输入的数据。应用程序可能使用它们保存登录进展状态信息，并且信任这些数据。例如，如果第三个阶段的请求中包含参数`stage2complete=true`，那么攻击者就可以通过设置这个值直接进入第三个阶段。尝试修改应用程序提交的值，确定是否可以使用这种方法进入或省略登录阶段。

## 暴力破解 2FA 验证码

与密码一样，网站需要采取措施防止对 2FA 验证码进行暴力破解。这一点尤其重要，因为验证码通常是一个简单的 4 位或 6 位数字。如果没有足够的暴力破解保护，破解这样的代码是轻而易举的。

有些网站试图通过在用户输入一定数量的错误验证码后自动将其注销来防止这种情况。这在实践中是无效的，因为高级攻击者甚至可以通过为 Burp Intruder [创建宏](/burp/documentation/desktop/settings/sessions#macros)来自动化这一多步骤过程。[Turbo Intruder](https://portswigger.net/bappstore/9abaa233088242e8be252cd4ff534988) 扩展也可用于此目的。

- 使用脚本或 burp 宏：执行多步骤，取得其中的各种 cookie 与令牌应用到下一步

### MFA 绕过场景：OTP 绕过

考虑一个需要 OTP 完成认证过程的场景。登录应用程序后，OTP 发送到用户注册的电子邮件地址。

进一步检查发现，OTP 长度为五位数字，且没有过期时间。此外，应用程序未强制执行任何速率限制或账户锁定机制。据此，我们可以确定此 OTP 的总可能排列数为 100,000（范围从 00000 到 99999）。

鉴于这些漏洞，自动化猜测 OTP 是可行的。

以下脚本尝试通过系统发送 OTP 值并检查成功登录来暴力破解 OTP。逻辑还触发 OTP 重新发送，遍历所有 100,000 个可能的 OTP 排列。

**POC**
```python
import requests

url = "http://portal.redseclabs.com"
headers = {
    "Cookie": "session=eyJ1c2VybmFtZSI6ImFkbWluIn0.ZRt-Ug.krmeKBbbbaVBmLE7fKeL8vYDqVo",
}

def brute(otp):
    payload = {
        "otp": otp
    }
    response = requests.post(url + "/otp", headers=headers, data=payload, allow_redirects=False)
    if response.status_code == 302:
        print("[+] OTP Found! ", otp)
        print("Response cookies:", response.cookies.values())
        return True

print("[+] Generating OTPs")
for i in range(100):
    requests.post(url + "/resend_otp", headers=headers)

for i in range(100000):
    otp = str(i).zfill(5)
    if brute(otp):
        break
```

在渗透测试中遇到过类似场景，但略有不同。虽然 OTP 设计为在 5 分钟后过期，然后生成新的，但发现先前的 OTP 仍然有效且可用。这意味着在任何给定时间，有两个有效的 OTP。因此，猜测正确 OTP 所需的总排列数实际上减少了一半。为了利用此漏洞，设计了两个暴力破解脚本：第一个从 00000 到 10000 递增猜测，第二个反向进行，从 10000 递减到 00000。
