# JWT 攻击

在本节中，我们将探讨设计问题和 JSON Web 令牌（JWT）处理中的缺陷如何使网站面临各种高严重性攻击。由于 JWT 最常用于身份验证、会话管理和访问控制机制中，这些漏洞可能危及整个网站及其用户。

Burp Scanner 可以自动检测 JWT 机制中的许多漏洞。更多信息，请参见 **Target > Issued definitions** 选项卡中的相关问题定义。

## 什么是 JWT？

JSON Web 令牌（JWT）是一种标准化格式，用于在系统之间以加密签名方式发送 JSON 数据。理论上它们可以包含任何类型的数据，但最常用于在身份验证、会话处理和访问控制机制中传递关于用户的信息（“声明”）。

与传统的会话令牌（服务器保存状态）不同，服务器需要的所有数据都存储在客户端的 JWT 本身中。这使得 JWT 成为高度分布式网站的热门选择，在这些网站中，用户需要与多个后端服务器无缝交互。

### JWT 格式

JWT 由 3 部分组成，它们各自用点 `.` 分隔，如下所示：

- **头部（Header）**：包含令牌类型（通常为 JWT）和签名算法。
- **有效载荷（Payload）**：包含实际传输的数据内容。
- **签名（Signature）**：保护令牌的完整性。

JWT 的头部和载荷部分是*去除等号后的* base64url 编码的 JSON 对象。头部包含关于令牌本身的元数据，而载荷包含关于用户的实际“声明”。例如，您可以解码上面令牌中的载荷，以显示以下声明：

```json
{
    "iss": "portswigger",
    "exp": 1648037164,
    "name": "Carlos Montoya",
    "sub": "carlos",
    "role": "blog_author",
    "email": "carlos@carlos-montoya.net",
    "iat": 1516239022
}
```

在大多数情况下，任何能够访问令牌的人都可以轻松读取或修改这些数据。因此，任何基于 JWT 的机制的安全性都严重依赖于加密签名。

#### 头部

头部定义了令牌类型（通常为 `JWT`）和用于签名的算法。一个解码后的头部示例如下：

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

用于计算签名的主要算法有三种类型：

| 算法 | 描述 |
|-----------|-------------|
| HSxxx | 使用密钥和 SHA-xxx 的 HMAC。 |
| RSxxx 和 PSxxx | 使用 RSA 的公钥签名。 |
| ESxxx | 使用 ECDSA 的公钥签名。 |

还有多种[其他算法](https://www.iana.org/assignments/jose/jose.xhtml#web-signature-encryption-algorithms)可用于加密令牌（JWE），尽管这些不太常见。

#### 载荷

JWT 的载荷包含实际数据。一个示例载荷如下所示：

```json
{
  "username": "administrator",
  "is_admin": true,
  "iat": 1516239022,
  "exp": 1516242622
}
```

此 JWT 包含用户名和管理员状态，以及两个标准声明（`iat` 和 `exp`）。这些声明在 [RFC 7519](https://tools.ietf.org/html/rfc7519#section-4.1) 中定义，下表简要总结了它们：

| 声明 | 全称 | 描述 |
|-------|-----------|-------------|
| `iss` | 颁发者 | 颁发令牌的方的身份。 |
| `iat` | 颁发时间 | 令牌颁发时的 Unix 时间戳。 |
| `nbf` | 生效时间 | 令牌可被使用的最早日期的 Unix 时间戳。 |
| `exp` | 过期时间 | 令牌过期的 Unix 时间戳。 |

#### JWT 签名

颁发令牌的服务器通常通过对头部和载荷进行哈希来生成签名。在某些情况下，它们还会对生成的哈希进行加密。无论哪种方式，此过程都涉及一个秘密签名密钥。此机制为服务器提供了一种方式，以验证令牌中的数据自颁发以来未被篡改：

- 由于签名直接源自令牌的其余部分，更改头部或载荷的单个字节都会导致签名不匹配。
- 如果不知道服务器的秘密签名密钥，就不应该能够为给定的头部或载荷生成正确的签名。

> **提示：** 如果您想更好地理解 JWT 是如何构建的，可以使用 [`jwt.io`](https://www.jwt.io/) 上的调试器来试验任意令牌。
>
> [在 Burp Suite 中使用 JWT](https://portswigger.net/burp/documentation/desktop/testing-workflow/vulnerabilities/session-management/jwts)


### JWT vs JWS vs JWE

JWT 规范实际上非常有限。它只定义了一种将信息（“声明”）表示为可在两方之间传输的 JSON 对象的格式。在实践中，JWT 并不是真正作为独立实体使用的。JWT 规范由 JSON Web 签名（JWS）和 JSON Web 加密（JWE）规范扩展，这些规范定义了实际实现 JWT 的具体方式。

换句话说，JWT 通常是 JWS 或 JWE 令牌。当人们使用术语“JWT”时，他们几乎总是指 JWS 令牌。JWE 非常相似，只是令牌的实际内容是加密的而不仅仅是编码的。

> **注意：** 为简单起见，在本材料中，“JWT”主要指 JWS 令牌，尽管描述的一些漏洞也可能适用于 JWE 令牌。

## 什么是 JWT 攻击？

JWT 攻击涉及用户向服务器发送修改过的 JWT，以达到恶意目的。通常，此目的是通过冒充已经过身份验证的其他用户来绕过身份验证和访问控制。

## JWT 攻击的影响是什么？

JWT 攻击的影响通常很严重。如果攻击者能够创建具有任意值的自己的有效令牌，他们可能能够提升自己的权限或冒充其他用户，完全控制其账户。

## JWT 攻击的漏洞是如何产生的？

JWT 漏洞通常源于应用程序本身对 JWT 的处理存在缺陷。与 JWT 相关的各种规范在设计上相对灵活，允许网站开发人员自行决定许多实现细节。这可能导致他们即使在使用经过实战考验的库时也会意外引入漏洞。

这些实现缺陷通常意味着 JWT 的签名没有被正确验证。这使得攻击者能够通过令牌的载荷篡改传递给应用程序的值。即使签名被严格验证，它是否真正可信也在很大程度上取决于服务器的秘密密钥是否保持机密。如果此密钥以某种方式泄露，或者可以被猜测或暴力破解，攻击者就可以为任何任意令牌生成有效签名，从而破坏整个机制。

## 利用有缺陷的 JWT 签名验证

按照设计，服务器通常不存储有关它们颁发的 JWT 的任何信息。相反，每个令牌都是一个完全自包含的实体。这有几个优点，但也引入了一个根本性问题——服务器实际上不知道令牌的原始内容，甚至不知道原始签名是什么。因此，如果服务器没有正确验证签名，就没有什么可以阻止攻击者对令牌的其余部分进行任意更改。

例如，考虑一个包含以下声明的 JWT：

```json
{
    "username": "carlos",
    "isAdmin": false
}
```

如果服务器基于此 `username` 标识会话，修改其值可能使攻击者能够冒充其他已登录用户。同样，如果 `isAdmin` 值用于访问控制，这可能为权限提升提供一个简单的向量。

在最初的几个实验中，您将看到这些漏洞在现实应用程序中可能出现的一些示例。

### 接受任意签名

JWT 库通常提供一种验证令牌的方法和另一种仅解码令牌的方法。例如，Node.js 库 `jsonwebtoken` 有 `verify()` 和 `decode()`。

偶尔，开发人员会混淆这两种方法，只将传入的令牌传递给 `decode()` 方法。这实际上意味着应用程序根本不验证签名。

### 接受没有签名的令牌

除此之外，JWT 头部还包含一个 `alg` 参数。这告诉服务器用于签署令牌的算法，因此也告诉服务器在验证签名时需要使用的算法。

```json
{
    "alg": "HS256",
    "typ": "JWT"
}
```

这本质上是有缺陷的，因为服务器别无选择，只能隐式地信任来自令牌的用户可控输入，而在此刻，该输入根本没有被验证过。换句话说，攻击者可以直接影响服务器如何检查令牌是否可信。

JWT 可以使用一系列不同的算法进行签名，但也可以不签名。在这种情况下，`alg` 参数设置为 `none`，表示所谓的“不安全的 JWT”。由于这明显的危险性，服务器通常会拒绝没有签名的令牌。然而，由于这种过滤依赖于字符串解析，您有时可以使用经典的混淆技术（如混合大小写和意外编码，如 `noNe`）来绕过这些过滤器。

```json
{
    "alg": "none",
    "typ": "JWT"
}
```

然后重新对头部进行 Base64 编码，并移除签名，载荷部分仍需以尾随点结尾。

### ECDSA “心灵签名”

在 Java 版本 15 到 18 中发现了一个漏洞，在某些情况下它们无法正确验证 ECDSA 签名（[CVE-2022-21449](https://neilmadden.blog/2022/04/19/psychic-signatures-in-java/)，称为“心灵签名”）。如果使用这些易受攻击的版本之一解析使用 `ES256` 算法的 JWT，则可以通过篡改正文，然后将签名替换为以下值来完全绕过签名验证：

```txt
MAYCAQACAQA
```

结果得到如下所示的 JWT：

```txt
eyJhbGciOiJFUzI1NiIsInR5cCI6IkpXVCJ9.eyJhZG1pbiI6InRydWUifQ.MAYCAQACAQA
```

## 暴力破解密钥

某些签名算法，如 HS256（HMAC + SHA-256），使用任意的独立字符串作为密钥。就像密码一样，至关重要的是这个密钥不能被攻击者轻易猜测或暴力破解。否则，他们可能能够创建具有任何头部和载荷值的 JWT，然后使用该密钥以有效签名重新签署令牌。

在实现 JWT 应用程序时，开发人员有时会犯错误，比如忘记更改默认或占位符密钥。他们甚至可能复制粘贴在网上找到的代码片段，然后忘记更改作为示例提供的硬编码密钥。在这种情况下，攻击者使用[众所周知的密钥字典列表](https://github.com/wallarm/jwt-secrets/blob/master/jwt.secrets.list)暴力破解服务器密钥可能是轻而易举的。

### 使用 hashcat 暴力破解密钥

我们建议使用 hashcat 来暴力破解密钥。您可以[手动安装 hashcat](https://hashcat.net/wiki/doku.php?id=frequently_asked_questions#how_do_i_install_hashcat)，但它也已预装在 Kali Linux 中并准备就绪。

> **注意：** 如果您使用的是 Kali 的预构建 VirtualBox 镜像而不是裸机安装版本，则可能没有足够的内存分配来运行 hashcat。

您只需要来自目标服务器的有效签名 JWT 和一个[众所周知的密钥字典列表](https://github.com/wallarm/jwt-secrets/blob/master/jwt.secrets.list)。然后您可以运行以下命令，将 JWT 和字典列表作为参数传入：

```
hashcat -a 0 -m -D 1 16500 <jwt> <wordlist>
```
- `-a` 攻击模式默认 0
- `-m` hash 类型编号，对应 JWT 在 hashcat 中的编号
- `-D 1` 显式设置设备，避免出现设备内存分配不足的异常

Hashcat 使用字典列表中的每个密钥对 JWT 的头部和载荷进行签名，然后将生成的签名与服务器的原始签名进行比较。如果任何签名匹配，hashcat 将以以下格式输出识别的密钥，以及各种其他详细信息：

```
<jwt>:<identified-secret>
```

> **注意：** 如果您多次运行该命令，您需要包含 `--show` 标志以输出结果。

由于 hashcat 在您的本地机器上运行，并且不依赖于向服务器发送请求，因此即使使用巨大的字典列表，这个过程也非常快。

一旦您识别出密钥，您就可以使用它为任何您喜欢的 JWT 头部和载荷生成有效的签名。关于如何在 Burp Suite 中重新签署修改后的 JWT 的详细信息，请参阅[编辑 JWT](/burp/documentation/desktop/testing-workflow/vulnerabilities/session-management/jwts#editing-jwts)。

- 在 burp JWT 编辑器扩展栏中，选择新建对称密钥，选择使用指定秘密并粘贴秘密
    - 或手动 base64 编码秘密，生成随机秘密，替换其 json `"k"` 字段（`k` 字段即 base64 编码的秘密）
- 在重复器的 JWT 编辑标签，选择签名，选择之前新建的对称密钥

如果服务器使用了极其薄弱的密钥，甚至可能可以逐个字符地暴力破解，而不是使用字典列表。

#### 其他暴破工具

- 使用 [crackjwt.py](https://github.com/Sjord/jwtcrack) 脚本，该脚本只需 JWT 和字典文件。

- 使用 [jwt2john.py](https://github.com/Sjord/jwtcrack/blob/master/jwt2john.py) 脚本将 JWT 转换为 [John the Ripper](https://github.com/openwall/john) 可用的格式。然后可以使用 John 对密钥进行更高级的攻击。

    - 如果 JWT 很大，可能超过 John 支持的最大大小。可以通过增加 `/src/hmacSHA256_fmt_plug.c`（或其他 HMAC 格式的等效文件）中的 `SALT_LIMBS` 变量并重新编译 John 来解决，如以下 [GitHub issue](https://github.com/openwall/john/issues/1904) 中所述。

## JWT 头部参数注入

根据 JWS 规范，只有 `alg` 头部参数是强制性的。然而，在实践中，JWT 头部（也称为 JOSE 头部）通常包含其他几个参数。以下参数对攻击者特别感兴趣。

- `jwk`（JSON Web Key）—— 提供一个表示密钥的内嵌 JSON 对象。
- `jku`（JSON Web Key Set URL）—— 提供一个 URL，服务器可以从该 URL 获取包含正确密钥的密钥集。
- `kid`（Key ID）—— 提供一个 ID，在需要从多个密钥中选择时，服务器可以用它来识别正确的密钥。根据密钥的格式，这可能有匹配的 `kid` 参数。

如您所见，这些用户可控的参数各自告诉接收服务器在验证签名时应使用哪个密钥。在本节中，您将学习如何利用这些参数来注入使用您自己的任意密钥（而不是服务器密钥）签名的修改 JWT。

### 通过 jwk 参数注入自签名 JWT

[JSON Web 签名（JWS）标准](https://tools.ietf.org/html/rfc7515)（定义了 JWT 使用的头部和签名）描述了一个可选的 `jwk` 头部参数，服务器可以使用该参数将其公钥直接以 JWK 格式嵌入令牌中。

> **JWK：** JWK（JSON Web Key）是一种将密钥表示为 JSON 对象的标准化格式。

您可以在以下 JWT 头部中看到这样的示例：

```json
{
    "kid": "ed2Nf8sb-sD6ng0-scs5390g-fFD8sfxG",
    "typ": "JWT",
    "alg": "RS256",
    "jwk": {
        "kty": "RSA",
        "e": "AQAB",
        "kid": "ed2Nf8sb-sD6ng0-scs5390g-fFD8sfxG",
        "n": "yy1wpYmffgXBxhAUJzHHocCuJolwDqql75ZWuCQ_cb33K2vh9m"
    }
}
```

> **公钥和私钥：** 如果您不熟悉“公钥”和“私钥”这两个术语，我们已将其作为算法混淆攻击材料的一部分进行了介绍。更多信息，请参见"对称与非对称算法"小节

理想情况下，服务器应仅使用有限的公钥白名单来验证 JWT 签名。然而，配置错误的服务器有时会使用嵌入在 `jwk` 参数中的任何密钥。

您可以通过使用您自己的 RSA 私钥签署修改后的 JWT，然后将匹配的公钥嵌入 `jwk` 头部中来利用此行为。

虽然您可以手动在 Burp 中添加或修改 `jwk` 参数，但 [JWT Editor 扩展](https://portswigger.net/bappstore/26aaa5ded2f74beea19e2ed8345a93dd)提供了一个有用的功能来帮助您测试此漏洞：

1. 加载扩展后，在 Burp 的主标签栏中，转到 **JWT Editor Keys** 选项卡。
2. [生成一个新的 RSA 密钥](/burp/documentation/desktop/testing-workflow/vulnerabilities/session-management/jwts#adding-a-jwt-signing-key)。
3. 将包含 JWT 的请求发送到 Burp Repeater。
4. 在消息编辑器中，切换到扩展生成的 **JSON Web Token** 选项卡，并随意[修改](/burp/documentation/desktop/testing-workflow/vulnerabilities/session-management/jwts#editing-jwts)令牌的载荷。
5. 点击 **Attack**，然后选择 **Embedded JWK**。在提示时，选择您新生成的 RSA 密钥。
6. 发送请求以测试服务器如何响应。

您也可以通过自己添加 `jwk` 头部来手动执行此攻击。但是，您可能还需要更新 JWT 的 `kid` 头部参数以匹配嵌入密钥的 `kid`。扩展的内置攻击会为您处理此步骤。

其他工具：
- [jwk-node-jose.py](https://github.com/zi0Black/POC-CVE-2018-0114) 
- [jwt_tool](https://github.com/ticarpi/jwt_tool)。

### 通过 jku 参数注入自签名 JWT

某些服务器不是使用 `jwk` 头部参数直接嵌入公钥，而是允许您使用 `jku`（JWK Set URL）头部参数引用包含密钥的 JWK Set。在验证签名时，服务器会从此 URL 获取相关密钥。

> **JWK Set：** JWK Set 是一个 JSON 对象，包含一个表示不同密钥的 JWK 数组。您可以在下面看到这样的示例。

```json
{
    "keys": [
        {
            "kty": "RSA",
            "e": "AQAB",
            "kid": "75d0ef47-af89-47a9-9061-7c02a610d5ab",
            "n": "o-yy1wpYmffgXBxhAUJzHHocCuJolwDqql75ZWuCQ_cb33K2vh9mk6GPM9gNN4Y_qTVX67WhsN3JvaFYw-fhvsWQ"
        },
        {
            "kty": "RSA",
            "e": "AQAB",
            "kid": "d8fDFo-fS9-faS14a9-ASf99sa-7c1Ad5abA",
            "n": "fc3f-yy1wpYmffgXBxhAUJzHql79gNNQ_cb33HocCuJolwDqmk6GPM4Y_qTVX67WhsN3JvaFYw-dfg6DH-asAScw"
        }
    ]
}
```

这种 JWK Set 有时会通过标准端点（如 `/.well-known/jwks.json`）公开。

JWT 元数据段设置 jku 地址，并使用对应 RSA 密钥签名：

```json
{
    "alg": "RS256",
    "jku": "https://hacker.net/jku"
}
```
- 若 JKU 设置多个 RSA 公钥，在 JWT 中设置对应的 `kid` 字段，以从 JKU 列表中匹配对应公钥

更安全的网站只会从受信任的域获取密钥，但您有时可以利用 URL 解析差异来绕过此类过滤。我们在 SSRF 主题中介绍了一些此类示例。

### 通过 kid 参数注入自签名 JWT

服务器可能使用多个加密密钥来签署不同类型的数据，而不仅仅是 JWT。因此，JWT 的头部可能包含一个 `kid`（Key ID）参数，帮助服务器在验证签名时识别要使用的密钥。

验证密钥通常存储为 JWK Set。在这种情况下，服务器可能只需查找与令牌具有相同 `kid` 的 JWK。然而，JWS 规范没有为这个 ID 定义具体的结构——它只是开发人员选择的任意字符串。例如，他们可能使用 `kid` 参数检索数据库或文件系统中的特定条目。

如果此参数也容易受到路径遍历攻击，攻击者可能强制服务器使用文件系统中的任意文件作为验证密钥。

```json
{
    "kid": "../../path/to/file",
    "typ": "JWT",
    "alg": "HS256",
    "k": "asGsADas3421-dfh9DGN-AFDFDbasfd8-anfjkvc"
}
```

如果服务器还支持使用[对称算法](/web-security/jwt/algorithm-confusion#symmetric-vs-asymmetric-algorithms)签名的 JWT，这尤其危险。在这种情况下，攻击者可能将 `kid` 参数指向一个可预测的静态文件，然后使用与此文件内容匹配的密钥来签署 JWT。

理论上您可以使用任何文件来做到这一点，但最简单的方法之一是使用 `/dev/null`，它存在于大多数 Linux 系统上，或 `nul`（在 Windows 上）。由于这是一个空文件，读取它返回一个空字符串。因此，使用**空字符串**签署令牌将产生有效签名。

#### 命令/SQL 注入

如果服务器将其验证密钥存储在数据库中，`kid` 头部参数也可能是 SQL 注入攻击的潜在向量。

例如，攻击者可以将 SQL 载荷注入 `kid` 参数，以控制数据库返回的密钥：

```json
{
  "alg": "HS256",
  "typ": "JWT",
  "kid": "invalid-key' UNION SELECT 'attacker-controlled-key'--"
}
```

这允许攻击者强制应用程序使用已知密钥（例如“attacker-controlled-key”）进行验证，从而能够伪造有效令牌。

### 其他有趣的 JWT 头部参数

以下头部参数对攻击者也可能很有趣：

- `cty`（Content Type）—— 有时用于声明 JWT 载荷中内容的媒体类型。这通常从头部中省略，但底层解析库可能仍然支持它。如果您找到了绕过签名验证的方法，可以尝试注入 `cty` 头部将内容类型更改为 `text/xml` 或 `application/x-java-serialized-object`，这可能会为 [XXE] 和[反序列化]攻击启用新的向量。
- `x5c`（X.509 Certificate Chain）—— 有时用于传递用于数字签署 JWT 的密钥的 X.509 格式公钥证书或证书链。此头部参数可用于注入自签名证书，类似于上面讨论的 [`jwk` 头部注入](#通过-jwk-参数注入自签名-jwt)攻击。由于 X.509 格式及其扩展的复杂性，解析这些证书也可能引入漏洞。更多详情，请查看 [CVE-2017-2800](https://talosintelligence.com/vulnerability_reports/TALOS-2017-0293) 和 [CVE-2018-2633](https://mbechler.github.io/2018/01/20/Java-CVE-2018-2633)。

## JWT 算法混淆

即使服务器使用了您无法暴力破解的强密钥，您仍然可能通过使用开发人员未预料到的算法签署令牌来伪造有效的 JWT。这被称为算法混淆攻击。

## 如何防止 JWT 攻击

您可以通过采取以下高层措施来保护您自己的网站免受我们介绍的许多攻击：

- 使用最新的库来处理 JWT，并确保您的开发人员充分理解其工作原理以及任何安全影响。现代库使您更难无意中不安全地实现它们，但由于相关规范固有的灵活性，这并非万无一失。
- 确保您对接收到的任何 JWT 执行严格的签名验证，并考虑边缘情况，例如使用意外算法签名的 JWT。
- 为 `jku` 头部强制实施严格的主机白名单。
- 确保您不容易通过 `kid` 头部参数受到路径遍历或 SQL 注入攻击。

### JWT 处理的其他最佳实践

虽然不是严格必要的，但我们建议在您的应用程序中使用 JWT 时遵循以下最佳实践：

- 始终为您颁发的任何令牌设置过期日期。
- 尽可能避免在 URL 参数中发送令牌。
- 包含 `aud`（audience）声明（或类似内容）以指定令牌的预期接收者。这可以防止它被用于不同的网站。
- 使颁发服务器能够撤销令牌（例如在注销时）。
