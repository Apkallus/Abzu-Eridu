# 基于暂停的反同步攻击

看似安全的网站可能包含隐藏的反同步漏洞，这些漏洞只有在您请求中途暂停时才会暴露出来。

服务器通常配置有读取超时时间。如果在一定时间内没有收到更多数据，无论它们被告知预期有多少字节，它们都会将请求视为完成并发出响应。当服务器使请求超时但保持连接打开以供复用时，就会发生基于暂停的反同步漏洞。在合适的条件下，这种行为可以为服务器端和客户端反同步攻击提供替代向量。

> #### PortSwigger 研究
>
> 本节中的材料和实验基于 PortSwigger Research 的 [Browser-Powered Desync Attacks: A New Frontier in HTTP Request Smuggling](https://portswigger.net/research/browser-powered-desync-attacks)。

## 服务器端基于暂停的反同步

您可以使用基于暂停的技术来诱发类似 [CL.0](https://portswigger.net/web-security/request-smuggling/browser/cl-0) 的行为，从而为看似安全的网站构造服务器端请求走私攻击。

这依赖于以下条件：

- 前端服务器必须立即将请求的每个字节转发到后端，而不是等待收到完整请求。
- 前端服务器必须不（或可以被诱导不）在后端服务器之前使请求超时。
- 后端服务器必须在读取超时后保持连接打开以供复用。

为了演示此技术的工作原理，让我们看一个示例。以下是一个标准的 [CL.0 请求走私](https://portswigger.net/web-security/request-smuggling/browser/cl-0)探测：

```http
POST /example HTTP/1.1
Host: vulnerable-website.com
Connection: keep-alive
Content-Type: application/x-www-form-urlencoded
Content-Length: 34

GET /hopefully404 HTTP/1.1
Foo: x
```

考虑一下，如果我们向易受攻击的网站发送头部，但在发送消息体之前暂停，会发生什么。

1. 前端将头部转发到后端，然后继续等待 `Content-Length` 头承诺的剩余字节。
2. 一段时间后，后端超时并发送响应，即使它只消费了部分请求。此时，前端可能会或可能不会读取此响应并将其转发给我们。
3. 我们最终发送消息体，在此情况下它包含一个基本的请求走私前缀。
4. 前端服务器将此视为初始请求的延续，并通过同一连接将其转发到后端。
5. 后端服务器已经对初始请求做出了响应，因此它假定这些字节是另一个请求的开始。

在这一点上，我们已经有效地实现了 CL.0 反同步，用请求前缀投毒了前端/后端连接。

我们发现，当服务器自行生成响应而不是将请求传递给应用程序时，更容易受到攻击。

与 0.CL 的差异：
- 0.CL
    - 前端发送完整请求1后，得到后端的立即响应1
    - 后端保持连接打开，继续等待请求1的 CL
    - 前端发送请求2
    - 后端截断请求2的开头到请求1，剩余内容拆分为走私请求
- CL.0 
    - 前端发送部分请求1，继续等待客户端发送请求1的 CL
    - 后端超时返回响应1，将后续内容作为请求2
    - 前端收到后端的超时响应1，但仍将客户端的后续请求1发送到后端
    - 后端收到客户端的请求1后续，将其作为走私请求2

> #### PortSwigger 研究
>
> 我们的研究团队在广泛使用的 Apache HTTP Server 上发现了此漏洞，当执行从 `/example` 到 `/example/` 的服务器级重定向时，该服务器表现出这种行为。我们报告了此问题，并已在 2.4.53 版本中修复，因此如果您还没有更新，请务必更新。更多详情，请查看 PortSwigger Research 的 [Browser-Powered Desync Attacks: A New Frontier in HTTP Request Smuggling](https://portswigger.net/research/browser-powered-desync-attacks#pause)。

### 测试基于暂停的 CL.0 漏洞

可以使用 Burp Repeater 测试基于暂停的 CL.0 漏洞，但前提是前端服务器在生成超时响应后立即将其转发给您，但情况并非总是如此。我们建议使用 [Turbo Intruder](https://portswigger.net/bappstore/9abaa233088242e8be252cd4ff534988) 扩展，因为它允许您在请求中途暂停，然后无论是否收到响应都可以继续。

1. 在 Burp Repeater 中，创建一个 CL.0 请求走私探测，就像我们在上面示例中使用的那样，然后将其发送到 Turbo Intruder：

    ```http
    POST /example HTTP/1.1
    Host: vulnerable-website.com
    Connection: keep-alive
    Content-Type: application/x-www-form-urlencoded
    Content-Length: 34

    GET /hopefully404 HTTP/1.1
    Foo: x
    ```

2. 在 Turbo Intruder 的 Python 编辑器面板中，调整请求引擎配置以设置以下选项：

    ```python
    concurrentConnections=1
    requestsPerConnection=100
    pipeline=False
    ```

3. 将请求加入队列，向 `queue()` 接口添加以下参数：
   - `pauseMarker` —— 一个字符串列表，Turbo Intruder 将在这些字符串之后暂停。
   - `pauseTime` —— 暂停的持续时间，以毫秒为单位。

   例如，要在头部之后暂停 60 秒，将请求加入队列如下：

    ```python
    engine.queue(target.req, pauseMarker=['\r\n\r\n'], pauseTime=60000)
    ```
    - > 注意，若走私的请求包含请求体，需调整暂停字符序列以避免在走私请求体前暂停

4. 像往常一样将任意后续请求加入队列：

    ```python
    followUp = 'GET / HTTP/1.1\r\nHost: vulnerable-website.com\r\n\r\n'
    engine.queue(followUp)
    ```

5. 确保将所有响应记录到结果表中：

    ```python
    def handleResponse(req, interesting):
        table.add(req)
    ```

当您第一次开始攻击时，您不会在结果表中看到任何结果。然而，在指定的暂停持续时间之后，您应该会看到两个结果。如果对第二个请求的响应与您对走私前缀的预期相符（在此情况下为 404），这强烈表明反同步是成功的。

> **注意：** 除了使用 `pauseMarker` 基于字符串匹配来指定暂停之外，您还可以使用 `pauseBefore` 参数来指定偏移量。例如，您可以通过指定与 `Content-Length` 相反的偏移量（`pauseBefore=-34`）在消息体之前暂停。

## 客户端基于暂停的反同步

理论上，可能可以执行基于暂停的 CL.0 反同步的客户端变体。不幸的是，我们还没有找到一种可靠的方法让浏览器在请求中途暂停。然而，有一种可能的变通方法——主动 MITM 攻击。

TLS 提供的加密可能会阻止 MITM 读取传输中的流量，但没有什么可以阻止他们延迟从浏览器到 Web 服务器的 TCP 数据包。通过简单地延迟最终数据包直到 Web 服务器发出响应，您可能能够使浏览器的连接失同步。

此攻击的流程与任何其他客户端反同步攻击类似。用户访问一个恶意网站，该网站导致其浏览器向目标站点发出一系列跨域请求。在这种情况下，您需要故意填充第一个请求，使操作系统将其拆分为多个 TCP 数据包。由于您可以控制填充，您可以填充请求直到最终数据包具有不同的大小，以便您可以确定要延迟哪一个。

关于这在实践中如何实现的示例，请参见 [Browser-Powered Desync Attacks: A New Frontier in HTTP Request Smuggling](https://portswigger.net/research/browser-powered-desync-attacks#mitm)。
