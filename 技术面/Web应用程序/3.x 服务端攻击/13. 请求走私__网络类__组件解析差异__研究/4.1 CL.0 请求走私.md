# CL.0 请求走私

请求走私漏洞是由链式系统在确定每个请求的开始和结束位置时的差异引起的。这通常是由于[头部解析不一致](https://portswigger.net/web-security/request-smuggling#how-do-http-request-smuggling-vulnerabilities-arise)，导致一个服务器使用请求的 `Content-Length`，而另一个服务器将消息视为分块传输。然而，可以在不依赖这两个问题的情况下执行许多相同的攻击。

在某些情况下，服务器可以被说服忽略 `Content-Length` 头，这意味着它们假设每个请求在头部结束处结束。这实际上等同于将 `Content-Length` 视为 `0`。

如果后端服务器表现出这种行为，但前端仍然使用 `Content-Length` 头来确定请求的结束位置，您可能可以利用这种差异进行 HTTP 请求走私。我们决定将其称为“CL.0”漏洞。

## 测试 CL.0 漏洞

要探测 CL.0 漏洞，首先发送一个在其消息体中包含另一个部分请求的请求，然后发送一个正常的后续请求。然后您可以检查后续请求的响应是否受到走私前缀的影响。

在以下示例中，对首页的后续请求收到了 404 响应。这强烈表明后端服务器将 `POST` 请求的消息体（`GET /hopefully404...`）解释为另一个请求的开始。

```http
POST /vulnerable-endpoint HTTP/1.1
Host: vulnerable-website.com
Connection: keep-alive
Content-Type: application/x-www-form-urlencoded
Content-Length: 34

GET /hopefully404 HTTP/1.1
Foo: xGET / HTTP/1.1
Host: vulnerable-website.com
```

```http
HTTP/1.1 200 OK

HTTP/1.1 404 Not Found
```

关键要注意的是，我们没有任何方式篡改头部——请求的长度由一个完全正常、准确的 `Content-Length` 头指定。

要使用 Burp Repeater 自行尝试：

1. 创建一个包含设置请求的选项卡和另一个包含任意后续请求的选项卡。
2. 按正确顺序将两个选项卡添加到一个组中。
3. 使用 **Send** 按钮旁边的下拉菜单，将发送模式更改为 **Send group in sequence (single connection)**。
4. 将 `Connection` 头更改为 `keep-alive`。
5. 发送序列并检查响应。

在实际中，我们主要是在那些根本不期望 `POST` 请求的端点上观察到这种行为，因此它们隐式地假设没有请求具有消息体。触发服务器级重定向的端点和静态文件的请求是主要候选。

## 诱发 CL.0 行为

如果您找不到任何看似易受攻击的端点，可以尝试诱发这种行为。

当请求的头部触发服务器错误时，某些服务器会发出错误响应，但不消耗套接字上的请求体。如果它们之后不关闭连接，这可以提供一种替代的 CL.0 反同步向量。

您也可以尝试使用带有混淆 `Content-Length` 头的 `GET` 请求。如果您能够对后端隐藏此头但不能对前端隐藏，这也可能导致反同步。我们在讨论 TE.TE 请求走私时介绍了一些[头部混淆技术](https://portswigger.net/web-security/request-smuggling#te-te-behavior-obfuscating-the-te-header)。

## H2.0 漏洞

将 [HTTP/2 请求降级为 HTTP/1](https://portswigger.net/web-security/request-smuggling/advanced/http2-downgrading) 的网站，如果后端服务器忽略了降级后请求的 `Content-Length` 头，则可能存在等效的“H2.0”问题。
