# HTTP 请求隧道

我们介绍过的许多请求走私攻击之所以可能，是因为前端和后端之间的同一连接处理了多个请求。虽然某些服务器会为任何请求复用连接，但其他服务器则有更严格的策略。

例如，某些服务器只允许来自同一 IP 地址或同一客户端的请求复用连接。其他服务器则根本不复用连接，这限制了您通过经典请求走私所能达到的效果，因为您没有明显的方式来影响其他用户的流量。

虽然您无法投毒套接字来干扰其他用户的请求，但您仍然可以发送单个请求，该请求将从后端引出两个响应。这可能使您能够将请求及其匹配的响应完全隐藏在前端之外。

您可以使用此技术绕过前端安全措施，否则这些措施可能会阻止您发送某些请求。事实上，即使是专门为防止请求走私攻击而设计的某些机制，也无法阻止请求隧道。

以这种方式向后端隧道传输请求提供了一种更有限形式的请求走私，但在合适的人手中仍然可能导致高严重性的漏洞利用。

## 使用 HTTP/2 进行请求隧道

请求隧道在 HTTP/1 和 HTTP/2 中都是可行的，但在仅支持 HTTP/1 的环境中检测起来要困难得多。由于 HTTP/1 中持久连接（`keep-alive`）的工作方式，即使您确实收到了两个响应，这也不一定确认请求已成功走私。

另一方面，在 HTTP/2 中，每个“流”应该只包含一个请求和响应。如果您收到一个 HTTP/2 响应，其消息体中似乎包含一个 HTTP/1 响应，那么您可以确信您已成功隧道传输了第二个请求。

## 通过 HTTP/2 请求隧道泄露内部头部

当请求隧道是您唯一的选择时，您将无法使用之前小节中介绍的技术来泄露内部头部，但 HTTP/2 降级提供了一种替代解决方案。

您可能可以诱使前端将内部头部附加到将在后端成为消息体参数的内容中。假设我们发送一个如下所示的请求：

**前端（HTTP/2）头部：**

- `:method`: `POST`
- `:path`: `/comment`
- `:authority`: `vulnerable-website.com`
- `content-type`: `application/x-www-form-urlencoded`
- `foo`:
  ```
  bar\r\n
  Content-Length: 200\r\n
  \r\n
  comment=
  ```
- **消息体**: `x=1`

在这种情况下，前端和后端都认为只有一个请求。有趣的是，它们可以被诱导在对头部结束位置的判断上产生分歧。

前端将我们注入的所有内容视为头部的一部分，因此在尾随的 `comment=` 字符串之后添加任何新头部。另一方面，后端看到 `\r\n\r\n` 序列，并认为这是头部的结束。`comment=` 字符串以及当前请求的内部头部被视为消息体的一部分。结果是一个 `comment` 参数，其值为内部头部。

```http
POST /comment HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 200

comment=X-Internal-Header: secretContent-Length: 3
x=1
```

## 盲请求隧道

某些前端服务器会读取它们从后端接收的所有数据。这意味着如果您成功隧道传输了一个请求，它们可能会将两个响应都转发给客户端，隧道请求的响应嵌套在主响应的消息体中。

其他前端服务器只读取响应 `Content-Length` 头中指定的字节数，因此只有第一个响应被转发给客户端。这导致了盲请求隧道漏洞，因为您将无法看到对隧道请求的响应。

## 使用 HEAD 进行非盲请求隧道

盲请求隧道可能难以利用，但您有时可以通过使用 `HEAD` 请求使这些漏洞变为非盲的。

对 `HEAD` 请求的响应通常包含一个 `content-length` 头，尽管它们本身没有消息体。这通常指的是对同一端点的 `GET` 请求将返回的资源长度。某些前端服务器未能考虑到这一点，并尝试读取头中指定的字节数。如果您成功将请求隧道传输通过这样做的后端服务器，此行为可能导致它过度读取来自后端的响应。因此，您收到的响应可能包含对隧道请求的响应的开头部分字节。

**请求头部：**

- `:method`: `HEAD`
- `:path`: `/example`
- `:authority`: `vulnerable-website.com`
- `foo`:
  ```
  bar
  
  GET /tunnelled HTTP/1.1
  Host: vulnerable-website.com
  X: x
  ```

**响应头部：**

- `:status`: `200`
- `content-type`: `text/html`
- `content-length`: `131`

**响应体：**

```http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 4286

<!DOCTYPE html>
<h1>Tunnelled</h1>
<p>This is a tunnelled respo
```

由于您实际上是在混合来自 `HEAD` 响应的 `content-length` 头和另一个响应的消息体，成功使用此技术需要一些平衡。

如果您发送 `HEAD` 请求的端点返回的资源比您试图读取的隧道响应短，它可能会在您看到任何有趣的内容之前被截断，如上面的示例所示。另一方面，如果返回的 `content-length` 比您的隧道响应长，您很可能会遇到超时，因为前端服务器会等待从后端接收额外的字节。

幸运的是，通过一些反复试验，您通常可以使用以下解决方案之一克服这些问题：

- 将您的 `HEAD` 请求指向一个不同的端点，该端点根据需要返回更长或更短的资源。
- 如果资源太短，在主 `HEAD` 请求中使用反射输入来注入任意填充字符。即使您实际上不会看到您的输入被反射，返回的 `content-length` 仍会相应增加。
- 如果资源太长，在隧道请求中使用反射输入来注入任意字符，以便隧道响应的长度匹配或超过预期内容的长度。

寻找反射端点，并将前端重写头部放入走私 POST 请求体参数的技巧仍可用。

## 通过 HTTP/2 请求隧道进行 Web 缓存投毒

尽管请求隧道通常比经典请求走私更有限，但有时您仍然可以构造高严重性的攻击。例如，您可以将我们迄今为止介绍的请求隧道技术结合起来，形成一种超强形式的 Web 缓存投毒。

通过非盲请求隧道，您可以有效地混合搭配来自一个响应的头部和另一个响应的消息体。如果消息体中的响应反射了未编码的用户输入，您可能能够在浏览器通常不会执行代码的上下文中利用此行为进行反射型 XSS。

例如，以下响应包含未编码的、攻击者可控制的输入：

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "name" : "test<script>alert(1)</script>" }
[etc.]
```

单独来看，这相对无害。`Content-Type` 意味着浏览器会将此载荷简单地解释为 JSON。但考虑一下如果您将请求隧道传输到后端会发生什么。此响应将出现在另一个响应的消息体内部，实际上继承了其头部，包括 `content-type`。

**响应头部：**

- `:status`: `200`
- `content-type`: `text/html`
- `content-length`: `174`

**响应体：**

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "name" : "test<script>alert(1)</script>" }
[etc.]
```

由于缓存发生在前端，缓存也可能被诱骗将这些混合响应提供给其他用户。

尝试各种走私设置点，直到请求的缓存键恰巧与目标资源相同。例如，若伪协议的两个字段均可设置走私点 `:method` `:path`，应当分别尝试是否被缓存。根据前端服务器的降级方式，虽然发送到后端的请求相同，但被前端缓存服务器视为缓存键不同
