# HTTP 请求走私

在本节中，我们将解释 HTTP 请求走私攻击，并描述常见的请求走私漏洞是如何产生的。

## 什么是 HTTP 请求走私？

HTTP 请求走私是一种干扰网站处理从一个或多个用户接收的 HTTP 请求序列方式的技术。请求走私漏洞通常性质严重，允许攻击者绕过安全控制、未经授权访问敏感数据，并直接危害其他应用程序用户。

请求走私主要与 HTTP/1 请求相关。然而，支持 HTTP/2 的网站也可能存在漏洞，具体取决于其后端架构。

## HTTP 请求走私攻击中发生了什么？

当今的 Web 应用程序通常在用户和最终应用程序逻辑之间使用 HTTP 服务器链。用户将请求发送到前端服务器（有时称为负载均衡器或反向代理），该服务器将请求转发到一个或多个后端服务器。这种架构在现代基于云的应用程序中越来越普遍，并且在某些情况下不可避免。

当前端服务器将 HTTP 请求转发到后端服务器时，它通常通过相同的后端网络连接发送多个请求，因为这更加高效且性能更好。协议非常简单；HTTP 请求一个接一个地发送，接收服务器必须确定一个请求在哪里结束，下一个请求在哪里开始：

在这种情况下，前端和后端系统就请求之间的边界达成一致至关重要。否则，攻击者可能能够发送一个歧义请求，被前端和后端系统以不同方式解释

在这里，攻击者导致其前端请求的一部分被后端服务器解释为下一个请求的开始。它实际上被附加到下一个请求之前，因此可以干扰应用程序处理该请求的方式。这就是请求走私攻击（失同步攻击），它可能产生毁灭性的后果。

## HTTP 请求走私漏洞是如何产生的？

大多数 HTTP 请求走私漏洞的产生是因为 HTTP/1 规范提供了两种不同的方式来指定请求的结束位置：`Content-Length` 头和 `Transfer-Encoding` 头。

`Content-Length` 头很简单：它以字节为单位指定消息体的长度。例如：

```http
POST /search HTTP/1.1
Host: normal-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 11

q=smuggling
```

`Transfer-Encoding` 头可用于指定消息体使用分块编码。这意味着消息体包含一个或多个数据块。每个块由块大小（以字节为单位，以**十六进制**表示）、换行符和块内容组成。消息以大小为 0 的块终止。例如：

```http
POST /search HTTP/1.1
Host: normal-website.com
Content-Type: application/x-www-form-urlencoded
Transfer-Encoding: chunked

b
q=smuggling
0
```

> **注意：** 许多安全测试人员不知道分块编码可以在 HTTP 请求中使用，原因有二：
>
> - Burp Suite 会自动解包分块编码，使消息更易于查看和编辑。
> - 浏览器通常不会在请求中使用分块编码，通常仅在服务器响应中看到。

由于 HTTP/1 规范提供了两种不同的方法来指定 HTTP 消息的长度，因此单个消息可能同时使用这两种方法，从而使它们相互冲突。规范试图通过规定如果同时存在 `Content-Length` 和 `Transfer-Encoding` 头，则应忽略 `Content-Length` 头来防止此问题。当只有一台服务器时，这可能足以避免歧义，但当两台或多台服务器串联时则不然。在这种情况下，可能因两个原因出现问题：

- 某些服务器不支持请求中的 `Transfer-Encoding` 头。
- 某些支持 `Transfer-Encoding` 头的服务器可以通过某种方式混淆头来诱导其不处理它。

如果前端和后端服务器对（可能被混淆的）`Transfer-Encoding` 头的行为不同，那么它们可能会对连续请求之间的边界产生分歧，从而导致请求走私漏洞。

> **注意：** 端到端使用 HTTP/2 的网站天生免疫请求走私攻击。由于 HTTP/2 规范引入了一种单一、健壮的机制来指定请求的长度，攻击者无法引入所需的歧义。
>
> 然而，许多网站有一个支持 HTTP/2 的前端服务器，但将其部署在仅支持 HTTP/1 的后端基础设施之前。这意味着前端实际上必须将其接收到的请求转换为 HTTP/1。这个过程称为 HTTP 降级。更多信息，请参见[高级请求走私]小节

## 如何执行 HTTP 请求走私攻击

经典的请求走私攻击涉及将 `Content-Length` 头和 `Transfer-Encoding` 头都放入单个 HTTP/1 请求中，并操纵它们以使前端和后端服务器以不同方式处理请求。具体方式取决于两台服务器的行为：

- CL.TE：前端服务器使用 `Content-Length` 头，后端服务器使用 `Transfer-Encoding` 头。
- TE.CL：前端服务器使用 `Transfer-Encoding` 头，后端服务器使用 `Content-Length` 头。
- TE.TE：前端和后端服务器都支持 `Transfer-Encoding` 头，但可以通过某种方式混淆头来诱导其中一个服务器不处理它。

> **注意：** 这些技术只能使用 HTTP/1 请求实现。包括 Burp 在内的浏览器和其他客户端默认使用 HTTP/2 与在 TLS 握手期间明确通告支持 HTTP/2 的服务器通信。
>
> 因此，在测试支持 HTTP/2 的站点时，您需要手动在 Burp Repeater 中切换协议。您可以从 **Inspector** 面板的 **Request attributes** 部分执行此操作。

### CL.TE 漏洞

这里，前端服务器使用 `Content-Length` 头，后端服务器使用 `Transfer-Encoding` 头。我们可以如下执行一个简单的 HTTP 请求走私攻击：

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED
```

前端服务器处理 `Content-Length` 头，并确定请求体为 13 字节，直到 `SMUGGLED` 结束。此请求被转发到后端服务器。

后端服务器处理 `Transfer-Encoding` 头，因此将消息体视为使用分块编码。它处理第一个块，该块声明长度为零，因此被视为终止请求。以下字节 `SMUGGLED` 未被处理，后端服务器将把这些字节视为序列中下一个请求的开始。

CL.TE 载荷构造技巧
- 构建被走私的后端组件 TE 型载荷
    - 截断走私：
        ```http
        Transfer-Encoding: chunked
        Content-Length: 26

        0

        GPOST / HTTP/1.1
        X: 
        ```
        - 请求体中的 `0\r\n\r\n` 之后设置载荷

- 更新作为载体的前端 CL 长度
    - 全长度

### TE.CL 漏洞

这里，前端服务器使用 `Transfer-Encoding` 头，后端服务器使用 `Content-Length` 头。我们可以如下执行一个简单的 HTTP 请求走私攻击：

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 3
Transfer-Encoding: chunked

8
SMUGGLED
0


```

> **注意：** 要使用 Burp Repeater 发送此请求，您首先需要转到 Repeater 菜单并确保取消选中“Update Content-Length”选项。
>
> 您需要在最后的 `0` 之后包含尾随序列 `\r\n\r\n` 作为结尾。

前端服务器处理 `Transfer-Encoding` 头，因此将消息体视为使用分块编码。它处理第一个块，该块声明长度为 8 字节，直到 `SMUGGLED` 之后的行开始。它处理第二个块，该块声明长度为零，因此被视为终止请求。此请求被转发到后端服务器。

后端服务器处理 `Content-Length` 头，并确定请求体为 3 字节，直到 `8` 之后的行开始。以下以 `SMUGGLED` 开头的字节未被处理，后端服务器将把这些字节视为序列中下一个请求的开始。

TE.CL 载荷构造技巧
- 构建被走私的后端组件 CL 型载荷
    - 截断走私，被走私请求：

        ```http
        Transfer-Encoding: chunked
        Content-Length: 4

        2e
        GPOST / HTTP/1.1
        Content-Length: 14

        body: 
        0


        ```
        - 包含前端的 TE 的结尾序列 `0\r\n\r\n`，但无法作为常规头部。于是将其移入请求体，并且之后被走私攻击的请求将包含在此请求体中
        - 长度至少被走私载荷长度+1，以在后端服务器缓存中等待走私。示例被走私的请求体长度13，设置14


- 更新作为载体的前端 TE 长度

### TE.TE 行为：混淆 TE 头

这里，前端和后端服务器都支持 `Transfer-Encoding` 头，但可以通过某种方式混淆头来诱导其中一个服务器不处理它。

可能有无数种方式混淆 `Transfer-Encoding` 头。例如：

```http
Transfer-Encoding: xchunked

Transfer-Encoding[space]: chunked

Transfer-Encoding: chunked
Transfer-Encoding: x

Transfer-Encoding:[tab]chunked

[space]Transfer-Encoding: chunked

X: X[\n]Transfer-Encoding: chunked

Transfer-Encoding
: chunked
```

这些技术都涉及对 HTTP 规范的微妙偏离。实现协议规范的真实代码很少完全精确地遵循它，不同的实现容忍规范的不同变体是很常见的。要发现 TE.TE 漏洞，有必要找到 `Transfer-Encoding` 头的某种变体，使得只有前端或后端服务器之一处理它，而另一个服务器忽略它。

根据是前端还是后端服务器可以被诱导不处理混淆的 `Transfer-Encoding` 头，攻击的其余部分将采取与已描述的 CL.TE 或 TE.CL 漏洞相同的形式。

## 浏览器驱动的请求走私

到目前为止，您学到的请求走私技术依赖于使用专用黑客工具（如 Burp Repeater）发送故意格式错误的请求。实际上，可以使用完全与浏览器兼容的请求执行相同的攻击，这些请求使用完全正常的 `Content-Length` 头使两台服务器失去同步。

这甚至使您能够发起这些攻击的客户端变体，诱使受害者的浏览器投毒其与易受攻击网站之间的连接。这不仅将单服务器站点暴露于请求走私式攻击，甚至使您能够攻击您无法直接访问的站点。查看学习材料和 lab 了解如何操作。

## 如何防止 HTTP 请求走私漏洞

HTTP 请求走私漏洞产生于前端服务器和后端服务器使用不同机制确定请求之间边界的情况。这可能是由于 HTTP/1 服务器是使用 `Content-Length` 头还是分块传输编码来确定每个请求的结束位置之间的差异所致。在 HTTP/2 环境中，为后端[降级 HTTP/2 请求](/web-security/request-smuggling/advanced/http2-downgrading)的常见做法也充满问题，并启用或简化了许多额外的攻击。

为防止 HTTP 请求走私漏洞，我们建议以下高层措施：

- 尽可能端到端使用 HTTP/2 并禁用 HTTP 降级。HTTP/2 使用健壮的机制来确定请求的长度，当端到端使用时，天生受到保护免受请求走私攻击。如果无法避免 HTTP 降级，请确保根据 HTTP/1.1 规范验证重写的请求。例如，拒绝包含头中换行、头名称中冒号以及请求方法中空格的请求。

- 使前端服务器规范化歧义请求，并使后端服务器拒绝任何仍然歧义的请求，同时关闭 TCP 连接。

- 永远不要假设请求不会有消息体。这是 CL.0 和客户端反同步漏洞的根本原因。

- 在处理请求时，如果触发了服务器级异常，默认丢弃连接。

- 如果通过转发代理路由流量，请尽可能启用上游 HTTP/2。

正如我们在学习材料中所示，禁用后端连接的复用将有助于缓解某些类型的攻击，但这仍然不能保护您免受[请求隧道]攻击。
