# Web 缓存欺骗 —— 寻找源服务器忽略，而缓存服务器接受的格式

Web 缓存欺骗是一种漏洞，它使攻击者能够诱骗 Web 缓存存储敏感的动态内容。该漏洞源于缓存服务器与源服务器在处理请求时的差异。

在 Web 缓存欺骗攻击中，攻击者诱使受害者访问恶意 URL，诱导受害者的浏览器发出对敏感内容的模糊请求。缓存将请求误解为对静态资源的请求，并存储响应。随后，攻击者可以通过请求相同的 URL 来获取缓存的响应，从而未经授权访问私人信息。

> **注意**
> 区分 Web 缓存欺骗与 Web 缓存投毒很重要。虽然两者都利用缓存机制，但方式不同：
> - Web 缓存投毒操纵缓存键，将恶意内容注入缓存的响应中，然后提供给其他用户。
> - Web 缓存欺骗利用缓存规则，诱骗缓存存储敏感或私有内容，攻击者随后可访问这些内容。
> 
> 有关 Web 缓存投毒的更多详细信息，请参阅我们的 [Web 缓存投毒](https://portswigger.net/web-security/web-cache-poisoning) Academy 主题。

## Web 缓存

Web 缓存是位于源服务器和用户之间的系统。当客户端请求静态资源时，请求首先被定向到缓存。如果缓存中没有该资源的副本（即缓存未命中），请求将被转发到源服务器，源服务器处理并响应请求。响应在发送给用户之前先发送到缓存。缓存使用预配置的规则集来决定是否存储响应。

当将来再次请求相同的静态资源时，缓存会直接将存储的响应副本提供给用户（即缓存命中）。

![缓存行为 Web 缓存欺骗](https://portswigger.net/web-security/images/caching.svg)

缓存已成为交付 Web 内容的一个常见且关键的方面，尤其是随着内容分发网络（CDN）的广泛使用。CDN 使用缓存将内容副本存储在全球分布的服务器上，通过从离用户最近的服务器提供内容来加快交付速度，通过最小化数据传输距离来减少加载时间。

### 缓存键

当缓存收到 HTTP 请求时，它必须决定是否有缓存的响应可以直接提供，还是需要将请求转发到源服务器。缓存通过从 HTTP 请求的元素生成一个“缓存键”来做出此决定。通常，这包括 URL 路径和查询参数，但也可能包括头、内容类型等各种其他元素。

如果传入请求的缓存键与先前请求的缓存键匹配，缓存认为它们是等效的，并提供缓存的响应副本。

> **注意**
> 要了解如何操纵缓存键将恶意内容注入缓存，请参阅我们的 [Web 缓存投毒](https://portswigger.net/web-security/web-cache-poisoning) Academy 主题。

### 缓存规则

缓存规则决定了哪些内容可以被缓存以及缓存多长时间。缓存规则通常设置为存储静态资源，这些资源通常不经常更改，并且在多个页面中重复使用。动态内容不会被缓存，因为它更可能包含敏感信息，确保用户直接从服务器获取最新数据。

Web 缓存欺骗攻击利用缓存规则的适用方式，因此了解一些不同类型的规则很重要，特别是那些基于请求 URL 路径中定义字符串的规则。例如：

- 静态文件**扩展名**规则——这些规则匹配所请求资源的文件扩展名，例如样式表的 `.css` 或 JavaScript 文件的 `.js`。
- 静态**目录**规则——这些规则匹配所有以特定前缀开头的 URL 路径。它们通常用于定位只包含静态资源的特定目录，例如 `/static` 或 `/assets`。
- **文件名**规则——这些规则匹配特定文件名，以定位 Web 操作普遍需要且很少更改的文件，例如 `robots.txt` 和 `favicon.ico`。

缓存还可能基于其他标准实现自定义规则，例如 URL 参数或动态分析。

## 构造 Web 缓存欺骗攻击

一般而言，构造基本的 Web 缓存欺骗攻击涉及以下步骤（寻找敏感信息端点，识别 URL 解析差异，将敏感信息 URL 构造为可被缓存的格式）：

1. 识别返回包含敏感信息的动态响应的目标端点。在 Burp 中检查响应，因为某些敏感信息可能在渲染的页面上不可见。重点关注支持 `GET`、`HEAD` 或 `OPTIONS` 方法的端点，因为改变源服务器状态的请求通常不会被缓存。
2. 识别缓存和源服务器在解析 URL 路径方面的差异。这种差异可能体现在它们如何：
  - 将 URL 映射到资源。
  - 处理分隔符字符。
  - 规范化路径。
3. 构造一个恶意 URL，利用差异诱骗缓存存储动态响应。当受害者访问该 URL 时，他们的响应被存储在缓存中。然后，你可以使用 Burp 向同一 URL 发送请求，以获取包含受害者数据的缓存响应。避免直接在浏览器中执行此操作，因为某些应用程序会重定向没有会话的用户或使本地数据失效，这可能会掩盖漏洞。

我们将探讨几种构造 Web 缓存欺骗攻击的不同方法。

### 使用缓存破坏器

在测试差异和构造 Web 缓存欺骗漏洞利用时，请确保你发送的每个请求都具有不同的缓存键。否则，你可能会收到缓存的响应，这会影响测试结果。

由于 URL 路径和任何查询参数通常都包含在缓存键中，你可以通过向路径添加查询字符串并在每次发送请求时更改它来更改键。使用 Param Miner 扩展自动执行此过程。为此，安装扩展后，点击顶层 **Param miner > Settings** 菜单，然后选择 **Add dynamic cachebuster**。Burp 现在会在你发出的每个请求中添加一个唯一的查询字符串。你可以在 **Logger** 选项卡中查看添加的查询字符串。

### 检测缓存响应

在测试期间，能够识别缓存响应至关重要。为此，查看响应头和响应时间。

各种响应头可能表明响应已被缓存。例如：

- `X-Cache` 头提供有关响应是否来自缓存的信息。典型值包括：
  - `X-Cache: hit` —— 响应来自缓存。
  - `X-Cache: miss` —— 缓存中没有请求键对应的响应，因此从源服务器获取。在大多数情况下，响应随后被缓存。要确认，再次发送请求，查看值是否更新为 hit。
  - `X-Cache: dynamic` —— 源服务器动态生成了内容。通常这意味着响应不适合缓存。
  - `X-Cache: refresh` —— 缓存内容已过期，需要刷新或重新验证。
- `Cache-Control` 头可能包含指示缓存的指令，例如带有大于 `0` 的 `max-age` 的 `public`。注意，这仅表明资源可缓存，并不总是意味着它已被缓存，因为缓存有时会覆盖此头。

如果你注意到同一请求的响应时间有很大差异，这也可能表明较快的响应来自缓存。

## 利用静态扩展缓存规则

缓存规则通常通过匹配常见的文件扩展名（如 `.css` 或 `.js`）来定位静态资源。这是大多数 CDN 的默认行为。

如果缓存和源服务器在如何将 URL 路径映射到资源或使用分隔符方面存在差异，攻击者可能能够构造一个带有静态扩展名的动态资源请求，该扩展名被源服务器忽略但被缓存视为静态。

### 路径映射差异

URL 路径映射是将 URL 路径与服务器上的资源（如文件、脚本或命令执行）相关联的过程。不同框架和技术使用多种不同的映射风格。两种常见风格是传统 URL 映射和 RESTful URL 映射。

传统 URL 映射表示文件系统上资源的直接路径。典型示例如下：

`http://example.com/path/in/filesystem/resource.html`

- `http://example.com` 指向服务器。
- `/path/in/filesystem/` 表示服务器文件系统中的目录路径。
- `resource.html` 是正在访问的特定文件。

相比之下，REST 风格的 URL 不直接匹配物理文件结构。它们将文件路径抽象为 API 的逻辑部分：

`http://example.com/path/resource/param1/param2`

- `http://example.com` 指向服务器。
- `/path/resource/` 是表示资源的端点。
- `param1` 和 `param2` 是服务器用于处理请求的路径参数。

缓存和源服务器在将 URL 路径映射到资源方式上的差异可能导致 Web 缓存欺骗漏洞。考虑以下示例：

`http://example.com/user/123/profile/wcd.css`

- 使用 REST 风格 URL 映射的源服务器可能将此解释为对 `/user/123/profile` 端点的请求，并返回用户 `123` 的个人信息，忽略 `wcd.css` 作为非重要参数。
- 使用传统 URL 映射的缓存可能将其视为对位于 `/user/123` 下 `/profile` 目录中名为 `wcd.css` 的文件的请求。它将 URL 路径解释为 `/user/123/profile/wcd.css`。如果缓存配置为存储路径以 `.css` 结尾的请求的响应，它会将个人信息作为 CSS 文件缓存并提供。

### 利用路径映射差异

要测试源服务器如何将 URL 路径映射到资源，在目标端点的 URL 中添加一个任意路径段。如果响应仍然包含与基础响应相同的敏感数据，则表明源服务器抽象了 URL 路径并忽略了添加的段。例如，如果将 `/api/orders/123` 修改为 `/api/orders/123/foo` 仍然返回订单信息，就是这种情况。

要测试缓存如何将 URL 路径映射到资源，你需要通过添加静态扩展名来修改路径以尝试匹配缓存规则。例如，将 `/api/orders/123/foo` 更新为 `/api/orders/123/foo.js`。如果响应被缓存，这表明：

- 缓存解释完整的 URL 路径及其静态扩展名。
- 存在缓存规则来存储以 `.js` 结尾的请求的响应。

缓存可能具有基于特定静态扩展名的规则。尝试一系列扩展名，包括 `.css`、`.ico` 和 `.exe`。

然后你可以构造一个 URL，返回动态响应并被缓存。注意，此攻击仅限于你测试的特定端点，因为源服务器通常对不同的端点具有不同的抽象规则。

> **注意**
> Burp Scanner 在审计期间会自动检测由路径映射差异引起的 Web 缓存欺骗漏洞。你也可以使用 [Web Cache Deception Scanner](https://portswigger.net/bappstore/7c1ca94a61474d9e897d307c858d52f0) BApp 来检测配置错误的 Web 缓存。

### 元素分隔符差异

分隔符指定 URL 中不同元素之间的边界。字符和字符串作为分隔符的使用通常是标准化的。例如，`?` 通常用于分隔 URL 路径和查询字符串。然而，由于 URI RFC 相当宽松，不同框架或技术之间仍然存在差异。

缓存和源服务器在如何将字符和字符串用作分隔符方面的差异可能导致 Web 缓存欺骗漏洞。考虑示例 `/profile;foo.css`：

- Java Spring 框架使用 `;` 字符添加称为矩阵变量的参数。因此，使用 Java Spring 的源服务器会将 `;` 解释为分隔符。它在 `/profile` 后截断路径并返回个人信息。
- 大多数其他框架不使用 `;` 作为分隔符。因此，不使用 Java Spring 的缓存很可能将 `;` 及其后的所有内容解释为路径的一部分。如果缓存有规则存储以 `.css` 结尾的请求的响应，它可能会将个人信息作为 CSS 文件缓存并提供。

对于在不同框架或技术之间使用不一致的其他字符也是如此。考虑以下对运行 Ruby on Rails 框架的源服务器的请求，该框架使用 `.` 作为分隔符来指定响应格式：

- `/profile` —— 此请求由默认的 HTML 格式化程序处理，返回用户个人信息。
- `/profile.css` —— 此请求被识别为 CSS 扩展名。没有 CSS 格式化程序，因此请求不被接受并返回错误。
- `/profile.ico` —— 此请求使用 `.ico` 扩展名，Ruby on Rails 无法识别。默认的 HTML 格式化程序处理该请求并返回用户个人信息。在这种情况下，如果缓存配置为存储以 `.ico` 结尾的请求的响应，它会将个人信息作为静态文件缓存并提供。

> 关于 `format` 的默认行为是：如果它被包含在 URL 中，Rails 会自动从 URL 中捕获它并将其放入 `params[:format]`，但 `format` 并不是 URL 中必需的部分。

编码字符有时也可能用作分隔符。例如，考虑请求 `/profile%00foo.js`：

- OpenLiteSpeed 服务器使用编码的空字节 `%00` 字符作为分隔符。因此，使用 OpenLiteSpeed 的源服务器会将路径解释为 `/profile`。
- 大多数其他框架在 URL 中包含 `%00` 时会返回错误。但是，如果缓存使用 Akamai 或 Fastly，它会将 `%00` 及其后的所有内容解释为路径。

### 利用元素分隔符差异

你可以利用分隔符差异，在路径中添加一个静态扩展名，该扩展名被缓存看到但源服务器忽略。为此，你需要识别一个被源服务器用作分隔符但缓存不用的字符。

首先，找出被源服务器用作分隔符的字符。向目标端点的 URL 添加一个任意字符串作为触点判断。例如，将 `/settings/users/list` （作为 hit）修改为 `/settings/users/listaaa` （作为 miss）。当你开始测试分隔符字符时，将此响应作为参考。

> **注意**
> 如果响应与原始响应相同，这表明请求被重定向。你需要选择另一个端点进行测试。

接下来，在原始路径和任意字符串之间添加一个可能的分隔符字符，例如 `/settings/users/list;aaa`：

- 如果响应与基础响应相同，这表明 `;` 字符被用作分隔符，源服务器将路径解释为 `/settings/users/list`。
- 如果它与带有任意字符串的路径响应匹配，这表明 `;` 字符未被用作分隔符，源服务器将路径解释为 `/settings/users/list;aaa`。

一旦你识别出源服务器使用的分隔符，测试缓存是否也使用它们。为此，在路径末尾添加一个静态扩展名。如果响应被缓存，这表明：

- 缓存不使用该分隔符，并解释完整的 URL 路径及其静态扩展名。
- 存在缓存规则来存储以 `.js` 结尾的请求的响应。

确保测试所有 ASCII 字符和一系列常见扩展名，包括 `.css`、`.ico` 和 `.exe`。我们在实验室中提供了一个潜在分隔符字符列表供你开始，请参阅 [Web 缓存欺骗实验室分隔符列表](https://portswigger.net/web-security/web-cache-deception/wcd-lab-delimiter-list)。使用 Burp Intruder 快速测试这些字符。为防止 Burp Intruder 编码分隔符字符，请在 **Payloads** 侧面板的 **Payload encoding** 下关闭 Burp Intruder 的自动字符编码。

然后你可以构造一个触发静态扩展缓存规则的漏洞利用。例如，考虑负载 `/settings/users/list;aaa.js`。源服务器使用 `;` 作为分隔符：

- 缓存将路径解释为：`/settings/users/list;aaa.js`
- 源服务器将路径解释为：`/settings/users/list`

源服务器返回动态个人信息，该信息被存储在缓存中。

由于分隔符通常在每台服务器内部一致使用，你通常可以在许多不同端点上使用此攻击。

> **注意**
> 某些分隔符字符在浏览器将请求转发到缓存之前可能会被处理。这意味着某些分隔符不能在漏洞利用中使用。例如，浏览器会对 `{`、`}`、`<` 和 `>` 等字符进行 URL 编码，并使用 `#` 来截断路径。
> 如果缓存或源服务器解码这些字符，则可能在漏洞利用中使用编码版本。

### 元素分隔符解码差异

网站有时需要在 URL 中发送包含具有特殊意义字符（如分隔符）的数据。为确保这些字符被解释为数据，通常会对它们进行编码。然而，某些解析器在处理 URL 之前会解码某些字符。如果分隔符字符被解码，它可能会被视为分隔符，从而截断 URL 路径。

缓存和源服务器解码哪些分隔符字符的差异可能导致它们在解释 URL 路径时产生差异，即使它们都将相同字符用作分隔符。考虑示例 `/profile%23wcd.css`，它使用 URL 编码的 `#` 字符：

- 源服务器将 `%23` 解码为 `#`。它使用 `#` 作为分隔符，因此将路径解释为 `/profile` 并返回个人信息。
- 缓存也使用 `#` 字符作为分隔符，但不解码 `%23`。它将路径解释为 `/profile%23wcd.css`。如果存在 `.css` 扩展名的缓存规则，它将存储响应。

此外，某些缓存服务器可能会解码 URL，然后将请求转发出去，其中包含解码后的字符。其他缓存服务器首先基于编码的 URL 应用缓存规则，然后解码 URL 并将其转发到下一台服务器。这些行为也可能导致缓存和源服务器在解释 URL 路径时产生差异。考虑示例 `/myaccount%3fwcd.css`：

- 缓存服务器基于编码路径 `/myaccount%3fwcd.css` 应用缓存规则，并决定存储响应，因为存在 `.css` 扩展名的缓存规则。然后它将 `%3f` 解码为 `?`，并将重写后的请求转发给源服务器。
- 源服务器收到请求 `/myaccount?wcd.css`。它使用 `?` 字符作为分隔符，因此将路径解释为 `/myaccount`。

### 利用元素分隔符解码差异

你可以利用解码差异，通过使用编码的分隔符来在路径中添加一个静态扩展名，该扩展名被缓存看到但源服务器忽略。

使用你用于识别和利用分隔符差异的相同测试方法，但使用一系列编码字符。确保也测试编码的非打印字符，特别是 `%00`、`%0A` 和 `%09`。如果这些字符被解码，它们也可以截断 URL 路径。

## 利用静态目录缓存规则

Web 服务器将静态资源存储在特定目录中是常见做法。缓存规则通常通过匹配特定的 URL 路径前缀（如 `/static`、`/assets`、`/scripts` 或 `/images`）来定位这些目录。这些规则也可能容易受到 Web 缓存欺骗的攻击。

> **注意**
> 要利用静态目录缓存规则，你需要了解路径遍历攻击的基础知识。更多信息，请参阅我们的 [路径遍历](https://portswigger.net/web-security/file-path-traversal) Academy 主题。

### 规范化差异

规范化涉及将 URL 路径的各种表示形式转换为标准化格式。这有时包括解码编码字符和解析点段，但这在不同解析器之间差异很大。

缓存和源服务器在规范化 URL 方式上的差异可能使攻击者能够构造一个路径遍历负载，每个解析器对其解释不同。考虑示例 `/static/..%2fprofile`：

- 一个解码斜杠字符并解析点段的源服务器会将路径规范化为 `/profile` 并返回个人信息。
- 一个不解析点段或解码斜杠的缓存会将路径解释为 `/static/..%2fprofile`。如果缓存存储以 `/static` 前缀的请求的响应，它会缓存并提供个人信息。

如上例所示，路径遍历序列中的每个点段都需要被编码。否则，受害者的浏览器会在将请求转发到缓存之前解析它。因此，可利用的规范化差异要求缓存或源服务器在解码路径遍历序列中的字符的同时，也解析点段。

### 检测源服务器的规范化

要测试源服务器如何规范化 URL 路径，向一个不可缓存资源发送请求，路径开头带有一个路径遍历序列和一个任意目录。选择一个不可缓存资源，例如查找非幂等方法如 `POST`。例如，将 `/profile` 修改为 `/aaa/..%2fprofile`：

- 如果响应与基础响应匹配并返回个人信息，这表明路径已被解释为 `/profile`。源服务器解码斜杠并解析点段。
- 如果响应与基础响应不匹配，例如返回 `404` 错误消息，这表明路径已被解释为 `/aaa/..%2fprofile`。源服务器要么不解码斜杠，要么不解析点段。

> **注意**
> 在测试规范化时，从仅编码点段中的第二个斜杠开始。这很重要，因为某些 CDN 会匹配静态目录前缀后的斜杠。
> 你也可以尝试编码完整的路径遍历序列，或者编码点而不是斜杠。这有时会影响解析器是否解码该序列。

### 检测缓存服务器的规范化 （表述模糊，或检测方法本身即模糊）

你可以使用几种不同的方法来测试缓存如何规范化路径。首先识别潜在的静态目录。在 **Proxy > HTTP history** 中，查找具有常见静态目录前缀和缓存响应的请求。通过将 HTTP 历史过滤器设置为仅显示具有 2xx 响应和脚本、图像及 CSS MIME 类型的消息，来聚焦于静态资源。

然后你可以选择一个具有缓存响应的请求，并在静态路径开头使用路径遍历序列和一个任意目录重新发送该请求。选择一个响应包含已缓存证据的请求。例如，`/aaa/..%2fassets/js/stockCheck.js`：

- 如果响应不再被缓存，这表明缓存不会在将路径映射到端点之前对其进行规范化。这表明存在基于 `/assets` 前缀的缓存规则。
- 如果响应仍然被缓存，这可能表明缓存已将路径规范化为 `/assets/js/stockCheck.js`。

你也可以在目录前缀之后添加一个路径遍历序列。例如，将 `/assets/js/stockCheck.js` 修改为 `/assets/..%2fjs/stockCheck.js`：

- 如果响应不再被缓存，这表明缓存在规范化期间解码斜杠并解析点段，将路径解释为 `/js/stockCheck.js`。这表明存在基于 `/assets` 前缀的缓存规则。
- 如果响应仍然被缓存，这可能表明缓存尚未解码斜杠或解析点段，将路径解释为 `/assets/..%2fjs/stockCheck.js`。

注意，在两种情况下，响应都可能是由于其他缓存规则（例如基于文件扩展名的规则）而被缓存。要确认缓存规则是基于静态目录的，将目录前缀后的路径替换为任意字符串。例如，`/assets/aaa`。如果响应仍然被缓存，则确认缓存规则是基于 `/assets` 前缀的。注意，如果响应似乎未被缓存，这并不一定排除静态目录缓存规则，因为有时 `404` 响应不会被缓存。

> **注意**
> 你可能无法明确确定缓存是否解码点段和解码 URL 路径，而不尝试漏洞利用。

### 利用源服务器的规范化

如果源服务器解析编码的点段，但缓存不解析，你可以尝试构造以下结构的负载来利用差异：

`/<static-directory-prefix>/..%2f<dynamic-path>`

例如，考虑负载 `/assets/..%2fprofile`：

- 缓存将路径解释为：`/assets/..%2fprofile`
- 源服务器将路径解释为：`/profile`

源服务器返回动态个人信息，该信息被存储在缓存中。

步骤
- 测试动态端点的任意规范化是否被解析
    `/任意路径/..%2fprofile`
    - 是否返回相同资源数据（后端是否存在规范化而消除）
- 测试静态端点的资源规范化否被缓存
    `/assets/任意路径/..%2f实际路径/实际文件`
    - 是否返回相同资源数据（后端规范化）
    - 是否显示缓存信息（前端缓存规则，路径前缀或扩展名）
- 删除静态端点测试序列，访问原始静态端点
    `/assets/实际路径/实际文件`
    - 缓存是否命中（前端是否视两次静态端点测试为不同资源）

### 利用缓存服务器的规范化

如果缓存服务器解析编码的点段，但源服务器不解析，你可以尝试构造以下结构的负载来利用差异：

`/<dynamic-path>%2f%2e%2e%2f<static-directory-prefix>`

> **注意**
> 在利用缓存服务器的规范化时，对路径遍历序列中的**所有字符**进行编码。使用编码字符有助于避免使用分隔符时的意外行为，并且不需要在静态目录前缀后面有一个未编码的斜杠，因为缓存将处理解码。

在这种情况下，仅靠路径遍历不足以进行漏洞利用。例如：
- 考虑缓存和源服务器如何解释负载 
  `/profile%2f%2e%2e%2fstatic`：

  - 缓存将路径解释为：`/static`
    执行规范化，视为资源端点的可被缓存资源
  - 源服务器将路径解释为：`/profile%2f%2e%2e%2fstatic`
    不做路径规范化，并未返回静态，而是不存在的资源

- 立即访问静态端点的原资源 
    `/static`
    - 若为 404，缓存 hit，则可确认缓存服务器的规范化行为（原本的静态资源被替换为源服务器对不存在资源的响应）

- 调换顺序，先静态端点，再路径遍历 URL
    - 预期：路径遍历 URL 得到静态资源响应


为了利用这种差异，还需要识别一个被源服务器用作分隔符但缓存不用的分隔符。通过将可能的分隔符添加到动态路径之后的负载中进行测试：

- 如果源服务器使用分隔符，它将截断 URL 路径并返回动态信息。
- 如果缓存不使用分隔符，它将解析路径并缓存响应。

例如，考虑负载 `/profile;%2f%2e%2e%2fstatic`。源服务器使用 `;` 作为分隔符：

- 缓存将路径解释为规范化的静态资源：`/static`
- 源服务器将路径解释为忽略分隔符的动态端点：`/profile`

源服务器返回动态个人信息，该信息被存储在缓存中。因此，你可以使用此负载进行漏洞利用。访问任意被缓存服务器规范化的 URL 或原静态端点，即可得到缓存欺骗资源

> 似乎各种 Unicode 特殊字符也可能作为分隔符

> 注意，之前均为对动态端点的路径分隔符暴破：不被缓存，无需添加缓存破坏器。而此处尝试对预期被规范化的缓存 URL，需添加缓存破坏器，确保每次从后端拉取资源以避免触点响应混乱（例如，无论路径分隔符是否有效，由于缓存服务器的规范化，均返回缓存的内容。之后的有效路径分隔符，收到缓存服务器的静态资源缓存。若此处添加缓存破坏器，则立即返回动态资源）

## 利用文件名缓存规则

某些文件如 `robots.txt`、`index.html` 和 `favicon.ico` 是 Web 服务器上常见的文件。由于它们很少更改，通常会被缓存。缓存规则通过匹配精确的文件名字符串来定位这些文件。

要识别是否存在文件名缓存规则，发送一个 `GET` 请求请求可能的文件，查看响应是否被缓存。

### 检测规范化差异

要测试源服务器如何规范化 URL 路径，使用与静态目录缓存规则相同的方法。更多信息，请参阅 [检测源服务器的规范化](#detecting-normalization-by-the-origin-server)。

要测试缓存如何规范化 URL 路径，发送一个在文件名之前带有路径遍历序列和一个任意目录的请求。例如，`/profile%2f%2e%2e%2findex.html`：

- 如果响应被缓存，这表明缓存将路径规范化为 `/index.html`。
- 如果响应未被缓存，这表明缓存不解码斜杠和解析点段，将路径解释为 `/profile%2f%2e%2e%2findex.html`。

### 利用规范化差异

由于只有当请求匹配精确文件名时响应才会被缓存，你只能利用缓存服务器解析编码点段但源服务器不解析的差异。使用与静态目录缓存规则相同的方法——只需将静态目录前缀替换为文件名。更多信息，请参阅 [利用缓存服务器的规范化](#exploiting-normalization-by-the-cache-server)。

## 预防 Web 缓存欺骗漏洞

你可以采取一系列措施来预防 Web 缓存欺骗漏洞：

- 始终使用 `Cache-Control` 头标记动态资源，设置指令 `no-store` 和 `private`。
- 配置你的 CDN 设置，使你的缓存规则不会覆盖 `Cache-Control` 头。
- 激活 CDN 针对 Web 缓存欺骗攻击的任何防护。许多 CDN 允许你设置缓存规则，验证响应 `Content-Type` 是否与请求的 URL 文件扩展名匹配。例如，Cloudflare 的 Cache Deception Armor。
- 验证源服务器和缓存之间在解释 URL 路径方面不存在任何差异。
