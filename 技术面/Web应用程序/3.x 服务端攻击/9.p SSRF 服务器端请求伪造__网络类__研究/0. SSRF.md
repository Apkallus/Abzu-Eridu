# 服务器端请求伪造（SSRF）

如果应用程序接受用户可控制的输入，并将其合并到使用后端 HTTP请求检索的 URL 中，这种行为就会导致服务器端重定向漏洞。用户提交的输入中可能包含被检索的完整 URL，或者应用程序可能会对该 URL 进行某种处理，如添加标准的后缀。

后端HTTP请求可能指定公共因特网上的某个域，或者指定用户无法直接访问的内部服务器。所请求的内容可能对应用程序的功能非常关键，如支付网关的接口；或者较为次要，如从第三方提取的内容。这种技巧常用于将几个单独的内部和外部应用程序组件结合到一个前端应用程序中，再由该应用程序代表这些组件实施访问控制和会话管理。如果攻击者能够控制后端HTTP请求中的IP地址或主机名，他就可以使应用程序服务器连接到任意资源，有时甚至能够检索后端响应的内容。

SSRF 是一类漏洞，允许攻击者诱使服务端应用程序向非预期的位置发出请求（使用应用程序的权限）。通常存在于允许通过用户提供的输入远程获取图像、视频、文档和其他文件导入的功能中。

当应用程序服务器能够与用户无法直接访问的其他后端系统交互，这些后端系统通常
- 具有不可路由的私有 IP 地址或仅限于某些主机
- 缺乏更复杂的访问控制
- 包含敏感数据或功能。

成功利用 SSRF 可能导致使用服务器作为外部端口扫描的代理、拒绝服务、读取和访问 Web 服务器内部文件，甚至访问服务器上未公开的内部资源以及本地网络上的其他内部服务。在某些情况下，SSRF 漏洞可能允许攻击者执行任意命令。

导致连接到外部第三方系统的 SSRF 攻击可能会引发恶意的后续攻击。这些攻击可能看起来源自托管易受攻击应用程序的组织。

## 常见的 SSRF 攻击

SSRF 攻击通常利用组件间缺乏防御，将攻击从易受攻击的应用程序升级，并执行未经授权的操作。这些缺陷可能存在于服务器本身，也可能存在于同一组织内的其他后端系统之间。

攻击者将易受攻击的应用程序作为开放的HTTP代理服务器，以实施各种其他攻击：

- 攻击者将该代理服务器用于攻击互联网上的第三方系统。恶意流量针对的是运行易受攻击的应用程序的服务器上的目标。

- 攻击者将该代理服务器用于连接到组织内部网络中的任意主机，从而访问无法通过因特网直接访问的目标。

- 攻击者将该代理服务器用于反向连接在应用程序服务器本身上运行的其他服务，从而突破防火墙的限制，并利用信任关系来避开身份验证。

- 最后，攻击者通过使应用程序在响应中包含受控的内容，利用代理功能实施跨站点脚本等攻击。

SSRF漏洞有两种类型：**普通SSRF**和**盲SSRF**。唯一的区别在于，在盲SSRF中，攻击者不会通过HTTP响应或错误消息收到来自服务器的反馈。

虽然盲SSRF更难利用，但对攻击者来说仍然非常有价值，他们可能能够进行网络扫描并利用网络上的其他漏洞。我们稍后会详细讨论。

### 针对服务器的 SSRF 攻击

在针对服务器的 SSRF 攻击中，攻击者使应用程序通过其回环网络接口向托管该应用程序的服务器本身发出 HTTP 请求。这通常涉及提供主机名为 `127.0.0.1`（指向回环适配器的保留 IP 地址）或 `localhost`（同一适配器的常用名称）的 URL。

例如，假设一个购物应用程序允许用户查看某个商品在特定商店是否有库存。为了提供库存信息，应用程序必须查询各种后端 REST API。它通过前端 HTTP 请求将 URL 传递给相关的后端 API 端点来实现这一点。当用户查看商品的库存状态时，他们的浏览器发出以下请求：

```http
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

stockApi=http://stock.weliketoshop.net:8080/product/stock/check%3FproductId%3D6%26storeId%3D1
```

这导致服务器向指定的 URL 发出请求，获取库存状态，并将其返回给用户。

在此示例中，攻击者修改请求，指定一个服务器本地的 URL：

```http
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

stockApi=http://localhost/admin
```

服务器获取 `/admin` URL 的内容并将其返回给用户。

攻击者访问 `/admin` URL，但管理功能通常只对经过身份验证的用户开放。这意味着攻击者不会看到任何有趣的内容。但是，如果对 `/admin` URL 的请求来自本地机器，则正常的访问控制就会被绕过。应用程序授予对管理功能的完全访问权限，因为该请求看似来自受信任的位置。

为什么应用程序会以这种方式运行，并隐式信任来自本地机器的请求？这可能出于多种原因：

- 访问控制检查可能由位于应用程序服务器前面的不同组件实现。当连接回到服务器时，该检查被绕过。
- 出于灾难恢复目的，应用程序可能允许来自本地机器的任何用户无需登录即可进行管理访问。这为管理员在丢失凭据时提供了一种恢复系统的方法。这是基于只有完全受信任的用户才会直接来自服务器的假设。
- 管理界面可能监听与主应用程序不同的端口号，用户可能无法直接访问。

这类信任关系（即来自本地机器的请求与普通请求的处理方式不同）常常使 SSRF 成为一个关键漏洞。

### 针对其他后端系统的 SSRF 攻击

在某些情况下，应用程序服务器能够与用户无法直接访问的后端系统交互。这些系统通常具有不可路由的私有 IP 地址。后端系统通常受网络拓扑保护，因此它们通常具有较弱的安全态势。在许多情况下，内部后端系统包含敏感功能，任何能够与之交互的人都可以在无需身份验证的情况下访问。

在前面的示例中，假设后端 URL `http://192.168.0.68/admin` 处有一个管理界面。攻击者提交以下请求来利用 SSRF 漏洞并访问管理界面：

```http
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

stockApi=http://192.168.0.68/admin
```

## SSRF 攻击回顾

利用通过网络扫描、识别服务和获取实例元数据所发现的信息来执行有影响力的攻击。值得注意的是，你可能能够绕过访问控制、泄露机密信息和执行代码。

首先，尝试绕过访问控制。一些内部服务可能仅基于IP地址或内部头来控制访问，因此可能只需从受信任机器发送请求即可绕过对敏感功能的控制。例如，你可能能够通过代理Web服务器访问内部网站：

`url=https://admin.example.com`

尝试通过SSRF端点执行内部API调用。这类攻击需要了解内部系统和API语法，通过侦察和系统的其他信息泄露来获得。例如，假设API端点`admin.example.com/delete_user`删除用户，且只能由内部地址请求。如果你发现一个SSRF允许你从受信任网络中的机器发送请求，就可以触发该请求：

`url=https://admin.example.com/delete_user?user=1`

其次，如果你能够通过SSRF利用头信息泄露或查询实例元数据找到凭据，请使用这些凭据访问存储在网络上的机密信息。例如，如果你能够找到Amazon S3密钥，枚举公司的私有S3存储桶，并查看是否可以使用找到的凭据访问它们。

第三，使用你收集的信息将SSRF转换为远程代码执行。例如，如果你找到了具有写入权限的管理员凭据，尝试将Shell上传到Web服务器。或者，如果你找到了不安全的控制面板，查看是否有任何功能允许执行脚本。使用普通或盲SSRF通过向可达机器发送设计用于检测已知漏洞的载荷来测试目标网络上的其他漏洞。

寻找 SSRF 的步骤回顾：

1. **识别容易出现SSRF的功能**，并做记录以供将来参考。
2. **设置回调监听器**以检测盲SSRF，使用在线服务、Netcat或Burp的Collaborator功能。
3. **向潜在易受攻击端点提供常见的内部地址**或你的回调监听器地址。
4. **检查服务器是否响应了确认SSRF的信息**。在盲SSRF的情况下，检查服务器日志中来自目标服务器的请求。
5. **在盲SSRF的情况下**，检查当你请求不同主机或端口时服务器行为是否不同。
6. **如果实施了SSRF防护**，尝试使用本章讨论的策略绕过它。
7. **选择一种策略来提升SSRF的影响**。


## 防御措施

当服务器需要发送请求以获取外部资源时，就可能发生SSRF。当应用程序允许请求严格限制下的预定义和白名单端点时，可能被视为一个功能，而不是安全漏洞。例如，当你在Twitter上发布链接时，Twitter会从该外部站点获取图片以创建缩略图。但如果服务器不阻止用户使用相同的机制访问内部资源，就会发生SSRF漏洞。

让我们看另一个例子。假设`public.example.com`上的一个页面允许用户通过从URL检索来上传个人资料照片，使用以下POST请求：

```http
POST /upload_profile_from_url
Host: public.example.com

user_id=1234&url=https://www.attacker.com/profile.jpeg
```

为了从`attacker.com`获取`profile.jpeg`，Web应用程序必须访问并从`attacker.com`检索内容。这是应用程序的安全且预期的行为。但如果服务器不区分内部和外部资源，攻击者轻易地请求存储在服务器上的本地文件或网络上的任何其他文件。例如，他们可以发出以下POST请求，这将导致Web服务器获取敏感文件并将其显示为用户的个人资料图片：

```http
POST /upload_profile_from_url
Host: public.example.com

user_id=1234&url=https://localhost/passwords.txt
```

针对SSRF主要有两种防护类型：**黑名单**和**白名单**。黑名单是被禁止地址的列表。如果请求包含黑名单地址作为输入，服务器将阻止该请求。由于应用程序通常需要从各种互联网来源获取资源，数量太多而无法明确允许，大多数应用程序使用这种方法。公司将内部网络地址列入黑名单，并拒绝任何重定向到这些地址的请求。

另一方面，当站点实施白名单防护时，服务器只允许包含预定义列表中URL的请求，并拒绝所有其他请求。一些服务器还通过在内部请求中要求特殊头或秘密令牌来防范SSRF。

实例：
- Snapchat 预览服务允许用户在打开内容之前查看内容的简要预览。然而，2019年测试者在 Snapchat 的广告图片导入中发现 SSRF 漏洞：使用 DNS 重绑定技术与云元数据服务通信，最终可获得敏感凭据。[hackerone 报告](https://hackerone.com/reports/530974)。

有关 SSRF 预防的更多信息，参见[OWASP 服务器端请求伪造防护速查表](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)。
