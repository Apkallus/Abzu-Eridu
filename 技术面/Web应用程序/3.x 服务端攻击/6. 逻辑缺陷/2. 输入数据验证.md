# 未能处理非常规输入

## 概述

应用程序逻辑的目标之一是将用户输入限制为符合业务规则的值。例如，应用程序可能被设计为接受特定数据类型的任意值，但逻辑决定该值从业务角度来看是否可接受。许多应用程序在逻辑中加入了数字限制。这可能包括旨在管理库存、应用预算限制、触发供应链阶段等的限制。

让我们以在线商店的简单示例为例。在订购产品时，用户通常指定他们想要订购的数量。尽管从理论上讲，任何整数都是有效输入，但业务逻辑可能会阻止用户订购超过当前库存数量的商品，例如。

为了实现此类规则，开发人员需要预见所有可能的场景，并在应用程序逻辑中纳入处理它们的方法。换句话说，他们需要告诉应用程序是否应允许给定输入，以及如何根据各种条件做出反应。如果没有处理给定情况的显式逻辑，这可能导致意外且可能可被利用的行为。

例如，数字数据类型可能接受负值。根据相关功能，业务逻辑允许这样做可能没有意义。但是，如果应用程序没有执行充分的服务器端验证并拒绝此输入，攻击者可能能够传入负值并诱导非预期的行为。

考虑两个银行账户之间的资金转账。此功能几乎肯定会在完成转账之前检查发送方是否有足够的资金：

```php
$transferAmount = $_POST['amount'];
$currentBalance = $user->getBalance();

if ($transferAmount <= $currentBalance) {
    // Complete the transfer
} else {
    // Block the transfer: insufficient funds
}
```

但如果逻辑没有充分阻止用户在 `amount` 参数中提供负值，攻击者可以利用这一点绕过余额检查并以“错误”方向转账。如果攻击者向受害者账户发送 -1000 美元，这实际上可能导致他们从受害者那里收到 1000 美元。逻辑将始终评估 -1000 小于当前余额并批准转账。

如果出现在正确的功能中，这种简单的逻辑缺陷可能是毁灭性的。它们在开发和测试期间也容易被忽略，特别是因为此类输入可能被 Web 界面上的客户端控制阻止。

在审计应用程序时，您应该使用 Burp Proxy 和 Repeater 等工具尝试提交非常规值。特别是，尝试合法用户不太可能输入的数值范围。这包括
- 异常高或异常低的数字输入
- 基于文本字段的异常长字符串
- 非预期的数据类型

通过观察应用程序的响应，尝试回答以下问题：

- 对数据施加了哪些限制？
- 当您达到这些限制时会发生什么？
- 您的输入是否进行了任何转换或规范化？

这可能暴露薄弱的输入验证，允许您以非寻常方式操纵应用程序。请记住，如果您在目标网站上发现一个表单未能安全处理非常规输入，很可能其他表单也存在同样的问题。

应用程序或仅在（依赖）前端进行数据验证，甚至前后端均（彻底）缺失数据验证

## 如何测试

### 测试方法

- 尝试向应用程序提交逻辑上无效的数据。
- 审查项目文档，探测组件交接点对数据的处理是否一致

## 示例

### 规避交易限制

1. 功能

    财务人员有资格在公司拥有的银行账户与公司关键客户和供应商的账户之间进行转账。为防止金融欺诈，应用程序将大多数用户的转账金额限制在10 000美元之内。如果转账金额超出这个限制，就需要得到高级经理的批准。

2. 假设

    应用程序中负责金额检查的代码：对 int 进行大小检查

    开发者认为这种透明的检查非常安全。如果转账金额超出预先设定的限制，只有得到高级经理的许可交易才能进行。

3. 攻击方法

    开发者的假设存在缺陷，因为他完全忽略了用户用负金额进行转账的可能性。由于任何负值都小于转账金额限制，因此不需要得到进一步的批准。但是，应用程序的银行模块接受负值转账，并以反向正值转账的形式对其进行处理。因此，如果用户希望从A账户转账20 000美元到B账户，他只需从B账户转账-20 000美元到A账户，即可得到相同的效果，并且不需要经过批准。应用程序实施的反欺诈防御措施也被轻易避开！

许多Web应用程序在它们的交易逻辑中采用数字限额，例如：

- 零售应用程序禁止用户订购超出其库存量的商品；
- 银行应用程序禁止用户支付超出其当前账户余额的账单；
- 保险应用程序根据年龄限制调整报价。

找到规避这个限额的方法表示所有者依赖应用程序实施的控制存在缺陷。

在发布应用程序前执行的用户验收测试过程中，我们通常可以检测出最明显的漏洞。然而，隐藏较深的漏洞依然存在，特别是操纵隐藏参数造成的漏洞。

#### 渗透测试步骤

尝试规避交易限制的第一步是了解受控制的相关输入接受哪些字符。

1. 尝试输入负值，看应用程序是否接受这些值并按预想的方式对它们进行处理。

2. 可能需要执行几步操作，改变应用程序的状态，使其对攻击有用。例如，可能需要在账户之间进行几次转账，直到得到可提取的适当余额。

### 验证规则不当 -> 业务逻辑缺陷，查询返回所有订单

通常，业务逻辑缺陷也可能源于不当的验证规则，如正则表达式。让我们看一个示例：

**易受攻击的代码：**
```php
<?php
if (isset($_GET['order_id'])) {
    $order_id = $_GET['order_id'];
    // 查看参数值是否以数字开头
    if (preg_match('/\d/', $order_id)) {
        // 将参数值拼接到 SQL 查询中
        $SQL = "SELECT * FROM orders WHERE order_id = $order_id";
        echo "<p>Query executed: $SQL</p>";
    } else {
        echo "<p>Invalid order_id.</p>";
    }
}
?>
```

该代码通过 `order_id` 参数接收订单 ID，并构造 SQL 查询，从 `orders` 表中获取所有 `order_id` 与用户提供的 `order_id` 匹配的记录。这里明显的漏洞是 SQL 注入，因为 `order_id` 直接用于构造 SQL 查询，未经任何清理。然而，这里还存在一个业务逻辑漏洞。

在此示例中，在构造 SQL 查询之前，应用程序使用 `preg_match` 函数检查 `order_id` 参数是否为数字。正则表达式 `/\d/` 对于任何至少包含一个数字的字符串都将返回真。换句话说，使用 `1001 or 1=1` 提供的 `order_id` 参数将使整个语句为真，并返回数据库中的所有订单：

**POC**
```
www.vulnerablebank.com/orders.php?order_id=1001 or 1=1
```

更好的验证方法是使用 `^` 和 `$` 分隔符，正则表达式为 `/^\d+$/`，仅当 `order_id` 完全由一个或多个数字组成时返回真

### 示例：缺失捐赠最低金额限制，导致接收方花费更高手续费而亏损

**[分布式拒绝美元（DDo$）](https://news.hitb.org/content/pirate-bay-proposes-distributed-denial-dollars-attack-ddo)：**
这是由网站“海盗湾”的创始人针对对该网站提起诉讼的律师事务所发起的一项活动。目标是利用银行接收捐赠的业务功能设计中错误以及银行转账验证过程中的特性。

此攻击通过向律师事务所捐赠非常少量的金钱（1 瑞典克朗，约 0.13 美元）来执行。收款银行账户仅有 1000 次免费转账，之后任何金额的转账都会对账户持有人收取附加费（2 瑞典克朗）。在前一千笔互联网交易之后，每一笔 1 瑞典克朗的捐款实际上最终会使账户持有人花费 1 瑞典克朗。

### 示例：缺乏数字符号验证，导致充值功能窃取客户余额

某食品配送服务实现了一项功能，允许其骑手在特定情况下（如退款或调整）为客户钱包充值，以处理不完整或错误的订单。此功能对于增强用户体验至关重要，因为它提供了灵活的支付选项并确保无缝交易。例如，如果客户收到不完整的订单，骑手可以立即以缺失商品等值的金额充值客户钱包，而不是让客户联系支持聊天并排队等待，而支持代理再联系骑手和餐厅，造成不必要的延迟。

在渗透测试中，发现了一个关键漏洞，该端点允许骑手充值客户钱包余额。恶意的骑手可以通过在 `topup` 参数中提供负值来利用此漏洞，从现有客户的钱包中窃取资金。

例如，通过在 `topup` 参数中提供 `-50`，恶意骑手可以成功从客户钱包余额中扣除 50 美元，而不是增加它：

**请求**
```http
POST /api/v1/rider/topup HTTP/1.1
Host: secure.example.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 135

_id=12345abcde&tokenId=67890fghij&transId=12345klmno&topup=-50&passengerId=6789
```

此漏洞的根本原因是钱包功能只是简单地将指定金额应用到客户钱包余额中，而不检查金额是否为正。


### 示例：超长字符串，绕过输入确认

1. 功能

    该应用程序包含一组输入确认程序，以防范各种类型的攻击。其中的两种防御机制为SQL注入过滤和长度限制。

    通常，应用程序对在基于字符串的用户输入中出现的任何单引号进行转义（并拒绝在数字输入中出现的任何单引号），以防范SQL注入。两个单引号在一起将构成一个转义序列，表示一个原义单引号，数据库会将其解释为引用字符串中的数据，而不是结束字符串的终止符。因此，许多开发者认为，通过将用户提交的输入中的任何单引号配对，就可以防止SQL注入攻击。

    长度限制适用于所有输入，确保用户提交的变量不会超过128个字符。如果任何变量超过128个字符，它会将其截短。

2. 假设

    从安全的角度来说，SQL注入过滤和长度限制都属于适当的防御机制，因此两种防御机制都应该采用。

3. 攻击方法

    SQL注入防御通过将用户输入中的任何引号配对而生效，因此，在每对引号中，第一个引号将作为第二个引号的转义字符。但是，开发者并没有考虑到，如果将经过转义的输入提交给“截短”功能，将会发生什么情况。

    假设应用程序将用户输入中的任何单引号配对，然后对该数据实施长度限制，将其截短为128个字符。
    
    如果提交以下用户名（包含127个a后接一个单引号）：应用程序会首先将单引号配对，然后将字符串截短为128个字符，导致输入又恢复其原始值。这时会生成数据库错误，因为在查询中注入了另外一个单引号，而没有纠正周围的语法。此时密码载荷成功避开登录

    由a组成的字符串末尾的已配对引号将被解释为转义引号，因而被作为查询数据的一部分。这个字符串将继续有效，直到下一个单引号位置结束，而在原始的查询中，这个位置为用户提交的密码值的开始部分。

    因此，之后的任何内容均被解释为查询的一部分，因而可以进行专门设计以破坏查询逻辑。


不必清楚了解应用程序实施的长度限制，只需轮流提交两个超长奇偶单引号字符串，并确定是否会生成错误，即可测试这种类型的漏洞

截短转义输入将在偶数或奇数个字符之后发生。无论是哪一种情况，以上其中一个字符串将导致在查询中插入奇数数量的单引号，从而生成无效的语法。

#### 渗透测试步骤

记下应用程序修改用户输入（特别是截短、删除数据、编码或解码）的任何位置。对于观察到的每一个位置，确定是否可以人为构造恶意字符串。

1. 如果数据已被过滤一次（非递归），确定是否可以提交一个“补偿”过滤操作的字符串(预期被删除的冗余字符串)。例如，如果应用程序过滤SELECT这个SQL关键字，则可以提交SELSELECTECT，看过滤机制是否会删除其中的SELECT子字符串，而留下SELECT。

2. 如果数据确认按设定的顺序发生，并且有一个或多个确认步骤修改了数据，则确定是否可以将这些步骤用于破坏之前的确认步骤。例如，如果应用程序执行URL编码，然后过滤掉恶意数据（如`<script>`标签），则通过提交被冗余字符串分隔的URL编码载荷字符串来避开确认机制

跨站点脚本过滤经常会错误地删除HTML标签对之间的所有数据，如`<tag1>aaaaa</tag1>`。这种行为通常易于受到上述攻击。

### 净化使用转义符，但遗漏转义符本身

1. 功能

    应用程序的设计者决定执行某种功能，该功能需要以自变量的形式向操作系统命令提交用户控制的输入。应用程序的开发者知道这种操作包含着内在的风险，并决定净化用户输入中出现的任何潜在的恶意字符，从而防御这种风险。各种元字符使用反斜线（`\`）进行转义
    
    以这种方式进行转义后，shell命令解释器就把它们当做提交给被调用命令的自变量的一部分，而非shell元字符。后者可用于注入其他命令或自变量、重定向输出等。

2. 假设

    开发者确信，他们设计的方法可有效防御命令注入攻击。他们考虑到了每一个可能被攻击者利用的字符，并确保对它们进行了适当的转义处理，因而它们不会造成风险。

3. 攻击方法

    开发者忘记了对转义字符本身进行转义。

    通常，攻击者在利用简单的命令注入漏洞时并不直接使用反斜线，因此开发者认为它并非恶意字符。然而，正是由于没有对它进行转义，攻击者就可以完全破坏应用程序的净化机制。

    当攻击者提交的包含转义字符的数据作为自变量提交给操作系统命令时，shell 解释器把第一个反斜线作为转义字符，而把第二个反斜线当做字面量反斜线处理；反斜线不是一个转义字符，而是自变量的一部分。然后它遇到分号字符，该字符明显没有进行转义。解释器把分号作为一个命令分隔符，因此继续执行攻击者注入的命令。

#### 渗透测试步骤

当在应用程序中探查命令注入及其他缺陷时，尝试在受控制的数据中插入相关元字符后，接着在每个元字符前插入一个反斜线，测试前面描述的逻辑缺陷。

一些防御跨站点脚本攻击的措施中也存在这种的逻辑缺陷。将用户提交的输入直接复制到一段 JS 脚本的字符串变量值中时，这个值包含在引号内。为防御跨站点脚本攻击，许多应用程序使用反斜线对出现在用户输入中的引号进行转义。然而，如果反斜线本身并没有转义，那么攻击者就可以提交`\'`破坏字符串，从而控制脚本。早先版本的 Ruby On Rails 框架的 escape_javascript 函数中就存在这种漏洞。

### 电子邮件地址解析器差异

某些网站解析电子邮件地址以提取域并确定电子邮件所有者属于哪个组织。虽然这个过程最初看起来很简单，但实际上非常复杂，即使对于符合 RFC 的有效地址也是如此。

电子邮件地址解析方式的差异可能破坏此逻辑。当应用程序的不同部分以不同方式处理电子邮件地址时，就会出现这些差异。

攻击者可以使用编码技术来伪装电子邮件地址的部分内容，从而利用这些差异。这使攻击者能够创建通过初始验证检查但被服务器解析逻辑以不同方式解释的电子邮件地址。

电子邮件地址解析器差异的主要影响是未授权访问。攻击者可以使用来自受限域名的看似有效的电子邮件地址注册帐户。这使他们能够访问应用程序的敏感区域，如管理面板或受限用户功能。

> **更多信息**：有关电子邮件解析差异的详细信息，包括如何利用它们，请参阅 PortSwigger 研究团队 Gareth Heyes 的白皮书 [Splitting the Email Atom: Exploiting Parsers to Bypass Access Controls](https://portswigger.net/research/splitting-the-email-atom)。

- 格式：
    - `=?utf-7?q?abc?=foo@目标域名`
    - `=?字符集?编码?数据?=foo@目标域名`
- 核心：在数据中设置之后被解码的特殊符号
    - 设置数据段为最终邮件
    - 设置终止符（空格/空字节/下划线）或上下文的闭、开字符（尖括号/双引号）
- 使用 `&-` 格式的 IMAP 邮件版 UTF-7 编码，而不是研究文章中的 `+-` 普通 UTF-7 格式。见 [RFC 3501](https://datatracker.ietf.org/doc/html/rfc3501#section-5.1.3)

- 流程
    - 探测：是否支持编码？使用普通字符
    - 编码：是否支持特殊字符编码？
    - 利用：尝试各种组合
