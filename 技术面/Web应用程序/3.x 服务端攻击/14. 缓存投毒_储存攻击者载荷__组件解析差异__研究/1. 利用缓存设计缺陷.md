# 利用缓存设计缺陷

在本节中，我们将更深入地探讨缓存设计中的常见缺陷如何导致 Web 缓存投毒漏洞，并演示如何利用这些漏洞。

简而言之，如果网站以不安全的方式处理未键控（unkeyed）输入，并允许后续 HTTP 响应被缓存，则容易受到 Web 缓存投毒攻击。此漏洞可作为多种不同攻击的传播载体。

## 利用 Web 缓存投毒传递 XSS 攻击

最简单的 Web 缓存投毒漏洞利用场景是：未键控输入在可缓存的响应中被直接反射，且未经过适当清理。

例如，考虑以下请求和响应：

```http
GET /en?region=uk HTTP/1.1
Host: innocent-website.com
X-Forwarded-Host: innocent-website.co.uk
```

```http
HTTP/1.1 200 OK
Cache-Control: public
<meta property="og:image" content="https://innocent-website.co.uk/cms/social.png" />
```

此处，`X-Forwarded-Host` 头的值被用于动态生成 Open Graph 图片 URL，并反射在响应中。关键在于，`X-Forwarded-Host` 头通常是未键控的。在此例中，缓存可能被如下包含简单 XSS 负载的响应投毒：

```http
GET /en?region=uk HTTP/1.1
Host: innocent-website.com
X-Forwarded-Host: a."><script>alert(1)</script>"
```

```http
HTTP/1.1 200 OK
Cache-Control: public
<meta property="og:image" content="https://a."><script>alert(1)</script>"/cms/social.png" />
```

如果此响应被缓存，所有访问 `/en?region=uk` 的用户都将收到此 XSS 负载。该示例仅触发浏览器弹窗，但实际攻击可能窃取密码、劫持用户账户等。

## 利用 Web 缓存投毒攻击资源导入的不安全处理

某些网站使用未键控头动态生成资源导入 URL，例如外部托管的 JavaScript 文件。此时，若攻击者将对应头的值改为自己控制的域名，就可能将 URL 指向其恶意 JavaScript 文件。

如果包含该恶意 URL 的响应被缓存，则任何使用匹配缓存键发起请求的用户，其浏览器会话都会导入并执行攻击者的 JavaScript 文件。

```http
GET / HTTP/1.1
Host: innocent-website.com
X-Forwarded-Host: evil-user.net
User-Agent: Mozilla/5.0 Firefox/57.0
```

```http
HTTP/1.1 200 OK
<script src="https://evil-user.net/static/analytics.js"></script>
```

## 利用 Web 缓存投毒攻击 Cookie 处理漏洞

Cookie 常被用于动态生成响应内容。常见例子是表示用户首选语言的 Cookie，用于加载对应语言版本的页面：

```http
GET /blog/post.php?mobile=1 HTTP/1.1
Host: innocent-website.com
User-Agent: Mozilla/5.0 Firefox/57.0
Cookie: language=pl;
Connection: close
```

此例请求波兰语版本的博客文章。注意，语言版本信息仅包含在 `Cookie` 头中。假设缓存键包含请求行和 `Host` 头，但不包含 `Cookie` 头。那么，若此请求的响应被缓存，之后所有访问该博客文章的用户都将收到波兰语版本，无论他们实际选择了何种语言。

缓存的这种不当 Cookie 处理也可被 Web 缓存投毒技术利用。不过在实践中，这类基于 Cookie 的投毒漏洞相比基于头的漏洞更为罕见，且一旦出现，通常很快被发现并修复，因为合法用户也可能意外投毒缓存。

## 利用多个头进行 Web 缓存投毒

某些网站容易受到如上所示的简单 Web 缓存投毒攻击，但另一些则需要更复杂的攻击，仅在攻击者能构造出操纵多个未键控输入的请求时才变得脆弱。

例如，假设某网站要求使用 HTTPS 安全通信。为了强制执行，如果收到使用其他协议的请求，网站会动态生成一个指向自身但使用 HTTPS 的重定向：

```http
GET /random HTTP/1.1
Host: innocent-site.com
X-Forwarded-Proto: http

HTTP/1.1 301 moved permanently
Location: https://innocent-site.com/random
```
- 或使用 `X-Forwarded-Scheme`

该行为本身不一定存在漏洞。但结合之前关于动态生成 URL 漏洞的知识，攻击者可能利用此行为生成可缓存的响应，将用户重定向至恶意 URL。递归探测有趣的头部，例如：HTTPS 重定向或使用 Host 设置动态 URL，而此处可能存在 Host 头注入漏洞。

## 利用响应中暴露过多信息

有时网站会因暴露过多自身及其行为信息，而使自身更易受到 Web 缓存投毒攻击。

### Cache-Control 指令

构造 Web 缓存投毒攻击的挑战之一是确保有害响应被缓存。这通常需要大量手动试验以研究缓存行为。然而，有时响应会明确暴露攻击者成功投毒所需的一些信息。

例如，响应包含缓存清除频率或当前缓存响应年龄的信息：

```http
HTTP/1.1 200 OK
Via: 1.1 varnish-v4
Age: 174
Cache-Control: public, max-age=1800
```

虽然这不会直接导致 Web 缓存投毒漏洞，但能减少攻击者手动尝试的工作量，因为他们确切知道何时发送负载才能确保被缓存。

该知识还可用于更精细的攻击。攻击者无需向后端服务器发送大量请求直到命中缓存（这可能引起怀疑），而是可以精确计时发送单个恶意请求来投毒缓存。

### Vary 头

`Vary` 头通常的简单用法也可能为攻击者提供帮助。`Vary` 头指定了应作为缓存键一部分的额外头列表（即使它们通常未键控）。例如，它常被用来指定 `User-Agent` 头为键控，以免移动版网站被错误地提供给非移动用户。

此信息也可用于构建多步骤攻击，以针对特定用户子集。例如，若攻击者知道 `User-Agent` 头是缓存键的一部分，则可通过先识别目标受害者的用户代理，定制攻击使其仅影响使用该用户代理的用户。或者，他们可以找出最常访问该网站的用户代理，从而定制攻击以影响最多数量的用户。

## 利用 Web 缓存投毒攻击 DOM 型漏洞

如前所述，如果网站不安全地使用未键控头导入文件，攻击者可能利用此导入恶意文件。但这不仅限于 JavaScript 文件。

许多网站使用 JavaScript 从后端获取并处理额外数据。如果脚本以不安全方式处理来自服务器的数据，可能引发各类 DOM 型漏洞。

例如，攻击者可投毒缓存，使其导入包含如下负载的 JSON 文件：

```json
{"someProperty" : "<svg onload=alert(1)>"}
```

如果网站随后将该属性的值传递到支持动态代码执行的“汇点”（sink），该负载将在受害者浏览器会话上下文中执行。

若使用 Web 缓存投毒让网站从你的服务器加载恶意 JSON 数据，你可能需要通过 CORS 授予网站访问该 JSON 的权限：

```http
HTTP/1.1 200 OK
Content-Type: application/json
Access-Control-Allow-Origin: *

{
    "malicious json" : "malicious json"
}
```

## 链式组合 Web 缓存投毒漏洞

如前所述，有时攻击者只能通过使用多个头构造请求来引发恶意响应。但攻击类型之间的组合也是如此。Web 缓存投毒有时需要攻击者将我们讨论过的多种技术串联起来。通过组合不同漏洞，通常能暴露出原本不可利用的额外攻击面。

常见手法
- 将文件 URL 控制抽象为原语。如 fetch JSON URL 抽象为任意端点 GET。而任意端点 GET 本身即拥有很多操作空间。
- 路径规范化重定向。假设目标端点可设置所需状态，但无法被缓存。若此端点同时存在路径规范化重定向
    - 设置可被缓存的之后被路径规范化的请求
    - 服务器返回对目标端点的重定向
    - 浏览器最终向目标端点请求，从而设置状态
