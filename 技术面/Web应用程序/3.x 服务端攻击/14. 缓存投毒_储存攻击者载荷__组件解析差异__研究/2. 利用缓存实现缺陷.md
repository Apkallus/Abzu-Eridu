# 利用缓存实现缺陷

在前面的实验室中，你学习了如何通过操纵常见的未键控输入（如 HTTP 头、Cookie、URL）来利用 Web 缓存投毒漏洞。虽然这种方法很有效，但这只是 Web 缓存投毒可能性的冰山一角。

在本节中，我们将演示如何通过利用缓存系统特定实现中的奇技淫巧，来访问更大范围的 Web 缓存投毒攻击面。我们将特别关注缓存键生成方式中的缺陷如何使网站容易受到缓存投毒攻击，即使是那些传统上被认为不可利用的独立漏洞。我们还将展示如何将经典技术进一步延伸，以潜在地投毒应用级缓存，通常会产生毁灭性的后果。

这些技术最早由我们的研究总监 James Kettle 在其演讲“Web Cache Entanglement: Novel Pathways to Poisoning”（BlackHat USA 2020）中记录。如果你有兴趣了解他如何在真实环境中发现并利用这些漏洞，可以从我们的研究页面访问该演讲录像和随附的白皮书。

## 缓存键缺陷

一般而言，网站的大部分输入来自 URL 路径和查询字符串。因此，这是各种黑客技术常见的攻击面。然而，由于请求行通常是缓存键的一部分，这些输入传统上被认为不适合用于缓存投毒。任何通过键控注入的负载都会充当缓存破坏器，意味着你投毒的缓存条目几乎肯定不会提供给其他用户。

但仔细观察，单个缓存系统的行为并不总是如你所预期。实际上，许多网站和 CDN 在将键控组件保存到缓存键时，会对它们执行各种转换。这包括：

- 排除查询字符串
- 过滤特定查询参数
- 规范化键控组件中的输入

这些转换可能会引入一些意想不到的怪癖。这些主要基于写入缓存键的数据与传递给应用程序代码的数据之间的差异，尽管两者都源自相同的输入。这些缓存键缺陷可以被利用，通过最初看似不可用的输入来投毒缓存。

在完全集成的应用级缓存中，这些怪癖可能更加极端。事实上，内部缓存可能如此不可预测，以至于有时很难在不经意间为真实用户投毒缓存的情况下进行测试。

## 缓存探测方法论

探测缓存实现缺陷的方法论与经典的 Web 缓存投毒方法论略有不同。这些较新的技术依赖于缓存特定实现和配置中的缺陷，这可能因网站而异。这意味着你需要更深入地了解目标缓存及其行为。

在本节中，我们将概述探测缓存以了解其行为并识别任何潜在缺陷的高级方法论。之后，我们将提供一些常见缓存键缺陷的具体示例以及如何利用它们。

该方法论包括以下步骤：

1. [识别合适的缓存预言机](#identify-a-suitable-cache-oracle)
2. [探测键处理](#probe-key-handling)
3. [识别可利用的“小工具”](#identify-an-exploitable-gadget)

### 识别合适的缓存预言机

第一步是识别一个适合用于测试的“缓存预言机”。缓存预言机只是一个能够提供关于缓存行为反馈的页面或端点。它必须可缓存，并且必须以某种方式表明你收到的是缓存响应还是来自服务器的直接响应。这种反馈可以有多种形式，例如：

- 明确告诉你是否命中缓存的 HTTP 头
- 动态内容的可观察变化
- 明显的响应时间差异

理想情况下，缓存预言机还会在响应中反映完整的 URL 和至少一个查询参数。这将有助于注意到缓存和应用程序之间的解析差异，这对于后续构建不同的漏洞利用很有用。

如果你能识别出正在使用特定的第三方缓存，你还可以查阅相应的文档。其中可能包含关于默认缓存键如何构建的信息。你甚至可能会偶然发现一些有用的技巧，例如允许你直接查看缓存键的功能。例如，基于 Akamai 的网站可能支持 `Pragma: akamai-x-get-cache-key` 头，你可以用它来在响应头中显示缓存键：

```http
GET /?param=1 HTTP/1.1
Host: innocent-website.com
Pragma: akamai-x-get-cache-key

HTTP/1.1 200 OK
X-Cache-Key: innocent-website.com/?param=1
```

### 探测键处理

下一步是调查缓存在生成缓存键时是否对你的输入执行了任何额外处理。你要寻找的是隐藏在看似键控组件中的额外攻击面。

你应特别关注正在发生的任何转换。在添加到缓存键时，是否有任何内容从键控组件中被排除？常见的例子包括排除特定查询参数，甚至整个查询字符串，以及从 `Host` 头中移除端口。

如果你足够幸运能够直接访问缓存键，你可以简单地比较注入不同输入后的键。否则，你可以利用你对缓存预言机的理解来推断你是否收到了正确的缓存响应。对于你要测试的每种情况，发送两个相似的请求并比较响应。

假设我们的缓存预言机是目标网站的首页。该页面会自动将用户重定向到区域特定页面。它使用 `Host` 头动态生成响应中的 `Location` 头：

```http
GET / HTTP/1.1
Host: vulnerable-website.com

HTTP/1.1 302 Moved Permanently
Location: https://vulnerable-website.com/en
Cache-Status: miss
```

为了测试端口是否从缓存键中排除，我们首先需要请求一个任意端口，并确保我们收到一个反映此输入的来自服务器的新鲜响应：

```http
GET / HTTP/1.1
Host: vulnerable-website.com:1337
```
```http
HTTP/1.1 302 Moved Permanently
Location: https://vulnerable-website.com:1337/en
Cache-Status: miss
```

接下来，我们再发送另一个请求，但这次不指定端口：

```http
GET / HTTP/1.1
Host: vulnerable-website.com
```
```http
HTTP/1.1 302 Moved Permanently
Location: https://vulnerable-website.com:1337/en
Cache-Status: hit
```

如你所见，即使请求中的 `Host` 头未指定端口，我们仍然获得了缓存的响应。这证明端口已从缓存键中排除。重要的是，完整的头仍然传递给应用程序代码并反映在响应中。

简而言之，尽管 `Host` 头是键控的，但缓存对其转换的方式允许我们将负载传递到应用程序中，同时仍然保留一个“正常”的缓存键，该键将映射到其他用户的请求。这种行为是本节中我们将讨论的所有漏洞利用背后的关键概念。

你可以使用类似的方法来研究缓存对你输入的任何其他处理。你的输入是否以任何方式被规范化？你的输入如何存储？你是否注意到任何异常？稍后我们将通过具体示例来介绍如何回答这些问题。

### 识别可利用的“小工具”

到目前为止，你应该对目标网站的缓存行为有了相对扎实的了解，并且可能已经发现了一些关于缓存键构建方式的有趣缺陷。最后一步是识别一个合适的“小工具”，你可以将其与此缓存键缺陷串联起来。这是一项重要技能，因为任何 Web 缓存投毒攻击的严重性在很大程度上取决于你能够利用的小工具。

这些小工具通常是经典的客户端漏洞，例如反射型 XSS 和开放重定向。通过将它们与 Web 缓存投毒相结合，你可以大幅提升这些攻击的严重性，将反射型漏洞转变为存储型漏洞。你的负载将自动提供给任何访问普通、完全合法 URL 的用户，而无需诱使受害者访问特制 URL。

更有趣的是，这些技术使你能够利用许多未分类的漏洞，这些漏洞通常被视为“不可利用”而未修补。这包括资源文件中的动态内容，以及需要浏览器永远不会发送的畸形请求的漏洞利用。

### 未键控端口

`Host` 头通常是缓存键的一部分，因此，最初看起来不太可能用于注入任何类型的负载。然而，一些缓存系统会解析该头并从缓存键中排除端口。

在这种情况下，你有可能利用此头进行 Web 缓存投毒。例如，考虑我们之前看到的案例，其中重定向 URL 是基于 `Host` 头动态生成的。这可能使你能够通过简单地向请求添加任意端口来构建拒绝服务攻击。所有浏览到首页的用户将被重定向到一个无效端口，实际上使首页瘫痪，直到缓存过期。

如果网站允许你指定非数字端口，这种攻击可以进一步升级。例如，你可以利用它注入 XSS 负载。

### 未键控查询字符串

与 `Host` 头一样，请求行通常是键控的。然而，最常见的缓存键转换之一是完全排除查询字符串。

#### 检测未键控查询字符串

如果响应明确告诉你是否命中缓存，这种转换相对容易发现——但如果它不告诉你呢？这会产生副作用，使动态页面看起来像是完全静态的，因为很难知道你是在与缓存通信还是与服务器通信。

为了识别动态页面，你通常会观察更改参数值如何影响响应。但如果查询字符串未键控，大多数时候你仍然会命中缓存，因此无论你添加什么参数，都会得到不变的响应。显然，这也使得经典的缓存破坏查询参数变得多余。

幸运的是，有替代方法可以添加缓存破坏器，例如将其添加到不会干扰应用程序行为的键控头中。一些典型示例包括：

```http
Accept-Encoding: gzip, deflate, cachebuster
Accept: */*, text/cachebuster
Cookie: cachebuster=1
Origin: https://cachebuster.vulnerable-website.com
```

如果你使用 Param Miner，你还可以选择“Add static/dynamic cache buster”和“Include cache busters in headers”选项。然后，它会自动在你使用 Burp 手动测试工具发送的任何请求中，将缓存破坏器添加到常见的键控头中。

另一种方法是查看缓存和后端在规范化请求路径方面是否存在任何差异。由于路径几乎可以肯定是被键控的，你有时可以利用这一点发出具有不同键但仍能命中同一端点的请求。例如，以下条目可能各自被单独缓存，但在后端被视为等同于 `GET /`：

- Apache: `GET //`
- Nginx: `GET /%2F`
- PHP: `GET /index.php/xyz`
- .NET: `GET /(A(xyz)/`

这种转换有时会掩盖本来显而易见的反射型 XSS 漏洞。如果渗透测试人员或自动化扫描仪只收到缓存响应而未意识到，就可能表现为页面上没有反射型 XSS。

#### 利用未键控查询字符串

从缓存键中排除查询字符串实际上可以使这些反射型 XSS 漏洞更加严重（将本来不会被普通用户访问到的特殊构造缓存，转为普通端点缓存）。

通常，此类攻击依赖于诱使受害者访问恶意构造的 URL。然而，通过未键控查询字符串投毒缓存，会导致负载被提供给访问本来完全正常 URL 的用户。这有可能影响更多受害者，而无需攻击者进一步交互。

### 特定未键控查询参数

到目前为止，我们已经看到在某些网站上，整个查询字符串会从缓存键中排除。但有些网站只排除与后端应用程序不相关的特定查询参数，例如用于分析或定向广告的参数。像 `utm_content` 这样的 UTM 参数是测试期间很好的检查候选者。

已从缓存键中排除的参数不太可能对响应产生重大影响。很可能不会存在任何接受这些参数输入的有用小工具。尽管如此，一些页面以易受攻击的方式处理整个 URL，使得利用任意参数成为可能。

### 缓存参数隐藏

如果缓存从缓存键中排除了一个无害参数，并且你找不到任何基于完整 URL 的可利用小工具，你可能认为自己走进了死胡同。然而，这实际上正是事情变得有趣的地方。

如果你能弄清楚缓存如何解析 URL 以识别和删除不需要的参数，你可能会发现一些有趣的怪癖。特别值得关注的是缓存和应用程序之间的任何解析差异。这可能会允许你通过将任意参数“隐藏”在被排除的参数中，从而将其偷偷放入应用程序逻辑。

例如，事实上的标准是，参数如果查询字符串中的第一个，则以问号（`?`）开头，否则以与号（`&`）开头。一些编写不佳的解析算法会将任何 `?` 视为新参数的开始，无论它是否为第一个。

假设从缓存键中排除参数的算法以这种方式运作，但服务器的算法只接受第一个 `?` 作为分隔符。考虑以下请求：

```http
GET /?example=123?excluded_param=bad-stuff-here
```

在这种情况下，缓存会识别两个参数，并从缓存键中排除第二个。但是，服务器不接受第二个 `?` 作为分隔符，而是只看到一个参数 `example`，其值是整个查询字符串的剩余部分，包括我们的负载。如果 `example` 的值被传递到一个有用的小工具中，我们就成功注入了负载而不影响缓存键。（即，将载荷隐藏在被视为非缓存键的构造中）

#### 利用参数解析怪癖

类似的参数隐藏问题也可能出现在相反的场景中，即后端识别出缓存未识别的不同参数。例如，Ruby on Rails 框架将与号（&）和分号（;）都解释为分隔符。当与不允许这样做的缓存结合使用时，你可以利用另一个怪癖来覆盖应用程序逻辑中键控参数的值。

考虑以下请求：

```http
GET /?keyed_param=abc&excluded_param=123;keyed_param=bad-stuff-here
```

顾名思义，`keyed_param` 包含在缓存键中，而 `excluded_param` 则不包含。许多缓存只会将其解释为两个由与号分隔的参数：

1. `keyed_param=abc`
2. `excluded_param=123;keyed_param=bad-stuff-here`

一旦解析算法移除 `excluded_param`，缓存键将只包含 `keyed_param=abc`。然而，在后端，Ruby on Rails 看到分号并将查询字符串拆分为三个独立的参数：

1. `keyed_param=abc`
2. `excluded_param=123`
3. `keyed_param=bad-stuff-here`

但现在出现了重复的 `keyed_param`。这是第二个怪癖发挥作用的地方。如果存在重复参数且每个参数具有不同值，Ruby on Rails 会优先处理最后一个出现的值。最终结果是缓存键包含一个无害的、期望的参数值，允许缓存响应正常提供给其他用户。但在后端，同一参数具有完全不同的值，即我们注入的负载。正是这第二个值将被传递给小工具并反映在被投毒的响应中。

如果它能让你控制将要执行的函数，这种漏洞利用会特别强大。例如，如果网站使用 JSONP 进行跨域请求，通常包含一个 `callback` 参数来对返回数据执行给定函数：

```http
GET /jsonp?callback=innocentFunction
```

在这种情况下，你可以使用这些技术来覆盖预期的回调函数，并改为执行任意 JavaScript。

#### 利用胖 GET 支持

在特定情况下，HTTP 方法可能未被键控。这可能允许你用包含正文中恶意负载的 `POST` 请求投毒缓存。然后你的负载甚至会被提供给用户的 `GET` 请求作为响应。虽然这种情况相当罕见，但你有时可以通过简单地向 `GET` 请求添加正文来创建“胖”`GET` 请求，以达到类似效果：

```http
GET /?param=innocent HTTP/1.1

param=bad-stuff-here
```

在这种情况下，缓存键将基于请求行，但参数的服务器端值将从正文中获取。

只有在网站接受带有正文的 `GET` 请求时才可能实现，但也有潜在的变通方法。你有时可以通过覆盖 HTTP 方法来鼓励“胖 GET”处理，例如：

```http
GET /?param=innocent HTTP/1.1
Host: innocent-website.com
X-HTTP-Method-Override: POST
…
param=bad-stuff-here
```

只要 `X-HTTP-Method-Override` 头未键控，你就可以提交一个伪 `POST` 请求，同时保留从请求行派生的 `GET` 缓存键。

#### 利用资源导入中的动态内容

导入的资源文件通常是静态的，但有些会反映来自查询字符串的输入。这通常被认为无害，因为浏览器在直接查看这些文件时很少执行它们，而且攻击者无法控制用于加载页面子资源的 URL。然而，通过将其与 Web 缓存投毒相结合，你有时可以将内容注入资源文件。

例如，考虑一个在导入语句中反映当前查询字符串的页面：

```http
GET /style.css?excluded_param=123);@import… HTTP/1.1
```
```http
HTTP/1.1 200 OK
…
@import url(/site/home/index.part1.8a6715a2.css?excluded_param=123);@import…
```

你可以利用此行为注入恶意 CSS，从而从任何导入 `/style.css` 的页面窃取敏感信息。

如果导入 CSS 文件的页面未指定 `doctype`，你甚至可能可以利用静态 CSS 文件。在正确的配置下，浏览器只会搜索文档中的 CSS 并执行它。这意味着你有时可以通过触发反映被排除查询参数的服务器错误来投毒静态 CSS 文件：

```http
GET /style.css?excluded_param=alert(1)%0A{}*{color:red;} HTTP/1.1

HTTP/1.1 200 OK
Content-Type: text/html
…
This request was blocked due to…alert(1){}*{color:red;}
```

### 规范化缓存键

对缓存键应用的任何规范化也可能引入可利用的行为。事实上，它有时甚至可以启用一些否则几乎不可能实现的漏洞利用。

例如，当你在参数中发现反射型 XSS 时，在实践中通常无法利用。这是因为现代浏览器在发送请求时通常会对必要字符进行 URL 编码，而服务器不会解码它们。预期受害者收到的响应仅包含无害的 URL 编码字符串。（即，攻击者发送到服务器的未编码反射 XSS 载荷，在预期受害者的浏览器中将被编码发送。且服务器最终不会解码，导致载荷无法在受害者浏览器中执行）

某些缓存实现在将键控输入添加到缓存键时对其进行规范化。在这种情况下，以下两个请求将具有相同的键：

```http
GET /example?param="><test>
GET /example?param=%22%3e%3ctest%3e
```

这种行为允许你利用这些原本“不可利用”的 XSS 漏洞。如果你使用 Burp Repeater 发送恶意请求，你可以用未编码的 XSS 负载投毒缓存。当受害者访问恶意 URL 时，负载仍会被其浏览器进行 URL 编码；然而，一旦 URL 被缓存规范化，它将与包含未编码负载的响应具有相同的缓存键。

因此，缓存将提供被投毒的响应，并且负载将在客户端执行。你只需确保在受害者访问 URL 时缓存已被投毒。

### 缓存键注入 —— 使用组件分隔符

你有时会在键控头中发现客户端漏洞。这也是一个经典的“不可利用”问题，有时可以通过缓存投毒加以利用。

键控组件通常捆绑在一个字符串中以创建缓存键。如果缓存未正确对**组件之间的分隔符**进行转义，你可能利用此行为构造两个不同请求但具有相同缓存键。

以下示例使用双下划线分隔缓存键中的不同组件，并且未对其进行转义。你可以通过首先使用包含相应键控头中负载的请求投毒缓存来利用这一点：

```http
GET /path?param=123 HTTP/1.1
Origin: '-alert(1)-'__
```
```http
HTTP/1.1 200 OK
X-Cache-Key: /path?param=123__Origin='-alert(1)-'__

<script>…'-alert(1)-'…</script>
```

如果你随后诱导受害用户访问以下 URL，他们将收到被投毒的响应：

```http
GET /path?param=123__Origin='-alert(1)-'__ HTTP/1.1
```
```http
HTTP/1.1 200 OK
X-Cache-Key: /path?param=123__Origin='-alert(1)-'__
X-Cache: hit

<script>…'-alert(1)-'…</script>
```

注意此处的载荷格式：`__载荷__`，载荷前后添加缓存组件分隔符

## 投毒内部缓存

到目前为止，我们已经研究了如何利用外部 Web 缓存实现中的缺陷，以暴露隐藏在看似键控组件中的扩展攻击面。然而，除了使用独立的外部组件外，一些网站还在应用程序中直接实现缓存行为。这有几个优点，例如避免我们之前探讨的那种解析差异。

由于这些集成缓存是专门为特定应用程序构建的，这也为开发人员提供了更大的自由度来定制其行为。因此，这些缓存有时会以不寻常的方式运行，而你在需要与多个应用程序兼容的更标准化的外部缓存中通常不会看到这种行为。有时，这些奇怪的行为也可能为一些高严重性的缓存投毒漏洞利用提供机会。

其中一些缓存不是缓存整个响应，而是将响应分解为可重用的片段，并分别缓存每个片段。例如，用于导入广泛使用资源的片段可能作为独立的缓存条目存储。用户随后可能会收到一个包含来自服务器的内容以及来自缓存的多个单独片段的混合响应。

由于这些缓存的片段旨在跨多个不同响应中重用，因此缓存键的概念实际上并不适用。包含给定片段的每个响应都将重用相同的缓存片段，即使响应的其余部分完全不同。在这种场景下，投毒缓存会产生广泛影响，尤其是当你投毒了每个页面都会使用的片段时。由于没有缓存键，你只需一个请求就能为每个用户的每个页面投毒。

这通常只需要你使用基本的 Web 缓存投毒技术，例如操纵 `Host` 头。

### 如何识别内部缓存

集成应用级缓存带来的挑战之一是它们可能难以识别和调查，因为通常没有面向用户的反馈。为了识别这些缓存，你可以寻找一些迹象。

例如，如果响应反映了你上次请求的输入和之前请求的输入的混合，这是缓存存储片段而非完整响应的关键指标。如果你的输入在多个不同页面的响应中被反映，特别是在你从未尝试注入输入的页面中，这同样适用。

其他时候，缓存的行为可能非常不寻常，以至于最合乎逻辑的结论是它必须是一个独特且专门化的内部缓存。

当网站实现多层缓存时，可能难以理解幕后发生了什么以及网站的缓存系统如何运作。

### 安全测试内部缓存

在测试普通 Web 缓存时，我们建议使用缓存破坏器以防止被投毒的响应提供给其他用户。然而，如果集成缓存没有缓存键的概念，那么传统的缓存破坏器就毫无用处。这意味着很容易不小心为真实用户投毒缓存。

因此，在测试这类漏洞时，务必尽最大努力减轻潜在损害。在发送每个请求之前，仔细考虑注入负载的影响。特别是，你应该确保只使用你控制的域名来投毒缓存，而不是任意的“`evil-user.net`”。这样，如果出现问题，你可以控制接下来会发生什么。
