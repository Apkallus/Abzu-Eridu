# OpenID Connect

在本节中，我们将提供一些关于 OpenID Connect 的关键背景信息，以帮助您理解我们将要介绍的一些漏洞。如果您是 OAuth 和 OpenID Connect 的新手，我们建议您在尝试完成基于 OpenID 的实验之前先阅读本节。

[关联 portswigger 研究](https://portswigger.net/research/hidden-oauth-attack-vectors)

## 什么是 OpenID Connect？

OpenID Connect 扩展了 OAuth 协议，提供了一个专用的身份和认证层，位于基本 OAuth 实现之上。它增加了一些简单的功能，使 OAuth 的身份验证用例得到更好的支持。

OAuth 最初并非为身份验证而设计；它旨在成为应用程序之间为特定资源委派授权的一种手段。然而，许多网站开始定制 OAuth 作为身份验证机制。为实现此目的，它们通常请求读取一些基本用户数据的权限，如果获得此访问权限，就假设用户已在 OAuth 提供商一侧完成了身份验证。

这些朴素的 OAuth 身份验证机制远非理想。首先，客户端应用程序无法知道用户是在何时、何地或如何被认证的。由于这些实现中的每一个都是某种自定义变通方案，也没有标准的方式来为此目的请求用户数据。为了正确支持 OAuth，客户端应用程序必须为每个提供商配置单独的 OAuth 机制，每个机制都有不同的端点、独特的作用域集合等等。

OpenID Connect 通过添加标准化的、与身份相关的功能，使通过 OAuth 的身份验证以更可靠和统一的方式工作，从而解决了许多此类问题。

## OpenID Connect 如何工作？

OpenID Connect 可以无缝地嵌入到普通的 OAuth 流程中。从客户端应用程序的角度来看，关键区别在于存在一组附加的、标准化的作用域，这些作用域对所有提供商都是相同的，以及一个额外的响应类型：`id_token`。

### OpenID Connect 角色

OpenID Connect 的角色与标准 OAuth 基本相同。主要区别在于规范使用了略微不同的术语。

- **依赖方（Relying party）** —— 请求对用户进行身份验证的应用程序。这与 OAuth 客户端应用程序同义。
- **最终用户（End user）** —— 正在被认证的用户。这与 OAuth 资源所有者同义。
- **OpenID 提供商（OpenID provider）** —— 配置为支持 OpenID Connect 的 OAuth 服务。

### OpenID Connect 声明和作用域

术语“声明（claims）”指的是资源服务器上表示用户信息的 `key:value` 对。声明的一个示例可以是 `"family_name":"Montoya"`。

与基本 OAuth 的作用域因提供商而异不同，所有 OpenID Connect 服务都使用一组相同的作用域。为了使用 OpenID Connect，客户端应用程序必须在授权请求中指定作用域 `openid`。然后，它们可以包含一个或多个其他标准作用域：

- `profile`
- `email`
- `address`
- `phone`

这些作用域中的每一个都对应着对 OpenID 规范中定义的关于用户的一系列声明的读取访问权限。例如，请求作用域 `openid profile` 将授予客户端应用程序对与用户身份相关的一系列声明的读取访问权限，如 `family_name`、`given_name`、`birth_date` 等。

### ID 令牌

OpenID Connect 提供的另一个主要补充是 `id_token` 响应类型。它返回一个使用 JSON Web 签名（JWS）签名的 JSON Web 令牌（JWT）。JWT 载荷包含基于初始请求作用域的声明列表。它还包含有关用户上次由 OAuth 服务认证的方式和时间的信息。客户端应用程序可以使用此信息来决定用户是否已被充分认证。

使用 `id_token` 的主要好处是减少了客户端应用程序和 OAuth 服务之间需要发送的请求数量，从而总体上可能提供更好的性能。无需先获取访问令牌再单独请求用户数据，包含此数据的 ID 令牌在用户完成身份验证后立即发送到客户端应用程序。

与基本 OAuth 中仅依赖可信通道不同，ID 令牌中传输的数据的完整性基于 JWT 加密签名。因此，使用 ID 令牌可能有助于防御某些中间人攻击。然而，由于用于签名验证的加密密钥通过同一网络通道传输（通常暴露在 `/.well-known/jwks.json` 上），某些攻击仍然是可能的。

请注意，OAuth 支持多种响应类型，因此客户端应用程序发送同时包含基本 OAuth 响应类型和 OpenID Connect 的 `id_token` 响应类型的授权请求是完全可行的：

```
response_type=id_token token
response_type=id_token code
```

在这种情况下，ID 令牌以及代码或访问令牌将同时发送给客户端应用程序。

## 识别 OpenID Connect

如果客户端应用程序正在积极使用 OpenID Connect，这从授权请求中应该很明显。最可靠的检查方法是查找强制性的 `openid` 作用域。

即使登录过程最初看起来没有使用 OpenID Connect，仍然值得检查 OAuth 服务是否支持它。您可以尝试添加 `openid` 作用域或将响应类型更改为 `id_token`，并观察是否会导致错误。

与基本 OAuth 一样，查看 OAuth 提供商的文档以了解有关其 OpenID Connect 支持的任何有用信息也是一个好主意。您还可以尝试从标准端点 `/.well-known/openid-configuration` 访问配置文件。

## OpenID Connect 漏洞

OpenID Connect 的规范比基本 OAuth 严格得多，这意味着通常较少出现带有明显漏洞的古怪实现。也就是说，由于它只是 OAuth 之上的一层，客户端应用程序或 OAuth 服务仍可能容易受到我们之前介绍的一些基于 OAuth 的攻击。事实上，您可能已经注意到，我们所有的 OAuth 身份验证实验也使用了 OpenID Connect。

在本节中，我们将介绍 OpenID Connect 的一些额外功能可能引入的其他漏洞。

### 未受保护的动态客户端注册

OpenID 规范概述了一种允许客户端应用程序向 OpenID 提供商注册的标准化方式。如果支持动态客户端注册，客户端应用程序可以通过向专用的 `/registration` 端点发送 `POST` 请求来注册自己。此端点的名称通常在配置文件和文档中提供。

在请求体中，客户端应用程序以 JSON 格式提交其关键信息。例如，它通常需要包含一个白名单回调 URI 数组。它还可以提交一系列附加信息，例如它们想要暴露的端点名称、应用程序名称等。典型的注册请求可能如下所示：

```http
POST /openid/register HTTP/1.1
Content-Type: application/json
Accept: application/json
Host: oauth-authorization-server.com
Authorization: Bearer ab12cd34ef56gh89

{
    "application_type": "web",
    "redirect_uris": [
        "https://client-app.com/callback",
        "https://client-app.com/callback2"
        ],
    "client_name": "My Application",
    "logo_uri": "https://client-app.com/logo.png",
    "token_endpoint_auth_method": "client_secret_basic",
    "jwks_uri": "https://client-app.com/my_public_keys.jwks",
    "userinfo_encrypted_response_alg": "RSA1_5",
    "userinfo_encrypted_response_enc": "A128CBC-HS256",
    …
}
```

有两个规范定义了此请求中的参数：用于 OAuth 的 [RFC7591](https://tools.ietf.org/html/rfc7591) 和 [Openid Connect Registration 1.0](https://openid.net/specs/openid-connect-registration-1_0.html#rfc.section.3.1)。

OpenID 提供商应要求客户端应用程序进行身份验证。在上面的示例中，它们使用了 HTTP 承载令牌。然而，某些提供商将允许在没有任何身份验证的情况下进行动态客户端注册，这使攻击者能够注册自己的恶意客户端应用程序。根据这些攻击者可控制的属性值的使用方式，这可能产生各种后果。

例如，您可能已经注意到其中一些属性可以作为 URI 提供。如果 OpenID 提供商访问其中任何一个，除非有额外的安全措施，否则这可能会导致二阶 SSRF 漏洞：大多数服务器在收到注册请求时并不会立即解析这些 URL。它们只是保存这些参数，并在稍后的 OAuth 授权流程中使用它们。。

以下参数对于 SSRF 攻击特别有趣：

- **logo_uri** —— 引用客户端应用程序徽标的 URL。注册客户端后，您可以尝试使用新的“`client_id`”调用 OAuth 授权端点（“`/authorize`”）。登录后，服务器将要求您批准该请求，并可能显示来自“`logo_uri`”的图像。如果服务器自行获取图像，则 SSRF 应由此步骤触发。或者，服务器可能仅通过客户端“`<img>`”标签包含徽标。虽然这不会导致 SSRF，但如果 URL 未被转义，则可能导致跨站脚本（XSS）。

- **jwks_uri** —— 客户端 JSON Web Key Set [JWK] 文档的 URL。当使用 JWT 进行客户端认证 [RFC7523] 时，服务器需要此密钥集来验证向令牌端点发出的签名请求。为了测试此参数中的 SSRF，请使用恶意的“`jwks_uri`”注册一个新的客户端应用程序，执行授权流程以获取任何用户的授权码，然后使用以下正文获取“`/token`”端点：

  ```http
  POST /oauth/token HTTP/1.1
  ...

  grant_type=authorization_code&code=n0esc3NRze7LTCu7iYzS6a5acc3f0ogp4&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer&client_assertion=eyJhbGci...
  ```

  如果存在漏洞，服务器应向提供的“jwks_uri”发出服务器到服务器的 HTTP 请求，因为它需要此密钥来检查请求中“client_assertion”参数的有效性。不过，这可能只是一个[盲 SSRF] 漏洞，因为服务器期望一个正确的 JSON 响应。

- **sector_identifier_uri** —— 此 URL 引用一个包含 redirect_uri 值的单个 JSON 数组的文件。如果支持，服务器可能会在您提交动态注册请求时立即获取此值。如果未立即获取，请尝试在服务器上为此客户端执行授权。由于它需要知道 redirect_uris 才能完成授权流程，这将强制服务器向您的恶意 sector_identifier_uri 发出请求。

- **request_uris** —— 此客户端允许的 request_uris 数组。授权端点可能支持“request_uri”参数，以提供包含请求信息的 JWT 的 URL（参见 [https://openid.net/specs/openid-connect-core-1_0.html#rfc.section.6.2]）。

  即使**未启用动态客户端注册**，或者需要身份验证，我们也可以通过使用“request_uri”在授权端点上尝试 SSRF：

  ```http
  GET /authorize?response_type=code%20id_token&client_id=sclient1&request_uri=https://ybd1rc7ylpbqzygoahtjh6v0frlh96.burpcollaborator.net/request.jwt
  ```

  注意：不要将此参数与“redirect_uri”混淆。“redirect_uri”用于授权后的重定向，而“request_uri”在授权过程开始时由服务器获取。

  同时，我们见过的许多服务器不允许任意的“request_uri”值：它们只允许在客户端注册过程中预先注册的白名单 URL。这就是为什么我们需要事先提供“request_uris”：“https://ybd1rc7ylpbqzygoahtjh6v0frlh96.burpcollaborator.net/request.jwt”。

如果您以 OpenID 服务器为目标，“.well-known/openid-configuration”上的发现端点有时包含“registration_endpoint”、“request_uri_parameter_supported”和“require_request_uri_registration”等参数。这些可以帮助您找到注册端点和其他服务器配置值。

### 允许通过引用进行授权请求

到目前为止，我们已经研究了通过查询字符串提交授权请求所需参数的标准方式。某些 OpenID 提供商允许您选择以 JSON Web 令牌（JWT）的形式传递这些参数。如果支持此功能，您可以发送一个单独的 `request_uri` 参数，指向一个包含其余 OAuth 参数及其值的 JSON Web 令牌。根据 OAuth 服务的配置，此 `request_uri` 参数是 SSRF 的另一个潜在向量。

您也可以利用此功能来绕过对这些参数值的验证。某些服务器可能有效地验证了授权请求中的查询字符串，但可能未能充分地对 JWT 中的参数（包括 `redirect_uri`）应用相同的验证。

要检查是否支持此选项，您应该在配置文件或文档中查找 `request_uri_parameter_supported` 选项。或者，您可以尝试添加 `request_uri` 参数以查看它是否有效。您可能会发现某些服务器支持此功能，即使它们在文档中没有明确提及。
