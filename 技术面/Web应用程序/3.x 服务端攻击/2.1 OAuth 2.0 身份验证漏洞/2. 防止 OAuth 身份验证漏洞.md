# 如何防止 OAuth 身份验证漏洞

为了防止 OAuth 身份验证漏洞，OAuth 提供商和客户端应用程序都必须对关键输入实施健壮的验证，尤其是 `redirect_uri` 参数。OAuth 规范中内置的保护措施很少，因此开发人员自身需要尽可能确保 OAuth 流程的安全性。

需要注意的是，漏洞可能出现在客户端应用程序一侧，也可能出现在 OAuth 服务本身一侧。即使您自己的实现坚如磐石，您最终仍然依赖于另一端应用程序同样健壮。

## 针对 OAuth 服务提供商

- 要求客户端应用程序注册有效的 `redirect_uris` 白名单。尽可能使用严格的逐字节比较来验证任何传入请求中的 URI。只允许完全且精确的匹配，而不是使用模式匹配。这可以防止攻击者访问白名单域上的其他页面。

- 强制执行 `state` 参数的使用。其值还应通过包含一些不可猜测的、与会话相关的数据（例如包含会话 Cookie 的哈希值）来绑定到用户的会话。这有助于保护用户免受类似 CSRF 的攻击。这也使攻击者更难使用任何窃取的授权码。

- 在资源服务器上，确保验证访问令牌是否颁发给了发出请求的同一 `client_id`。您还应该检查所请求的作用域，以确保其与最初授予令牌的作用域匹配。

## 针对 OAuth 客户端应用程序

- 在实施 OAuth 之前，确保您完全了解其工作原理的细节。许多漏洞仅仅是由于对每个阶段确切发生的内容以及如何被利用缺乏简单的了解而引起的。

- 即使 `state` 参数不是强制性的，也应使用它。

- 不仅向 `/authorization` 端点发送 `redirect_uri` 参数，也向 `/token` 端点发送。

- 在开发移动或原生桌面 OAuth 客户端应用程序时，通常无法保持 `client_secret` 的私密性。在这些情况下，可以使用 `PKCE`（`RFC 7636`）机制来提供额外的保护，以防止访问代码被拦截或泄露。

- 如果您使用 OpenID Connect 的 `id_token`，请确保根据 JSON Web 签名、JSON Web 加密和 OpenID 规范对其进行了正确验证。

- 谨慎处理授权码——当加载外部图像、脚本或 CSS 内容时，它们可能通过 `Referer` 头泄露。同样重要的是，不要将它们包含在动态生成的 JavaScript 文件中，因为它们可能通过 `<script>` 标签从外部域加载代码执行。
