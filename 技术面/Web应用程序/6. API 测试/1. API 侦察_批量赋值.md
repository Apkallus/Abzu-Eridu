# API 测试

所有动态网站都由 API 组成，因此 SQL 注入等经典 Web 漏洞也可归类为 API 测试。在本主题中，我们将教你如何测试网站前端未完全使用的 API，重点放在 RESTful 和 JSON API 上。我们还将教你如何测试可能影响内部 API 的服务端参数污染漏洞。

## API 侦查概述

API 端点分析是侦察工具包中继子域名发现之后的下一项逻辑技能。该应用使用了哪些域？如果此应用有三个域（例如 `x.domain`、`y.domain` 和 `z.domain`），我应该注意它们各自可能有自己独特的 API 端点。

一般来说，我们可以使用与尝试查找子域名时非常类似的技术。暴力破解攻击和字典攻击在这里效果不错，但手动努力和逻辑分析也常常会得到回报。

在发现子域名之后，了解 Web 应用结构的第二步是查找 API。这一步将为我们提供开始理解某个暴露 API 用途所需的信息。当我们理解 API 为何通过网络暴露时，我们就能开始看到它如何融入应用以及它的业务目的是什么。

要开始 API 测试，你首先需要尽可能多地收集有关 API 的信息，以发现其攻击面。

首先，你应该识别 API 端点。这些是 API 接收关于其服务器上特定资源请求的位置。例如，考虑以下 `GET` 请求：

```http
GET /api/books HTTP/1.1
Host: example.com
```

此请求的 API 端点是 `/api/books`，它会与 API 交互以从图书馆检索书籍列表。另一个 API 端点可能是 `/api/books/mystery`，它将检索悬疑类书籍列表。

识别端点后，你需要确定如何与它们交互。这使你能够构造有效的 HTTP 请求来测试 API。例如，你应该了解以下信息：

- API 处理的输入数据，包括必填和可选参数。
- API 接受的请求类型，包括支持的 HTTP 方法和媒体格式。
- 速率限制和身份验证机制。

## API 类型

API 可分为公有或私有。

### 公有 API

正如 SOAP 服务附带 WSDL 文件一样，开发人员可能会选择使用 Swagger（现称为 OpenAPI）框架来设计和记录 RESTful API。该框架使开发人员能够详细描述其 API 的结构，包括每个可能 API 调用的名称、路径和参数。Swagger 定义通常以 JSON 或 YAML 格式编写。

获取此文档对于了解攻击面至关重要。同样重要的是查找此文档的旧版本，这些版本可能显示已弃用但仍然可运行且可能存在安全漏洞的代码。

请记住，无论这份文档意图如何，它可能不准确，也可能未披露完整的 API。

公有 API 也可能在共享库或 API 目录中记录。

### 私有 API

私有 API 的可见性取决于目标消费者是谁。一个 API 可以是私有的，但仅对订阅客户端（也称为“合作伙伴”）可访问，或仅对内部客户端（如公司内部的其他部门）可访问。使用侦查技术查找私有 API 也很重要。这些 API 可以通过多种技术发现，我们将在下文讨论。

通常，用户在其API请求中包含访问令牌。其他时候，用户需要使用特殊的身份验证头或Cookie。

## 测试目标

- 查找后端服务器代码支持的所有 API 端点，无论是否有文档记录。
- 查找后端服务器支持的每个端点的所有参数，无论是否有文档记录。
- 发现发送给客户端的 HTML 和 JavaScript 中与 API 相关的有趣数据。

## API 文档

在公有和私有两种情况下，API 文档的质量和准确性决定了其实用价值。公有 API 文档通常与所有人共享，而私有 API 文档仅与目标客户端共享。然而，无论哪种情况，发现意外泄露或以其他方式泄露的文档都将对您的调查有所帮助。

文档可以是人类可读和机器可读两种形式。人类可读的文档旨在帮助开发者理解如何使用 API，可能包含详细说明、示例和使用场景。机器可读的文档旨在供软件处理，用于自动化 API 集成和验证等任务，以 JSON 或 XML 等结构化格式编写。

无论 API 的可见性如何，搜索 API 文档都可能找到旧的、尚未发布或意外泄露的 API 文档。这些文档将非常有助于理解 API 暴露的攻击面。

### 浏览和爬取应用程序

使用 ZAP 或 Burp Suite 等拦截代理浏览应用程序，可以记录端点以供后续检查。此外，使用其内置的爬取功能，拦截代理可以帮助生成全面的端点列表。从爬取的 URL 中，查找具有明显 API URL 命名方案的链接。这些包括：

- `https://example.com/api/v1`（或 v2 等）
- `https://example.com/graphql`

或应用程序可能使用或依赖的子域名：

- `https://api.example.com/api/v1`

渗透测试人员应尽量尽可能多地触发应用程序的功能。这不仅是为了生成全面的端点列表，也是为了规避懒加载和代码拆分带来的问题。此外，渗透测试活动应包含不同权限级别的示例账户，以便浏览器和爬虫能够访问并暴露尽可能多的功能对应的端点。

完成此操作后，从浏览和爬取应用程序获得的端点信息，可帮助渗透测试人员使用 Postman 等其他工具编写目标的 API 文档。

### 分析拦截到的请求

在审计 REST API 时，使用拦截代理收集完整的 HTTP 请求。REST 服务使用的不仅仅是 URL 参数，因此捕获完整的请求体和头部至关重要。

分析收集到的请求，以识别非标准或隐藏参数：

- 识别影响应用程序行为或资源选择的 HTTP 头部。
- 确定 URL 段是否在多个 URL 中具有重复模式。包含日期、数字或标识符值的模式可能表示 URL 嵌入的参数。例如，在 URL `https://api.example.com/user/2026-10-03/profile` 中，日期段可能代表一个参数值。
- 识别格式化为 JSON、XML 或其他自定义结构的结构化参数值。
- 检查 URL 的最后一个元素。如果它缺少文件扩展名，则可能是一个参数。
- 查找高度变化的 URL 段。如果单个段在数百个请求中频繁变化，则它更可能代表参数值而非静态路径组件。

### 客户端应用程序

服务器发送给客户端的 HTML 和 JavaScript 是 API 及其他信息的绝佳来源。我们可以使用多种工具来帮助从传输到浏览器的 JavaScript 中提取敏感信息。这些工具通常基于两种方法之一：正则表达式或抽象语法树（AST）。还有一些通用工具可帮助我们组织或管理 JS 文件，以便于 AST 和正则表达式工具进行审查。

正则表达式方法更直接，通过搜索 JS 或 HTML 内容中的已知模式来查找信息。然而，这种方法可能会遗漏未在正则表达式中明确标识的内容。鉴于某些 JS 的结构，这种方法可能会遗漏大量信息。另一方面，AST 是表示源代码语法的树状结构。树中的每个节点对应代码的一部分。对于 JavaScript，AST 将代码分解为基本组件，使工具和编译器能够轻松理解和修改代码。

### 与 API 端点交互

识别 API 端点后，使用 Burp Repeater 和 Burp Intruder 与之交互。这使你能够观察 API 的行为并发现额外的攻击面。例如，你可以调查 API 如何响应更改 HTTP 方法和媒体类型。

在与 API 端点交互时，仔细查看错误消息和其他响应。有时它们包含可用于构造有效 HTTP 请求的格式信息。

> 观察应用程序是否使用了认证，如果我们遇到一个使用空载荷未返回任何有趣内容的端点，我们应该尝试的第一件事是附加一个授权头部，看看当我们以认证用户身份请求时，它是否有不同反应。

#### 识别支持的 HTTP 方法

HTTP 方法指定要对资源执行的操作。例如：

- `GET` - 从资源检索数据。
- `PATCH` - 对资源应用部分更改。
- `OPTIONS` - 检索关于资源上可用的请求方法类型的信息。

一个 API 端点可能支持不同的 HTTP 方法。而 HTTP 规范定义了特殊方法 `OPTIONS`，仅用于提供有关特定 API 动词的信息。然而，很少有应用会暴露 `OPTIONS`。因此，在调查 API 端点时，务必测试所有可能的方法。这可以让你识别额外的端点功能，从而打开更多攻击面。

例如，端点 `/api/tasks` 可能支持以下方法：

- `GET /api/tasks` - 检索任务列表。
- `POST /api/tasks` - 创建新任务。
- `DELETE /api/tasks/1` - 删除任务。

使用 Burp Intruder 中的内置 **HTTP verbs** 字典或其他工具暴破一系列方法。

#### 识别支持的内容类型

API 端点通常期望特定格式的数据。因此，它们的行为可能因请求中提供的数据内容类型而异。更改内容类型可以让你：

- 触发泄露有用信息的错误（揭示格式或字段）。
- 绕过有缺陷的防御措施。
- 利用处理逻辑的差异。例如，API 在处理 JSON 数据时可能是安全的，但在处理 XML 时可能容易受到注入攻击。

要更改内容类型，请修改 `Content-Type` 头，然后相应地重新格式化请求体。你可以使用 [Content type converter](https://portswigger.net/bappstore/db57ecbe2cb7446292a94aa6181c9278) BApp 自动将请求中提交的数据在 XML 和 JSON 之间转换。

#### 暴破隐藏端点

识别一些初始 API 端点后，使用自动化工具发现隐藏端点。例如，考虑一个场景，你已识别了以下用于更新用户信息的 API 端点：

`PUT /api/user/update`

要识别隐藏端点，暴破具有相同结构的其他资源。例如，你可以向路径的 `/update` 位置添加一个包含其他常见函数（如 `delete` 和 `add`）的负载。

在查找隐藏端点时，使用基于常见 API 命名约定和行业术语的单词列表。确保还包含基于你初始侦查的与应用程序相关的术语。

## 查找隐藏参数

在进行 API 侦查时，你可能会发现 API 支持未记录的参数。你可以尝试使用它们来改变应用程序的行为。Burp 包含多种工具，可帮助你识别隐藏参数：

- Burp Intruder 使你能够使用常见参数名称的单词列表自动发现隐藏参数，以替换现有参数或添加新参数。确保还包含基于你初始侦查的与应用程序相关的名称。
- [Param miner](https://portswigger.net/bappstore/17d2949a985c4b7ca092728dba871943) BApp 使你能够自动猜测每个请求多达 65,536 个参数名称。Param miner 会根据从范围中获取的信息自动猜测与应用程序相关的名称。
- [内容发现](https://portswigger.net/burp/documentation/desktop/tools/engagement-tools/content-discovery)工具使你能够发现未从可见内容链接的内容，包括参数。

sqlmap 工具包含一个 [common-columns.txt](https://github.com/sqlmapproject/sqlmap/blob/master/data/txt/common-columns.txt) 单词列表，可用于识别潜在的敏感属性。
常见有趣属性名称的小示例包括：

- `is_admin`
- `is_administrator`
- `isAdmin`
- `isAdministrator`
- `admin`
- `administrator`
- `role`

不安全的应用可能会以 HTTP 错误消息的形式给您提示。例如，假设您使用以下请求体调用 `POST https://www.mega-bank.com/users/config`：

```json
{
  "user_id": 12345,
  "privacy": {
    "publicProfile": true
  }
}
```

您很可能会收到类似 `401 not authorized` 或 `400 internal error` 这样的 HTTP 状态码。如果状态码附带了类似 `auth_token not supplied` 的消息，您可能偶然发现了一个缺失的参数。

在另一个带有正确 `auth_token` 的请求中，您可能会收到另一个错误消息：`publicProfile only accepts "auth" and "noAuth" as params`。

### 批量赋值漏洞

https://cwe.mitre.org/data/definitions/915.html

赋值攻击是一种常见的攻击对象的方法。虽然通常使用现代标准化术语“批量赋值攻击”或“批量赋值漏洞”来指代，但历史上也曾使用“自动绑定攻击”（针对 Spring MVC 和 ASP.NET 框架）和“对象注入攻击”（针对遗留 PHP 漏洞）等术语。所有这些术语都指同一套利用系统。

批量赋值漏洞：当软件框架自动将请求参数绑定到内部对象的字段时，允许攻击者通过向函数调用传递对象中额外的、未经键验证的字段，来更改应用程序支持开发者从未打算处理的、本不应该被更改的字段。

敏感属性示例：

- **与权限相关的属性**：
  应仅由特权用户设置（例如 `is_admin`、`role`、`approved`）。
- **与流程相关的属性**：
  应仅在流程完成后由内部设置（例如 `balance`、`status`、`email_verified`）。
- **内部属性**：
  应仅由应用程序内部设置（例如 `created_at`、`updated_at`）。

#### 识别隐藏参数

由于批量赋值从对象字段创建参数，你通常可以通过手动检查 API 返回的对象来识别这些隐藏参数，尤其注意：

- HTML 页面源代码
- 自定义 JavaScript 代码
- API 响应

例如，考虑一个 `PATCH /api/users/` 请求，它允许用户更新其用户名和电子邮件，并包含以下 JSON：

```json
{
    "username": "wiener",
    "email": "wiener@example.com",
}
```

并发的 `GET /api/users/123` 请求返回以下 JSON：

```json
{
    "id": 123,
    "name": "John Doe",
    "email": "john@example.com",
    "isAdmin": "false"
}
```

这可能表明隐藏的 `id` 和 `isAdmin` 参数与更新的用户名和电子邮件参数一起被绑定到内部用户对象。

#### 测试批量赋值漏洞

要测试你是否可以修改枚举出的 `isAdmin` 参数值，请将其添加到 `PATCH` 请求中：

```json
{
    "username": "wiener",
    "email": "wiener@example.com",
    "isAdmin": false,
}
```

此外，发送一个带有无效 `isAdmin` 参数值的 `PATCH` 请求：

```json
{
    "username": "wiener",
    "email": "wiener@example.com",
    "isAdmin": "foo",
}
```

如果应用程序行为不同，这可能表明无效值影响了查询逻辑，而有效值没有。这可能表明用户能够成功更新该参数。

然后，你可以发送一个将 `isAdmin` 参数值设置为 `true` 的 `PATCH` 请求，以尝试利用该漏洞：

```json
{
    "username": "wiener",
    "email": "wiener@example.com",
    "isAdmin": true,
}
```

如果请求中的 `isAdmin` 值在未经充分验证和清理的情况下被绑定到用户对象，用户 `wiener` 可能被错误地授予管理员权限。要确定是否如此，请以 `wiener` 身份浏览应用程序，查看你是否可以访问管理功能。

#### 批量赋值示例：JavaScript

批量赋值漏洞通常出现在那些大量传递状态相关数据（以对象形式）的系统。一个典型的容易受到批量赋值攻击的应用是视频游戏，它会经常传递用户状态信息。另一种可能易受攻击的应用是实现了“动态表单”的 Web 应用，即表单的标题、数据类型等可以由最终用户更改。如果没有考虑到安全性进行编程，这两种应用都很容易受到批量赋值攻击。

以下代码片段描述了一种常见的批量赋值漏洞形式：

```javascript
/*
 * 这是一个服务端 API 端点，用于更新基于 Web 的视频游戏 "MegaGame" 的玩家数据。
 */
app.post("updatePlayerData", function(req, res, next) {
  // 如果客户端发回了玩家状态数据，则在数据库中更新
  if (!!req.body.data) {
    db.update(session.currentUser, req.body.data);
    return res.sendStatus(200); // 成功
  } else {
    return res.sendStatus(400); // 错误
  }
});
```

在这个批量赋值漏洞的示例中，视频游戏 MegaGame 实现了一个可通过 HTTP POST 访问的 API 端点。该端点从客户端（Web 浏览器）接收一个参数，形式为状态对象。如果状态对象不为空，API 端点会调用数据库辅助库，使用客户端（代表正在玩游戏的用户）提供的状态来更新当前用户的游戏状态。

API 端点中引用的 `db.update()` 函数编写如下：

```javascript
const update = function(data) {
  for (const [key, value] of Object.entries(data)) {
    database.upsert({ `${key}`: `${value}` })
  }
}
```

请注意，这个 `update()` 函数中的问题（漏洞）并不在于它 upsert（如果不存在则插入，如果存在则更新）客户端提供的数据。相反，批量赋值漏洞之所以出现，是因为该函数没有验证客户端提供的任何信息，尤其是 `data` 对象中的键。

该应用开发者的假设是客户端会传回包含以下数据的载荷：

```javascript
const data = {
  playerId: 123,
  playerPosition: { "x": 125, "y": 346 },
  playerHP: 90
};
```

因为 `update()` 函数缺乏任何验证，并直接接受来自客户端的原始数据，黑客可以在传输过程中修改载荷，或者发送一个恶意载荷，包含以下数据：

```javascript
const data = {
  playerId: 123,
  playerPosition: { "x": 125, "y": 346 },
  playerHP: 90,
  isAdmin: true // 这是载荷的“攻击”部分
};
```

通过修改载荷使其包含 `isAdmin` 键，`update()` 函数将在用户数据库行中写入或修改 `isAdmin` 条目。现在，用户通过滥用 `update()` 函数中未进行清理和验证的事实，将其在游戏中的角色提升为管理员。如果 `update()` 函数验证了对象的键并对 `isAdmin` 键进行了清理，那么当这个恶意载荷命中 `updatePlayerData` 端点时，就不会发生角色升级。

#### 批量赋值示例：Java

假设一个 Java Web 应用程序具有类似于以下的 `User` 对象：

```java
public class User {
   private String username;
   private String password;
   private String email;
   private boolean isAdmin;

   //Getters & Setters
}
```

为了创建一个新的 `User`，Web 应用程序实现了以下视图：

```html
<form action="/createUser" method="POST">
     <input name="username" type="text">
     <input name="password" type="text">
     <input name="email" text="text">
     <input type="submit" value="Create">
</form>
```

处理创建请求的控制器（Spring 提供与 `User` 模型的自动绑定）：

```java
@RequestMapping(value = "/createUser", method = RequestMethod.POST)
public String createUser(User user) {
   userService.add(user);
   return "successPage";
}
```

当表单提交时，浏览器生成以下请求：

```http
POST /createUser
[...]
username=bob&password=supersecretpassword&email=bob@domain.test
```

然而，由于自动绑定，攻击者可以向请求添加 `isAdmin` 参数，控制器将自动将其绑定到模型。

```http
POST /createUser
[...]
username=bob&password=supersecretpassword&email=bob@domain.test&isAdmin=true
```

然后，用户以 `isAdmin` 属性设置为 `true` 的方式被创建，从而在应用程序中授予其管理权限。

#### 灰盒测试

采用灰盒测试方法进行分析时，可以遵循相同的方法来验证问题。然而，由于对应用程序有更深入的了解，可以更轻松地识别易受批量赋值漏洞影响的框架和处理器。

特别是当源代码可用时，可以更准确、更轻松地搜索输入向量。在源代码审查期间，可使用简单工具（如 `grep` 命令）在应用程序代码中搜索一个或多个常见模式。

访问数据库模式或源代码也能帮助快速识别敏感字段。

##### Java

Spring MVC 允许将用户输入自动绑定到对象。识别处理状态更改请求的控制器（例如，查找 `@RequestMapping` 的出现位置），然后验证是否实施了控制措施（无论是在控制器中还是在涉及模型中）。对批量赋值利用的限制可能采取以下形式：

- 通过 `DataBinder` 类的 `setAllowedFields` 方法设置可绑定字段列表（例如 `binder.setAllowedFields(["username","password","email"])`）
- 通过 `DataBinder` 类的 `setDisallowedFields` 方法设置不可绑定字段列表（例如 `binder.setDisallowedFields(["isAdmin"])`）

还应注意 `@ModelAttribute` 注解的使用，它允许指定不同的名称/键。

##### PHP

Laravel Eloquent ORM 提供了 `create` 方法，允许自动分配属性。然而，最新版本的 Eloquent ORM 提供了针对批量赋值漏洞的默认保护，要求通过 `$fillable` 数组显式指定允许自动分配的属性，或通过 `$guarded` 数组指定需要保护的属性（不可绑定）。因此，通过分析模型（扩展 `Model` 类的类），可以识别哪些属性被允许或拒绝，从而指出潜在漏洞。

##### .NET

ASP.NET 中的模型绑定会自动将用户输入绑定到对象属性。这也适用于复杂类型，并且如果输入与属性名称匹配，它将自动将输入数据转换为属性。识别控制器，然后验证是否实施了控制措施（无论是在控制器内部还是在涉及的模型中）。对批量赋值利用的限制可能采取以下形式：

- 声明为 `ReadOnly` 的字段
- 通过 `Bind` 属性（例如 `[Bind(Include = "FirstName, LastName")] Student std`）、`includeProperties`（例如 `includeProperties: new[] { "FirstName, LastName" }`）或通过 `TryUpdateModel` 设置可绑定字段列表
- 通过 `Bind` 属性（例如 `[Bind(Exclude = "Status")] Student std`）或通过 `excludeProperties`（例如 `excludeProperties: new[] { "Status" }`）设置不可绑定字段列表

## 预防 API 中的漏洞

在设计 API 时，确保从一开始就将安全性纳入考虑。具体来说，请确保：

- 如果你不打算让 API 公开访问，请保护你的文档。
- 确保你的文档保持最新，以便合法测试人员能够全面了解 API 的攻击面。
- 应用允许的 HTTP 方法白名单。
- 验证每个请求或响应的内容类型是否符合预期。
- 使用通用错误消息，避免泄露对攻击者有用的信息。
- 对你的 API 的所有版本都使用保护措施，而不仅仅是当前的生产版本。

为防止批量赋值漏洞，请允许用户可更新的属性白名单，并阻止不应由用户更新的敏感属性。防止此问题的一种架构方法是使用*数据传输对象*（DTO）模式以避免直接绑定。DTO 应仅包含旨在供用户编辑的字段。
