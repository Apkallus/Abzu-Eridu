# API 测试概述

## Web API 简介

Web 应用程序编程接口（API）促进了不同软件系统之间通过网络或互联网进行通信和数据交换。Web API 使不同应用程序能够以标准化、高效的方式相互交互，从而允许它们利用彼此的功能和数据。

云计算、微服务架构和单页应用程序等不同技术的采用，都推动了 API 作为一种架构趋势的兴起。

与任何新概念的引入一样，缺陷和漏洞的出现使得测试成为必要。否则，安全防护薄弱的 API 可能成为通向敏感数据的无限制直接路径。

本章旨在引导安全研究人员掌握测试 API 所需的概念。本节特别探讨了不同的 API 技术及其发展历史。

## 选择哪种 API 技术？

在对我们正在测试的 API 类型做出假设之前，了解安全研究人员可能遇到的整个问题空间的全貌会有所帮助。这些包括：

1. 表述性状态转移（REST）API
    - 架构风格
2. gRPC 远程过程调用（gRPC）
    - 使用诸如 XML-RPC（使用 XML 进行数据传输）和 JSON-RPC（使用 JSON）等协议
3. 简单对象访问协议（SOAP）API
    - 可视为 XML-RPC 的后继者，它通过使用加密和数字签名提供了更好的安全性。
4. GraphQL API （独立章节）
5. WebSocket API （独立章节）

### RPC 与 REST 的区别

以下是 RPC 和 REST 之间的一些关键区别：

|          | RPC                                  | REST                                 |
|----------|--------------------------------------|--------------------------------------|
| **焦点** | 动作驱动                             | 数据驱动                             |
| **说明** | RPC 以名词为中心；侧重于远程函数/过程的调用并返回客户端响应。通常在你希望提供一组严格指令时使用。 | REST 以资源为中心；使用 HTTP 动词与资源交互。侧重于使用 HTTP 方法执行的操作。 |
| **方法示例** | 考虑一个负责管理预订的 Web 服务。RPC 将调用用于搜索酒店和预订的方法：<br>`hotelSearch(location, check-in, check-out)`——根据位置和日期检索酒店可用性。<br>`bookHotel(hotelId, guestInfo)`——为选定的酒店进行预订。 | REST API 将具有诸如“hotels”之类的端点，并使用 HTTP 动词来检索酒店，而不是调用唯一的函数。<br>`GET /hotels/{hotelId}`——检索酒店列表。<br>`POST /hotels/{hotelId}/bookings`——为选定的酒店进行预订。 |
| **用例** | 在根据特定条件搜索可用酒店时很有用。 | 在检索酒店列表时很有用。然而，它们可以互换使用。 |

### 单体架构与分布式架构

与过去应用程序构建在单体架构上不同，Web 服务也促进了更通用和分布式系统的创建。在单体架构中，一个单一的服务器保存整个 Web 应用程序代码以及相关组件（如数据库）。虽然这种方法在易于管理方面具有优势，但它也有自己的缺点，其中一个组件出现故障就可能导致整个系统瘫痪——Web 服务迎来了微服务架构时代。在这里，应用程序被分解为松散耦合的服务，每个服务执行特定的功能。这消除了单点故障，提高了整体系统的弹性。

让我们以预订网站为例。它由几个微服务组成，每个微服务负责一个特定的功能：用户登录服务处理用户认证和授权；预订搜索服务返回特定日期的可用酒店并提供价格比较；预订服务管理房间预订、确认和取消；支付服务处理交易和第三方交互。

如果在任何时候，预订搜索微服务宕机，用户仍然能够登录其账户、查看和取消现有预订，并访问其他功能。与单体架构相比，这提供了显著的优势，因为如果发生故障，整个系统都会宕机。同样，微服务架构可能允许根据需求进行选择性扩展。例如，在旺季，预订搜索服务和预订服务可能经历高需求，而其他组件则不然。这就是 Docker 和 Kubernetes 等技术发挥作用的地方。

在这种设计中，每个微服务都托管在自己的 Docker 容器中，Kubernetes 用于管理和编排这些服务，允许独立扩展特定服务而不影响系统的其余部分。

## REST（表述性状态转移）API

### 什么是 REST？

REST 是一套用于与 Web 资源交互的规则和约定。URI、HTTP 方法、头部和状态码等关键组件支持 REST 的各项原则。

REST Web 服务主要使用 JSON 或 XML 进行数据传输；然而，消息格式并不严格限于这些格式。其他格式（如纯文本、HTML 等）也可以用作消息格式。

### 发展历史

由于其简单性、可扩展性以及与现有 Web 基础设施的兼容性，在撰写本文时，基于 REST 的 API 已成为互联网上最常见的 API 架构。基于 REST 的 API 经历了从研究到广泛采用的漫长过程。

1994 年，HTTP 规范的主要作者之一 Roy Fielding 在加州大学欧文分校的博士论文中开始了 REST 的研究工作。到 2000 年，他发表了论文《[架构风格与基于网络的软件架构设计](https://ics.uci.edu/~fielding/pubs/dissertation/top.htm)》，在文中引入并将 REST 定义为一组架构风格。REST 旨在利用 HTTP 的现有特性，强调可扩展性、无状态交互和统一接口。

2010 年代，由于 REST 的简单性以及与 Web 底层架构的兼容性，它成为 Web API 的事实标准。RESTful API 的广泛使用得益于移动应用、云计算和微服务架构的增长。Swagger/OpenAPI、RAML 和 API Blueprint 等工具和框架的开发，促进了 REST API 的设计、文档编写和测试。

到 2020 年代，GraphQL 等技术的出现推动了 REST 的进一步发展。同时，OpenAPI/Swagger 规范成为描述 REST API 的广泛采用标准，实现了更好的集成和自动化。

### 统一资源标识符

REST API 使用统一资源标识符（URI）来访问资源。URI 是 REST 架构的关键元素。URI 是一串字符，用于唯一标识特定资源。URI 在互联网上广泛用于定位和交互资源，如网页、文件和服务。

URI 由多个组件组成，每个组件都有特定用途。根据 [RFC3986](https://tools.ietf.org/html/rfc3986) 定义的通用 URI 语法如下：

> `URI = scheme "://" authority "/" path [ "?" query ] [ "#" fragment ]`

对于 REST，**方案（scheme）** 通常为 `HTTP` 或 `HTTPS`，但广义上指示用于访问资源的协议或方法。其他常见方案包括 `ftp`、`mailto` 和 `file`。

**权限（authority）** 指定资源所在服务器的域名或 IP 地址，并可能包含端口号。它也可能包含用户信息作为子组件。

**路径（path）** 指定资源在服务器上的具体位置。我们关注 URI 的路径，因为它反映了用户与资源之间的关系。例如，`https://api.example.com/admin/testing/report` 可能显示一份测试报告。其中体现了管理员用户与其报告之间的关系。

任何 URI 的路径都将定义 REST API 的资源模型。资源以正斜杠分隔，并基于自上而下的设计。

例如：

- `https://api.example.com/admin/testing/report`
- `https://api.example.com/admin/testing/`
- `https://api.example.com/admin/`

**查询（query）** 提供资源的额外参数。它以 `?` 开头，由 `&` 分隔的键值对组成。

**片段（fragment）** 指示资源的特定部分，例如网页中的某个章节。它以 `#` 开头。需要注意的是，片段标识符仅在客户端处理，不会发送到服务器。

### HTTP 方法

REST API 使用标准的 HTTP 方法对资源执行操作，遵循 [RFC7231](https://tools.ietf.org/html/rfc7231) 中定义的 [HTTP 请求方法](https://tools.ietf.org/html/rfc7231#section-4)。这些方法映射到 CRUD，即计算机科学中持久存储的四种基本操作。CRUD 代表创建（Create）、读取（Read）、更新（Update）和删除（Delete），是对数据可执行的四种操作。

HTTP 请求方法包括：

| 方法    | 描述                           |
|---------|--------------------------------|
| GET     | 获取资源状态的表示              |
| POST    | 创建新资源                      |
| PUT     | 更新资源                        |
| DELETE  | 移除资源                        |
| HEAD    | 获取资源状态相关的元数据         |
| OPTIONS | 列出可用方法                    |

#### 头部

REST 依赖头部来支持在请求或响应中传递附加信息。这些头部包括：

- `Content-Type`：指示资源的媒体类型（例如 `application/json`）。
- `Authorization`：包含身份验证凭据（例如令牌）。
- `Accept`：指定响应可接受的媒体类型。

#### 状态码

遵循 REST 原则的应用程序 API 使用 HTTP 响应消息中的状态码，向客户端通知其请求的结果。

| 状态码 | 状态消息           | 描述                                                         |
|--------|-------------------|------------------------------------------------------------|
| 200    | OK                | 成功处理客户端请求                                           |
| 201    | Created           | 新资源已创建                                                 |
| 301    | Moved Permanently | 永久重定向                                                  |
| 304    | Not Modified      | 缓存相关响应，当客户端拥有与服务器相同的资源副本时返回        |
| 307    | Temporary Redirect| 资源的临时重定向                                             |
| 400    | Bad Request       | 客户端请求格式错误                                           |
| 401    | Unauthorized      | 客户端无权发出请求或访问特定资源                              |
| 403    | Forbidden         | 客户端被禁止访问该资源                                       |
| 404    | Not Found         | 资源不存在，或根据请求不正确                                 |
| 405    | Method Not Allowed| 使用了无效或未知的方法                                       |
| 500    | Internal Server Error| 服务器因内部错误无法处理请求                              |

## SOAP API

SOAP 是一种 RPC 协议，它使用 XML 访问 Web 服务，在 REST 之前广泛流行。虽然 SOAP 如今不再非常普遍，但在许多企业系统中仍在使用。

由于 SOAP 基于 XML 协议构建，我们在前面章节中研究的所有基于 XML 的漏洞（如 XPath、XML、XXE 注入等）在处理 SOAP 应用程序时仍然适用。

这些漏洞并非 SOAP 协议本身固有的，而是 Web 应用程序处理 SOAP 消息的方式导致的。如果来自 SOAP 请求的数据在未经适当清理或参数化的情况下用于构造 SQL 查询，并且如果来自 SOAP 请求的数据未经清理就传递给 shell 函数，则会导致远程代码执行。

SOAP API使用XML传输数据，其消息具有头和体。一个简单的SOAP请求如下所示：

```http
DELETE / HTTPS/1.1
Host: example.s3.amazonaws.com

<DeleteBucket xmlns="http://doc.s3.amazonaws.com/2006-03-01">
    <Bucket>quotes</Bucket>
    <AWSAccessKeyId>AKIAIOSFODNN7EXAMPLE</AWSAccessKeyId>
    <Timestamp>2006-03-01T12:00:00.183Z</Timestamp>
    <Signature>Iuyz3d3P0aTou39dzbqaEXAMPLE=</Signature>
</DeleteBucket>
```

此示例请求取自Amazon S3的SOAP API文档。它删除一个名为`quotes`的S3存储桶。如你所见，API请求参数作为XML文档中的标签传递给服务器。

SOAP响应如下所示：

```xml
<DeleteBucketResponse xmlns="http://s3.amazonaws.com/doc/2006-03-01">
    <DeleteBucketResponse>
        <Code>204</Code>
        <Description>No Content</Description>
    </DeleteBucketResponse>
</DeleteBucketResponse>
```

此响应表示存储桶已成功删除，不再存在。

### 与 SOAP 服务交互

一旦识别出 SOAP 服务，下一步就是了解如何与之交互。与通常需要外部文档的 REST API 不同，SOAP 服务通常提供 Web 服务描述语言（WSDL）文档，这是一个 XML 文档，可以视为一种内置文档。

WSDL 文件提供了 Web 服务允许的操作的完整列表，指定了所需的参数、输入和输出的正确语法甚至数据类型。该文件通常在 SOAP Web 服务必须对公众保持可访问性时使用。虽然它为开发人员提供了与 Web 服务交互的简化方式，但也为攻击者提供了识别潜在漏洞的宝贵信息。

WSDL 文件通常可以通过在端点 URL 后附加`.wsdl`或`?wsdl`来访问，或搜索包含术语`wsdl`的URL端点。例如，如果您的 Web 服务端点是 `http://example.com/webservice`，您可以通过导航到 `http://example.com/webservice?wsdl` 来访问 WSDL 文档。

> 额外，**SOAPAction 欺骗**：研究和理解如何使用 SOAP 操作欺骗来滥用 SOAP 服务。

## JSON-RPC

JSON-RPC 是一种 RPC 协议，利用 JSON 在客户端和服务器之间交换消息。与 XML-RPC 相比，JSON-RPC 具有多项优势，例如使用 JSON 实现人类可读消息以及更小的消息大小，从而提高网络性能和效率。

根据 JSON-RPC 的实现方式以及用户输入的处理方式，JSON-RPC 可能导致 SQL 注入、RCE 和 IDOR。

为了说明，让我们看一个 JSON-RPC 的基本请求和响应示例。以下请求调用“getEmail”方法以获取 userID 1 的详细信息。

**请求：**
```json
{
    "jsonrpc": "2.0",   // 指定版本
    "method": "getEmail", // 指示正在调用的方法
    "params": {
        "userId": 1
    },                  // 包含输入参数
    "id": 1             // 分配唯一标识符以匹配请求/响应
}
```

此请求是使用 JSON 序列化的单个对象，包含三个属性：method、params 和 ID。以下是示例响应：

**响应：**
```json
{"jsonrpc": "2.0", "result": "tmgm@tmgm.com", "id": 1}
```
