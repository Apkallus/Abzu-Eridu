# 服务端参数污染

有些系统包含无法直接从互联网访问的内部 API。当网站将用户输入嵌入到内部 API 的服务端请求中，且未进行充分编码时，就会产生服务端参数污染。这意味着攻击者可能能够操纵或注入参数，从而实现例如：

- 覆盖现有参数。
- 修改应用程序行为。
- 访问未授权数据。

你可以测试任何用户输入是否存在参数污染。例如，查询参数、表单字段、头部和 URL 路径参数都可能存在漏洞。

![服务端参数污染示例](https://portswigger.net/web-security/api-testing/images/api-testing-2.jpg)

> **注意**
> 此漏洞有时被称为 HTTP 参数污染。然而，该术语也用于指代 Web 应用程序防火墙（WAF）绕过技术。为避免混淆，在本主题中我们将仅使用“服务端参数污染”这一说法。
> 
> 此处，参数污染不仅对应参数覆盖，还包含参数注入
> 
> 此外，尽管名称相似，此类漏洞与服务端原型污染几乎没有共同点。

## 测试查询字符串中的服务端参数污染

许多服务器会在所请求的 URL 抵达时重写这些 URL，再将它们映射到应用程序中的相关后端功能。除传统的 URL重写外，服务器在处理 REST风格的参数、定制导航包装器以及其他 URL转换方法时都会进行 URL重写。这种处理方式可能易受服务器端参数污染攻击。

为了简化和便于导航，一些应用程序在 URL 的文件路径，而非查询字符串中插入参数值。通常，应用程序会通过一些简单的规则转换 URL 为后端请求，然后将其转发给真正的目标。

在这种情况下，攻击者就可以利用服务器端参数污染攻击在经过重写的 URL 中注入另一个参数。这种攻击能否成功取决于服务器如何处理重复的参数

要测试查询字符串中的服务端参数污染，请在输入中放置 `#`、`&` 和 `=` 等查询语法字符，并观察应用程序如何响应。

考虑一个易受攻击的应用程序，它允许你根据用户名搜索其他用户。当你搜索用户时，浏览器会发出以下请求：

```http
GET /userSearch?name=peter&back=/home
```

为了检索用户信息，服务器会向内部 API 发出以下请求：

```http
GET /users/search?name=peter&publicProfile=true
```

### 截断查询字符串

你可以使用 URL 编码的 `#` 字符来尝试截断服务端请求。为了帮助解释响应，你也可以在 `#` 字符后添加一个字符串。

例如，你可以将查询字符串修改为：

```http
GET /userSearch?name=peter%23foo&back=/home
```

前端将尝试访问以下 URL：

```http
GET /users/search?name=peter#foo&publicProfile=true
```

> **注意**
> 务必对 `#` 字符进行 URL 编码，否则前端应用程序会将其解释为片段标识符，而不会传递给内部 API。
> 
> 在前端读取参数后，对参数值字符串进行 URL 解码时，取出攻击者注入的参数。最后发送到内部 API。

检查响应中是否有查询被截断的线索。例如，如果响应返回用户 `peter`，则服务端查询可能已被截断。如果返回 `Invalid name` 错误消息，则应用程序可能将 `foo` 视为用户名的一部分（`peter%23foo`），这表明服务端请求可能未被截断。

如果你能够截断服务端请求，就消除了 `publicProfile` 字段必须为 true 的要求，你可能能够利用此漏洞返回非公开用户资料。

### 注入无效参数

你可以使用 URL 编码的 `&` 字符尝试向服务端请求添加第二个参数。

例如，你可以将查询字符串修改为：

```http
GET /userSearch?name=peter%26foo=xyz&back=/home
```

这将产生以下对内部 API 的服务端请求：

```http
GET /users/search?name=peter&foo=xyz&publicProfile=true
```

检查响应以获取关于额外参数如何被解析的线索。例如，如果响应不变，可能表明参数被成功注入但被应用程序忽略。即，`foo=xyz` 被解析为参数，而非用户名的一部分 `name=peter%26foo=xyz`

要建立更完整的情况，你需要进一步测试。

### 注入有效与隐藏参数

如果你能够修改查询字符串，则可以尝试向服务端请求添加第二个有效参数。

> **相关页面**
> 有关如何识别可注入查询字符串的参数的信息，请参阅[API 测试 - 查找隐藏参数]部分。

例如，如果你识别了 `email` 参数，可以按如下方式将其添加到查询字符串：

```http
GET /userSearch?name=peter%26email=foo&back=/home
```

这将产生以下对内部 API 的服务端请求：

```http
GET /users/search?name=peter&email=foo&publicProfile=true
```

检查响应以获取关于额外参数如何被解析的线索。

### 覆盖现有参数

要确认应用程序是否易受服务端参数污染，你可以尝试覆盖原始参数。方法是通过注入一个同名的第二个参数。

例如，你可以将查询字符串修改为：

```http
GET /userSearch?name=peter%26name=carlos&back=/home
```

这将产生以下对内部 API 的服务端请求：

```http
GET /users/search?name=peter&name=carlos&publicProfile=true
```

内部 API 会解释两个 `name` 参数。这取决于应用程序如何处理第二个参数，不同 Web 技术的处理方式不同。例如：

- PHP 只解析最后一个参数，这将导致搜索用户 `carlos`。
- ASP.NET / IIS 将两个参数使用逗号合并，这将导致搜索 `peter,carlos`，可能产生 `Invalid username` 错误消息。
- Java Servlet/ Node.js / Express 只解析第一个参数，这将导致搜索用户 `peter`，结果不变。
- Python 所有出现值在列表 `name=['peter','carlos']`

如果你能够覆盖原始参数，则可能实施利用。例如，你可以向请求中添加 `name=administrator`，这可能使你能够以管理员用户身份登录。

> 除参数的原位置外，还测试其他参数前后，以及请求的不同位置（查询字符串、cookie和消息主体中）

## 测试 REST 路径中的服务端参数污染

RESTful API 可能将参数名称和值放在 URL 路径中，而非查询字符串中。例如，考虑以下路径：

`/api/users/123`

该 URL 路径可拆解如下：

- `/api` 是根 API 端点。
- `/users` 表示一个资源，此处为 `users`。
- `/123` 表示一个参数，此处为特定用户的标识符。

考虑一个允许你根据用户名编辑用户个人资料的应用程序。请求发送到以下端点：

```http
GET /edit_profile.php?name=peter
```

这将产生以下服务端请求：

```http
GET /api/private/users/peter
```

攻击者可能通过操纵服务端 URL 路径参数来利用 API。要测试此漏洞，请添加路径遍历序列以修改参数，并观察应用程序如何响应。

你可以提交 URL 编码的 `peter/../admin` 作为 `name` 参数的值：

```http
GET /edit_profile.php?name=peter%2f..%2fadmin
```

这可能产生以下服务端请求：

```http
GET /api/private/users/peter/../admin
```

如果服务端客户端或后端 API 对此路径进行规范化，则可能解析为 `/api/private/users/admin`。

> 应用路径遍历主题技巧，如：探测 `/./原路径` 当前目录，向上遍历探测另一个用户或资源 `原用户/../覆盖用户`，向上遍历读取/暴破文件 `/../../../../§目标文件§#` 
>
> 技巧，尝试向下与向上两个方向暴破路径名：
> - 向下暴破：考虑到 `功能/参数值` 格式，1层暴破或不足够，尝试两层作为名值（有效功能+任意参数值）
> - 向上暴破：以有效响应为 hit 触点，逐渐增加遍历序列探测更上层
>   - `../§测试路径§/有效路径`
>   - `../../§测试路径§/探测路径/有效路径`

## 测试结构化数据格式中的服务端参数污染

攻击者可能通过操纵参数，利用服务器处理其他结构化数据格式（如 JSON 或 XML）时的漏洞。要测试这一点，请将非预期的结构化数据注入用户输入，并观察服务器如何响应。

考虑一个允许用户编辑个人资料的应用程序，然后将更改通过请求发送到服务端 API。当你编辑姓名时，浏览器发出以下请求：

```http
POST /myaccount
name=peter
```

这将产生以下服务端请求：

```http
PATCH /users/7312/update
{"name":"peter"}
```

你可以尝试按如下方式向请求添加 `access_level` 参数：

```http
POST /myaccount
name=peter","access_level":"administrator
```

如果用户输入未经充分验证或清理便被添加到服务端 JSON 数据中，则会产生以下服务端请求：

```http
PATCH /users/7312/update
{"name":"peter","access_level":"administrator"}
```

这可能导致用户 `peter` 被授予管理员访问权限。

> **相关页面**
> 有关如何识别可注入查询字符串的参数的信息，请参阅[查找隐藏参数]部分。

考虑一个类似的示例，但客户端用户输入是 JSON 数据。当你编辑姓名时，浏览器发出以下请求：

```http
POST /myaccount
{"name": "peter"}
```

这将产生以下服务端请求：

```http
PATCH /users/7312/update
{"name":"peter"}
```

你可以尝试按如下方式向请求添加 `access_level` 参数：

```http
POST /myaccount
{"name": "peter\",\"access_level\":\"administrator"}
```

如果用户输入被解码后，未经充分编码便被添加到服务端 JSON 数据中，则会产生以下服务端请求：

```http
PATCH /users/7312/update
{"name":"peter","access_level":"administrator"}
```

同样，这可能导致用户 `peter` 被授予管理员访问权限。

结构化格式注入也可能发生在响应中。例如，如果用户输入被安全地存储在数据库中，然后未经充分编码便嵌入到后端 API 的 JSON 响应中，就可能发生这种情况。你通常可以像检测请求中的结构化格式注入一样，检测并利用响应中的此类注入。

> **注意**
> 以下示例使用 JSON，但服务端参数污染可发生在任何结构化数据格式中。XML 示例请参见 XML 外部实体（XXE）注入主题中的 [XInclude 攻击](https://portswigger.net/web-security/xxe#xinclude-attacks) 部分。

## 使用自动化工具测试

Burp 包含可帮助你检测服务端参数污染漏洞的自动化工具。

Burp Scanner 在执行审计时会自动检测可疑的输入转换。当应用程序接收用户输入、以某种方式转换后对结果进行进一步处理时，就会发生这种情况。此行为本身不一定构成漏洞，因此你需要使用上述手动技术进行进一步测试。更多信息，请参阅[可疑输入转换（反射）](https://portswigger.net/kb/issues/00400d00_suspicious-input-transformation-reflected) 问题定义。

你还可以使用 Backslash Powered Scanner BApp 来识别服务端注入漏洞。该扫描器将输入分类为“无聊”、“有趣”或“易受攻击”。你需要使用上述手动技术调查“有趣”的输入。更多信息，请参阅白皮书 [反斜杠驱动扫描：狩猎未知漏洞类别](https://portswigger.net/research/backslash-powered-scanning-hunting-unknown-vulnerability-classes)。

## 预防服务端参数污染

为防止服务端参数污染，请使用白名单定义无需编码的字符，并确保所有其他用户输入在包含到服务端请求之前都经过编码。同时确保所有输入都符合预期的格式和结构。
