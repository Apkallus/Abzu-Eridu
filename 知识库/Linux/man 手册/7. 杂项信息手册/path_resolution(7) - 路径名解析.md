# `path_resolution` - 路径名如何解析为文件

## 描述

某些 UNIX/Linux 系统调用将一个或多个文件名作为参数。文件名（或路径名）按如下方式解析。

### 步骤 1：解析过程的开始

如果路径名以 `/` 字符开头，则起始查找目录是调用进程的根目录。进程从父进程继承其根目录。通常这将是文件层次结构的根目录。进程可以通过使用 [chroot(2)] 系统调用获得不同的根目录，或者通过使用 [openat2(2)] 并设置 `RESOLVE_IN_ROOT` 标志来临时使用不同的根目录。

如果进程——或其祖先之一——是由设置了 `CLONE_NEWNS` 标志的 [clone(2)] 系统调用启动的，则该进程可能获得完全私有的挂载命名空间。这处理路径名中的 `/` 部分。

如果路径名不以 `/` 字符开头，则解析过程的起始查找目录是进程的当前工作目录——或者，对于 [openat(2)] 风格的系统调用，是 `dfd` 参数（如果 `AT_FDCWD` 作为 `dfd` 参数传入，则为当前工作目录）。当前工作目录从父进程继承，并可以通过 [chdir(2)] 系统调用更改。

以 `/` 字符开头的路径名称为绝对路径名。不以 `/` 开头的路径名称为相对路径名。

### 步骤 2：沿路径遍历

将当前查找目录设置为起始查找目录。现在，对于路径名的每个非最终组件（其中组件是由 `/` 字符分隔的子字符串），在当前查找目录中查找该组件。

如果进程对当前查找目录没有搜索权限，则返回 `EACCES` 错误（“权限被拒绝”）。

如果未找到该组件，则返回 `ENOENT` 错误（“没有那个文件或目录”）。

如果找到该组件，但它既不是目录也不是符号链接，则返回 `ENOTDIR` 错误（“不是目录”）。

如果找到该组件且它是目录，我们将当前查找目录设置为该目录，并转到下一个组件。

如果找到该组件且它是符号链接，我们首先解析该符号链接（以当前查找目录作为起始查找目录）。发生错误时，返回该错误。如果结果不是目录，则返回 `ENOTDIR` 错误。如果符号链接解析成功并返回目录，我们将当前查找目录设置为该目录，并转到下一个组件。注意，如果路径名的前缀（`dirname`）组件包含一个解析为目录的符号链接文件名（该目录的前缀组件可能包含符号链接，依此类推），则此处的解析过程可能涉及递归。为了保护内核免受栈溢出，并防止拒绝服务，对最大递归深度和跟随的符号链接最大数量都有限制。超过最大值时返回 `ELOOP` 错误（“符号链接层数过多”）。

目前在 Linux 上的实现中，解析路径名时最多跟随的符号链接数量为 40。在 Linux 2.6.18 之前，递归深度限制为 5。从 Linux 2.6.18 开始，此限制提高到 8。在 Linux 4.2 中，内核的路径名解析代码经过重构以消除递归的使用，因此唯一剩下的限制是整个路径名最多 40 次解析。

通过使用 [openat2(2)] 并设置 `RESOLVE_NO_SYMLINKS` 标志，可以阻止此阶段中的符号链接解析。

### 步骤 3：查找最终条目

路径名最终组件的查找与所有其他组件的查找一样，如上一节所述，但有两个不同之处：(i) 最终组件不必是目录（至少就路径解析过程而言——由于特定系统调用的要求，它可能必须是目录或非目录）；(ii) 如果未找到该组件，不一定就是错误——也许我们只是正在创建它。有关最终条目处理的详细信息，在特定系统调用的手册页中描述。

### `.` 和 `..`

按照惯例，每个目录都有条目 `.` 和 `..`，分别指向目录本身及其父目录。

路径解析过程将假定这些条目具有其传统含义，无论它们是否实际存在于物理文件系统中。

不能向上越过根目录：`/..` 与 `/` 相同。

### 挂载点

执行 `mount dev path` 命令后，路径名 `path` 指向设备 `dev` 上文件系统层次结构的根，而不再指向先前的任何内容。

可以走出已挂载的文件系统：`path/..` 指向 `path` 的父目录，位于 `dev` 上文件系统层次结构之外。

通过使用 [openat2(2)] 并设置 `RESOLVE_NO_XDEV` 标志，可以阻止遍历挂载点（但请注意，这也会限制绑定挂载的遍历）。

### 末尾斜杠

如果路径名以 `/` 结尾，这会强制按照步骤 2 解析前一个组件：斜杠之前的组件要么存在并解析为目录，要么命名一个在路径名解析后立即要创建的目录。否则，末尾的 `/` 会被忽略。

### 最终符号链接

如果路径名的最后一个组件是符号链接，则所引用的文件将是符号链接本身还是对其内容进行路径解析的结果，取决于系统调用。例如，系统调用 [lstat(2)] 将作用于符号链接，而 [stat(2)] 作用于符号链接所指向的文件。

### 长度限制

路径名有最大长度。如果路径名（或解析符号链接时获得的某个中间路径名）过长，则返回 `ENAMETOOLONG` 错误（“文件名过长”）。

### 空路径名

在最初的 UNIX 中，空路径名指向当前目录。如今 POSIX 规定空路径名不得成功解析。在这种情况下，Linux 返回 `ENOENT`。

### 权限

文件的权限位由三组三位组成；参见 [chmod(1)] 和 [stat(2)]。当调用进程的有效用户 ID 等于文件的所有者 ID 时，使用第一组三位。当文件的组 ID 等于调用进程的有效组 ID，或者是调用进程的补充组 ID 之一（由 [setgroups(2)] 设置）时，使用第二组三位。当两者都不成立时，使用第三组。

在使用的三位中，第一位确定读权限，第二位确定写权限，最后一位在普通文件情况下确定执行权限，在目录情况下确定搜索权限。

Linux 在权限检查中使用 `fsuid` 而不是有效用户 ID。通常 `fsuid` 等于有效用户 ID，但 `fsuid` 可以通过系统调用 [setfsuid(2)] 更改。

（这里“`fsuid`”表示类似“文件系统用户 ID”的东西。这个概念是在进程可以向具有相同有效用户 ID 的进程发送信号的时期，为实现用户空间 NFS 服务器而需要的。它现在已过时。没有人应该使用 [setfsuid(2)]。）

类似地，Linux 使用 `fsgid`（“文件系统组 ID”）而不是有效组 ID。参见 [setfsgid(2)]。

### 绕过权限检查：超级用户与能力

在传统的 UNIX 系统上，超级用户（`root`，用户 ID 0）拥有全部权力，并在访问文件时绕过所有权限限制。

在 Linux 上，超级用户特权被划分为能力（参见 [capabilities(7)]）。有两个能力与文件权限检查相关：`CAP_DAC_OVERRIDE` 和 `CAP_DAC_READ_SEARCH`。（如果进程的 `fsuid` 为 0，则它具有这些能力。）

`CAP_DAC_OVERRIDE` 能力覆盖所有权限检查，但仅当文件的三个执行权限位中至少有一个被设置时才授予执行权限。

`CAP_DAC_READ_SEARCH` 能力授予对目录的读和搜索权限，以及对普通文件的读权限。
