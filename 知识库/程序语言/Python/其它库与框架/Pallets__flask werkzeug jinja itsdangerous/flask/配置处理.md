# 配置处理

应用需要某种配置。你可能希望根据应用环境更改不同设置，例如切换调试模式、设置密钥以及其他与环境相关的设置。

Flask 的设计方式通常要求配置在应用启动时就可用。你可以将配置硬编码在代码中，对许多小型应用来说这其实并不算太糟，但还有更好的方式。

无论你如何加载配置，都会有一个保存已加载配置值的 `config` 对象可用：`Flask` 对象的 `config` 属性。这里既是 Flask 自身放置某些配置值的地方，也是扩展放置其配置值的地方。同时，你也可以在这里放置自己的配置。

## 配置基础

`config` 实际上是字典的子类，可以像任何字典一样修改：

```py
app = Flask(__name__)
app.config['TESTING'] = True
```

某些配置值也会转发到 `Flask` 对象，因此你可以从那里读取和写入它们：

```py
app.testing = True
```

要一次更新多个键，可以使用 `dict.update()` 方法：

```py
app.config.update(
    TESTING=True,
    SECRET_KEY='192b9bdd22ab9ed4d12e236c78afcb9a393ec15f71bbf5dc987d54727823bcbf'
)
```

## 调试模式

`DEBUG` 配置值比较特殊，因为如果在应用开始设置之后更改它，其行为可能不一致。为了可靠地设置调试模式，请在 `flask` 或 `flask run` 命令上使用 `--debug` 选项。`flask run` 在调试模式下默认会使用交互式调试器和重载器。

```console
$ flask --app hello run --debug
```

建议使用该选项。虽然可以在配置或代码中设置 `DEBUG`，但强烈不建议这样做。`flask run` 命令无法提前读取它，而且某些系统或扩展可能已经根据先前的值完成了自身配置。

## 内置配置值

以下配置值由 Flask 内部使用：

- `DEBUG`  
    是否启用调试模式。使用 `flask run` 启动开发服务器时，未处理异常会显示交互式调试器，代码更改时服务器会重新加载。`debug` 属性映射到此配置键。该值由 `FLASK_DEBUG` 环境变量设置。如果在代码中设置，可能不会按预期工作。
    
    **请勿在生产部署中启用调试模式。**
    
    默认：`False`

- `TESTING`  
    启用测试模式。异常会被传播，而不是由应用的错误处理器处理。扩展也可能改变其行为以便于测试。你应该在自己的测试中启用它。
    
    默认：`False`

- `PROPAGATE_EXCEPTIONS`  
    异常会被重新抛出，而不是由应用的错误处理器处理。如果未设置，则在启用 `TESTING` 或 `DEBUG` 时隐式为 true。
    
    默认：`None`

- `TRAP_HTTP_EXCEPTIONS`  
    如果没有针对 `HTTPException` 类型异常的处理程序，则重新抛出该异常，交由交互式调试器处理，而不是将其作为简单错误响应返回。
    
    默认：`False`

- `TRAP_BAD_REQUEST_ERRORS`  
    尝试从 `args` 和 `form` 等请求字典中访问不存在的键时，会返回 400 Bad Request 错误页面。启用此项可将该错误视为未处理异常，从而进入交互式调试器。这是 `TRAP_HTTP_EXCEPTIONS` 的更具体版本。如果未设置，则在调试模式下启用。
    
    默认：`None`

- `SECRET_KEY`  
    用于安全签名会话 cookie 的密钥，也可供扩展或应用用于任何其他安全相关需求。它应是较长的随机 `bytes` 或 `str`。例如，将以下命令的输出复制到配置中：
    
    ```console
    $ python -c 'import secrets; print(secrets.token_hex())'
    '192b9bdd22ab9ed4d12e236c78afcb9a393ec15f71bbf5dc987d54727823bcbf'
    ```
    
    **在发布问题或提交代码时不要泄露密钥。**
    
    默认：`None`

- `SECRET_KEY_FALLBACKS`  
    旧密钥列表，这些密钥仍可用于取消签名。这允许项目实现密钥轮换，而不会使活动会话或其他最近签名的机密失效。
    
    应在一段适当时间后移除密钥，因为检查每个额外密钥都会增加一些开销。
    
    顺序无关紧要，但默认实现会先测试列表中的最后一个密钥，因此按从旧到新排序可能更合理。
    
    Flask 内置的安全 cookie 会话支持此功能。使用 `SECRET_KEY` 的扩展可能尚不支持。
    
    默认：`None`
    
    *在 3.1 版本中新增。*

- `SESSION_COOKIE_NAME`  
    会话 cookie 的名称。如果你已经有一个同名 cookie，可以更改它。
    
    默认：`'session'`

- `SESSION_COOKIE_DOMAIN`  
    会话 cookie 上 `Domain` 参数的值。如果未设置，浏览器只会将 cookie 发送到设置它的确切域名。否则，它们还会将其发送到给定值的任何子域名。
    
    不设置此值比设置它限制更强、更安全。
    
    默认：`None`
    
    > **警告**
    >
    > 如果在浏览器创建了使用一种设置的 cookie 之后更改此值，可能会导致创建另一个 cookie。浏览器可能以未定义的顺序发送两者。在这种情况下，你可能还需要更改 `SESSION_COOKIE_NAME`，或以其他方式使旧会话失效。
    
    *在 2.3 版本中更改：默认不设置，且不回退到 `SERVER_NAME`。*

- `SESSION_COOKIE_PATH`  
    会话 cookie 有效的路径。如果未设置，cookie 将在 `APPLICATION_ROOT` 下有效；如果后者也未设置，则在 `/` 下有效。
    
    默认：`None`

- `SESSION_COOKIE_HTTPONLY`  
    出于安全考虑，浏览器不允许 JavaScript 访问标记为“HTTP only”的 cookie。
    
    默认：`True`

- `SESSION_COOKIE_SECURE`  
    如果 cookie 标记为“secure”，浏览器只会通过 HTTPS 发送该 cookie。应用必须通过 HTTPS 提供服务，此设置才有意义。
    
    默认：`False`

- `SESSION_COOKIE_PARTITIONED`  
    浏览器将根据顶级文档的域名发送 cookie，而不仅仅是设置 cookie 的文档域名。这可以防止在 iframe 中设置的第三方 cookie 在独立站点之间“泄漏”。
    
    浏览器开始禁止非分区的第三方 cookie，因此如果你希望 cookie 在此类嵌入场景中正常工作，需要将其标记为分区。
    
    启用此项会隐式启用 `SESSION_COOKIE_SECURE`，因为它仅在通过 HTTPS 提供服务时有效。
    
    默认：`False`
    
    *在 3.1 版本中新增。*

- `SESSION_COOKIE_SAMESITE`  
    限制从外部站点发起的请求中如何发送 cookie。可以设置为 `'Lax'`（推荐）或 `'Strict'`。参见 `Set-Cookie options`。
    
    默认：`None`
    
    *在 1.0 版本中新增。*

- `PERMANENT_SESSION_LIFETIME`  
    如果 `session.permanent` 为 true，则 cookie 的过期时间将设置为未来这么多秒。可以是 `datetime.timedelta` 或 `int`。
    
    Flask 的默认 cookie 实现会验证加密签名不早于该值。
    
    默认：`timedelta(days=31)`（`2678400` 秒）

- `SESSION_REFRESH_EACH_REQUEST`  
    当 `session.permanent` 为 true 时，控制是否在每个响应中都发送 cookie。每次发送 cookie（默认）可以更可靠地防止会话过期，但会使用更多带宽。非永久会话不受影响。
    
    默认：`True`

- `USE_X_SENDFILE`  
    提供文件时，设置 `X-Sendfile` 头，而不是由 Flask 提供数据。某些 Web 服务器（如 Apache）会识别该头并更高效地提供数据。仅在使用此类服务器时才有意义。
    
    默认：`False`

- `SEND_FILE_MAX_AGE_DEFAULT`  
    提供文件时，将缓存控制 max age 设置为该秒数。可以是 `datetime.timedelta` 或 `int`。可通过应用或蓝图上的 `get_send_file_max_age()` 按文件覆盖此值。
    
    如果为 `None`，`send_file` 会告诉浏览器使用条件请求，而不是基于时间的缓存，这通常更可取。
    
    默认：`None`

- `TRUSTED_HOSTS`  
    根据这些受信任值验证 `Request.host` 及其他使用它的属性。如果主机无效，则引发 `SecurityError`，导致 400 错误。如果为 `None`，所有主机都有效。每个值要么是精确匹配，要么可以以点 `.` 开头以匹配任何子域名。
    
    验证在路由期间针对此值进行。`before_request` 和 `after_request` 回调仍会被调用。
    
    默认：`None`
    
    *在 3.1 版本中新增。*

- `SERVER_NAME`  
    告知应用它绑定到的主机和端口。
    
    如果启用了 `subdomain_matching`，则必须设置，以便能够从请求中提取子域名。
    
    必须在请求上下文之外由 `url_for` 生成外部 URL 时设置。
    
    默认：`None`
    
    *在 3.1 版本中更改：对于 `subdomain_matching` 和 `host_matching`，都不再将请求限制为仅此域名。*
    
    *在 2.3 版本中更改：不影响 `SESSION_COOKIE_DOMAIN`。*
    
    *在 1.0 版本中更改：不会隐式启用 `subdomain_matching`。*

- `APPLICATION_ROOT`  
    告知应用它由应用/Web 服务器挂载在什么路径下。这用于在请求上下文之外生成 URL（在请求内，调度器负责设置 `SCRIPT_NAME`；有关调度配置示例，参见 `Application Dispatching`）。
    
    如果未设置 `SESSION_COOKIE_PATH`，将用于会话 cookie 路径。
    
    默认：`'/'`

- `PREFERRED_URL_SCHEME`  
    在非请求上下文中生成外部 URL 时使用此 scheme。
    
    默认：`'http'`

- `MAX_CONTENT_LENGTH`  
    在此请求期间将读取的最大字节数。如果超过此限制，会引发 413 `RequestEntityTooLarge` 错误。如果设置为 `None`，Flask 应用级别不强制执行限制。但是，如果为 `None` 且请求没有 `Content-Length` 头，并且 WSGI 服务器未指示它会终止流，则不会读取任何数据，以避免无限流。
    
    每个请求默认使用此配置。可以在特定 `Request.max_content_length` 上设置，以将限制应用于该特定视图。应根据应用或视图的具体需求适当设置。
    
    默认：`None`
    
    *在 0.6 版本中新增。*

- `MAX_FORM_MEMORY_SIZE`  
    `multipart/form-data` 正文中任何非文件表单字段可能具有的最大字节数。如果超过此限制，会引发 413 `RequestEntityTooLarge` 错误。如果设置为 `None`，Flask 应用级别不强制执行限制。
    
    每个请求默认使用此配置。可以在特定 `Request.max_form_memory_parts` 上设置，以将限制应用于该特定视图。应根据应用或视图的具体需求适当设置。
    
    默认：`500_000`
    
    *在 3.1 版本中新增。*

- `MAX_FORM_PARTS`  
    `multipart/form-data` 正文中可能存在的最大字段数。如果超过此限制，会引发 413 `RequestEntityTooLarge` 错误。如果设置为 `None`，Flask 应用级别不强制执行限制。
    
    每个请求默认使用此配置。可以在特定 `Request.max_form_parts` 上设置，以将限制应用于该特定视图。应根据应用或视图的具体需求适当设置。
    
    默认：`1_000`
    
    *在 3.1 版本中新增。*

- `TEMPLATES_AUTO_RELOAD`  
    模板更改时重新加载。如果未设置，则在调试模式下启用。
    
    默认：`None`

- `EXPLAIN_TEMPLATE_LOADING`  
    记录调试信息，追踪模板文件的加载方式。这对于弄清楚模板为何未加载或似乎加载了错误文件很有用。
    
    默认：`False`

- `MAX_COOKIE_SIZE`  
    如果 cookie 头大于此字节数，则发出警告。默认 `4093`。较大的 cookie 可能会被浏览器静默忽略。设置为 `0` 可禁用警告。

- `PROVIDE_AUTOMATIC_OPTIONS`  
    设置为 `False` 可禁用自动添加 OPTIONS 响应。可以通过更改 `provide_automatic_options` 属性按路由覆盖此设置。
    
    *在 3.10 版本中新增：新增 `PROVIDE_AUTOMATIC_OPTIONS` 以控制自动生成的 OPTIONS 响应是否默认添加。*

**变更日志**

- 在 3.10 版本中新增：新增 `PROVIDE_AUTOMATIC_OPTIONS` 以控制自动生成的 OPTIONS 响应是否默认添加。
- 在 2.3 版本中更改：移除了 `JSON_AS_ASCII`、`JSON_SORT_KEYS`、`JSONIFY_MIMETYPE` 和 `JSONIFY_PRETTYPRINT_REGULAR`。默认的 `app.json` 提供器改为具有等效属性。

## 从 Python 文件配置

如果能将配置存储在单独文件中，最好位于实际应用包之外，配置会更有用。你可以部署应用，然后针对特定部署单独配置它。

常见模式如下：

```py
app = Flask(__name__)
app.config.from_object('yourapplication.default_settings')
app.config.from_envvar('YOURAPPLICATION_SETTINGS')
```

这首先从 `yourapplication.default_settings` 模块加载配置，然后用 `YOURAPPLICATION_SETTINGS` 环境变量指向的文件内容覆盖这些值。可以在启动服务器前在 shell 中设置该环境变量：

**Bash**

```console
$ export YOURAPPLICATION_SETTINGS=/path/to/settings.cfg
$ flask run
 * Running on http://127.0.0.1:5000/
```

**Fish**

```console
$ set -x YOURAPPLICATION_SETTINGS /path/to/settings.cfg
$ flask run
 * Running on http://127.0.0.1:5000/
```

**CMD**

```console
> set YOURAPPLICATION_SETTINGS=\path\to\settings.cfg
> flask run
 * Running on http://127.0.0.1:5000/
```

**Powershell**

```console
> $env:YOURAPPLICATION_SETTINGS = "\path\to\settings.cfg"
> flask run
 * Running on http://127.0.0.1:5000/
```

配置文件本身是实际的 Python 文件。只有大写的值最终才会存储在配置对象中。因此请确保配置键使用大写字母。

以下是一个配置文件示例：

```py
# 示例配置
SECRET_KEY = '192b9bdd22ab9ed4d12e236c78afcb9a393ec15f71bbf5dc987d54727823bcbf'
```

请确保尽早加载配置，以便扩展在启动时能够访问配置。配置对象还有其他方法可以从单个文件加载。完整参考请阅读 `Config` 对象的文档。

## 从数据文件配置

也可以使用 `from_file()` 从你选择格式的文件中加载配置。例如，从 TOML 文件加载：

```py
import tomllib
app.config.from_file("config.toml", load=tomllib.load, text=False)
```

或者从 JSON 文件：

```py
import json
app.config.from_file("config.json", load=json.load)
```

## 从环境变量配置

除了使用环境变量指向配置文件外，你可能会发现直接通过环境变量控制配置值很有用（或必要）。Flask 可以使用 `from_prefixed_env()` 指示将所有以特定前缀开头的环境变量加载到配置中。

可以在启动服务器前在 shell 中设置环境变量：

**Bash**

```console
$ export FLASK_SECRET_KEY="5f352379324c22463451387a0aec5d2f"
$ export FLASK_MAIL_ENABLED=false
$ flask run
 * Running on http://127.0.0.1:5000/
```

**Fish**

```console
$ set -x FLASK_SECRET_KEY "5f352379324c22463451387a0aec5d2f"
$ set -x FLASK_MAIL_ENABLED false
$ flask run
 * Running on http://127.0.0.1:5000/
```

**CMD**

```console
> set FLASK_SECRET_KEY="5f352379324c22463451387a0aec5d2f"
> set FLASK_MAIL_ENABLED=false
> flask run
 * Running on http://127.0.0.1:5000/
```

**Powershell**

```console
> $env:FLASK_SECRET_KEY = "5f352379324c22463451387a0aec5d2f"
> $env:FLASK_MAIL_ENABLED = "false"
> flask run
 * Running on http://127.0.0.1:5000/
```

然后可以通过配置加载并访问这些变量，键等于去掉前缀后的环境变量名，即

```py
app.config.from_prefixed_env()
app.config["SECRET_KEY"]  # 为 "5f352379324c22463451387a0aec5d2f"
```

前缀默认为 `FLASK_`。这可以通过 `from_prefixed_env()` 的 `prefix` 参数配置。

值会被解析，以尝试将其转换为比字符串更具体的类型。默认使用 `json.loads()`，因此任何有效的 JSON 值都可能，包括列表和字典。这可以通过 `from_prefixed_env()` 的 `loads` 参数配置。

使用默认 JSON 解析添加布尔值时，只有小写的“true”和“false”是有效值。请记住，Python 中任何非空字符串都被视为 `True`。

可以通过用双下划线（`__`）分隔键来设置嵌套字典中的键。父字典中不存在的任何中间键都会初始化为空字典。

```console
$ export FLASK_MYAPI__credentials__username=user123
```

```py
app.config["MYAPI"]["credentials"]["username"]  # 为 "user123"
```

在 Windows 上，环境变量键始终为大写，因此上述示例最终会变为 `MYAPI__CREDENTIALS__USERNAME`。

如需更多配置加载功能，包括合并和 Windows 大小写不敏感支持，可尝试 [Dynaconf](https://www.dynaconf.com/) 等专用库，它包含 Flask 集成。

## 配置最佳实践

前面提到的方法的缺点是会使测试稍微困难一些。通常没有 100% 的单一解决方案，但你可以记住以下几点来改善体验：

1. 在函数中创建应用并在其上注册蓝图。这样你可以创建多个附加不同配置的应用实例，使单元测试容易得多。你可以使用它在需要时传入配置。
2. 不要编写在导入时需要配置的代码。如果限制自己仅在请求中访问配置，就可以根据需要稍后重新配置对象。
3. 确保尽早加载配置，以便扩展在调用 `init_app` 时能够访问配置。

## 开发 / 生产

大多数应用需要不止一种配置。至少应该为生产服务器和开发期间使用的配置分别设置。处理此问题的最简单方法是使用始终加载并纳入版本控制的默认配置，以及一个根据需要覆盖值的单独配置，如上面的示例所示：

```py
app = Flask(__name__)
app.config.from_object('yourapplication.default_settings')
app.config.from_envvar('YOURAPPLICATION_SETTINGS')
```

然后你只需添加一个单独的 `config.py` 文件，并导出 `YOURAPPLICATION_SETTINGS=/path/to/config.py`，就完成了。不过也有其他方式。例如，你可以使用导入或子类化。

Django 世界中非常流行的一种做法是在配置文件中显式导入：在文件顶部添加 `from yourapplication.default_settings import *`，然后手动覆盖更改。你也可以检查类似 `YOURAPPLICATION_MODE` 的环境变量，将其设置为 `production`、`development` 等，并据此导入不同的硬编码文件。

另一个有趣的模式是使用类和继承进行配置：

```py
class Config(object):
    TESTING = False

class ProductionConfig(Config):
    DATABASE_URI = 'mysql://user@localhost/foo'

class DevelopmentConfig(Config):
    DATABASE_URI = "sqlite:////tmp/foo.db"

class TestingConfig(Config):
    DATABASE_URI = 'sqlite:///:memory:'
    TESTING = True
```

要启用这样的配置，只需调用 `from_object()`：

```py
app.config.from_object('configmodule.ProductionConfig')
```

注意 `from_object()` 不会实例化类对象。如果你需要实例化类，例如访问属性，则必须在调用 `from_object()` 之前完成：

```py
from configmodule import ProductionConfig
app.config.from_object(ProductionConfig())

# 或者，通过字符串导入：
from werkzeug.utils import import_string
cfg = import_string('configmodule.ProductionConfig')()
app.config.from_object(cfg)
```

实例化配置对象后，你可以在配置类中使用 `@property`：

```py
class Config(object):
    """基础配置，使用暂存数据库服务器。"""
    TESTING = False
    DB_SERVER = '192.168.1.56'

    @property
    def DATABASE_URI(self):  # 注意：全部大写
        return f"mysql://user@{self.DB_SERVER}/foo"

class ProductionConfig(Config):
    """使用生产数据库服务器。"""
    DB_SERVER = '192.168.19.32'

class DevelopmentConfig(Config):
    DB_SERVER = 'localhost'

class TestingConfig(Config):
    DB_SERVER = 'localhost'
    DATABASE_URI = 'sqlite:///:memory:'
```

有很多不同的方式，如何管理配置文件取决于你。不过以下是一些好的建议：

- 将默认配置保留在版本控制中。可以用此默认配置填充配置，或在你自己的配置文件中导入它，然后覆盖值。
- 使用环境变量在配置之间切换。这可以在 Python 解释器之外完成，使开发和部署容易得多，因为你可以快速轻松地在不同配置之间切换，而完全无需修改代码。如果你经常处理不同项目，甚至可以创建自己的脚本，用于激活 virtualenv 并为你导出开发配置。
- 使用 [fabric](https://www.fabfile.org/) 等工具将代码和配置分别推送到生产服务器。

## 实例文件夹

Flask 0.8 引入了实例文件夹。长期以来，Flask 可以直接引用相对于应用文件夹的路径（通过 `Flask.root_path`）。许多开发者也通过这种方式加载存储在应用旁边的配置。然而不幸的是，这只有在应用不是包时才工作良好；如果应用是包，根路径会指向包的内容。

Flask 0.8 引入了一个新属性：`Flask.instance_path`。它指的是一个称为“实例文件夹”的新概念。实例文件夹被设计为不纳入版本控制，并且特定于部署。它是放置运行时更改的内容或配置文件的完美位置。

你可以在创建 Flask 应用时显式提供实例文件夹的路径，也可以让 Flask 自动检测实例文件夹。要显式配置，请使用 `instance_path` 参数：

```py
app = Flask(__name__, instance_path='/path/to/instance/folder')
```

请记住，提供时此路径**必须**是绝对路径。

如果未提供 `instance_path` 参数，则使用以下默认位置：

- 未安装的模块：
    
    ```text
    /myapp.py
    /instance
    ```

- 未安装的包：
    
    ```text
    /myapp
        /__init__.py
    /instance
    ```

- 已安装的模块或包：
    
    ```text
    $PREFIX/lib/pythonX.Y/site-packages/myapp
    $PREFIX/var/myapp-instance
    ```
    
    `$PREFIX` 是 Python 安装的前缀。它可以是 `/usr` 或你的 virtualenv 路径。你可以打印 `sys.prefix` 的值来查看前缀设置为什么。

由于配置对象支持从相对文件名加载配置文件，我们使得在需要时可以将通过文件名加载改为相对于实例路径。可以通过应用构造函数的 `instance_relative_config` 开关，在“相对于应用根目录”（默认）和“相对于实例文件夹”之间翻转配置文件中相对路径的行为：

```py
app = Flask(__name__, instance_relative_config=True)
```

以下是一个完整示例，展示如何配置 Flask 从模块预加载配置，然后在实例文件夹中的文件存在时从中覆盖配置：

```py
app = Flask(__name__, instance_relative_config=True)
app.config.from_object('yourapplication.default_settings')
app.config.from_pyfile('application.cfg', silent=True)
```

实例文件夹的路径可以通过 `Flask.instance_path` 找到。Flask 还提供了使用 `Flask.open_instance_resource()` 从实例文件夹打开文件的快捷方式。

两者用法示例：

```py
filename = os.path.join(app.instance_path, 'application.cfg')
with open(filename) as f:
    config = f.read()

# 或者通过 open_instance_resource：
with app.open_instance_resource('application.cfg') as f:
    config = f.read()
```
